# v1.0.2 release report — expected-failure accounting (measured; re-measure at final qualification)

**What this is.** Dave's instruction of 2026-10-08 07:09 MST, item 2: *"Correct the release report's expected-failure
accounting now. The 31 marks failing for a different reason are masked coverage, not proof of their named defects.
Separate those counts explicitly. Do not broaden or add marks to absorb failures."* No v1.0.2 release report exists
yet; it is written at final qualification, as `docs/QUALIFICATION-<sha>.md` was for earlier releases. This file is that
report's expected-failure section, written now. The release report carries it forward, re-measured on the final
candidate. Ruling C4 (`D-IMPL-378`, `b1c9c3fc`) requires the twelve frozen-family quarantines to be listed by name;
they are in section 3.

**What was measured, and how.** The tree is `dl-378-integ` at `72bb194a`. The reconciliation merge `8cfe77b2` changed
only `docs/DECISIONS.md`, so `src/`, `runtime/`, `tests/` and `examples/` are byte-identical in both.
- **Hosted counts:** run 37777928428 — quick suite 6 expected failures, Postgres leg 93, Fluree leg 12.
- **By name:** the hosted logs print counts only, so a throwaway diagnostic branch (`diag-378-xfail-accounting`, never
  merged) ran the Postgres and Fluree legs exactly as CI does, with every expected failure reported by test id (run
  37793705373). It reproduced the 93 and the 12.
- **Each marked test's first real failure:** the same legs ran again with `--runxfail`, which ignores the marks, so
  each marked test fails on whatever it reaches first. Postgres: run 37796334071, on fresh service containers. (Run
  37793705373 ran this step on the same container right after the plain leg; four seeding tests then saw doubled rows,
  so its Postgres step was redone clean.) Fluree: run 37793705373. Quick suite: run locally, because it needs no
  database.
- **The rule.** A marked test *fails on its named defect* when its first real failure is a defect its mark's reason
  names. Otherwise it is **masked**: it fails first on something else, so its expected failure proves nothing about
  the defect it is marked for.

**No mark was added, removed, broadened or edited** by this accounting.

  or D-08 for the nine cp-04 tests. Those tests stop before reaching what they were written to show.

  after D-GATE-24.7". `D-GATE-24.7` is recorded as APPROVED and CLOSED in `docs/DECISIONS.md`, yet the marks remain.
  Un-quarantining now would fail on SEC353-G-07 first. Lifting them waits for the frozen family's bare-key repair,
  which `D-IMPL-355` Option A keeps out of scope.
- **Two marks are non-strict**, and both tests run in CI:
  - the s1-00 configuration-equivalence test (quick suite);
  - the cp-04 two-caller test listed in section 5 (Postgres and Fluree legs).
  A non-strict mark does not turn CI red if its test starts passing.
- **Four of the masked tests are example-level checks that a withheld or suppressed subject cannot be told from a
  missing one:** cp-01 `test_a_suppressed_entity_leaves_no_marker` and
  `test_cpr_g08_a_principal_matching_no_entity_is_refused_and_cannot_be_told_from_a_missing_one`, cp-02
  `test_a_suppressed_facility_is_indistinguishable_from_a_missing_one`, and cp-03
  `test_ofs_g15_suppression_is_indistinguishable_from_absence`. They currently prove nothing. SEC-020's evidence comes
  from the SDK's own closing test (`tests/products/test_sec020_combined_proof.py` on `lane-378b-s020proof`), not from
  them.
- **Not counted here:** the 59 marked Postgres tests and 59 marked Fluree tests that CI skips before their mark
  applies, because they read the curated estate. Their marks are untested in CI either way.
