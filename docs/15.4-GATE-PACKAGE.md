## 1. What was delivered

- **`ccf.graph.registry`** — one registration record, two discovery sources
  (the adapter package on disk for built-ins, the `ccf.graph_backends`
  entry-point group for third parties), one resolution path, and fail-closed
  refusals for unknown, duplicate and reserved names. Twelve public names.
  Discovery reads packaging metadata and imports nothing; `resolve()` imports
  exactly the one adapter a deployment named.
- **Six per-backend write modules** at `src/ccf/graph/backends/<name>_write.py`.
  `src/ccf/graph/_writer.py` went from 3,215 lines to 935 and imports no
  backend — importing it pulls no substrate module into `sys.modules`. That is
  the change that turns the D-IMPL-93 dependency arrow around.
- **Six typed connection contracts**, one per adapter, each declaring what that
  adapter requires. The hand-maintained substrate-to-required-argument table in
  the wiring layer is gone; both of its refusals are now the adapter's own
  contract's — a required field, and the inherited `extra="forbid"`.
- **The public API break, with its migration note.** `boot()` went from sixteen
  keyword arguments — eleven per-database, with the substrate chosen by asking
  which was not `None` — to eight, none of which names a database.
  `load_and_boot()` went to four. The eleven-row connection-key mapping is in
  the `Migration` field of the `ccf.boot.boot` entry in
  `docs/SURFACE-CHANGES.md`, which is the D-15B condition.
- **Credentials by reference.** The manifest names an environment variable;
  boot resolves it; an unset or empty reference is refused, naming the variable
  and never its value. The one production environment read in `src/` is in the
  wiring layer.
- **Decision Replay dimension 2 pins the adapter** — name, version, and the
  *names* of the credential references in force. This is the first adapter pin
  in any replay dimension, not a widening of an existing one (correction C-02).
- **Two structural lint rules**, `cinv02-backend-import` and
  `cinv04-substrate-name`/`-prose`, running in `make lint` and in the always-on
  CI lint job. The D-IMPL-92 line-budget gate and its whole package were
  deleted in the same plan that registered them.
- **`ccf backends list` over `GET /backends`** — what the removed schema enum
  could never answer: what is installed *here*, third-party adapters included.
- **An out-of-tree proof adapter**, `tests/fixtures/ccf-demo-adapter`, a second
  installable distribution that registers through the entry-point group, boots
  a working fabric, honours single-writer across the boundary, and passes both
  conformance suites as an ordinary unmarked param.
- **WR-01 and WR-05 closed** (D-14).
- **`public/how-to/write-a-graph-backend-adapter.md`** — the published
  adapter-authoring guide.

### Test 3 — Generality

> *Does the change add capability that makes all future adapters cheaper,
> carrying no adapter-specific knowledge?*

**What the substrate gained.** A registration seam, and with it: a plugin
surface where none existed (`ccf.graph_backends` is this project's first entry
point); one typed-config declaration path an adapter fills in rather than a
core table an adapter is added to; one shared connection-validation wrapper

mechanism that is auditable where the old boot arguments were merely invisible;
and a replay pin that records which adapter answered, at which version, under

code.

The seam moved knowledge that was already declarative out of core files that
had to be edited per substrate, into the adapters that own it. That is the
whole of the generality claim, and it is deliberately not larger.

## 5. The deviation Dave is owed a line about (D-13)

**D-IMPL-93's own wording says `tools/lints/allowlist.yaml` governs exceptions
to the two new rules. It does not, and it cannot as written.**

Three independent reasons, each checkable:

1. `apply_allowlist` runs for `cinv01*` — the no-hardcoding rule — and nothing
   else. The path is structurally unreachable from an import rule.
2. The allowlist's `fingerprint` field is a hash of an offending *literal*.
   An import rule produces no literal to fingerprint.
3. Two written statements already in this repository say an import restriction
   with exceptions is not an invariant: `allowlist.yaml`'s own header, and
   `tools/lints/harness_imports.py`.

**Dave ruled: no allowlist for either new rule.** That is *stricter* than the
instruction it replaces — an exception becomes a reviewed code change rather
than a YAML line — which is the right direction for a structural invariant.
The ruling is written into `allowlist.yaml`'s header naming all three rule ids
with all three reasons, into the lint runner's module docstring where a reader
of `apply_allowlist` will meet it, and into both checkers. A standing test,
`test_neither_new_rule_can_reach_the_allowlist`, makes the structural half an
assertion rather than a one-time grep.

**This is a deliberate deviation from a written instruction, not an oversight,
and no carve-out was needed.** Both rules were registered exactly as written
and `make lint` was green on the first run after registration.
`SUBSTRATE_NAME_EXEMPT_PACKAGES` still holds its two argued entries — the
adapter package, and the similarity package whose reference vector index shares
a stem with one graph adapter — with a test asserting the count, so a third
entry is a decision somebody has to make on purpose.

### Three residuals this phase created

**1. A dynamic import is invisible to an import lint.** `resolve()` imports the
named adapter through `importlib.import_module`, which an AST import rule
cannot see. The claim strength is stated in the checker's docstring as *no
unforced path exists*, never *no path exists*. The compensating control is
confinement to a single call site in `ccf.graph.registry`, asserted by
`test_exactly_one_dynamic_import_site_exists_across_both_linted_trees`, which
scans `src/` **and** `runtime/` — the same two trees the rule is scoped to, so
the control is exactly as wide as the rule.

**2. The CINV-02 lints are scoped to this repository's core, so they do not
walk a third-party adapter.** That is a scope statement, not a hole: the
invariant does not rest on the lint. It rests on `mint_boot_token` refusing a
second live writer per graph identity, which is asserted across the boundary by
booting the out-of-tree adapter twice on one graph name and once on two.

**3. `cinv02-graph-writer`'s reach narrowed in one respect, and this is where
that is said out loud.** `BackendRegistration.make_writer` is a public field on
a public frozen record returned by the public `resolve()`. A core module can
therefore now obtain a writer *constructor* without importing a guarded write
module. D-01's argument is that the lint keeps its exact present shape, and it
does — but the set of ways to reach a writer factory got wider, and a widening
nobody wrote down is the kind of thing a later phase discovers as a surprise.

What holds instead, and a reader can run it:
`tests/graph/test_backend_registry.py::test_every_make_writer_call_site_is_the_composition_root`
asserts that every `make_writer` **call** site under `src/` and `runtime/` is in
`src/ccf/boot.py`. And the boot-token mint still refuses a second live writer
per graph identity.

**The disagreement is recorded rather than lost.** The plan-stage cross-AI
review split on this residual. One reviewer called the AST call-site test "a
sophisticated and appropriate compensating control" and rated it LOW; another
rated it the phase's highest risk and wanted a static lint rule flagging any
`make_writer` attribute access outside `boot.py`. The test stands, for a stated
reason: attribute access on a value returned by a function is not reliably
decidable statically — the record can be bound, passed, aliased or unpacked —
so a lint rule would be either trivially evadable or noisy, while the test
already walks both linted trees and finds every call site. A reader who
disagrees should be able to see the argument and not have to rediscover the
disagreement.

## 9. Discretionary choices, recorded here rather than as decision-log entries

Following the I.2 precedent. Each was the planner's or the executor's call.

- **The entry-point group name is `ccf.graph_backends`.** This project's first
  entry point, so the name is new ground rather than an extension of a pattern.
- **Built-in adapters are discovered in-package, not through entry points.**
  Ruled on a measured result: a repo-root `*.egg-info` shadows the installed
  `dist-info` whenever `.` is on `sys.path`, and a stale editable install can
  hide an adapter. Reading the adapter package's directory is a disk read, so
  neither failure mode can reach it, and a built-in can never be shadowed by an
  installed distribution.
- **The adapter pin travels on `FabricHandle`.** The handle has until now
  carried capabilities and no state a caller could misuse; it now carries a
  fact. Named in the class docstring rather than slipped in.
- **`GET /backends` returns names, not versions or distribution names.** The
  registry knows both; the route returns neither, because a caller who learned
  them would have learned the deployment's dependency inventory. Asserted as
  `set(body) == {"backends"}`, which fails on any widening rather than on a
  list of fields somebody thought of.
- **Bad metadata from an unselected adapter fails every boot.** `resolve()`
  calls `declared_names()` first, so a duplicate, reserved or malformed name
  declared by *any* installed distribution refuses *every* boot — including a
  boot of a built-in that has nothing to do with the conflict. Ruled
  fail-closed, because the refusals are evidence that "which code does this
  name select" is ambiguous. The narrower alternative — degrade only the
  listing and that one name — is recorded in the registry's docstring as
  available later, with its own entry. The operability requirement that follows
  is a message requirement, and it is met: each refusal names the offending
  distribution and says the requested adapter was never reached, so an operator
  reads a packaging conflict rather than a missing adapter.
- **The demo fixture adapter installs with `make install`, always.** Opt-in was
  rejected for a concrete reason: plan 15.4-11's parity test asserts the
  conformance param lists and `declared_names()` agree in both directions, so
  an uninstalled `demo` makes `make ci-core` red for any developer who skipped
  an extra step — the proof would be conditional on a step nothing reminds
  anyone to take. **The accepted cost is visible in this deployment right now:**
  `ccf backends list` returns
  `["demo","fluree","memory","mongo","neo4j","postgres","sqlite"]` — a seventh
  name that is not a supported substrate. It is bounded because the fixture is
  not a dependency of the `ccf` distribution, and that is a test rather than a
  sentence.
- **One config-validation wrapper, `ccf.graph.registry.validate_connection`.**
  `boot()`, the manifest preflight and the V11 tests all call it and none of
  them formats a validation error itself. The alternative was three wrappers,
  and the specific hazard is that a hand-rolled one reaches for the exception's
  own rendering or the supplied value, which puts that value — on one path, a
  credential — back into the refusal. The one wrapper builds every line from
  the error's location and message, and raises outside the handler so the
  unsanitized cause is not even reachable on `__context__`.

## 11. Open rulings this phase surfaced and did not take

Three. Each is a decision rather than a defect, and none is fixable inside this
phase without falsifying its own headline measurement.

### 11.1 Six names an out-of-tree adapter must reach for are not exported

Found by plan 15.4-10 and classified programmatically against each module's
`__all__` rather than by eye:

| Name | Module |
|---|---|
| `materialize_view` | `ccf.graph.reader` — not in `__all__`; docstring says "graph-tier internal API" |
| `_ordered_view` | `ccf.graph.reader` — private |
| `_entity_records` | `ccf.graph.reader` — private |
| `_relationship_records` | `ccf.graph.reader` — private |
| `_LineageRowsFor` | `ccf.graph.reader` — private |
| `_GraphTxn` | `ccf.graph._writer` — private, in a private module |

**None is avoidable.** Ordering belongs to the interface rather than to an
answerer, so an adapter that sorted for itself would fork the convention the
shared helper exists to hold. Two of the six have no public counterpart at all,
so two history operations are unimplementable from public names.
`BaseGraphReader` *is* public but is SQL-shaped — it wants five SQL class
variables and a `_query(sql, params)`, which a dictionary store cannot supply.

**So both of these are true at once, and that is the finding.** D-11's claim
holds exactly as written — no line changed in `src/ccf` — *and* the surface a
third-party adapter reaches for is not the public surface. The published
authoring guide states the gap plainly rather than routing around it, which
raises rather than lowers the case for deciding it.

**The ruling wanted:** close the gap now (export the six, with the surface
entry and migration note that implies), or book it with an entry.

### 11.2 The `ccf` distribution name is taken on PyPI by an unrelated project

Measured during plan 15.4-10: `pip index versions ccf` reports an unrelated
project at 7.0.12. This repository's `ccf` is 0.1.0, private and unpublished.

The consequence lands on exactly the population the out-of-tree adapter exists
to represent: a third-party adapter's natural spelling is
`dependencies = ["ccf"]`, and in any environment without a local editable
install that resolves to somebody else's package rather than failing. The demo
fixture therefore declares **no** dependencies at all — with the reasoning at
the site and in its README — and relies on install ordering plus a loud
`ImportError`.

Nothing in this phase can fix it. It is a naming decision, and it is upstream
of anything an adapter author can do.

### 11.3 One error code is underscore-separated among seven hyphenated ones

The new HTTP error code is `backend_registry_conflict`. Every existing value in
the API's error-code vocabulary is hyphenated (`subject-conflict`,
`tenant-unauthorized`). Plan fidelity won during execution — the plan named the
literal and called it stable — and the inconsistency is recorded here rather
than resolved silently, because that module's own docstring says renaming a
code is a breaking change to every consumer.

**This is the cheap moment.** The code has never shipped in a release. If it is
to be hyphenated, now is the only time it costs nothing.

## 12. Two process observations worth recording

Neither is an execution error; both are planning-template defects that repeated
across the phase and will repeat again.

1. **Five consecutive plans listed a surface-change *fragment* in
   `files_modified` but not the assembled `docs/SURFACE-CHANGES.md` it
   regenerates.** The assembled log has a standing always-on staleness gate, so
   every one of those plans went red on its own diff and recorded the same
   deviation. Plans 15.4-02, -03, -04, -05, -06, -08 and -09 each hit it. The
   fix is one line in the plan template: a plan that writes a fragment also
   writes the assembled log.
2. **Four plans hit the same self-referential trap** — a docstring, comment or
   Makefile note that explains why a token is absent, failing the grep that
   asserts the token's absence. First the registry, then plan 15.4-06's
   forbidden-key comment, then plan 15.4-07's Makefile retirement note, then
   plan 15.4-09's CLI docstring. Each time the resolution was the same: describe
   the token rather than spelling it, and say in the text that that is what is
   happening. Worth a line in the planning guidance, because writing the
   criterion and the explanation as two independent acceptance criteria
   guarantees the contradiction.

## 13. What this package does not prove

Stated because the standing lesson of this project is that a gate which does
not say what it is blind to is how a defect class survives.

- **The lints measure direction and recurrence, not correctness.** `make lint`
  green says the core names no adapter and imports none. It says nothing about
  whether what the core does instead is right. The conformance suites, the four
  legs and the differential corpus are what carry that, and they are a bar the
  adapters agree on rather than a proof that the agreed answer is correct.
- **The zero-cost measurement is a fact about one diff over one range.** It
  says the substrate did not move while a seventh adapter arrived. It does not
  say the *next* adapter will cost nothing — only that the mechanism that used
  to make it cost something is gone, and that a lint now refuses the shape that
  made it cost something.
- **The citation gate checks anchored citations only.** §8 records what that
  leaves uncovered, measured.
- **`git diff --stat` gates nothing.** Every freeze and zero-cost check in this
  package is `--stat` for the record and `--quiet` for the gate, and the
  `--quiet` form is shown returning 1 over a range where the file did change.
  That pairing exists because the cross-AI review found the unpaired form in
  the plans.
- **No post-execution code review has run yet.** Phase 15.3's own gate was
  approved and then *withdrawn* when the code review that runs after the phase
  gate returned three verified Criticals. This package is the self-review and
  triage CLAUDE.md §3.1 steps 1–2 require, presented before approval; it is not
  a substitute for the review that follows.
