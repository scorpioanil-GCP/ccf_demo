Approver: Dave. Originally: Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.4 Step 4 vs §6.3 (INV-CH6-04). **D-IMPL-56 — where a skill's tool description and argument schema are declared. RESOLVED (Dave, 2026-07-27): the entry declares both, one shared derivation renders them into all three harnesses, and a fifth `procedure` skill type carries the Anthropic Agent Skills model through seam 1.** `SkillCatalogEntry` declares neither a human-readable description nor an argument schema, yet every one of the three v0 harness adapters needs both: Google ADK's `FunctionTool` and LangGraph's `StructuredTool` each want a description string and a typed argument model, and the Claude Agent SDK adapter wants the same fields to build its tool block. All three adapters surfaced the gap independently, which is the signal that it is not an adapter's problem. Plan 06-12 set the in-phase precedent and 06-13/06-14 followed it: compose the description from fields the entry already carries (name, skill type, binding identifiers) and transcribe `Agent.invoke_skill`'s `Mapping[str, str]` signature into one shared schema constant — deliberately *not* authoring prose in SDK code, which would breach the No-Hardcoding Rule (CLAUDE.md §6.4), and deliberately shared rather than per-adapter, because three adapters inventing three descriptions would break the D-18 portability equivalence 06-15 proves. That precedent is a workaround, not a resolution: what a skill is *for* is the deployment's statement, and the place it belongs is the skill-catalog artifact schema — a Control Plane decision (CLAUDE.md §6.2 channel 2, D-IMPL-12/D-IMPL-28), not an adapter's. **The question for Dave:** does `SkillCatalogEntry` gain optional `description` and `argument_schema` fields (making the tool surface a declared artifact property), or does the adapter-composed derivation become the ruled mechanism (making tool prose structurally SDK-derived, and identical across harnesses because one shared constant supplies it)? Consequence of leaving it open: every future adapter re-derives the same fields, and the first one to derive them differently silently breaks harness equivalence. Surfaced: 2026-07-27, plans 06-12/06-13/06-14, gate-assembled in 06-16. Originates: CLAUDE.md §6.2, §7.3 seam 2; `docs/PHASE_I3_GATE.md` §4.

**Dave's ruling (2026-07-27), four parts.** The question was asked as an either/or — declared artifact property *or* ruled adapter derivation — and the ruling takes the first, then extends past what was asked, because the goal Dave stated is broader than the gap the adapters surfaced: *skills must be transferable across the Claude Agent SDK, ADK and LangGraph, with the Anthropic Agent Skills model importable and CrewAI-style dynamic context binding available in the declaration.*

1. **`SkillCatalogEntry` gains a required `description` and a typed `argument_schema`; the adapter-composed derivation is retired, not kept as a fallback.** `description` is required rather than optional: what a skill is *for* is the deployment's statement, and silence is not the same statement as a declared value — the same D-IMPL-38 discipline `SkillRequirements` already applies to an empty-versus-absent frozenset. Optional-with-fallback was rejected specifically because a retained fallback is a retained divergence risk: described and undescribed skills would behave differently and the three composed strings would still exist to drift. The three `_tool_description` helpers (`runtime/ccf_runtime/adapters/{claude_agent,langgraph,adk}/adapter.py`) and the per-adapter `SKILL_ARGUMENT_SCHEMA` constant are **deleted**, not deprecated. Consequence, accepted: a major bump on the `ccf.skill-catalog-entry` schema lane, and every existing entry and fixture declares a description.

2. **`argument_schema` is a typed constrained subset of JSON Schema, never a raw dict.** A `SkillArgumentSchema` contract: named properties carrying a scalar or enum type plus an optional per-property description, and a `required` list. Raw JSON-Schema passthrough was rejected on the entry's own logic — full JSON Schema cannot be reliably derived into ADK's signature inference or a LangGraph Pydantic model, so passthrough would reintroduce exactly the per-harness divergence this entry exists to prevent, while also weakening the typed-boundary invariant. The subset is deliberately narrower to begin with (no nested objects, no `oneOf`): widening is a schema-lane bump when a real deployment case demands it, not speculative generality shipped ahead of need. Ratifying today's shared `Mapping[str, str]` constant as the ruled mechanism was also rejected: it is trivially safe for D-18 equivalence but permanently prevents a skill from declaring typed arguments, which is the capability the question exists to obtain.

3. **One shared derivation module renders the single declaration into three harness-native tool surfaces, so equivalence is structural rather than three adapters agreeing.** Claude Agent SDK → `@tool(name, description, schema)`; LangGraph → `StructuredTool` with `args_schema` built via `create_model`; ADK → `FunctionTool` over a synthesized annotated signature, since ADK introspects `__name__`/`__doc__`/annotations rather than accepting a declaration. Adapters *call* the derivation and never compose. This is the part that closes advisory A6's stated consequence — "every future adapter re-derives the same fields, and the first one to derive them differently silently breaks harness equivalence" — because after this there is nothing per-adapter left to derive.

4. **A fifth `skill_type`, `procedure`, carries the Anthropic Agent Skills model, bound through seam 1 (context injection) rather than seam 2 (tool exposure).** Its binding is an `InstructionBinding` — the existing axis-6 contract, reused rather than reinvented — plus optional pinned resource artifact URIs. It declares `description` (which is the *trigger* surface in the Anthropic model, the same field part 1 adds) and declares **no** `argument_schema`, because nothing calls it. The reasoning is the load-bearing part of this ruling: Anthropic Skills and CCF skills share a word but are different things — a SKILL.md is instructions loaded into context under progressive disclosure, while the four existing types are callable capability bindings invoked with arguments. ADK and LangGraph have no skills concept at all, so forcing a procedure into a tool shape would require inventing an argument vocabulary for something never invoked, and would leave the instruction body with no governed home on a binding whose meaning is "callable". Injected context, by contrast, requires no harness feature and is therefore portable to *any* harness by construction — which is what makes this the transferability mechanism rather than a convenience. And progressive disclosure — what to load, and when — is a fabric and policy decision that lands in replay, which is precisely CCF's job and not the harness's. Consequence I.4 must plan for: `expose_skills` filters to the callable types, and a `procedure` entry surfacing as a harness tool is a defect, not a degenerate case.

**SKILL.md is an authoring format, not a canonical artifact.** Import is one-way (`ccf skill import <dir>`, D-IMPL-22 surface): frontmatter `name` → `name`, frontmatter `description` → `description`, the body → a registered `ccf.prompt-artifact`, and `references/` → further pinned artifacts, with a `procedure` entry emitted referencing them. Replay resolves *exact* artifact versions (D-IMPL-26) and a SKILL.md in a working tree is not content-addressed, so treating it as canonical would put git state in the replay path. `allowed-tools` is **not** auto-mapped onto `SkillRequirements`: a harness permission token is not a policy-regime identifier, the SDK never interprets a requirement identifier (D-IMPL-29), and inferring one would be the SDK inventing the deployment's policy vocabulary.

**Templating reuses `render_instruction`; no second render mechanism is introduced.** The CrewAI-style dynamic binding Dave asked for already exists and is already hardened — `ccf.agents.prompts` holds the sandboxed environment, the exact-match declared-parameters rule in both directions, `str`-only values, and determinism per artifact version, and it is deliberately the SDK's *only* render entry point because the seam that calls it has three implementations and one of them getting the sandbox wrong would be three chances to get it wrong (T-06-60). A skill-side renderer would reopen that.

**Rejected: a separate manifest artifact** holding `description` and `argument_schema` so that prose edits would not churn skill grants. It does not work: replay must pin exact versions, so the entry would have to pin an exact manifest version and any prose change bumps the entry regardless — the indirection buys nothing on the churn axis and costs an artifact class plus a level of resolution. The churn is also arguably correct rather than a cost: a description change alters what the model is told and is therefore decision-relevant, so it belongs inside the versioned identity replay reproduces.

**The `procedure` token is ruled, not left to planning.** D-IMPL-59's naming escalation set the precedent that a vocabulary choice with this much surface is Dave's rather than a planner's; the token is fixed here so it cannot land silently as something else. If I.4 planning finds a materially better token it escalates back rather than substituting.

**Scope: ruled now, implemented in Phase I.4 — this entry does not block `D-GATE-I.3`.** 06-23's verification sweep re-ran every gate checklist row against the current tree (987 passed / 2 skipped, mypy clean, lints green). A breaking skill-schema change reaching all three adapters, every skill fixture and the grant lane would invalidate that sweep, force the gate package to be rebuilt, and put seven closed gap-closure findings at risk for no gain in correctness. Advisory **A6 therefore remains open in the I.3 disposition table with its consequence intact**, and this ruling is A6's designated closure in I.4. 2026-07-27. Approver: Dave. **D-IMPL-57 — what lineage strict equality (INV-CH7-47) means for a federated Context Product. RESOLVED (Dave, 2026-07-27): reading (a) — signature accountability is the federated form of the gate.** The whitepaper makes lineage strict equality one of the three Context Product validation gates: the operators the product *declares* it was built from must equal the operators the engine *resolved*. RESOLVED (Dave, 2026-07-27).** The Phase I.3 gate review surfaced three findings (B1, B2, A2) that were all, on inspection, symptoms of one structural fact: a *category* — governed context exchange between peer fabrics — had been named after its *first instance*, A2A. Every core module that legitimately needed the category had to say "A2A" to reach it, so `ccf.assembly.worker` imports `ccf.a2a.admission`, `ccf.controlplane.audit` declares `a2a_admitted` / `a2a_admission_refused`, and `ccf.skills.dispatch` carries `A2ABinding` / `A2AInvocation` / `A2ASkillRegistry` and an `"a2a"` skill type. The dependency *direction* was already correct — `wire.py` declares the Protocol in `/src` while every concrete transport lives in `/runtime` per D-04, and its own docstring already states the governing commitment ("the Context Product Contract is the stable layer; the wire is replaceable") — so what was wrong was vocabulary, not coupling. **Whitepaper posture supports the abstraction rather than merely permitting it.** §8.3 Pattern 4's commitment is to a *discipline* — trust boundaries "resolved via Policy bindings carried in the exchanged Context Product and verified at the consumer's Control Plane before admission into the consuming fabric's graph" — and it names A2A as the industry-emergent instance carrying that discipline, explicitly declining to claim "production-deployed federation networks that are not yet industry-standard". Naming the seam for the discipline rather than for one protocol is therefore the more faithful reading under CLAUDE.md §1, not a departure from it.

**Dave's ruling (2026-07-27), four parts.**
1. **The seam is named `Peering`.** Chosen over `FederationLink`, `LinkSeam`, `FederatedSeam`, and `Legation`. `*Seam` was rejected on collision grounds: CLAUDE.md already uses "seam" as generic vocabulary for any boundary a contract binds (the harness-adapter seam, the ArtifactStore seam, "the neutral seams are the stable layer", and the §3 seam-diagram mandate), so naming one specific thing `Seam` would nest the word inside itself. `Peering` was chosen because its trust semantics are an exact match rather than a metaphor: BGP peering is two autonomous systems that establish an explicit session, exchange policy-bearing announcements, and accept what the peer asserts while holding it accountable, because independent verification is unavailable — which is precisely D-IMPL-57's ruling that INV-CH7-47 is "verifiable inside a fabric, attributable across one". The name teaches the hardest part of the concept to the audience that has to approve it.
2. **A2A is not withdrawn and no code is deleted.** A2A remains a v0 commitment per CLAUDE.md §7.2 and remains the reference Peering transport; the withdraw-from-v0 option was considered and rejected on the stated ground that A2A is the fastest adoption path in the target institution. §7.2 is reframed, not amended: A2A is first-class as a *transport*, `Peering` is the seam. This ruling is a re-description of existing structure, not a rebuild — the transports, the identity primitives, the admission gate, and the trust policy all stay.
3. **Scope is peer-symmetric only. MCP is explicitly not under `Peering`.** The defining property of a Peering is that the counterparty *has a Control Plane*, which is what makes admission meaningful and what makes lineage **merge** rather than originate. MCP ingress at L1/L4/L5 is asymmetric — nothing to verify against, and it *creates* lineage rather than reconciling it — so folding it under the same word would blur the one property that makes federation hard. MCP remains its own surface per CLAUDE.md §7.1.
4. **A Peering declares trust *inputs*, never the verdict.** This preserves the guarantee `wire.py` already records for D-12: "the admission gate sits **above** every transport, so a second transport cannot arrive with its own private check, and a transport that wanted to reach L2 would have to be handed something it has no way to make." A Peering surfaces peer identity, attestation, and the asserted policy bindings; **core runs the admission gate uniformly over every Peering and constructs the admitted value L2 will accept.** A Peering implementation can no more manufacture admission than a harness adapter can acquire a write handle — the same structural device applied at a second boundary, and the reason single-writer survives federation.

**What remains open under this entry.** The mechanical naming surface (module path, Protocol name, skill-type token, Control Plane artifact key) follows from part 1 but is not itself ruled here; it is planning work against this decision. Whether the negotiated terms between two peers get their own artifact name distinct from the channel — an `Accord` or `Compact` governing a `Peering` — was raised and not ruled. Neither blocks the abstraction.

**Interaction with D-IMPL-58.** Reading (d) exists because of this ruling: once the seam is a first-class concept with its own audited admission record, the merged lineage has a natural home that is not `LineageEntry`. D-IMPL-58 remains open and gates the replan of the Phase I.3 gap-closure wave.

**D-IMPL-61 — Semantics of a workflow node with no per-node exception ref.** RESOLVED — **option (a), propagate-to-terminal.** A workflow node that declares no per-node exception ref does not fail validation; instead, absence is a *defined, explicit, audited* transition: when the node's exception path fires and no ref is bound, the workflow transitions to a terminal `failed` state, and that transition is recorded in the workflow trace like any other first-class state transition. This is the D-13 residual (D-13 rules that exception refs are per-node; it did not rule what an *absent* ref means) and it is whitepaper-silent — an SDK-defined artifact-schema surface under CLAUDE.md §8.1, which requires exception paths to be first-class state transitions, not error handling glued on. The ruling matches the positive-sentinel doctrine: the terminal `failed` transition is a positive, replayable event in the trace, never an unrecorded fall-through. It also keeps "let it fail" expressible — an author can legitimately intend a node's failure to terminate the workflow, and the alternative reading (option (b), validation error at artifact load, per the D-16 required-description forcing-function precedent) would force a boilerplate ref onto every node of every workflow and quietly make let-it-fail inexpressible, a policy choice the SDK must not impose (mechanism, not values). Accepted consequence: an author can omit a handler they meant to bind and the workflow still validates — mitigated by the trace making every propagate-to-terminal transition visible and audited, so the omission is observable at first exercise rather than silent. This ruling gates plan 07-04's WorkflowDefinition exception-routing validator semantics. 2026-07-30. Approver: Dave. Originates: CLAUDE.md §8.1 (exception paths as first-class state transitions), §15 (whitepaper-silent → Dave's ruling); D-13 (per-node exception refs — the residual this closes), D-16 (the declined forcing-function precedent); `.planning/phases/07-phase-i-4-orchestration-hitl-experience/07-01-PLAN.md` Task 2.
