- **D-IMPL-01 — Language target.** RESOLVED — Python 3.12+ as the sole v0 target; typed contracts as Pydantic v2 `extra=forbid`; Protocol-based seams; no TypeScript port in v0. Rationale: the whitepaper's mechanism commitments are Python-native idioms (structural-typing Π dispatch, `extra=forbid` bases, kw-only `tenant_id` — INV-CH7-12/13/73), CLAUDE.md §11 already presumes Pydantic-in-Python, and the harness ecosystem (D-IMPL-24 candidates) is Python-first. Build-time single-writer prevention gap compensated by the D-IMPL-41 enforcement stack. 2026-07-25. Approver: Dave.
- **D-IMPL-02 — Graph storage substrate.** RESOLVED — `GraphStore` Protocol + reference Postgres implementation + SQLite-for-dev implementation. Rationale: substrate-neutral invariant semantics (INV-CH7-16/17/21/04) carried by the Protocol (see D-IMPL-34); SQLite-for-dev is load-bearing for the §9 examples discipline. 2026-07-25. Approver: Dave.
- **D-IMPL-03 — Vector substrate.** RESOLVED — `SimilarityIndex` Protocol + reference implementation on sqlite-vec (dev default), Chroma as a second reference impl if budget allows. Rationale: the Similarity determinism contract (INV-CH7-27) requires vendor-neutral corpus/index versioning and version pinning in L; sqlite-vec pairs with the SQLite-for-dev graph store for a zero-infra quickstart. 2026-07-25. Approver: Dave.
- **D-IMPL-04 — Runtime topology for v0.** RESOLVED — (a) single distribution with two packages (`ccf` library + `ccf-runtime`) in the monorepo, installable separately; (b) async-first runtime with sync facades; fabric core (operator/projection path) stays sync per the read-only-sync operator contract (INV-CH7-22). Rationale: the `/src` vs `/runtime` seam becomes a packaging boundary reinforcing the harness-neutrality lint; runtime obligations (MCP both roles, A2A, suspended workflows, monitoring triggers) are inherently concurrent. 2026-07-25. Approver: Dave.
- **D-IMPL-05 — Tenancy model.** RESOLVED — multi-tenant with `tenant_id` first-class throughout; single-tenant is the degenerate case (one fixed tenant id), not a separate mode. Rationale: tenancy is structural in the whitepaper (INV-CH7-16 no-untenanted-path; kw-only `tenant_id` per INV-CH7-73(e); tenant in the product cache key per INV-CH7-52); a mode split would fork every signature. 2026-07-25. Approver: Dave.
- **D-IMPL-06 — Snapshot management for replay.** RESOLVED — logical snapshots by construction: a snapshot is an immutable as-of reference (`graph_snapshot_id` = temporal boundary + tenant + store-state watermark) plus a touched-substate manifest (the entity URIs, relationship ids, and lineage entries the decision actually read, already enumerated by lineage strict equality); never a physical graph copy. The full-fidelity tier (INV-CH7-89) additionally materializes the touched substate as a content-addressed ArtifactStore artifact per D-IMPL-26; at compression it reduces to hash + re-hydration recipe per D-IMPL-44. Similarity-index snapshots: the index version pinned in L is the reference; the SimilarityIndex Protocol (D-IMPL-03) must support version-pinned reads; periodic full-index snapshots are ArtifactStore artifacts on a Control-Plane-configured cadence (values, not SDK policy). 2026-07-25. Approver: Dave.
- **D-IMPL-07 — Embedding model abstraction.** RESOLVED — `EmbedderProtocol` with two reference adapters (one API-based, one local/deterministic for tests); model identity + version exposed as part of the Protocol contract. Rationale: "same embedding model version" is a determinism input (INV-CH7-27), so `(model_id, model_version)` reporting is a Protocol obligation; the local deterministic embedder is replay test-strategy infrastructure. 2026-07-25. Approver: Dave.

Rationale: the non-negotiable mechanism is the output contract (ingestion-time extraction, typed E/R nodes, passage-level L anchors — INV-CH7-19); stage Protocols express the mode variance of the Alternating Derivation Pipeline (INV-CH8-12) and give the `@algorithmic` lint per-stage enforcement targets. 2026-07-25. Rationale: replay dimension 3 (Model Version Record) makes version capture a structural obligation of the client contract; one Protocol module gives the `@algorithmic` lint a crisp import target; D-IMPL-46 will own the passage-citation provider Protocol shape specifically. 2026-07-25. - **D-IMPL-11 — Agent base shape.** RESOLVED — single concrete `Agent` runtime class (the factory's output type), specialized entirely by its definition artifact; archetypes as Protocol-typed composable behavior bundles attached by declaration; no class hierarchy and no user subclassing — code-level extension happens via Protocol seams (skills, harness adapters, archetype components). Composition semantics per D-IMPL-19. 2026-07-25. Approver: Dave.
- **D-IMPL-12 — Skill catalog model.** RESOLVED — dynamic Control Plane skill catalog: skills registered as typed, versioned Control Plane artifacts (per the D-IMPL-28 format) at boot or at runtime through an audited Control Plane action; four skill types (local callable | MCP resource/tool | A2A endpoint | tool) — MCP-Resources-as-skills is one type, not the unified mechanism; catalog entries carry a requirements declaration (policy scope, context-contract access, egress) feeding the D-IMPL-29 compatibility check; grants/revocations are separate versioned artifacts referencing catalog entries by version. 2026-07-25. Approver: Dave.
- **D-IMPL-13 — MCP role allocation.** RESOLVED — MCP allocated to exactly the five CLAUDE.md §7.1 edges: one `ccf` MCP client library serving both L1 ingress (via `MCPSourceAdapter` normalizing into the D-IMPL-33 `SignalEnvelope`) and L4–L5 content acquisition; one `ccf-runtime` MCP egress server serving L6 Context Products as Resources and permitted agent invocations as Tools (L6 + Experience access are one server, two resource families); a separate ArtifactStore MCP server contract (§7.4), never merged with egress. Packaging follows D-IMPL-04; single-writer unaffected (acquisition results reach L3 only via L2). 2026-07-25. Approver: Dave.
- **D-IMPL-14 — A2A wire protocol.** RESOLVED — the Linux Foundation A2A protocol (JSON-RPC over HTTPS with Agent Card discovery and the task/artifact model) as the v0 default `WireProtocol` implementation, carrying the typed Context Product as the artifact payload; mTLS via deployment configuration; a plain typed-HTTP fallback transport ships as the second reference impl. The Context Product Contract remains the stable layer; consumer-side Control Plane verification happens above the transport (INV-CH8-07/08). 2026-07-25. Approver: Dave.
- **D-IMPL-15 — Agent identity and signing.** RESOLVED — `IdentityProvider` Protocol with a two-layer model: workload/transport identity via mTLS (X.509) as deployment configuration, and product-level signing via detached JWS over the canonical serialized Context Product (producer agent identity + version + key id) verified at the consumer's Control Plane during A2A admission. Reference impls: static-keypair JWS signer/verifier (dev) + certificate-backed keys (production posture). SPIFFE/SPIRE is a conforming Protocol implementation, not required. 2026-07-25. Approver: Dave.
- **D-IMPL-16 — Control Plane scope at A2A boundary.** RESOLVED — verify every inbound A2A Context Product: full Control Plane verification (signature, Policy bindings, contract validation, lineage integrity) on every admission, no fast path in v0. Peer trust tiers configure only what is admissible (producers, product classes, policy regimes a peer may assert), never verification skips. Post-v0 performance relief via verification caching memoized on immutable artifact identity, preserving verify-everything semantics. Ruled after a performance/safety discussion — admission is off the hot path, amortized once per product version. 2026-07-25. Approver: Dave.
- **D-IMPL-17 — Orchestration primitive scope.** RESOLVED — minimal in-SDK Workflow primitive plus `OrchestrationProtocol` for external orchestrators (the CLAUDE.md §12 recommended option). The Workflow primitive ships exactly the §8.1 committed properties (skill/agent/HITL-gate nodes, state-machine semantics, suspend/resume on Control Plane state per D-IMPL-18, first-class exception paths, harness-neutral agent nodes, definitions as Control Plane artifacts through the Task Factory); traces land in replay dimensions 4/5 by construction. `OrchestrationProtocol` is the seam to Temporal-class external engines with identical replay obligations. LangGraph two-seam disambiguation per the D-IMPL-24 ruling: the LangGraph *harness adapter* binds only the §7.3 agent-loop seams; LangGraph *as an orchestrator of CCF agents* is a distinct, optional `OrchestrationProtocol` integration — one tool, two seams, never conflated; DESIGN.md documents the boundary explicitly. 2026-07-25. Approver: Dave.
- **D-IMPL-18 — Workflow state persistence.** RESOLVED — Control Plane persistence (the CLAUDE.md §12 recommended option): suspended workflow execution state (current node, variable bindings, pending-gate references) lives at the Control Plane boundary as typed, versioned state records on the Control Plane's native store — mutable until terminal, therefore off the ArtifactStore per the D-IMPL-27 mutability rule. Every state transition appends to the execution trace; the trace is written through to the ArtifactStore as part of the replay record at terminal and at each suspend (long-horizon audit). Persistence substrate is the Control Plane's storage seam — pluggable there, no separate workflow-store Protocol. 2026-07-25. Approver: Dave.
- **D-IMPL-19 — Agent archetype expression.** RESOLVED — composition over mixins: archetypes are Protocol-typed component bundles the factory attaches to the single `Agent` class per the artifact's declared archetype list; multi-archetype agents are ordered composition with explicit conflict rules — identical obligations contributed twice are deduplicated; conflicting configuration defaults resolve by declaration order with a factory warning; hard contradictions are a factory construction error. The composed archetype list is channel-1 identity (axis 1) and lands in replay dimension 4. 2026-07-25. Approver: Dave.
- **D-IMPL-20 — HITL transport.** RESOLVED — `HITLTransportProtocol` (typed queue interface) as the core mechanism: pending HITL events (ApprovalGate, ExceptionEscalation, OverrideBoundary, ReviewQueue items) are typed records — event class, workflow state reference, the Context Product the human must see, deadline/escalation policy reference — enqueued by the HITL primitives; actions (approve/reject/override/annotate) return through the same surface and land in the replay record by construction, no transport path bypassing capture. Two reference transports: (1) MCP server endpoints exposing HITL queues as Resources and actions as Tools on the Experience-Layer surface (primary — serves example 05 and the `ccf hitl` CLI); (2) webhooks (secondary, notify-only — the webhook notifies, the action always flows back through the typed queue, so notification and authority are separated and audit-by-construction cannot be bypassed). No inbox UI per CLAUDE.md §8.2/§13. 2026-07-25. Approver: Dave.
- **D-IMPL-21 — HITL identity binding.** RESOLVED — pluggable via the same `IdentityProvider` Protocol family as D-IMPL-15, with a distinct human-principal binding shape: every HITL action record carries a typed `HumanPrincipalBinding` — approver identity (subject id + identity-provider reference), authentication context (method, assurance level, session reference), action time, and the content hash (per D-IMPL-26) of the Context Product the approver saw. OIDC/SAML enterprise providers are the realistic human-principal path (vs. mTLS+JWS for workloads per D-IMPL-15). Reference impls: authenticated-principal record from the HTTP/MCP auth context (dev) and a JWS-signed binding reusing the D-IMPL-15 signing machinery for cryptographic non-repudiation. Audit-by-construction holds regardless of provider: no HITL action lands without a binding. 2026-07-25. Approver: Dave.
- **D-IMPL-22 — CLI shape.** RESOLVED — noun-verb subcommand structure `ccf <noun> <verb>` covering exactly the §8.3 enumerated surfaces (`agent`, `skill`, `workflow`, `hitl`, `replay`, `artifact`, `product`, `config` noun set), as a thin client over the HTTP API with a `--local` direct-library mode for the SQLite/file-backed dev quickstart (examples 00–02). Every mutating verb routes through the same factories/Control Plane actions as any other client — `ccf agent declare` takes an artifact file, never inline definition flags (No-Hardcoding §6.4) — so the CLI adds zero privileged paths and keeps one authorization/audit surface. 2026-07-25. Approver: Dave.
- **D-IMPL-23 — HTTP API surface.** RESOLVED — minimal v0 skeleton mirroring the CLI noun set: product retrieval, agent declare/list/show/versions, skill grants/catalog, workflow invocations/status/resume, HITL queues/actions, replay decisions/resolve, artifact get/put, health + OpenAPI. OpenAPI generated from the Pydantic `extra=forbid` contracts the SDK already defines — the API adds serialization, auth hooks, and routing, no new semantics. L1 ingestion is deliberately NOT on the v0 HTTP surface: ingress is CDC/MCP-adapter territory (D-IMPL-13/33), and a generic write endpoint would invite a second writer path. 2026-07-25. - **D-IMPL-25 — HarnessAdapterProtocol seam scope.** RESOLVED — three seams mandatory for every conforming adapter: context injection, replay hooks, and effect capture as governed refusal; skill exposure conditionally mandatory (required iff the bound agent has a non-empty skill-set). Single-writer holds across the adapter boundary (CLAUDE.md §7.3 seam 3, §10). 2026-07-25. Approver: Dave.
- **D-IMPL-26 — Artifact addressing and versioning.** RESOLVED — hybrid addressing: content-addressed canonical identity plus versioned-URI naming, resolved through the Control Plane. Canonical identity of every artifact is `sha256(canonical_serialization)` — immutability and replay determinism become verifiable properties (a tampered artifact fails its own address; replay resolves exact versions by hash per CLAUDE.md §7.4). Human/system-facing addressing is a versioned URI `ccf-artifact://{tenant}/{artifact_class}/{name}@{artifact_version}` per the D-IMPL-28 two-field version discipline, maintained as an append-only Control Plane mapping (versioned-URI → content hash; a version once bound to a hash is never rebound). `@latest` is permitted only at authoring/Control Plane surfaces — never in a replay record or lineage entry, which store the hash (URI carried as annotation). The reference artifact MCP server (per the D-IMPL-13 separate ArtifactStore contract) exposes artifacts addressable by both forms, with a typed metadata resource per artifact. 2026-07-25. Approver: Dave.
- **D-IMPL-27 — Substrate split.** RESOLVED — split by mutability: immutable, versioned, replay-relevant artifacts route through the ArtifactStore (Decision Replay records with all extensions, materialized graph-substate and similarity-index snapshots per D-IMPL-06, Context Products at rest, Control Plane bundles, all No-Hardcoding artifacts — the full CLAUDE.md §7.4 class list); hot mutable state stays on native Protocols (live Context Graph on GraphStore per D-IMPL-02, live similarity index per D-IMPL-03, operator-plan intermediate caches per D-IMPL-36, suspended workflow execution state per D-IMPL-18 — mutable until terminal, whose terminal trace then lands in the ArtifactStore). The mutability criterion is a single structural rule; single-writer preserved trivially (the store never holds live graph state). 2026-07-25. Approver: Dave.

Artifact addressing/storage remains D-IMPL-26. Homecams' YAML+Jinja2 shape was a data point, never a default. 2026-07-25. Approver: Dave.
- **D-IMPL-29 — Skilling governance depth.** RESOLVED — two-tier governance, both mechanism: tier 1, the automatic policy-compatibility check, always on and non-waivable (the Control Plane refuses a bind whose declared requirements exceed the agent's policy regime or context contract); tier 2, policy regimes may declare that grants (all, or matching declared criteria) additionally require an ApprovalGate before taking effect — whether tier 2 is engaged is Control Plane configuration, values not SDK policy. Requirements-declaration schema is the typed block on the D-IMPL-12 catalog entry, validated per D-IMPL-28. Grant, approval, and effective-time all land in the audit record. 2026-07-25. Approver: Dave. Originally: Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.4 Step 4 vs §6.3 (INV-CH6-04). Three placements were considered. **Extend dimension 3 (`ModelVersionRecord`)** — chosen: harness-attributable values *are* model-attributable values, the dimension already exists for exactly that question, and the extension is a sub-structure so dimension 3's own `assembly_mode` and `model_version` stay governed fields the fabric alone writes (T-06-62: a harness reports its own `model_version` inside `harness_trace` and can never overwrite the fabric's claim about what *it* invoked). **Extend dimension 5 (Content Generation Path)** — rejected: dimension 5 records how the delivered content came to be as an operator plan and step sequence, and D-IMPL-45's `TraceCorrelationHook` attaches to the same replay-hooks seam in I.4, so putting the harness identity there would make one dimension answer two unrelated questions. **A sixth top-level block** — rejected outright: INV-CH7-80 makes the five dimensions inviolate, so a sixth block is a whitepaper-fidelity defect, not a design option. `DecisionReplayRecord`'s five dimension fields are unchanged and `tests/replay/test_harness_trace.py::test_the_record_still_has_exactly_five_dimensions` asserts it against the named set rather than a field count (the record also carries `tenant_id` and `recorded_at` as record-level metadata, so a raw `len(model_fields)` check would pass or fail for the wrong reason). **D-IMPL-56 — where a skill's tool description and argument schema are declared. RESOLVED (Dave, 2026-07-27): the entry declares both, one shared derivation renders them into all three harnesses, and a fifth `procedure` skill type carries the Anthropic Agent Skills model through seam 1.** `SkillCatalogEntry` declares neither a human-readable description nor an argument schema, yet every one of the three v0 harness adapters needs both: Google ADK's `FunctionTool` and LangGraph's `StructuredTool` each want a description string and a typed argument model, and the Claude Agent SDK adapter wants the same fields to build its tool block. All three adapters surfaced the gap independently, which is the signal that it is not an adapter's problem. Plan 06-12 set the in-phase precedent and 06-13/06-14 followed it: compose the description from fields the entry already carries (name, skill type, binding identifiers) and transcribe `Agent.invoke_skill`'s `Mapping[str, str]` signature into one shared schema constant — deliberately *not* authoring prose in SDK code, which would breach the No-Hardcoding Rule (CLAUDE.md §6.4), and deliberately shared rather than per-adapter, because three adapters inventing three descriptions would break the D-18 portability equivalence 06-15 proves. That precedent is a workaround, not a resolution: what a skill is *for* is the deployment's statement, and the place it belongs is the skill-catalog artifact schema — a Control Plane decision (CLAUDE.md §6.2 channel 2, D-IMPL-12/D-IMPL-28), not an adapter's. **The question for Dave:** does `SkillCatalogEntry` gain optional `description` and `argument_schema` fields (making the tool surface a declared artifact property), or does the adapter-composed derivation become the ruled mechanism (making tool prose structurally SDK-derived, and identical across harnesses because one shared constant supplies it)? Consequence of leaving it open: every future adapter re-derives the same fields, and the first one to derive them differently silently breaks harness equivalence. Surfaced: 2026-07-27, plans 06-12/06-13/06-14, gate-assembled in 06-16. Originates: CLAUDE.md §6.2, §7.3 seam 2; `docs/PHASE_I3_GATE.md` §4.

**Dave's ruling (2026-07-27), four parts.** The question was asked as an either/or — declared artifact property *or* ruled adapter derivation — and the ruling takes the first, then extends past what was asked, because the goal Dave stated is broader than the gap the adapters surfaced: *skills must be transferable across the Claude Agent SDK, ADK and LangGraph, with the Anthropic Agent Skills model importable and CrewAI-style dynamic context binding available in the declaration.*

1. **`SkillCatalogEntry` gains a required `description` and a typed `argument_schema`; the adapter-composed derivation is retired, not kept as a fallback.** `description` is required rather than optional: what a skill is *for* is the deployment's statement, and silence is not the same statement as a declared value — the same D-IMPL-38 discipline `SkillRequirements` already applies to an empty-versus-absent frozenset. Optional-with-fallback was rejected specifically because a retained fallback is a retained divergence risk: described and undescribed skills would behave differently and the three composed strings would still exist to drift. The three `_tool_description` helpers (`runtime/ccf_runtime/adapters/{claude_agent,langgraph,adk}/adapter.py`) and the per-adapter `SKILL_ARGUMENT_SCHEMA` constant are **deleted**, not deprecated. Consequence, accepted: a major bump on the `ccf.skill-catalog-entry` schema lane, and every existing entry and fixture declares a description.

2. **`argument_schema` is a typed constrained subset of JSON Schema, never a raw dict.** A `SkillArgumentSchema` contract: named properties carrying a scalar or enum type plus an optional per-property description, and a `required` list. Raw JSON-Schema passthrough was rejected on the entry's own logic — full JSON Schema cannot be reliably derived into ADK's signature inference or a LangGraph Pydantic model, so passthrough would reintroduce exactly the per-harness divergence this entry exists to prevent, while also weakening the typed-boundary invariant. The subset is deliberately narrower to begin with (no nested objects, no `oneOf`): widening is a schema-lane bump when a real deployment case demands it, not speculative generality shipped ahead of need. Ratifying today's shared `Mapping[str, str]` constant as the ruled mechanism was also rejected: it is trivially safe for D-18 equivalence but permanently prevents a skill from declaring typed arguments, which is the capability the question exists to obtain.

3. **One shared derivation module renders the single declaration into three harness-native tool surfaces, so equivalence is structural rather than three adapters agreeing.** Claude Agent SDK → `@tool(name, description, schema)`; LangGraph → `StructuredTool` with `args_schema` built via `create_model`; ADK → `FunctionTool` over a synthesized annotated signature, since ADK introspects `__name__`/`__doc__`/annotations rather than accepting a declaration. Adapters *call* the derivation and never compose. This is the part that closes advisory A6's stated consequence — "every future adapter re-derives the same fields, and the first one to derive them differently silently breaks harness equivalence" — because after this there is nothing per-adapter left to derive.

4. **A fifth `skill_type`, `procedure`, carries the Anthropic Agent Skills model, bound through seam 1 (context injection) rather than seam 2 (tool exposure).** Its binding is an `InstructionBinding` — the existing axis-6 contract, reused rather than reinvented — plus optional pinned resource artifact URIs. It declares `description` (which is the *trigger* surface in the Anthropic model, the same field part 1 adds) and declares **no** `argument_schema`, because nothing calls it. The reasoning is the load-bearing part of this ruling: Anthropic Skills and CCF skills share a word but are different things — a SKILL.md is instructions loaded into context under progressive disclosure, while the four existing types are callable capability bindings invoked with arguments. ADK and LangGraph have no skills concept at all, so forcing a procedure into a tool shape would require inventing an argument vocabulary for something never invoked, and would leave the instruction body with no governed home on a binding whose meaning is "callable". Injected context, by contrast, requires no harness feature and is therefore portable to *any* harness by construction — which is what makes this the transferability mechanism rather than a convenience. And progressive disclosure — what to load, and when — is a fabric and policy decision that lands in replay, which is precisely CCF's job and not the harness's. Consequence I.4 must plan for: `expose_skills` filters to the callable types, and a `procedure` entry surfacing as a harness tool is a defect, not a degenerate case.

**SKILL.md is an authoring format, not a canonical artifact.** Import is one-way (`ccf skill import <dir>`, D-IMPL-22 surface): frontmatter `name` → `name`, frontmatter `description` → `description`, the body → a registered `ccf.prompt-artifact`, and `references/` → further pinned artifacts, with a `procedure` entry emitted referencing them. Replay resolves *exact* artifact versions (D-IMPL-26) and a SKILL.md in a working tree is not content-addressed, so treating it as canonical would put git state in the replay path. `allowed-tools` is **not** auto-mapped onto `SkillRequirements`: a harness permission token is not a policy-regime identifier, the SDK never interprets a requirement identifier (D-IMPL-29), and inferring one would be the SDK inventing the deployment's policy vocabulary.

**Templating reuses `render_instruction`; no second render mechanism is introduced.** The CrewAI-style dynamic binding Dave asked for already exists and is already hardened — `ccf.agents.prompts` holds the sandboxed environment, the exact-match declared-parameters rule in both directions, `str`-only values, and determinism per artifact version, and it is deliberately the SDK's *only* render entry point because the seam that calls it has three implementations and one of them getting the sandbox wrong would be three chances to get it wrong (T-06-60). A skill-side renderer would reopen that.

**Rejected: a separate manifest artifact** holding `description` and `argument_schema` so that prose edits would not churn skill grants. It does not work: replay must pin exact versions, so the entry would have to pin an exact manifest version and any prose change bumps the entry regardless — the indirection buys nothing on the churn axis and costs an artifact class plus a level of resolution. The churn is also arguably correct rather than a cost: a description change alters what the model is told and is therefore decision-relevant, so it belongs inside the versioned identity replay reproduces.

**The `procedure` token is ruled, not left to planning.** D-IMPL-59's naming escalation set the precedent that a vocabulary choice with this much surface is Dave's rather than a planner's; the token is fixed here so it cannot land silently as something else. If I.4 planning finds a materially better token it escalates back rather than substituting.

**Scope: ruled now, implemented in Phase I.4 — this entry does not block `D-GATE-I.3`.** 06-23's verification sweep re-ran every gate checklist row against the current tree (987 passed / 2 skipped, mypy clean, lints green). A breaking skill-schema change reaching all three adapters, every skill fixture and the grant lane would invalidate that sweep, force the gate package to be rebuilt, and put seven closed gap-closure findings at risk for no gain in correctness. Advisory **A6 therefore remains open in the I.3 disposition table with its consequence intact**, and this ruling is A6's designated closure in I.4. 2026-07-27. Approver: Dave. **D-IMPL-57 — what lineage strict equality (INV-CH7-47) means for a federated Context Product. RESOLVED (Dave, 2026-07-27): reading (a) — signature accountability is the federated form of the gate.** The whitepaper makes lineage strict equality one of the three Context Product validation gates: the operators the product *declares* it was built from must equal the operators the engine *resolved*. Inside one fabric that is a real check, because the engine's resolution is an independent witness. Across an A2A trust boundary it is not: the consumer never ran the producer's operator plan, so `ccf.a2a.admission._run_contract_gates` currently passes `engine_resolved=product.lineage.operators_invoked` — the producer's own claim — as the witness. The module docstring states plainly that the gate is "structurally vacuous here" and offers signature accountability as the substitute: the producer signed the lineage it asserted, so a false claim is attributable even though it is not independently verifiable. **That substitution is a narrowing of a whitepaper-committed validation gate, and it was made in implementation rather than by ruling — `docs/DECISIONS.md` records it nowhere.** Three readings, with consequences: **(a) Accept signature accountability as the federated form of the gate.** INV-CH7-47 becomes "verifiable inside a fabric, attributable across one." Cheapest; makes the current code correct as written; but a compromised or buggy peer can assert any operator plan and the consumer admits it. **(b) Require an independent consumer-side witness.** The consumer re-resolves the declared operator plan against its own registry before admission, and refuses a product naming operators it cannot resolve. Restores the gate's teeth; costs a resolution pass at admission and means a consumer cannot admit products built with operators it does not itself have — which may be exactly right, or may be too strict for federation across differently-provisioned tenants. **(c) Refuse to run the gate at all on the A2A path and gate differently.** Admission stops claiming INV-CH7-47 and instead names the checks it actually performs (signature, policy bindings, trust policy, TTL), so no gate is asserted vacuously. Most honest about what holds; requires amending the gate documentation and the ROADMAP criterion so neither claims lineage strict equality across the boundary. Consequence of leaving it open: the phase ships with a whitepaper validation gate silently reinterpreted at the one boundary where it was hardest to hold — the precise failure mode CLAUDE.md §11's "surface gaps; do not paper over them" exists to prevent. **D-IMPL-59 — the federation seam is an abstraction named `Peering`; A2A is one Peering transport, not the concept. RESOLVED (Dave, 2026-07-27).** The Phase I.3 gate review surfaced three findings (B1, B2, A2) that were all, on inspection, symptoms of one structural fact: a *category* — governed context exchange between peer fabrics — had been named after its *first instance*, A2A. Every core module that legitimately needed the category had to say "A2A" to reach it, so `ccf.assembly.worker` imports `ccf.a2a.admission`, `ccf.controlplane.audit` declares `a2a_admitted` / `a2a_admission_refused`, and `ccf.skills.dispatch` carries `A2ABinding` / `A2AInvocation` / `A2ASkillRegistry` and an `"a2a"` skill type. The dependency *direction* was already correct — `wire.py` declares the Protocol in `/src` while every concrete transport lives in `/runtime` per D-04, and its own docstring already states the governing commitment ("the Context Product Contract is the stable layer; the wire is replaceable") — so what was wrong was vocabulary, not coupling. **Whitepaper posture supports the abstraction rather than merely permitting it.** §8.3 Pattern 4's commitment is to a *discipline* — trust boundaries "resolved via Policy bindings carried in the exchanged Context Product and verified at the consumer's Control Plane before admission into the consuming fabric's graph" — and it names A2A as the industry-emergent instance carrying that discipline, explicitly declining to claim "production-deployed federation networks that are not yet industry-standard". Naming the seam for the discipline rather than for one protocol is therefore the more faithful reading under CLAUDE.md §1, not a departure from it.

**Dave's ruling (2026-07-27), four parts.**
1. **The seam is named `Peering`.** Chosen over `FederationLink`, `LinkSeam`, `FederatedSeam`, and `Legation`. `*Seam` was rejected on collision grounds: CLAUDE.md already uses "seam" as generic vocabulary for any boundary a contract binds (the harness-adapter seam, the ArtifactStore seam, "the neutral seams are the stable layer", and the §3 seam-diagram mandate), so naming one specific thing `Seam` would nest the word inside itself. `Peering` was chosen because its trust semantics are an exact match rather than a metaphor: BGP peering is two autonomous systems that establish an explicit session, exchange policy-bearing announcements, and accept what the peer asserts while holding it accountable, because independent verification is unavailable — which is precisely D-IMPL-57's ruling that INV-CH7-47 is "verifiable inside a fabric, attributable across one". The name teaches the hardest part of the concept to the audience that has to approve it.
2. **A2A is not withdrawn and no code is deleted.** A2A remains a v0 commitment per CLAUDE.md §7.2 and remains the reference Peering transport; the withdraw-from-v0 option was considered and rejected on the stated ground that A2A is the fastest adoption path in the target institution. §7.2 is reframed, not amended: A2A is first-class as a *transport*, `Peering` is the seam. This ruling is a re-description of existing structure, not a rebuild — the transports, the identity primitives, the admission gate, and the trust policy all stay.
3. **Scope is peer-symmetric only. MCP is explicitly not under `Peering`.** The defining property of a Peering is that the counterparty *has a Control Plane*, which is what makes admission meaningful and what makes lineage **merge** rather than originate. MCP ingress at L1/L4/L5 is asymmetric — nothing to verify against, and it *creates* lineage rather than reconciling it — so folding it under the same word would blur the one property that makes federation hard. MCP remains its own surface per CLAUDE.md §7.1.
4. **A Peering declares trust *inputs*, never the verdict.** This preserves the guarantee `wire.py` already records for D-12: "the admission gate sits **above** every transport, so a second transport cannot arrive with its own private check, and a transport that wanted to reach L2 would have to be handed something it has no way to make." **D-IMPL-61 — Semantics of a workflow node with no per-node exception ref.** RESOLVED — **option (a), propagate-to-terminal.** A workflow node that declares no per-node exception ref does not fail validation; instead, absence is a *defined, explicit, audited* transition: when the node's exception path fires and no ref is bound, the workflow transitions to a terminal `failed` state, and that transition is recorded in the workflow trace like any other first-class state transition. This is the D-13 residual (D-13 rules that exception refs are per-node; it did not rule what an *absent* ref means) and it is whitepaper-silent — an SDK-defined artifact-schema surface under CLAUDE.md §8.1, which requires exception paths to be first-class state transitions, not error handling glued on. The ruling matches the positive-sentinel doctrine: the terminal `failed` transition is a positive, replayable event in the trace, never an unrecorded fall-through. It also keeps "let it fail" expressible — an author can legitimately intend a node's failure to terminate the workflow, and the alternative reading (option (b), validation error at artifact load, per the D-16 required-description forcing-function precedent) would force a boilerplate ref onto every node of every workflow and quietly make let-it-fail inexpressible, a policy choice the SDK must not impose (mechanism, not values). Accepted consequence: an author can omit a handler they meant to bind and the workflow still validates — mitigated by the trace making every propagate-to-terminal transition visible and audited, so the omission is observable at first exercise rather than silent. This ruling gates plan 07-04's WorkflowDefinition exception-routing validator semantics. 2026-07-30. Approver: Dave. Originates: CLAUDE.md §8.1 (exception paths as first-class state transitions), §15 (whitepaper-silent → Dave's ruling); D-13 (per-node exception refs — the residual this closes), D-16 (the declined forcing-function precedent); `.planning/phases/07-phase-i-4-orchestration-hitl-experience/07-01-PLAN.md` Task 2.
