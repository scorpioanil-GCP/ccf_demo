**D-IMPL-30 — Context Product Contract element count (eight vs nine).** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.3 (INV-CH6-03). Ambiguous passage: §6.3 prose opens "Nine elements jointly specify the contract" and the table lists nine (Assembly Mode included; §6.4 calls it "the §6.3 specification's ninth element"), yet the same §6.3 prose describes "the § 6.1 canonical 8-property table" and CLAUDE.md §5 refers to "the eight-element specification per §6.3." Readings: (a) the contract has nine elements and the "eight" references denote the external comparison test only — consequence: the SDK Contract base carries all nine fields including Assembly Mode; (b) the contract has eight elements and Assembly Mode is a per-product *configuration* property layered on the contract — consequence: Assembly Mode lives in Control Plane product-class registration, not the product schema; (c) revision drift; the count is editorial — consequence: Dave rules which count is canonical and the inventory annotates the discrepancy. The 8-property→9-element mapping is asserted but never tabulated.

**D-IMPL-31 — TTL granularity: per-signal vs per-product.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.4 Step 4 vs §6.3 (INV-CH6-04). Ambiguous passage: §6.4 Step 4 states "Temporal Validation assigns TTL to each mutation," while §6.3 defines TTL as a per-product contract element, and §6.4's worked thread gives both per-product TTLs (4h/24h) and per-signal TTLs (15 min blotter entry). Readings: (a) TTL exists at two granularities and product TTL derives (e.g., min) from constituent signal validities — consequence: SDK needs a signal-level validity primitive plus a product-level TTL with a defined derivation rule; (b) Step 4's "TTL" loosely means the T-dimension validity envelope and only the contract-level TTL is properly TTL — consequence: SDK type surface must disambiguate half-life-derived validity from contract TTL; (c) product TTL is independently configured per class and Step 4 only validates constituent signals — consequence: no derivation rule, but the asymmetric-freshness mixing-refusal rule still needs formal definition. §7.7 partially informs but does not resolve.

**D-IMPL-32 — Context Trust Triangle scoring mechanics.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.6.3 (INV-CH6-08). Ambiguous passage: "when all three legs hold, the recursion may terminate" — no aggregation function, scale, or threshold mechanics are specified for any leg or the aggregate. Readings: (a) thresholds are Control-Plane-configurable; SDK ships a TrustScore Protocol with pluggable per-leg scorers and a conjunctive combinator — mechanism-not-values; (b) the legs are derived quantities via §7.7 D_c mechanics (the §7.7.8 debt-mapping supports this partially: leg strengths derive from the three debt components) — consequence: no independent trust primitive; (c) the triangle is advisory vocabulary — consequence: no SDK primitive; only replay capture of computed trust inputs. Gates whether v0 ships a trust-scoring surface.

**D-IMPL-33 — Canonical L1 event envelope schema.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.1 (INV-CH7-02). "Whatever raw payload the upstream system emitted" — the envelope fields are enumerated in prose (source, ingestion timestamp, observed-time?, raw payload) but no formal schema is given. The SDK must commit a typed L1 envelope contract. Homecams' normalized enrichable-event contract with per-source adapters is one data point.

**D-IMPL-34 — Graph-storage Protocol requirement surface.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.3.1 (INV-CH7-15). "The physical representation maps to ~10 collections" is reference-implementation grounding, not a normative count. What the SDK's graph-storage Protocol must require of a backend (compound index, supersession semantics, per-relationship-type lineage, append-only discipline) versus what stays backend-internal is a design decision. Do NOT inherit the Homecams collection layout. Interacts with D-IMPL-02.

**D-IMPL-35 — Entity Resolver contract.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.3.5 (INV-CH7-21). Correlation via "shared attributes (the LEI where one exists, registered address and authorized-signatory metadata where it does not)" is a domain-flavored pattern. The SDK needs a general-purpose resolution Protocol (pluggable strategy vs shipped mechanism); attribute-correlation strategies are user configuration.

**D-IMPL-36 — Operator-plan intermediate scheduling and materialization.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.4.2, Fig-CH07-08 (INV-CH7-28). The contract is committed (intermediates persistable, cache-coherent under λ_c invalidation, reusable for replay) but the scheduling/materialization mechanism (when intermediates cache, eviction, reuse policy) is not specified. Homecams' TTL-indexed `projection_cache` separate from graph state is one working resolution — do NOT inherit (CLAUDE.md §2.1). Interacts with D-IMPL-06/D-IMPL-27.

**D-IMPL-37 — Operator registry population surface.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.4.2 (INV-CH7-29). "Import-time / boot-time loaded" with fail-fast duplicates is committed, but how user-supplied operators register against the SDK's registry (entry points, explicit registration API, config-driven) is unspecified.

**D-IMPL-38 — Control Plane parameter schema for operator thresholds.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.4.3/§7.4.6 and §8.4 (INV-CH7-24, INV-CH8-12). Thresholds (materiality floors, similarity `threshold=0.85`/`0.75`, the §8.4 distance-weighted-deduplication confidence threshold) are stated as Control-Plane-governed contract parameters, but no threshold schema, declaration surface, defaulting rule, or versioning discipline is specified. Interacts with §7.8.3 configuration surface and the No-Hardcoding Rule (CLAUDE.md §6.4).

**D-IMPL-39 — MAX_TTL configuration locus.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.6.1/§7.6.4 (INV-CH7-48). Ambiguous passage: "TTL bounds rejects a Contract whose expires_at is in the past or beyond a MAX_TTL envelope" — where MAX_TTL is configured and what governs its value is never specified. Readings: (a) Control Plane configuration per Context Product class (consistent with §7.8 posture) — SDK ships mechanism, users supply values; (b) fabric-wide constant — collides with the mechanism/values boundary; (c) derived from the product's λ_c band — elegant but nowhere stated.

**D-IMPL-40 — CAR threat-level scale and class-specific D_c thresholds.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.7.7 (INV-CH7-65). Ambiguous passage: "ELIF threat_level ≤ LOW → Conditional … ELIF D_c above the class-specific threshold → Forced LLM" — the threat-level scale, its source, and how class-specific D_c thresholds are set are unspecified. Readings: (a) both are Control Plane configuration per decision class; SDK ships routing mechanism only; (b) threat level is fabric-computed from signal characteristics — would require a computation the paper never gives.

**D-IMPL-41 — Build-time single-writer enforcement substrate.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.8.4 (INV-CH7-73). "Compilation of those services against write-capable interfaces is prevented by the type system at build time" assumes a compiled/typed substrate; how the SDK realizes build-time prevention depends on D-IMPL-01 (language target) — in Python, structural typing + DI approximates but does not equal build-time prevention.

**D-IMPL-42 — Learning-signal taxonomy naming.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.9.2 vs Fig-CH07-24 (INV-CH7-76). Prose categories (outcome / context-validity / audit-lineage) diverge from figure handler names (Outcome / Correction / Metadata) — an informational naming divergence inside the whitepaper. The SDK's typed learning-signal enum must pick one canonical taxonomy.

**D-IMPL-43 — Closed-loop interpretation step: automated vs human-gated.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.9.1 (INV-CH7-75). "The interpretation step is where business judgment, statistical significance, and regulatory calibration constraints enter the loop" — whether interpretation is automated, human-gated, or configurable is unspecified. Interacts with SDK HITL primitives (CLAUDE.md §8.2) and D-IMPL-29 governance depth.

**D-IMPL-44 — Cold-archive re-hydration contract for compressed replay records.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.10.1/§7.10.5 (INV-CH7-80/81/89). Replay "at any future time the audit obligation requires" plus per-decision graph substate at millions-of-decisions/day scale: the snapshot substrate, the deterministic-hash-based re-hydration mechanism, and the cold-source-archive contract are unspecified. Constrains and is constrained by D-IMPL-06 (snapshot management), D-IMPL-26 (artifact addressing), D-IMPL-27 (substrate split); this entry owns the re-hydration contract specifically.

**D-IMPL-45 — Model-trace composition seam.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.10.2 (INV-CH7-86). The whitepaper assumes a mature deployment composes CCF environment replay with an external model-trace tool (LangSmith/Weave) but specifies no interface for the composition. The SDK's replay-hook seam (CLAUDE.md §7.3 seam 4, SDK-defined) is the natural attachment point — a Phase D design question.

**D-IMPL-46 — Passage-citation provider Protocol.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.10.3 (INV-CH7-87). "Populated by whatever component primitive the deployment has selected" — the Protocol shape for a pluggable passage-citation provider (and its relationship to D-IMPL-09 LLM access) is unspecified.

**D-IMPL-47 — Computable definitions for the F, C, S debt factors.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.7.4/§8.7.1 (INV-CH7-62, INV-CH8-16). The extended form `D_c = 1 − (F · C · S)` is given without specifying how F (freshness), C (completeness), and S (semantic consistency) are individually computed; §7.7.6 names the runtime signals per component but not the factor computations. The SDK must commit a computable definition (or a scoring Protocol) per factor.

**D-IMPL-48 — Supervision Quality: scoring function and SDK-scope disposition.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §8.8 (INV-CH8-19). The composite scoring function combining the five behavioral axes with VLM/LLM reasoning outputs is unspecified — axis weights, fusion function, and score semantics are open. Also open: whether Supervision Quality is SDK mechanism at all or a reference pattern users implement — CLAUDE.md §13 does not list it in v0 scope.

**D-IMPL-49 — Projection-plan selection signature.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.5 (silent on selection inputs); Homecams resolution observed (homecams-patterns appendix). Homecams derives a projection plan from the (agent role, decision intent, product contract) triple. Is that triple the SDK's canonical projection-selection signature, or is intent modeling out of scope? Data point only, never a default.

**D-IMPL-50 — Replay fidelity-lifecycle mechanism: SDK-shipped or ArtifactStore-delegated.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.10.5 (three-tier compression is committed mechanism); homecams-patterns appendix (one working lifecycle). Does the SDK ship the fidelity-lifecycle mechanism (deterministic compression, severity exemption, retention-reason field) as core, or leave retention entirely to the ArtifactStore implementation? Interacts with D-IMPL-06/D-IMPL-27; distinct in that it allocates the mechanism, not the substrate.
