## Open Decisions (D-IMPL)

**D-IMPL-01 through D-IMPL-29** are scaffolded in CLAUDE.md §12, which remains their canonical home — they are referenced here, not duplicated. Status notes:

- **D-IMPL-01 — Language target.** RESOLVED — Python 3.12+ as the sole v0 target; typed contracts as Pydantic v2 `extra=forbid`; Protocol-based seams; no TypeScript port in v0. Rationale: the whitepaper's mechanism commitments are Python-native idioms (structural-typing Π dispatch, `extra=forbid` bases, kw-only `tenant_id` — INV-CH7-12/13/73), CLAUDE.md §11 already presumes Pydantic-in-Python, and the harness ecosystem (D-IMPL-24 candidates) is Python-first. Build-time single-writer prevention gap compensated by the D-IMPL-41 enforcement stack. 2026-07-25. Approver: Dave.
- **D-IMPL-02 — Graph storage substrate.** RESOLVED — `GraphStore` Protocol + reference Postgres implementation + SQLite-for-dev implementation. Rationale: substrate-neutral invariant semantics (INV-CH7-16/17/21/04) carried by the Protocol (see D-IMPL-34); SQLite-for-dev is load-bearing for the §9 examples discipline. 2026-07-25. Approver: Dave.
- **D-IMPL-03 — Vector substrate.** RESOLVED — `SimilarityIndex` Protocol + reference implementation on sqlite-vec (dev default), Chroma as a second reference impl if budget allows. Rationale: the Similarity determinism contract (INV-CH7-27) requires vendor-neutral corpus/index versioning and version pinning in L; sqlite-vec pairs with the SQLite-for-dev graph store for a zero-infra quickstart. 2026-07-25. Approver: Dave.
- **D-IMPL-04 — Runtime topology for v0.** RESOLVED — (a) single distribution with two packages (`ccf` library + `ccf-runtime`) in the monorepo, installable separately; (b) async-first runtime with sync facades; fabric core (operator/projection path) stays sync per the read-only-sync operator contract (INV-CH7-22). Rationale: the `/src` vs `/runtime` seam becomes a packaging boundary reinforcing the harness-neutrality lint; runtime obligations (MCP both roles, A2A, suspended workflows, monitoring triggers) are inherently concurrent. 2026-07-25. Approver: Dave.
- **D-IMPL-05 — Tenancy model.** RESOLVED — multi-tenant with `tenant_id` first-class throughout; single-tenant is the degenerate case (one fixed tenant id), not a separate mode. Rationale: tenancy is structural in the whitepaper (INV-CH7-16 no-untenanted-path; kw-only `tenant_id` per INV-CH7-73(e); tenant in the product cache key per INV-CH7-52); a mode split would fork every signature. 2026-07-25. Approver: Dave.
- **D-IMPL-07 — Embedding model abstraction.** RESOLVED — `EmbedderProtocol` with two reference adapters (one API-based, one local/deterministic for tests); model identity + version exposed as part of the Protocol contract. Rationale: "same embedding model version" is a determinism input (INV-CH7-27), so `(model_id, model_version)` reporting is a Protocol obligation; the local deterministic embedder is replay test-strategy infrastructure. 2026-07-25. Approver: Dave.
- **D-IMPL-08 — Unstructured pipeline (Pattern 5) pluggability.** RESOLVED — each stage as a Protocol with one opinionated reference pipeline wired from the reference implementations. Rationale: the non-negotiable mechanism is the output contract (ingestion-time extraction, typed E/R nodes, passage-level L anchors — INV-CH7-19); stage Protocols express the mode variance of the Alternating Derivation Pipeline (INV-CH8-12) and give the `@algorithmic` lint per-stage enforcement targets. 2026-07-25. Approver: Dave.
- **D-IMPL-09 — LLM access for semantic stages.** RESOLVED — `LLMClientProtocol` with a first-class Anthropic reference adapter carrying the §7.10.3 Citations capability; the Protocol requires model-version reporting and models citation-bearing responses as an optional capability surface. Rationale: replay dimension 3 (Model Version Record) makes version capture a structural obligation of the client contract; one Protocol module gives the `@algorithmic` lint a crisp import target; D-IMPL-46 will own the passage-citation provider Protocol shape specifically. 2026-07-25. Approver: Dave.
- **D-IMPL-10 — Repo shape.** Provisionally resolved as **monorepo** at `github.com/drcastillo/ccf_code` per CLAUDE.md §2.2 (logged 2026-07-24). Remaining open under this entry: whether adapters split into separate packages or repos post-v0.

**D-IMPL-30 — Context Product Contract element count (eight vs nine).** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.3 (INV-CH6-03). Ambiguous passage: §6.3 prose opens "Nine elements jointly specify the contract" and the table lists nine (Assembly Mode included; §6.4 calls it "the §6.3 specification's ninth element"), yet the same §6.3 prose describes "the § 6.1 canonical 8-property table" and CLAUDE.md §5 refers to "the eight-element specification per §6.3." **D-IMPL-31 — TTL granularity: per-signal vs per-product.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.4 Step 4 vs §6.3 (INV-CH6-04). Ambiguous passage: §6.4 Step 4 states "Temporal Validation assigns TTL to each mutation," while §6.3 defines TTL as a per-product contract element, and §6.4's worked thread gives both per-product TTLs (4h/24h) and per-signal TTLs (15 min blotter entry). Readings: (a) TTL exists at two granularities and product TTL derives (e.g., min) from constituent signal validities — consequence: SDK needs a signal-level validity primitive plus a product-level TTL with a defined derivation rule; (b) Step 4's "TTL" loosely means the T-dimension validity envelope and only the contract-level TTL is properly TTL — consequence: SDK type surface must disambiguate half-life-derived validity from contract TTL; (c) product TTL is independently configured per class and Step 4 only validates constituent signals — consequence: no derivation rule, but the asymmetric-freshness mixing-refusal rule still needs formal definition. §7.7 partially informs but does not resolve.

**D-IMPL-32 — Context Trust Triangle scoring mechanics.** Open — awaiting Dave. 2026-07-25. Originates: whitepaper §6.6.3 (INV-CH6-08). Ambiguous passage: "when all three legs hold, the recursion may terminate" — no aggregation function, scale, or threshold mechanics are specified for any leg or the aggregate. Readings: (a) thresholds are Control-Plane-configurable; SDK ships a TrustScore Protocol with pluggable per-leg scorers and a conjunctive combinator — mechanism-not-values; (b) the legs are derived quantities via §7.7 D_c mechanics (the §7.7.8 debt-mapping supports this partially: leg strengths derive from the three debt components) — consequence: no independent trust primitive; (c) the triangle is advisory vocabulary — consequence: no SDK primitive; only replay capture of computed trust inputs. **D-IMPL-34 — Graph-storage Protocol requirement surface.** RESOLVED — the Protocol requires the six invariant semantics and leaves all physical layout backend-internal: (1) compound uniqueness on `(tenant_id, entity_uri)` at the persistence tier (INV-CH7-16); (2) idempotent upsert with set-union lineage accumulation (INV-CH7-17); (3) logical supersession with `superseded_by`/`superseded_at` and as-of reads (INV-CH7-21); (4) append-only-forward (INV-CH7-04); (5) per-relationship-type edge lineage (INV-CH7-20); (6) bitemporal read support (INV-CH7-14 T axis). Backend-internal: collection/table decomposition ("~10 collections" is reference grounding, not normative), indexing strategy, partitioning. Protocol exposes separate reader and writer interfaces as the seam for D-IMPL-41. Conformance verified by a Protocol test suite both D-IMPL-02 reference impls must pass. (Ruling note: Dave initially selected the thinner-Protocol alternative in error and immediately corrected to the recommendation; the ruling of record is the six-semantics surface.) 2026-07-25. Approver: Dave. Originally: Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.3.1 (INV-CH7-15). "The physical representation maps to ~10 collections" is reference-implementation grounding, not a normative count. What the SDK's graph-storage Protocol must require of a backend (compound index, supersession semantics, per-relationship-type lineage, append-only discipline) versus what stays backend-internal is a design decision. Do NOT inherit the Homecams collection layout. Interacts with D-IMPL-02.

**D-IMPL-41 — Build-time single-writer enforcement substrate.** RESOLVED — four-layer enforcement stack (assumes the D-IMPL-01 Python ruling): (1) interface split — separate `GraphReader`/`GraphWriter` Protocols per D-IMPL-34, read-path constructors accept only `GraphReader`; (2) DI-at-boot — composition root constructs exactly one `GraphWriter`, injected into L2/Assembly only; (3) static gate — strict mypy in CI rejects non-L2 `GraphWriter` type references, plus an import lint (same machinery as the `@algorithmic` and harness lints) forbidding the writer module's import outside L2 and the composition root; CI failure = build failure, Python's honest equivalent of "prevented by the type system at build time" (INV-CH7-73(a)); (4) runtime backstop — writer handle constructed with a boot-time token only the composition root can mint. Residual honesty note (Python cannot make determined-insider evasion impossible; claim strength is "no unforced path exists and every forced path fails CI or fails at boot") goes to DESIGN.md's Invariant Preservation chapter. 2026-07-25. Approver: Dave. Originally: Open — awaiting Dave. 2026-07-25. Originates: whitepaper §7.8.4 (INV-CH7-73). "Compilation of those services against write-capable interfaces is prevented by the type system at build time" assumes a compiled/typed substrate; how the SDK realizes build-time prevention depends on D-IMPL-01 (language target) — in Python, structural typing + DI approximates but does not equal build-time prevention.
