# Release-hardening incident — 2026-09-22

**A documented control violation, not an accidental write to a generally
mutable store.** Classified by Dave, 2026-09-22, after the write path had been
traced and the blast radius measured.

CLAUDE.md §9 establishes the contract in absolute terms: *"reads go to `.76`,
writes go to a local disposable store. Never the reverse."* and *"Nothing seeds
`.76`, ever."* That rule was violated once during the release-hardening pass.

---

## The statement the final qualification package must carry, verbatim

> **Release-hardening incident:** the established read-only estate policy in
> CLAUDE.md §9 was violated once during testing. The curated `ccf:main` ledger
> received 134 unintended append-only transactions, advancing from `t=1474` to
> `t=1608`. The violation was bounded, the write path was identified, and a
> structural session-level fence was added to prevent recurrence.

This paragraph is a **release requirement**, not a summary. Any qualification
or release document produced from this repository states it.

## What happened

Investigating six failing `test_s1_01_governed_resolver_adoption` nodes, an
environment script was generated by extracting every variable the example tests
and environment documents declare, then mapping them to values **by suffix
pattern** — `*_FLUREE_URL` to the estate's Fluree, `*_POSTGRES_SCHEMA` to
`ccf_v2`, and so on.

`CCF_TEST_FLUREE_URL` ends in `_FLUREE_URL`. It names the **local disposable
store**, not the estate. The pattern swept it up, and `s1-01` — which writes,
because it boots and populates a fresh fabric per call — wrote to `.76`.

## The blast radius, measured before and after

| | ledgers | `ccf:main` `t` |
|---|---|---|
| before | 30 | **1474** |
| after one test node | 30 | **1608** |

- **No new ledger was created.**
- **`fibo-v2` was not touched** (`t=5878` before and after, and unchanged since).
- **The 27 known `ccf:cp04-*` branches are unchanged** — 7 `cp04-debt-*` and
  20 `cp04-examples-*`, each still at `t=1`.
- Fluree is append-only. **No rewind, deletion or compensating write was
  attempted, and none is implied.** The 134 transactions are permanent.
- `ccf:main` has stayed at **`t=1608`** across every subsequent run.

## The write path, traced to one variable

- **Every Fluree writer in the test suite** is built from `tests/conftest.py`'s
  `fluree_url` fixture, whose only source is **`CCF_TEST_FLUREE_URL`**. One
  door.
- **Example acquisitions cannot write at all.** Measured: **zero**
  non-query Fluree calls across every `examples/*/acquisition.py`; they issue
  only `/v1/fluree/query` and `/v1/fluree/ledgers`, both reads. The ~23
  `CCF_CP_NN_FLUREE_URL` variables pointing at `.76` are **read paths** and
  were never the exposure.

## Why the existing guard did not fire

`tests/examples/estate_guard.py::refuse_to_write_the_curated_estate` exists for
exactly this accident — its own docstring names the 27 `cp04-*` ledgers as the
reason it was written. It did not fire, for two measured reasons:

1. **It only protects modules that import it.** Nine test modules name
   `CCF_TEST_FLUREE_URL` or `CCF_TEST_POSTGRES_DSN`; **two** called the guard.
2. **The nine were never the whole exposure.**
   `test_s1_01_governed_resolver_adoption` reaches the store through its
   example's own `artifacts/backends.yaml` and **names the variable nowhere**.
   No per-module call site could have caught it.

## The structural repair, and its release status

A **session-scoped autouse fixture** in `tests/conftest.py` calls the same
guard once, before any test can write, and refuses **the run** rather than a
call — refused, never silently redirected, on the guard's own reasoning that
redirecting would run a suite against a store nobody chose.

It raises through `pytest.fail(..., pytrace=False)` for a credential reason
found while testing it: the guard redacts the password out of its *message*,
but a pytest traceback renders the raising frame's arguments, and one of them
is the raw DSN.

`tests/examples/test_curated_estate_write_fence.py` proves it, including the
positive control — a `localhost` store must run through, or a fence that
refused everything would pass every negative test.

**RELEASE REQUIREMENT (Dave, 2026-09-22).** The read-only fence is a release
requirement, not a cleanup item. *"The SDK can still release, but only after
the hardening branch containing that fence is reviewed and merged, and final
qualification runs with `.76` technically protected from writes."*

So the release sequence is constrained:

1. the hardening branch carrying the fence is reviewed and **merged**;
2. final qualification runs **with the fence active**, so `.76` is technically
   protected from writes for the duration of the qualification run;
3. the qualification package carries the verbatim statement above.

## What was deliberately not done

No repair of the curated ledger: no deletion, no rewind, no compensating
writes. No restart of the stopped `ccf-fluree-15-3` container the six `s1-01`
tests actually need — that is the estate owner's decision, and those nodes stay
recorded as **NOT EXECUTED** rather than skipped.
