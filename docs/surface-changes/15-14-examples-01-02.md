# 15-14 — examples/01-agent-basics and examples/02-skilling reshaped to typed artifact documents

Plan 15-14 adds **no** public Python surface: `tools/dump_surface.py --report`
shows nothing added by this plan (the accumulated set it prints belongs to
15-01 through 15-13). Every entry below is therefore `Public surface: false`.

The two examples' multi-artifact bundles are now typed, closed-world,
`$schema`-annotated documents — twenty for example 01 and eighteen for
example 02 — enumerated by one deployment manifest each. An adopter who copied
either example's artifacts needs the mapping, which is what this fragment is
for. Both examples follow the recipe plan 15-13 established for the quickstart;
the entries below record only what is specific to these two.

**No document in either example uses a deferral marker or any other escape
hatch.** Every `*.yaml` under both `artifacts/` directories carries a real
`# yaml-language-server: $schema=` first line naming a committed schema —
either the class's own, or the `ccf.declared-artifact` envelope for
deployment-authored classes (the route 15-13 opened). Six SDK-owned classes had
no committed schema before this plan; the last entry records what was done
about that.

## docs/schemas/ccf.agent-definition.json, ccf.prompt-artifact.json, ccf.task-definition.json, ccf.skill-catalog-entry.json, ccf.skill-grant.json, ccf.workflow-definition.json

- Surface: docs/schemas/
- Public surface: false
- Change type: added
- Before: absent — these six SDK-owned classes had no committed schema, so a hand-authored agent definition, prompt artifact or skill catalog entry had no honest `$schema` target and could only pass `make schema-headers` with a deferral marker
- After: committed JSON Schemas, emitted by `tools/dump_schemas.py` from a second set, `author_versioned_classes()`, alongside the `SDK_ARTIFACT_CLASSES` set and the envelope
- Why: all six carry D-IMPL-28 two-field versioning and register through `register_versioned`, whose D-05 bump check holds the author's `artifact_version` claim against content identity. `load_and_boot` registers through `register_typed`, which does not run that check — so they are deliberately **not** manifest-addressable, and adding them to `SDK_ARTIFACT_CLASSES` would have silently dropped the governance they exist to carry. They are nonetheless SDK-owned schemas an adopter authors by hand, so they are committed without becoming addressable, on the same reasoning that admitted the `DeclaredArtifact` envelope in 15-13
- Migration: point your agent definitions, prompt artifacts and skill catalog entries at their own committed schema, and keep registering them through `register_versioned` rather than through a manifest

## tools/check_schema_headers.py

- Surface: tools/check_schema_headers.py
- Public surface: false
- Change type: behavior
- Before: a `$schema` header could only name a member of `SDK_ARTIFACT_CLASSES`, and the envelope route refused only class ids in that same set
- After: both the header lookup and the envelope route's refusal read the union of the manifest-addressable and author-versioned sets
- Why: without the second half, an agent definition could annotate itself as deployment-authored — its class id is absent from `SDK_ARTIFACT_CLASSES`, which used to be the whole test — and have every constraint `AgentDefinition` declares go unchecked
- Migration: none — existing headers are unaffected
