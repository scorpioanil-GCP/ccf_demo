# 15-12 — schema export (ERGO-12)

Committed JSON Schema per SDK artifact class, an HTTP route and CLI noun to
export one, and a correctness gate over the `$schema` headers example
artifact documents carry.

## ccf_runtime.cli.commands.schema.register

- Surface: ccf_runtime.cli.commands.schema.register
- Public surface: true
- Change type: added
- Before: absent — no CLI path to an artifact class's JSON Schema
- After: the ninth noun, `ccf schema export [--class-id ID]`, returning
  `RequestSpec`s against `/schema` exactly like the other eight
- Why: D-IMPL-79. `ccf schema export` (D-04) is in-process JSON Schema
  generation with no fabric handle behind it, so the obvious implementation
  is a local path in the CLI — which would be `main()`'s first
  non-`RequestSpec` branch and would weaken the documented posture from
  "every command travels the same routes any client uses" to "every command
  except schema export". The first exception is the one that makes the
  second easy, so the route was added instead and the noun stayed uniform.
  D-IMPL-22's noun enumeration is amended to nine as the mechanical
  consequence; `tests/http_api/test_routes.py` reads that text to hold the
  mounted prefixes to it.
- Migration: none — a new noun; nothing existing moved

## ccf_runtime.http_api.routes.schema.build_router

- Surface: ccf_runtime.http_api.routes.schema.build_router
- Public surface: true
- Change type: added
- Before: absent — the SDK's artifact-class schemas were not reachable over
  the wire
- After: two read-only endpoints, `GET /schema` (the class ids the SDK owns
  the schema of) and `GET /schema/{class_id}` (that class's JSON Schema),
  emitted from the live models with an unowned id returning a typed 404
- Why: the route D-IMPL-79 rules the CLI noun onto. It generates from
  `SDK_ARTIFACT_CLASSES` rather than reading `docs/schemas/` off disk, on
  the same relation `create_app().openapi()` has to the committed
  `openapi.json` — a route serving the committed files would make the
  freshness gate circular, agreeing with itself and with nothing else. The
  route holds no fabric handle: artifact classes are SDK mechanism, not
  deployment state. Note the path prefix is singular `/schema`, matching the
  CLI noun and the other eight prefixes, rather than the plural the plan
  text used.
- Migration: none — a new read-only surface

## docs/schemas/

- Surface: docs/schemas/
- Public surface: false
- Change type: added
- Before: absent — an adopter authoring an artifact document had no schema
  to point an editor at, and marshalling errors surfaced at boot
- After: one committed JSON Schema per entry in `SDK_ARTIFACT_CLASSES`
  (eleven today), each annotated `x-ccf-class-id`, regenerated by
  `make schemas` and held to the live models by a bytes-equality gate in the
  always-on `test` job that fails on drifted, missing, **and orphaned** files
- Why: D-11's generate-at-build posture has one standing exception, D-12's
  committed `openapi.json`, for contracts external consumers read. The
  schemas are the same case one step earlier: they are what adopters author
  *against*, in an editor, before anything runs, and a schema that exists
  only at build time cannot be the target of a `$schema` header in a
  checked-in document. Classes the SDK does not own get no committed schema
  — the SDK never invents one for a namespace that is not its own.
- Migration: run `make schemas` after adding or changing an `ArtifactClass`;
  a stale tree is a red build, not a silent difference

## make schemas

- Surface: make schemas
- Public surface: false
- Change type: added
- Before: absent
- After: regenerates the committed `docs/schemas/` tree from
  `SDK_ARTIFACT_CLASSES`; `tools/dump_schemas.py --check` is the
  write-nothing form the gate uses
- Why: the single documented command surface (D-10) — every target CI runs, a
  developer runs the same way. The failure message names this target, because
  a failure nobody can act on is a failure that gets muted.
- Migration: none

## make schema-headers

- Surface: make schema-headers
- Public surface: false
- Change type: added
- Before: absent — nothing checked that a `$schema` header was *correct*
- After: `tools/check_schema_headers.py` verifies, per artifact document,
  that the header resolves from the document's **own directory** (as an
  editor resolves it, not as a repo-root-relative test would), that the
  target is a committed schema annotated with a real SDK class id matching
  its file name, that the named class's contract **actually accepts the
  document**, and that any deployment manifest in the directory declares the
  same `class_id` the header names. Auto-arming: a directory joins the
  checked set as soon as it carries its first header, so each example-rewrite
  plan gates its own headers at its own wave. `DIR=<path>` narrows it;
  `--require-all` is the tree-wide form for the phase close.
- Why: an editor hint has a failure mode no runtime has — it can be wrong for
  months and nothing breaks, because nothing reads it but the adopter's
  editor, which will happily annotate a document with confident nonsense from
  a real schema for the wrong class. Existence of the target is therefore not
  the property worth gating; correctness is. Validating through the SDK's own
  `load_artifact` makes the check exactly as strong as the validator the
  adopter's fabric runs at boot, and costs no new dependency.
- Migration: run `make schema-headers DIR=<your artifacts dir>` when adding
  headers

## examples/00-quickstart/artifacts/

- Surface: examples/00-quickstart/artifacts/
- Public surface: false
- Change type: added
- Before: no schema annotation of any kind
- After: each document carries an explicit
  `# ccf-schema: deferred(15-13) …` first line
- Why: **no SDK artifact class accepts any of these four documents today** —
  verified, not assumed — because each is a multi-artifact bundle and the
  contracts are `extra=forbid`. A `$schema` header on such a file would
  annotate every key belonging to the other artifacts as an error, so the
  "hint" would be a wall of false positives in the adopter's editor: worse
  than no header. Plan 15-13 splits these into typed per-class documents with
  a manifest and writes the real headers then, which is also when they become
  reviewable alongside the reshaped documents. The deferral is explicit,
  greppable, names the plan that closes it, and is *counted* — a document with
  neither a header nor a marker fails the gate, so nothing falls through
  silently.
- Migration: none — the markers disappear at 15-13
