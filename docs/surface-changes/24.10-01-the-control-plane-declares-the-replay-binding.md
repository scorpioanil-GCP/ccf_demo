# 24.10-01 — the Control Plane declares the replay binding

Plan `24.10-01`, requirement row `R-12`. The ruling of record is `D-IMPL-282`
`R-12` option 2a (Dave, 2026-09-08): *"The `replay:` Control Plane section
supplies defaults. Explicit constructor arguments override the declaration. No
builder API break in 24.10. The declared binding must actually be consumed and
exercised; declaration-only is insufficient."*

The evidence that produced the row is cp-05's own, quoted from
`examples/cp-05-credit-exposure-rollup/artifacts/replay.yaml` (read, never
edited, under the phase boundary): the Control Plane document's section
vocabulary is closed and a `replay:` section is refused by name, so *"it leaves
a deployment's own replay binding with nowhere declared to live. cp-04 put
these three strings in `deployment.py` as module constants; this rung puts them
in an artifact instead. Neither is the Control Plane."*

## ccf.controlplane.artifacts.ReplayBinding

- Surface: ccf.controlplane.artifacts.ReplayBinding
- Public surface: true
- Change type: added
- Before: absent — a deployment's replay binding had no declared home, so it lived either as module constants in the deployment's own Python or as an adopter-namespaced artifact beside the config, and neither is the Control Plane
- After: a `VersionedArtifact` carrying `record_class`, `query_pin_class` and `store_dirname`, and nothing else; a fourth key is refused by the inherited `extra=forbid`, and a `store_dirname` that is absolute, rooted, drive-qualified or carries a `..` segment is refused by name through the same `_leaves_its_own_directory` predicate `ManifestEntry.path` is held to
- Why: `D-IMPL-282` `R-12` — replay binding becomes a first-class Control Plane concern with the smallest declarative addition that could carry it, and the three-member closure is how *"No product-specific replay semantics in the Control Plane—only deployment binding/configuration"* is enforced by the contract rather than by prose
- Migration: none. The `replay:` section is optional and a deployment that declares none derives exactly what it derived before.

## ccf.controlplane.artifacts.REPLAY_BINDING

- Surface: ccf.controlplane.artifacts.REPLAY_BINDING
- Public surface: true
- Change type: added
- Before: absent
- After: `ArtifactClass(class_id="ccf.replay-binding", contract=ReplayBinding)`, registered in `ccf.deployment.classes.SDK_ARTIFACT_CLASSES` so a manifest — and the derived `replay:` section — can name it
- Why: a class the SDK ships that a manifest cannot address is a class no adopter can register, and the reserved-section derivation resolves the class id through the same lookup every manifest entry does
- Migration: none.

## Two counts move, and they are different counts

`ccf.deployment.config._RESERVED_SECTIONS` was an **8-entry** mapping and is
now a **9-entry** one. `DeploymentConfig`'s class docstring documented **nine**
reserved section names — the eight mapping entries plus `operators`, which the
mapping handles separately — and now documents **ten**. Both numbers are
stated in the code beside what they count, so a reader comparing them is
comparing two different things on purpose.

## What did NOT change

- **`GovernedResolver` is untouched.** Its fields stay required and
  defaultless; only `build_governed_resolver` resolves a default.
- **`ccf.client.adapters.binding_document`** already carries these three
  members in the client's `binding.yaml`, which is a client wiring document and
  not the Control Plane. It passes all three explicitly and therefore wins
  under the ruled precedence, unchanged.
- **No shipped config gains a section.** Every existing `ccf_config.yaml`
  derives byte-for-byte what it derived before; `replay` is appended last in
  the derivation order so a config without one produces the same key order it
  always did.
