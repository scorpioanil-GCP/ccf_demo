# 24.1.1-03 — a governed refusal returns as data

Plan `24.1.1-03` closes `D-60`. `src/ccf/agents/assembler.py::ContextAssemblerProtocol`'s
`assemble` returned `AssemblyOutcome` and nothing else, so a conforming assembler holding a
governed refusal could only **raise** — in a codebase whose stated posture is the opposite.
`src/ccf/products/request.py::ProductRequestViolation`'s own docstring says it: *a refusal
returned as data cannot be swallowed by a bare* `except`. This phase converts; it invents
nothing.

## What did NOT change

On this change the negatives carry more information than the positives.

- **No new refusal type was minted.** `src/ccf/products/refusal.py` is untouched — 0 diff
  lines against the phase base — because
  `src/ccf/products/request.py::ProductRequestViolation` is **already** a `REFUSAL_KINDS`
  member. Measured, not asserted: `tests/products/test_refusal_envelope.py` is green on the
  shipped tree **and was watched RED on a planted `…Refusal` decoy class** added to
  `src/ccf/agents/assembler.py`, which tripped both the set-equality gate and its allowlist
  control. A green exhaustiveness gate with no decoy is a gate nobody has shown to look.
- **`src/ccf/agents/errors.py::AssemblyRefused` is KEPT.** The boundary, in one sentence: a
  *governed* refusal — this question does not conform to the contract it addresses — is data
  and returns; an *identity* disagreement — wrong tenant, or a role this agent was not
  declared under — stays an exception, because it says the caller reached the wrong agent
  rather than that the answer is a refusal. Both pre-existing `AssemblyRefused` tests are
  unchanged and pass.
- **No implementation widened its annotation.** Return types are covariant, so
  `examples/cp-00-institutional-holders/assembler.py::HoldersAssembler` and the test
  assembler stay conforming with `-> AssemblyOutcome`. Evidence: `mypy` clean over 211
  source files with no implementation edited.
- **`src/ccf/replay/serve.py` and `src/ccf/products/resolver.py` are untouched.**
  `D-IMPL-214` refused Reading A explicitly, which is what would have pulled them in.

## Surface

- Surface: ccf.agents.assembler.DeterministicAssembler
- Public surface: true
- Change type: behavior
- Before: `(agent: 'Agent', projection: 'ProjectionOutput', acquisitions:
  'tuple[AcquiredContent, ...]' = ()) -> None` — the reference assembler could only succeed
  or raise, so the SDK's own worked example demonstrated *raise-or-succeed* while the
  codebase taught refusal-as-data
- After: the same constructor plus one optional field, `request_contract:
  'ProductRequestContract | None' = None`. With it absent the assembler is byte-for-byte
  what it was; with it present, `assemble` makes ONE call into
  `src/ccf/products/request.py::refuse_request` and RETURNS the resulting
  `ProductRequestViolation`
- Why: `D-IMPL-214`, ruling on criterion 6 — *"`DeterministicAssembler` is what deployments
  diff against. If only a test-local assembler can refuse, the reference impl still
  demonstrates 'raise or succeed' and criterion 6 becomes theater."* The conformity check is
  ordered AFTER the two identity checks, because a question asked of the wrong agent is not
  a question about a contract's conformity
- Migration: none — additive and keyword-only with a default

- Surface: ccf.agents.DeterministicAssembler
- Public surface: true
- Change type: behavior
- Before: the package re-export of the same class, carrying the same constructor shape
- After: the same re-export, carrying the reshaped constructor above
- Why: the same change, visible at the package boundary because `ccf.agents` re-exports the
  symbol. Recorded as its own entry because the manifest records it as its own entry — and
  because the plan predicted ONE reshaped entry where the tree has TWO, which is the reason

- Migration: none — additive and keyword-only with a default

## A blind spot in the surface gate — RECORDED, not closed

**The single most consequential change in this phase moves ZERO manifest entries.**
`ccf.agents.assembler.ContextAssemblerProtocol`'s recorded shape is `"(*args, **kwargs)"` —
its *constructor* — so widening `assemble`'s **method** return type from `AssemblyOutcome` to
`AssemblyOutcome | ProductRequestViolation` is invisible to the gate that exists to catch
consequential changes. Measured: the reshape list names only the two `DeterministicAssembler`
entries and the two `build_operator_registry` entries from plan `24.1.1-02`.

A fix would be the surface dumper capturing Protocol *member* signatures rather than only the
class constructor. **This phase does not do it.** It is tooling, it is outside the
`D-IMPL-213` fence, and `D-IMPL-214` admits no fourth file. It is carried forward in
`24.1.1-06`'s verification record so it survives between a fragment and a SUMMARY.

Adjacent, and found in the same phase: `24.1.1-02` measured that `unclaimed_drift` treats a
drifting name as claimed when the name **or its dotted module** appears in any fragment, so a
Phase 15 fragment silently claimed this phase's `ccf.deployment.operators` reshape. Same gate,
two different holes, both recorded and neither closed.
