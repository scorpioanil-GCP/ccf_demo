# 15.2-13 — the MongoDB backend: staged aggregation pushdown behind the `mongo` extra (D-06)

Plan 15.2-13 ships the fifth and last adapter of Phase 15.2 — the phase's
hardest differential target and its named risk budget (D-06). MongoDB is also
the Homecams triangulation point: the substrate a real CCF realization
persisted its fabric on, reproduced here as *mechanism* with every domain
value factored out (CLAUDE.md §2.1). Four public names are added
(`ccf.graph.backends.mongo.MongoGraphStore`,
`ccf.graph.backends.mongo.MongoGraphReader`,
`ccf.graph.backends.mongo.DEFAULT_PARTITION`,
`ccf.graph.backends.mongo.DEFAULT_DATABASE`); `ccf.boot.boot` gains a
`mongo_uri` / `mongo_partition` selector pair; and
`DeploymentManifest.backend` extends its Literal with `"mongo"`. The
writer-side machinery (`_MongoTxn`, `MongoGraphWriter` in
`ccf.graph._writer`) is invisible to the name-level manifest — the module is
import-restricted by CINV-02 — and carries a `behavior` entry per the 15.1-11
precedent. Everything is extras-gated: the tree without the `mongo` extra
installed stays fully importable and fully green.

## ccf.graph.backends.mongo.MongoGraphStore

- Surface: ccf.graph.backends.mongo.MongoGraphStore
- Public surface: true
- Change type: added
- Before: absent — no document substrate existed; the four shipped adapters
  were two SQL backends, an in-memory KV floor and a graph-native engine
- After: `MongoGraphStore(uri=…, partition=…, database=…)` — connection and
  index owner over the official `pymongo` driver (extra-gated, lazy
  in-constructor import per the chroma_index / neo4j precedent; constructing
  the store is the first moment the dependency is demanded). Physical model
  is adapter-owned (D-IMPL-34): six collections mirroring the relational
  layout, claim documents carrying `claim_json` verbatim plus write-time
  projections of predicate-relevant fields, timestamps as canonical RFC3339
  UTC text (never BSON dates — the byte-drift trap), compound unique indexes
  rendering the identity semantics, and a **doubled-edge traversal
  collection** — every edge stored forward AND reverse, because
  `$graphLookup` is directed while CCF traversal is undirected and two
  directed lookups do not compose (15.2-RESEARCH.md Pitfall 3). `partition`
  names one fabric's graph inside one database — the Postgres schema role —
  so `graph_identity` (host/port/database/partition, never credentials —
  threat T-15.2-05) distinguishes fabrics per partition. Offers `reader`,
  `collection()`, `scope()`, `close()`, and context management
- Why: D-06 ships all five adapters, and the aggregation pipeline is the
  substrate family neither SQL nor Cypher represents — the proof that the
  read seam is not shaped like a query language
- Migration: new surface — none. `boot(mongo_uri=…)` constructs the store;
  install with `pip install "ccf[mongo]"`

## ccf.graph.backends.mongo.MongoGraphReader

- Surface: ccf.graph.backends.mongo.MongoGraphReader
- Public surface: true
- Change type: added
- Before: absent
- After: a `GraphReader` over the database, inheriting the whole shared read
  path from `BaseGraphReader`: five acquisition reads answer dict rows into
  the substrate-neutral materialization core
  (`ccf.graph.reader.materialize_view` — lineage-at-boundary,
  supersession-as-of, ordering and freezing are inherited, never
  re-implemented; 15.2-RESEARCH.md Pitfall 5). MongoDB's dialect is a
  *document*, not a statement, so the five `SELECT_*` slots the base declares
  carry the **name** of each read and `_query` builds the filter from the
  typed positional parameters — strictly stronger than statement text for the
  T-15.2-01 surface, because there is no query language for a value to be
  mistaken for. `as_of()` is the D-07 degenerate-query derivation;
  `attestation` reports tier 1. The `_translate_query` hook answers the
  **whole** query (GQ-32) natively: `$match` filter documents for every record
  predicate, and — **stage 2, promoted after the corpus proved parity** — one
  `$graphLookup` over the doubled-edge collection for the traverse family,
  with hop admissibility and `allowed_entities` membership carried in
  `restrictSearchWithMatch`, `maxDepth = depth_limit - 1`, explicit seed
  re-inclusion, and the stage skipped entirely at `depth_limit=0`
  (15.2-RESEARCH.md Pitfall 3's three corrections plus the doubled layout)
- Why: the fifth adapter's read half, held to the same differential
  byte-identity bar as the other four
- Migration: new surface — none. Promotion is invisible to callers and to
  replay by construction: what was translated versus scanned is telemetry
  (`translated_answers` / `fallback_answers`), never a replay input (GQ-34)

## ccf.graph.backends.mongo.DEFAULT_PARTITION

- Surface: ccf.graph.backends.mongo.DEFAULT_PARTITION
- Public surface: true
- Change type: added
- Before: absent
- After: `"ccf"` — the partition a store attaches to when the caller does not
  say otherwise; a name, not a tuning value (CINV-01), mirroring
  `ccf.graph.backends.postgres.DEFAULT_SCHEMA` and
  `ccf.graph.backends.neo4j.DEFAULT_PARTITION`
- Why: partitions are what make "a fresh graph per boot" true on a shared
  server; the default names the single-fabric case
- Migration: new surface — none

## ccf.graph.backends.mongo.DEFAULT_DATABASE

- Surface: ccf.graph.backends.mongo.DEFAULT_DATABASE
- Public surface: true
- Change type: added
- Before: absent
- After: `"ccf"` — the database a store attaches to when neither the URI path
  nor the caller names one. Same posture as `DEFAULT_PARTITION`: a name,
  never a value
- Why: a MongoDB URI may or may not name a database, and a store that guessed
  differently per URI shape would make `graph_identity` — the key the
  single-writer boot check uses — depend on how the deployment happened to
  spell its connection string
- Migration: new surface — none

## ccf.boot.boot

- Surface: ccf.boot.boot
- Public surface: true
- Change type: reshaped
- Before: `boot(*, database_path=None, postgres_dsn=None, postgres_schema=…,
  memory=False, neo4j_uri=None, neo4j_partition=None, registry, …)` — exactly
  one of {`database_path`, `postgres_dsn`, `memory=True`, `neo4j_uri`}
  selected the substrate
- After: a `mongo_uri: str | None = None` keyword joins the selector set (with
  `mongo_partition: str | None = None` riding along in the
  `neo4j_partition` / Postgres `postgres_schema` role); the exclusivity check
  now reads exactly one of {`database_path`, `postgres_dsn`, `memory=True`,
  `neo4j_uri`, `mongo_uri`}, refused in the same
  the-fabric-does-not-infer-its-substrate ValueError style. The mongo branch
  imports the backend lazily, so boot stays importable — and every other
  branch stays bootable — without the extra
- Why: explicit selection, never inference (the `_open_backend` posture),
  extended to the fifth and last substrate of the phase
- Migration: none for existing callers — the new keywords default to `None`
  and every existing selector is untouched

## ccf.controlplane.artifacts.DeploymentManifest

- Surface: ccf.controlplane.artifacts.DeploymentManifest
- Public surface: true
- Change type: reshaped
- Before: `backend: Literal["sqlite", "postgres", "memory", "neo4j"]`
- After: `backend: Literal["sqlite", "postgres", "memory", "neo4j", "mongo"]`.
  A `mongo` manifest declares the kind only (D-08); the connection URI is
  environment-supplied through `load_and_boot`'s new `mongo_uri` argument,
  mirroring `neo4j_uri` and `postgres_dsn` exactly — a MongoDB URI can carry
  userinfo, and a content-hashed audit artifact must never persist one
  (threat T-15.2-05). Preflight refuses a `mongo` declaration with no URI and
  refuses the URI alongside any other declared backend, before any document is
  read. The re-export `ccf.deployment.DeploymentManifest` reshapes
  identically. The committed `docs/schemas/ccf.deployment-manifest.json`
  regenerated (ERGO-12)
- Why: Open Question 4's resolution — all three new backends join `boot()` and
  the manifest Literal in-phase, each in its owning plan; this is the last of
  the three
- Migration: none for existing manifests — all four existing kinds are
  untouched; new manifests may declare `backend: mongo` and supply
  `mongo_uri` from the environment

## ccf.graph._writer.MongoGraphWriter

- Surface: ccf.graph._writer.MongoGraphWriter
- Public surface: false
- Change type: behavior
- Before: the typed write seam (`_GraphTxn`, plan 15.2-02) had two non-SQL
  implementations — `_MemoryTxn` (15.2-06) and `_Neo4jTxn` (15.2-12) — beside
  the shared SQL adapter, and every one of them held an open substrate
  transaction
- After: `_MongoTxn` implements the nine typed operations as **buffered
  pymongo bulk operations** — the first *batched* implementation of the seam,
  and the case the `_GraphTxn` contract names in as many words (D-IMPL-88):
  mutating operations resolve their rowcounts before commit from committed
  state read before buffering plus the buffer's own contents (sound because
  INV-CH7-10 guarantees no concurrent writer), and `select_*_chain` merges the
  committed chain with the claim appended earlier in the same transaction.
  Buffering rather than a MongoDB multi-document transaction is deliberate: a
  plain `mongo:7` deployment is a standalone server and multi-document
  transactions require a replica set, which a GitHub Actions service container
  cannot be asked to start — so the adapter's conformance does not depend on a
  topology. Ordering inside a collection is preserved by
  `bulk_write(ordered=True)`, which is what lets the chain restitch update a
  claim the same transaction inserted; every operation is an upsert on its
  compound identity, so the writer's whole algorithm stays idempotent
  (INV-CH7-04). The doubled-edge traversal documents are maintained here, in
  the same buffered transaction as the relationship node they double, so the
  layout cannot drift from the edge it represents. Write-time projections
  (`_mongo_claim_projection`) store the predicate-relevant claim fields —
  validity window re-rendered through `canonical_timestamp`, `entity_class`,
  string-valued attributes whose names `attribute_field_path` admits as
  document field paths. All of it lives in `ccf.graph._writer` only (CINV-02;
  threat T-15.2-06 — no write operation exists in the reader module)
- Why: D-05/D-06 lock that conformance writes go through booted L2, and a
  document store executes neither SQL nor Cypher; the typed seam exists
  precisely so this class could be written without interpreting SQL constants
- Migration: none — the module is import-restricted to `ccf.assembly` /
  `ccf.boot`; deployments reach the writer only through `boot(mongo_uri=…)`
