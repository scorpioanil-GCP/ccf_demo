# 24.5-14 — the product door answers 409 for a declared-obligation refusal, and states DIV-4 for every other kind

Plan `24.5-14`, ledger row `24.5-L-14` (the door half; `D-IMPL-236`). The
gate half is plan `24.5-13`'s (`GATE_DECLARED_OBLIGATIONS`,
`DeclaredObligationRefusal`, kind `declared-obligation-refusal`). This plan
gives the HTTP product door its FIRST typed refusal status — ROADMAP Phase
24.5 criterion 21's "typed `409`" — for exactly that one kind, and proves the
same kind at the MCP door with no runtime edit.

## What did NOT change, stated first

- **No signature moved.** `tools/dump_surface.py --report` shows no drift for
  `ccf_runtime.http_api.routes.product`: `build_router(deps, *,
  entitlement_source=None, perspective_resolver=None) -> APIRouter` is
  byte-identical in shape, and the route's query surface (`role`, `subject`,
  `intent`, `freshness`, `asked_at`, `parameters`) is unchanged. The one
  entry below is `behavior` for that reason.
- **No second mechanism, no gate, no payload inspection** (`D-IMPL-237`,
  `D-IMPL-238`). The door MAPS a refusal it already receives to a status; it
  decides nothing. The envelope comes from
  `src/ccf/products/door.py::door_refusal` — the same translation both MCP
  doors run — and the kind is compared to
  `REFUSAL_KINDS[DeclaredObligationRefusal]` by the mapping's value, never a
  string literal (T-24.5-38).
- **Every existing status the door answers stays** (`D-10`): a served product
  answers `200` with the same bytes as before (compared against
  `canonical_response`'s own output for the same product);
  `400` / `403` / `404` / `503` are decided before the new branch is reached.
  `tests/http_api/test_product_declared_obligation_409.py::test_a_served_product_still_answers_200_with_the_same_bytes`
  and `::test_the_existing_refusal_statuses_are_unchanged`.
- **Every OTHER refusal kind keeps the pre-plan behavior, explicitly** —
  DIV-4 preserved and scoped. A `ttl-refusal` envelope (or any of the other
  eighteen kinds) still reaches `served_answer` and raises `TypeError` naming
  the shape, the opaque 500, because the status and body for the remaining
  kinds is a ruling nobody has made.
  `::test_any_other_refusal_kind_still_reaches_served_answer` asserts it.
- **The MCP door is unedited.** `runtime/ccf_runtime/mcp/egress.py` names
  neither `DeclaredObligationRefusal` nor `declared-obligation`; the kind
  arrives at a real `ClientSession` as `outcome.refusal.kind` with
  `is_error False` through the envelope Wave 2 shipped.
  `tests/mcp/test_egress_declared_obligation.py`.
- **No example was edited.** `examples/` is closed. cp-01's `CPR-G08`
  observation ("200 with the debt block rather than 409", `24.5-09`) is plan
  `24.5-16`'s flip candidate; nothing here makes it true by editing cp-01.

## ccf_runtime.http_api.routes.product.build_router

- Surface: ccf_runtime.http_api.routes.product.build_router
- Public surface: true
- Change type: behavior
- Before: the door had no refusal channel (DIV-4). A resolver answering with any `RefusalEnvelope` reached `served_answer`, which raised `TypeError` naming the shape — an opaque 500 for every kind alike; the module docstring said rendering a fabric refusal over HTTP was a status and body decision nobody had ruled
- After: `retrieve` routes the resolver's answer through `door_refusal(resolved, asked=asked, product_class=..., version=...)` before `served_answer`. An envelope whose `kind == REFUSAL_KINDS[DeclaredObligationRefusal]` (`declared-obligation-refusal`) returns `JSONResponse(status_code=409, content={"kind": <kind>, "refusal_type": "DeclaredObligationRefusal", "refusal": <the whole envelope, canonically rendered>})` — the `routes/skill.py` body shape, so the gate's `declared`/`observed` pair, the request identity and the pre-assembly lineage all travel. A bare `DeclaredObligationRefusal` on a call that posed a question is translated by the door and answered the same way (lineage honestly `None`); a bare refusal on a call with no question is `door_refusal`'s documented `ValueError` — no response, as before, now naming why. Every other envelope falls through to `served_answer` exactly as before. The module docstring names the one mapped kind and DIV-4 for the rest in place of the sentence that said the door had no refusal channel
- Why: `24.5-L-14`; `D-IMPL-237` (the one structural mechanism, whose refusal the Standard §9 says the door answers as "409 with the debt block"); ROADMAP Phase 24.5 criterion 21. Additive: a status is added and none is moved (`D-10`). Sabotage: `tests/http_api/test_product_declared_obligation_409.py::test_the_status_check_refuses_a_200_for_a_declared_obligation` (the predicate over a fake 200, a 409 of another kind, and no response — each RED naming the kind) and `::test_a_door_with_the_409_branch_removed_is_red_by_name` (a scratch copy of the route with the decision line made `False`, loaded under another name and bound into `create_app` for one build — RED by name; its control leg answers 409; the shipped module byte-compared before and after)
- Migration: none for a served product or for any existing refusal status. A client of this door that reached an opaque 500 for an over-ceiling product (a class declaring `serve_obligations.debt_ceiling`, plan `24.5-13`) now receives `409` with the envelope; a client should branch on `body["kind"]` and read `body["refusal"]["fields"]` (each value in the SDK's canonical form — a string arrives quoted), never parse `detail`
