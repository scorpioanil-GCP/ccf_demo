# 15.4-03 — the writer split: each backend's write path moves beside its reader (D-01)

Plan 15.4-03 relocates every backend's writer class out of the 3,215-line
`ccf.graph._writer` into a module beside that backend's reader, at
`ccf.graph.backends.<name>_write`. `ccf.graph._writer` survives as the neutral
base — the boot token, the live-writer table, the transaction Protocols, the
write semantic in `BaseGraphWriter`, and the shared SQL adapter — and imports
no backend.

This is the change that makes the D-IMPL-93 dependency arrow reversible.
Before it, `ccf.graph._writer` imported all six adapters, so nothing could
import the write module without importing every substrate; a registry that
resolves one adapter by name is impossible while that is true.

**The relocation is verbatim.** Each moved span is byte-identical to what it
was, except for its imports and one recorded defect fixed on the way past
(WR-01, below). No write semantic changed, and the four container legs at
their recorded counts are the evidence.

**Six public names enter the surface on this commit.** `ccf.graph._writer` is
invisible to `tools/dump_surface.py` — a dotted segment starting with an
underscore is skipped — while `ccf.graph.backends.<name>_write` is not, and
each new module carries an `__all__`. So six writer classes that were
previously private-by-module-name are now *named* on the public surface. Their
**reachability is unchanged**: the CINV-02 `cinv02-graph-writer` lint guards
the new modules exactly as it guarded the old one, because its guarded set
became the predicate `is_write_module` in plan 15.4-01. Only `ccf.assembly`
(L2) and `ccf.boot` (the composition root) may import them, and that is
CI-enforced, not conventional.

## ccf.graph.backends.sqlite_write.SqliteGraphWriter

- Surface: ccf.graph.backends.sqlite_write.SqliteGraphWriter
- Public surface: true
- Change type: added
- Before: defined in `ccf.graph._writer`, a module invisible to the generated
  manifest by its leading-underscore segment — so the class was on no public
  name list
- After: defined in `ccf.graph.backends.sqlite_write`, beside the SQLite
  reader. The class did not change: same `BaseGraphWriter` subclass, same nine
  dialect `ClassVar` statements, same `_SqliteTxn` over a `sqlite3` connection,
  same `_SqlGraphTxn` shared adapter — only where it lives
- Why: D-01. While `ccf.graph._writer` imported all six adapters, importing the
  write path meant importing every substrate, and the registry seam D-IMPL-93
  specifies could not exist. Reads and writes in one module per backend was
  considered and rejected: it would force the single-writer lint to guard a
  *class* instead of a module, which is weaker and harder to check statically
- Migration: none. The module is import-restricted to `ccf.assembly` and
  `ccf.boot` by the `cinv02-graph-writer` lint; deployments reach the writer
  only through `boot(database_path=…)`. A deployment that had somehow named
  `ccf.graph._writer.SqliteGraphWriter` was already failing that lint

## ccf.graph.backends.fluree.policy_key

- Surface: ccf.graph.backends.fluree.policy_key
- Public surface: false
- Change type: behavior
- Before: `policy_key` was the *read* side's key construction only. The write
  side held its own copy of the separator (`_POLICY_KEY_SEPARATOR` in
  `ccf.graph._writer`) and joined the `(entity_class, attribute, value)` triple
  by hand, on the stated argument that importing the reader from the writer
  would break the CINV-02 confinement and create a cycle. The argument was
  false — the write path already imported the reader — and the duplicate is
  what made defect CR-01 reachable, because the injectivity guard lived on one
  copy only
- After: the duplicate constant and the hand-rolled join are deleted.
  `_fluree_claim_projection` calls `policy_key` and skips the triples it
  refuses, so a key that cannot be built on the read side is no longer stored
  on the write side. The observable answer does not move: an unencodable stored
  key was already unreachable from the read path (every pushed key carries
  exactly two separators; a smuggled one carries more), and a query naming such
  a triple still declines the pushdown so the fallback answers the whole thing
  (D-04). What moves is that the over-disclosure surface is now closed at both
  ends rather than at one
- Why: D-14 (Dave, 2026-08-09), review finding WR-01. Relocating a
  known-defective duplicate unchanged is worse than either fixing it or
  deferring it explicitly, and the writer split removes the last shred of the
  duplicate's justification
- Migration: none. `policy_key`'s own signature and behaviour are untouched;
  only its second caller is new

# 15.4-04 — each adapter declares what it needs (D-07)

Plan 15.4-04 adds two public names to each of the six write modules this
fragment already covers: a typed connection-settings model and the module-level
`REGISTRATION` record `ccf.graph.registry.resolve` reads off it. **This fragment
is extended rather than a `15.4-04-` one opened**, because the fragment is keyed
to the module set it describes, and splitting one module's surface across two
files makes the phase-close cross-check harder to read for no gain.

**What moved, and from where.** The knowledge "which connection argument does
this backend require" was a hand-maintained mapping in
`ccf.deployment.manifest._preflight_backend`, a core file that had to be edited
for every substrate. It is now six models in six adapters. The mapping was
already declarative, so this is largely a relocation of knowledge that was
always data.

**Both refusals it performed survive, and their mechanisms differ.** A declared
backend whose connection argument is missing is refused because the field is
*required*. An argument the declared backend does not take is refused — rather
than ignored — because every model derives from `ccf.contracts.base.CCFContract`
and inherits `extra="forbid"`. The second is the one a migration loses silently:
a model written against a plain open base keeps every valid manifest working and
drops the refusal with nothing going red, which is why
`tests/deployment/test_adapter_config.py` sweeps every registered adapter
asserting `model_config["extra"] == "forbid"`.

**The `__all__` ruling, made explicitly.** Each write module's `__all__` gains
its config model and `REGISTRATION`, and gains nothing else — `_open_store` and
`_make_writer` are private by name and stay off the surface. Both exported names
are part of the contract a third-party adapter author reproduces: the config
model is what an adopter authors a manifest against, and `REGISTRATION` is the
object an entry point in the `ccf.graph_backends` group points at. A public
contract the surface manifest cannot see is a contract nothing holds anyone to.
Leaving them out would have been a decision too, so it is recorded either way.

**No credential is a field on any of these models.** Pydantic reports
`input_value=` verbatim in a `ValidationError`, so a misspelled connection key
beside a live token would print the token. The Fluree adapter therefore names
its credential in `secret_fields` and takes the value through a separate mapping
that is never validated.

## ccf.graph.backends.sqlite_write.SqliteConnection

- Surface: ccf.graph.backends.sqlite_write.SqliteConnection
- Public surface: true
- Change type: added
- Before: absent. The SQLite adapter's one required connection argument was an
  entry in the `required` dict in `ccf.deployment.manifest._preflight_backend`
  (`"sqlite": "database_path"`), and the refusal for any *other* backend's
  argument supplied alongside it was a loop in the same function
- After: a frozen, closed-world model with one required field, `database_path`,
  annotated `Path` rather than `str` because Pydantic coerces a string to a
  `Path` and not the reverse while callers pass both. `extra="forbid"` is
  inherited from `CCFContract`, so an undeclared key is refused by the contract
  base rather than by a loop in core
- Why: D-07. An adapter should state its own requirements in its own module, so
  that adding a substrate costs no edit in a core file — the dependency-arrow
  reversal D-IMPL-93 asks for, applied to configuration as well as to code
- Migration: none. The name is new; nobody could have been using it

## ccf.graph.backends.sqlite_write.REGISTRATION

## ccf.graph.backends.fluree_write.REGISTRATION

- Surface: ccf.graph.backends.fluree_write.REGISTRATION
- Public surface: true
- Change type: added
- Before: absent — one branch of `ccf.boot._open_backend`'s cascade, which
  threaded `fluree_bearer_token` straight into the store constructor
- After: the module-level record for the `fluree` adapter, and the only one of
