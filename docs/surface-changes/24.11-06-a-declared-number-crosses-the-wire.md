# 24.11-06 — a declared `number` crosses the wire as canonical decimal text

`D-IMPL-302` (Dave, 2026-09-09). Found by cp-05's MCP door verification
(`D-IMPL-298` step 3), and fixed in the SDK rather than by misdeclaring the
example's arguments.

Two surfaces were individually right and their composition made a legitimate
request impossible. The product contract refused a `str` with `type-mismatch`
(declared `number`); `WireRequest` refused a `float` because *"canonical JSON
renders it as text, so the decoded echo would differ from what was sent"*.
Wire-stable values are `str`, `int`, `bool` — so **a fractional number had no
representation at all**.

cp-04 declares one `number` argument and its own config calls it *"DECLARED AND
ADVISORY at this tier"*; its tests never send it over the wire. cp-05 is the
first product whose numeric arguments are consequential — materiality shapes the
answer, tolerance decides fulfillment — so it is the first that had to transport
them.

## ccf.products.request.decode_declared_request

- Surface: ccf.products.request.decode_declared_request
- Public surface: true
- Change type: added
- Before: absent. A declared `number` sent as canonical decimal text was refused `type-mismatch` before anything could type it, and sent as a float was refused at the wire
- After: `(request, declared) -> ProductRequest`. Returns a NEW request whose declared `number` arguments carrying canonical decimal text become exact `Decimal`s. Called at the head of `resolve_effective_request`, so the bounds comparison, the policy constraints, the conformity check and the effective value recorded in replay are all numeric
- Why: `D-IMPL-302` — *"the transport encoding should not leak into the product's semantic contract"*. The wire keeps `"0.05"` and its echo cross-check; the governed request carries exact `Decimal("0.05")`. Wire stability does not require semantic type erasure
- Migration: none. A request with no declared `number` argument returns the identical object, and a value that is already numeric passes through untouched.

## What did NOT change

- **`WireRequest`'s float refusal.** Deliberately preserved — *"`0.05` as an IEEE
  float is not the deterministic representation CCF wants"*. **No `float`
  appears anywhere in the decoded path**, asserted positively against
  `Decimal(0.05)`, which is a different number from `Decimal("0.05")`.
- **`refuse_request` stays a validator.** The decode is a separate step beside
  it, not a new return shape rippling through every caller. The sequence is
  decode, then judge.
- **The narrowness is the contract.** Only *declared `number` + canonical
  decimal text*. No `"true"` -> bool, no `"123"` -> int, no date parsing, no
  enums, no scalar-to-collection promotion, no transform registry. The accepted
  lexical form is deliberately narrower than `Decimal`'s own parser: `NaN`,
  `Infinity` and `1e-2` are **not** decoded, and pass through unchanged so
  `refuse_request` refuses them by name.
