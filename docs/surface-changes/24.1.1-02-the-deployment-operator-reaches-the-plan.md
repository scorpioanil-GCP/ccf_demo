# 24.1.1-02 — a deployment's own operator reaches the operator plan

Plan `24.1.1-02` closes `D-59`. `ccf.deployment.operators.build_operator_registry`
dispatched on artifact **type** through an `isinstance` chain and raised on anything it did
not recognise, so a deployment's own operator had no route into the registry the operator
plan reads. The registry beneath it was already open —
`src/ccf/operators/registry.py::OperatorRegistry.register` takes no category argument and
reads category and parameter schema off the operator — but the composition path in front of
it was not.

## What did NOT change

Worth leading with, because the seam is additive and the temptation is to read it as more:

- **The `isinstance` artifact dispatch is untouched.** Manifest artifacts still become
  operators exactly as before, in the same order, with the same refusals.
- **The four canonical categories are unchanged.** No new `OperatorCategory`, and
  `src/ccf/operators/base.py::CATEGORY_ORDER` still holds the same four.
- **`OperatorOutput` and the composition law are untouched.**
- **`src/ccf/products/resolver.py` is untouched** — see the known limit below.
- **No validation gate was added.** `src/ccf/products/gates.py::run_gates` is unchanged;
  a fourth gate is forbidden by `D-IMPL-102` limb 3.


## ccf.deployment.operators.build_operator_registry

- Surface: ccf.deployment.operators.build_operator_registry
- Public surface: true
- Change type: behavior
- Before: `def build_operator_registry(*, parameters, view, pins, policy_bundle_key,
  similarity_index_version=None) -> OperatorRegistry` — the builder dispatched on artifact
  TYPE through an `isinstance` chain and raised `ValueError` on anything it did not
  recognise, so a deployment's own operator had no route into the registry the operator plan
  reads
- After: the same signature plus one defaulted, keyword-only parameter,
  `deployment_operators: Sequence[Operator] = ()`, whose members are registered FIRST and
  sorted by `operator.key`, through `register(operator)` with **no category argument**
- Why: `D-59`. The registry beneath the builder was already open —
  `src/ccf/operators/registry.py::OperatorRegistry.register` reads category and parameter
  schema off the operator — but the composition path in front of it was not, so
  `examples/cp-00-institutional-holders/deployment.py` had to register into a private
  registry the projection plan never sees. That workaround is exactly why cp-00's recipe
  witness for step 1 is `payload_key_present` rather than `operator_in_lineage`
- Migration: none — additive and keyword-only with a default

## ccf.deployment.build_operator_registry

- Surface: ccf.deployment.build_operator_registry
- Public surface: true
- Change type: behavior
- Before: the package re-export of the same function, carrying the same signature
- After: the same re-export, carrying the reshaped signature above
- Why: the same change, visible at the package boundary because `ccf.deployment` re-exports
  the symbol; recorded as its own entry because the manifest records it as its own entry and
  a reader who imports from the package should not have to infer it from the module
- Migration: none — additive and keyword-only with a default

Both entries are the same function — the module and its package re-export — and both are
**reshaped**, not added or removed.

```python
# before
def build_operator_registry(
    *,
    parameters: Mapping[str, OperatorParametersArtifact],
    view: GraphView,
    pins: ResolvedPins,
    policy_bundle_key: str,
    similarity_index_version: str | None = None,
) -> OperatorRegistry: ...

# after — one defaulted, keyword-only parameter
def build_operator_registry(
    *,
    parameters: Mapping[str, OperatorParametersArtifact],
    view: GraphView,
    pins: ResolvedPins,
    policy_bundle_key: str,
    similarity_index_version: str | None = None,
    deployment_operators: Sequence[Operator] = (),
) -> OperatorRegistry: ...
```

**Migration: none — additive and keyword-only with a default.** Every call site that
predates the seam compiles and passes unmodified, measured rather than asserted: the eleven
calls in `tests/deployment/test_operator_builder.py`, the three shipped example spines, and
the `perf/` and `archive/examples/` callers.

## What the seam does and does not guarantee

- **The category is still read off the operator.** `register(operator)` is called with **no**
  category argument, because a caller-declared category would let the planner order an
  operator into a position it does not belong in — the Policy-after-Similarity failure
  `INV-CH7-26` forbids. `tests/deployment/test_operator_builder.py::test_the_builder_passes_no_category_to_register`
  is an AST walk over the whole module and covers the new call site; that coverage was
  **proven by sabotage**, not assumed.
- **`DuplicateOperatorKey` stays fatal** across the new channel, whether both keys come from
  the manifest, both from `deployment_operators`, or one from each.
- **Parameters do not travel as a Control Plane artifact through this channel** (`D-IMPL-38`).
  The operator *instance* carries them and it is the caller's job to have built it from an
  artifact. The manifest path takes artifacts and constructs operators; this path takes
  operators. Deliberate — the SDK cannot know how to construct an operator it has never seen
  — but it means the replay-determinism argument for these operators rests on the caller's
  artifact discipline rather than on this builder's.

## The known limit, recorded rather than papered over

`src/ccf/products/resolver.py::GovernedResolver` and
`src/ccf/products/resolver.py::build_governed_resolver` have **no channel** to pass a
deployment operator through: they build the registry inline and consume it in the same
expression chain. Handing this builder's result to
`src/ccf/projection/engine.py::ProjectionEngine` directly — what every shipped example spine
does — is the supported route, and is what the `D-59` criterion asks for. `resolver.py` is
outside this phase's ruled file roster (`D-IMPL-214`) and was deliberately not touched.
