# 24.5-05 — the directed descendant walk

Plan `24.5-05` works ledger row `24.5-L-06`. Before it, the L4 walk was an
undirected NEIGHBORHOOD: `TraversalNeighborhood` adds both endpoints of every
crossable edge to its adjacency, so a node one undirected hop from a reached
node — a parent's other child, a cycle's closing edge — is reached a depth
early. cp-04 (`24.4-D-36`, deferred item 5) measured exactly one such node
(`CycThornburyCapitalLtd`: 20/22/22 reached at depths 1/2/3 where the
directed census is 20/21/22), and the SDK had no expression for a DIRECTED
walk. The fix is a SIBLING operator key under the existing `traversal`
category — `traversal.typed-descendants`, `TraversalDescendants` — with its
own parameter class and, in this plan's second task, its own artifact class,
dispatch arm and committed schema. `OperatorCategory` stays four
(`D-IMPL-223`): a second SHAPE, not a fifth category. The two walks call one
private `_bounded_walk`, so they differ in exactly the adjacency line and
cannot drift.

The mirrored spec gains `direction: TraversalDirection = "undirected"`, and
`src/ccf/graph/fallback.py::_walk` honors it. Every backend DECLINES a
`direction` other than `"undirected"` to the oracle from this plan's first
commit (D-04): a pushdown that ignored the field would walk undirected while
the oracle walks directed, a divergence nothing would observe at an
intermediate commit. **Plan `24.5-18` lands the rest of this row under the
same id** — backend HONOR on sqlite/postgres/neo4j (the decline stays on
mongo and fluree, whose interposed layout carries no edge direction), the
corpus `direction_cases`, `GQ-10` at semantics version 1.2.0, the
`tests/properties/strategies.py` registration that puts the sibling into the
n² composition suite, and the 20/21/22 vs 20/22/22 fixture measurement. That
work is signature-neutral, so this fragment is the row's only fragment.

## What did NOT change

- **`OperatorCategory` is four.** `typing.get_args(OperatorCategory)` is
  `("policy", "similarity", "temporal", "traversal")` before and after;
  `TraversalDescendants.category == "traversal"`.
- **Every existing traversal artifact, call and corpus entry passes
  unchanged.** `direction` defaults to `"undirected"`, the 1.0.x walk
  byte-for-byte; `TraversalNeighborhood.read_intent()` emits it explicitly.
  The four-field `TraversalSpec(...)` construction still works; every corpus
  case is undirected, so no backend's answer changes and the quick
  conformance suite is green with no corpus edit.
- **No artifact value chooses a direction.** Neither parameter class carries
  a `direction` field; the direction is fixed by which operator key the
  artifact class selects (`"backward"` is not a value — `TraversalSpec`
  refuses it at construction).
- **`content_hash(GraphQuery)` moves for every traverse query** (`GQ-20`),
  as it did for `admitted_entity_classes` in `24.5-04`: `canonical_bytes`
  walks every field. No committed query pin exists in the tree (measured in
  `24.5-RESEARCH.md` §B.3).
- **`tests/properties/test_composition.py`'s n² suite is untouched (n = 4).**
  The sibling enters it when plan `24.5-18` registers it in
  `tests/properties/strategies.py::shipped_operators`.

## ccf.graph.protocols.TraversalDirection

- Surface: ccf.graph.protocols.TraversalDirection
- Public surface: true
- Change type: added
- Before: absent — the walk's direction was a property of the one operator's
  two `adjacency.setdefault(...)` lines, stated nowhere in a type
- After: `Literal["undirected", "forward"]`, the closed direction vocabulary
  of `TraversalSpec`, in the `PolicyBindingMode` form. `"undirected"` crosses
  an edge from either endpoint; `"forward"` crosses it only from
  `subject_uri` to `object_uri` AS STORED — the graph's own orientation, so
  a deployment that wants parent→child normalizes at ingest (cp-04 does).
  No `"backward"`: a reverse walk is the same edge stored the other way
- Why: `24.5-L-06`; `D-IMPL-223` — the direction is a spec field, not a
  category
- Migration: none — additive

## ccf.graph.protocols.TraversalSpec

- Surface: ccf.graph.protocols.TraversalSpec
- Public surface: true
- Change type: reshaped
- Before: four fields after `24.5-04` — `seed_entity_classes`,
  `relationship_types`, `depth_limit`, `admitted_entity_classes=None`
- After: a fifth, last, sentinel-defaulted field
  `direction: TraversalDirection = "undirected"`. The default is the 1.0.x
  behavior; `"forward"` is emitted only by `TraversalDescendants.read_intent`.
  A pushed answerer that cannot express the direction declines the whole
  query to the fallback (`GQ-32`, D-04) — which every backend does at this
  plan's tip
- Why: `24.5-L-06`; pushdown and the fallback read the spec, not the
  operator, so the direction has to travel on the spec
- Migration: none — additive. `TraversalSpec(seed_entity_classes=…,
  relationship_types=…, depth_limit=…)` still constructs and still means the
  undirected walk

## ccf.operators.categories.TraversalDescendants

- Surface: ccf.operators.categories.TraversalDescendants
- Public surface: true
- Change type: added
- Before: absent — no SDK operator could walk a stored orientation
- After: `key = "traversal.typed-descendants"`, `category = "traversal"`,
  constructed from `parameters: TraversalDescendantsParameters`.
  `read_intent()` projects the four fields onto `TraversalSpec` with
  `direction="forward"` fixed by the operator; `apply()` runs the shared
  `_bounded_walk(..., forward=True)`, whose adjacency adds only
  `subject → object` — the one line on which the two walks differ. Joins
  `_CONFORMANCE` (Protocol conformance asserted at import) and `__all__`.
  Registers under its own key, so `DuplicateOperatorKey` never fires beside
  the neighborhood
- Why: `24.5-L-06`, criterion 9; `D-IMPL-223` (a sibling shape, the category
  count untouched); `24.5-RESEARCH.md` Pitfall 3 (a sibling key enters the
  n² suite for free once registered)
- Migration: none — additive. A deployment that wants the directed walk
  authors an artifact of the new class (`24.5-05` Task 2) and requires the
  new key in its product class

## ccf.operators.categories.TraversalNeighborhood

- Surface: ccf.operators.categories.TraversalNeighborhood
- Public surface: true
- Change type: behavior
- Before: `apply()` held its own BFS with the two undirected
  `adjacency.setdefault(...)` lines inline; `read_intent()` left
  `TraversalSpec.direction` to its default
- After: `apply()` calls the shared `_bounded_walk(..., forward=False)` —
  the same BFS, the same admission predicate, now in one place for both
  walks; `read_intent()` emits `direction="undirected"` explicitly. Constructor
  and key unchanged (the manifest records constructors only, so the
  behavior-neutral refactor is claimed here). Answers are byte-identical:
  `tests/operators/test_traversal_admission.py` and the quick conformance
  suite pass with no edit
- Why: `24.5-L-06`; one walk function so the two shapes cannot drift
  (threat `T-24.5-13`)
- Migration: none
