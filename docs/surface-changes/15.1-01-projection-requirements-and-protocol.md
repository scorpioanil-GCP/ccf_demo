# 15.1-01 — the projection-requirements artifact class and the widened Control Plane Protocol

Plan 15.1-01 lands the contracts the rest of Phase 15.1 depends on and nothing that
depends on them. Two are public Python names — the `ProjectionRequirements` contract
and its `ArtifactClass` constant, which design E2 (`docs/DECISIONS.md` D-IMPL-86)
requires so the projection's operator set is a *separately authored* document from
the product class's claim. One is a widening of an existing Protocol
(`ControlPlaneProtocol` gains `register_versioned`, D-IMPL-82) which the generated
manifest is structurally incapable of showing. One is a committed JSON Schema.

**This fragment is named `15.1-01-…`, not `15-22-…`, and that required widening two
gate modules.** `tests/test_surface_drift.py` and `tools/assemble_surface_changes.py`
both globbed `docs/surface-changes/15-*.md`, which a `15.1-` name does not match, and
the assembler's `_PLAN_NUMBER` sort key had the same shape. Both are widened to
`15*-*.md` and `^15(?:\.(?P<minor>\d+))?-(?P<plan>\d+)-`. Phase 15.1 is a gap-closure
cycle against Phase 15's own deliverables and its fragments are *its* audit trail;
filing them under Phase 15 plan numbers would be permanently wrong. The widening
changes what the gates **read**, never what they **permit**.

## ccf.controlplane.artifacts.ProjectionRequirements

- Surface: ccf.controlplane.artifacts.ProjectionRequirements
- Public surface: true
- Change type: added
- Before: absent — a projection plan's `required_operators()` had exactly one
  authored source available to it, `ProductClassDeclaration.required_operator_keys`,
  which is also the value that fills `lineage.operators_invoked`
- After: a `VersionedArtifact` declaring `plan_id: str` and
  `required_operator_keys: tuple[str, ...]` with `min_length=1`
- Why: with one document, the two sides of Gate 2 (lineage strict equality,
  INV-CH7-47) are not merely equal in practice — they are identical by construction.
  `execution.operators_invoked` is `frozenset(declared.required_operator_keys)`
  through five pure transforms with no branch: the declaration feeds `plan.required`;
  `plan.required_operators()` returns it; `build_operator_plan` resolves each key
  self-keyed so `resolve(k).key == k`; the engine writes `outputs[operator.key]`; and
  it returns `operators_invoked=frozenset(outputs)`. Nothing a deployment could author
  would make the two sides diverge, which is why the remedy first recorded for CR-2
  was withdrawn as circular. Under design E2 the projection reads **this** artifact
  and the product class keeps the claim, so the two sets are separately authored and a
  one-key edit to either document is reachable drift (D-IMPL-86; T-15.1-01-02). An
  artifact rather than operator keys in a projection class body, because under the
  rejected design the compliant state (an author typed the keys) and the violating
  state (an author transcribed them from the product-class document) are textually
  identical and no AST gate can distinguish them — E2 satisfies the No-Hardcoding Rule
  (CLAUDE.md §6.4) by construction rather than by argument
- Migration: nothing breaks today; this plan adds the contract and no caller. From
  plan 15.1-05 onward a deployment authors a second document of class
  `ccf.projection-requirements` naming its plan and that plan's operator keys, and
  builds its `ProjectionPlan` from it rather than from the product-class declaration.
  The binder added in plan 15.1-04 — placed between plan construction and
  `ProjectionEngine.execute`, per D-IMPL-86's correction of 2026-08-05 — refuses when
  the two documents disagree

## ccf.controlplane.artifacts.PROJECTION_REQUIREMENTS

- Surface: ccf.controlplane.artifacts.PROJECTION_REQUIREMENTS
- Public surface: true
- Change type: added
- Before: absent — no class id addressed a projection's own operator declaration, so
  a D-05 manifest could not name one
- After: `ArtifactClass(class_id="ccf.projection-requirements", contract=ProjectionRequirements)`,
  registered in `ccf.deployment.classes.SDK_ARTIFACT_CLASSES`
- Why: manifest addressability, on the same rule as every sibling — a class the SDK
  ships that a manifest cannot address is a class no adopter can register. It matters
  more here than usual: the binder's comparison has two authored inputs and this
  document is one of them, so a deployment that could not register it could not author
  half of the check
- Migration: name `ccf.projection-requirements` in the manifest entry, with
  `role: register`

## ccf.controlplane.registry.ControlPlaneProtocol

- Surface: ccf.controlplane.registry.ControlPlaneProtocol
- Public surface: true
- Change type: behavior
- Before: the Protocol declared `register`, `register_typed`, `resolve`,
  `resolve_latest` and `audit_events`. `register_versioned` — the D-05 hash-verified
  bump check — existed only on the reference `ControlPlaneRegistry`, so a conforming
  implementation could omit it entirely
- After: the Protocol also declares
  `register_versioned(key, artifact, artifact_class, *, actor=None, reissuable=False) -> str | RegistrationRefusal`,
  with a signature identical to the reference implementation's
- Why: D-IMPL-82 (Dave, 2026-08-05). The bump check is a governance obligation, and
  the Protocol's own docstring already argues that the obligations sit on the surface
  "precisely so a remote plane cannot conform while quietly dropping them" — a remote
  Control Plane that cannot run the bump check is exactly such a plane, and
  `load_and_boot` must be able to dispatch author-versioned classes to it to close
  CR-1 at all (T-15.1-01-01). Rejected: a narrow second
  `VersionedRegistrationProtocol`, which preserves the posture at the cost of a
  two-Protocol mental model in the phase whose subject is one mental model; and
  narrowing `load_and_boot` to the concrete `ControlPlaneRegistry`, which breaks the
  Protocol-over-inheritance posture CLAUDE.md §11 mandates. Recorded as
  `Change type: behavior` rather than `reshaped` because
  `docs/surface/v0.2-surface.json` records a Protocol's shape as `(*args, **kwargs)`:
  a member addition changes what conforms without moving any signature the generated
  manifest can see, which is the case the `behavior` class exists for
  (`docs/surface-changes/README.md`)
- Migration: a non-reference Control Plane implementation must now provide
  `register_versioned` — this is a FABR-07 remote-plane implementation obligation.
  The in-process `ControlPlaneRegistry` already satisfies it and needs no change; no
  caller's code changes. An implementation that omits the member no longer type-checks
  as conforming, and `isinstance(x, ControlPlaneProtocol)` returns `False` for it

## docs/schemas/ccf.projection-requirements.json

- Surface: docs/schemas/ccf.projection-requirements.json
- Public surface: false
- Change type: added
- Before: absent
- After: the committed JSON Schema for `ccf.projection-requirements`, emitted by
  `make schemas` from the live contract and carrying
  `"x-ccf-class-id": "ccf.projection-requirements"`
- Why: ERGO-12's authoring baseline covers every SDK-owned artifact class, gated by
  `tests/cli/test_schema_export.py`'s every-class-has-a-schema tree walk, so a new
  class ships its schema in the same commit or fails the build. This entry is
  `Public surface: false` because a committed schema is not an `__all__` name and can
  never appear in an `__all__`-derived manifest diff — see
  `docs/surface-changes/README.md` §"the classification field"
- Migration: none. Adopters authoring a `ccf.projection-requirements` document can
  point their editor at this schema, or fetch the same document from the HTTP
  `/schema` route, which enumerates `SDK_ARTIFACT_CLASSES` and therefore serves the
  new class by construction
