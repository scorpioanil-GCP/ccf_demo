# 15.4-09 — `ccf backends` (D-15)

A read-only route and a CLI noun answering which adapter names a deployment
accepts. This is what replaces the `enum` the deployment manifest's schema lost
when plan 15.4-06 removed the six-name `backend` `Literal`.

## ccf_runtime.http_api.routes.backends.build_router

- Surface: ccf_runtime.http_api.routes.backends.build_router
- Public surface: true
- Change type: added
- Before: absent — the set of adapter names a deployment would accept was not
  reachable over the wire; an adopter learned it from the refusal they got
  after naming one wrong
- After: one read-only endpoint, `GET /backends`, returning
  `{"backends": [...]}` — the sorted result of
  `ccf.graph.registry.declared_names()`, mounted under the same authentication
  and tenant-authorization dependencies as every other read route
- Why: the route D-IMPL-79 rules the CLI noun onto, on the argument that
  earned `GET /schema` its own module — the CLI's posture is that every
  command travels the same routes any client uses, and the first exception is
  the one that makes the second easy. It enumerates no vocabulary: the names
  come from the registry, which derives them from the adapter package on disk
  and from installed entry points, so a hand-written list here would
  reintroduce exactly what 15.4-06 removed (CINV-01). The success path
  deliberately carries names only — the registry knows each adapter's
  distribution and version, and a caller who learned those would have learned
  the deployment's dependency inventory, which this endpoint owes nobody
  (T-15.4-11). The one narrowing is the refusal path: `declared_names()` is
  fail-closed on any installed distribution's bad entry-point metadata, so
  that refusal is caught here and returned as `503` carrying the registry's
  own message, which names the offending distribution. `503` because the
  deployment is misconfigured rather than the request malformed; not `200`
  with an empty list, because an empty list is a different fact. Without the
  distribution name a fail-closed refusal is unactionable, and the path is
  reachable only when the deployment's own installed adapters already
  conflict.
- Migration: none — a new read-only surface

## GET /backends

- Surface: GET /backends
- Public surface: false
- Change type: added
- Before: absent
- After: `{"backends": ["<name>", ...]}` on 200; on 503 the API's existing
  typed-refusal shape, `{"detail": {"error_code": "backend-registry-conflict",
  "message": "..."}}`. The answer is deployment-local — it describes the
  process serving the request, which under `ccf --local` is the CLI's own
  process and over HTTP is the server's.
- Why: a route path is not a Python name and can never appear in the generated
  manifest diff, so it is classified `false` — classifying it `true` would
  fail the phase-close cross-check in the direction that catches
  misclassification. D-IMPL-22's noun enumeration is amended to ten as the
  mechanical consequence of adding it; `tests/http_api/test_routes.py` reads
  that ruling text to hold the mounted prefixes to it.
- Migration: none — a new endpoint; nothing existing moved

## ccf_runtime.cli.commands.backends.register

- Surface: ccf_runtime.cli.commands.backends.register
- Public surface: true
- Change type: added
- Before: absent — no CLI path to the adapter names a deployment accepts
- After: the tenth noun, `ccf backends list`, whose verb returns a single
  `RequestSpec(method="GET", path="/backends")` exactly like the other nine
- Why: D-IMPL-79 again, and the trade is worth stating plainly. The deployment
  manifest's `backend` field used to be a six-name `Literal`, which put an
  `enum` in `docs/schemas/ccf.deployment-manifest.json` and gave an adopter's
  editor a completion list. Plan 15.4-06 removed the `Literal` because a
  generated six-name list would still have been six substrate names in a core
  contract (D-12), and the `enum` went with it. This command is what replaces
  it, and it answers a better question: the enum could only ever say what
  someone hard-coded, while this reads the deployment's own registry and says
  what is *installed here* — third-party adapters included, which is the case
  that becomes interesting the moment an adapter can arrive from outside this
  repository. The command holds no local generation path: it returns a
  `RequestSpec` and nothing else, so the route's fail-closed `503` and the
  distribution name it carries arrive over the same path any client sees,
  under `--local` too.
- Migration: none for the command itself — a new noun; nothing existing moved.
  An adopter who relied on editor autocompletion of the manifest's `backend`
  field should run `ccf backends list` against the deployment they are writing
  the manifest for, and use a name from that answer. It is strictly better
  information than the enum was: the enum listed what the SDK shipped at the
  version the schema was generated from, while this lists what the target
  deployment actually has installed. A typo is still caught — at manifest
  load, by a membership check against the same registry, with a refusal that
  lists the accepted names.

## ccf backends list

- Surface: ccf backends list
- Public surface: false
- Change type: added
- Before: absent
- After: prints the `GET /backends` response body; exit 0 on success, and a
  nonzero wiring exit carrying the registry's refusal message on a packaging
  conflict
- Why: the command an adopter types is not a Python name, so it can never
  appear in the manifest diff and is classified `false`. The noun-verb shape
  is D-IMPL-22's ruling — there is deliberately no bare `ccf backends`.
- Migration: none — a new command
