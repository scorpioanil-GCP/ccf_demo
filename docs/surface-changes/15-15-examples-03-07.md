# 15-15 — examples 03 and 07 reshaped to typed artifact documents

Plan 15-15 adds **no** public Python surface: `tools/dump_surface.py --report`
shows nothing added by this plan (the accumulated set it prints belongs to
15-01 through 15-14). Every entry below is therefore `Public surface: false`
with `Change type: reshaped` or `added`, and every `Surface` string names a
repo-relative artifact document — an artifact-format change is real and
adopters must act on it, but it can never appear in the `__all__`-derived
manifest diff.

Both examples' multi-artifact bundles are now typed, closed-world,
`$schema`-annotated documents enumerated by one deployment manifest, and both
drivers boot in a single `load_and_boot` call. An adopter who copied either
example's artifacts needs the mapping, which is what this fragment is for.

## Cross-plan dependency: the author-versioned schema set (15-14)

No document in either example uses a deferral marker. Two of example 03's
documents point their `$schema` headers at schemas plan **15-14** commits via
`tools/dump_schemas.author_versioned_classes()`:

- `examples/03-harness-portability/artifacts/prompt.yaml` →
  `docs/schemas/ccf.prompt-artifact.json`
- `examples/03-harness-portability/artifacts/agents/agent-definition.yaml` →
  `docs/schemas/ccf.agent-definition.json`

Why those classes are not in `SDK_ARTIFACT_CLASSES`, and must not be added:
`ccf.agent-definition` and `ccf.prompt-artifact` need `register_versioned`'s
D-05 hash-verified bump check, and `load_and_boot` registers through
`register_typed`. Adding them to the class registry would make them
manifest-addressable *and* silently drop that check — the exact "passes for a
reason unrelated to what it claims" shape. 15-14's fix commits real schema
files without making the classes manifest-addressable, on the same reasoning
15-13 used for the `DeclaredArtifact` envelope.

Consequence for merge order: **15-14 merges before 15-15.** Until it does, this
plan's `make schema-headers DIR=examples/03-harness-portability/artifacts` leg
reports the two targets as unresolvable. That is the known ordering dependency,
not a defect, and it is deliberately not worked around here.

Neither document is a manifest entry, and `agent-registration.yaml` (new,
`role: load`) carries the Control Plane keys the old `keys:` wrappers held so
that each agent document can be exactly one artifact class at its root.
