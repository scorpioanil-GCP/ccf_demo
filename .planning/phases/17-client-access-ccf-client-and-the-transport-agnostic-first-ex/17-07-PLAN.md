<objective>
Write the adapter conformance suite once, parameterize it over adapters, and bind
the in-process adapter into it as its first subject.

Purpose: **D-15.** This suite is the CI enforcement of the "value evaporates"
concern — the same class of gate as the composition-preservation tests. **An adapter
is official when it passes.** The MCP adapter (plan `17-10`) ships on passing it,
not on demoing.

And **D-22 with full force.** `.planning/HANDOFF-2026-08-15.md:170`: *"Every defect
found was in the verification or in the plans, never in the mechanism."* The gate
work in Phase 16 shipped five of its own. A parity suite whose assertions have never
been observed failing is not a parity gate; it is a parity claim.

Output: `make conformance` runs a suite that has been proven to fail on four
distinct deliberate breakages, and a `tests/client/conformance/` package a second
adapter joins by adding one parameter.
</objective>

**The suite is written once and parameterized.** Not "written for in-process and
generalized later." The whole value of the gate is that a second adapter cannot
quietly get a different set of assertions, and a suite refactored into shape after
the second adapter arrives will have been shaped by that adapter. Structure it now:
`suite.py` holds adapter-agnostic assertions taking an adapter-factory fixture;
`test_inprocess_conformance.py` binds the in-process factory in. Plan `17-10` adds
one binding module and changes nothing in `suite.py`.

**The four properties, from spec §6, with the measured trap under each.**

| Property | Assertion | The trap |
|---|---|---|
| Same question, same instant | identical `Result` fields **and identical content address** across adapters | *"A parity test that compares only `payload` will stay green — that is the failure mode to prove absent."* |
| Same refusal | identical `refused` / `reason` / `key` / request identity | Dropping `refusal.key` from one adapter's decode must be reported as a difference, not a pass |
| Guard | post-assembly fields raise on every adapter | Six fields, six assertions; one `pytest.raises` on `payload` licenses five unguarded fields |
| Wire failure | never masquerades as refusal | Without a control, `except Exception: return refusal` passes silently — the exact inversion D-07/D-10 exist to prevent |

**D-23, and where it currently lives.** The property *"two thresholds → two content
addresses"* is asserted today by
`tests/examples/test_s1_00_output.py::test_two_thresholds_are_two_products`, which
carries `pytestmark = pytest.mark.postgres`. Plan `17-08` removes that module along
with its tree. **This plan must land the client-seam replacement first**, so the
property is never unasserted between the two plans. That ordering is why `17-08`
depends on this plan and not the other way round; if you find the property already
gone, **stop and dispute** — a plan ran out of order.

**A single-adapter parity suite is a real gate, not a placeholder.** With one
adapter bound, the cross-adapter comparisons degenerate to self-comparisons and
prove little on their own — which is exactly why the sabotage controls in Task 3 are
this plan's substance rather than its epilogue. Write the suite so the comparison is
over a *collection* of adapters from the first line, and prove the comparison fires
by parameterizing the controls with a deliberately-divergent second adapter.

   "break this transport" so the assertion stays adapter-agnostic.

in-process factory in. It should be short — a factory, a break-hook, and the four

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| adapter implementation → client contract | the point at which a transport could re-implement the contract differently and evaporate its value |
| test suite → CI verdict | a suite whose assertions cannot fail produces a green build that means nothing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-24 | Tampering | an adapter returning a subtly different `Result` for the same question | mitigate | Served-parity compares every declared `Result` field plus the content address, over a derived field list, with a control proving a moved field is caught |
| T-17-25 | Repudiation | an adapter flattening a refusal so the governed "no" loses its identity | mitigate | Refusal-parity compares `reason`, `key`, `kind` and request identity, with a dropped-key control |
| T-17-26 | Spoofing | a broken wire presented as a governed refusal | mitigate | Wire-failure leg asserts `TransportError` and asserts no `Result` is produced; a swallowing-adapter control proves it fires |
| T-17-27 | Repudiation | the parity gate itself passing vacuously with one adapter bound | mitigate | Every control parameterizes a deliberately-divergent second adapter, so the comparison machinery is exercised even before a real second adapter exists |
| T-17-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no package |
</threat_model>
