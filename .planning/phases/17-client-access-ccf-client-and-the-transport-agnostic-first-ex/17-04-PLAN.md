## The served half — measured, and frozen as measured

Every door emits `canonical_bytes(servable.product)` and nothing else:
`egress.py:465`, `egress.py:597`, `experience.py:894`, and
`routes/product.py:154` via `canonical_response`. `ServableProduct.product` is a
`ContextProductContract` (`gates.py:420-423`), whose canonical field order is
(`contract.py:686-698`):

```
schema_name, schema_version, plan_id, tenant_id, temporal_boundary,
expires_at, ttl_anchor, lineage{operators_invoked, policy_bundle_versions,
graph_snapshot_at}, payload, debt, debt_evidence, source_refresh_recency,
obligation_in_force
```

`content_hash(obj) = sha256(canonical_bytes(obj))` (`canonical.py:229`).

## The outcome-level encoding, frozen here — and it must be, because `bytes` is impossible

**The measurement that forces this ruling.** `canonical_bytes` is
`_dumps(_normalize(obj)).encode("utf-8")` (`canonical.py:193-205`), and `_normalize`
has **no branch admitting `bytes`**: the `Sequence` branch at `:177` explicitly
excludes `(str, bytes)`, and the function falls through to
`raise CanonicalizationError(f"{type(value).__name__} has no canonical rendering")`
at `:180-182`. So a `CCFContract` carrying a `bytes` field **cannot be
canonically serialized at all** — it raises on the first `canonical_bytes` call.
Verify it yourself before writing a line:

```
PYTHONPATH=src .venv/bin/python -c "from ccf.contracts.canonical import canonical_bytes; canonical_bytes({'x': b'ab'})"
```

A `WireOutcome` with `product_bytes: bytes` would therefore be simultaneously
required to encode deterministically, forbidden from inventing a second
serialization, and unable to be serialized by the only one that exists. Three
constraints, no satisfying assignment. **That is a plan defect, and freezing the
encoding is this plan's job — not the executor's.**

**The premise was also off by a type.** The doors do not emit bytes. All three MCP
emission sites emit `str`:

```
egress.py:465       return canonical_bytes(servable.product).decode("utf-8")
egress.py:597       return canonical_bytes(servable.product).decode("utf-8")
experience.py:894   return canonical_bytes(servable.product).decode("utf-8")
```

**Ruled: the vessel rides as the utf-8 `str` the doors already emit.** The field is
`product_json: str | None`, and there is no `bytes` anywhere in `WireOutcome`.

Why this satisfies all three constraints at once, stated so nobody re-derives it:

- **It is not a second serialization.** The string *is* the canonical rendering.
  `canonical_bytes` produces UTF-8 bytes of canonical JSON text; decoding those
  bytes to `str` and re-encoding them is the identity, byte for byte. Nothing is
  re-serialized, re-ordered or re-formatted anywhere in the codec.
- **`WireOutcome` stays canonically serializable**, because `str` is a rendering
  `_normalize` admits. So the outcome itself has a content address, `extra=forbid`
  applies to it, and encoding is deterministic — the property Task 2's sixth
  behavior asserts.
- **The address recomputation is exact.** `sha256(product_json.encode("utf-8"))`
  equals `content_hash(product)` identically, because
  `product_json == canonical_bytes(product).decode("utf-8")` by construction. Assert
  that identity as its own test rather than reasoning about it.
- **Decode is `ContextProductContract.model_validate_json(product_json)`** — the
  contract's own parser, `extra=forbid` enforced at the boundary, no hand-rolled
  reader.

A base64 or nested-JSON envelope was the alternative and is **rejected**: it would
put a second rendering of the vessel on the wire, which is the one thing freezing
the served half exists to prevent, and it would make the recomputed address a
function of the envelope rather than of the product. Record this reasoning in
`wire.py`'s docstring, with the `canonical.py:177-182` citation, so a later reader
does not "fix" `product_json` into `product_bytes` and rediscover the raise.

**DIV-1, and it decides where the address lives.** The HTTP door publishes the
address in a header, computed from the *same single* `canonical_bytes` call that
produced the body (`routes/__init__.py:111-177`); the MCP doors publish nothing,
and `routes/__init__.py:159-163` records why this is deliberate rather than a
defect: *"their bodies **are** the product — so carrying the address inside the
body would change the body and therefore change the address it claims."*

Consequence, and it is a design decision this plan makes explicitly: **the content
address is never carried inside the vessel.** It rides as an outcome-level sibling
of the vessel bytes when a transport has a channel for it, and the decoder
**always recomputes it** from the received bytes. When the wire supplied one and
the recomputation disagrees, that is a corrupted wire and the decoder raises
`TransportError`, not a refusal. This is exactly what the HTTP header exists to let
a zero-`ccf` client verify, and it makes the MCP doors' silence harmless.

## The refusal half, `replay_ref` and the request identity — new surface

- `replay_ref` reaches **no** wire consumer (`serve.py:42-44`, verified by grep).
- The request identity is on **no** wire: the vessel carries `schema_name`,
  `schema_version`, `tenant_id`, `temporal_boundary` and **no `parameters` field**.
  `ProductRequest` carries `parameters` (`request.py:239`) and reaches replay
  dimension 5, never the wire.
- **No door emits a fabric refusal in any body** (DIV-4).

**A decode-path choice this plan must make explicitly**, because research flagged
that the two options differ under a proxying transport (`17-RESEARCH.md` §2.3
DIV-3): does the request identity in a `WireOutcome` come from the outcome, or is
it reconstructed by the client from the `WireRequest` it sent? **Ruled here: the
outcome echoes it, and the decoder cross-checks the echo against the sent
`WireRequest`.** Reconstruction alone is cheaper but cannot detect a transport that
answered a different question than the one asked; the echo turns that into a
detectable `TransportError`. State this in the codec's docstring with the reason.
