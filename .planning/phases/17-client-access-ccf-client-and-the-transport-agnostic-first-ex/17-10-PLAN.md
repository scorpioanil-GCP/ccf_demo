<objective>
Make the MCP product door carry a client's parameters and a fabric's refusal, then
ship the MCP adapter — on passing the conformance suite, not on demoing.

Purpose: **D-15, D-28 rollout, and the absorbed `16-26` / `D-IMPL-133`.**

**On absorbing `16-26`: the decision, and the measurement behind it.** `16-26` is
recorded as *"neighboring, not gating."* It is gating here, and this is why: the
shipped egress tool hard-wires `parameters={}` (`egress.py:588`), and its own
docstring states the consequence — *"a product class whose request contract declares
**any** required parameter is not reachable through this tool"* (`:544-549`). The
phase's example class declares `revenue_threshold` as **required**. So without the
fix, the MCP adapter cannot ask the phase's own question, cannot pass D-15(a) parity
against the in-process adapter, and cannot carry D-23's two-thresholds property.
Deliverable 5 is unreachable without it. Absorbed, and planned.

Output: `CCF_BINDING="mcp+stdio:…"` runs the same `consume.py` and returns an
identical `Result` — the portability claim, mechanized.
</objective>

## What the door does today, measured

- Both MCP surfaces emit `canonical_bytes(servable.product).decode("utf-8")` and
  nothing else (`egress.py:465`, `:597`, `experience.py:894`).
- The MCP resource passes `request=None` deliberately (`egress.py:440-448`): the
  `ccf-product://` template has three segments and no query surface, so the door
  says so rather than inventing a subject, an intent, a freshness figure and an
  instant nobody asked for.
- The MCP **tool** builds a `ProductRequest` but hard-wires `parameters={}`
  (`egress.py:588`), for a recorded reason: *"a flat tool-argument map cannot carry
  `D-IMPL-103`'s declared nested types without the door guessing at coercions, and a
  declared-parameter surface here would make this tool wider than the HTTP door."*
  **That reason is a real constraint on the fix, not an obstacle to it.** The
  resolution must not make the tool guess at coercions and must not make it wider
  than the HTTP door. Read `runtime/ccf_runtime/http_api/routes/product.py:36-44`
  and `_asked` at `:245-331` — the HTTP door's parameter surface is the width
  ceiling.
- **No door emits a fabric refusal in any body** (DIV-4). The resolver seam in
  `runtime/` is typed `-> ServableProduct`, so a resolver's refusal has nowhere to
  go at the door.
- The content address travels on HTTP as `X-CCF-Content-Address` and on no MCP door,
  and that divergence is **documented as deliberate and transport-derived**
  (`routes/__init__.py:159-163`), not a defect. Plan `17-04`'s decoder recomputes the
  address, so the MCP adapter needs no header channel — record that rather than
  inventing one.

## What this plan does and does not change

**Does:** the egress tool's parameter surface; the egress door's ability to emit a
refusal envelope; the `mcp+stdio` adapter; the conformance binding.

**Does not:** the `runtime/` resolver Protocol's return type. Widening it to carry a
refusal would reshape both MCP doors and the HTTP door and is a fourth-door's worth
of work. Instead, the **door** catches the fabric refusals its resolver raises or
returns and renders them through `ccf.products.refusal.envelope_for`. State the
choice and its boundary in the door's docstring so a later reader knows the seam
type is unchanged on purpose.

**Async posture (D-24).** MCP client libraries are async-native; the spec names the
MCP adapter as the *concrete revisit trigger* for the async question. **The v0
answer stands: sync-only at the client surface.** The adapter bridges internally.
Do not add an async `ask()`, and do not widen `ccf.client.__all__`. If the bridge is
genuinely unworkable — measured, not felt — stop and report it; that is a ruling for
Dave, and it is exactly the trigger the spec anticipated.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client → MCP server | a real process boundary; untrusted bytes and an untrusted lifecycle cross it |
| tool arguments → `ProductRequest.parameters` | client-supplied values reach a request contract that must validate rather than coerce them |
| door → refusal rendering | the point at which a governance refusal and a fabric refusal must stay distinguishable |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-37 | Tampering | client-supplied tool parameters coerced by the door into types the class did not declare | mitigate | The fix carries values without coercion; `refuse_request` compares them against the declared contract; the width-ceiling test runs one case table against both doors so neither can drift wider |
| T-17-38 | Elevation of privilege | a governance refusal rendered as a fabric refusal, so "not entitled" reads as "the fabric said no" | mitigate | Task 2's fourth behavior asserts governance refusals still raise; the boundary is a tested decision |
| T-17-39 | Spoofing | a dead or hostile MCP server's output presented as a governed refusal | mitigate | The adapter raises `TransportError` on every wire failure; plan `17-04`'s decoder cross-checks the echoed request identity and recomputes the content address; plan `17-07`'s control 5 watches for a swallowing adapter |
| T-17-40 | Information disclosure | the MCP door serving without a principal entitlement check | transfer | The egress door's `entitled_perspective` path is unchanged by this plan; contract-level principal/entitlement at the **client** seam remains on the v0 not-list, and plan `17-06`'s named exemption is the standing record |
