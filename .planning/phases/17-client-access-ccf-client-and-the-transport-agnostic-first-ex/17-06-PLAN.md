<objective>
Build the in-process adapter: a true degenerate wire that boots the fabric lazily
behind the seam, caches it per binding address, and hands the client the same
bytes-shaped thing an HTTP body would contain.

Purpose: **D-13, D-14, D-16, D-30.** In-process is not a privileged fast path — it
serializes live objects to the canonical wire form so all transports share one
decode path, a parity bug has exactly one place to live, and the adapter is
*physically* prevented from leaking live producer-side objects across the seam.
Cost: a microsecond of serialization.

And **D-30 is not a performance optimization.** Research measured it directly: a
second `load_and_boot` against the same graph raises `SingleWriterViolation`
(`manifest.py:626-634`), so caching is what makes a second `ask()` legal at all.

Output: `CCF_BINDING="inprocess:./deployment"` + `client.ask(...)` returns a
`Result`, against an always-on, network-free, credential-free deployment fixture.
</objective>

## Three planning decisions this plan carries, each with its reasoning

**(1) How the adapter reaches a deployment's resolver — a `binding.yaml` document.**

Measured constraint: `DeploymentConfig` is a closed-world typed contract with seven
reserved sections and no slot for a projection plan, a debt scorer or a max-TTL
value (`src/ccf/deployment/config.py:180-188`, `artifacts.py:1310-1400`). And
`config.py:82-91` refuses a `signal_batch` section by explicit decision. So a
deployment must contribute Python that the adapter reaches by *some* mechanism, and
`ccf_config.yaml` cannot be that mechanism without reopening `D-IMPL-136`.

Ruled here, in the `backends.yaml` posture: the deployment root carries a
`binding.yaml` — **deployment-environment material, never a Control Plane artifact,
never registered, never content-hashed** — naming:
  - `config:` the `ccf_config.yaml` path, relative to the root;
  - `resolver:` a `<module>:<attribute>` reference resolved relative to the root,
    whose attribute is a factory returning a `ServedProductResolverProtocol`;
  - `connection:` the connection-composition document (`backends.yaml`) when the
    deployment has one.

Why a document and not a fixed filename convention: the same reason `backends.yaml`
exists — the deployment states its own wiring rather than the SDK guessing — and it
gives the gates something to assert against. Why not a packaging entry point: an
example directory is not an installed distribution (`pyproject.toml [project.scripts]`
declares one console script and no example is a distribution), so entry points are
unreachable without a `pip install -e` per example.

**This is a new adopter-facing authoring surface and it needs Dave's ratification.**
Record it in `docs/DECISIONS.md` as `D-IMPL-140` — the high-water mark is
`D-IMPL-139` (`17-RESEARCH.md` §8) — stating the question, this resolution, and the
two rejected alternatives with their measured costs. Do not treat the ruling as
made; treat it as proposed and recorded.

**(2) Cache lifetime, `close()`, and two clients on one binding.** Ruled here:
process-lifetime cache keyed by the resolved binding address, held in a
module-level mapping inside the adapter. **No `close()` on `ProductClient`.** Two
`ProductClient`s for one binding share the one cached fabric — which is exactly what
makes them both legal, since a second boot would raise. Teardown is an
`atexit`-registered close so the graph handle is released at process exit.
Reasoning from measurement: `manifest.py:626-634` warns that *"a loop that never
closes leaks one connection per iteration"*; a process-lifetime cache creates
exactly one handle per binding, so nothing leaks. Expose an internal
`reset_boot_cache()` in the adapter module **for tests only** — not re-exported from
`ccf.client`, since D-03 fixes the public surface at four names.

**(3) Which pipeline proves what (D-32).** The example's deployment points at
already-populated stores that live outside the repository, so it **cannot run in
always-on CI** — that pipeline is network-free and holds no credentials. But the
**conformance suite must** run always-on, or the parity gate is opt-in and protects
nothing. So this plan builds a **test-owned deployment fixture** under
`tests/client/fixtures/deployment/` on an always-on reference backend, seeded at
*fixture setup* time through `booted.handle.worker` — outside any client call, so
D-16 is satisfied by construction. D-32's prohibition is on committing demo data to
`examples/`; a test fixture in `tests/` is a different thing and this plan says so
rather than letting a later reader assume otherwise.
