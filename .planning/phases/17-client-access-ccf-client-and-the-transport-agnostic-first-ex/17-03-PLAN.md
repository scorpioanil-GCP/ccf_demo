## The three shapes research measured, and why only one is admissible

| Shape | Verdict |
|---|---|
| (a) A new `src/`-resident resolver Protocol the deployment supplies | **This is D-29.** Consistent with D-14, keeps the SDK off the verdict path, mirrors the two `runtime/` seams. |
| (b) `ccf.client` imports `ccf_runtime.mcp.egress.ProductResolverProtocol` | Would be the **first `src → runtime` import in the tree**. D-29 rules it out with no exception. |
| (c) `ccf.client` runs `run_gates` + `serve` itself | Puts an SDK-owned verdict on the serve path — what `D-IMPL-102` limb 3 declined — and makes `src/ccf/client/` a fourth ungoverned product door. |

Shape (a) is what this plan builds. Note the distinction that makes D-29
implementable at all: **`GovernedResolver` is a reference implementation a
deployment instantiates and supplies, not a resolver the SDK invokes on its own
authority.** The SDK ships the composition; the deployment decides to use it. That
is the same relationship `DeterministicAssembler` already has to
`ContextAssemblerProtocol` (`src/ccf/agents/assembler.py:291`) — a shipped
reference carrying no privileged status.

## The two runtime seams this one mirrors and deliberately widens

Both are `(*, tenant, product_class, version, perspective, request) -> ServableProduct`:
- `ccf_runtime.mcp.egress.ProductResolverProtocol` (`egress.py:195-299`)
- `ccf_runtime.mcp.experience.ExperienceProductResolverProtocol` (`experience.py:288-357`)

The argument list is copied **exactly**, so a deployment writes one shape rather
than two. The return type widens in the two ways research measured to be missing:

- **`ServedProduct`, not `ServableProduct`** (DIV-2). `ServedProduct`
  (`src/ccf/replay/serve.py:94-104`) carries `product` **and** `replay_ref`;
  `ServableProduct` carries only the product. `serve.py:42-44` states plainly that
  *"all three shipped delivery paths serialize `servable.product` and none of them
  reads `servable.replay_ref`"* — the seam being typed `-> ServableProduct` is
  precisely why no door can reach it. The ruled `Result` exposes `.replay_ref`, so
  the seam must carry it.
- **A refusal in the union** (DIV-4). Every fabric refusal produced behind the
  current seam has nowhere to go. `RefusalEnvelope` (plan `17-02`) is where it goes.

**This plan does not change the two `runtime/` seams.** Unifying them is not in
scope, is not ruled, and would put a fourth door's worth of work into a plan that
has none of that budget. Say so in the module docstring so the divergence is
recorded rather than discovered.

## What the composition is, measured

The rejected example's `produce.py::assemble_and_serve`
(`examples/s1-00-companies-over-revenue/produce.py:202-411`) is the composition,
and it imports **only** from `ccf` — zero `ccf_runtime` imports, verified. Read it
in full before writing this module: it is the working shape, not a shape to invent.
Its steps, in order:

`refuse_request` → read the graph view at the temporal boundary →
`build_operator_registry` → `ProjectionEngine.execute` → mint the candidate
`ContextProductContract` → `run_gates` → `build_replay_record` → `serve`.

Two steps of that example are **out of scope here**:
- The **L1 ingest loop** (`produce.py:252-253`). D-32 rules that there is no
  demo-data mechanism in this phase and no ingest anywhere near the client seam;
  the deployment is already populated. A resolver that ingests is a resolver that
  provisions, which D-16 forbids.
- The **per-run database minting** (`deployment.py:156`, `uuid.uuid4().hex`). Also
  provisioning.
