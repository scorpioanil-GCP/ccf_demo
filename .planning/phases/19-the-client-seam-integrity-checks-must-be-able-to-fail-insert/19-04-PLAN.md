## Rulings settled at planning, so they are not re-litigated in execution

1. **The decorator lives in `suite.py`, not in each binding module.** `C-12` says *"the
   suite wraps each registered adapter"*, which is explicit: an adapter author writes
   nothing and cannot opt out. A decorator per binding module would be a decorator an
   author can forget.
2. **The decorator WRAPS; it does not subclass, and the stand-in must be able to fail.**
   `assert_wire_failure_parity` enforces `type(broken) is type(healthy)` for the break hook
   (`suite.py:610-618`), and that check is real only because `break_transport` is an
   **independent hook** that could have returned a different type. A wrapper has no such
   independence, so the obvious stand-in — *"assert the wrapper's inner adapter is the
   object `subject.connect(root)` returned"* — is a **tautology**: the leg built the wrapper
   from that object one line earlier, and no implementation of anything could make the
   assertion fail. An assertion that cannot fail, in the phase whose subject is assertions
   that cannot fail, is not acceptable at any strength.

   The ruling: assert something checkable instead. Per subject, connect a **second,
   independent** adapter from the same factory over its own provisioned root
   (`witness = subject.connect(provision(f"{subject.name}-witness"))`) and assert
   `type(inner) is type(witness)`. That can fail — a subject whose factory returns a
   different adapter type depending on the root, or which the leg wrapped before the factory
   ran, goes red — and it is the nearest true analogue of the parity leg's check. The
   docstring states plainly that it is **weaker** than the break-hook check and why: there
   the two objects come from two independent hooks, here they come from two calls to one
   hook, so this pins factory type-stability rather than substrate damage. A dropped check
   nobody notices is this repo's recurring failure; a fake check nobody notices is worse.
3. **The tamper keeps the bytes well-formed.** Appending a space inside the vessel's JSON
   text is a byte change that is not a contract violation, so the failure lands on the
   address check rather than on the parser (`codec.py:296`) or the contract check
   (`codec.py:254`). A tamper that broke JSON validity would make the leg prove the parser
   fires — `19-RESEARCH.md` Pitfall 3.
4. **The crossed echo is DERIVED, never spelled.** Read the question the leg was handed and
   produce a different one from it — flip an admitted parameter value, or suffix
   `product_id`. A spelled second question is a red no-hardcoding lint and would also put
   deployment vocabulary in a module whose whole claim is that it holds none.
5. **`D-GATE-18`'s zero-diff claim is not violated.** It was about binding a new *adapter*
   without touching the suite. Both new legs take the same `SUBJECTS` tuples and the same
   `provision` fixture; no existing leg changes; `test_inprocess_conformance.py` and
   `test_mcp_conformance.py` each gain exactly **two call lines**. Record that arithmetic
   (8 → 10 each) in the SUMMARY.

Add one control per new leg.

**The mechanism is ruled here, not chosen in execution.** `CLNT-12`/`D-22` require the
named sabotage control to ship in the same plan as its assertion, and wave 4 depends on this
plan, so an executor arriving at a menu is an executor arriving at a stop.

The controls cannot simply pass an honest subject — the legs wrap their subjects themselves,
so an honest subject would still be tampered. The divergence is made at the **subject**
level, using the **reversing-adapter** form:

For each leg, construct an `AdapterSubject` carrying the same `name` and `break_transport`
as an existing subject, and a `connect` that returns
`_Tampering(real_connect(root), edit)` — where `_Tampering` is the **shipped** decorator
Task 1 added and `edit` is the **shipped** edit function that same leg uses, imported from
`suite.py` rather than copied. The leg then wraps that subject's adapter in `_Tampering`
again with the same edit, so the client sees `edit(edit(bytes))`, which is the original
bytes because Task 1's edits are **involutions**. The client therefore does not raise, and
the leg's **first** limb fires.

Why this form and not the alternative: it fails safe. If an edit ever stops being an
involution — or stops changing anything at all — the composition stops being the identity
and the control goes red, loudly, rather than passing for a reason nobody can state. The
rejected alternative was giving the legs an internal seam a control could substitute; it was
rejected because a seam that exists only so a control can reach through it is a second path
into the leg, and a leg with a substitutable interior is a leg whose shipped behaviour is
not what the control exercised. There is no escape hatch here: if the reversing form does
not work, that is a defect in Task 1's edits — fix the edit's involution property in Task 1
and say so — not grounds to invent a third mechanism.

Both controls import `_Tampering` and the two edit functions from `suite.py` directly. That
is deliberate and is this module's own rule: *"a control that tests a copy proves only that
the copy fires."* A control that re-implemented the edit would prove the copy is an
