## Rulings settled at planning, so they are not re-litigated in execution

1. **Scope is `src/ccf/client/adapters/` only.** Not `src/`, not `runtime/`, not
   `examples/`. `door_answer` constructs the outcome and lives in `src/ccf/products/door.py`
   — that is the **one** place it should be constructed, and a wider scope would count it
   and force an exemption list, which is how a narrow gate becomes the framework `C-13`
   rejected.
2. **The gate counts TWO shapes, because its analog counts two.**
   `tests/client/test_surface.py:256-265` counts a call to an `ast.Name` bound by an import
   **and** any `isinstance(function, ast.Attribute) and function.attr == "Result"`, and its
   docstring states the reason in the repo's own words: *"over-counting fails the build and
   puts a human in front of the question, while under-counting is the silent direction."*
   A gate that counted only the first would be **weaker than the pattern it claims to
   mirror**: an adapter writing `import ccf.client.wire` … `ccf.client.wire.WireOutcome(...)`,
   or `from ccf.client import wire` … `wire.WireOutcome(...)`, resolves no local name and
   would go uncounted.

   So: count a call whose `func` is an `ast.Name` in the import-resolved alias set — after
   `19-01` that is `DoorOutcome` (the definition) and `WireOutcome` (the alias), plus any
   local `as` alias, resolved the way `count_result_construction_sites` resolves `Result`'s —
   **and** count a call whose `func` is an `ast.Attribute` with
   `attr in {"WireOutcome", "DoorOutcome"}`, regardless of what it is an attribute *of*.
   The second is deliberately broader than it needs to be, on the analog's own argument, and
   the docstring says so. **Measure before writing the rule**, as the analog did: confirm
   with a one-off AST run that no such attribute call exists anywhere in the scanned trees
   today, and state the measurement in the docstring and in the SUMMARY.
3. **The gate raises on an unresolvable root or an unparseable file, and reports zeros.**
   Copied verbatim in spirit from `test_surface.py:24-32`: a sweep that drops what it
   cannot resolve reports less as the tree grows, which is exactly how a citation gate in
   this repo passed vacuously for a full wave. The shipped assertion additionally refuses a
   walk that read **nothing**.
4. **This gate does not replace the type change; it survives it.** Both hold. Say so in the
   docstring, with the reason: `mypy`'s `files` is `["src", "runtime"]`, so an out-of-tree
   adapter is invisible to it, and an in-tree adapter could construct-then-encode without
   violating the return type at all.
5. **The gate states its blind spot, and the blind spot is not hypothetical.** The analog
   ends with an explicit *"Not detectable, and named rather than pretended away"* paragraph;
   this one gets the same, naming two shapes:

   - a construction reached through `getattr(module, "WireOutcome")(...)` — dynamic dispatch
     no AST walk of this kind resolves;
   - **re-labelling**, which is not a construction at all: `decode_outcome(raw, sent=…)`
     followed by `.model_copy(update={"request": request})` and `encode_outcome`. No
     construction counter can see it, because nothing is constructed. This is the shape most
     likely to re-open `B0`, and it is **not** hypothetical — `19-03` Task 2 and `19-04`
     Task 1 both use exactly that idiom to build their controls. A gate whose docstring
     claimed *"no adapter can produce a forged outcome"* would be falsified by this phase's
     own test code, one directory over.

   What actually stops re-labelling is not this gate: it is `19-04`'s conformance obligation,
   which corrupts every registered subject's bytes and requires the client to raise, and
   which an adapter author neither writes nor can opt out of. Say that in the docstring, so
   the reader who finds the blind spot also finds its coverage.
