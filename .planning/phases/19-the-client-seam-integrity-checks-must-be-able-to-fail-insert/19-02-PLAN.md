## Rulings settled at planning, so they are not re-litigated in execution

1. **No compatibility shim, and no deprecation window for out-of-tree adapters.**
   Pre-1.0; `docs/surface/v0.2-surface.json` is a v0.2 baseline; there is no plugin
   discovery and `D-05` forbids one, so an out-of-tree adapter can only exist by a third
   party assigning into `SCHEME_REGISTRY`. An `ask` accepting **either** bytes or an
   outcome object would restore `D-11`'s permission and an adapter taking the object
   branch reconstructs the echo again with every gate green — Pitfall 2. `19-08` records
   the ruling in a `D-IMPL` entry (`C-16` rules it in the same entry as the tool break).
2. **The wire between the MCP door and the MCP adapter stays text; the adapter encodes
   it.** Raw bytes cannot be an MCP tool result without base64, and `wire.py:50-53`
   rejects a second rendering. `ask` returns `text.encode("utf-8")`. This is a *text*
   pass-through the adapter never inspects, which is what `C-06` asks for: no transcoding
   of the shape.
3. **The malformed-bytes diagnostic narrows, and that is accepted.** `_decode:468-473`
   raises a `TransportError` naming the scheme and the program; `decode_outcome`
   (`codec.py:296-301`) says the same thing in the same words without that context. Take
   the generic message. A thin adapter-level well-formedness check would parse and
   discard — not a transcoding step, but a place a future adapter grows one.
4. **The clock does not move** (`C-15`). `inprocess.ask` keeps
   `request.temporal_boundary or datetime.now(UTC)` exactly where it is, and passes the
   resolved instant to the door half as a separate argument — mirroring `mcp+stdio`,
   where `asked_at` is a separate tool argument. The **encoded** `WireRequest` carries
   `None`. **`C-18`'s temporal cross-check is deliberately NOT replicated here**, and the
   reason is structural rather than an omission: in-process, the resolved instant is
   derived from the very `WireRequest` the client just encoded, inside one process, with no
   wire between the two — so a comparison would compare a value with itself, which is the
   defect this phase exists to close, not a check. The double source `C-18` closes exists
   only where `asked_at` is a separate **transport** argument, which is the MCP tool
   (`19-01` Task 2 owns it). The underlying defect (the client reads the clock, while
   `client.py:139-141` promises the deployment does) is `19-07`'s prose amendment and
   `19-08`'s deferred `D-IMPL` entry, **not** this plan's fix.
5. **`decode_outcome` returns a `DecodedOutcome`, and that shape is RULED here rather than
   left to the executor.** Measured at HEAD: `decode_outcome` calls `check_outcome` and then
   **discards its return** (`codec.py:303-304` — `check_outcome(outcome, sent=sent)` on one
   line, `return outcome` on the next), while `_result_from` sources the vessel *from* that
   return (`client.py:215` — `vessel = check_outcome(outcome, sent=sent)`) and
   `Result.__init__` requires it (`result.py:203-206`). So moving the call into the decoder
   and leaving the signature alone would strand `_result_from` with no vessel, and its only
   escapes are both forbidden: re-parsing `product_json` in `client.py` is a **second**
   contract validation and a **second** decode path, which is what `D-12` exists to
   prevent; and editing `codec.py` was, until this revision, not declared in
   `files_modified`. The ruling is therefore: `codec.py` is in scope, and the decoder
   carries the vessel out. A frozen dataclass rather than a bare tuple, because
   `ccf.products.door.ServedAnswer` already sets that precedent for *"a value and the thing
   that authorized it"* in this codebase, and because a positional pair at a published
   surface reads as an accident at the first call site that unpacks it wrong.
6. **The in-process door half takes text, never a `WireRequest` object.** That is the
   whole of `C-07`: if it took the object, the two halves would share one object and the
   in-process check would be cosmetic on the most-used transport.
