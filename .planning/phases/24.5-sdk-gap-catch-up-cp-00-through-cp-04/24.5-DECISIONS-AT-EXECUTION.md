## 24.5-L-23 — CUT under criterion 18's own branch (2026-09-02, plan 24.5-11)

**Dave's conditional, verbatim from `24.5-LEDGER.md` row `24.5-L-23` (RULED, Dave, 2026-09-02):**

**Criterion 18, verbatim from `.planning/ROADMAP.md` `### Phase 24.5`:**

> *(`L-23`, CONDITIONAL) `ProductClassDeclaration` gains the max-TTL ceiling ONLY IF the plan
> states in ONE sentence "class declares the cap; deployment supplies the number; serve refuses
> over-cap by name" and a test enforces exactly that precedence; otherwise `L-23` is CUT by a
> dated note in the phase record and NO field is added — two unused fields is RED.*

**The one sentence:**

**Class declares the cap (`max_ttl_key`); deployment supplies the number (`MaxTTL.seconds` registered under that key); serve refuses over-cap by name (`ttl-bounds`).**

**The measurement.** The sentence is already true of the tree — `24.5-RESEARCH.md` measured it
at `bcd2360`, and plan `24.5-11` measured it again on `55c2fe6` and pinned it by test:

| Limb | Symbol | Pinned by |
|---|---|---|
| Class declares the cap | `src/ccf/controlplane/artifacts.py::ProductClassDeclaration.max_ttl_key` — a KEY, by design; the class's own docstring says why the number is not here | `tests/products/test_max_ttl_precedence.py::test_no_ceiling_in_seconds_lives_on_the_class_or_the_registered_class` |
| Deployment supplies the number | `src/ccf/products/contract.py::MaxTTL.seconds`, registered by the deployment under that key; `src/ccf/products/contract.py::register_product_class` resolves `(max_ttl_key, max_ttl_version)` and refuses a non-`MaxTTL` | `tests/products/test_max_ttl_precedence.py::test_the_deployment_moves_the_cap_and_the_class_declaration_does_not_change` |
| Serve refuses over-cap by name | `src/ccf/products/gates.py::_refuse_ttl` returns `src/ccf/products/gates.py::TTLRefusal` with `gate == GATE_TTL_BOUNDS` (`"ttl-bounds"`) carrying the REGISTERED `max_ttl_seconds` | `tests/products/test_max_ttl_precedence.py::test_the_registered_number_decides_and_serve_refuses_over_cap_by_name` |

**What the ledger row named as the gap, and why it is not one.** Row `24.5-L-23` reads *"carries
`max_ttl_key` and no field for the ceiling's seconds; the value lives only in the example's own
`artifacts/ttl.yaml`."* That is the precedence working, not failing: the declaration is the
authored class artifact and the ceiling's number is a separately registered Control Plane value
whose version is minted at registration (`D-IMPL-76`'s shape, restated on
`ProductClassDeclaration`'s docstring). A seconds field on the declaration would be a second
copy of the number the resolver already enforces from the registry — the *"second copy of
`binding.yaml`'s TTL ints"* Dave's conditional names — and would be read by nothing on the serve
path, since `_refuse_ttl` reads `MaxTTL.seconds` off the registered artifact. Two unused fields
is RED.

**Disposition: CUT.** `L-23` is closed without an edit to `src/` or `runtime/`:

- **NO field was added** to `ProductClassDeclaration` or to `RegisteredProductClass`. Measured:
  `git diff phase-24.5-base..HEAD -- src/ccf/controlplane/artifacts.py` touches only
  `HalfLifeEntry` (`24.5-L-22`), and `grep -v '^\s*#' src/ccf/controlplane/artifacts.py | grep -c
  max_ttl_seconds` = 0. The precedence test's third case asserts by set comprehension that no
  `max_ttl*` name other than `max_ttl_key` / `max_ttl_version` and no `*ttl_seconds` name exists
  on either class, so a future second copy goes RED there rather than shipping quietly.
- The precedence is **stated** (above), **enforced** (the three tests), and **cut** (this note) —
  criterion 18's cut branch in full.

**Whose call this is.** This is the planning-and-execution call inside criterion 18, not a Dave
ruling. `D-IMPL-240` says so by name: *"It does not rule `24.5-L-23`, whose CUT-or-keep is
criterion 18's own branch."* Dave stated the conditional; he did not state the cut, and his name
is not written on it (`D-IMPL-227`). One reading of criterion 18's first branch deserves stating
so the gate can weigh it: since the sentence *can* be stated and *is* tested, a reader might take
the first branch as satisfied and expect the declaration to "gain the ceiling". Plan `24.5-11`
reads it the other way, following the conditional's own last clause: the declaration already
holds the cap as a key, the number is enforced from the registry, and the only thing the first
branch could add is the unused field the conditional forbids. If that reading is disputed at the
gate, the remedy is a ruling, not a field.

**Forward.** A future proposal to put a ceiling-in-seconds on the class declaration is a
`D-IMPL` (it would change where the number is authored and how `max_ttl_version` is minted), not a
field added under this row. `L-23` does not reappear on any roster by this note; widening is a
dated `D-IMPL` before the edit (`D-IMPL-214`).
