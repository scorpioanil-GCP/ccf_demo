## Critical Issues

### CR-01: Sentinel-default additive fields change every content hash they touch, so pre-phase replay records diverge and pre-phase artifact versions change — the D-IMPL-240 (1) defect class, in five more places

**File:** `src/ccf/operators/params.py::TraversalNeighborhoodParameters` (`admitted_entity_classes`), `src/ccf/graph/protocols.py::TraversalSpec` (`admitted_entity_classes`, `direction`), `src/ccf/products/contract.py::ProductLineage` (`store_snapshot_pin`), `src/ccf/controlplane/artifacts.py::HalfLifeEntry` (`decay`, `half_life_seconds`), `src/ccf/controlplane/artifacts.py::ProductClassDeclaration` (`serve_obligations`), `src/ccf/products/request.py::ProductRequestContract` (`unsupported_arguments`), `src/ccf/assembly/worker.py::RelationshipResolutionRule` (three selector fields). Consumers: `src/ccf/replay/engine.py::replay` (the `execution.steps != path.steps` and `graph_query_sequence` comparisons), `src/ccf/operators/base.py::mint_provenance` (`parameter_hash=content_hash(operator.parameters)`), `src/ccf/controlplane/registry.py` (content-hash versions).

**Issue:** Measured with identical inputs at `13bd250` and HEAD:

| contract | base | HEAD |
|---|---|---|
| `TraversalNeighborhoodParameters(seed={"a"}, types={"r"}, depth=1)` | `34df2d94…` | `6515f4a7…` |
| `GraphQuery(tenant="t", as_of=…, traverse=TraversalSpec(…))` | `905e1f81…` | `e5086593…` |
| `HalfLifeTable(entries={"x": HalfLifeEntry(10, "d", "e")})` | `66d55b5f…` | `76ce10bc…` |

Consequences that follow from code already in the tree, not from speculation:

1. Every replay record written before this phase whose plan contains a traversal step carries a `parameter_hash` computed at base. `replay()` re-executes at HEAD, `mint_provenance` hashes the same artifact to the new value, and `execution.steps != path.steps` raises `ReplayDivergence("… a differing parameter hash means the operators are no longer the ones that ran")` — for operators that are exactly the ones that ran. All five ladder products traverse.
2. The same record's `graph_query_sequence` pins (D-11) were computed over a `GraphQuery` whose `TraversalSpec` had three fields; the re-executed queries hash with five. The D-11 comparison diverges for the same reason.
3. `product_content_address` is recomputed from the rehydrated product, whose `ProductLineage` now serializes `store_snapshot_pin`. D-IMPL-240 (1) saw this for cp-04's two seals and re-sealed them; it does not reach a record in an ArtifactStore.
4. The registry's version of a byte-identical `HalfLifeTable` (or product-class declaration, or request contract) document is a different string at HEAD. A deployment that re-registers its unchanged Control Plane on upgrade gets new versions; a record pinning the old version resolves only what the store still holds by the old address.

The project already knows this property of `_normalize` — `src/ccf/replay/engine.py` (lines 288–300) documents that a rebuilt model "serializes every sentinel-defaulted field a *later* contract version added" and protects the **record's own address** by byte-first verification (D-IMPL-89) — but the three hashes above are recomputed from re-execution, so byte-first verification cannot protect them, and `ContextFabricSnapshot.build` deliberately kept `store_snapshot_pin` out of `graph_snapshot_id` "to keep the re-derived id comparable across records written before and after the field existed" while the sibling hashes one line away were left to move. The phase's "additive over breaking" claim holds for signatures and validation; it does not hold for identity, and whitepaper §7.10 / CLAUDE.md §7.4 make identity the contract.

No test went red because no pre-phase record exists in the tree (the only `graph_query_sequence` mention under `examples/` is a governance document, not a record).

**Fix:** This needs a ruling before an edit, in the D-IMPL-240 shape (it is the same question with a wider scope). Two mechanisms are available; both are additive to the canonicalizer, neither touches the fields:

```python
# Option A — src/ccf/contracts/canonical.py::_normalize
# Omit a field whose value equals a declared "hash-transparent" default,
# marked at the field: `Field(default=NO_STORE_SNAPSHOT_PIN, json_schema_extra={"ccf_hash_transparent": True})`.
# A record hashed before the field existed then re-hashes identically; a
# non-default value is rendered and changes the hash, as it should.

# Option B — no code change; record in D-GATE-24.5 that replay records and
# Control Plane versions are bound to the SDK contract revision that wrote
# them, and that the 24.5 upgrade re-registers artifacts under new versions.
```

Whichever is chosen, `tests/replay/` should gain a golden record fixture serialized at `13bd250` and replayed at HEAD, so this class is caught the next time a sentinel field is added.

## Warnings

### WR-01: The lineage half of the declared-obligations gate reads payload content (`len(value)`), which the contract docstring says it never does — a ruling question under D-IMPL-238 limb 3

**File:** `src/ccf/products/gates.py::_refuse_declared_obligations` (the `for member in sorted(obligations.lineage_inputs_at)` loop); `src/ccf/products/contract.py::ServeObligations` (docstring: "what those members contain is never read here").

**Issue:** The loop does `value = candidate.payload.get(member)` and then `isinstance(value, Sized) and len(value) == 0`. Presence of a named top-level member is arguably structural; measuring the member's *length* is a read of served payload content, and the review brief's rule is "no payload inspection anywhere in `gates.py`". The `ServeObligations` docstring asserts the opposite of what the code does ("what those members contain is never read here"), so the tree currently makes two incompatible claims. D-IMPL-238 licenses "structural gates" and forbids a "payload-schema gate"; whether emptiness is structure or schema is a reading nobody has recorded.

**Fix:** Either narrow the gate to presence-only (`value is None` → `absent`) and delete the `Sized` branch so the code matches its docstring, or record in D-GATE-24.5 that "present and non-empty" is the structural reading D-IMPL-238 licenses and correct the `ServeObligations` docstring to say the member's emptiness is read. Do not leave the docstring and the code disagreeing.

### WR-02: A request `debt_tolerance` outside `[0, 1]` is honored, so a negative tolerance refuses every measured product and the refusal reports it as what the class declared

**File:** `src/ccf/products/gates.py::effective_debt_ceiling`, `src/ccf/products/gates.py::_as_finite_decimal`, `src/ccf/products/gates.py::_refuse_declared_obligations`.

**Issue:** `ServeObligations._ceiling_is_a_proportion` holds the **class** ceiling to `[0, 1]`, but the **request** tolerance is only checked for finiteness. Measured: `effective_debt_ceiling(declared=Decimal("0.5"), requested=-1)` returns `-1`. Every candidate with `debt.debt >= 0` — which is all of them — is then refused with `declared="-1"`, a number no class declared, in a refusal whose `declared` field the docstring defines as "what the class declared, rendered". A caller can force a 409 on any class that declares a ceiling by sending `debt_tolerance: -1`. Not an entitlement bypass, but a refusal that lies about its cause and a denial lever the ruling ("a request may tighten") did not contemplate.

**Fix:**

```python
def _as_finite_decimal(requested: object) -> Decimal | None:
    ...
    if not value.is_finite() or not (Decimal(0) <= value <= Decimal(1)):
        return None  # not a proportion → not a tolerance; the class's ceiling stands
    return value
```

and a test that `debt_tolerance=-1` leaves the effective ceiling at the class's number.

### WR-03: Endpoint-selection fields on `RelationshipResolutionRule` are not cross-validated, so a dangling `subject_rule`/`object_rule` silently never fires and the required `*_entity_class` fields are inert under endpoint selection

**File:** `src/ccf/assembly/worker.py::RelationshipResolutionRule`, `src/ccf/assembly/worker.py::EntityResolutionSpec` (no validator), `src/ccf/assembly/worker.py::AssemblyWorker` (the `by_rule.get(rule.subject_rule, ())` branch).

**Issue:** Measured: an `EntityResolutionSpec` whose relationship rule names `object_rule="nonexistent-rule"` constructs without error; at ingest `by_rule.get(...)` returns `()` and the rule mints nothing, forever, with no refusal. Under endpoint selection the subjects and objects are chosen purely by `resolved_by`, and `subject_entity_class` / `object_entity_class` — still required — are never consulted; the docstring's claim that they "describe the endpoints the named entity rules produce" is not enforced, so a rule naming `subject_entity_class="org"` with `subject_rule` pointing at a rule that resolves `person` mints the edge anyway. That is two declared fields with no effect — the exact shape L-23 was cut to avoid (".continue-here.md": "two unused fields is RED").

**Fix:** A `model_validator(mode="after")` on `EntityResolutionSpec`:

```python
@model_validator(mode="after")
def _endpoint_selectors_resolve(self) -> EntityResolutionSpec:
    by_key = {rule.match_key: rule for rule in self.entity_rules}
    for rel in self.relationship_rules:
        for selector, declared_class in (
            (rel.subject_rule, rel.subject_entity_class),
            (rel.object_rule, rel.object_entity_class),
        ):
            if selector is None:
                continue
            entity_rule = by_key.get(selector)
            if entity_rule is None:
                raise ValueError(f"relationship rule {rel.relationship_type!r} selects endpoint by rule {selector!r}, which no entity rule declares (24.5-L-21)")
            if entity_rule.entity_class != declared_class:
                raise ValueError(f"... rule {selector!r} resolves {entity_rule.entity_class!r}, not the declared {declared_class!r}")
    return self
```

### IN-01: The store-pin `ReplayDivergence` branch in `replay()` is unreachable through `replay()` itself

**File:** `src/ccf/replay/engine.py::replay` (the `reproduced_snapshot.store_snapshot_pin != snapshot.store_snapshot_pin` branch); `src/ccf/replay/snapshots.py::SnapshotReader.snapshot_pin`.

**Issue:** `replay()` always drives the engine through `SnapshotReader`, whose `snapshot_pin()` returns the *recorded* pin, and `ProjectionEngine._reader_snapshot_pin` reads exactly that. So `reproduced_snapshot.store_snapshot_pin == snapshot.store_snapshot_pin` by construction and the branch cannot fire from this function. No test asserts its message (`grep "read under store pin" tests/` finds nothing). The real protection is `SnapshotReader._pinned_reader` refusing an unpinnable reader, which is tested. This is a vacuity note, not a defect: either document the branch as a defense against an environment that bypasses `SnapshotReader`, or drop it.

## Rejected on verification

These were candidate findings that the tree disproved; they are recorded so the panel does not re-derive them.

- **`AssemblyRefusal` cannot be enveloped because it is not in `_PRE_ASSEMBLY_REFUSALS`.** `envelope_for` only raises when a lineage is *offered* for a pre-assembly kind; a non-pre-assembly kind with `pre_assembly_lineage=None` envelopes normally. Not a defect.
- **`neo4j.py` uses `starts` / `entity_rows` before definition in the admission block.** Both are defined earlier in the same `answer_whole_query` closure. Not a defect.
- **SQLite/Postgres admission with an empty `admitted_entity_classes` renders invalid SQL.** `_in_clause` returns the `_FALSE` fragment for an empty set; the fallback's `class_of.get(n) in frozenset()` is also always false. Consistent.
- **Circular import between `ccf.products.refusal` and `ccf.agents.errors`.** Both import cleanly in isolation; `errors.py` depends only on `ccf.contracts.base`.
- **`product.py` uses `json` without importing it.** `import json` is present at line 130.
- **`SnapshotReader.as_of` builds a `GraphQuery` with too few fields.** `GraphQuery`'s only required fields are `tenant_id` and `as_of`.
- **The `refusal.py` docstring's "twenty" kinds is a stale count.** `len(REFUSAL_KINDS) == 20`.
- **The HTTP 409 door compares a string literal.** It compares `REFUSAL_KINDS[DeclaredObligationRefusal]`, the mapping value.
- **`build_operator_registry` arm order lets one traversal artifact match the other.** The two parameter artifact classes share only the marker base; `isinstance` cannot cross.
