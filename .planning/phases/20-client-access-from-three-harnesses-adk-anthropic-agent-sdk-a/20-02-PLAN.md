Dave's ruling 6(b) requires `cinv01a-prompt-shape` to refuse a short agent prompt
embedding domain instruction. Two candidate tightenings were scored over the
whole of `RULE_TREE_SCOPE["no-hardcoding"]` (`src`, `runtime`, `examples`,

**Candidate A — lower `PROMPT_SCORE_THRESHOLD` from 2 to 1. REJECTED: 94 new
findings.** By tree: `src` 58, `runtime` 8, `tests` 28, `examples` 0. Effectively
all are false positives of two classes — Cypher/SQL fragments that clear
`_is_prose_candidate` because they do not open with a `_SQL_OPENERS` keyword

prose in error messages and docstring-adjacent constants. Shipping this means 94
rewordings or 94 allowlist entries for zero real violations, and it does not even
close the hole: the blocker's own shapes score 0-1 and two of the four would

is a proxy for the wrong thing** — the same objection this module's own docstring
already records against the diagnostic false positives Dave ruled on 2026-08-04.

**Candidate B — a destination arm. ADOPTED: 2 findings, both genuine.** Refuse a
prose-candidate literal that reaches a **model-instruction sink**, without
consulting `prompt_score` at all. This is the discriminator the module docstring
already commits to in words — *"a prompt is a string sent to a model; a
diagnostic is a string shown to a developer"* — implemented by destination rather
than by shape. Measured counts by sink family over the four trees: sink keyword
argument 1, chat-message mapping 1, sink call positional-0 **0**, and **0** in
each of `src`, `runtime`, `tests`.

**The two findings are real §6.4 violations that this phase surfaces, not false
positives, and task 4 remediates them rather than exempting them:**

| Site | Sink | Literal |
|------|------|---------|
| `examples/external/00-hello-context/client_adk.py:59` | `types.Part(text=…)` | `"Use the available tools to retrieve the governed context, then state your recommendation."` |
| `examples/external/00-hello-context/client_anthropic.py:59` | `{"role": "user", "content": …}` | the same literal |

Both are the **same** hardcoded agent instruction, reached the same way: a
`os.environ.get("CCF_EXAMPLE_QUESTION", <literal>)` fallback that is what actually
runs on the default path. That is a prompt in code wearing an env var as a hat,
and it is exactly the shape ruling 6(a) forbids for leg 2. The sibling file
`examples/s2-01-external-consumers/client_claude_agent.py:39` states the correct
shape in its own docstring — *"prompts never appear in code — CLAUDE.md §6.4"* —
and uses required `os.environ[...]` with no default. **Ruling 6(c) is why this
matters: plan `20-07` moves that file out of `examples/`, so the only in-tree

**The length floor was measured, not guessed.** The arm reuses

**Accepted residual, stated because a name-keyed sink set has one.** The sink
sets are enumerations of names, so a harness whose instruction API uses a name

The arm is the mechanism of record; it is not a proof of absence.

**Door resolution (`H-02`).** `resolve_door(root) -> tuple[str, list[str]]` returns
the opaque pair: the command is `sys.executable`, and the args are
`[str(load_binding_document(root).server), str(root)]`. Resolved from the
deployment's own `binding.yaml`, never composed from a remembered path. The
runner prints the resolved pair once, so a reader of the console output can see
that the thing handed to each client is an ordinary program invocation and
nothing CCF-shaped.

**The question address (`H-03`, widened by measurement).** Eight values the door
requires — `tenant`, `product_class`, `version`, `subject`, `intent`, `freshness`,
`asked_at`, plus the request parameters — are deployment facts living in
`binding.yaml`'s `question:` block and `ccf_config.yaml`. Under CLAUDE.md §9 they
may not be literals in client code, so the runner resolves them and passes them
to each client **on argv**. `H-02`/`H-03`'s intent is unchanged and reinforced:
the client receives the door's location and the question's address as *input*,
never as knowledge — only the flag count grows.

`build_question(root, as_of) -> dict` assembles those values from the copy's own
documents. **Ship them as one `--question-json` flag**, not eight scalar flags:
eight flags is eight parsing sites in each of three clients, and the recommended
single flag keeps each client's argv surface to three items —
`--server-command`, `--server-arg` (repeatable) and `--question-json` — which is
what makes the three clients readably the same program three ways. Record that
