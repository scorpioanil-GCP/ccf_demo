### CR-01: The `R-1` fix asserts two SDK facts that the SDK contradicts

**File:** `examples/cp-04-corporate-family-tree/run.py:262-272`; `examples/cp-04-corporate-family-tree/transport.py:49-55`

**Issue.** The replacement comment written at `1a416ef0` says:

> `run.py:268-270` — "**BOTH are this example's own types, the SDK knows neither**,
> and `ccf.products.refusal::REFUSAL_KINDS` therefore **declares no envelope naming
> either**."
>
> `transport.py:53-54` — "… and **the fabric declares no envelope for either**."

Both clauses are measurably false, and both were introduced by the correction to `R-1`.

1. **"this example's own types" is false for the non-integer refusal.** The
   non-integer `max_depth` case raises `AssemblyRefused`
   (`examples/cp-04-corporate-family-tree/deployment.py:2193`), and `AssemblyRefused`
   is an **SDK** class defined at `src/ccf/agents/errors.py:128` and imported by
   `deployment.py` and by `run.py:85`. There is no example-local type for that case
   at all. Only `DepthOutOfBounds` (`deployment.py:2143`) is the example's own.

2. **"declares no envelope"/"the fabric declares no envelope for either" is false
   as a statement about the condition.** `AssemblyRefusal` — the value sibling of
   `AssemblyRefused`, housed beside it at `src/ccf/agents/errors.py:167` — **is** in
   `REFUSAL_KINDS` under the token `assembly-refusal`
   (`src/ccf/products/refusal.py:270`). `AssemblyRefused.as_refusal()`
   (`src/ccf/agents/errors.py:154`) exists to convert the raise into that value, and
   `AssemblyRefusal.reason` is a free `str` whose vocabulary is explicitly *"the
   deployment's to declare"* (`src/ccf/agents/errors.py:195-202`). The assembler seam
   returns `AssemblyOutcome | ProductRequestViolation | AssemblyRefusal`
   (`src/ccf/agents/assembler.py:298`), and that docstring at `:311-316` states the
   `24.5-L-11` widening exists *"so that a conforming assembler can return it rather
   than raising `AssemblyRefused` and having the verdict reach a client as `ToolError`
   prose."*

3. **Therefore the framing "A RECORDED SDK-SURFACE GAP RATHER THAN A CHOICE"
   (`run.py:262-263`) is backwards.** The SDK ships the channel and documents the
   decision as the deployment's; `AssemblyRefusal`'s own docstring closes with *"A
   deployment chooses per refusal: raise for identity, return this for an …"*. cp-04
   **already uses that channel** thirty lines away — `assembler.py:259-269` returns
   `AnchorAmbiguityRefusal` rather than raising, and its comment at `:251-253` says
   so. So the same file demonstrates the choice while `run.py` calls it a gap.

**Fix.** Replace both passages with the measured statement, or return the depth
refusals as data. Minimum correction:

```python
# TWO CONDITIONS ON THIS RUNG REACH A CALLER AS A RAISE, AND THAT IS THIS
# DEPLOYMENT'S CHOICE RATHER THAN AN SDK GAP (`24.5-L-11`). A non-integer
# `max_depth` is refused inside `deployment.py::resolve_max_depth` (`WR-01`)
# with `ccf.agents.errors.AssemblyRefused` — an SDK type; a depth above the
# declared ceiling returns from that same function as this example's own
# `deployment.DepthOutOfBounds` and `assembler.py` raises `AssemblyRefused`
# for it. The SDK's returned-as-data sibling `AssemblyRefusal` IS in
# `ccf.products.refusal::REFUSAL_KINDS` (token `assembly-refusal`), so either
# could cross typed; this rung keeps the raise and records why at spec §F.4.
```

and in `transport.py:53-54`, `"the fabric declares no envelope for either"` →
`"neither is routed through the envelope on this rung, though `assembly-refusal`
would carry both"`.
