## Implementation Decisions

All four ruled by Dave at this sitting, 2026-09-03, in one message; recorded verbatim at
`docs/DECISIONS.md` `D-IMPL-245`. His framing governs every row: **distinguish product semantics
from implementation mechanics, so the product ladder is not over-versioned.**

### Re-version semantics (cp-01, cp-02, cp-03)
- **D-01: the Context Product lane stays `1.0.0`** — `semver` and `schema_version` in each
  `ccf_config.yaml` unchanged. The served bytes and the product contract did not change (seals
  restored to base under `D-IMPL-240` am.1). The Standard's change classes (§14, table at
  `references/Context_Product_Specification_Standard_v0-3.md:694-696`) are the boundary: PATCH =
  gates/telemetry/documentation with no consumer-shape impact; MINOR = additive payload field, new
  optional parameter, projection plan, λ_c recalibration; MAJOR = field removal/retyping, changed
  defaults, `ttl_anchor`, Assembly Mode, policy-envelope semantics. *"I would not move the product from
  1.0.0 merely because the SDK now carries a refusal correctly as data."* **No MINOR bump.**
- **D-02: `ASSEMBLER_VERSION` `1.0.0` → `1.0.1` in each example assembler whose behavior changed**
  (`examples/cp-0{1,2,3}-*/assembler.py`, each declares the constant and returns it from
  `assembler_version`): where the assembler previously raised a prose exception for `as_of` and now
  returns the typed refusal through the same seam, *"replay should distinguish those two
  implementations."* The planner measures which of the three actually changed behavior (the
  `ParameterNotSupported` branch is unreachable for `as_of` since `refuse_request`'s tier step fires
  first — its removal is the behavior change) and bumps exactly those. cp-04's assembler: bump only if
  its ambiguous-anchor change (D-08) lands in `assembler.py`; otherwise its constant does not move.
- **D-03: what a re-pin is** — corrected prose (README, `summary_explanations.md`, module docstrings,
  the dead branch and its comment), rewritten tests, a re-run and re-pinned `page/run-transcript.txt`,
  a republished page. Every content address is re-hashed LIVE before any seal line moves
  (`D-IMPL-240` am.1's lesson); the expectation is that the seals do NOT move.

### hw1 rebuild
- **D-04: seed hw1 so the default example succeeds.** A small DETERMINISTIC fixture batch is ingested
  at boot so that `inprocess:` and `mcp+stdio:` return the SAME SUCCESSFUL product on a clean
  checkout — the answer plus Context Debt, content address, replay record and expiry the README says
  the example demonstrates. Constraint the planner must honor: hw1's README posture *"nothing here is
  committed as data — no store file, no seed artifact"* must be reconciled explicitly — the seed is a
  declared signal-batch ARTIFACT interpreted at boot (the `tests/deployment` `events.yaml` shape, the
  L1 envelope), never a committed store file; the README sentence is rewritten to say so.
- **D-05: keep the empty-fabric refusal as a NEGATIVE test.** A separate test boots empty and proves
  `empty-operator-result` refuses by name on both transports (transport parity on a refusal is a
  useful conformance test, *"but a poor primary teaching experience"*). hw1's `consume.py` printing
  `— None` for a gate refusal's key is corrected in the same pass (`deferred-items.md` item 3).
- **D-06: `hw1-harness-clients` is NOT rewritten.** Its runner already seeds a private deterministic
  scenario (`examples/hw1-harness-clients/runner/drive.py`, `scenario-rows.yaml`). At most, shared
  fixture or prose is aligned if the base hw1 change makes something it says inaccurate. *"Do not
  touch the three client programs merely for symmetry."*

### Pages, transcripts, specs
- **D-07a: regenerate transcripts and pages.** `page/run-transcript.txt` is evidence of what the
  example does NOW; where the refusal surface changed, re-run, re-pin, republish the page (the
  published artifacts are updated in place at their existing URLs; `context-product-doc-pages-are-artifacts`
  in memory names cp-00 and cp-01's). README and `summary_explanations.md` speak in the PRESENT
  TENSE about the current SDK: *"there is no member for it"* must not remain as current prose when
  `ProductRequestViolationReason` carries `not-supported-at-tier` and the SDK exports
  `AnchorAmbiguityRefusal`.
- **D-07b: CP-SPEC findings are HISTORY — preserved, then closed by appended note.** *"Do not rewrite
  a measured historical finding as though it never happened."* Each §F.4 finding closed by 24.5 gets a
  dated `CLOSED` / `SUPERSEDED` note stating what the SDK lacked when measured, which 24.5 ledger id
  closed it, and the current mechanism; the finding's status is updated, the original observation
  preserved (the cp-04 discipline of preserved superseded readings). **Exception:** a NORMATIVE
  statement about what the product should do — not a historical finding about the SDK — is updated
  in place.

### The two product rulings
- **D-08 (cp-01 `CPR-G08`): REFUSE.** A principal whose grant matches no entity is refused — never
  `200 + D_c = 1 + fail_closed`. Architectural reason, Dave's words: *"policy exclusion is not
  Context Debt. D_c measures the shortfall between context required for the decision and context the
  fabric could deliver. A principal being unauthorized for the entity is a policy outcome, not
  degraded context."* Encoding it as debt *"risks turning Debt into an entitlement oracle"*. The
  refusal obeys SUPPRESSION SILENCE: unauthorized / not-visible is INDISTINGUISHABLE from unavailable
  at that product boundary (the caller is not told "the entity exists but you cannot see it"). The gate
  statement's "or an explicit debt contribution" limb is retired for this product; the test asserts
  the refusal by name and the indistinguishability (a control: an unauthorized principal and a
  nonexistent subject produce the same refusal shape).
- **D-09 (cp-04 ambiguous anchor): `AnchorAmbiguityRefusal`.** Not 404 (*"says nothing resolved,
  which is false"*); not serve-with-a-finding (*"contradicts the E-dimension invariant"* — whitepaper:
  when the anchor is ambiguous, everything attached to it becomes unreliable). Ambiguity fails closed
  as TYPED AMBIGUITY DATA through the D-60 channel. The SDK kind already exists
  (`src/ccf/products/request.py::AnchorAmbiguityRefusal`, `24.5-L-16`); cp-04 mints it where its
  anchor resolves to more than one entity (the shared-LEI case, `24.4` deferred 14 / `D-IMPL-234` (d)).
  *"Debt must not become a substitute vocabulary for policy refusal, and ambiguity in E must not be
  allowed downstream as merely another finding."*
