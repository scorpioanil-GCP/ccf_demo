## 3. The rulings (2026-09-06 11:29 MST)

> Feel free to offer your opinion where you have a different recommendation. Want to ensure we get things right this time. My rulings are:
>
> **Q1: b.** A dangling endpoint is an **unresolved reference**: legal persisted graph state, but not a traversal member until an entity claim exists for it. That preserves the existing first-class-edge model without pretending that an edge assertion creates an entity assertion.
>
> **Q2: a.** Traversal membership requires an entity claim. An edge establishes a relationship assertion; it does **not** establish the existence/type of an entity for traversal purposes.
>
> This gives us a useful invariant:
>
> > **Edges may reference unresolved entities, but traversal operates over claimed entities.**
>
> **Q3: not admitted; no placeholder.** I agree with Claude's recommendation. Creating a synthetic entity record would manufacture context the source never asserted. That would be worse than the current divergence.
>
> **Q4: a, with a carry.** Exclusion is a **traversal semantic**, not an invariant failure. A path through a claim-less endpoint does not exist for traversal, so the walk proceeds as though that endpoint cannot be crossed.
>
> However, Claude is right that the existence of unresolved references may eventually be useful completeness evidence. Record that as a **separate observability carry**, not part of G-28 and not a requirement for 24.8. I do not want fixing traversal equivalence to grow into product findings/debt design.
>
> So:
>
> > **Traversal silently excludes the unresolved endpoint from path formation. Whether the existence/count of excluded unresolved references should later become execution/completeness evidence is explicitly deferred.**
>
> **Q5: b, with an important definition.** Require **byte-identical canonical traversal results**, not raw implementation/internal bytes.
>
> The semantic result must first be identical—same admitted entities, same admitted edges, same depth assignments/path consequences—and then the normal canonical ordering/rendering must produce identical bytes. We should not require two implementations to have identical internal collections, query plans, or backend response ordering.
>
> The invariant is:
>
> > **Equivalent traversal questions over equivalent pinned state must yield the same canonical traversal result regardless of execution path.**
>
> That is stronger and more useful than "same set," because ordering drift can still poison replay/content addressing.
>
> **Q6: a.** One rule. A claim-less URI is neither a valid walk start nor an intermediate hop. There should not be one ontology of "entity" for anchors and another for neighbors.
>
> **Q7: a.** An excluded endpoint consumes no depth and participates in no path or cycle. Depth counts **admitted traversal hops**, not persisted edge hops through entities that do not exist in the traversal universe.
>
> This is important. Otherwise two implementations could agree on the final entity set yet assign different depths because one secretly walked through an unresolved reference.
>
> **Q8: a.** Generic traversal-family semantics, not an adapter capability.
>
> G-28 is precisely evidence that we currently have **two meanings of traversal inside the SDK**. A capability flag would institutionalize the divergence instead of fixing it.
>
> The query-tier rule should become the traversal-family rule:
>
> > **Construct the admitted entity universe first; endpoint-close edges against that universe; then walk.**
>
> The in-process operator should conform to that same sequence, and the new differential should compare operator-tier results against the query-tier/reference semantics.
>
> ### Compact record
>
> > **Q1:b**
> > **Q2:a**
> > **Q3:not admitted — no placeholder**
> > **Q4:a — traversal semantic; unresolved-reference observability is a named future carry**
> > **Q5:b — byte-identical canonical result, not identical internal/backend representation**
> > **Q6:a**
> > **Q7:a**
> > **Q8:a**
>
> I would also explicitly record two principles because they are the substance of the ruling:
>
> > **Persisted graph state and traversal membership are not the same universe. An edge may legally name an unresolved endpoint; that does not make the endpoint traversable.**
>
> and
>
> > **Traversal semantics are execution-path invariant. In-process, fallback, and pushed implementations may execute differently, but the same question over the same pinned state must produce the same canonical traversal result.**
>
> This looks like a well-bounded 24.8. The fix should be in traversal semantics and SDK implementation, not in cp-04.
