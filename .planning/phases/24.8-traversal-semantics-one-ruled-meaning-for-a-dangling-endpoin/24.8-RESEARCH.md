#### What a dangling endpoint is
- **D-01 (Q1 b):** an **unresolved reference** — legal persisted graph state (edges are first-class claims, INV-CH7-20; the everything-answer keeps them, `GQ-05`/`GQ-21`), NOT a traversal member until an entity claim exists for it. *"an edge assertion [does not create] an entity assertion."*
- **D-02 (Q2 a):** traversal membership REQUIRES an entity claim. The invariant, his words: *"Edges may reference unresolved entities, but traversal operates over claimed entities."*
- **D-03 (Q3):** NOT admitted; NO placeholder. No synthetic entity record, no provenance-marked stand-in — *"That would be worse than the current divergence."*

#### What exclusion is
- **D-04 (Q4 a, with a carry):** exclusion is a **traversal semantic**, not a finding and not an invariant failure: *"Traversal silently excludes the unresolved endpoint from path formation."* Whether the existence/count of excluded unresolved references later becomes execution/completeness evidence is **explicitly deferred** — carry `24.8-C-01`, not a 24.8 requirement, and *"I do not want fixing traversal equivalence to grow into product findings/debt design."*

#### Equivalence
- **D-05 (Q5 b, defined):** **byte-identical canonical traversal results** — first the semantic result identical (same admitted entities, same admitted edges, same depth assignments/path consequences), then the normal canonical ordering/rendering identical bytes. NOT identical internal collections, query plans, or backend response ordering. The invariant: *"Equivalent traversal questions over equivalent pinned state must yield the same canonical traversal result regardless of execution path."*

#### Anchors, depth, cycles
- **D-06 (Q6 a):** one rule — a claim-less URI is neither a valid walk start nor an intermediate hop; one ontology of "entity" for anchors and neighbors.
- **D-07 (Q7 a):** an excluded endpoint consumes NO depth and participates in NO path or cycle: *"Depth counts admitted traversal hops, not persisted edge hops through entities that do not exist in the traversal universe."* Two implementations agreeing on the entity set but disagreeing on depth is a defect.

#### Where the rule lives
- **D-08 (Q8 a):** generic traversal-family semantics, NOT an adapter capability (*"A capability flag would institutionalize the divergence"*). The query-tier rule becomes the family rule: **construct the admitted entity universe first; endpoint-close edges against that universe; then walk.** The in-process operator conforms to that sequence; the new differential compares operator-tier results against the query-tier/reference semantics.

#### The two principles (Dave, verbatim)
- **P-1:** *"Persisted graph state and traversal membership are not the same universe. An edge may legally name an unresolved endpoint; that does not make the endpoint traversable."*
- **P-2:** *"Traversal semantics are execution-path invariant. In-process, fallback, and pushed implementations may execute differently, but the same question over the same pinned state must produce the same canonical traversal result."*

## Summary

**The divergence, proven.** On the smallest graph that exhibits G-28 — a claimed seed A, an edge A→X where X carries NO entity claim, an edge X→B where B is claimed — the operator tier (`categories.py::_bounded_walk` applied over `reader.as_of(...)`) with `admitted_entity_classes=None` answers `{A, B}` at depth 2 and 3 while `fallback.answer` and every one of the six adapters (sqlite, postgres, neo4j, mongo, fluree, memory) answer `{A}`; at depth 0 and 1 all tiers answer `{A}`. The operator's answer carries B with ZERO edges — `_substitute` prunes the two X-edges after the walk crossed them — so it is a view asserting B is in A's neighborhood with nothing connecting them. Canonical bytes: operator `994d2a1fba…` vs fallback/pushed `208669aec6…` on the divergent rows; identical on every other row. Across 3 graphs × 14 questions × 6 adapters (252 pushed rows), every query-tier answer is byte-identical to `fallback.answer`; the operator tier disagrees on exactly 10 of 42 (graph, question) pairs — every one a `depth ≥ 2`, `admitted=None` row on a path through X (§ Priority 1).

**What is and is not exposed today.** The engine (`src/ccf/projection/engine.py::ProjectionEngine.execute`) issues `reader.query()` per pushable segment and then RE-APPLIES the segment's operators in-process over the query answer (`:664`, `:668`) — an answer that is already endpoint-closed — and every other operator's `_substitute` closes edges before a downstream traversal sees them. So no `src/`, `runtime/` or `examples/` production path reaches `_bounded_walk` with a dangling edge in view: the only callers of `Operator.apply` outside tests are the planner's compose/cache paths driven by the engine (§ Priority 5). The divergence is reachable only by applying a traversal operator directly over a raw `as_of` view (what tests and adopters do) — which is exactly what P-2 forbids being different, and why no frozen example test changes color (§ Priority 5): cp-04's twelve estate-booting traversal tests are already `xfail`-quarantined by 24.7 for a cause upstream of any walk, and its census/cycles modules never call the SDK walk at all.

**The rosters.** Eight walk implementations, each read at HEAD: the operator tier's one function and its two callers close NOTHING before walking; the fallback and the five adapters close against the surviving entity universe before walking, in four different mechanisms (SQL `EXISTS` against a materialized `survivors` CTE; Cypher `IN $survivors` with the walk's `all(n IN nodes(p) …)` path predicate; a `$in` on materialized survivor URIs plus `$graphLookup.restrictSearchWithMatch`; Fluree's prefixed `$admissible` list) — and mongo and fluree DELEGATE the `direction="forward"` question (mongo also the admitted question) to the fallback rather than pushing it (§ Priority 2). No implementation emits per-node depth; the SQL walks compute a `depth` column internally and never return it (§ Priority 3). Both tiers already produce the same TYPE — an ordered `GraphView` — so `canonical_bytes(GraphView)` is the one rendering, with no normalization needed on either side (§ Priority 4). The document's amendments are line-count-neutral edits to the clause body plus an appended `GQ-35` entry, because 392 line-anchored cites hang off the clause headings and `tools/lints/citations.py` checks each one (§ Priority 6). All three candidate mechanisms for `_bounded_walk` are byte-identical to the fallback on 42/42 rows and each restores an idempotence the shipped walk lacks on a dangling graph (§ Priority 7).

**Primary recommendation:** plan the phase as (a) one `_bounded_walk` change chosen from § Candidate approaches, (b) a new corpus strategy for the G-28 shape (the corpus has NONE today — its only dangling case has BOTH endpoints claim-less, so no seed can reach it), (c) a new operator-vs-query differential in the `test_staged_vs_direct.py` shape but with a traversal-first plan over raw views, (d) a line-neutral 1.3.0 amendment to `GQ-10`/`GQ-13`/`GQ-16` with the entry under `GQ-35`, and (e) re-derivation of the three source/document pins that the change moves. No frozen example test is expected to change color; run the legs once at Wave 0 and once at the gate to observe rather than assume that.

## Priority 3 — D-07's measurable form

**No implementation emits per-node depth.** Verified by reading every walk in § Priority 2: the operator tier's `_bounded_walk` returns `(entities, traversable)` with no depth (`categories.py:174-177`); the fallback's `_walk` returns `(kept_entities, kept_edges)` (`fallback.py:279-287`); the answer contract is `GraphView` (`protocols.py::GraphView`, `:214-233` — `tenant_id`, `as_of`, `entities`, `relationships`; no per-record depth field). Internally, the sqlite and postgres recursive CTEs DO compute a depth column — `walk(uri, depth)` with `w.depth + 1` and `WHERE w.depth < ?` (`sqlite.py:557-583`, `postgres.py:557-591`) — but only `uri` is projected into the answer (`IN (SELECT uri FROM walk)`); mongo's `$graphLookup` has a `depthField` option the adapter does not set (`mongo.py:919-936`); neo4j and fluree return `DISTINCT x.entity_uri` (`_WALK_RETURN`, `neo4j.py:474`, `fluree.py:1543`). No test or product surface reads a depth per node (cp-04's `max_depth_applied`/`depth_reached` are request-level echoes in the example's own code, not a per-node value from the SDK).

**The observable:** depth-limited reach sets on a graph where the unresolved endpoint shortens a path — G3-bypass. Under the ruled semantics B's admitted distance from A is 3 (A→C→D→B); through the phantom it would be 2. So the D-07 instrument is: on G3 with `admitted=None`, `depth_limit=2` must answer `{A, C, D}` with edges `{AC, CD}` and `depth_limit=3` must answer `{A, B, C, D}` with `{AC, CD, DB}` — at BOTH tiers, both directions. Measured today: the query tier already does; the operator tier answers `{A, B, C, D}` at depth 2 (`0bf69ce155`), the D-07(b) "counts a hop" behavior Dave rejected. The cycle half (G2) adds no separate observable beyond G1's: a cycle through X is a path through X, and `reached` de-duplicates.

**Why this is sufficient for D-07:** two implementations that agreed on the entity set at depth 3 but disagreed on depth would necessarily disagree on the depth-2 reach set — the depth-limited reach set IS the depth assignment, observed one level at a time. A per-node depth field would be a new contract member (a `GraphView` change with hash consequences under `D-IMPL-243`) and nothing in the rulings asks for it.

## Priority 4 — D-05's rendering

**Both tiers already produce the same type: an ordered `GraphView`.** The query tier freezes every answer through `src/ccf/graph/reader.py::_ordered_view` (`:210-235`; entities by `entity_uri`, relationships by `relationship_key`, stable sort) — for translated answers via `materialize_view` (`:239-286`) and for fallback answers at `BaseGraphReader.query` (`:425-429`); the memory reader does the same (`memory.py:303-352`).
