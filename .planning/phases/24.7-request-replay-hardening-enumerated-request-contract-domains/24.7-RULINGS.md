## 3. The thirteen rulings (16:18 MST, one batch)

> **Q1: a.** `intent` is a top-level request concept, not an ordinary argument. `ProductDiscovery.intents` is the declaration of what the class serves. A duplicate `arguments.properties.intent` is a shadow declaration and should fail contract construction. Leave cp-04 frozen as evidence of the gap.
>
> **Q2: a.** Always advertise the legal set. This is contract truth, not Policy. A caller should be able to know the valid vocabulary before making the request. If someday the existence of an intent itself becomes sensitive, that would require a different discovery model; don't make request validity disclosure-dependent here.
>
> **Q3: a.** Exactly one domain shape: numeric bounds or enumerated values. Non-empty, duplicate-free, and any declared default must be inside the domain. Neither shape is also invalid if `ArgumentDomain` is present.
>
> **Q4: a.** Exact canonical match. No trimming, case folding, aliases, or silent substitution. Canonicalization, if ever wanted, should be an explicit mechanism upstream of domain validation.
>
> **Q5: a.** New `not-in-domain` reason. Wrong type and valid type/wrong value are materially different failures. The presented value can be named; disclosure controls whether the allowed set is exposed.
>
> **Q6: a.** Any supported primitive type, with homogeneous members matching the declared property type. Don't unnecessarily make this string-specific.
>
> **Q7: a.** Resolution participated whenever the resolution step actually ran. If it refuses halfway through, that partial work is still governed truth and belongs in replay. "It failed before producing an effective request" must not erase what resolution already established.
>
> **Q8: a.** Return the refusal paired with the partial resolution. Keep refusal vocabulary separate from resolution provenance rather than cloning resolution fields into multiple refusal classes. I would think of this as a common resolution outcome shape: completed request or governed refusal, both with the resolution evidence accumulated so far.
>
> **Q9: a.** Legitimate non-applicability. A path that never invokes resolution should say so explicitly. Do not redefine all direct validators as defective merely because the newer resolver exists. The frozen rungs are specimens of that earlier path.
>
> **Q10: a.** Make the builder require an explicit choice: effective/partial resolution, or a typed not-applicable marker with a reason. No implicit omission for new records. Keep the historical sentinel readable and hash-stable for old records.
>
> **Q11: a.** Enforce at construction **and** verify at replay. Construction prevents new incomplete records. Replay verification protects against a false `not-applicable` claim. The verification must use the **pinned historical contract/constraint state**, not today's configuration.
>
> **Q12: a.** Preserve old records exactly. The new invariant applies prospectively. Do not retroactively declare previously valid replay artifacts defective because the SDK acquired a stronger contract.
>
> **Q13: a.** Accept the reds. Under Q10, explicitness is the invariant; inferring non-applicability from missing arguments would reopen the ambiguity we are trying to close. cp-00–cp-03 therefore become quarantined evidence if their existing calls fail under the new builder. Do not edit them.
>
> The compact answer for the record is:
>
> > Q1:a Q2:a Q3:a Q4:a Q5:a Q6:a Q7:a Q8:a Q9:a Q10:a Q11:a Q12:a Q13:a

## 4. The two architectural principles (same message)

> There are two architectural ideas I would make explicit in the ruling because they connect the two gaps.
>
> First, **declaration and advertisement are different responsibilities**:
>
> > The request contract is the authority for legal values; schemas and discovery advertise that authority but never independently define it.
>
> Second, **absence and omission are different things in replay**:
>
> > `not applicable` is an explicit governed fact with a reason. Missing resolution information is an internal integrity failure.
>
> That second sentence is really the essence of G-33. It prevents us from ever again treating "the caller didn't provide the replay input" as equivalent to "resolution did not participate."

## 6. Rulings on the research's stop-and-return findings (17:44 MST, after `24.7-RESEARCH.md` at `b0150cf9`)

> **F-1: a.** The default not-discoverable state means **"no discovery declaration exists," not "this class serves zero intents."** If a class explicitly declares discovery, then its intent set is authoritative and judged strictly. An explicitly declared empty set means "serves none." That preserves backward compatibility without destroying the ability to express an intentionally closed class.
>
> I would sharpen the invariant:
>
> > **Absence of a discovery declaration is non-applicability. Presence of a discovery declaration makes its intent set authoritative, including an explicitly empty set.**
>
> That also fits the distinction we just established for replay: **absence is not the same thing as omission or an empty declaration.**
>
> **F-2: accept and quarantine.** The four frozen rungs remain frozen. If D-01 now proves that their `arguments.properties.intent` declarations are shadows of the top-level field, their construction failures are **specimen evidence**, not an instruction to repair the examples.
>
> So yes:
>
> > cp-01 through cp-04 may go red for this reason and those tests are quarantined under D-IMPL-261 with their assertions unchanged.
>
> Do not rewrite those contracts during 24.7.
>
> **F-3: a.** The recorder must require the explicit resolution input too.
>
> If the builder is fail-closed but the recorder still accepts `resolution=None`, then the API permits exactly the omission we are trying to prohibit and merely delays the failure by one call frame. Worse, having the recorder infer non-applicability would contradict Q10/Q13.
>
> So the explicitness invariant applies across the seam:
>
> > **Any API that constructs or delegates construction of a replay record must require an explicit resolution state: effective/partial resolution or explicit not-applicable marker. No intermediate layer may manufacture the marker from omission.**
>
> The shipped Protocol change is justified. Frozen cp-04 red is evidence.
>
> **F-5: d — and this amends the practical scope of my earlier Q2 ruling.**
>
> Research found something we did not know at the design sitting: **there is no existing product-contract advertisement surface.** "Always advertise it" sounded like a render enhancement; in the actual tree it requires inventing or choosing a new Experience Layer API.
>
> I do **not** want 24.7 to turn into another broad delivery/experience phase.
>
> So:
>
> > Build the canonical contract-to-schema render in the SDK and prove that an enumerated `ArgumentDomain` renders the corresponding enum. Do not create a new MCP or HTTP publication surface in 24.7. Publication of that schema onto an externally discoverable Experience Layer surface is explicitly deferred.
>
> This means I am refining D-02 based on the measured tree:
>
> > **The legal set is intrinsically advertisable contract truth and must have a canonical SDK rendering. 24.7 does not invent the Experience Layer surface on which that rendering is published.**
>
> That is not "enforce only, never advertise" in the architectural sense. It separates **representation** from **delivery**, because we discovered delivery does not currently exist.
>
> I would create a named carry row for the unresolved external-surface question so we do not forget it. But do not scope MCP/HTTP surface design into 24.7.
>
> On the paired outcome shape consequence: **accept the frozen cp-04 red and quarantine it.** Do not distort the new SDK return type to preserve an old example `isinstance` check. That is exactly what D-IMPL-261 was written to prevent.
>
> ### Compact record
>
> > **F-1: a** — absent discovery declaration means intent unjudged; an explicit declaration is authoritative; explicitly empty means serves none.
> > **F-2: accept/quarantine** — cp-01 through cp-04 remain frozen; no contract repairs.
> > **F-3: a** — recorder also requires explicit resolution state; no inference from omission.
> > **F-5: d** — build canonical SDK render, defer publication surface to a later Experience Layer decision. This refines D-02 based on the measured absence of any current product-contract surface.
> > **Paired outcome shape:** frozen cp-04 reds are quarantined evidence, not compatibility requirements.
>
> With those amendments, I would allow the criteria to be authored and brought back for lock. I would **not** do another design expansion unless criteria research uncovers another genuine architectural ambiguity.

## 10. The `archive/examples/` ruling — `D-IMPL-265` (2026-09-06 06:27 MST, after waves 1–6 at `3fba984e`)

The question put to Dave (the wave-4 and wave-6 STATE heads): 12 `build_replay_record` calls under `archive/examples/` omit the now-required `resolution=`; 184 ids in twelve `tests/examples/` modules plus `tests/perf_smoke::test_suite_runs_untimed[crossproc]` red, none red at the phase base; no ruling named `archive/` on either side of the `D-IMPL-263` freeze. Two options were offered (quarantine ~184 ids; or re-derive the 12 sites, recommended on size). His ruling, verbatim:

> That changes my ruling.
>
> Given that history, archive/examples/ should not be treated as SDK compatibility scaffolding. Those examples were deliberately retired because they embodied a usage model you no longer want developers to follow. Keeping them green against the evolving SDK creates exactly the wrong incentive: we spend effort preserving code whose interaction model is intentionally obsolete.
>
> The important distinction is:
>
> HW/CP examples are the supported usage model. archive/examples/ is historical evidence, not a compatibility target.
>
> So I would revise D-IMPL-265 to Option 1 in spirit, but with a stronger disposition than ordinary quarantine:
>
> * Do not modify the 12 archived builder calls.
> * Do not modernize the archived examples to the new explicit replay API.
> * Preserve them as historical/reference material because some SDK-interaction ideas may still be useful.
> * Their 184 test failures should not be treated as regressions in the supported SDK surface.
> * Prefer removing those archived tests from the release-gating denominator, or marking them explicitly as archived/non-gating, rather than maintaining ~184 ordinary xfails forever.
>
> I would not classify them under the same D-IMPL-261 freeze as cp-00–cp-04 either. Those CP/HW examples are active diagnostic specimens. The archive is different: it is retired design history.
>
> So I would establish three categories explicitly:
>
> | Surface | Role | Expected maintenance |
> | --- | --- | --- |
> | examples/hw-*, examples/cp-* | Supported examples / SDK probes | Frozen when probing; rerun after SDK changes |
> | archive/examples/* | Retired usage-model history | No compatibility maintenance |
> | SDK unit/integration tests | SDK contract | Must stay current |
>
> The clean long-term fix is probably to make the test harness reflect that distinction. If archive/examples/ is currently part of the normal 6,000+ test gate, that is itself a repository-organization problem. A retired example should not be able to block release of an SDK whose supported interaction model deliberately replaced it.
>
> I would therefore amend the ruling to:
>
> D-IMPL-265 — archive/examples/ contains retired examples whose usage model is not supported guidance. They are preserved for historical/technical reference but are not compatibility consumers of the current SDK. No archived source is modified to accommodate 24.7. Tests whose only purpose is exercising those retired examples are removed from the release-gating denominator or explicitly marked archived/non-gating. HW/CP examples remain the supported example and diagnostic surfaces.
>
> And I would make one caution: do not delete the archive yet. There may still be SDK techniques worth mining from it, as you said. Just stop treating it as something the current SDK owes compatibility to.
>
> This is actually an important clarification for the whole project: the SDK should be shaped by the HW/CP usage model you intend developers to adopt, not by historical examples you already rejected.
