#### The two principles (Dave, verbatim)
- **P-1 — Declaration and advertisement are different responsibilities.** *"The request contract is
  the authority for legal values; schemas and discovery advertise that authority but never
  independently define it."*
- **P-2 — Absence and omission are different things in replay.** *"`not applicable` is an explicit
  governed fact with a reason. Missing resolution information is an internal integrity failure."*
  *"It prevents us from ever again treating 'the caller didn't provide the replay input' as
  equivalent to 'resolution did not participate.'"*

#### A. Where an enumerated domain lives (G-26)
- **D-00: One declaration of record.** `ArgumentDomain` (on `ProductRequestContract.argument_domains`)
  is where a closed set of legal values is declared. The argument-schema render
  (`src/ccf/skills/catalog.py::SkillArgumentSchema` → MCP `inputSchema`) DERIVES `enum` from it; there
  is no second declaration and the two can never disagree (P-1). Wizard answer: *"Both, one
  declaration of record."*
- **D-01: `intent` is judged against `ProductDiscovery.intents`.** *"`intent` is a top-level request
  concept, not an ordinary argument. `ProductDiscovery.intents` is the declaration of what the class
  serves."* A request naming an intent the class is not registered to serve is a request-validity
  refusal (returned as data). *"A duplicate `arguments.properties.intent` is a shadow declaration and
  should fail contract construction."* cp-04's declaration of `intent` under `arguments.properties`
  (`examples/cp-04-corporate-family-tree/ccf_config.yaml`) stays frozen *"as evidence of the gap"*.
- **D-02: The legal set is ALWAYS advertised.** *"This is contract truth, not Policy. A caller should
  be able to know the valid vocabulary before making the request."* Request validity is NOT
  disclosure-dependent: *"If someday the existence of an intent itself becomes sensitive, that would
  require a different discovery model."*

#### B. Domain semantics and refusal vocabulary (G-26)
- **D-03: Exactly one domain shape.** Numeric bounds OR enumerated values; both is invalid; neither
  is invalid *"if `ArgumentDomain` is present"*. The set is non-empty and duplicate-free. *"Any
  declared default must be inside the domain"* — extends the existing validator
  `ProductRequestContract._every_domain_bounds_a_declared_number_the_default_respects` to membership.
- **D-04: Exact canonical match.** *"No trimming, case folding, aliases, or silent substitution.
  Canonicalization, if ever wanted, should be an explicit mechanism upstream of domain validation."*
- **D-05: One new `ProductRequestViolationReason`: `not-in-domain`.** *"Wrong type and valid
  type/wrong value are materially different failures. The presented value can be named; disclosure
  controls whether the allowed set is exposed."* (Advertisement of the set in discovery is D-02 and
  unconditional; exposure of the set inside a refusal shell follows the disclosure level — the two
  are different channels.)
- **D-06: Any supported primitive type**, *"with homogeneous members matching the declared property
  type. Don't unnecessarily make this string-specific."* `JsonSchemaType` is the closed vocabulary
  (`catalog.py:98`).

#### C. What "participated" means (G-33)
- **D-07: Resolution participated whenever the resolution step actually ran**, whatever its
  outcome. *"If it refuses halfway through, that partial work is still governed truth and belongs in
  replay. 'It failed before producing an effective request' must not erase what resolution already
  established."* The live SDK case: `src/ccf/products/resolver.py:1299-1308` records a
  `ConstraintRefusal` / `PolicyResolutionConflict` / `ProductRequestViolation` returned by
  `resolve_effective_request` with NO resolution although defaults and constraints were resolved
  first. That is the omission this phase closes inside the SDK.
- **D-08: The refusal is returned PAIRED with the partial resolution.** *"Keep refusal vocabulary
  separate from resolution provenance rather than cloning resolution fields into multiple refusal
  classes. I would think of this as a common resolution outcome shape: completed request or governed
  refusal, both with the resolution evidence accumulated so far."* `resolve_effective_request`'s
  return type (`EffectiveRequest | ConstraintRefusal | PolicyResolutionConflict |
  ProductRequestViolation`, `constraints.py:697`) is the seam; `RefusalEnvelope.provenance`
  (`refusal.py:532`) and `PolicyBindingsSnapshot.request_resolution` both carry the partial record.
- **D-09: A path that never invokes resolution is LEGITIMATE non-applicability, stated
  explicitly.** *"Do not redefine all direct validators as defective merely because the newer
  resolver exists. The frozen rungs are specimens of that earlier path."* Direct callers of
  `refuse_request` today: `src/ccf/agents/assembler.py:507` and the frozen examples (cp-00, cp-01,
  cp-02, cp-03, s1-00, s1-01, cp-04).

#### D. Where fail-closed binds, and non-applicability (G-33)
- **D-10: The builder requires an explicit choice.** *"effective/partial resolution, or a typed
  not-applicable marker with a reason. No implicit omission for new records. Keep the historical

  being acceptable; `None` is refused. The legacy value `no-request-resolution` remains readable and
