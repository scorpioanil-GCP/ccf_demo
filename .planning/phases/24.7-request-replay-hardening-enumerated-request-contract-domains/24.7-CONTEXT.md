## Phase Boundary

Two SDK surfaces, nothing else:

1. **G-26 — the request contract can declare the legal values of a parameter.** Today
   `src/ccf/products/request.py::ArgumentDomain` states numeric bounds only. After this phase it
   states numeric bounds OR a closed set of values, the schema render derives the advertised `enum`
   from it, and the top-level request field `intent` is judged against `ProductDiscovery.intents`.
2. **G-33 — Decision Replay carries effective-request resolution whenever resolution occurred, and
   says so explicitly when it did not.** Today `src/ccf/replay/record.py::build_replay_record`
   accepts `resolution=None` and writes the sentinel `no-request-resolution`; the replay engine reads
   it nowhere; the SDK's own resolver records mid-resolution refusals with no resolution.

**Fence (`D-IMPL-263`).** `src/` and `runtime/` OPEN. `examples/` CLOSED — every rung frozen
(`D-IMPL-261`); cp-04 in particular is neither edited, rerun, re-pinned nor republished.
`tests/examples/` may be touched ONLY to quarantine or mark expected-failure an existing example
test the SDK work turns red; never its assertion, expected value, fixture, data or semantics; the
quarantine names the causing gap/decision and is removed, the test rerun unchanged, when the gap
closes. Dave, verbatim: *"cp-04 remains frozen throughout 24.7 and 24.8. These phases repair SDK
surfaces identified by the cp-04 probe; they do not repair, republish, re-pin, or otherwise modify
cp-04. After the applicable SDK work lands, cp-04 may be rerun as validation evidence. Any red
produced by the frozen example is evidence to classify, not an instruction to edit the example."*

**Not in this phase.** G-28 (traversal; 24.8). Any generic validation language on the request
contract. Any change to the four ESTATE-LIMITATION ledger rows. A whitepaper edit.

## Implementation Decisions

All thirteen ruled by Dave at this sitting, 2026-09-05 16:18 MST, recorded at `docs/DECISIONS.md`
`D-IMPL-264` and VERBATIM in `24.7-RULINGS.md` (D-NN here = Q-NN there; the verbatim file governs).
Every option considered is in `24.7-DISCUSSION-LOG.md`. Two principles (P-1, P-2) are his framing
of why the two gaps belong together; they bind every decision below.

### The two principles (Dave, verbatim)
- **P-1 — Declaration and advertisement are different responsibilities.** *"The request contract is
  the authority for legal values; schemas and discovery advertise that authority but never
  independently define it."*
- **P-2 — Absence and omission are different things in replay.** *"`not applicable` is an explicit
  governed fact with a reason. Missing resolution information is an internal integrity failure."*
  *"It prevents us from ever again treating 'the caller didn't provide the replay input' as
  equivalent to 'resolution did not participate.'"*

### A. Where an enumerated domain lives (G-26)
- **D-00: One declaration of record.** `ArgumentDomain` (on `ProductRequestContract.argument_domains`)
  is where a closed set of legal values is declared. The argument-schema render
  (`src/ccf/skills/catalog.py::SkillArgumentSchema` → MCP `inputSchema`) DERIVES `enum` from it; there
  is no second declaration and the two can never disagree (P-1). Wizard answer: *"Both, one
  declaration of record."*
- **D-01: `intent` is judged against `ProductDiscovery.intents`.** *"`intent` is a top-level request
  concept, not an ordinary argument. `ProductDiscovery.intents` is the declaration of what the class
  serves."* A request naming an intent the class is not registered to serve is a request-validity
  refusal (returned as data). *"A duplicate `arguments.properties.intent` is a shadow declaration and
  should fail contract construction."* cp-04's declaration of `intent` under `arguments.properties`
  (`examples/cp-04-corporate-family-tree/ccf_config.yaml`) stays frozen *"as evidence of the gap"*.
- **D-02: The legal set is ALWAYS advertised.** *"This is contract truth, not Policy. A caller should
  be able to know the valid vocabulary before making the request."* Request validity is NOT
  disclosure-dependent: *"If someday the existence of an intent itself becomes sensitive, that would
  require a different discovery model."*

### B. Domain semantics and refusal vocabulary (G-26)
- **D-03: Exactly one domain shape.** Numeric bounds OR enumerated values; both is invalid; neither
  is invalid *"if `ArgumentDomain` is present"*. The set is non-empty and duplicate-free. *"Any
  declared default must be inside the domain"* — extends the existing validator
  `ProductRequestContract._every_domain_bounds_a_declared_number_the_default_respects` to membership.
- **D-04: Exact canonical match.** *"No trimming, case folding, aliases, or silent substitution.
  Canonicalization, if ever wanted, should be an explicit mechanism upstream of domain validation."*
- **D-05: One new `ProductRequestViolationReason`: `not-in-domain`.** *"Wrong type and valid
  type/wrong value are materially different failures. The presented value can be named; disclosure
  controls whether the allowed set is exposed."* (Advertisement of the set in discovery is D-02 and
  unconditional; exposure of the set inside a refusal shell follows the disclosure level — the two
  are different channels.)
- **D-06: Any supported primitive type**, *"with homogeneous members matching the declared property
  type. Don't unnecessarily make this string-specific."* `JsonSchemaType` is the closed vocabulary
  (`catalog.py:98`).

### C. What "participated" means (G-33)
- **D-07: Resolution participated whenever the resolution step actually ran**, whatever its
  outcome. *"If it refuses halfway through, that partial work is still governed truth and belongs in
  replay. 'It failed before producing an effective request' must not erase what resolution already
  established."* The live SDK case: `src/ccf/products/resolver.py:1299-1308` records a
  `ConstraintRefusal` / `PolicyResolutionConflict` / `ProductRequestViolation` returned by
  `resolve_effective_request` with NO resolution although defaults and constraints were resolved
  first. That is the omission this phase closes inside the SDK.
- **D-08: The refusal is returned PAIRED with the partial resolution.** *"Keep refusal vocabulary
  separate from resolution provenance rather than cloning resolution fields into multiple refusal
  classes. I would think of this as a common resolution outcome shape: completed request or governed
  refusal, both with the resolution evidence accumulated so far."* `resolve_effective_request`'s
  return type (`EffectiveRequest | ConstraintRefusal | PolicyResolutionConflict |
  ProductRequestViolation`, `constraints.py:697`) is the seam; `RefusalEnvelope.provenance`
  (`refusal.py:532`) and `PolicyBindingsSnapshot.request_resolution` both carry the partial record.
- **D-09: A path that never invokes resolution is LEGITIMATE non-applicability, stated
  explicitly.** *"Do not redefine all direct validators as defective merely because the newer
  resolver exists. The frozen rungs are specimens of that earlier path."* Direct callers of
  `refuse_request` today: `src/ccf/agents/assembler.py:507` and the frozen examples (cp-00, cp-01,
  cp-02, cp-03, s1-00, s1-01, cp-04).

### D. Where fail-closed binds, and non-applicability (G-33)
- **D-10: The builder requires an explicit choice.** *"effective/partial resolution, or a typed
  not-applicable marker with a reason. No implicit omission for new records. Keep the historical
  sentinel readable and hash-stable for old records."* `build_replay_record(resolution=None)` stops
  being acceptable; `None` is refused. The legacy value `no-request-resolution` remains readable and
  hash-transparent (`D-IMPL-243`) so every record written before keeps its content address.
- **D-11: Enforce at construction AND verify at replay.** *"Construction prevents new incomplete
  records. Replay verification protects against a false `not-applicable` claim. The verification must
  use the pinned historical contract/constraint state, not today's configuration."* Today
  `src/ccf/replay/engine.py::replay` (:528) reads `request_resolution` nowhere. A construction-time
  omission is an internal integrity failure (P-2) and raises, under 24.6 D-15's rule (a failed
  invariant is a fabric failure, not a governed determination).
- **D-12: Old records are preserved exactly.** *"The new invariant applies prospectively. Do not
  retroactively declare previously valid replay artifacts defective because the SDK acquired a
  stronger contract."*
- **D-13: The frozen rungs' reds are ACCEPTED.** *"Under Q10, explicitness is the invariant;
  inferring non-applicability from missing arguments would reopen the ambiguity we are trying to
  close. cp-00–cp-03 therefore become quarantined evidence if their existing calls fail under the new
  builder. Do not edit them."* Builder call sites that pass no resolution today: cp-00, cp-01, cp-02,
  cp-03 `produce.py`, s1-00 `produce.py`, s1-01 `spine.py` (measured: 10 sites, 3 pass `resolution=`).
  Each red is a `tests/examples/` quarantine under the `D-IMPL-263` rule, naming `D-IMPL-264` D-10/D-13.

### Reusable Assets
- `ArgumentDomain` already has the construction-refusal pattern (neither end / inverted) and a
  `refuses(value) -> reason | None` method; the enumerated shape extends the same type and the same
  `_refuse_domain` step (D-00, D-03, D-05).

  (`_every_domain_bounds_a_declared_number_the_default_respects`); membership is the same rule.
- `EffectiveRequest` and `RefusalEnvelope.provenance` already carry a resolution; the paired
  outcome (D-08) reuses `EffectiveRequest` for the partial record rather than a new provenance type.
- `NO_REQUEST_RESOLUTION` is hash-transparent (`D-IMPL-243`) — the legacy compatibility D-12 needs
  is already the field's discipline; only the *default* changes (D-10).
- The 24.6 test-writing pattern: sabotage controls per invariant (delete the declaration → red;
  remove the step → red), `tests/products/test_request_contract.py` (88 tests),
  `test_policy_constraints.py` (33), `test_policy_constraint_resolver.py` (19),
  `tests/replay/test_refusal_replay_record.py`, `test_dimension_extensions.py`.

### Established Patterns
- Refusals are data (`D-IMPL-251`); a refused request-validity verdict is a `ProductRequestViolation`
  returned, never raised; a failed internal invariant raises (24.6 D-15). D-11's construction-time
  omission is the second kind.
- Reasons are closed `Literal` vocabularies with a translation table from the payload surface
  (`_REASONS`); `not-in-domain` joins `ProductRequestViolationReason` (D-05).
- Provenance is never collapsed (24.6 D-01); the partial resolution carries the authorities it
  established, not a summary.
- One canonical-bytes render per value (24.6-03): the resolution lands as bytes rendered from the
  VALUE in the builder, never a pre-serialized block — the not-applicable marker renders the same way.
- Every governed determination reaches the replay writer before release (24.6 D-37); the builder
  change (D-10) sits inside that sequence, so a mis-built record is a fabric failure at the door.

### Integration Points
- `refuse_request` step order (address → tier → payload → tolerance → domain): the intent check
  (D-01) is presumed beside address/tier; the enumerated check is the existing domain step.
- `SkillArgumentSchema.render` → MCP `inputSchema`: the derived `enum` (D-00/D-02) appears here and
  in whatever discovery surface publishes the contract.
- `resolve_effective_request` return union → the governed resolver's `isinstance` branch
  (`resolver.py:1299`) → `_record_refusal` → `refusal_recorder.record(... resolution=...)`: the pairing
  (D-08) threads through all four.
- `build_replay_record(resolution=...)` → `PolicyBindingsSnapshot.request_resolution`: the explicit
  input (D-10) and its render.
- `engine.replay()` / `_resolve_bindings`: the replay-time verification (D-11) against the pinned
  request-contract artifact, pinned constraint bindings and pinned class declaration.
