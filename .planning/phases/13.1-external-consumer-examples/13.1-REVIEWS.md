# Cross-AI Plan Review — Phase 13.1

## Gemini Review

This review covers the four implementation plans for **Phase 13.1: External-Consumer Examples (MCP Egress)**. These plans demonstrate the "black box" consumption of CCF context products by external agents (Anthropic SDK, Google ADK, etc.) with zero client-side library dependencies.

### 1. Summary
The Phase 13.1 implementation plans provide a comprehensive and rigorous demonstration of CCF's "black box" adoption path via MCP. By implementing four distinct client legs (Bare MCP, Anthropic SDK, Google ADK, and a docs-only Claude Code registration) with zero CCF library dependencies, the phase successfully validates the project's core "harness neutrality" mandate. The use of transport-level replay for CI determinism and the inclusion of lineage/replay retrieval over the MCP surface ensure that the examples are not just functional, but also provide the full auditability story required by governed domains.

### 2. Strengths
*   **Harness Neutrality Proof:** The "zero-CCF-imports" rule for client legs (enforced by static analysis in `run.py`) provides an empirical proof of the SDK's portability and ease of adoption.
*   **Determinism via Replay Server:** The `replay_server.py` component allows for fully offline, deterministic CI runs of LLM-based agents, solving a common flakiness problem in AI testing while preserving "live mode" for manual verification.
*   **Auditability Egress:** Extending the Experience Layer MCP surface deployment-side to expose `get_lineage` and `get_replay_record` (D-15) demonstrates how external consumers can participate in the CCF trust model without direct fabric access.
*   **Deployment-Side Extension Pattern:** Using FastMCP decorators to add tools in `serve.py` instead of modifying the core runtime (Pattern 1) preserves architectural role separation while meeting specific example requirements.
*   **Multi-Leg Coverage:** Covering three different programmatic harnesses plus a popular CLI (Claude Code) registration snippet ensures broad appeal to various engineering personas.

### 3. Concerns
*   **Port 0 Synchronization (MEDIUM):** While the `READY <port>` handshake is a proven pattern in this repo, it relies on standard output redirection and parsing which can occasionally be brittle across different shell environments or OS versions.
*   **Fixture Maintenance Overhead (LOW):** The requirement for "reviewed event" fixture regeneration (D-10) is excellent for security but adds friction to artifact updates. This is a trade-off for determinism, but worth noting as a potential point of "adopter friction" if they follow this pattern.
*   **Agent Tool Noise (LOW):** The Experience server advertises agent-invocation tools by default. For a pure "Context Product" consumer, these might appear as "noise" in `list_tools`, though the bare client was updated to handle this by only calling satisfiable tools.
*   **Anthropic Extra Dependency (LOW):** Adding `anthropic` as a project extra is the correct technical choice, but documentation must be very clear that this is only for the example and not a core CCF dependency.

### 4. Suggestions
*   **Core Tool Elevation:** Consider whether `get_context`, `get_lineage`, and `get_replay_record` should eventually be promoted from "deployment-side extensions" to core features of `ccf_runtime.mcp.experience` if they prove universally useful for external consumers.
*   **Grep Robustness:** In `run.py`, ensure the static grep for `ccf` imports is scoped specifically to the import section to avoid false positives (e.g., if a developer mentions "ccf" in a comment or a log message).
*   **Ready Handshake Timeout:** Ensure `run.py` has a clear, localized timeout on the `readline()` call for the `READY` line to avoid hanging the CI runner if a server fails to boot or print its port.

### 5. Risk Assessment
**LOW.** The plans are exceptionally well-grounded in the existing codebase and follow established patterns (from examples 03, 04, and 06). The technical risks associated with LLM nondeterminism and harness coupling are effectively mitigated by the replay-server and static grep assertions. The architecture faithfully realizes the whitepaper's vision of the Experience Layer as a "black box" front door for external agents.

## Plan 13.1-02 Review

### Strengths

- Correctly chooses the authenticated Experience MCP server instead of modifying raw egress.

### Concerns

- **HIGH:** Request capture plus `ReplayWriter` composition may require custom metadata in the replay record. The plan assumes `{client_id, args/URI, timestamp}` can be recorded cleanly without verifying the existing replay schema supports this directly.

- **MEDIUM:** The plan’s acceptance criterion “No changes under runtime/ or src/” may be too strict if execution discovered a real SDK surface gap. If execution changed core code, that should be explicitly justified and tested.
- **LOW:** `min_lines: 200` for `serve.py` encourages size rather than clarity.

### Suggestions

- Re-check that every product-serving path, including concrete resource reads and `get_context`, writes a replay record before returning bytes.
- Confirm the replay record includes request identity and request args/URI in a stable, inspectable field.
- Add or verify a small manifest file written by `serve.py`, for example `runtime_state/served_records.jsonl`, so `run.py` can locate replay refs deterministically.
- Re-check that invalid tenant/entity/resource arguments fail closed and do not serve default context.
- Confirm the replay server never binds beyond `127.0.0.1` and fails loudly on fixture exhaustion.

### Risk Assessment

**MEDIUM-HIGH.** The architecture is right, but this is the densest plan and carries the most integration risk, especially around replay-record semantics and auth context capture.

## Ollama Review (gemma4:cloud)

# Cross-AI Plan Review: Phase 13.1 (External-Consumer Examples)

## Summary
The implementation plan for Phase 13.1 is exceptionally rigorous, demonstrating a deep understanding of the "black-box" requirement for external agent consumption. By utilizing transport-level replay (HTTP base-URL redirection) rather than code-level mocking, the plan ensures that the client legs remain "textbook" examples of their respective harnesses (Anthropic, Google ADK, Bare MCP) with zero CCF leakage. The structural discipline—partitioning by consumption model rather than domain and enforcing strict README templates—maintains the high standard of the existing example suite while extending the SDK's reach to external runtimes.

## Strengths
*   **Strict Harness Neutrality:** The "zero-CCF-import" rule is not just a goal but a CI-enforced invariant (via `run.py` greps), ensuring that the SDK remains a mechanism, not a framework.
*   **Deterministic LLM Testing:** The use of a local `replay_server.py` to serve recorded JSON fixtures allows for 100% deterministic CI runs of complex LLM tool-use loops without relying on flaky or expensive live API calls.
*   **Deployment-Side Composition:** The decision to extend the `Experience` server via decorators in `serve.py` rather than modifying the `runtime/` core prevents "example-driven" drift in the SDK's architectural role separation.
*   **Auditability Proof:** Implementing `get_access_token()` for requester identity and asserting byte-equal reproduction (D-16) via the `ReplayWriter` proves the whitepaper's commitment to decision-ready context and replayability.
*   **Comprehensive Client Lineup:** Covering the spectrum from a bare MCP client to a high-level ADK agent and a docs-only `.mcp.json` configuration provides a complete adoption map for external engineers.

## Concerns
*   **Fixture Fragility (LOW):** Minor changes in LLM SDK versions can sometimes alter the exact request shape (e.g., adding a new field to the Messages API). While the ordinal-per-path routing is simple, it may require occasional fixture regeneration.
*   **Resource Template Visibility (LOW):** As noted in Pitfall 4, some MCP clients struggle to "browse" templated resources. The plan mitigates this by adding concrete resource registrations, which is the correct approach.
*   **Auth-Middleware Complexity (LOW):** The dependency on both `token_verifier` and `auth_settings` being present for the middleware to activate (Pitfall 3) is a subtle failure mode; the plan correctly identifies and encodes this into the `serve.py` task.

## Suggestions
*   **Fixture Diffing Tool:** For future "band" expansions (10-19, 50+), consider a small utility script that compares a "live" recording against the current fixture and highlights JSON diffs to make the "reviewed event" (D-10) easier to audit.
*   **Explicit Base-URL Documentation:** In the `external/README.md`, explicitly highlight the `ANTHROPIC_BASE_URL` and `GOOGLE_GEMINI_BASE_URL` environment variables as the primary mechanism for deterministic testing, as this is a powerful pattern for other teams to adopt.

## Risk Assessment
**Overall Risk: LOW**

**Justification:** The plan is grounded in verified research (verified against installed source code and SDK signatures). It avoids the "temptation" to modify the core SDK for example convenience, instead using deployment-side composition. The security posture is consistent with Phase-10 auth machinery, and the testing strategy (deterministic transport replay) is the gold standard for LLM-integrated software. The execution path is clear, self-contained, and preserves all existing project invariants.
