# Phase 13.1: External-Consumer Examples (MCP Egress) - Context

**Gathered:** 2026-08-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Prove — with runnable examples — that an agent built entirely OUTSIDE CCF
(its own harness, its own loop, zero CCF imports client-side) can consume
decision-ready, typed Context Products by pointing at the CCF MCP egress
server. CCF operates as a black box behind MCP: governed context in
response to a request; lineage and replay available on demand; nothing
required of the client. This demonstrates CLAUDE.md §7.1 (MCP as egress)
and §8.3 (Experience Layer) as the PRIMARY adoption path, rather than
asserting it. Rationale (Dave, 2026-08-02): users must never be forced to
construct agents inside CCF — that becomes tech debt.

Phase scope: the `examples/external/` family charter README plus
`examples/external/00-hello-context` complete with all client legs, CI
green. Deep financial-services examples (10-band) and the
SituationalIntelligence family (50-band) are deferred to later phases.

</domain>

<decisions>
## Implementation Decisions

### Directory structure and family partitioning
- **D-01:** New `examples/external/` family, unified by consumption model
  (external harness → MCP → black-box CCF), NOT by domain. Existing
  examples 00–08 unchanged.
- **D-02:** Domain number-bands inside the family: `00-hello-context` =
  hello world; `10–19` reserved for financial-services depth progression
  (e.g. credit review, covenant monitoring); `50+` reserved for the
  SituationalIntelligence family. New domains slot in without renumbering.
- **D-03:** `external/README.md` is the family charter: defines the
  zero-CCF-imports-client-side rule, client-leg conventions, auth posture,
  and the band map.
- **D-04:** Each example is self-contained (own `artifacts/`, own
  `serve.py` booting fabric + MCP egress server) — no cross-example fabric
  coupling, consistent with the existing suite discipline.

### Client harness lineup (00-hello-context)
- **D-05:** Four client legs, one directory, one shared fabric, one README
  (mirrors example 03's multi-leg pattern):
  1. `client_bare.py` — ~40-line generic `mcp` client, no LLM;
  2. `client_anthropic.py` — pure `anthropic`-SDK agent with its own
     tool-use loop;
  3. `client_adk.py` — Google ADK agent with the CCF MCP server registered
     as an ADK toolset;
  4. Claude Cowork / Claude Code / Claude Desktop — docs-only leg: a
     `.mcp.json` registration snippet in the README for interactive use.
- **D-06:** Client code must read as a textbook example of its harness —
  no CCF imports, no CCF-shaped helpers. The only CCF knowledge a client
  has is an MCP server URL and a bearer token.
- **D-07:** Hello-world domain is financial services (primary initial user
  base), kept deliberately small — one product, one clear decision the
  served context visibly changes.

### CI vs live LLM split
- **D-08:** ALL legs are CI-mandatory and deterministic — including the
  Anthropic and ADK legs.
- **D-09:** Determinism via transport-level replay: client code stays a
  pure harness agent; CI redirects the model API base URL (env var only,
  zero code branches in client legs) to a small local replay server
  serving recorded API responses. Live mode = unset the env var and
  provide real keys; same client code runs unmodified.
- **D-10:** Recorded responses are versioned fixtures; regeneration is a
  reviewed event with a documented command (carries Phase-13 D-09/D-10
  expected-output discipline forward).

### MCP surface the client sees
- **D-11:** Both surfaces demonstrated: Context Products listed/readable
  as MCP Resources (whitepaper Pattern 3, browsable from Claude
  Desktop/Cowork) AND a `get_context`-style MCP Tool callable mid-loop
  with an entity/scope argument.
- **D-12:** Bearer-token auth ON from day one, shown in the README;
  clients pass the token via env var. Uses the Phase-10 auth machinery.
  No anonymous mode in this example — financial-services users need the
  real posture from the first touch.

### Fabric-side replay and lineage (black-box audit story)
- **D-13:** The fabric records the inbound request itself — the
  "instructions given to the CCF": tool-call arguments / resource URI,
  requesting identity (from the auth token), timestamp — as part of the
  serve-side record. Zero client-side obligation.
- **D-14:** A replay-ready serve record (snapshot, policy bindings,
  lineage) lands fabric-side for every product served to an external
  client, by construction.
- **D-15:** Lineage and replay are READABLE BY CLIENTS over the same MCP
  surface (read-only resources/tools): an external agent or its operator
  can ask "where did this context come from, can you reproduce it?"
  without touching CCF internals. The example asserts a client leg
  retrieves lineage + the replay record over MCP.
- **D-16:** Byte-equal reproduction is asserted fabric-side (the example
  re-derives the served product from the recorded snapshot/policy
  versions and compares canonical bytes).

### Carried forward from Phase 13
- **D-17:** README follows the Phase-13 D-02 seven-heading template, D-04
  gloss discipline, D-11/D-12 [ADAPT]/[MECHANISM] artifact markers, and
  per-example atomic commits with reviewed expected-output changes.

### Claude's Discretion
- Whether the egress surface is served by the raw L6 egress server or the
  Experience Layer MCP server module (`runtime/ccf_runtime/mcp/
  experience.py` vs `egress.py`) — pick whichever matches §7.1/§8.3 role
  separation most faithfully; document the choice in the README.
- The exact replay-server mechanism for D-09 (recorded HTTP fixtures,
  local proxy, etc.) — constraint: client code purity, full determinism,
  live mode available.
- The specific finserv hello-world scenario (entities, product, decision),
  kept small; fresh artifacts, nothing ported.
- Makefile target naming (`make example-ext-00` or similar) and CI wiring.

</decisions>

## Existing Code Insights

### Reusable Assets
- MCP egress + auth servers already exist and are exercised by example 04
  from a separate OS process — the fabric side of this phase is mostly
  composition, not new mechanism.
- Example 03's multi-leg pattern (deterministic + live legs, conformance
  assertions) is the structural analog for the four client legs.
- Phase-10 token machinery (`tokens.yaml` patterns in examples 05/06)
  covers the bearer-token posture.

### Established Patterns
- Self-contained example directories, artifacts-first, No-Hardcoding CI
  lint, `make example-NN` targets run in `make ci`.
- Expected-output regeneration as a reviewed event.

### Integration Points
- `Makefile` (new example target + ci inclusion), `examples/external/`
  (new tree), possibly a small new read-only MCP tool/resource for
  lineage/replay retrieval if the current egress surface doesn't expose it
  yet (mechanism gap to verify during research).

<specifics>
## Specific Ideas

- "The beauty of CCF is it's a black box to the client caller if I want
  it to operate that way" — the README's framing sentence.
- Users work in Claude Cowork or Google ADK; the example must meet them
  there — the Cowork `.mcp.json` registration is a first-class leg, not a
  footnote.
- Progression story: hello world now → deep financial services (10-band)
  → SituationalIntelligence family (50-band).

</specifics>
