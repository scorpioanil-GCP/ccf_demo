**(a) `ProductRequestContract.from_declared` — and the ruling on why this shape.**

`D-IMPL-126` offers two shapes: a `from_declared` classmethod, **or** teaching the
manifest loader to parse `class_id: *.request-contract` into the typed model.
**Take `from_declared`. Reject the loader shape, and record the rejection in the
method's docstring** so a later reader does not re-propose it:

1. A suffix pattern over `class_id` would have the SDK claim `*.request-contract`
   across **every adopter namespace**. `D-IMPL-84` draws the SDK's ownership line
   at exactly one prefix, `ccf.`, and `classes.py`'s module docstring records that
   the earlier wider reading *"was too wide"*.
2. It is a silent behavioural break with no version lane: a committed manifest
   naming `acme.request-contract` resolves to `DeclaredArtifact` today and would
   resolve to `ProductRequestContract` tomorrow, changing what registers, what
   pins, and what enters replay dimension 2.
3. `resolve_artifact_class` is a total function with three exhaustive branches and
   no pattern matching. A fourth branch keyed on adopter namespace text is the
   shape `CINV-01` exists to keep out of `src/`.

A **third** shape — register `PRODUCT_REQUEST_CONTRACT` in
`SDK_VERSIONED_ARTIFACT_CLASSES` so a manifest can name
`class_id: ccf.product-request-contract` — is also **not taken**, for the reasons
already committed at `request.py:273-287`. Name it in the docstring as available
to a later ruling, not as an oversight.

**Put this rationale in the METHOD docstring, not the module docstring.**
`tools/dump_schemas.py` copies module and class docstrings verbatim into schema
`description` fields; a method docstring is not copied, so no schema regeneration
is owed and `make docs-strict`'s `docs/schemas/` scan root sees no change.

**(b) `ServableProduct` states why it is unconstructible — on BOTH channels.**

Enumerate the pydantic construction spellings **once, exhaustively**, in one
module-level greppable frozenset — the
`tests/invariants/test_no_obligation_vocabulary.py::CONTAINER_FORMS` precedent
from Phase 15.6, where a language's forms were enumerated once rather than
discovered one instance at a time. Include at least `model_construct`,
`model_validate`, `model_validate_json`, `model_validate_strings`, `model_copy`,
`construct`, `parse_obj`, `parse_raw`, `parse_file`, `from_orm`.

**Two channels, because a metaclass covers only one.** Measured at this HEAD by
simulation: a metaclass `__getattr__` makes `ServableProduct.model_construct()`
refuse correctly while `instance.model_copy()` still gives the bare
`AttributeError` the fix exists to remove — and `model_copy`, `model_dump` and
`parse_obj` are *instance* methods in pydantic, which is precisely what a reader
holding a returned object reaches for. So:
  - a metaclass `__getattr__` for the **class** channel, and
  - a `__getattr__` on `ServableProduct` itself for the **instance** channel,
both reading the same frozenset. Any name outside the set falls through to the
default `AttributeError` on both channels — that boundary is the point, and it
must not swallow a genuine typo.

**Price and fix the `hasattr` hazard.** `GateBypassError` subclasses `TypeError`
(`gates.py:124`), so raising it from `__getattr__` makes
`hasattr(ServableProduct, "model_construct")` **raise** instead of returning
`False`, and `getattr(x, "model_copy", None)` raise instead of defaulting.
Nothing in this tree duck-types those names today, so this is an adopter hazard
rather than a present break — but it is a real one, and it is created by this
fix. **Raise a refusal deriving from both `GateBypassError` and `AttributeError`**
(a small named subclass in `gates.py`, exported), so a probe degrades to
`False`/`None` while `except GateBypassError` still catches and the message is
unchanged. This is the one place this plan adds an exception class, and the
reason is written above rather than assumed.

The message says three things in order: this type is deliberately
unconstructible; the only construction path is `ccf.products.gates.run_gates`,
because holding one *is* the evidence the three gates ran; and this is
`INV-CH7-52` (whitepaper §7.6) working, not a pydantic version problem.

`__init__`'s token check is unchanged. Neither `__getattr__` adds a construction
path and no `__call__` is overridden.

**(a) The header, and the ruling on `ETag` versus a CCF-specific name.**

**Take `X-CCF-Content-Address`. Do not use `ETag`, and do not ship both.** Record
the reasoning in `canonical_response`'s docstring:

1. **A CCF content address is an identity, not a cache validator.** It is the
   `D-IMPL-26` primitive the ArtifactStore resolves and replay pins against. RFC
   9110 permits intermediaries to weaken a strong `ETag` to `W/"..."` or rewrite
   it across a content-coding transformation. An identity a proxy may legally
   alter is not an identity.
2. **`ETag` advertises cacheability on an entitlement-scoped body.** These
   responses are per-principal and per-perspective (`entitled_perspective`
   decides before the resolver runs). An `ETag` invites an intermediary to hold
   and re-serve a governed product; an `X-CCF-*` header carries **no** HTTP
   caching semantics and creates no such invitation. That is also why no
   `Cache-Control` change is needed — the hazard is avoided by the header choice
   rather than papered over with a second header.
3. **`ETag` is per-representation; the address is per-object.** The moment this
   door gains content negotiation or compression the two must diverge, and an
   `ETag` set to the content address would be lying.
4. Implementing `ETag` honestly means `If-None-Match` and a 304 path — real
   behaviour on a shipped door, outside what `D-IMPL-126` ruled.
