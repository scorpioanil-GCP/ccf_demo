**(a) `ProductRequestContract.from_declared` — and the ruling on why this shape and not the other two.**

`D-IMPL-126` offers two shapes: a `from_declared` classmethod, **or** teaching the
manifest loader to parse `class_id: *.request-contract` into the typed model.
**Take `from_declared`. Reject the loader shape, and record the rejection in the
method's docstring** so a later reader does not re-propose it:

1. A suffix pattern over `class_id` would have the SDK claim `*.request-contract`
   across **every adopter namespace**. `D-IMPL-84` draws the SDK's ownership line
   at exactly one prefix, `ccf.`, and `classes.py`'s module docstring states that
   the earlier wider reading *"was too wide"*. A suffix rule re-widens it on a
   different axis.
2. It is a silent behavioural break with no version lane: a committed manifest
   whose adopter happens to name a class `acme.request-contract` resolves to
   `DeclaredArtifact` today and would resolve to `ProductRequestContract`
   tomorrow, changing what registers, what pins, and what enters replay
   dimension 2.
3. `resolve_artifact_class` is a total function with three exhaustive branches
   and no pattern matching anywhere in it. A fourth branch keyed on adopter
   namespace text is the shape `CINV-01` exists to keep out of `src/`.

A **third** shape — register `PRODUCT_REQUEST_CONTRACT` in
`SDK_VERSIONED_ARTIFACT_CLASSES` so a manifest can name
`class_id: ccf.product-request-contract` directly — is also **not taken**, and
the reason is already committed at `request.py:273-287`: `SDK_ARTIFACT_CLASSES`
*is* the set the HTTP `GET /schema` route and `ccf schema export` enumerate, so
widening it is an unruled runtime surface change made incidentally; and the
versioned mapping is closed to a contract declaring no `artifact_version`, which
this one does not. Name this third shape in the docstring as available to a later
ruling, not as an oversight.

Add `from_declared` as a `classmethod` on `ProductRequestContract` taking one
positional `DeclaredArtifact`. It reads `artifact.semver` for the document's own
lane and the three keys `schema_name`, `schema_version`, `arguments` off
`artifact.declaration`, validating `arguments` through `ProductPayloadSchema`
(the alias `ccf.products.payload` exports, exactly as `deployment.py:878` does).
Missing keys are refused by name in one message listing all of them, not by the
first `KeyError` — an adopter fixing three keys one exception at a time is the
papercut restated. Reuse `ArtifactLoadError` if its contract fits ("a serialized
artifact cannot be admitted as written"); if it does not, raise `ValueError` in
the `resolve_artifact_class` voice. Do **not** invent a new exception class
without stating why in the docstring.

The docstring cites `D-IMPL-126` as an SDK extension per CLAUDE.md §11 (this
entry, not a whitepaper section), states that the artifact reaches it from a
manifest through the `DeclaredArtifact` envelope, and names the two rejected
shapes above.

**(b) `ServableProduct` states why it is unconstructible.**

The current `AttributeError` is correct and useless. Give `ServableProduct` a
metaclass whose `__getattr__` raises `GateBypassError` for an **enumerated,
module-level, greppable frozenset** of pydantic construction spellings — the
`tests/invariants/test_no_obligation_vocabulary.py::CONTAINER_FORMS` precedent
from Phase 15.6, where a language's forms were enumerated **once, exhaustively**,
in one named constant rather than discovered one instance at a time. Enumerate at
least: `model_construct`, `model_validate`, `model_validate_json`,
`model_validate_strings`, `model_copy`, and the pydantic-v1 spellings a reader
migrating from older code will reach for — `construct`, `parse_obj`, `parse_raw`,
`parse_file`, `from_orm`.

Any name **outside** the set falls through to the default `AttributeError`. That
boundary is the point: the refusal must not swallow a genuine typo into a
governance error.

The message says three things, in this order: this type is deliberately
unconstructible; the only construction path is
`ccf.products.gates.run_gates`, because holding one *is* the evidence the three
validation gates ran; and this is `INV-CH7-52` (whitepaper §7.6) working, not a
pydantic version problem. Use `GateBypassError` — the type `__init__` already
raises — so a deployment catching one catches both.

`__init__`'s existing token check is unchanged. The metaclass adds no `__call__`
override and no construction path.

Update `src/ccf/products/gates.py`'s `ServableProduct` docstring to say the type
answers pydantic construction with a refusal rather than an `AttributeError`, and
cite `D-IMPL-126`.

**(a) The header, and the ruling on `ETag` versus a CCF-specific name.**

**Take `X-CCF-Content-Address`. Do not use `ETag`, and do not ship both.** Record
the reasoning in `canonical_response`'s docstring, because this is a real design
question and a later reader will re-ask it:

1. **A CCF content address is an identity, not a cache validator.** It is the
   `D-IMPL-26` primitive the ArtifactStore resolves and replay pins against. RFC
   9110 permits intermediaries to weaken a strong `ETag` to `W/"..."` or rewrite
   it across a content-coding transformation. An identity a proxy may legally
   alter is not an identity.
2. **`ETag` advertises cacheability on an entitlement-scoped body.** These
   responses are per-principal and per-perspective (`entitled_perspective`
   decides before the resolver runs). An `ETag` invites an intermediary cache to
   hold and re-serve a governed product; an `X-CCF-*` header carries **no** HTTP
   caching semantics and creates no such invitation. This is also why no
   `Cache-Control` change is needed or made here — the hazard is avoided by the
   header choice rather than papered over by a second header.
3. **`ETag` is per-representation; the content address is per-object.** The
   moment this door gains content negotiation or compression the two must
   diverge, and at that point an `ETag` set to the content address would be
   lying. A distinct name can stay true through that change.
4. Implementing `ETag` honestly would also mean implementing `If-None-Match` and
   a 304 path — real behaviour on a shipped door, and outside what `D-IMPL-126`
   ruled.

Put the header in **`canonical_response` itself**, not in `product.py`. All six
call sites serve `canonical_bytes(...)`, so the claim is uniformly true, there is
one place to compute it, and there is one place to test it. Compute the bytes
once and derive both the body and the digest from that single value — never
serialize twice.

Name the header in a module-level constant so the tests, any future client
helper, and the docs all read one definition.

`refusal_response` is unchanged and gains no header.

**MCP is deliberately untouched.** The MCP doors have no header channel and their
bodies are the product itself; adding the address to an MCP body would change the
body and therefore change the address it claims. Say this in the docstring so a
later reader does not read the asymmetry as an oversight.
