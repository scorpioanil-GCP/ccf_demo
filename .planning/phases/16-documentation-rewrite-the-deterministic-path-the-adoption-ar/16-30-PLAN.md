<objective>
Close `D-IMPL-136`: one call over one `ccf_config.yaml` boots a fabric, and the
compatibility commitment in §10 — *"existing multi-file deployments work
unchanged"* — is **proved** rather than asserted.

Purpose: §3 argues from the tree that merging artifacts into one file does not
collapse their version identities, because `ArtifactPin.version` **is** a content
hash, `canonical_bytes` addresses the parsed object, and `manifest.py`
content-addresses the parsed contract rather than the file bytes. That argument
is correct and it was verified before this plan set was written. An argument is
not a regression test. This plan turns it into one, so that a future change to
canonicalisation, to the registry, or to either loader fails loudly instead of
quietly making one authoring form address differently from the other.

**Scope, per Dave's dual-model ruling of 2026-08-14:** *"We will need to support
a dual model — we build everything new on the new implementation design. We will
convert all examples to the new implementation as we start to build them out.
This is new examples only."* So **nothing is converted**. No file under
`examples/` is written by this plan. Existing examples convert only when they
are next rebuilt for their own reasons, and no bulk migration is planned. The
repository keeps a live running example of **both** shapes, which is what a dual
model should look like in the tree.

Output: one public entry point, one internal extraction, two test modules, one
surface fragment, one regenerated `docs/SURFACE-CHANGES.md`.
</objective>

`load_and_boot` then reads: parse the manifest, resolve the tenant, preflight
entries, preflight the adapter, resolve secrets, read and `load_artifact` each
document, call `_register_and_boot`. `load_config_and_boot` reads: parse the
config through `load_artifact(text, DEPLOYMENT_CONFIG)`, `derive_deployment`,
resolve the tenant, preflight entries, preflight the adapter, resolve secrets,
`parse_artifact` each materialised document, call `_register_and_boot`.

**Why extraction rather than a second loop, stated in the code.** The register
loop carries three things that are easy to get subtly wrong and expensive to get
wrong twice: the `register_versioned` narrowing that stops a returned
`RegistrationRefusal` being recorded as a pin, the deliberate absence of a
fallback to `register_typed`, and the `ArtifactPin` construction that **is**
replay dimension 2. A second copy would drift, and the drift would be invisible
until a replay disagreed. Put that reasoning at the extraction site.

**The derived path resolves to a real file, and that is the point.** Every
derived entry's `path` is the config filename, so `_document_inside_the_deployment`
resolves all of them to the config document itself — inside the deployment,
passing both `ManifestEntry` validators and the symlink check. Run the preflight
on the config path rather than skipping it: a check that is skipped for the new
door is a door the audit plane knows less about. Note in the docstring that the
key → path mapping is then total and constant, and that the config path does not
*use* the returned paths (its documents are already in memory) — it runs the
preflight for its refusals.

**Do not widen `load_and_boot`.** No `config_path` parameter, no
`Union[manifest, config]` argument, no auto-detection by filename. Two names,
two doors, one shared spine. Auto-detection would make *which loader ran* a
function of a filename, and the loader in force is a fact replay should be able
to read off the call site. Record the rejected alternative in
`load_config_and_boot`'s docstring.

**`manifest.yaml` optional (§7) is satisfied by having a second entry point, not
by making `load_and_boot` fall back.** A config-form deployment simply does not
have a manifest file. If a deployment wants both — a config plus a manifest
carrying deviations — that is out of scope here and must be named as such in the
docstring rather than half-built.

**Name what the form cannot express.** There is no `signal_batch` section, and
that is a decision, not a gap: a signal batch is `role: load` because registering
one would content-hash raw event data into replay dimension 2 (`D-IMPL-80`), and
events are not Control Plane configuration. A deployment that puts a signal
batch in its manifest keeps its manifest — which the dual model supports
indefinitely. Put this in the module docstring, because `16-30`'s equivalence
test is scoped by it and a reader meeting that scope later deserves the reason.

**Citations use `path.py::Symbol`.** `D-IMPL-114`; the ratchet is at 0.
