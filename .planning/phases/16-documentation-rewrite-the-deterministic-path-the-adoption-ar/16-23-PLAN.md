<objective>
Give the MCP egress door a parameterised tool alongside its unchanged resource,
taking the four §6.3 axes the HTTP door already accepts, so that an MCP client
can ask its own question.

Purpose: `D-IMPL-126`'s decisive finding is that *"which question gets answered
is entirely the server's choice, so the MCP door as shipped cannot refute the
reading that a Context Product is a precalculated static object"* — which is
precisely what `D-IMPL-125` requires the consumer example to refute, and
precisely the surface Dave's own mental model reaches for. `D-IMPL-127` makes it
a hard sequencing constraint: **HW-2 is unbuildable until this lands**, because
today `PRODUCT_URI_TEMPLATE` is three path segments (`egress.py:116`), the
handler passes `request=None` as a hard-coded literal (`:368`), and the server
advertises zero tools — confirmed live at this HEAD as `TOOLS: []`.

This **extends `D-IMPL-108` rather than contradicting it.** The resource remains
the standing-answer surface at its unchanged URI; the tool is a second door. The
two are deliberately non-overlapping: the resource answers *the class's standing
answer* (`request=None`), the tool answers *a question* (all four axes, required
together). A caller wanting the standing answer reads the resource.

**The structural fact that makes this small: the seam is already wide enough.**
`ProductResolverProtocol.__call__` already takes `request: ProductRequest | None`
— `D-IMPL-108` and plan `15.5-15` paid for that widening across 24 files
specifically so it would never have to be paid again. This plan changes **no
Protocol signature** and reshapes **no** resolver call site.

The security of a client-parameterised door is the plan's central risk, not a
footnote. See `<threat_model>`, and see the three residuals recorded in Task 3
which are **named and escalated rather than designed around**, per CLAUDE.md §11.

Permitted by ROADMAP criterion 10 as amended by `D-IMPL-96`. `16-VALIDATION.md`'s
V-10 row is stale on the "zero lines changed" limb; this plan does not edit it.

Output: one opt-in tool, an over-the-wire security matrix that fails if the tool
is ever the weaker path, one surface-change fragment, and three recorded
residuals with a named candidate ruling for Dave.
</objective>

them — the resource answers the class's standing answer, the tool answers a
question — and that this **extends** `D-IMPL-108` per `D-IMPL-126`.

**(a) The opt-in switch.** Two new keyword-only parameters on
`build_egress_server`, both defaulting to the closed position:
`expose_product_tool: bool = False` and
`product_tool_description: str | None = None`. Registering the tool requires the
boolean; supplying a description without the boolean, or the boolean without a
description, raises `ValueError` in the `_missing` voice

pattern). Two parameters rather than one, and say why in the docstring: *is this
door open?* must be answerable by grepping for a boolean, not inferred from
whether a prose string happened to be supplied. Security surfaces are explicit.

Opt-in rather than always-on is not caution for its own sake. An existing
deployment reviewed and approved a resource-only door; upgrading the SDK must not
hand it a parameterised authorization surface it never assessed. Deny-by-default
is this module's stated posture and this is the same posture applied to exposure.

The description is a **required deployment value** — `CINV-01`: the prose an
adopter's consumers read about what this door answers is not the SDK's to write.
Unlike `experience.py`, ship **no** `DEFAULT_*` constant for it.

**(b) The tool.** Name it in a module-level constant, exported in `__all__`, so
the server, the client, the tests and the docs all read one definition — the
`product_uri` reasoning at `:245-251`. Signature, keyword-shaped and all
required:

`tenant`, `product_class`, `version` — the same three facts the resource URI
carries, so both surfaces address a product identically.
`subject`, `intent`, `freshness` as `str`; `asked_at` as `datetime`, so the
advertised JSON Schema says `format: date-time` and a client sends ISO-8601.

**All four axes required, deliberately.** The HTTP door's *some-but-not-all*
refusal exists because query parameters are individually omittable; a tool's
input schema can require them, which makes a partial address **unrepresentable**
rather than refused — strictly stronger, and the same property the HTTP door
already achieves for `schema_name`. Document that the standing-answer case is the
resource, not a four-`None` tool call.

**No `role` parameter.** The resource on this server passes
`requested_role=None` and the resolver derives the role from the verified grant.
The tool does the same. A `role` argument would give the tool a wider surface
than the resource beside it, and this plan's whole discipline is that the tool is
never the wider path.

the security property** (the `entitled_perspective` docstring's own phrasing):
