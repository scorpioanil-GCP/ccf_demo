<objective>
Give the MCP egress door a parameterised tool alongside its unchanged resource,
taking the four §6.3 axes the HTTP door already accepts, so that an MCP client
can ask its own question.

Purpose: `D-IMPL-126`'s decisive finding is that *"which question gets answered
is entirely the server's choice, so the MCP door as shipped cannot refute the
reading that a Context Product is a precalculated static object"* — precisely
what `D-IMPL-125` requires the consumer example to refute, and precisely the
surface Dave's own mental model reaches for. `D-IMPL-127` makes it a hard
sequencing constraint: **HW-2 is unbuildable until this lands**, because today
`PRODUCT_URI_TEMPLATE` is three path segments (`egress.py:116`), the handler
passes `request=None` as a hard-coded literal (`:368`), and the server advertises
zero tools — confirmed live at this HEAD as `TOOLS: []`.

This **extends `D-IMPL-108` rather than contradicting it.** The resource remains
the standing-answer surface at its unchanged URI; the tool is a second door. The
two are deliberately non-overlapping: the resource answers *the class's standing
answer* (`request=None`), the tool answers *a question* (all four axes, required
together).

**The structural fact that makes this small: the seam is already wide enough.**
`ProductResolverProtocol.__call__` already takes `request: ProductRequest | None`
— `D-IMPL-108` and plan `15.5-15` paid for that widening across 24 files
specifically so it would never be paid again. This plan changes **no** Protocol
signature and reshapes **no** resolver call site.

`_PLAN_NUMBER` regex, both of which are hardcoded to Phase 15 — measured, a
`16-*` fragment is invisible to `tests/test_surface_drift.py` and to
`tools/assemble_surface_changes.py`. Three wave-3 plans all file `16-*`
fragments, and "whichever lands first owns the widening" is undefined under
parallel execution. `16-22` owns it; this plan depends on it and files its
fragment against machinery that can already read it.

resource handler's body, its `request=None` literal and its return expression are

resource answers the class's standing answer, the tool answers a question — and

**(a) The opt-in switch.** Two keyword-only parameters, both defaulting closed:
`expose_product_tool: bool = False` and
`product_tool_description: str | None = None`. Either without the other raises
`ValueError` in the `_missing` voice (`experience.py:638-645`, the `D-03`

be answerable by grepping for a boolean, not inferred from whether a prose string
happened to be supplied. Security surfaces are explicit.

Opt-in is not caution for its own sake. An existing deployment reviewed and
approved a resource-only door; upgrading the SDK must not hand it a
parameterised authorization surface it never assessed. Deny-by-default is this
module's stated posture, applied to exposure.

The description is a **required deployment value** — `CINV-01`: the prose an
adopter's consumers read is not the SDK's to write. Unlike `experience.py`, ship
**no** `DEFAULT_*` constant for it.

**(b) The tool.** Name it in a module-level constant, exported in `__all__`, so
the server, the tests and the docs read one definition — the `product_uri`
reasoning at `:245-251`. Signature, keyword-shaped and all required:

`tenant`, `product_class`, `version` — the same three facts the resource URI
carries, so both surfaces address a product identically.
`subject`, `intent`, `freshness` as `str`; `asked_at` as `datetime`, so the
advertised JSON Schema says `format: date-time`.

**All four axes required, deliberately.** The HTTP door's *some-but-not-all*
refusal exists because query parameters are individually omittable; a tool's
input schema can require them, making a partial address **unrepresentable**
rather than refused — strictly stronger, and the same property the HTTP door
already achieves for `schema_name`. Document that the standing-answer case is the
resource, not a four-`None` tool call.

**No `role` parameter.** The resource passes `requested_role=None` and the
resolver derives the role from the verified grant. The tool does the same. A
`role` argument would give the tool a wider surface than the resource beside it.
