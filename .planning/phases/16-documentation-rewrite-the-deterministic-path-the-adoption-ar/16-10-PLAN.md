<objective>
Ship Section 3's first example: **embedding CCF in your own application** — in
process, then across a process boundary over MCP and A2A, then with the
ArtifactStore swapped underneath a running deployment.

Purpose: "the section most likely to be used for real problems." Concretely,
against today's surface, embedding means an in-process `load_and_boot(...)` →
`BootedFabric` inside the host application's own process, then the seven-step
spine, then either returning the `ServedProduct` in-process, standing up
`build_experience_server` for external consumers, or emitting over A2A/peering.
This example absorbs the material of `examples/04-cross-process` (assembler in a
subprocess, one product over **MCP and A2A**, Control Plane admission, tampered
envelope refusal) and `examples/07-artifact-store-mcp` (swap the store, nothing
else changes), which both retire in plan 16-17 with the pages that source from
them.

Two things this example must state and not blur. **A harness never acquires a
write handle to the graph** — single-writer holds across the adapter boundary
(CLAUDE.md §7.3, §10). And an inbound A2A Context Product is **not admissible to
L3 until the consuming Control Plane validates its Policy bindings** (§7.2) —
that is a structural commitment, and the example exercises it rather than
narrating it.

**Domain: `northwind-logistics` shipment exception handling — a third domain.**
Section 1 is banking KYC/UBO, Section 2 is e-commerce order fulfillment, and
this is freight. The suite visibly crosses domains, which is what `D-IMPL-52`
and CLAUDE.md §9 require and why `D-03`'s "spine" takes its narrow reading.

Output: one example directory with an explicit host-application boundary, a
cross-process producer, and assertions covering admission, refusal and the swap.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| producer process → consumer process | An A2A Context Product crosses an organisational boundary; everything about it is untrusted until the consumer's Control Plane says otherwise. |
| host application → Context Graph | The adopter's own code runs in the same process as the fabric; single-writer must hold anyway. |
| ArtifactStore substrate → L3 | The store is reached through mechanism and must never become a second writer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-10-01 | Spoofing | inbound A2A product identity | mitigate | Admission verifies the product's policy bindings at the **consumer's** Control Plane before anything reaches L3 (§7.2, `D-IMPL-16` — every inbound product, no fast path). Asserted on the verification outcome, not on the presence of a call. |
| T-16-10-02 | Tampering | the A2A envelope | mitigate | A tampered envelope is refused **during the run**, and the test asserts the refusal's type and reason so the assertion names which boundary held. |
| T-16-10-03 | Elevation of privilege | single-writer across the process and store boundaries | mitigate | Nothing constructs a graph writer; the host app writes only via `handle.worker.ingest`; the ArtifactStore is a substrate behind mechanism and never a second writer (CLAUDE.md §7.4, §10). Enforced by `cinv02-graph-writer` in `make lint`. |
| T-16-10-04 | Information disclosure | store endpoint and credentials | mitigate | The store artifact carries `store.type` with an env-templated root and endpoint; no path, port or credential is committed. The MCP store child and the client factory read the **same** auth block so credentials cannot drift (plan 08-09 precedent). |
| T-16-10-05 | Repudiation | over-claiming the binder | mitigate | The consumer-side comparison is cited as independent; the producer-side pattern is not, and no text claims the binder makes dual authorship structural — `D-IMPL-86`'s authorship residual is open and structurally unclosable by this mechanism family. |
| T-16-10-SC | Tampering | npm/pip/cargo installs | accept | No install. |
</threat_model>
