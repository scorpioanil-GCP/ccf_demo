<objective>
Make the Section-1 example a **parameterized runner**: one body, any registered
backend, **selected by a configuration artifact**, with a matrix asserting the
served Context Product is byte-identical across substrates.

Dave's ruling on criterion 4 is the shape: *"I like the example of sending in a
configuration that tells the example driver which backend to use as opposed to
creating six examples."* One driver. The backend binding lives in a
**configuration artifact** — not in a code path, not in a per-backend code fork,
and not as a value baked into the driver. A CLI flag may select *which*
configuration is loaded; the substrate name, the connection shape and the
credentials-by-env all belong to the configuration. That is also what CLAUDE.md
§6.4's No-Hardcoding Rule requires and what the Phase 15.4 registry seam exists
to enable.

Purpose: `D-06` asks the suite to prove substrate-neutrality as a **property**
rather than by repetition, and the Phase 15.4 backend registry seam is exactly
what makes that a lookup instead of a fork. Six literal per-backend variants
would re-fork the code that phase just un-forked. Greenfield makes this cheaper,
not dearer — every current example hardcodes `backend: sqlite` in its artifacts,
so parameterization is a design premise here rather than a nine-example
migration.

The precedent is not hypothetical: `tests/conformance/test_graphstore.py::
graph_backend` already parametrizes seven backends over `tests/conftest.py::
fabric_boot`, whose `location` mapping is keyed on each adapter's own config-model
field names. This example's connection resolver is its structural twin, and that
fixture's own docstring is the claim `D-06` wants the example matrix to make.

Output: per-backend thin manifests, one backend **configuration artifact**, a
`connection.py` that is a pure interpreter of it, a `--backend` flag that selects
which configuration is loaded (choices sourced from the registry, never a
literal tuple), a non-loopback socket guard, and a matrix test that proves there
is exactly one driver.
</objective>

THREE parameterization points, in order of authority:
 1. DeploymentManifest.backend — one string per manifest document. A manifest is
    content-hashable Control Plane state, so this value CANNOT be env-substituted
    inside the document without destroying the pin. Honest shapes: sibling
    manifest-<backend>.yaml files in ONE artifacts/ directory, all naming the same
    artifact documents. (load_and_boot preflights that every entry's document lies
    INSIDE the deployment, so co-location satisfies it; per-backend subdirectories
    do not.)
 2. connection= mapping — keys are the ADAPTER's own config-model field names,
    not boot's. Caller-supplied, so this is the one place a DSN/URI legitimately
    lives.
 3. backend_secrets — only `fluree` declares a secret field (bearer_token).
    Postgres/Neo4j/Mongo carry credentials inside the DSN/URI, which arrives
    through (2) and therefore never enters the tree.

WHAT IS SAFE TO COMPARE ACROSS BACKENDS:
ContextProductContract fields = schema_name, schema_version, plan_id, tenant_id,
  temporal_boundary, expires_at, ttl_anchor, lineage, payload.
ProductLineage = operators_invoked, policy_bundle_versions, graph_snapshot_at.
NO field is substrate-dependent, and expires_at derives from an authored instant.
So content_hash(product) byte-identity across all six is defensible.

WHAT IS NOT SAFE TO COMPARE (RESEARCH P-3):
The REPLAY RECORD is not byte-identical by design. PolicyBindingsSnapshot carries
graph_adapter, graph_adapter_version and graph_secret_refs as of plan 15.4-08
(src/ccf/replay/record.py:283-285). Assert equivalence on the SERVED PRODUCT and
assert the replay record's NON-ADAPTER dimensions separately. A plan asserting
"byte-identical replay records across six backends" will fail and would be wrong
to "fix" by dropping the adapter pin.

**(a) Sibling manifests.** Create `manifest-<backend>.yaml` in the *same*
`artifacts/` directory for each backend the matrix runs — at minimum `sqlite`
and `memory` (always-on) plus `postgres`, `neo4j`, `mongo` and `fluree`. Every
sibling names the **same** artifact documents by the same relative paths, and
differs only in its `backend:` value and, for `fluree`, its `backend_secrets`
entry naming the `bearer_token` field and its environment variable. Keep the
original `manifest.yaml` as the default (or fold it into
`manifest-sqlite.yaml` and repoint `run.py`; record which you chose and why).
Co-location is required: `load_and_boot` preflights that every entry's document
lies inside the deployment, so per-backend subdirectories will refuse.

**(b) `artifacts/backends.yaml` — the backend configuration artifact.** This is
where Dave's criterion-4 ruling lands, so author it **before** the code that
reads it. It is a declarative document, on the
`examples/03-harness-portability/artifacts/live.yaml` pattern, and it carries
the entire per-backend binding:

- one entry per backend the matrix runs, keyed by the same name the manifest's
  `backend:` field uses;
- for each, the **connection field names that adapter's own config model
  expects** (not `boot`'s), each paired with the environment variable that
  supplies its value and, where one exists, a value-free default description;
- `memory` declares an **empty** connection field set — the empty mapping is a
  declared fact, not a Python branch;
- for `fluree`, the `backend_secrets` *(field, env var)* pair naming
  `bearer_token`.

It is **deliberately not a manifest entry** — naming it in the manifest would
make the always-on legs parse and hand back configuration for a mode they never
enter. Its header lists every environment variable that overrides a default. It
carries **no** credential and — this is a hard gate — **no `192.168.4.76`
literal**: the DGX endpoints are supplied entirely from the environment, and the
artifact records variable names and value-free descriptions, never the host.
State in the header that a connection string is a deployment environment value
and that putting one in a versioned, content-hashed artifact would persist it
into the audit plane.

**(c) `connection.py` — a pure interpreter, not a resolver cascade.** It reads
`artifacts/backends.yaml`, looks up the entry for the named backend, and
materialises the `connection=` mapping by reading each declared field's
environment variable (falling back to the declared default where one exists).
It holds **no** substrate name, **no** endpoint, DSN, URI, host or port literal,
and **no** per-backend branch — an unknown name is a refusal because the
artifact declares no such entry, not because a Python `else` raises.

Say plainly in the module docstring what a reviewer will otherwise mis-read:
this module selects nothing. **Adapter selection is `DeploymentManifest.backend`
→ registry lookup; connection *values* are read from the environment against a
shape the configuration artifact declares.** Deleting `backends.yaml` must leave
this module with nothing to interpret — CLAUDE.md §6.4's own test of the
No-Hardcoding Rule.

**(d) `--backend` in `run.py` — a configuration selector, nothing more.** Add an
argparse flag on the `--mode` precedent whose only effect is to choose **which
configuration is loaded**: `artifacts/manifest-<name>.yaml` plus the matching
entry in `artifacts/backends.yaml`. Its `choices` come from
`ccf.graph.registry.declared_names()` intersected with the names the
configuration artifact declares, **not a literal tuple** — a literal six-name
tuple in an example is the substrate-name hardcode 15.4 removed from
`DeploymentManifest.backend`, and `cinv04-substrate-name` scopes `src/` only, so
nothing in CI would catch it here. Default to `sqlite` so the plain run command
keeps working. `run.py` stays a thin driver: it resolves the configuration,
hands the mapping to the spine, and asserts nothing. **No line in `run.py` may
branch on the backend's identity.**

The other four examples pin a single backend, and that is fine — they pin it
**by configuration** (their manifest's `backend:` field), and their READMEs say
so rather than implying the choice is structural.
