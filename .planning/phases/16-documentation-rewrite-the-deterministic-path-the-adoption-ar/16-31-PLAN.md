<objective>
Convert HW-1 — `examples/s1-00-companies-over-revenue` — from ten authored
config files to one `ccf_config.yaml`, under the `D-IMPL-136` **amendment** of
2026-08-15.

**Why this plan exists separately from `16-27`…`16-30`.** Those four build the
machinery and prove the two forms equivalent. None of them touches an example,
and that was correct while `D-IMPL-136` ruled HW-1 stays multi-file. The
amendment changed that clause and nothing else: `ccf_config.yaml` becomes the
sole *documented* authoring surface, and **HW-1 converts because it is the first
example a newcomer opens** (`D-IMPL-131`). Leaving the first example as the most
verbose one in the suite inverts the adoption story the examples exist to tell.

**What this plan does not do.** It does not remove or weaken the multi-file
loader — `D-IMPL-136` §10's absolute compatibility is unchanged and the loader is
retained indefinitely. It does not convert any other example: `00`–`08`,
`s1-01`, `ext-00`, `s2-01` and every manifest-authoring test fixture convert only
when next rebuilt for their own reasons, and **there is still no bulk
migration**. It does not touch `backends.yaml`, which stays a separate document
by design spec §9 because connection material is deployment environment, not
Control Plane state.
</objective>

<execution_context>
Branch `phase-16`. `16-30` must be merged and green before this starts — this

</execution_context>

<context>

**The measurement this plan moves.** `examples/s1-00-companies-over-revenue/artifacts/config/`
holds ten documents totalling **99 non-comment lines**:

| file | lines | becomes |
|---|---:|---|
| `manifest.yaml` | **46** | **deleted** — the index of itself that `D-IMPL-136` removes |
| `backends.yaml` | 10 | **stays where it is** (§9) |
| `request-contract.yaml` | 11 | `request_contract:` section |
| `product-class.yaml` | 7 | `product_class:` section |
| `half-life-table.yaml` | 6 | `half_life:` section |
| `resolution-spec.yaml` | 6 | `resolution:` section |
| `debt-profile.yaml` | 4 | `debt_profile:` section |
| `policy-bundle.yaml` | 4 | `policy:` section |
| `perspective.yaml` | 3 | `default_perspective:` section |
| `operator-parameters-temporal.yaml` | 2 | `operators:` section |

`manifest.yaml` alone is 46% of the surface and is an index of things the
filenames already say — the measurement that produced `D-IMPL-134` and
`D-IMPL-136`.

**Two sections are adopter-owned and carry three bookkeeping lines each.**
`policy` and `request_contract` map to classes the SDK does not own, so
`class_id`, `role` and `registration` must all be stated —
`D-IMPL-138`(a), because deriving an adopter's `class_id` would require the SDK
to invent an adopter namespace and `D-IMPL-84` forbids it. Six lines of the
converted file are this, and they are the whole cost of keeping `D-IMPL-80`,
`D-IMPL-85` and `D-IMPL-84` intact together.

**The design spec's stated target is "roughly 30 lines against HW-1's current
99".** That target predates `D-IMPL-138`(a)'s three-line rule and the two
required pointer fields. **Measure the result; do not tune the file to hit the
number.** If the converted file lands materially above the target, that is a
finding to record in the SUMMARY with the line-by-line account, not something to
compress by moving content out of the file.

<interfaces>

**`load_config_and_boot`** — shipped by `16-30` in `src/ccf/deployment/config.py`.
The single-file entry point. `deployment.py` currently reaches the fabric through
`load_and_boot` over `MANIFEST = CONFIG / "manifest.yaml"`
(`examples/s1-00-companies-over-revenue/deployment.py:60`); after this plan it
reaches it through `load_config_and_boot` over `ccf_config.yaml`.

**`tests/examples/test_s1_00_config_equivalence.py`** — written by `16-30`. It
reads HW-1's committed multi-file documents and compares content addresses
against a hand-authored single-file fixture. **This plan removes its input**, and
Task 1 exists to keep it working. Read it before changing anything.

**`tests/examples/test_s1_00_output.py`** — HW-1's output assertions. The
conversion must not change what the example prints; if this test needs an edit
beyond a path, the conversion changed behaviour and that is a defect.

**Content addressing** — `src/ccf/deployment/pins.py::ArtifactPin.version` is a
content hash over the **parsed object**, so *pin identity is content identity*.
`D-IMPL-136` measured that sections parsed from one file therefore yield
byte-identical addresses. This is the plan's strongest correctness check: **the
product's content address must not move.**

</interfaces>
