<objective>
Close `D-IMPL-128` limb 1: the SDK's **external** front door ships a tool that
reaches Context Product assembly with no entitlement check, standing beside a
resource on the same server that checks properly.

Purpose: `runtime/ccf_runtime/mcp/experience.py:775-777` is
`def get_context(tenant: str, entity: str) -> str: return
context_seam(tenant=tenant, entity=entity)`. Both arguments are client-supplied
and the handler calls neither `verified_grant()` nor `entitled_perspective(...)`.
The `context_product` resource on the same server calls both, at `:686-693`. The
module's own docstring at `:48-58` argues the posture it violates — *"a fabric
whose external door is less governed than its internal one has its threat model
backwards … shipping the SDK's own front door ungated would be that complaint,
self-inflicted"* — and `experience.py` **is** the external door.

`D-IMPL-128` also rules that this is **evidence about a class, not an incident**:
`get_lineage` and every other tool on the server are to be checked for the same
shape. This plan therefore audits all five, gates the two that a Context Product
entitlement can honestly decide, and leaves the three it cannot gate without
inventing an authorization semantic the SDK has no artifact for — a disposition
`D-IMPL-129` has since ruled.

**What this plan does not do.** It does not close `D-IMPL-128` limb 2. Client-chosen
`entity`/`subject` scoping is a named residual, unassigned by ruling, because
closing it needs a perspective-scoped assembly path that `D-IMPL-119` limb 2
measured as *empty on the shipped path* and put out of scope, and that `D-IMPL-124`
Shape D was **blocked** on. This plan gates the door. It builds no scoped assembly.

Authority: `D-IMPL-128` (Dave, 2026-08-13) and `D-IMPL-129`, under ROADMAP
criterion 10 as amended by `D-IMPL-96`, which revoked the "no fabric changed"
wording precisely so Phase 16 could repair defects it finds. `16-VALIDATION.md`'s
V-10 row is reconciled against, not rewritten, by this plan.

Output: two gated handlers, three pinned-open gaps, one over-the-wire refusal

  <action>
**(a) The two new builder parameters, their conditional requiredness, and the
ordering constraint that keeps two existing tests honest.** Add two keyword-only
parameters to `build_experience_server`, both `str | None = None`:
`entitled_product_class` and `lineage_tenant`.

`entitled_product_class` is the second operand of the entitlement decision for the
gated consumption tools. It must be **deployment-supplied, never client-supplied**,
and the docstring must say why in one sentence a reviewer can check: the class the
entitlement is decided against has to be the class the injected provider actually
serves, and only the deployment knows that. A client-supplied class would let a
caller name a class it *is* entitled to while the provider returned a different
one — the entitlement checking one operand while the door serves another. Note the
contrast explicitly: the `context_product` **resource** may take its class from the
client precisely because that same value addresses the resolver, so check and serve
cannot diverge there.

`lineage_tenant` is the tenant `get_lineage` decides under. It exists because that
tool carries **no arguments at all** — there is no tenant on the wire, and
inventing one would be the SDK holding a deployment value (`CINV-01`).
`get_context` takes no such parameter: it has a wire `tenant`, and deciding against
the caller's own tenant argument is exactly what `D-IMPL-128` asks for.

Requiredness is conditional on exposure, following the `D-03` pattern at
`:765-769`, and it fails in both directions:
  - `GET_CONTEXT_TOOL` allowlisted and `entitled_product_class is None` -> `ValueError`.
  - `GET_LINEAGE_TOOL` allowlisted and either value is `None` -> `ValueError`.
  - a value supplied for a tool the allowlist does not admit -> `ValueError`.

**ORDERING IS MANDATORY, NOT STYLISTIC.** Inside each `if <TOOL> in allowed:`
block, the existing provider/description check must run **first and unchanged**,
and the declared-address check must run **strictly after it**, raising a
**distinct message that does not reuse `_missing`'s wording**. Add a sibling
helper (e.g. `_missing_address`) rather than widening `_missing`'s condition. The
reason is specific and verifiable: `test_an_allowlisted_tool_without_its_provider_is_refused`
(`:329-352`) and `test_an_allowlisted_tool_without_its_description_is_refused`
(`:400-427`) both allowlist `GET_CONTEXT_TOOL` off `_builder_kwargs`, which
supplies no `entitled_product_class`, and both assert only
`GET_CONTEXT_TOOL in str(raised.value)`. Folding the new check into the same
condition or the same message would make both tests pass off the **new** check
regardless of whether their own legs still work — two shipped D-03 assertions
silently losing their discriminating power. Ordering plus a distinct message keeps
them failing for their own reasons; Task 2 additionally repairs their inputs.
