<objective>
Build **HW-1**, the first example a newcomer runs: a very simple Context Product
assembled from Postgres, consumed by an in-process client that supplies its own
revenue threshold at call time.

Purpose: Dave read `examples/s1-01-hello-context-product/artifacts/` on GitHub
and asked *"Do I really require this many yaml files to construct my context
product?"* — 20 files, ~1060 non-comment lines. `D-IMPL-131` and `D-IMPL-132`
are the rulings that came out of that reading, and this plan is their first
discharge. The deliverable is therefore **two things at once**: a working
example, and **a measured number** — how many files an adopter authors and how
many non-comment lines that is, split into what CCF requires versus what
fabricates the demonstration.

Output: `examples/s1-00-companies-over-revenue/`, one `make` target, one test
module, and `MEASUREMENT.md` carrying the number with the commands that
reproduce it.
</objective>

<what_dave_specified>
Verbatim, 2026-08-14:

> *"Let's do a simple query that simply asks for company's who have over a
> certain amount of revenue. The revenue is passed in by the client. Very simple
> context product. Use last update as the input for context debt."*

Four commitments, and each is load-bearing:

1. **The question** — which companies have revenue over a threshold.
2. **The threshold comes from the client, at call time.** `D-IMPL-125` and
   `D-IMPL-127` require this precisely so a reader cannot mistake a Context
   Product for a precalculated static object: *"a context product is not a
   precalculated static object"*. A fixed threshold would destroy the
   demonstration and is not a permitted simplification.
3. **Context Debt is driven by `last_updated`** on the source rows. That is the
   one governance dimension this example teaches, and it is the natural one — a
   plain SQL query returns rows and tells you nothing about how stale they are.
4. **Very simple.**

**The comparison the example must win, stated plainly in the README:**

    SELECT name, revenue FROM companies WHERE revenue > :threshold;

That returns rows. The same question through CCF returns rows **plus** their
staleness as a measured `D_c`, the policy version that applied, a content
address, and a replayable record. If a reader cannot see that difference in the
printed output, the example has not earned its extra machinery.
</what_dave_specified>

<the_parameter_shape_and_why_it_is_required>
**`revenue_threshold` is a genuinely REQUIRED declared request parameter.** It
appears in `ProductRequestContract.arguments.properties` **and** in that schema's
`required` tuple. A `ProductRequest` that omits it is refused with
`reason='missing-required-parameter'`, which is the correct behaviour: a
threshold nobody supplied is not a question this class answers.

**Why this needs saying at all.** The phase's `deferred-items.md:83-104` assigned
this plan a constraint: both parameterised doors hard-code `parameters={}`, so a
class declaring any required parameter was unreachable through them — and it
recorded the repair as *blocked*, on the reasoning that carrying declared
parameters *"requires validating them against the `RegisteredProductClass`,
which the door never holds."*

**That reasoning is false and `D-IMPL-133` corrects it.** A door never needs the
class **because a door never validates**. `src/ccf/products/request.py:530` says
so in the function's own docstring — *"Called by the deployment's own resolver,
not by any door"* (`D-IMPL-121`, extending `D-IMPL-113`) — and the same docstring
records that an earlier revision claimed the opposite and was corrected for being
false as written. Verified independently at plan time: `refuse_request` appears in
`runtime/` only as three docstring cross-references (`egress.py:220`, `:547`,
`experience.py:240`) and is **called nowhere**. The door carries the mapping
through to the resolver, which holds the class and runs the comparison where
`D-IMPL-121` put it. The repair is two lines — `egress.py:588` and
`product.py:330` — and **plan `16-26` implements it for both doors.**

**Three consequences, and each is small:**

- **HW-1 does not depend on `16-26`.** Its client is in-process and passes
  `parameters` directly to the production side, never through a door. **Do not
  add `16-26` to `depends_on`** and do not wait for it.
- **The contortion is gone.** An earlier draft of this plan declared
  `revenue_threshold` with `required: []` purely to keep the class reachable
  through a defective door. That is exactly the shape `D-IMPL-133` says would
  have *"shaped the first example around a door defect"*, and a reader would have
  had to be told why an obviously-required parameter was declared optional. It is
  removed.
- **HW-2 is unblocked in full.** With `16-26` landed, HW-2 reuses HW-1's product
  unchanged and changes only the client, and can prove **both** halves of what
  `D-IMPL-127` asks it to teach: that remoteness costs nothing, **and** that the
  client owns the question. Say that in the README as a forward reference; there
  is no open question here and nothing for this plan to escalate.
</the_parameter_shape_and_why_it_is_required>
