<objective>
Ship the **document half** of `D-IMPL-136`: `ccf_config.yaml` as a typed,
closed-world, schema-exported artifact class. Parsing only — nothing is derived,
materialised, registered or booted in this plan.

Purpose: `D-IMPL-136` rules that *"the section name **is** the class"* and that
*"unknown top-level keys are an error"*. Both are contract properties, and this
codebase already has the mechanism for them — `CCFContract`'s `extra="forbid"`
and the `ArtifactClass` registry that feeds `tools/dump_schemas.py`. Building
the document as a typed class rather than hand-rolling a dict walk is what makes
the refusal structural, gives the adopter editor completion before anything
runs, and keeps `ccf_config.yaml` on exactly the same footing as the ten files
it replaces.

Splitting the document from the derivation (`16-29`) is deliberate. The
derivation is where `D-IMPL-134`'s narrowing lives and where every refusal in
design-spec §11.2 and §6 fires; putting both in one plan would put a contract
and its interpreter in one context window, and the interpreter is the larger of
the two by a wide margin.

Output: one contract, one `ArtifactClass`, one registry entry, one test module,
one committed schema, one surface fragment, one regenerated
`docs/SURFACE-CHANGES.md`.
</objective>

**Deployment-level fields**, each mirroring `DeploymentManifest`'s field of the
same name so the two documents cannot drift: `tenant_id: str | None = None`,
`backend: str = Field(pattern=r"^[a-z][a-z0-9_]*$")`,

**The two pointer fields carry design spec §6.3 exactly and must not be
dropped.** §6.3 rules that `resolution_spec_key` and `policy_bundle_key` are
*"derived from the section names — `resolution:` and `policy:` — and are not
authored"*, but that they *"remain overridable for a deployment that registers
several and must name which is in force"*. Omitting them would make the second
half of that ruling unexpressible in the single-file form. `None` is the ordinary
case and means *derive from the section name*; `16-29` reads them.

**`backend_secrets` and `survivor_cap` are not in the design spec's §4.1 list,
and adding them is a judgement this plan must defend in the docstring.** §10
commits that *"compatibility is absolute"* and that the single-file form is an
*additional* authoring surface. Without these two, a deployment whose adapter
takes a credential, or which has configured a D-10 survivor cap, **cannot** be
expressed in the new form — so the single-file form would be strictly less
capable than the one it sits beside, and §10 would be false for every
credentialed adapter. Both carry names, never values (`SecretReference` records
the two mechanisms that make that structural), so neither weakens §9's
backends-stay-out boundary: what stays out is the **connection**, which is
`load_and_boot`'s caller-supplied `connection` mapping and is not a field of
either document.

**Section fields.** `product_class` required; the rest optional with a default
that is distinguishable from an empty mapping — `None`, and say in the docstring
why absent and empty are different: an absent `policy:` is a deployment that
declares no regime, an empty one is an adopter who wrote a heading and nothing
under it, and `16-29` refuses the second.

Type the **SDK-owned** sections (`product_class`, `resolution`, `half_life`,
`debt_profile`, `default_perspective`) and the operator bodies as open mappings
at this layer, **not** as their eventual contracts. The reason is
`D-IMPL-136`'s derivation model: a section body is materialised into a document
that also carries the derived `semver` and, for `half_life`, is *wrapped* under
`entries:` — so a body typed as `HalfLifeTable` here would demand a `semver` the
adopter is not writing and an `entries:` key the section deliberately elides.
Validation against the real contract happens in `16-29` through
`parse_artifact`, which is the seam that already produces `ArtifactLoadError`
with the class named. State this in the class docstring so the next reader does
not "tighten" it and break the materialisation.

Type the **adopter-owned** sections (`policy`, `request_contract`) as open
mappings too, and here the reason is a ruling rather than a mechanism:
`D-IMPL-136` §14.3 — the SDK owns the slot name and the adopter owns the schema
and contents. A typed body would be the SDK validating what it has ruled it does
not interpret.

**The unknown-section refusal.** `extra="forbid"` already refuses, but its
message is Pydantic's — *"Extra inputs are not permitted"* — which is precisely
the *"refusal about a missing key three layers down"* the spec is trying to
delete. Add a `model_validator(mode="before")` that collects **every** unknown
top-level key and raises one `ValueError` naming them all and listing the
reserved names. Build the list of reserved names from
`DeploymentConfig.model_fields` rather than a second literal tuple — a
hand-maintained list beside the fields is the drift `_preflight_adapter`'s
refusal was rewritten to avoid, and its payback there was *"an error message
that can say what IS registered here"*. Same payback, same shape.

A `mode="before"` validator, not `mode="after"`: `extra="forbid"` fires during
field validation, so an `after` validator never runs on the failing document.

**Docstring discipline.** Cite `docs/DECISIONS.md` `D-IMPL-136` and `D-IMPL-84`
