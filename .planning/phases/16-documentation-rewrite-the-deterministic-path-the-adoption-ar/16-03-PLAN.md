build the two Section-2 client legs that do not exist, and prove them against the
**existing** `examples/external/00-hello-context` server before the greenfield
fabric exists.

Purpose: criterion 3 requires zero-CCF-import client legs across **all three**
harnesses — Claude Agent SDK, Google ADK and LangGraph (`D-09`, `D-IMPL-24`).
`16-RESEARCH.md` FINDING F-2 measured the tree: it ships bare-MCP, raw-Anthropic-SDK
and ADK legs. There is **no LangGraph client leg anywhere in the tree**, and
`16-PATTERNS.md` marks it `NO ANALOG` — the shipped
`runtime/ccf_runtime/adapters/langgraph/adapter.py` is the exact inverse of what
is wanted (it imports `ccf` by design). The Claude-Agent-SDK leg has only a near
analog: `client_anthropic.py` drives the raw `anthropic` SDK plus the `mcp`
client, which is a different harness binding.

Risk R-4 is explicit about the mitigation: *spike the LangGraph leg early
against the existing server, so a transport surprise surfaces in week one rather
than in wave four.* This plan is that spike, and its output is production code
rather than a throwaway — the two legs land in their final home and plan 16-09
repoints them at the new fabric.

Output: two client legs in `examples/s2-01-external-consumers/`, a spike test
that drives both against a real running server, and a recorded transport note.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external harness → CCF MCP door | The client legs are untrusted third-party runtimes; everything they can do is what the Experience server's `tool_allowlist` registered. |
| environment → client leg | `CCF_TOKEN` is a bearer credential and reaches the leg only through the environment. |
| PyPI → repository | A new dependency would widen the supply-chain surface of an example suite that currently installs nothing new. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-03-01 | Spoofing | MCP bearer auth | mitigate | The legs send `CCF_TOKEN` in an `Authorization` header against `runtime/ccf_runtime/mcp/auth.py`, which has **no anonymous mode**. No token literal enters either file; absence of the variable is a refusal, not a fallback. |
| T-16-03-02 | Information disclosure | `CCF_TOKEN` in logs | mitigate | Neither leg prints its token or its full URL with credentials; the only stdout is the process handshake. Asserted by the no-print criterion. |
| T-16-03-03 | Elevation of privilege | the harness's tool surface | accept | Tool exposure is a registration-time omission on the server (`tool_allowlist`, D-05): a tool absent from the allowlist is never registered, so a client leg cannot reach it regardless of what it asks for. The client side needs no mitigation. |
| T-16-03-04 | Tampering | the shipped external example | mitigate | This plan is read-only against `examples/external/00-hello-context/`; `git status --porcelain` on that path is asserted empty, because `tests/examples/test_ext00_hardening.py` and EXAM-04/ERGO-15 rest on those files being byte-unchanged. |
| T-16-03-SC | Tampering | npm/pip/cargo installs | mitigate | **No install.** `langchain-mcp-adapters` is `[ASSUMED]` in RESEARCH's Package Legitimacy Audit and recommended against; this plan takes the zero-new-dependency path. Any deviation requires a `checkpoint:human-verify` before install plus an exact pin, and is not authorised here. `git diff -- pyproject.toml` empty is an acceptance criterion on both leg tasks. |
</threat_model>
