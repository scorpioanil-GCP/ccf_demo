<objective>
Ship Section 2: external agents consuming governed context over MCP with **zero
CCF dependency**, across all three harnesses.

Purpose: this is the primary adoption path — an external agent consuming
governed context over MCP — and `D-09` keeps all three harnesses because harness
neutrality is mission success condition 3 (CLAUDE.md §1), `D-IMPL-24` ruled all
three ship v0 reference adapters, and a three-way assertion is a materially
stronger claim than a two-way one. The constraint **is** the demonstration: the
absence must be visible in the client code's own import list, which is exactly
what `examples/external/00-hello-context` already proves for three legs.

Plan 16-03 already built and proved the two missing legs against the old server.
This plan builds the fabric side they now point at and rebuilds the two proven
patterns (bare-MCP and ADK). **Proving the zero-dependency claim is plan
16-20's** — the AST guard, its five-spelling negative control, the
exactly-three-harnesses assertion and the README moved there at the plan review,
because thirteen files across three tasks in the phase's riskiest wave is a
context-budget failure waiting to happen. The seam is where the example *works*
and where the claim is *proven*.

**Domain: `atlas-commerce` order fulfillment — deliberately not KYC.** `D-03`
makes KYC/UBO the *spine*, and the narrow reading is the one taken at planning:
Section 1 and the adoption argument carry KYC because that is where the data
lives; Sections 2 and 3 carry other domains, so `D-IMPL-52` and CLAUDE.md §9's
horizontal-domain-mix ruling stay intact. That tension is named here so it is
visible rather than fallen into.

Output: one example directory, four client legs, and live-captured
deterministic fixtures. Plan 16-20 follows immediately with the guard nobody can
quietly widen.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external harness → CCF MCP door | Four untrusted third-party runtimes reach the fabric; the door is the whole boundary. |
| environment → client leg | `CCF_TOKEN` is a bearer credential and reaches a leg only through the environment. |
| captured fixture → CI | Live-captured fixtures are replayed as though they were server responses; a tampered fixture is a tampered test. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-09-01 | Spoofing | MCP bearer auth | mitigate | `runtime/ccf_runtime/mcp/auth.py` verifies against a manifest-loaded token table with **no anonymous mode**; `serve.py` passes it explicitly. No token value enters an artifact or a Python file; absence is a refusal, not a fallback. |
| T-16-09-02 | Elevation of privilege | the harness's tool surface | mitigate | `tool_allowlist` is a **registration-time omission** (`D-05`): a tool absent from it is never registered, so a client cannot reach `invoke_agent` or any other tool regardless of what it asks for. `serve.py`'s docstring states this so a reader does not mistake it for a runtime check. |
| T-16-09-03 | Tampering | replayed fixtures | mitigate | Fixtures are live-captured and diff-reviewed, matched by request fingerprint, and covered by a schema guard on the `tests/examples/test_ext00_fixture_schemas.py` model (EXAM-05). The review of each capture is recorded in the SUMMARY. |
| T-16-09-04 | Repudiation | the zero-CCF-dependency claim | transfer | The AST guard, its five-spelling negative control and the exactly-three-harnesses assertion are plan **16-20**'s, at wave 5, immediately after this plan. This plan ships the legs; 16-20 proves the claim about them. The transfer is recorded here so the threat is not lost at the split. |
| T-16-09-05 | Information disclosure | credentials in logs or fixtures | mitigate | No leg prints its token; fixtures are reviewed before commit; `grep` for assigned credential values across the directory returns nothing. |
| T-16-09-SC | Tampering | npm/pip/cargo installs | mitigate | **No install.** `langchain-mcp-adapters` is `[ASSUMED]` in RESEARCH's audit and recommended against; the LangGraph leg uses `mcp.ClientSession` directly. `git diff -- pyproject.toml` empty is an acceptance criterion. |
</threat_model>
