<objective>
Build the Claude Agent SDK reference adapter end to end, and harden
`HarnessAdapterProtocol` and the conformance suite against it — the first half of D-07's
"one adapter deep, then two against the suite".

Purpose: D-09 rejects doubles deliberately, because a double written to the Protocol we
designed can pass while the real SDK's surface disagrees, which is exactly the failure
this phase exists to prevent (§7.3 — portability is demonstrated, not asserted). Research
executed every seam against `claude-agent-sdk==0.2.128` and confirmed the SDK can be driven
with **no LLM calls and no `claude` CLI**: `create_sdk_mcp_server` returns a real
in-process server and `await tool.handler({...})` returns the payload directly. Build
against that verified surface.
Output: the first harness-importing module in the repository, and the conformance suite it
hardens.
</objective>

  <action>
Create `runtime/ccf_runtime/adapters/__init__.py`,
`runtime/ccf_runtime/adapters/claude_agent/__init__.py`, and
`runtime/ccf_runtime/adapters/claude_agent/adapter.py` — the first modules in the repository
permitted to import a harness package, per the D-24 carve-out landed in 06-01.

Bind the four seams to the concrete APIs research verified:
1. **Context injection** — the agent's typed Context Product and its already-pinned,
   already-rendered instructions go into `ClaudeAgentOptions.system_prompt` (and/or
   `agents={name: AgentDefinition(prompt=...)}`). The adapter passes rendered artifacts,
   never literals, and never re-resolves a prompt artifact (No-Hardcoding, and the
   `PHASE_I2_GATE.md` §5 constraint restated in 06-11's `prompts.py`).
2. **Skill exposure** — build tools with `@tool(name, description, input_schema)` closing
   over `Agent.invoke_skill`, assemble them with
   `create_sdk_mcp_server(name=..., version=..., tools=[...])`, bind via `mcp_servers={}`,
   and set `allowed_tools` to **exactly** the currently-bound skill-set. Skill names,
   descriptions, and schemas come from the catalog entries; none is a literal. Let the SDK
   derive the JSON Schema from the declared input model rather than hand-writing one.
3. **Effect capture** — route harness outputs back through `Agent.emit_effect` using
   `can_use_tool` returning `PermissionResultAllow`/`PermissionResultDeny`, with
   `hooks={'PreToolUse'/'PostToolUse': [HookMatcher(...)]}` as needed. The harness never
   acquires a write handle; emission is a returned typed value.
4. **Replay hooks** — capture `ClaudeAgentOptions.model` and the `ResultMessage` fields
   into the 06-11 `HarnessTrace`, and pass it to `build_replay_record` as the verbatim
   pre-serialized block.

The adapter's constructor takes `Agent` and its own configuration — keyword-only,
injected — and **nothing else from the fabric**. No `FabricHandle`, no
`ControlPlaneRegistry`, no reader, no writer.

Module docstring: the four `/runtime` blocks, with a citation line marking this as
SDK-defined per CLAUDE.md §7.3, and a "what this adapter cannot do" paragraph restated for
this seam — it holds no `GraphWriter`, and effects reach L2 only through
`Agent.emit_effect`. Write it in D-21 language: name what the Protocol's shape, the
CINV-02 lint, and the conformance suite enforce.

**Do not set `__ccf_mode__ = "algorithmic"`.** Adapters bind a harness that reaches a
model — they are the semantic boundary, and CINV-03 would deny their imports anyway.
Research's anti-pattern list is explicit about this.

Per D-07 this is the deep first adapter: where the real SDK surface disagrees with
06-11's Protocol, **change the Protocol** and record what forced the change in the SUMMARY.
That discovery is the reason this adapter is built first. Research also warns (assumption
A4) that Claude is the most callback-shaped of the three and therefore least likely to
surface LangGraph's topology-ownership requirement — resist over-fitting the Protocol to
callback semantics, and expect 06-13 to force further change.

  `Agent.emit_effect`, as a returned typed value;
