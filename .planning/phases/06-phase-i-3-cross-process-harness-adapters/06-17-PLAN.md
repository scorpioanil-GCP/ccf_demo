<objective>
Bind the shared MCP client at its second consumer — the L4/L5 decision-time content
acquisition path that CLAUDE.md §7.1 names and the whitepaper's §6.6 search-inference
recursion describes — and prove the edge with a test that fails when the edge is unbound.

Purpose: ROADMAP criterion 1 and XPRC-01 require MCP client ingress at "L1/L4/L5/
Experience". 06-06 delivers L1; this plan delivers L4/L5. They are separate plans because
they are separate consumers with separate contracts: L1 normalizes an external response
into a `SignalEnvelope` for L2 to write, while L4/L5 acquires content at read time that
terminates in a projection payload and never enters the graph at all. A shared client
library serving one of them does not serve the other, and saying it does is exactly the
overclaim D-21 forbids.
Output: the `ContentAcquirer` seam in `/src`, its MCP reference implementation, the engine
stage that runs it, and unit plus cross-process proofs.

The Experience-layer leg of criterion 1 is Phase 7 scope per `06-CONTEXT.md`'s deferral of
the Experience Layer front doors; 06-16 records that deferral as an explicit gate row.
</objective>

  <action>
Bind the one shared MCP client at its second consumer: the L4/L5 read path, where a
projection needs content that is not in the graph at decision time. Three pieces.

**`src/ccf/projection/acquisition.py` — the seam, declared in `/src`, transport-free.**
- `ContentRequest` (a `CCFContract`): a *reference* to what is needed — the Control Plane
  key of the source and the resource selector carried as declared artifact values. No
  URL, no host, no scheme literal in this module.
- `AcquiredContent` (a `CCFContract`): the fetched item plus `content_hash` of its
  canonical form, plus the request that produced it. Frozen and opaque: acquisition
  fetches, it does not parse the meaning of what it fetched (CINV-03 — this module is
  `__ccf_mode__ = "algorithmic"` and must import no LLM client; the lint enforces it).
- `ContentAcquirer` — a `runtime_checkable` Protocol with one method,
  `acquire(*, requests, tenant_id) -> Mapping[str, AcquiredContent]`. Read-only by shape:
  it takes no graph handle and returns values, exactly as `Operator` does.
- `ContentAcquiringPlan` — a structural extension of `ProjectionPlan` adding
  `required_content() -> tuple[ContentRequest, ...]` and accepting
  `acquired_content: Mapping[str, AcquiredContent]` in `invoke()`. A **separate** Protocol
  rather than a widened `ProjectionPlan`, so every I.1/I.2 projection still conforms
  unchanged and the engine detects the capability structurally — the same argument
  `plan.py` already makes for having no base class.
  Restate `required_operators()`'s discipline for content: `required_content()` is a
  declaration the engine resolves, never a plan reaching out to fetch for itself. A plan
  that could acquire on its own would be its own provenance authority.

**`src/ccf/mcp/acquisition.py` — `McpContentAcquirer`, the reference implementation.**
Implements `ContentAcquirer` over the shared `ccf.mcp.client` sync facade. It constructs
no session, no event loop, and no bridge of its own (D-03, D-IMPL-13, pitfall B3) — the
identical constraint Task 2 puts on dispatch. Keyword-only constructor takes the resolved
Control Plane source configuration; **no public method accepts a URL, host, or scheme at
call time**, carrying the same SSRF posture as 06-06 Tasks 1–2, enforced by shape rather than by
validation. Marked as the L4/L5 client role in its header, distinct from the L1 ingress
role in `signal/mcp_source.py` and the ArtifactStore role in `artifacts/mcp_store.py`
(D-03's three-role separation).

**`src/ccf/projection/engine.py` — the acquisition stage.**
Add an optional keyword-only `acquirer: ContentAcquirer | None = None` to
`ProjectionEngine.__init__`, and a stage in `execute()` that runs **after** the operator
plan and **before** Π: if the plan is a `ContentAcquiringPlan`, resolve
`required_content()` through the acquirer and pass the result into `invoke()`. Ordering is
load-bearing and belongs in the docstring: acquisition runs after Policy has already
constrained the view, so nothing is fetched on behalf of a principal the policy stage
excluded (the INV-CH7-26 argument, applied to acquisition).

Three refusals, each a typed error rather than a silent default:
- a `ContentAcquiringPlan` with no acquirer injected;
- an acquirer configured for a source the plan did not declare;
- a declared request the acquirer could not satisfy.
Do not fall back to "proceed without the content" — a projection that silently interprets
absent content is the debt-blind case the fabric exists to prevent.

Record every acquisition in `ExecutionResult` as an `acquisitions: tuple[AcquiredContent, ...]`
in resolution order, so replay dimension 5 names what was fetched and its hash.
**Replay re-feeds the recorded content; it never re-acquires** (INV-CH7-31) — say this in
the docstring and make it structural by keeping the acquirer optional and injected, so a
replay path constructs the engine without one.

Nothing here touches L3. The engine still has no writer, the acquirer holds no graph
handle, and acquired content terminates in the projection payload — if a deployment wants
acquired content in the graph, it enters through L1/L2 like everything else (CLAUDE.md
§10). State that as the reason the seam returns values.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| External MCP content server → L4/L5 read path | Untrusted content acquired at decision time and interpreted by Π |
| Projection plan declaration → outbound network call | A declared content request determines what the process fetches |
| L4/L5 acquisition → L3 | Must not exist; acquired content terminates in the projection payload |
