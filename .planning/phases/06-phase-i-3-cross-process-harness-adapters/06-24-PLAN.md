<objective>
Realize D-IMPL-59: the federation seam becomes a first-class abstraction named **`Peering`**,
and A2A becomes one Peering transport rather than the concept.

Purpose: the gate review's B1, B2 and A2 were symptoms of one structural fact — a *category*
(governed context exchange between peer fabrics) named after its *first instance*. Every core
module that legitimately needed the category had to say "A2A" to reach it. The dependency
direction was already correct (D-04: Protocol in `/src`, transports in `/runtime`), so what
is wrong is vocabulary, not coupling. This is a **re-description of existing structure, not a
rebuild.**
Output: the core seam under its own name, with A2A named as its reference transport.

**Hard constraint, from Dave, restated because it governs every task here: no code is
deleted.** Renames, moves and additions only. A `git mv` preserves content and is a move, not
a deletion; the acceptance criteria require the diff to show rename status rather than paired
add/delete, so the constraint is checkable rather than promised.
</objective>

<naming_surface>
D-IMPL-59 part 1 rules the *name*; the mechanical surface is explicitly left to planning
("module path, Protocol name, skill-type token, Control Plane artifact key ... is planning
work against this decision"). This plan decides the core half; 06-25 decides the skill half.
The decisions, and why:

| Current | Becomes | Reason |
|---|---|---|
| `src/ccf/a2a/` | `src/ccf/peering/` | the package is the category |
| `src/ccf/a2a/wire.py` | `src/ccf/peering/protocol.py` | matches `ccf/harness/protocol.py` and `ccf/artifacts/protocol.py` — the SDK's existing name for the Protocol module of a seam package |
| `WireProtocol` | `Peering` | the Protocol *is* the seam. Not `PeeringProtocol`: the SDK names Protocols for what they are (`GraphWriter`, `EmbedderProtocol` both exist, but the seam types read better unsuffixed and `Peering` is the ruled word) |
| `A2AAdmissionGate` | `PeeringAdmissionGate` | part 4 — core runs *one* gate uniformly over every Peering |
| `A2ATrustPolicy` / `A2A_TRUST_POLICY` | `PeeringTrustPolicy` / `PEERING_TRUST_POLICY` | trust *inputs* are declared per Peering |
| `AuditAction "a2a_admitted"` / `"a2a_admission_refused"` | `"peering_admitted"` / `"peering_admission_refused"` | the verdict is a Peering verdict whichever transport carried it |
| `runtime/ccf_runtime/a2a/` | `runtime/ccf_runtime/peering/` | the package holds transports of the seam |
| `lf_a2a.py`, `typed_http.py` | **unchanged** | a transport is correctly named for the protocol it speaks; renaming these would erase the very distinction the ruling draws |
| `AdmittedProduct`, `ingest_admitted`, `union_lineage`, `InboundProduct`, `PeerRef` | **unchanged** | already transport-neutral; the ruling says so explicitly. Only their docstrings say A2A |
| `admission_record` artifact class id | **unchanged** | D-IMPL-58's ruling names the literal string |

Not renamed, deliberately: anything under `src/ccf/mcp*` or `ccf_runtime/mcp/`. Part 3 puts
MCP outside Peering — it is asymmetric, originates lineage rather than merging it, and stays
its own surface per CLAUDE.md §7.1.
</naming_surface>
