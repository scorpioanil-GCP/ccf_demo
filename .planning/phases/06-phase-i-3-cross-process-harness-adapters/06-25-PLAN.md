<naming_surface>
The skill half of D-IMPL-59's open mechanical surface, decided here:

| Current | Becomes | Reason |
|---|---|---|
| `SkillType` member `"a2a"` | `"peering"` | the token names what class of counterparty the skill reaches: a peer fabric with a Control Plane. `"mcp"` stays a separate member — part 3 |
| `A2ABinding` | `PeeringBinding` | its `endpoint` is already documented as a *logical peer-endpoint name*, never a URI — the field was always about a peer, not a protocol |
| `A2AInvocation` | `PeeringInvocation` | |
| `A2ASkillRegistry` | `PeeringSkillRegistry` | |
| `a2a_skills=` on `Agent` and `AgentFactory` | `peering_skills=` | |
| `BINDING_BY_TYPE` entry `"a2a"` | `"peering"` | the dispatch table is keyed by the token |

Explicitly not renamed: the `"mcp"` skill type, `McpBinding`, `McpSkillRegistry`,
`mcp_skills`. D-IMPL-59 part 3 puts MCP outside Peering — asymmetric, originates lineage
rather than merging it — and folding it in would blur the one property that makes federation
hard.
</naming_surface>
