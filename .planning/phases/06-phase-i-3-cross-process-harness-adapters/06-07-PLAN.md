<objective>
Build the trust primitives the A2A admission gate depends on: real detached-JWS signing
and verification (D-13, D-IMPL-15) behind an `IdentityProvider` Protocol, and the typed
Control Plane trust-policy artifact (D-IMPL-16) that bounds what each peer may assert.

Purpose: D-13 rules that signature verification is load-bearing for admission, so a
stubbed signer would make the admission gate untestable. Research proved the full
sign → detach → reattach → verify → tamper-refusal cycle end to end with `joserfc` ES256,
including `BadSignatureError` on a tampered payload — build against that verified shape.
The trust-policy artifact is what makes D-IMPL-16's "no fast path for high-trust peers"
structural: the contract simply has no field a deployment could set to skip verification.
Output: `ccf.a2a.identity`, `ccf.a2a.trust_policy`, and their multi-peer tests.
</objective>

Create `src/ccf/a2a/identity.py` (plus `src/ccf/a2a/__init__.py`) as an algorithmic module
with the house header. Citation line: SDK-defined per CLAUDE.md §7.2, marked as an
extension; whitepaper §8.3 Pattern 4; D-IMPL-15.

Declare:
- `@runtime_checkable class IdentityProvider(Protocol)` with keyword-only methods for
  signing and verifying, plus whatever key-lookup surface the admission gate needs to
  resolve a `kid` to a public key. Bodies are `...`, never `pass`, never
  `raise NotImplementedError`. Include the house `runtime_checkable` caveat sentence.
  The docstring names what the Protocol omits: no transport, no L2 handle, no graph
  handle — identity is a pure algorithmic concern with no wire dependency.
- A typed `SignedContextProduct` contract: the canonical bytes plus the detached-JWS
  members. Research verified that `jws.detach_json_content()` yields exactly
  `{'signature', 'protected'}` with the payload travelling separately — model those two
  members explicitly rather than storing an opaque blob.
- A key-source Protocol (custody seam) and a **file-backed development** reference
  implementation behind it.
- The reference `IdentityProvider` implementation using `joserfc`:
  `jws.serialize_json({"protected": {"alg": "ES256", "kid": ..., "typ":
  "application/ccf-product+json"}}, canonical_bytes(product), key)` then
  `jws.detach_json_content(...)`; verification reattaches the base64url payload received
  and calls `jws.deserialize_json(reattached, public_key)`.
- Typed verification failures distinguishing at minimum: bad signature, unknown `kid`,
  and an algorithm other than the one the deployment declared.

**ES256 (P-256), not EdDSA.** `joserfc` refuses EdDSA by default with
`UnsupportedAlgorithmError` and emits a `SecurityWarning` about RFC 9864 deprecation even
with an explicit registry. Record that reason in a comment so a future contributor does
not "modernize" it back.

Do not hand-roll base64url detachment. `joserfc.jws.detach_json_content` is the one
function; hand-rolled detachment is where verification bugs hide, and D-13 makes this
path load-bearing for admission.

Docstring must state, in D-21 language, exactly what the shipped implementation provides
(genuine signing and verification with a file-backed development key source) and exactly
what it does not (PKI/HSM custody, which is deployment infrastructure per CLAUDE.md §13,
and channel security, which D-13 scopes out of v0). Do not write "secure by
construction". Key material, `kid` values, and algorithm identifiers that a deployment
chooses are values, not code constants — except the ES256 default, which is mechanism
justified inline.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Peer CCF fabric → consumer's Control Plane | An inbound product's asserted identity must be verified before anything trusts it |
| Deployment key store → IdentityProvider | Key custody; the v0 reference source is development-grade |
| Trust-policy artifact → admission decision | Configuration that bounds what a peer may assert, and must not be able to disable verification |

| T-06-31 | Tampering | Modified Context Product accepted as signed | mitigate | Signature is over the exact canonical bytes the content address is computed from; tamper-refusal test asserts a typed signature failure distinct from unknown-kid |
