## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 — Missing critical] A second control — `test_the_two_one_verdict_gates_read_the_same_predicate` — asserting by source that both gates read one predicate**

- **Found during:** Task 1, applying wave 1's question — *what weaker implementation would still pass this control?*
- **Issue:** The plan's `CONTROL 19` asserts that both gates refuse the doctored cell. **Two divergent inline copies of the union rule satisfy that assertion on the day they land**, because they are equivalent on the day they land. The plan's own threat register carries this as `T-21.1-04` with disposition **mitigate** — *"both call `cell_verdicts`; a second implementation is what lets a gate drift"* — and a mitigation that exists only as an implementation choice, with nothing standing to hold it, is this phase's defect class arriving through the fix rather than through the check.
- **Fix:** A test that reads the two gates' source via `inspect.getsource` and requires each to call `cell_verdicts(` and to contain no `BOLDED_RUN`. It carries its own anti-vacuity clause: the shared predicate is **required** to reference `BOLDED_RUN`, so the check cannot be satisfied by a module that deleted the bolded reading entirely.
- **Files modified:** `tools/docs_tests/test_requirement_ledger.py`
- **Verification:** Sabotage 3 above — the roster gate was given its own currently-equivalent copy of the union rule. **`CONTROL 19` stayed green; only this control went red.** It was also watched failing pre-fix at `3c8908e`, alongside `CONTROL 19`.
- **Committed in:** `3c8908e` (Task 1 commit — before the fix, per `D-IMPL-170`)

**2. [Rule 2 — Missing critical] `CONTROL 19` asserts its victim is in `WORKING_SET_ROSTER` before exercising the roster-scoped gate**

- **Found during:** Task 1
- **Issue:** The plan asks the control to assert `roster_rows_with_two_verdicts(doctored, WORKING_SET_ROSTER)` names `HARD-02`. If `HARD-02` were ever removed from that frozen roster, that half of the control would be quantified over a row the roster never reaches and would pass no matter what the gate did — failure mode 1, *the subject never reached the branch under test*, which is how two Phase 21 controls failed.
- **Fix:** `assert victim in WORKING_SET_ROSTER` first, with a message saying what a violation would mean about the control rather than about the ledger.
- **Files modified:** `tools/docs_tests/test_requirement_ledger.py`
- **Verification:** Passes at `3c8908e` and at `5de6857`, which is why the recorded pre-fix failure is the refusal that did not fire rather than a subject that was never reached.
- **Committed in:** `3c8908e`

**3. [Rule 2 — Missing critical] The mutation is derived from the row and refuses rather than mutating silently**

- **Found during:** Task 1
- **Issue:** The plan says to use `_doctored` and `_table_line` so the control does not depend on a literal cell string. That covers the *line*, not the *mutation*: a `status.replace("**Complete** (", …)` that matched nothing would hand the gates an unmodified document and then assert a refusal that never came.
- **Fix:** `_cell_with_an_unbolded_lead_and_a_later_bolded_verdict` derives the mutation from the parsed cell and **refuses** if the row's cell is not three cells, if its leading token is outside the vocabulary or already equals the verdict being inserted, or if its lead is not actually bolded. `CONTROL 19` then asserts on the *result* — `verdict_token(mutated) == "Complete"` and `"**Partial**" in mutated` — so a mutation that produced the wrong shape is caught rather than silently making the control vacuous.
- **Files modified:** `tools/docs_tests/test_requirement_ledger.py`
- **Verification:** All preconditions passed at `3c8908e`; the recorded failure is the gate's `[]`, not a broken subject.
- **Committed in:** `3c8908e`
