Define `SignalBatch(_VersionedArtifact)` in `artifacts.py` with two fields: `tenant_id: str`
and `envelopes: tuple[SignalEnvelope, ...]` with `min_length=1`. Pydantic parses each mapping
into a `SignalEnvelope` directly, which is the point — the artifact document adopts the SDK's
own field vocabulary (`source: {system_id: ...}`, `raw_payload:`) rather than the SDK growing
a second one to accommodate the document's.

**Record in the class docstring that this is a `role: load` artifact under D-IMPL-80.** It is
parsed and validated through the same `parse_artifact` seam as every other class, and
`load_and_boot` returns it to the caller on the boot result — but it is never passed to
`register_typed` and never appears in the pin set. State the reason, because the asymmetry is
the interesting part: registering a signal batch would content-hash raw event data into Control
Plane state, and by D-06's own rationale the registered artifact set is dimension 2 of the
five-dimension replay record. Re-authoring an events file would then change "what was in force"
exactly as a policy-bundle bump does, which is not what an event stream is. D-IMPL-80 makes the
distinction an explicit, required field on each manifest entry rather than a property an
executor has to infer from the class — and a manifest entry with no `role` is refused.

Record in the class docstring why the batch carries `tenant_id`: `SignalEnvelope.tenant_id`
is per-envelope in the contract, but every event in a batch belongs to one tenant and the
value lives in a different document today (`ontology.yaml:24`), which D-03 makes closed-world
over rules only. Carrying it on the batch keeps it authored, in one place, in the artifact
that needs it — rather than becoming a loader argument that no artifact records. Use a
`model_validator(mode="after")` to reject a batch whose envelopes disagree with the batch's
`tenant_id`, with a refuse-never-repair message under 200 characters. Do not silently stamp
the batch value onto envelopes that omit it — a stamped value is a value nobody authored.

Do not touch `SignalEnvelope` or `SourceIdentity`. `raw_payload` stays opaque to L1 and its
keys stay the source's vocabulary; renaming the *container* key in the document does not
touch that, and the docstring should say so.

Add the `#:`-commented constant `SIGNAL_BATCH = ArtifactClass(class_id="ccf.signal-batch", contract=SignalBatch)`,
add both names to `__all__`, and register in `SDK_ARTIFACT_CLASSES`.

The 20 example `events.yaml` files are NOT reshaped in this plan — each example rewrite
reshapes its own, so the change is reviewable alongside the code that reads it.

Define two more artifact contracts in `artifacts.py`, following the same five-part template.

**`PerspectiveArtifact(_VersionedArtifact, Perspective)`** — subclass the existing contract
so the fields are inherited verbatim, exactly as plan 15-08 did for the parameters models,
and the parsed artifact is directly usable where a `Perspective` is expected. Constant:
`PERSPECTIVE = ArtifactClass(class_id="ccf.perspective", contract=PerspectiveArtifact)`.

**`ProductClassDeclaration(VersionedArtifact)`** — declares `schema_name`,
`schema_version`, `ttl_anchor`, `assembly_mode`, `max_ttl_key`, and
`required_operator_keys: tuple[str, ...]` with `min_length=1`.

`required_operator_keys` is the field a projection's `required_operators()` returns, and naming
it here is what makes plan 15-13's instruction ("declare `required` from the artifact")
executable rather than an invitation to invent an unschema'd YAML key or hardcode a frozenset
in `run.py` — either of which would be a CINV-01 problem once the pattern spread across nine
examples. It lives on the product-class declaration rather than on a projection artifact
because the product class is the artifact that already declares what the product *is*, and the
operator set a projection requires is a property of the product, not of the code that computes
it. The docstring must state the property this exists to protect: the projection's declaration
and the engine's resolution must remain **two independent mechanisms**, because Gate 2 compares
them for strict equality — a projection returning the registry's own keys makes that comparison
a value against itself. Plan 15-21 Task 4 adds a standing AST guard against exactly that
shortcut. It **must not** declare
`max_ttl_version`: that pin is minted by registering the `MaxTTL` value
(`run.py:318-320`), the same shape D-IMPL-76 ruled on for the policy bundle. The class
docstring states this and states why it is safe for Gate 3: the TTL ceiling stays an
authored artifact value, the pin is derived from registering it, and the product's own
`expires_at` remains a separately authored number — which is the independence Gate 3 checks.
Constant id: `ccf.product-class`.

Add all four names to `__all__` and register both constants in `SDK_ARTIFACT_CLASSES`.

Do not add a helper that calls `register_product_class` for the adopter in this plan; the
manifest entry point (plan 15-10) owns registration, and a second registration path would
make "what was in force" answerable from two places.
