<objective>
Replace the eleven hand-written lines before every `boot()` call with one manifest-driven
call that returns the fabric handle and the pins.

Purpose: D-05/D-06/D-08. `boot()` is already well-shaped — no defaults, no "latest", because
a fabric whose configuration drifts between boots cannot be replayed — and its contract is
preserved verbatim. What changes is what *produces* the pins. The manifest enumerates every
artifact explicitly because the set of Control Plane artifacts in force is dimension 2 of the
five-dimension replay record; a glob would make that set a function of directory contents at
boot time, with no artifact recording that a dropped-in file changed what was in force.

The governance risk this plan is most exposed to is the entry point growing past wiring —
the next obvious convenience, *and also runs the operators*, would swallow `engine_resolved`
and make lineage strict equality tautological. Plan 15-02's guard and lint ban stand against
exactly that; this plan must not weaken them.

Output: the manifest contract, the entry point, a plain pin record, and the tests that pin
determinism, glob refusal, and the loud Postgres failure.
</objective>

like `pins.policy_bindings()` would turn the adopter's `build_replay_record(policy_bindings=...)`

Implement in `manifest.py`:

```
def load_and_boot(
    manifest_path: str | Path,
    *,
    registry: ControlPlaneProtocol,
    database_path: str | None = None,
    postgres_dsn: str | None = None,
    tenant_id: str | None = None,
) -> BootedFabric
```

returning `BootedFabric` — a frozen dataclass (not a `CCFContract`; it carries a live handle,
which has no canonical serialization, the same reasoning `ArtifactClass` records at
`artifacts.py:103-106`) with four attributes: `handle: FabricHandle`, `pins: ResolvedPins`,
`tenant_id: str`, and `artifacts: Mapping[str, CCFContract]`.

**`artifacts` is D-IMPL-80's return path and it carries every parsed artifact keyed by manifest
key, both roles.** The ruling requires that `role: load` entries come back to the caller rather
than being registered; returning the `register`-role ones alongside them costs nothing and
closes a second gap. Without it, an adopter who needs the four parsed operator-parameters
artifacts to hand to `build_operator_registry` would have to re-read them off disk or
`isinstance`-filter them out of the registry — and that filtering idiom, copied across nine
examples, would be a new duplication class of exactly the sort this phase exists to remove.
With it, the adopter writes `{key: booted.artifacts[key] for key in (...)}`, naming its own
manifest keys, which is explicit deployment configuration rather than type introspection.

State the invariant this does **not** weaken, in the attribute's docstring: `role` governs
registration and pinning, never visibility. A `role: load` artifact appearing in `artifacts` is
still absent from `pins`, still absent from the Control Plane registry, and still absent from
replay dimension 2. `artifacts` is a parse result handed back to the caller; `pins` is the
record of what was put in force.

Behavior, in order:

1. Read the manifest file's text and parse it via `load_artifact(text, DEPLOYMENT_MANIFEST)`.
   Route through `load_artifact`, never `yaml.safe_load` — the CLI's `load_document` helper
   bypasses D-02's suppressed resolver and must not be copied here.
2. Resolve `tenant_id`: exactly one of the manifest field and the argument must be present;
   refuse both-absent and refuse a conflicting pair, with messages in the house
   refuse-never-repair phrasing.
3. For each manifest entry in declared order: resolve the path relative to the manifest
   file's own directory (never `cwd`), read it, and `load_artifact` it against
   `resolve_artifact_class(entry.class_id)`. Put every parsed artifact into the `artifacts`
   mapping under `entry.key`, regardless of role. Then branch on `entry.role`, per D-IMPL-80:
   - `register` — call `registry.register_typed(entry.key, artifact, artifact_class)`, the
     existing mechanism for exactly this job, currently unused by any example, and collect the
     returned version into an `ArtifactPin`.
   - `load` — do nothing further. No `register_typed`, no `ArtifactPin`. A comment states that
     this branch is D-IMPL-80 and that adding a registration here would put raw signal data
     into replay dimension 2.

   **Parse every entry before registering any of them.** Run the read-and-parse loop to
   completion first, then the registration loop. A malformed document at entry seven would
   otherwise leave entries one through six registered — partial Control Plane state produced by
   a deployment that never booted. Two-phase ordering makes the common failure (a bad document)
   leave the registry untouched. State in the docstring what is still *not* guaranteed: a
   failure inside the registration loop itself — a backend error, say — can still leave earlier
   entries registered, and that is accepted rather than papered over, because registration is
   content-addressed and audited, so a re-run registers the identical content to the identical
   version and the audit log shows both attempts. Do not add a rollback; a Control Plane that
   silently un-registers is worse than one that records a retry.
4. Never call `resolve_latest`. That is the "latest" `boot()` refuses, and its absence from
   this module is asserted by a test.
5. Never construct a `ControlPlaneRegistry`. The registry is a caller argument so the
   adopter keeps one audit sequence; a registry built behind the adopter's back would split it.
6. Call `boot()` with `resolution_spec_key`/`resolution_spec_version` and
   `policy_bundle_key`/`policy_bundle_version` read from the collected pins, and with exactly
   one of `database_path`/`postgres_dsn` per the manifest's declared `backend`. If `backend`
   is `postgres` and no `postgres_dsn` is supplied, raise — loudly, naming the manifest's
   declaration and the missing argument. **Never** fall back to SQLite: a fabric that guessed
   its substrate could boot against a development file in production and still pass every test.
   If `backend` is `sqlite` and no `database_path` is supplied, raise the same way.

State in the function docstring what this call does **not** do, so the abstraction line is
legible from the surface itself: it does not execute operators, does not project, does not
build a Context Product, does not call `run_gates`, and does not construct a `ProductLineage`.
The adopter reads `pins` and passes them to `build_replay_record` themselves — D-06 requires
that line to stay in adopter code.

Export `load_and_boot`, `BootedFabric`, `DeploymentManifest`, `ManifestEntry`,
`ResolvedPins`, and `ArtifactPin` from `ccf.deployment.__all__`, and extend the package
docstring's `:mod:` list.

State in the function docstring the day-1 shape of what follows the call, so plan 15-13 is
writing down a spine this module already describes rather than inventing one: the adopter

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| manifest file → Control Plane registry | An adopter-authored document determines what is in force |
| deployment environment → boot substrate | The DSN crosses from the environment and is never persisted |
| entry point → L3 | Nothing may enter the graph except through L2 |
