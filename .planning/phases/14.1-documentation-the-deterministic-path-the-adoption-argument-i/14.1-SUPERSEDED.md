# Phase 14.1 — SUPERSEDED

**Superseded:** 2026-08-03, during `/gsd:discuss-phase 14.1`, before any plan was written.
**Superseded by:** Phase 16 (documentation rewrite), which follows Phase 15 (SDK ergonomics).
**Authority:** Dave.

## What happened

The discussion opened on how to fix UAT gap G-01 — the adopter's guide teaching an
agent-first mental model for an agent-optional capability. Dave supplied the document
structure he wanted, and then raised a third concern that changed the phase:

> "I can't tell from looking at the code which code is example code and which code is
> required by the CCF. Overall it seems like a lot of code a developer has to write to
> integrate with CCF. What am I missing here?"

Measured against `examples/00-quickstart/run.py` (451 lines):

| What | Lines | Whose code |
|---|---|---|
| CI assertions + print summary | ~85 | Nobody's — harness, but inside published snippets |
| YAML→typed-object marshalling (`_resolution_spec`, `_envelopes`, four operator parameter sets) | ~105 | The SDK's, but shipped as example code |
| `QuickstartPlan` — the projection Π | ~45 | Genuinely the deployment's (whitepaper §7.5) |
| The CCF call spine, L1→L6 | ~55 | The deployment's, and small — ~8 calls |
| Docstring, imports, `_load`/`_instant` | ~90 | Scaffolding |

`src/ccf/controlplane/artifacts.py` registers exactly two artifact classes with a
declarative parse path (`ccf.half-life-table`, `ccf.debt-profile`). Every other artifact
shape is hand-marshalled in `/examples`. The No-Hardcoding Rule (CLAUDE.md §6.4) pushed the
*values* into artifacts and left most of the *interpreters* outside `/src` — the inverse of
what §6.4 states ("code contains interpreters and factories, never the things interpreted").

Dave's ruling: fix the surface before documenting it.

> "The whole purpose of the SDK is to provide as much abstraction around details as possible
> and save me the time of doing them manually. I would like to tackle this problem first
> before anything else… I don't care if we wind up changing the documentation and example
> code to show a more streamlined version of how to use the CCF SDK."

## Rulings taken in this discussion

1. **Sequencing** — Phase 14 closes as-shipped; Phase 15 = SDK ergonomics; Phase 16 = the
   documentation rewrite, absorbing every 14.1 success criterion.
2. **API latitude (D-15B)** — free rein, pre-1.0. Phase 15 may reshape, rename, collapse, or
   remove any public surface; examples and docs follow. `v0.1.0` stays tagged as history.
3. **Abstraction line (D-15A)** — marshalling and wiring only. Every point where a deployment
   asserts something the fabric then verifies stays explicit in adopter code. Dave reserves
   the right to revisit surface by surface.
4. **Docs note** — roadmap-internal only. No provisional banner on the published site.
5. **Guide structure (→ Phase 16)** — one document, two sections: Section 1 deterministic
   assembly + external MCP consumption (the day-1 pattern, several worked instances);
   Section 2 CCF-agent assembly + external consumption over MCP *and* A2A.
6. **Example domain (→ Phase 16)** — banking-specific, drawn from the whitepaper's own
   scenarios, on simulated data as the suite already uses.
7. **Snippet legibility (→ Phase 16)** — re-cut markers so CI assertions and print summaries
   fall outside every published snippet, and isolate the CCF call spine from deployment code.

## Findings that survive into 15 and 16

- **A2A is already demonstrated.** `examples/04-cross-process` runs a `ContextAssemblyAgent`
  in its own subprocess, serves one product over MCP *and* A2A, verifies Control Plane
  admission, and exercises a tampered-envelope refusal path. Phase 16's Section 2 is
  narration, not new example code — but its domain is property situational assembly and is
  re-domained to banking in Phase 15.
- **Criterion 5's external example exists.** `examples/external/00-hello-context` is already
  a banking credit-context fabric with four zero-CCF-import consumer legs (bare MCP,
  Anthropic SDK, Google ADK, and Claude Desktop via `.mcp.json`), CI-asserted.
- **The invariant that bounds abstraction.** `run_gates()` takes the engine's resolved
  operators separately from the product's own lineage claim so strict equality has two
  independent sources. A helper computing both from one input makes the gate tautological.
  This is the worked example of D-15A's line, and the test any proposed helper must pass.
