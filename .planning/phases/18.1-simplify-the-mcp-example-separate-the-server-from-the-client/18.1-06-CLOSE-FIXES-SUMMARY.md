# Phase 18.1 Close Fixes: The Three Blocking Findings Summary

Three BLOCKING findings from the close review closed in-phase per CLAUDE.md §3.1 —
an untested limb of the phase's one new mechanism, a refusal that named the wrong
mistake and gave destructive advice, and a README claim credited to a gate that did
not hold it. Every fix carries the sabotage control that proves it.

Each finding had already been CONFIRMED by measurement against the tree before this
work began. Nothing here is speculative, and nothing advisory was touched.

## What Was Built

### Finding 1 — `D-18`'s equality limb now has a witness

`binding_document.py:731` is a disjunction:

```python
if server == root_path or root_path in server.parents:
```

Both existing `D-18` tests wrote `f"{deployment_root.name}/projection.py"` — a path
resolving *strictly under* the root, which satisfies the second limb alone. Removing
the first limb left 752 tests green. Half the predicate of the phase's **one** new
piece of SDK mechanism was unmeasured.

The mechanism was correct; the test was missing. `test_binding_document_refuses_a_server_that_is_the_deployment_root_itself`
feeds `server: <root-name>` with no trailing component, so the value resolves to the
root **itself** — which is outside `server.parents`, since a directory is never among
its own parents — and only the equality limb can refuse it. The test asserts on the
resolved path (`resolves to <root>, which is inside the`) so that a fixture drifting
back into `parents` territory is reported rather than silently re-covering the limb
the other test already covers.

The docstring records *why the limb matters to an adopter*, not only that it is
uncovered: without it the loader accepts a directory as a program, and the only check
left standing is `mcp_stdio`'s `is_file()`, whose message is *"names no server program
… which is not a file"* — a missing-file report for a value Amendment A.3 rules out by
name. That is the `B0b` class this phase's own `D-08` cites.

**No production code changed for this finding.** The mechanism was already right.

### Finding 2 — a spaced root path is no longer told to delete half of itself

Reproduced end-to-end before the fix:

```
McpStdioAdapter("/tmp/My Deployments/deployment")._declared()
-> `/tmp/My Deployments/deployment` states two tokens; … The second token was
   the server program … so drop it from the address and name the root alone
```

Following that instruction yields `mcp+stdio:/tmp/My`. Spaces in paths are ordinary
on macOS and Windows. The module docstring has stated since `18.1-02` that quoting is
the remedy; no message an adopter actually reads said so.

**The distinguishing work.** An unquoted spaced path and the pre-migration two-token
address are identical by token *count*, so the count is no longer what decides which
mistake is reported. A wrong count now asks the filesystem whether the **whole**
address names a directory that exists:

- **It does** → one path that needed quoting. The refusal shows the quoted string
  whole (`mcp+stdio:'/tmp/My Deployments/deployment'`) and says explicitly that this
  is *not* the pre-`18.1-02` address and there is nothing here to drop.
- **It does not** → `D-07`'s migration message stands **unweakened**. An adopter
  moving off the two-token grammar is still told where their program went.

Both count branches also gained a quoting clause, so a spaced path that does not yet
exist on disk is still pointed at the right remedy rather than only at the wrong one.

`os.path.isdir` rather than `Path.is_dir` deliberately: it answers `False` for a
string the platform cannot use instead of raising, so a grammar branch does not
become a new way out of the documented `BindingError` contract. The emptiness guard
is load-bearing too — `Path("")` is `Path(".")`, which *is* a directory, so a blank
address would otherwise have been told to quote the current working directory.

The grammar taxonomy went from five refusals to six. `SIGNATURES`, the pairwise
distinctness leg, the section banner and the module docstrings all name the sixth;
the distinctness leg's `set(messages) == set(SIGNATURES)` assertion made that
mandatory rather than optional.

A **positive leg** was added because the refusal now prescribes a remedy: a quoted
spaced root is driven through `ProductClient.ask` and asserted to serve a real
content address. Advice that nobody ran is a guess.

### Finding 3 — the README's claim and the purity gate, written against each other

Ruled by Dave (2026-08-19): fix **both** halves.

`README.md:51-54` credited `test_every_documented_command_names_a_distinct_binding_scheme`
with checking that the two commands *"differ by one word, the scheme"*. The test
asserted only that the two `CCF_BINDING` tokens are **distinct** and that everything
**after** the assignment is **identical**. It never compared the two addresses.
Measured: repointing the documented mcp address at a nonexistent `…/OTHERDEPLOYMENT`
in both README and Makefile left all 17 purity tests green. `D-15`'s whole observable
rested on a property no gate held.

**(a) The gate.** A third leg — the address *after* the scheme is the same string in
both. The split is done by a module-level `scheme_and_address()` taking its subject as
a parameter, in this suite's established shape, so the vacuity case is measurable:
`len(addresses) == 1` is satisfied by `{""}` just as well as by one real address.
Five malformed shapes (no assignment, wrong variable, no separator, empty address,
empty scheme) are fed to the **shipped** splitter and watched refusing. The
distinct-scheme leg is now asserted on the scheme itself rather than inferred from the
whole token, and both original assertions are kept.

**A correction to the review's own suggested fix, recorded because it would have
shipped a vacuous assertion.** Both the single-agent review (WR-07) and this task's
brief proposed:

```python
addresses = {binding.partition(":")[2].partition(":")[2] for binding in bindings}
```

Measured on these tokens: `CCF_BINDING=inprocess:examples/…/deployment`. The first
`partition(":")` yields `("CCF_BINDING=inprocess", ":", "examples/…/deployment")`; the
second, applied to a remainder containing **no colon**, yields `""`. Both commands
produce `""`, so `len(addresses) == 1` passes on the empty set and the strengthened
gate would have held exactly nothing — the same defect one layer deeper. Rejected and
replaced with an `=`-then-`:` split plus the non-emptiness guard.

**(b) The prose.** `README.md:51-54` rewritten to state precisely the three things the
strengthened test asserts — different schemes, same address, identical remainder — and
no more. It does not overstate the new assertion, and it no longer credits the test
with a comparison it does not make.

**Naming decision.** `test_every_documented_command_names_a_distinct_binding_scheme`
now checks three things and its name says one. The name was **kept**: five planning
documents in this phase's own record cite it verbatim (`18.1-04-PLAN.md`,
`18.1-VERIFICATION.md`, `18.1-RESEARCH.md` ×3, `18.1-PATTERNS.md`,
`18-D-IMPL-150-SUMMARY.md`), and renaming would strand the traceability the phase
record depends on. The name remains true, only incomplete; the docstring and the
README both carry the full statement.
