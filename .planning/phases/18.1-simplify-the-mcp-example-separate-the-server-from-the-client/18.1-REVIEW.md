### CR-01 (BLOCKING): D-18's `server == root_path` limb is guarded by no test

**File:** `src/ccf/client/adapters/binding_document.py:731`
**Test gap:** `tests/client/test_binding_document.py:850-869`,
`tests/client/test_data_only_deployment.py:443-475`

The refusal is a two-limb disjunction:

```python
if server == root_path or root_path in server.parents:
```

Both D-18 tests exercise only the **second** limb — they write
`f"{deployment_root.name}/projection.py"`, which resolves *strictly under* the
root. Nothing anywhere writes a value that resolves to the root **itself**
(`server: deployment`).

**Proven by sabotage.** Replacing the line with `if root_path in server.parents:`
and running `pytest tests/client tests/examples/test_hw1_two_transports.py`:

```

```

The phase's *one* new piece of SDK mechanism ships with half of its predicate
unmeasured. This is the recorded shape the brief warns about — an assertion
sitting below a disjunction, where satisfying one branch passes. It is also the
`assert_one_python_module` standard (`!= 1`, never `> 1`) not being met by the
check that cites it.

Concretely, under the sabotage `server: deployment` is accepted, `_contained`
passes it (the root is under the parent), and the only thing left standing is
`mcp_stdio`'s `is_file()`, which reports *"names no server program … which is not
a file"* — a message about a missing file for a value that was ruled out by name.

**Fix:** add a limb to `test_binding_document_refuses_a_server_reaching_back_inside_the_deployment`:

```python
    deployment_root: Path, inward: str

    ...
```

### CR-02 (BLOCKING): a deployment root containing a space is diagnosed as the pre-migration two-token address, with destructive advice

**File:** `src/ccf/client/adapters/mcp_stdio.py:257-274`

`_declared()` splits with `shlex.split` and then branches on the token **count**
alone. A root path with exactly one space yields exactly two tokens and lands in
D-07's migration branch:

```
$ CCF_BINDING="mcp+stdio:/tmp/tmpiubvqtm7/My Deployments/deployment"

`/tmp/tmpiubvqtm7/My Deployments/deployment` states two tokens; an `mcp+stdio`
address states one — the deployment root, as in `mcp+stdio:./deployment`. The
second token was the server program, and that program is now the deployment's
own `server:` key in its `binding.yaml`, so drop it from the address and name
the root alone
```

(Reproduced end-to-end through `ProductClient.for_product(...).ask(...)`.)

The adopter never had a server program in the address. Following the instruction —
"drop it from the address and name the root alone" — produces
`mcp+stdio:/tmp/tmpiubvqtm7/My`, which is strictly worse than what they typed.
A three-space path lands in the generic `!= 1` branch with the same problem.

**Neither** the `== 2` branch nor the `!= 1` branch mentions quoting. Only the
`shlex` `ValueError` branch (`:252-256`) does — and an unbalanced-quote error is
not the failure a user with a space in their path hits. The module docstring
(`:10-11`) states quoting is the remedy — *"parsed with `shlex.split` so a path
containing a space can still be quoted"* — but no message an adopter actually
reads says so.

This is precisely the class D-08 was ruled for: *"whose message would describe
something other than the mistake actually made — the report-quality class that
`B0b` was fixed for."* It is a missing element of this phase's own stated
deliverable, not a nitpick.

**Fix:** one clause in both messages:

```python
if len(tokens) == 2:
    raise BindingError(
        f"`{self._address}` states two tokens; an `{SCHEME}` address"
        " states one — the deployment root, as in"
        f" `{SCHEME}:./deployment`. If the root's path contains a space,"
        " quote it: `mcp+stdio:'/path/with a space/deployment'`. Otherwise"
        " the second token was the server program, and that program is now"
        f" the deployment's own `server:` key in its {BINDING_DOCUMENT_NAME},"
        " so drop it from the address and name the root alone"
    )
```

and the equivalent sentence in the `!= 1` branch. Add a control to
`tests/client/test_mcp_stdio_adapter.py` driving a root under a `tmp_path`
directory with a space in its name.

### WR-01 (ADVISORY): a declared-but-blank `server:` is reported as absent, telling the adopter to add a key that is on their screen

**File:** `src/ccf/client/adapters/binding_document.py:714`

```python
if declared_server is not None and str(declared_server).strip():
```

`server: ""` and `server: "   "` are silently coerced to `None`. The transport
then says:

```
…/binding.yaml declares no `server:`, so this deployment states no program to
launch and cannot be reached over `mcp+stdio`. Add `server:` naming its MCP
server program…
```

while the document on disk states `server: '   '`. Reproduced end-to-end.

The loader's own standard for the same input on a required key is the opposite —
`:636-643` refuses a blank value with an explicit *"{document} omits `config`"*.
`server:` is the only path-valued key where a blank value is silently reinterpreted
as an intentional omission.

**Fix:** refuse the blank case by name before the absence case:

```python
if declared_server is not None and not str(declared_server).strip():
    raise BindingError(
        f"`server:` in {document} states an empty value. Omission is a"
        " positive statement — a deployment reached at an endpoint launches"
        " nothing and states no `server:` at all — but a blank one is an"
        " unfinished edit. Remove the key or name the program"
    )
```

### WR-02 (ADVISORY): a non-string `server:` is coerced by `str()`, and the fixture's own comment invites the shape that breaks

**File:** `src/ccf/client/adapters/binding_document.py:716`
(`str(declared_server)`), aggravated by
`tests/client/fixtures/deployment/binding.yaml:78-79`

Measured against the real loader:

| `server:` value | result |
| --- | --- |
| `{path: x.py}` | ACCEPTED → `<parent>/{'path': 'x.py'}` |
| `[a.py]` | ACCEPTED → `<parent>/['a.py']` |
| `123` | ACCEPTED → `<parent>/123` |
| `true` | ACCEPTED → `<parent>/True` |

The aggravating factor is unique to this key: the fixture's own teaching comment
says

> `# this deployment. Sibling in spirit to the `{path: …}` form below: a location`

and `connection.database_path` genuinely accepts a `{path: …}` mapping. An
adopter following that sentence writes `server: {path: server/serve.py}`, gets it
accepted by the loader, and is then told *"names no server program — it resolves
to `<parent>/{'path': 'server/serve.py'}`, which is not a file."* A report about
a missing file for a type error.

The loader type-checks every other structured key (`operator_parameter_keys` at
`:690-695`, `question`/`perspective`/`debt` through `_mapping`), so this is the
established standard not being applied to the new key. CLAUDE.md §11 —
*"Typed contracts at every boundary. Validation is at the boundary, never
deferred."*

Note: `config:` and `artifact_store:` share the `str()` coercion, so this is a
class the new key joined rather than one it invented — but only `server:` has a
comment inviting the mapping form.

**Fix:** `if not isinstance(declared_server, str): raise BindingError(…)` naming
`server:` as a single path and pointing at D-04.

### WR-03 (ADVISORY): a NUL byte in any path-valued key escapes the documented `BindingError` contract

**File:** `src/ccf/client/adapters/binding_document.py:425`

`server: "a\0b"` (legal in a double-quoted YAML scalar) produces:

```
ValueError: embedded null byte
```

from `Path.resolve()`, not a `BindingError`. `load_binding_document`'s own
`Raises:` block (`:565-573`) commits to `BindingError` for *"names a path outside
itself"*, and `ProductClient.ask`'s contract is that every binding failure is a
`TransportError` (which `BindingError` inherits). A caller writing the documented
single `except` clause does not catch this.

Pre-existing for `config:`/`artifact_store:`; reported because the new key joined
the class and because the loader is the only place it can be fixed once.

**Fix:** wrap the resolve in `_contained`:

```python
try:
    resolved = (root / written).resolve()
except (ValueError, OSError) as unusable:
    raise BindingError(
        f"`{key}: {candidate}` in {document} is not a usable path —"
        f" {unusable}"
    ) from unusable
```

### WR-04 (ADVISORY): nothing distinguishes the correct `Path.parents` containment from a naive string prefix

**File:** `src/ccf/client/adapters/binding_document.py:731` (and `:426`)
**Test gap:** whole of `tests/client/`

The shipped code is **correct**. Nothing holds it correct.

**Proven by sabotage.** Replacing `:731` with
`if str(server).startswith(str(root_path)):` and running `pytest tests/client`:

```
371 passed in 26.45s
```

Under that regression, a deployment at `.../holder/deployment` declaring a
legitimate sibling `deployment-tools/serve.py` is wrongly refused with

```
… resolves to /…/holder/deployment-tools/serve.py, which is inside the
deployment root /…/holder/deployment
```

Every fixture root in the suite is named `deployment` and every sibling is
`stdio_server.py` / `broken_server.py` / `server/`, so no name in the corpus is a
prefix-extension of a root. The one property that makes the unusual parent base
safe has no witness.

**Fix:** one limb in the sibling test, and one in the acceptance test:

```python
def test_a_sibling_whose_name_extends_the_roots_is_not_inside_it(
    deployment_root: Path,
) -> None:
    """A prefix is not a parent — `Path.parents`, never `str.startswith`."""
    sibling = deployment_root.parent / f"{deployment_root.name}-tools"
    sibling.mkdir()
    (sibling / "serve.py").write_text("", encoding="utf-8")
    body = _document(deployment_root)
    body["server"] = f"{sibling.name}/serve.py"
    _rewrite(deployment_root, body)

    assert load_binding_document(deployment_root).server == (
        sibling / "serve.py"
    ).resolve()
```

### WR-08 (ADVISORY): the trust posture shifted and the docstring justifying `env=dict(os.environ)` predates it

**File:** `src/ccf/client/adapters/mcp_stdio.py:343-368`

Before this phase, the program `mcp+stdio` executes was named by the operator in
`CCF_BINDING`. It is now read from `server:` inside the deployment directory —
i.e. from data the deployment author controls — and executed under `sys.executable`
with the client's **entire** environment:

```python
parameters = StdioServerParameters(
    command=sys.executable,
    args=[str(program), str(root)],
    env=dict(os.environ),
)
```

The docstring's justification is *"A deployment's server program is the
deployment's own code reaching the same SDK, the same substrate settings and the
same credentials the client resolved; it is not a third-party server whose
environment should be curated."* That sentence was written when the operator
typed the program path. It now reads as a claim about a path the operator has
not seen.

Containment bounds the blast radius to the subtree of the deployment root's
**parent** (arbitrary depth), which is meaningful but wider than the deployment
itself. Pointing `CCF_BINDING` at an untrusted deployment root is now sufficient
for the deployment author to run code of their choosing with the client's full
environment, including credentials.

This is not a defect in the ruling (D-01/D-04 chose it deliberately, and stdio
always ran the deployment's program) — it is an undocumented change of posture in
a security-relevant docstring. Related: the `A5` advisory carried forward from
Phase 18 (*stdio auth is impersonation, not verification*) now compounds with it.

**Fix:** one paragraph in the `_call` docstring stating that since 18.1-02 the
program is the *deployment's* declaration rather than the caller's, that a client
therefore trusts the deployment root it is pointed at to the same degree it
trusts an executable, and that containment to the holding directory bounds but
does not eliminate that. No code change.
