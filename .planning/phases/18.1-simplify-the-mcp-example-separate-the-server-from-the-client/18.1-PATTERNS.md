### 1. `examples/hw1-companies-over-revenue/server/compose.py` — NEW (composition, boot → typed bundle)

**Naming — `compose.py` endorsed, with the reasoning the orchestrator asked for.**

Basename collision counts re-measured this session (excluding `.git`, `.venv`):
`compose.py` **0**, `fabric.py` **0**, `assemble.py` **0**, `wiring.py` **0**, `boot.py` **1**,
`deployment.py` **2**, `composition.py` **2**, `resolver.py` **1**, `run.py` **11**.
RESEARCH.md's counts are confirmed exactly.

The **established idiom** for a second, non-entry-point module beside an example program is a
plain noun naming what the module *is*: `deployment.py` (`examples/s1-00-…`, `s1-01-…`),
`spine.py`, `produce.py` / `consume.py`, `report.py`, `source_estate.py`, `producer_child.py`.
No example uses a verb-suffix or a `_helpers`/`_util` name anywhere in `examples/`.
`compose.py` fits that idiom (it is what D-11 named the cut), is collision-free, and avoids
all three landmines: `run.py` (it is `EXAMPLE_ROOT_MARKER`, `test_artifact_schema_headers.py:159`,
matched by an **rglob** at `:206`), `boot.py` (ambiguous basename → `tools/lints/citations.py`
**drops** ambiguous-basename citations rather than checking them), and `resolver.py` (CONTEXT's
own exclusion — `binding.yaml` refuses a `resolver:` key by name).

The one alternative worth naming: **`deployment.py` is the strongest *idiom* match** but is
disqualified here by position — a `server/deployment.py` sitting beside `deployment/` would read
as a second deployment root. Record the rejection; do not re-litigate it in execution.

### 6. The four D-05/06/07/08 refusal controls — placement confirmed, with a real caveat

**Placement: `tests/client/test_mcp_stdio_adapter.py` — RESEARCH's A4 is correct.** That module
already owns the adapter's refusal taxonomy (its docstring, `:1-30`, enumerates *"four ways this
transport can fail to produce an answer"*), already carries `pytestmark = pytest.mark.crossproc`

`config_document`, `seed` from `tests.client.conftest` and `STDIO_SERVER` from
`tests.client.fixtures` (`:47-48`).

**The caveat RESEARCH does not name.** That module has **zero** `CCF_BINDING`, zero
`monkeypatch`, and zero `ProductClient.for_product` today — grep confirms. Every ask goes
through `_ask` (`:113-123`), which constructs `McpStdioAdapter(...)` **directly**. Its module
docstring even says at `:25`: *"None of them monkeypatches the adapter."* So the env-var driver
is not a helper the module can call; it must be **added**, and the docstring sentence at `:25`
must be checked for whether it now reads as false (it does not — it says *monkeypatches the
adapter*, and `monkeypatch.setenv` does not — but a reviewer will stop on it, so say so in the
plan).

**The pattern to add — `tests/client/test_data_only_deployment.py:177-188`, verbatim:**

```python

    """A client reaching ``root`` through ``CCF_BINDING`` and nothing else.

    The environment variable rather than ``binding=`` on purpose: ``D-04``

    the environment, so an end-to-end test that passed the address in code
    would be exercising a path an adopter does not take.

        str(config_document(root)["product_class"]["schema_name"])
    )
```

Note `SCHEME` is imported from the adapter module, never spelled — matching
`mcp_stdio.py:130-132`'s *"Written once, so the registry entry, the refusal messages and the
tests all say the same string."* The mcp variant sets `f"{SCHEME}:{root}"` with `SCHEME`
already imported at `test_mcp_stdio_adapter.py:38`.

`monkeypatch.setenv("CCF_BINDING", f"{SCHEME}:{bad_remainder}")` and keep `for_product` +
`.ask(...)` unchanged, so the only thing varying across the four is the string an adopter would
have typed.
