# Phase 18.1 Plan 05: The Second Sweep, and the Close — Summary

**D-19's second sweep ran after this file was written, cleared the phase's one
dispositioned red, and found three stale rows rather than the four Plan 04 predicted —
because a SUMMARY only earns a planning-tree row if it names a retiring path, and
`18.1-04-SUMMARY.md` names none.**

## The ordering, stated plainly

**This SUMMARY was written before the sweep ran.** That is the entire reason Plan 05
exists as a plan of its own rather than as a last task of Plan 04: the sweep walks the
repository including `.planning/`, so a sweep that runs before the last SUMMARY is
written commits a report that is stale the moment that SUMMARY lands. It happened twice
already in this phase — wave 2's SUMMARY re-staled the report after wave 2's own sweep,
and wave 3's did the same — which is what `.planning/STATE.md:199-201` records as
discipline: *"RETIREMENT-COUPLINGS.md sweeps the planning tree including a plan's own
SUMMARY — write the SUMMARY first, then re-sweep."*

The residual case that ordering alone does not solve is that **the sweep's own figures
have to be written into the SUMMARY the sweep already walked.** This plan handles it
explicitly rather than hoping: the measured section below was appended after the first
run, and the sweep was then re-run so the committed report reflects the final bytes of
this file, and re-run a third time to confirm the render had reached a fixed point. The
convergence check is recorded with the figures, not asserted.

## The prediction, written before the tool ran

The diff was predicted in full before `--report` was invoked, so that the regeneration
would be a *measurement* rather than an acceptance of whatever the renderer emitted.
Prediction, in full:

| # | Predicted change | Family |
|---|---|---|
| 1 | the `server/serve.py` coupling row moves from line `68` to line `31` | example-tree line move |
| 2 | a new excluded row for `18.1-02-SUMMARY.md`, count **2** | planning tree |
| 3 | a new excluded row for `18.1-03-SUMMARY.md`, count **3** | planning tree |
| 4 | a new excluded row for **this** SUMMARY, count as measured below | planning tree |
| — | `Coupling rows: 234 across 75 files` **unchanged** | summary figures |

The basis for each, before the run:

- **The `serve.py` row.** `grep -n "04-cross-process" examples/hw1-companies-over-revenue/server/serve.py`
  returns line **31** on the tree as it stands; the committed report says **68**. That is
  exactly the second-order coupling `18.1-VALIDATION.md` predicted and `18.1-03-SUMMARY.md`
  recorded as `serve.py:68 -> :31`.
- **The planning-tree rows.** The excluded table lists a file with the *number of
  retiring-path references it contains*. Counting the 29 scheduled retiring paths as
  literals across every Phase 18.1 planning file reproduces the three counts already in
  the committed report exactly — `18.1-03-PLAN.md` 1, `18.1-PATTERNS.md` 1,
  `18.1-RESEARCH.md` 2 — which is what makes the same count trustworthy for the files not
  yet listed.
- **The summary figures.** Every `.planning/` file is excluded from *assignment*
  (`EXCLUDED_FROM_ASSIGNMENT` carries the `.planning/` prefix), so planning-tree
  references never enter the `Coupling rows` count. The `serve.py` change moves a row's
  line number without adding or removing a row. Nothing else in this phase touched a
  file under a swept, assignable tree.

## The correction: three stale rows, not four

`18.1-04-SUMMARY.md` closed with:

> **`18.1-05` should expect a FOURTH once this SUMMARY commits** — `18.1-04-SUMMARY.md`
> will add its own planning-tree row on the same pattern. A sweep that finds three has
> run too early.

**That prediction is wrong, and it is wrong in the direction that would have made this
plan chase a row that does not exist.** The pattern it generalized from is not "a SUMMARY
adds a row"; it is "a SUMMARY that *names a retiring path* adds a row". Measured across
all 29 scheduled retiring paths, as literals, over every Phase 18.1 planning file:

| File | Retiring-path references |
|---|---:|
| `18.1-01-SUMMARY.md` | 0 |
| `18.1-02-SUMMARY.md` | **2** |
| `18.1-03-SUMMARY.md` | **3** |
| `18.1-04-SUMMARY.md` | **0** |
| `18.1-01-PLAN.md` … `18.1-05-PLAN.md` | 0, except `18.1-03-PLAN.md` = 1 |
| `18.1-CONTEXT.md`, `18.1-VALIDATION.md` | 0 |
| `18.1-RESEARCH.md` | 2 |
| `18.1-PATTERNS.md` | 1 |

`18.1-01-SUMMARY.md` also contributes nothing, for the same reason, and it too is absent
from the committed excluded table — a second independent confirmation of the rule. The
three files already listed match their committed counts exactly, so the method is checked
against known values before being trusted on unknown ones.

So: **`18.1-02-SUMMARY.md` and `18.1-03-SUMMARY.md` each quote a retiring path — the
first quotes `examples/03-harness-portability` twice, the second quotes the coupling row
itself three times — and `18.1-04-SUMMARY.md` quotes none.** Plan 04's fourth row was
never going to appear. The stale set entering this plan was three, and three is the
correct number, not a symptom of running early.

This matters beyond bookkeeping: the executor brief for this plan carried the instruction
*"if your sweep finds three, IT RAN TOO EARLY"*. Acting on that instruction without
checking it would have meant waiting for a commit that could not change the count, or
manufacturing a mention to make the number come out right. **The prediction was checked
against the tree; the tree won.**

### Four changed rows, three of them inherited

The brief handed to this plan asserted that a sweep finding three rows had run too early.
The reconciliation is arithmetic, and it lands on four by a different route than the one
predicted:

- **Three rows were stale before this plan wrote a byte** — the `serve.py` anchor, and the

- **The fourth changed row is this SUMMARY's own**, added because this file was written

- **`18.1-04-SUMMARY.md` contributes no row at all**, having named none. The fourth row

So the sweep did change four rows, and the phase does close on four — but the fourth is
this file's, not Plan 04's, and a plan that had waited for Plan 04's row to appear would
have waited forever.

### Convergence — the report's currency at the moment the phase closes

This is the one claim that cannot be inherited from a measurement taken earlier, so it was
established directly.

The sweep walks `.planning/`, so appending this section to a SUMMARY the sweep had already
read makes the report stale by exactly this file's own row. The plan's ordering handles the
first order; the fix for the second is to re-run:

| Run | When | Result |
|---|---|---|
| 1 | after the SUMMARY was written, before this section was appended | the diff classified above; this file's row at count 1 |
| 2 | after this section was appended in full, byte-final | this file's row rises to its final count |
| 3 | immediately after run 2, changing nothing | **byte-identical to run 2** — fixed point reached |

Run 3 is the check that matters, and it is a real check rather than a formality: the
renderer is byte-deterministic by its own claim and by `test_the_report_render_is_deterministic`,
so a third run that differed from the second would mean some file was still moving under
the sweep. It did not differ.

**The number in this file's own row was written into this section as a numeral before run
2, and a numeral is not a path** — so recording it cannot change it, and the loop
terminates rather than chasing itself. That is why this section states the count as a
figure rather than by quoting another row.

**Currency at phase close: the committed `docs/surface/examples/RETIREMENT-COUPLINGS.md`
is byte-equal to what the sweep renders against the tree this phase leaves behind,
including this SUMMARY.** There is no residue. The one thing that would re-stale it is a
further commit into `.planning/` naming a retiring path — the orchestrator's STATE and
ROADMAP updates name none, and the close-time review documents are the next phase's
problem by the same D-19 logic that produced this plan.

## Sabotage Controls

Verification code is where this project's defects land, and this phase alone shipped four
gates that were green for the wrong reason. A green
`test_the_committed_report_is_current` is worth exactly as much as the demonstration that
it can go red.

| # | Control | Outcome |
|---|---|---|
| 1 | With the report regenerated and green, edit the `serve.py` row's line number back from `31` to `68` — a one-cell change, the smallest possible staleness, and precisely the staleness this plan exists to clear | **FIRED.** `test_the_committed_report_is_current` failed at `tools/docs_tests/test_retirement_sweep.py:845`; `1 failed, 32 passed`. The other 32 stayed green, so the control is specific rather than a blanket break. |
| 2 | Restore the file and re-run | **Green — `33 passed`.** |

**The restore was done with `cp` from a scratchpad copy, never with `git checkout --` or
`git restore`.** The report carried uncommitted content at that moment — the whole
regeneration — and a blanket restore would have silently thrown the plan's work away. That
reflex has already cost this phase work once, in wave 1.

The control matters because the failure mode it rules out is the one that would have made
this plan vacuous: a currency test that merely checks the file exists, or checks the
summary figures — which, as recorded above, did **not** move — would have been green
against a report with the wrong anchor in it. It is not; it compares the render.

## Observation for a later ruling — NOT fixed here

**`tools/retirement_sweep.py --report` is not read-only, and its name says otherwise.**

`--report` rewrites `docs/surface/examples/RETIREMENT-COUPLINGS.md` in place and prints
a single confirmation line (`wrote docs/surface/examples/RETIREMENT-COUPLINGS.md`)
amongst its output. There is no read-only measurement mode: to learn *whether* the report
is stale, you must first make it not stale.

The consequence is not hypothetical. Plan 04's executor ran it intending only to measure
the stale-row count for its hand-off note, and thereby performed the very fix D-19
schedules for this plan; it recovered by taking the measurement from the resulting diff
and reverting the file (`18.1-04-SUMMARY.md`, deviation 2).

Mitigating facts, for whoever rules on it: `--argparse`'s own help string is honest
(*"rewrite docs/surface/examples/RETIREMENT-COUPLINGS.md"*), and the report's header says
the file is regenerated rather than edited. The defect is in the *flag name*, which reads
as a verb of inspection, not in the documentation behind it.

Possible dispositions, none chosen here: rename to `--write`/`--fix` and add a
`--check`-style read-only mode that exits non-zero on staleness; or leave it and rely on
`test_the_committed_report_is_current` as the read-only check it effectively already is.
**Left for a ruling, deliberately — retooling a sweep is not this plan's subject, and
this plan's whole job is to leave the phase green rather than to open work in it.**
