## Codex Review

**Findings**

**HIGH — Case-insensitive filesystems can bypass the “server must not reach back inside root” rule.**  
File: `src/ccf/client/adapters/binding_document.py`  
Symbol: `load_binding_document`, the `if server == root_path or root_path in server.parents` check.

Concrete scenario: on a case-insensitive POSIX filesystem such as default macOS APFS, load the same deployment through a differently cased root path, e.g. caller passes `.../Deployment` while the real directory and `server:` value use `deployment/serve.py`. `_contained()` resolves the server under the parent, then the inside-root check compares `Path` objects lexically. `PosixPath(".../Deployment")` is not equal to `PosixPath(".../deployment")`, so `root_path in server.parents` can be false even though the filesystem object is inside the deployment root. Result: a `server:` value reaching back inside the root is accepted, violating the Phase 18.1 ruling.

**MEDIUM — Explicit empty/null/non-string `server:` values are silently accepted or coerced.**  
File: `src/ccf/client/adapters/binding_document.py`  
Symbol: `load_binding_document`, `declared_server = parsed.get("server")` and `str(declared_server)`.

Concrete scenario: `binding.yaml` contains `server: ""`, `server: "   "`, or `server:`. The loader treats this as omission and returns `BindingDocument.server is None`, even though the document explicitly stated a malformed key. Over `mcp+stdio`, the user then gets “declares no `server:`” instead of “`server:` is empty.” Likewise, `server: 1` becomes path `"1"`; if a sibling file named `1` exists, the transport can launch it. This weakens the typed boundary for a new public data key.

**MEDIUM — The server-shape test observes comments/docstring text, not the door document actually interpreted.**  
File: `tests/examples/test_hw1_two_transports.py`  
Symbol: `server_shape_violations`.

Concrete scenario: change `examples/hw1-companies-over-revenue/server/serve.py` so `EGRESS_DOOR = Path(__file__).resolve().parent / "other.yaml"`, but leave the module docstring mentioning `egress-door.yaml`. `server_shape_violations()` still passes because it checks `DOOR_DOCUMENT in door.read_text(...)`, not the `EGRESS_DOOR` assignment. The shipped server would read the wrong governance document while the structural gate stays green.

**LOW — Windows absolute/traversal spellings are host-dependent rather than grammar-refused.**  
File: `src/ccf/client/adapters/binding_document.py`  
Symbol: `_contained`.

Concrete scenario: on POSIX, `server: C:\tmp\serve.py` or `server: ..\outside\serve.py` is not considered absolute and has no `".."` path part, so it resolves as a relative filename under the holding directory. That is not a POSIX escape, but it means the artifact grammar accepts strings that are absolute/traversing paths on Windows. If binding artifacts are meant to be portable and “absolute paths are refused” means refused independent of host OS, this is a gap.

I did not see a surviving two-token `mcp+stdio` parser in the shipped adapter diff. The main grammar flip in `McpStdioAdapter._declared()` appears complete for the runtime path: two tokens are refused by name, one token is loaded as the deployment root, and the program comes from `BindingDocument.server`.

## What held (so the findings sit against a real baseline)

- **`resolve()` runs before the containment comparison.** `_contained` does `resolved = (root / written).resolve()` then `resolved != root and root not in resolved.parents`. A symlink-out of a plain name is refused; V-03 exercises it.
- **`..` after a symlink cannot sneak through.** `".." in written.parts` fires *before* resolve, so `link/../outside` is refused even when the resolved location would have been inside. Conservative, not a hole.

## MEDIUM

### 1. `_contained` does not implement the ManifestEntry rule it cites — Windows / drive-relative / backslash `..` are a native-`Path` question

**File / symbol:** `src/ccf/client/adapters/binding_document.py` :: `_contained` (417–432)  
**Cited but unused:** `src/ccf/controlplane/artifacts.py` :: `_leaves_its_own_directory` / `_PATH_FLAVOURS` (849–877)

`_contained`’s docstring says it applies ManifestEntry’s containment rule. ManifestEntry asks **both** `PurePosixPath` and `PureWindowsPath`, and also refuses `candidate.root` or `candidate.drive` (`C:foo`, `\\etc`). `_contained` only does:

```417:424:src/ccf/client/adapters/binding_document.py
    written = Path(candidate)
    if written.is_absolute() or ".." in written.parts:
        raise BindingError(
            ...
        )
```

**Concrete failure (Windows):** `server: C:steal.py` (drive-relative, no slash). `Path.is_absolute()` is false; `".." in parts` is false. `(root / written).resolve()` on Windows can jump to the current directory of `C:`, which need not be the holding directory. If that resolves *outside* the parent, the second check still refuses — but with the **symlink-out** sentence, which is the B0b misdiagnosis. If `C:`’s cwd happens to lie *under* the parent, the value is accepted and `mcp_stdio` will launch it.

**Concrete failure (POSIX authoring, ManifestEntry would already say no):** `server: foo\..\outside.py`. On Linux `Path.parts` is a single component, so the string check lets it through; resolve then treats it as a filename under the parent (no escape). ManifestEntry would have refused it via `PureWindowsPath` because `".." in parts`. The new key’s base is **wider** (the parent), so this is the moment the stricter string fence mattered, and it was not copied.

Empty / whitespace / `~` do not escape: `~` is not expanded in `_contained` (unlike the address token in `McpStdioAdapter._declared`). `server: ~/evil.py` is a directory literally named `~` under the parent.

I did **not** verify a dangling-symlink-then-target-appears race empirically; I am not asserting one.

## Gemini Review

This review covers the shipped code for CCF SDK Phase 18.1, focusing on path containment for the new `server:` key, the collapse of the `mcp+stdio` address grammar, and the robustness of the accompanying tests.

### 1. Containment and Path Traversal (`server:` resolution)
The implementation of the `server:` resolution in `binding_document.py` is architecturally sound and follows the "Mechanism, not domain values" invariant.

*   **Correct Base Resolution (HIGH):** The loader correctly uses `root_path.parent` as the resolution base for the `server:` key, satisfying the ruling that a server program is not deployment content. The use of `.resolve()` on the base and the resolved candidate ensures that containment checks are performed on canonical paths, mitigating risks from symlinks and case-insensitive filesystems.
*   **Double-Gated Jailing (HIGH):** The `_contained` utility provides two-layer protection:
    1.  **Lexical Gate:** It refuses absolute paths and explicit `..` segments via `Path.parts`. This catches traversal attempts before they reach the filesystem.
    2.  **Resolved Gate:** It verifies that the canonical path resides within the parent directory. This catches "sneaky" symlink escapes that bypass lexical checks.
*   **Amendment A.3 Enforcement (HIGH):** The explicit check `if server == root_path or root_path in server.parents` correctly prevents the `server:` key from being used to smuggle a second Python module into the deployment root. This is a crucial "hole-closing" measure necessitated by moving the resolution base outward.
*   **Platform Specifics:** On Windows, `Path.parts` correctly identifies `..` regardless of the separator used. On Linux, a backslash in a path is treated as a literal character, which `_contained` will resolve to a filename within the jail rather than a traversal, maintaining safety.

### 2. Tests That Cannot Fail (Disjunctions and Tautologies)
The phase effectively addresses several "green-tick" defect classes identified in previous reviews.

*   **Sabotage Controls (MEDIUM):** In `tests/examples/test_hw1_two_transports.py`, the `server_shape_violations` check uses `!= SERVER_MODULE_COUNT` rather than `>`. This ensures that a vacuous failure (0 modules) is caught, whereas a `>` check would have stayed green if the directory was emptied. 
*   **Report Quality (MEDIUM):** The utility `assert_the_refusal_named_the_parent_as_the_base` is a high-signal validation. It asserts both the presence of the correct base description and the *absence* of the default ("the deployment root"), directly preventing the "B0b" report-quality defect where a test passes against a misleading error message.
*   **Data vs. Unknown Keys (MEDIUM):** `test_a_reference_shaped_server_is_refused_as_a_reference` confirms that `server:` is now correctly recognized as a **data** position. This is verified by asserting that the error message specifies "reference in a data position" rather than generic unknown-key machinery, ensuring the key is fully integrated into the loader's schema.

### 3. Grammar-Flip Completeness (`mcp+stdio` collapse)
The transition from a two-token (`PROGRAM ROOT`) to a one-token (`ROOT`) address for `mcp+stdio` is implemented with high defensive coverage.

*   **Proactive Diagnostics (HIGH):** In `mcp_stdio.py`, the `_declared` method includes explicit guards for the old 2-token format (`if len(tokens) == 2`). This provides a clear migration path for users. 
*   **File/Directory Ambiguity (HIGH):** The transport now checks if the provided token is a file (`resolved.is_file()`) and raises a specific `BindingError` explaining that the address must name the *root*, not the *program*. This is a critical usability fix, as naming the script is the most likely user error following the grammar change.
*   **Consistency (MEDIUM):** The 1-token assumption is consistently applied across `binding.py`, `client.py`, and the example `README.md`. `tests/examples/test_client_example_purity.py` reinforces this by asserting that the `inprocess` and `mcp+stdio` commands are identical after the scheme assignment.

### 4. Example Pedagogy
The `hw1-companies-over-revenue` example maintains its role as a teacher of mechanism.

*   **Producer/Consumer Separation (LOW):** By moving the server composition logic to `compose.py` and off-staging it in the README, the example clarifies that the `ccf.client` user should not care *how* a product is served, only *where* it is.
*   **No Hardcoding (LOW):** The server name is derived from `fabric.tenant_id` and governance from `egress-door.yaml`. The code remains an interpreter of artifacts, even in the example "producer" code.
