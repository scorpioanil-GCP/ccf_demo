## Rulings settled at planning, so they are not re-litigated in execution

1. **The key is a bare `server:`, not a `transports:` map.** `binding.yaml` is one flat
   document; `OPTIONAL_KEYS` is a flat tuple of strings and the unknown-key refusal at
   `binding_document.py:584-598` enumerates flat key names. A nested map would need a
   refusal path for nested keys that does not exist, to carry a single entry.
   `connection:` is the precedent and it is flat.
2. **D-18's refusal does NOT go into `RULED_OUT_KEYS`.** That mapping refuses a key
   *unconditionally by name*, and `server:` is a legitimate optional key. D-18 refuses a
   *value*, in the register `RULED_OUT_KEYS` established. It is raised in the `server:`
   value-read block, after containment succeeds. Adding `"server"` to `RULED_OUT_KEYS`
   would refuse every deployment that declares one, including hw1's, and is wrong.
3. **The loader contains `server:` and does NOT require it to exist.** The `artifact_store`
   precedent (`:697`, contained and returned, not existence-checked) rather than the
   `config` precedent (`:622-627`, existence-checked). Existence is transport-specific:
   an in-process deployment never launches the program, and an unpopulated checkout may
   legitimately lack it. `mcp_stdio._declared()` does the `is_file()` check in `18.1-02`,
   where the transport is known. This ruling is what keeps every copied fixture loadable.
4. **The committed fixture deployment gains `server: stdio_server.py`.** So D-06's control
   in `18.1-02` is *"delete the key from a copy"* — a doctored divergent state — rather
   than *"copy unmodified"*, which would be a control over the status quo. This matches
   the discipline stated at `tests/examples/test_client_example_purity.py:35-40`: every
   control feeds a `tmp_path` copy into the same function the shipped assertion calls.
