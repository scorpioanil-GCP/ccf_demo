## User Constraints (from CONTEXT.md)

### Locked Decisions

**Where the server command is declared**

- **D-01:** The server command is declared as a **new key in `binding.yaml`** (the roadmap's form).
  `OPTIONAL_KEYS` gains an entry, and `binding.yaml`'s "data, with exactly one exception" header is
  rewritten to say why a *command* is data while a `plan:` *reference* is not.
- **D-02:** **The server does NOT move into the deployment root.** `server/` stays exactly where it
  is — a sibling of `deployment/` at the example's top level. *(This REVERSES an earlier same-day
  ruling that moved it to `deployment/server/`; Dave reopened it. See D-10 for the reasoning and the
  resolution rule.)*
- **D-03:** **MOOT — drops out of the phase.** Because the server does not move inside the
  deployment root, `D-IMPL-141` Amendment A.3 needs **no amendment** and `assert_one_python_module`
  needs **no rewrite**. `server/` sits outside both the deployment root (so the one-module gate never
  sees it) and the example root (so `test_client_example_purity` never sees it), which means a second
  module there costs nothing structurally. This is strictly *less* mechanism than the reversed
  ruling, in a phase scoped to ship none.
- **D-04:** The declared value is **a single path**. The adapter still spawns `sys.executable` and
  still passes the deployment root as `argv[1]`, so the measured cross-checkout failure recorded in
  `mcp_stdio._call` stays prevented. The only thing that changes is *where the client learned the
  path*. Not a full argv command, not a path plus extra args.

**The address grammar after the change**

- **D-05:** **One token only** — `mcp+stdio:<deployment-root>`. The two-token form is **replaced**,
  not kept alongside. `tests/client/test_binding.py:228` and the adapter's module docstring both
  change.
- **D-06:** **The adapter refuses when `server:` is absent, and names the transport.** The key stays
  OPTIONAL at the loader, because the loader cannot know which transport is asking and an in-process
  deployment will never declare one. `mcp_stdio._declared()` refuses, saying this deployment declares
  no server command and therefore cannot be reached over `mcp+stdio`, and naming the key to add. The
  requirement is transport-specific, so the refusal is too.
- **D-07:** **A named branch for exactly two tokens**, whose message names the migration: the second
  token is now this deployment's `server:` key in `binding.yaml`, so drop the program from the
  address. Any other count gets the generic "exactly one token, the deployment root" message. The
  migration branch is permanent grammar, not time-limited.
- **D-08:** **A targeted refusal when the single token resolves to a file** rather than a directory —
  the half-migration `mcp+stdio:.../server/serve.py`. The message says this names a program and an
  `mcp+stdio` address names the deployment root that declares the program. Chosen over falling
  through to `load_binding_document`, whose "no `binding.yaml` here" message would describe a missing
  document rather than the mistake actually made — the report-quality class that `B0b` was fixed for.

**How simple is simple enough for `serve.py`**

- **D-09:** **`server/` stays a sibling** (final; see D-02). Dave, reopening the morning's ruling:
  *"Server is temporary in this specific example because it is not the focus."* The reasoning that
  persuaded him, and that planning should preserve: filing the server inside the deployment root to
  satisfy a path check makes the example teach that a server is deployment *content*, which is false
  — the normal case is a remote server reached by an endpoint, with `server:` **absent entirely**. A
  design that reads correctly when the key is missing is the right design. Keeping it a sibling is
  also strictly less mechanism and costs nothing on the portability demo, because both addresses
  still name the identical token.
- **D-10:** **`server:` resolves against the deployment root's PARENT**, stated in the document
  header as the one key that does. `server: server/serve.py` with no `..` anywhere; absolute paths
  and symlink escapes are still refused. Containment stays a rule with **no holes** — only the base
  is declared. Survives the future `client/` + `server/` restructure unchanged.
- **D-11:** **Door stays, composition leaves.** `serve.py` keeps only what is about the MCP door:
  read the door's four governance values, `build_egress_server`, set the stdio identity, run on
  stdio. A second module beside it exports one function returning the booted fabric + control plane +
  governed resolver. The file `binding.yaml` names reads as a server, not as a fabric boot.
- **D-12:** **No line budget — the criterion is structural.** One file, one concern: `serve.py` holds
  only door concerns, composition lives in the other module. Nothing unenforced to keep in step, and
  no gate built for code Dave has called temporary and not the focus. *Rejected:* a second declared
  budget in the client README (`check_example_budget` refuses a README with two, counts only
  example-root modules, and it would put a server line-count back in the reader's document); and a
  separately-declared server budget (a new document plus a second checker).
- **D-13:** **The module docstring is trimmed to what only the server can say** — the stdio-identity
  trust statement (a real governance claim about this deployment's boundary, with nowhere else to put
  it) and the two documents the program reads. The README's new frame owns why a server exists at all
  and why it is a sibling, so the same argument is not made twice in two places that must stay in
  step. **Note for planning:** the filing rationale stays *true* because the file is not moving, but
  the address paragraph — *"an `mcp+stdio` binding names **this file** and the deployment root beside
  it"* — becomes **false** and must be rewritten regardless of how much else survives.

**What the README shows and what goes off-stage**

- **D-14:** **The frame sits immediately above the two commands**, where the reader is already asking

## Summary

CONTEXT.md's 17 decisions survive contact with the tree. Every measured fact it carries about
`serve.py` is **exactly right** (292 lines; docstring 1–70; `door_values()` 123–149 at 27 lines;
`serve()` 152–288 at 137 lines; 18 standalone comments; 32 blank). D-03's structural claim — that a
second module in `server/` is invisible to both `assert_one_python_module` and
`test_client_example_purity` — is **confirmed by reading both globs**: the first is
`root.glob("*.py")` over the *deployment* root, the second is `root.glob("*.py")` over the *example*
root, and neither is recursive. D-10's containment claim is confirmed **empirically**, by executing
`_contained`'s exact logic against a synthetic tree with the base set to the parent.

What CONTEXT.md does not carry, and what a plan written from it alone would get wrong, is the blast
radius. Six things:

1. **`_contained`'s refusal messages hard-code the phrase "the deployment root" and interpolate the
   base into it.** Passing `root.parent` is necessary and not sufficient — it produces a message that
   names the *example* root and calls it the deployment root. That is the B0b class, in the phase
   whose own decisions cite B0b. `_contained` needs a way to describe its base.
2. **Three test modules and one fixture package are built on the two-token address and are not named
   in CONTEXT.md**: `tests/client/test_mcp_stdio_adapter.py` (its `_address()` helper *is* the
   two-token form), `tests/client/conformance/test_mcp_conformance.py` (both the healthy and the
   break factory `shlex.join` two tokens), and `tests/client/fixtures/__init__.py` +
   `fixtures/stdio_server.py` (whose docstrings argue for the two-token form).
3. **`tests/examples/test_hw1_two_transports.py:261-263` destructures the address into exactly two
   tokens** (`program, root = (Path(t) for t in shlex.split(...))`). Under D-05 that raises
   `ValueError`. CONTEXT.md lists this file only as "carries the binding strings."
4. **The conformance and adapter fixtures provision a deployment into a `tmp_path` subdirectory whose
   parent does not contain a server program.** Under D-10 the `server:` key must resolve *inside*
   that parent, so the provisioning must copy a program there. This is real plan work, not a rename.
5. **`docs/surface/examples/RETIREMENT-COUPLINGS.md:126` carries a `serve.py:68` row** that the D-13
   docstring trim moves or deletes, and `tools/docs_tests/test_retirement_sweep.py::test_the_committed_report_is_current`
   asserts that file is byte-current. **That gate is already RED at HEAD** for an unrelated reason —
   so `make ci-core` is red at HEAD and the planner must not treat a red `gate-tools` as this phase's
   doing.
6. **The claim "ships no new SDK surface" is true of seams and false of `binding_document`.** A
   `server` field on the public `BindingDocument` dataclass changes its recorded shape. The drift
   *gate* will not fire (the module is already claimed by three Phase 17 fragments, and the gate is
   module-granular by design), but D-15's record discipline says file a fragment anyway.

**Primary recommendation:** plan this as **four waves against the tree, not three changes against the
CONTEXT**. Wave 0 lands `server:` in the loader with its own base-description mechanism and its
containment tests. Wave 1 rewrites `_declared()`'s four branches with four end-to-end controls. Wave
2 migrates every two-token construction site — six files, listed below — in one commit, because the
address grammar cannot be half-changed. Wave 3 is the `serve.py` cut, the README, and the coupled
prose. The README ↔ Makefile character-identity gate ties Wave 2's README block and Makefile recipe
into one commit; they cannot be split.

**`_contained()`'s real signature** — `binding_document.py:374`:

```python
def _contained(candidate: str, *, root: Path, key: str, document: Path) -> Path:
```

Body at `:385-401`. Two checks, neither covering the other:

```python
written = Path(candidate)
if written.is_absolute() or ".." in written.parts:
    raise BindingError(f"`{key}: {candidate}` in {document} names a path outside the"
                       " deployment root — a binding document describes the deployment it"
                       " sits in, so its paths are relative to that root and carry no `..`"
                       " segment and no leading `/`")
resolved = (root / written).resolve()
if resolved != root and root not in resolved.parents:
    raise BindingError(f"`{key}: {candidate}` in {document} resolves to {resolved}, which"
                       f" is outside the deployment root {root} — a plain name that is a"
                       " symlink out of the deployment is refused for the same reason a"
                       " `..` segment is")
return resolved
```

**`_contained` can take a different base without widening its rules — verified by execution.** The
exact logic was run in this session against a synthetic tree (`example/deployment/`,
`example/server/serve.py`, plus a symlink out of `example/`), with `root = deployment.parent`:

| Candidate | Result with base = parent |
|---|---|
| `server/serve.py` | **OK** → `…/example/server/serve.py` |
| `../server/serve.py` | **REFUSED** (`..` segment) |
| `/etc/passwd` | **REFUSED** (absolute) |
| `link.py` (symlink to `…/outside/evil.py`) | **REFUSED** (escape) |
| `deployment/projection.py` | **OK** ← see the open question below |

**BLOCKING FINDING — the messages, not the logic.** With `root = root_path.parent`, the second
refusal renders as *"…resolves to X, which is outside the deployment root `/…/example`"* — naming the
**example** root and calling it the deployment root. The first renders *"its paths are relative to
that root"*, which is false for `server:`. CONTEXT.md's `<code_context>` says *"pass `root.parent`
rather than widen the check"*; that is correct about the check and silent about the message. A
refusal that describes the wrong mistake is the class this project fixed `B0b` for, and D-08 in this
same phase cites that class by name.

**Recommended repair, minimal and non-widening:** add one keyword-only parameter,

```python
def _contained(candidate: str, *, root: Path, key: str, document: Path,
               base_description: str = "the deployment root") -> Path:
```

and interpolate `base_description` in both messages. Every existing call site keeps the default, so
`tests/client/test_binding_document.py:598-653` — three tests asserting the literal string
`"outside the deployment root"` — stay green unchanged. `server:` passes
`base_description="the directory holding this deployment"` (or similar wording that names what the
base actually is). This is the smallest edit that keeps containment a rule with no holes *and* keeps
the report honest.

**The `connection.database_path` `{path: …}` precedent — CONTEXT's claim confirmed.** `_connection`
at `:463-513`, docstring `:474-482`:

> *a single-key mapping `{path: <relative>}`, resolved against the deployment root and contained.
> This form exists because a rooted path is the one setting a deployment genuinely cannot spell as a
> literal — **the root is not known until the client names it**, and a relative path would resolve
> against the caller's working directory, which is a different deployment on every invocation.*

CONTEXT.md's paraphrase is accurate. It is a precedent for *"a key whose base is stated rather than
assumed"* — though note the mechanism differs: `connection` states the base by **value shape**
(`{path: …}` means "rooted"), whereas D-10 states it by **key identity** (`server:` is the one key
whose base is the parent). Both are declarations rather than assumptions; the planner should not
claim they are the same mechanism.

**Existence checking — the precedent says do not.** `config:` is existence-checked at `:622-627`
(`if not config.is_file(): raise`). `artifact_store:` is **not** — it is contained and returned. The
difference is that a missing artifact store is created on write; a missing config is a broken

## Fixture provisioning — the change CONTEXT.md does not name

This is the largest piece of unlisted work and it is invisible from CONTEXT.md alone.

**The fixture layout already matches D-10 perfectly in the repository:**

```
├── stdio_server.py      ← the fixture deployment's server program
└── deployment/          ← the deployment root; parent is fixtures/

    └── projection.py
```

`server: stdio_server.py` in `fixtures/deployment/binding.yaml` resolves against the parent
`fixtures/` and lands exactly on the shipped program. **The layout was already right; nobody knew it
yet.** `tests/client/fixtures/__init__.py`'s docstring even argues for it, for the old reason.

**But every consumer copies `deployment/` alone into a `tmp_path` subdirectory whose parent is
empty:**

| Consumer | Where | What it copies |
|---|---|---|
| `conftest.py:97-101` `deployment_root` | `tmp_path/deployment` | `copytree(FIXTURE_DEPLOYMENT, root)` — parent `tmp_path` gets nothing |

| `conformance/conftest.py:52-58` `provision()` | `tmp_path/NN-<name>/deployment` | same; parent gets nothing |

Under D-10 with an existence check in the adapter, `server: stdio_server.py` in a copied deployment

1. **`provision()` must also copy the server program into the parent** (one `shutil.copy2`), or the

   entirely absent from CONTEXT.md.

`tests/client/fixtures/__init__.py` that rewrites the copied `binding.yaml`'s `server:` key. Three

## Refusal-message register — the house voice, measured

CONTEXT.md's report-quality standard asks for the existing register so the planner specifies messages
that match rather than invent a voice. Read across both modules:

**Structure — four moves, in order:**

1. **Open with the offending literal, in backticks, and where it lives.**
   `` f"`{key}: {candidate}` in {document}…" `` / `` f"`{self._address}` states {len(tokens)} tokens…" ``
2. **Em-dash, then what the thing actually is / the rule.**
   `` "— a binding document describes the deployment it sits in" ``
3. **A because-clause naming the ruling, the invariant or the measurement.**
   `` "by `D-IMPL-141` Amendment A.3, which is its projection" ``, `` "because the SDK ships none and cannot" ``, `` "(`D-IMPL-38`)" ``
4. **Often, the rejected alternative or the remedy.**
   `` "Add `binding.yaml` stating `config:`, `question:`, …" ``

**Mechanical conventions, all confirmed by reading:**

- **No terminal period.** Verified across every refusal in both modules — internal sentences take
  periods, the message never ends with one.
- **Backticks around every identifier**: key names, schemes, ruling ids, filenames, constants.
- **Never second person.** No "you", no imperative addressed to a reader.
- **Show the shape, don't just name it.** `tests/client/test_binding.py:201-203` asserts this
  literally: *"the message must show the shape it wanted, not merely name it"* — which is why
  `binding.py:160` carries `` `inprocess:./deployment` or `mcp+stdio:./server.py` `` and why that
  second example must be corrected in this phase.
- **Refuse by name, never by shape alone.** `RULED_OUT_KEYS`' own docstring (`:160-166`): *"An
  unknown key is a typo; one of these is a deployment following the shape `D-IMPL-141` proposed
  before it was rejected, and telling its author 'not a binding-document key' would invite a
  re-spelling of the very thing that was declined."*
- **`SCHEME` is interpolated, never spelled.** `mcp_stdio.py:132-134`: *"Written once, so the
  registry entry, the refusal messages and the tests all say the same string."* All four new messages
  must use `{SCHEME}`.

**Worked drafts in that register** (the planner may improve the wording; the *shape* is what matters):

- **D-07 (exactly two tokens):**
  `` f"`{self._address}` states two tokens; an `{SCHEME}` address states one — the deployment root. The second token was the server program, and it is now this deployment's own `server:` key in its `binding.yaml`, so drop the program from the address and name the root alone, as in `mcp+stdio:./deployment`" ``
- **Generic (any count ≠ 1):**
  `` f"`{self._address}` states {len(tokens)} tokens; an `{SCHEME}` address states exactly one — the deployment root, as in `mcp+stdio:./deployment`. The program to launch is the deployment's, declared under `server:` in its `binding.yaml`, because the SDK ships no server program and cannot" ``
- **D-08 (single token resolves to a file):**
  `` f"`{token}` names a program — it resolves to {resolved}, which is a file. An `{SCHEME}` address names the **deployment root** that declares the program, not the program itself; the program is this deployment's `server:` key in its `binding.yaml`" ``
- **D-06 (`server:` absent):**
  `` f"{document.root}'s `{BINDING_DOCUMENT_NAME}` declares no `server:`, so this deployment states no program to launch and cannot be reached over `{SCHEME}`. Add `server:` naming its MCP server program, relative to the directory holding this deployment. The key is optional because a deployment reached in process never launches one — the requirement belongs to this transport, not to the document" ``

The D-06 draft's last sentence is doing the C-1 work at the mechanism level: it says the key's absence
is normal, which is exactly D-09's *"a design that reads correctly when the key is missing is the
right design."*

## Common Pitfalls

### Pitfall 1 — passing `root.parent` and stopping there
**What goes wrong:** containment behaves correctly and the refusal message calls the example root
"the deployment root."
**Why it happens:** `_contained` interpolates its `root` argument into a message with a hard-coded
noun phrase. CONTEXT.md's `<code_context>` says "different base, not a different rule," which is true
of the logic and silent about the prose.
**How to avoid:** the `base_description` keyword, defaulted so no existing call site or test changes.
**Warning sign:** a new containment test whose assertion string is `"outside the deployment root"` and
passes — that means the message is still wrong and the test is agreeing with it.

### Pitfall 2 — treating `test_hw1_two_transports.py` as "carries the binding strings"
**What goes wrong:** the plan changes the README and Makefile, the parity test passes, and
`test_the_mcp_leg_really_runs_the_examples_own_server_program` raises `ValueError` on a two-name
unpack.
**Why it happens:** the destructure at `:261-263` is eight lines below a `shlex.split` and reads like
plumbing.
**How to avoid:** rewrite that test in the same wave as the address change; its post-D-05 subject is
that `server:` resolves to a file outside the deployment root.
**Warning sign:** `ValueError: not enough values to unpack (expected 2, got 1)`.

### Pitfall 3 — forgetting that copied fixtures have empty parents
**What goes wrong:** the loader contains `server:` happily and the adapter refuses "names no server
program" for every conformance and adapter test.
**Why it happens:** the repository layout already satisfies D-10; the *copies* do not.
**How to avoid:** provision the program into the parent, in `conformance/conftest.py::provision`,
`test_mcp_stdio_adapter._root`, and anywhere else a deployment is copied and then reached over
`mcp+stdio`.
**Warning sign:** every `mcp+stdio` conformance leg failing identically with a `BindingError`, and
the in-process legs green.

### Pitfall 4 — a `server:` value that reaches back into the deployment root
**What goes wrong:** nothing, today, and Amendment A.3 is quietly widened tomorrow. **Verified:**
with base = parent, `server: deployment/projection.py` is **contained and accepted**.
**Why it happens:** the parent contains the deployment root, so parent-relative containment is
strictly weaker than root-relative containment in exactly one direction — inward.
**How to avoid:** see Open Question 1. This needs a ruling, not a silent default.
**Warning sign:** an adopter's `binding.yaml` reading `server: serve.py` and working.

### Pitfall 5 — trimming `serve.py`'s docstring past what other documents cite
**What goes wrong:** `server/egress-door.yaml:33` says *"see `serve.py`'s docstring"* for why the URLs
are inert over stdio, and `:29` says `serve.py` mints the credential. A trim that removes the
stdio-identity paragraph or moves the minting falsifies a document this phase does not open.
**How to avoid:** D-13 already protects the trust paragraph. Keep minting in `serve.py` (see the
disposition above).
**Warning sign:** no automated one. This is a review item.

### Pitfall 6 — assuming `make ci-core` is green at HEAD
**What goes wrong:** the executor sees a red `gate-tools`, attributes it to their own change, and
either chases it or "fixes" 26 lines of unrelated planning-tree drift mid-wave.
**How to avoid:** record the baseline in the plan: `test_the_committed_report_is_current` is red at
`7f048a6` from commit `6d6a99b`'s `abandoned/` move, and the fix belongs to the phase-close re-sweep.

### Pitfall 7 — a second budget line, or a `run.py`
**What goes wrong:** two `declared budget: N lines` matches make `declared_budget` return `None`,
which makes `check_example_budget` report *"declares no line budget"* — a red gate that reads like
the opposite of what happened. And a `server/run.py` registers `server/` as an example root in
`test_artifact_schema_headers.example_roots` (an `rglob`), failing the artifacts bijection.
**How to avoid:** D-12 forbids the first. `compose.py` avoids the second.

#### (a) `server:`'s containment still refuses absolute, `..`, and symlink escape with the parent base

### 1. May `server:` resolve *inside* the deployment root?

**What we know:** verified by execution — with `root = deployment.parent`, `server: projection.py`
and `server: deployment/anything.py` are both **contained and accepted**. Parent-relative containment
is strictly weaker than root-relative containment in exactly one direction: inward.

**What's unclear:** whether that is a hole. `assert_one_python_module` is a *test* over two known
roots, not a runtime check, so a third-party deployment declaring `server: serve.py` beside its
projection would load cleanly and quietly hold two Python modules in a directory Amendment A.3 grants
one. D-10 says *"containment stays a rule with no holes — only the base is declared."* Whether an
inward-reaching `server:` is a hole in *that* rule or in a *different* one (A.3's) is not settled.

**Recommendation:** refuse it, by name, in the register `RULED_OUT_KEYS` established — something like
*"`server: {value}` resolves inside the deployment root, which `D-IMPL-141` Amendment A.3 grants one
Python module — its projection. A deployment's server program is not deployment content; name it
beside the deployment, not inside it."* It is four lines and one test, it makes D-09's argument
mechanical rather than documentary, and it closes the only measured gap in D-10.

**Counter-argument the planner must weigh:** this is *new mechanism* in a phase whose first sentence
is *"ships no new SDK surface."* If it is rejected, the rejection must be recorded — and
`test_hw1_two_transports`'s surviving `assert document.server.parent != root` becomes the only thing
holding the line, for the shipped example only.

**Disposition: surface this to Dave rather than deciding it at planning.** It is a `D-IMPL-NN`-shaped
question (CLAUDE.md §15: *"whitepaper-silent question: add an entry, stop, ask"* — the SDK-extension
analogue applies).

### 2. Does the fixture deployment gain a `server:` key?

**What we know:** `tests/client/fixtures/deployment/binding.yaml` has none today, and its parent
already holds `stdio_server.py`. Two options with different consequences:

- **(a) Add it.** The conformance factories become `McpStdioAdapter(str(root))` with no per-test
  rewrite; `provision()` copies the program into the parent. D-06's "absent" control then has to
  *delete* the key from a copy — which is a fine control, and arguably a better one.
- **(b) Leave it out**, and have each `mcp+stdio` test declare it into its own copy via the helper.
  D-06's control becomes "copy unmodified," which is the weakest possible control (it tests the
  status quo).

**Recommendation: (a).** A shipped fixture that declares its own server matches the shipped example
and makes the *divergent* state the doctored one — the discipline
`test_client_example_purity.py:35-40` states as *"every control feeds a `tmp_path` copy into the same
function the shipped assertion calls."*

**This is a planning decision, not Dave's.** It falls under the discretion CONTEXT.md already granted.

### 3. Does the ROADMAP's "per-boot token minting is composition" survive D-11?

**What we know:** the ROADMAP scope bullet lists it as composition; D-11 (later, more specific) lists
`serve.py` as keeping *"set the stdio identity"*; `egress-door.yaml:28-30` says `serve.py` mints it;
and the credential is consumed only on the door side.

**Recommendation:** minting stays in `serve.py`, and the plan records the tension. D-11 is the binding
ruling and the ROADMAP bullet predates the cut's design.

### 4. Should the second `server/` module's export be a function or a small frozen dataclass?

**What we know:** D-11 says *"one function returning the booted fabric + control plane + governed
resolver."* Three return values need a shape. `_Declared` in `mcp_stdio.py:142-155` is the tree's
precedent (frozen, kw-only, `__slots__`-free, with a docstring stating *why* it is read per call).

**Recommendation:** a frozen `@dataclass(frozen=True)` returned by one function. A bare 3-tuple in
example code that is meant to be read is the wrong teaching. **Not a blocker; settle at planning.**
