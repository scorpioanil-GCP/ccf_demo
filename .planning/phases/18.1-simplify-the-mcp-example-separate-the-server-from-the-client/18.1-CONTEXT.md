# Phase 18.1: Simplify the MCP Example — Client-Side Access, Server Off-Stage - Context

**Gathered:** 2026-08-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the MCP example demonstrate **client access to the same Context Product,
reached a different way**, and stop the client's command from naming the server
program. A client-experience phase that **ships no new SDK surface**: no new
transport, no new adapter, no `mcp+http`, no change to the client seam.

Three changes, none of them new mechanism:

1. `CCF_BINDING` names a **deployment**, not a script — the server command is
   declared in `binding.yaml` as data.
2. `server/serve.py` is cut to a readable length, into a second module beside it.
3. The README states the frame — the same Context Product reached a different
   way, why a server appears at all, and that how it is assembled is out of
   scope until the assembly examples.

**The finding this phase acts on:** the spawn is inherent to MCP stdio (there is
no listening endpoint) and is **not** the defect. The defect is that the spawn is
the *client's business* in the reader's field of view.

**Independent of Phase 19** — no seam change, so either order works.

</domain>

<decisions>
## Implementation Decisions

### Where the server command is declared

- **D-01:** The server command is declared as a **new key in `binding.yaml`**
  (the roadmap's form). `OPTIONAL_KEYS` gains an entry, and `binding.yaml`'s
  "data, with exactly one exception" header is rewritten to say why a *command*
  is data while a `plan:` *reference* is not.
- **D-02:** **The server does NOT move into the deployment root.**
  `server/` stays exactly where it is — a sibling of `deployment/` at the
  example's top level. *(This REVERSES an earlier same-day ruling that moved it
  to `deployment/server/`; Dave reopened it. See D-10 for the reasoning and the
  resolution rule.)*
- **D-03:** **MOOT — drops out of the phase.** Because the server does not move
  inside the deployment root, `D-IMPL-141` Amendment A.3 needs **no amendment**
  and `assert_one_python_module` needs **no rewrite**. `server/` sits outside
  both the deployment root (so the one-module gate never sees it) and the
  example root (so `test_client_example_purity` never sees it), which means a
  second module there costs nothing structurally. This is strictly *less*
  mechanism than the reversed ruling, in a phase scoped to ship none.
- **D-04:** The declared value is **a single path**. The adapter still spawns
  `sys.executable` and still passes the deployment root as `argv[1]`, so the
  measured cross-checkout failure recorded in `mcp_stdio._call` stays prevented.
  The only thing that changes is *where the client learned the path*. Not a full
  argv command, not a path plus extra args.

### The address grammar after the change

- **D-05:** **One token only** — `mcp+stdio:<deployment-root>`. The two-token
  form is **replaced**, not kept alongside. `tests/client/test_binding.py:228`
  and the adapter's module docstring both change.
- **D-06:** **The adapter refuses when `server:` is absent, and names the
  transport.** The key stays OPTIONAL at the loader, because the loader cannot
  know which transport is asking and an in-process deployment will never declare
  one. `mcp_stdio._declared()` refuses, saying this deployment declares no server
  command and therefore cannot be reached over `mcp+stdio`, and naming the key to
  add. The requirement is transport-specific, so the refusal is too.
- **D-07:** **A named branch for exactly two tokens**, whose message names the
  migration: the second token is now this deployment's `server:` key in
  `binding.yaml`, so drop the program from the address. Any other count gets the
  generic "exactly one token, the deployment root" message. The migration branch
  is permanent grammar, not time-limited.
- **D-08:** **A targeted refusal when the single token resolves to a file**
  rather than a directory — the half-migration `mcp+stdio:.../server/serve.py`.
  The message says this names a program and an `mcp+stdio` address names the
  deployment root that declares the program. Chosen over falling through to
  `load_binding_document`, whose "no `binding.yaml` here" message would describe
  a missing document rather than the mistake actually made — the report-quality
  class that `B0b` was fixed for.

### How simple is simple enough for `serve.py`

- **D-09:** **`server/` stays a sibling** (final; see D-02). Dave, reopening the
  morning's ruling: *"Server is temporary in this specific example because it is
  not the focus."* The reasoning that persuaded him, and that planning should
  preserve: filing the server inside the deployment root to satisfy a path check
  makes the example teach that a server is deployment *content*, which is false —
  the normal case is a remote server reached by an endpoint, with `server:`
  **absent entirely**. A design that reads correctly when the key is missing is
  the right design. Keeping it a sibling is also strictly less mechanism and
  costs nothing on the portability demo, because both addresses still name the
  identical token.
- **D-10:** **`server:` resolves against the deployment root's PARENT**, stated
  in the document header as the one key that does. `server: server/serve.py`
  with no `..` anywhere; absolute paths and symlink escapes are still refused.
  Containment stays a rule with **no holes** — only the base is declared.
  Survives the future `client/` + `server/` restructure unchanged.
- **D-11:** **Door stays, composition leaves.** `serve.py` keeps only what is
  about the MCP door: read the door's four governance values, `build_egress_server`,
  set the stdio identity, run on stdio. A second module beside it exports one
  function returning the booted fabric + control plane + governed resolver. The
  file `binding.yaml` names reads as a server, not as a fabric boot.
- **D-12:** **No line budget — the criterion is structural.** One file, one
  concern: `serve.py` holds only door concerns, composition lives in the other
  module. Nothing unenforced to keep in step, and no gate built for code Dave
  has called temporary and not the focus. *Rejected:* a second declared budget in
  the client README (`check_example_budget` refuses a README with two, counts
  only example-root modules, and it would put a server line-count back in the
  reader's document); and a separately-declared server budget (a new document
  plus a second checker).
- **D-13:** **The module docstring is trimmed to what only the server can say** —
  the stdio-identity trust statement (a real governance claim about this
  deployment's boundary, with nowhere else to put it) and the two documents the
  program reads. The README's new frame owns why a server exists at all and why
  it is a sibling, so the same argument is not made twice in two places that
  must stay in step. **Note for planning:** the filing rationale stays *true*
  because the file is not moving, but the address paragraph — *"an `mcp+stdio`
  binding names **this file** and the deployment root beside it"* — becomes
  **false** and must be rewritten regardless of how much else survives.

### What the README shows and what goes off-stage

- **D-14:** **The frame sits immediately above the two commands**, where the
  reader is already asking why there are two of these and why one involves a
  server. It states the three things by name: the same Context Product reached a
  different way; why a server appears at all (the first example ran in-process
  with the SDK and produced the product directly, so nothing had to be stood up);
  and that how the server is assembled is deliberately out of scope here.
- **D-15:** **The two-token paragraph is deleted**, replaced by one sentence
  pointing at what the reader can now see for themselves: the two strings differ
  by one word, the scheme. How this deployment is reached is its own business,
  declared in `binding.yaml` beside its projection and its graph — stated once,
  not argued. The gates-and-filing reasoning goes away entirely; it answered a
  question the address no longer raises.
- **D-16:** **The `server/` paragraph shrinks to two sentences**, and must carry
  the no-generalizing note (see Constraints): `server/` is the producer's world,
  off-stage, open it if you are curious — and its location here is incidental to
  an example where the server is not the focus, with real servers commonly
  living elsewhere, on another machine. Everything else (public seams, the
  filing argument) drops; `serve.py`'s own docstring keeps what only it can say.
- **D-17:** **The forward reference describes, and links nothing.** Name the
  subject in prose — how a Context Product is assembled and served is the
  subject of a later set of examples — with no path and no number. Nothing to go
  stale, nothing to break a docs link check, and the sentence stays true whatever
  those examples end up being called.

### Constraints on the writing, not only the wiring

- **C-1 (Dave, 2026-08-18):** **The documentation must not generalize that
  servers live in the deployment.** *"Make sure not to generalize the
  documentation that servers will always be in deployment — they will not."*
  The server's location in this example is incidental; real servers live
  elsewhere, commonly on another machine. **A sentence implying otherwise is a
  defect in this phase's own terms**, and this applies to the README, to
  `binding.yaml`'s header, and to `serve.py`'s docstring alike.

### Claude's Discretion

- **The `server:` key name and whether it is transport-scoped.** Dave declined
  to rule. Leaning to a bare `server:` key rather than a `transports:` map,
  since `binding.yaml` is one flat document and a map would be structure built
  for a single entry. Planning may settle this.
- **The second `server/` module's name and its single export.** Not ruled;
  settle at planning. Note that `resolver.py` is a poor choice despite fitting —
  `binding.yaml` refuses a `resolver:` key **by name**, and a module of that name
  beside the deployment would read as the thing that was ruled out.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`_contained()` in `binding_document.py`** already implements exactly the
  refusals D-10 needs (absolute path, `..` segment, symlink escape). D-10 is a
  different *base*, not a different rule — pass `root.parent` rather than widen
  the check.
- **`connection.database_path`'s `{path: …}` form** is the precedent for a key
  whose base is stated rather than assumed: it exists because "the deployment
  root is not known until a client names it." `server:`'s parent-relative
  resolution is the same move.
- **`server/egress-door.yaml` + `door_values()`** already model "the door's own
  governance values, read strictly from a document." D-11 keeps this pair on the
  door side of the cut.

### Established Patterns
- **Refuse by name, never by shape alone.** `RULED_OUT_KEYS` exists because a
  refusal reading "unknown key" would look like a typo report. D-06, D-07 and
  D-08's messages are written in that register.
- **A gate that stops checking without going red is the defect.**
  `assert_one_python_module` uses `!= 1` rather than `> 1` for exactly this
  reason, and `check_example_budget` fails on zero matches. Any new check this
  phase adds inherits the standard.
- **Every refusal is driven end-to-end through `ProductClient.ask`** from a
  `CCF_BINDING` environment variable, because a refusal that fires in a loader
  and is then caught or never called is a gate wired to nothing.

### Integration Points
- `mcp_stdio._declared()` is where D-06, D-07 and D-08 all land, and where the
  `server:` value is read off the loaded document.
- `binding_document.py`'s `OPTIONAL_KEYS` and header prose are where D-01 and
  D-10 land.
- The README ↔ Makefile character-identity gate is the tightest coupling in the
  phase: the two binding strings, two recipes and two README blocks move as one.

### Measured facts worth carrying into planning
- `serve.py` is 292 lines: module docstring 1–70, imports to ~110,
  `door_values()` 123–149 (27), `serve()` 152–288 (137), 18 standalone comments,
  32 blank. The roadmap's "~180 lines of composition, ~35 of MCP server" is
  approximately `serve()` + `door_values()` + imports; **~30% of the file is
  prose about itself**, which no amount of moving composition out will shrink.
- After the change the two documented commands differ by **one word** — the
  scheme — against a byte-identical remainder. That makes "nothing but
  `CCF_BINDING` differs" visible rather than asserted (D-15 depends on this).
