# Phase 24.10 Plan 03: The Acquisition Boundary Emits Envelopes — Summary

**The seam already existed.** `R-09` was raised on the belief that the SDK had
no acquisition boundary for an external store. It has one —
`ccf.signal.source.SignalSourceProtocol` — and the measurement that establishes
it also drove cp-05's real source through it to **77 entities and 100
relationship claims** off L3. No new Protocol was declared, none was proposed,
and `D-IMPL-277` is resolved by **discoverability** rather than by new surface.

## The outcome, stated first

This was a **dual-outcome plan**. It ended in **OUTCOME A — REUSE**, which was
the presumed path under `D-IMPL-283` (2). Outcome B (propose a new surface and
halt for Dave's ruling) did not obtain, because the measurement did not support
it. Nothing was shipped on a presumption and nothing is awaiting a ruling.

## The measurement — task 1, step 1

Taken **before any file was written**, by constructing a throwaway
deployment-side adapter over `SignalSourceProtocol` and running it, not by
reading a signature and reasoning about it.

The adapter's constructor took cp-05's acquisition parameters
(`system_id`, `anchor_node`, `depth`, `follow_guarantees`,
`follow_cross_default`); its `envelopes(*, tenant_id)` yielded the envelopes
those parameters select.

| Question | Answer |
| --- | --- |
| `isinstance(adapter, SignalSourceProtocol)` | **`True`** |
| `adapter.source_identity()` | `SourceIdentity(system_id='exposure_graph')` |
| Did it produce envelopes for a parameterized acquisition? | **Yes — 77 node envelopes, 100 edge envelopes** |
| What could the constructor-state bridge not carry? | **Nothing** |

Command:
`PYTHONPATH=.:src:runtime .venv/bin/python <scratch>/measure_seam.py`
(throwaway, never committed; the shipped equivalent is
`tests/signal_layer/test_cp05_acquisition_boundary.py::test_the_live_acquisition_conforms_to_the_existing_seam`).

**The verdict:** the difference between the Protocol's async, tenant-only
signature and cp-05's synchronous, question-parameterized acquisition is not a
reason for a second Protocol. The parameters are constructor state. A
deployment constructs its source *for a question*, and the fabric asks the
constructed object for its envelopes under the one parameter the Protocol
carries. `MCPSourceAdapter` was the existence proof to test against and it uses
exactly this pattern for its `resources` selection.

**One instrument error, recorded because it nearly became a finding.** The
first two runs returned 5 nodes and then 2, and read like a small family. The
cause was the `FIBO` base IRI: I used `http://example.org/fibo` where the
ledger uses `https://spec.edmcouncil.org/fibo/ontology` for the three FIBO
predicates. cp-05's own `deployment.py` warns about precisely this class of
mistake — *"an earlier pass probed with the vault's prose labels … and measured
zero edges, which looked like a spec/estate divergence and was an instrument
error."* Corrected against the ledger, the same adapter returned 77 and 100. A
wrong number about the wrong predicate set survives re-checking; the anchor
resolution and the predicate IRIs are now both read from the estate in the
shipped harness rather than assumed.

## Findings

### `24.10-F-04` — a Protocol nobody could find is a different defect from a Protocol that does not exist

`R-09` was raised on cp-05's note at `assembler.py::acquire_edges`: *"Hand-rolled
because the SDK has no acquisition boundary for an external graph store — every
adapter in `ccf.graph.backends` is an L3 substrate the fabric OWNS."* That
sentence is **correct about the graph backends and imprecise about L1**. The
seam existed the whole time, one import away, with a conforming adapter beside
it. The `CP-05-SDK-CHANGE-PROPOSALS` row recording the current surface as
*"Nothing"* inherited the same imprecision.

The fix for "cannot be found" is not a new Protocol; it is the module docstring
an author will actually reach, which is what shipped. **`R-03` is the row that
measures discoverability**, and this row does not pre-empt that measurement —
it hands `R-03` one concrete, dated data point.

### `24.10-F-05` — the resolution half cannot express an edge between two entities that already exist in L3

**Measured against a real fabric, not inherited from cp-04's `D-35` note.** An
entity URI is `f"{entity_class}://{content_hash(identity)}"` where `identity`
is `{key: value}` over the rule's `identity_keys` — so the identity hash covers
the identity **key name**, not just its value.

Two probes, both booting a *copy* of cp-05's Control Plane document with its
resolution section varied (cp-05 itself never written), each minting two
entities the ordinary way and then pushing one edge envelope at `ingest`:

| Probe | Entity rules | Entities before → after | Relationships |
| --- | --- | --- | --- |
| Same identity key | both endpoints keyed on `entity_uri` | 2 → 3 | **0** — one URI twice, the self-loop is dropped |
| Distinct key names | `subject_uri` / `object_uri` | 2 → **4** | **1** — between two brand-new entities, **neither** of the two that existed |

So an edge envelope can only join entities the *same envelope* resolved, and
cp-05's edges join entities minted by earlier envelopes.

**Not worked around.** The edges reach L3 through
`AssemblyWorker.admit_relationship_claim` — the **admission** half of the same
L1→L2 path, still L2, still the single writer — which is where all 100 landed.
The evidence is executable at
`tests/signal_layer/test_cp05_acquisition_boundary.py::test_the_resolution_half_cannot_express_an_edge_between_existing_entities`,
and it is written to go **red the day the seam changes**: sabotage-verified by
inverting its assertion to the fixed-SDK world, which fails.

**This is a finding, not a request.** It proposes no surface and asks for no
ruling; `D-15` explicitly names *"the existing L1→L2 resolution/admission
path"*, both halves, and the admission half is sufficient.
