## Sitting 2 — the four gray areas (`D-IMPL-282`)

**The order, confirmed and reasoned:**

> *"Yes — use the endorsed order: `R-12` → `R-11` → `R-09` → `R-03`"*

> *"The earlier sequence table is superseded by the four explicit rulings that followed it. `R-03`
> is last by design; `R-12` and `R-11` are independent, and I prefer `R-12` first because it is
> smaller and establishes the deployment-binding pattern before we add another resolver extension
> seam."*

### `R-11` — option 1a

> *"1a. Use a Protocol-typed callable supplied to `build_governed_resolver`, analogous to
> `debt_scorer`. The gate identity/version remain declared in the Control Plane; implementation is
> deployment-supplied. Add a distinct product-gate refusal kind so runtime gate failure is
> distinguishable in replay/audit. Do not add an expression language and do not expand
> `GATE_DECLARED_OBLIGATIONS`."*

**The boundary on it:**

> *"For `R-11`, the runtime gate is not a new universal policy vocabulary. It is a declared product
> invariant with a governed identity, whose implementation is supplied by the deployment. It
> executes after candidate construction and before fitness/fulfillment. Replay should be able to
> say which gate ran and, if it refused, which gate produced the refusal."*

### `R-12` — option 2a

> *"2a. The `replay:` Control Plane section supplies defaults. Explicit constructor arguments
> override the declaration. No builder API break in 24.10. The declared binding must actually be
> consumed and exercised; declaration-only is insufficient."*

**The precedence, explicit:**

> *"explicit builder argument > Control Plane replay binding > no binding/refusal according to
> existing availability semantics"*

> *"Do not silently invent a replay backend when neither source provides one."*

### `R-09` — option 3a

> *"3a. Acquisition emits `SignalEnvelope`s only. Reuse the existing L1→L2 resolution/admission
> path to produce entities and relationship claims. Do not create a second relationship-claim
> output unless real evidence shows the existing envelope/resolution mechanism cannot express
> cp-05's edges. Ship the small file/fixture-backed reference implementation required by the SDK
> convention; use cp-05's real SPARQL only from the test harness to preserve the 77/100 evidence
> without putting domain logic in `src/`."*

**On the measurement that shaped it:**

> *"For `R-09`, your measurement makes the design much cleaner. `SignalEnvelope.raw_payload` is
> already the right acquisition vessel. The acquisition abstraction should answer how external
> source records enter CCF, not create a parallel normalization subsystem."*

> *"4a. Rewire s1-01 onto `GovernedResolver`. I am ruling s1-01 open for this purpose. It is
> already the SDK's teaching example for this seam, so leaving it hand-building a 617-line spine

> the same instrument as `R-04`."*
