**The stop rule is NOT met. cp-05 cannot use the canonical SDK path.** Driven
unchanged through `GovernedResolver`, cp-05's shipped declarations return a
**served product describing a family of 0** over an L3 holding **77 entities
and 100 relationship claims** — every universal gate green, a content address

`D-IMPL-280`'s stop rule, quoted again by Dave in `D-IMPL-281`:

> *"When **cp-05** can use the canonical SDK path without rebuilding fabric
> behavior itself, Phase 24.10 stops."*

**It cannot.** The escalation branch of `R-03`'s success criterion is the one

> `plan_factory` and the debt scorer, then the SDK architecture is

seam is live on cp-05's path and carries cp-05's own declared invariant, with
its positive control. `R-12` worked — the declared binding supplied the store,

not surviving parallel governance code; it is that **cp-05's declared policy
envelope has nowhere to be bound to the question being asked**, and the result
is not a refusal but a wrong answer.

**No redesign was started.** `D-25` / `D-IMPL-282`: *"No broader API redesign
is authorized up front."* What these two findings earn is Dave's ruling.
**cp-05 was not rewired** — that is the post-phase adoption step, described in
this document and not performed.

### `24.10-F-11` — a declared operator envelope cannot be bound to the question

**`GovernedResolver` reads its operator-parameters artifacts verbatim off
`BootedFabric.artifacts` by key, with no request in scope.**

```python
def _operator_parameters(self) -> dict[str, OperatorParametersArtifact]:
    """The adopter-side idiom: name your own keys, no type filtering."""
    return {
        key: self._artifact(key, OperatorParametersArtifact)
        for key in self.operator_parameter_keys
    }
```

cp-05 declares `permitted_classifications: []` **on purpose**, and says so in
its own words:

> *"BIND THIS REQUEST'S FAMILY ONTO THE DECLARED POLICY ENVELOPE. The
> declaration is empty on purpose and admits nothing; the substitution is what
> makes it admit THIS family and no other. Two families are two parameter-set
> hashes and therefore two content addresses, so the replay record says WHICH
> family a decision admitted rather than leaving it to be inferred from the
> payload."*

On the canonical path the empty declaration stands. The policy operator admits
nothing, the traversal chains from its empty output, and:

| | family served | L3 entities | L3 relationship claims |
| --- | --- | --- | --- |
| **cp-05's declarations, unbridged** | **0** | 77 | 100 |
| the same run with cp-05's own per-request substitution | **77** | 77 | 100 |

**This is not a thinner answer. It is a wrong one.** The product is *served*:
all three universal gates pass, `refuse_over_tolerance` does not withhold, a
content address is minted and a replay record is filed under the declared
store. cp-05's own spine would have refused — its first validation gate raises
on `family_size == 0` — and the canonical path has no equivalent, correctly:
`D-IMPL-242` amendment 1 and `D-IMPL-253` Q11/Q12 rule that an operator that
*ran* and returned nothing computed something, and it is served as a finding
rather than refused on cardinality.

**Credit where the SDK is right, stated so the finding is not overstated.** The
record is *not* silent: the served product carries

```
computed_empty=ComputedEmptyFinding(
    operators_returned_empty=frozenset({'policy.principal-subgraph',
                                        'traversal.typed-neighborhood'}),
    operators_invoked=frozenset({'policy.principal-subgraph',
                                 'traversal.typed-neighborhood'}),
    emptiness='attested')
```

so an examiner reading the record can see that both operators returned nothing.
The defect is upstream of that: the declaration cp-05 authored cannot express
the per-request binding, so the emptiness happens at all.

**The workaround, measured rather than assumed, and why it is not a seam.**
`BootedFabric` is a frozen dataclass whose `artifacts` field holds a **plain
mutable `dict`** — verified: `f.artifacts["x"] = 1` succeeds and
`dataclasses.replace(f, artifacts={...})` succeeds. So a deployment *can* reach
the right answer, by mutating a frozen type's field through the mutable object
it happens to hold, or by re-booting a fabric and rebuilding a resolver per
question. Neither is a declared seam; the first reaches around the type's own
frozen-ness, and the second makes a per-question boot the price of a
per-question policy envelope.

### `24.10-F-12` — a declaration admitted at boot is refused at builder time

cp-05's `request_contract` section authors `unsupported_arguments` as a **list**
(`- as_of`). `load_config_and_boot` **admits** the document without complaint —
the section is an adopter-owned `DeclaredArtifact` whose `declaration` body is
opaque at boot. `build_governed_resolver` then raises, three frames down:

```
ValueError: the declared artifact 'cp-05.request-contract' at lane '1.0.0'
carries 'unsupported_arguments' as list, and it must be a mapping of parameter
name to the declared reason prose — the shape the four ladder configs already
author (Standard §2.4, 24.5-L-13)
    raised by src/ccf/products/request.py::ProductRequestContract.from_declared
    called from src/ccf/products/resolver.py::build_governed_resolver
```

Measured, and the asymmetry is the finding: `cp-01` through `cp-04` all author
the mapping shape; cp-05 — the newest rung — authors the list, and its own
`deployment.py::request_contract` reshapes it in Python on the way to the same
typed contract. **The refusal itself is right** (a reason string is what makes
a refusal sayable). What is wrong is *where* it lands: a Control Plane that
admits a declaration the canonical reader cannot read has deferred a document
defect from boot to a builder call, which is the posture `D-IMPL-258` (5)
already corrected once for a different pair of documents — *"should fail
registration/configuration/boot validation, not produce a shell to a caller."*

The adoption consequence is arithmetic: **three config changes, not two**.

The plan's `<no_surface_fragment>` block asks that

### `[Scoped out]` The payload-shape difference, observed and not numbered

Under the resolver a product's payload is `execution.projection.payload` and
nothing else, so everything cp-05's own payload carries beside the projection —
`anchor`, `measures`, `guarantee_dedup`, `findings`, `reconciliation`,

reachable through the closure. `context_debt` cannot, because the resolver

rather than in the payload — which is arguably the better place for it. **This
changes cp-05's content address**, which bears on `R-03`'s *"without changing
its business result"* clause. Recorded as an observation rather than promoted
into the roster: it is a representational consequence of adopting the
composition, it was not measured against a rewired cp-05, and a finding
authored from a structural reading rather than a measurement is the instrument
error this tree has caught in itself before.
