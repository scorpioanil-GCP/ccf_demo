## Implementation Decisions

Two sittings, both 2026-09-08. **`24.10-RULINGS.md` carries Dave's words verbatim and GOVERNS over this file.** `docs/DECISIONS.md` `D-IMPL-281` (scope, order, boundary) and `D-IMPL-282` (the four gray areas) are the log entries.

### Order and sequencing
- **D-01:** Order is **`R-12` → `R-11` → `R-09` → `R-03`**. His reason: *"`R-12` and `R-11` are independent, and I prefer `R-12` first because it is smaller and establishes the deployment-binding pattern before we add another resolver extension seam."* The earlier sequence table in the same message is **superseded** by the four explicit rulings that followed it.
- **D-02:** `R-03` is last **by design** — it measures the phase rather than prejudging it.

### `R-12` — Control Plane replay binding (option 2a)
- **D-03:** The `replay:` section **supplies defaults**; explicit constructor arguments override the declaration. **No builder API break in 24.10.**
- **D-04:** Precedence is explicit and must be implemented as stated: **explicit builder argument > Control Plane replay binding > no binding/refusal according to existing availability semantics.**
- **D-05:** *"Do not silently invent a replay backend when neither source provides one."*
- **D-06:** *"The declared binding must actually be consumed and exercised; declaration-only is insufficient."* A section that boots but changes nothing does not discharge this row.
- **D-07:** Binding **only** — record class, query-pin class, store selection. *"No product-specific replay semantics in the Control Plane—only deployment binding/configuration."*

### `R-11` — runtime product-gate seam (option 1a)
- **D-08:** A **Protocol-typed callable supplied to `build_governed_resolver`, analogous to `debt_scorer`.** Implementation is deployment-supplied.
- **D-09:** **Gate identity and version remain declared in the Control Plane** — so `D-IMPL-224`'s CI-checked declaration still governs and replay can name the gate. Two halves: declaration governed, implementation supplied.
- **D-10:** **Add a distinct product-gate refusal kind** so a runtime gate failure is distinguishable in replay/audit.
- **D-11:** **Do not add an expression language. Do not expand `GATE_DECLARED_OBLIGATIONS`.** Its `obligation: Literal["lineage-inputs"]` stays a closed SDK-owned vocabulary.
- **D-12:** Execution point: *"after candidate construction and before fitness/fulfillment."* Concretely, between `run_gates` returning a `ServableProduct` and `refuse_over_tolerance`.
- **D-13:** What it is, in his framing: *"the runtime gate is not a new universal policy vocabulary. It is a declared product invariant with a governed identity, whose implementation is supplied by the deployment."*
- **D-14:** Replay obligation: *"Replay should be able to say which gate ran and, if it refused, which gate produced the refusal."*

### `R-09` — acquisition boundary (option 3a)
- **D-15:** **Acquisition emits `SignalEnvelope`s only.** Reuse the existing L1→L2 resolution/admission path to produce entities and relationship claims.
- **D-16:** **Do not create a second relationship-claim output** unless real evidence shows the existing envelope/resolution mechanism cannot express cp-05's edges. If such evidence appears, it is preserved and classified — not worked around.
- **D-17:** Ship the **small file/fixture-backed reference implementation** SDK convention requires (CLAUDE.md §11).
- **D-18:** **cp-05's real SPARQL runs only from the test harness** — preserving the 77/100 evidence without putting domain logic in `src/`.
- **D-19:** The required evidence, unchanged: *"same external source → acquisition boundary → 77 nodes / 100 relationship claims."*
- **D-20:** The design principle: *"The acquisition abstraction should answer how external source records enter CCF, not create a parallel normalization subsystem."*

### `R-03` — canonical author path (option 4a)
- **D-21:** **Rewire s1-01 onto `GovernedResolver`.** s1-01 is ruled OPEN for this purpose. *"It is already the SDK's teaching example for this seam, so leaving it hand-building a 617-line spine would directly undermine the remediation."*
- **D-22:** **Measure before/after executable-line count using the same instrument as `R-04`** — blank lines, comments and docstrings excluded, the instrument that produced the 204-vs-260 door measurement, so the numbers are comparable.
- **D-23:** **The constraint on the rewrite:** *"do not change s1-01's business behavior merely to make the resolver fit. If adopting `GovernedResolver` exposes a missing seam, preserve the evidence and classify it rather than working around the resolver."*
- **D-24:** The test this row IS: *"If the SDK's own canonical worked example can move from a hand-built 617-line governed spine to `GovernedResolver` with materially less plumbing, the surface has demonstrated usability. If it cannot, `R-03` has earned escalation beyond docstrings."*
- **D-25:** **No broader API redesign is authorized up front.** Escalation is earned by a measured failure of the cheap change, never assumed.

## Existing Code Insights

### Reusable assets
- **`debt_scorer` / `plan_factory` on `build_governed_resolver`** — the established seam for deployment-supplied mechanism, and D-08's explicit model for `R-11`. Copy the shape, do not invent a new one.
- **`GateRefusal` and its six subclasses** — `R-11`'s distinct refusal kind (D-10) is a seventh sibling, not a new hierarchy. Because `run_gates` already returns `ServableProduct | GateRefusal` and the resolver's refusal-recording path at `resolver.py:1483` already handles a `GateRefusal`, a conforming subclass reaches replay through machinery that already exists.
- **`_refuse_operator_set_divergence`** — the boot-time refusal shape, comparing two declarations and refusing rather than picking. `R-10` already followed it; `R-12`'s validation should read like it.
- **`SignalEnvelope.raw_payload`** — the acquisition vessel D-20 names. The L1→L2 resolution spec already turns source vocabulary into entities and relationships, which is exactly why D-15/D-16 refuse a second output type.

### Established patterns
- **Protocols with a shipped reference implementation** (CLAUDE.md §11) — binding on `R-09` (D-17).
- **Closed vocabularies stay SDK-owned.** `GATE_DECLARED_OBLIGATIONS`'s one-member `Literal` and `_RESERVED_SECTIONS`'s 8-entry map are both deliberately closed so that extending them is an SDK decision, never a deployment's. `R-11` must not widen the first; `R-12` widens the second by exactly one entry.
- **Refusals are values, not exceptions**, carrying the lineage the candidate claimed.
- **Boot-time refusal over runtime surprise** — validate what is statically provable, never infer dynamic cardinality (`D-IMPL-279` R-10).

### Integration points and the measurements that ground them
- **cp-05 references `GovernedResolver` zero times**; its spine is **2,553 lines** across five `.py` files. Measured on this branch.
- **s1-01's `spine.py` is 617 lines and does not use `GovernedResolver` either** — a second, independent instance of `R-03`'s pattern, found during this phase's scout and not present in either working document. It is what made D-21 possible.
- **`build_governed_resolver` takes 12 required + 7 optional keyword arguments** — the adoption-surface fact `R-03` is measuring.
- **Test baseline on this branch:** `tests/deployment` + `tests/replay` + `tests/products` + `tests/invariants` = **2,599 passed**, one red — `test_the_document_is_unchanged_since_the_phase_base[CLAUDE.md]`, which **also fails on `main`** and is out of scope. `make lint` green. Anything else going red is this phase's doing.
- **`main` has been red since 2026-08-26** from three causes originating in 24.5/24.6. Local green does not mean `main` is green; do not read CI on `main` as a signal about this branch.
