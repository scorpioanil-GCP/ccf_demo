# Phase 24.10 Plan 01: The Control Plane Declares the Replay Binding — Summary

A deployment's replay binding now has a declared home in the Control Plane —
a `replay:` section deriving a `ccf.replay-binding` artifact — and
`build_governed_resolver` consumes it under the ruled per-member precedence,
proved by a served product's decision record landing in a store the test roots
where the declaration said and the SDK never saw.

## What cp-05 measured, and what this closes

`examples/cp-05-credit-exposure-rollup/artifacts/replay.yaml` — read under the
phase boundary, never edited — records the finding in its own words: the
Control Plane document's section vocabulary is closed and a `replay:` section
is refused by name, so *"it leaves a deployment's own replay binding with
nowhere declared to live. cp-04 put these three strings in `deployment.py` as
module constants; this rung puts them in an artifact instead. Neither is the
Control Plane."*

The ruling executed is `D-IMPL-282` `R-12` option 2a (Dave, 2026-09-08):

> *"The `replay:` Control Plane section supplies defaults. Explicit constructor
> arguments override the declaration. No builder API break in 24.10. The
> declared binding must actually be consumed and exercised; declaration-only is
> insufficient."*

> *"explicit builder argument > Control Plane replay binding > no
> binding/refusal according to existing availability semantics"*

> *"Do not silently invent a replay backend when neither source provides one."*

> *"No product-specific replay semantics in the Control Plane—only deployment
> binding/configuration."*

### The `D-06` bar, specifically

The test that carries the row does **not** read the resolver's fields and stop
there. It builds a resolver with no `replay_record_class`, no `query_pin_class`
and no `artifact_store` — only `artifact_store_root` — serves a real product,
then:

1. asserts `served.replay_ref.artifact_class == "ccf.cp-05.decision-replay-record"`,
   the class the **Control Plane** declared and the call named nowhere;
2. builds a `FileArtifactStore` rooted at `root / "artifacts-store"` — a store
   object the SDK never saw — and resolves the served product's replay URI out
   of it, asserting the resolved address equals the reference's own content
   address;
3. carries a control (`test_the_landing_control_fires_on_a_store_rooted_anywhere_else`)
   proving the same lookup **fails** one directory over, so what (2) measured is
   the declared location and not the mere existence of a record.

## The threat register's one `mitigate` disposition

`T-24.10-01-01` (Tampering, `ReplayBinding.store_dirname`) is mitigated by a
field validator, and the mitigation is carried by
`test_a_store_dirname_that_leaves_its_root_is_refused_by_name` over six cases
(`/tmp/x`, `/var/lib/ccf`, `../x`, `a/../../x`, `..`, `sub/../../out`) plus
three containment controls (`artifacts-store`, `a/b`, `./a`) that a
refuse-everything validator would fail.

**Deviation from the plan's letter, for the better:** the plan asked for a new
validator refusing an absolute path and any `..` segment. The tree already
carries that exact predicate — `_leaves_its_own_directory`, which
`ManifestEntry.path` is held to and which additionally refuses rooted and
drive-qualified names on **both** path flavors so the refusal is
platform-invariant. Writing a second, weaker copy would have been two answers to
one question. The predicate and `_PATH_FLAVOURS` were moved up-module (no
behavior change, `ManifestEntry` still calls the same function) so the new class
can reach it.

## Deviations from the plan

### 1. `[Rule 1 - Bug]` `ReplayBinding` is NOT added to `SDK_VERSIONED_ARTIFACT_CLASSES`

- **Found during:** Task 1.
- **The plan said:** *"plus entries in both `SDK_ARTIFACT_CLASSES` and
  `SDK_VERSIONED_ARTIFACT_CLASSES`."*
- **Why that is wrong:** the two mappings are **disjoint by construction** and
  the tree asserts it —
  `tests/deployment/test_class_lookup.py::test_the_two_sdk_mappings_are_disjoint_and_both_precede_the_envelope`.
  `SDK_VERSIONED_ARTIFACT_CLASSES` means *the contract declares a string
  `artifact_version`*, which `ReplayBinding` does not (it inherits
  `VersionedArtifact`'s single `semver` lane, exactly as `DebtProfile` and
  `HalfLifeTable` do). Adding it to both would have made
  `refuse_registration_the_sdk_fixes` refuse the class for declaring `typed`
  **and** for declaring `versioned`, and would have tripped
  `test_every_author_versioned_class_is_in_the_versioned_mapping`'s stowaway
  assertion.
- **What was done:** registered in `SDK_ARTIFACT_CLASSES` only, beside
  `DEBT_PROFILE` and `POLICY_CONSTRAINT`, with a comment saying why the section
  derivation additionally requires it.
- **Commit:** `d4847616`.

### 2. `[Rule 3 - Blocking]` CINV-06 fired; the field is declared hash-transparent and the claim is measured

- **Found during:** Task 1, on `make lint`.
- **Issue:** `DeploymentConfig.replay declares a default and no
  'ccf_hash_transparent' key`.
- **Fix:** declared `HASH_TRANSPARENT_KEY: True` — `policy_constraints`'
  reasoning, unchanged: a rendered `replay: null` would move the content
  address of every `DeploymentConfig` already written, and pin identity **is**
  content identity. Added to the roster in
  `tests/contracts/test_hash_transparency.py` and measured by a new
  `test_a_config_naming_no_replay_binding_hashes_as_it_did`, with the
  positive control (a config that *does* declare a binding moves, and the key
  appears in its bytes).
- **Also fixed:** `test_a_config_naming_no_constraints_hashes_as_it_did` built
  its "before" side by excluding one named field, so a second transparent
  section made it red without anything having gone wrong. It now reads the
  exclusion set off `hash_transparent_fields(DeploymentConfig)` and asserts
  `policy_constraints` is in it, which keeps the non-vacuity the named field
  gave it. **The assertion was not weakened** — the same equality is asserted
  against the same subject.
- **Commit:** `d4847616`.

### 3. `[Rule 3 - Blocking]` the surface-changes fragment was written in Task 1, not Task 3

### 4. `[Rule 1 - Bug]` the ambiguity refusal is a statement about the CALL

- **Found during:** Task 2, by a control test the plan's behavior text implies
  (*"passing the three arguments explicitly is the stated way out"*).
- **Issue:** my first implementation called `_replay_binding_on(fabric)`
  unconditionally, so a deployment declaring two bindings was refused **even
  when the call named all three arguments** — and the refusal message's own
  claim (*"this call omits at least one of…"*) was then false.
- **Fix:** the lookup is lazy. A call supplying all three never asks the fabric,
  so the refusal fires on an ambiguous *resolution* and never on a deployment
  that resolved its own ambiguity. Carried by
  `test_two_declared_bindings_are_admitted_when_all_three_are_explicit`.
- **Commit:** `a811c79e`.

### 5. `[Rule 3 - Blocking]` the optional-parameter roster was widened, not loosened

- **Found during:** Task 2.
- **Issue:** `test_the_named_inputs_are_this_helper_s_own_optional_parameters`
  holds `DEBT_SCORER_INPUTS` against *every* parameter of
  `build_governed_resolver` that defaults to `None`, minus a named exclusion
  tuple. Four parameters became optional, so the equality broke.
- **Fix:** the four names were added to `not_debt_scorer_material`, with the
  reason. That tuple is **not** an escape hatch: the test asserts each excluded
  name is actually a parameter and actually defaults to `None`, so a typo fails
  rather than silently widening the comparison. Nothing about the comparison's
  strength changed.
- **Commit:** `a811c79e`.
