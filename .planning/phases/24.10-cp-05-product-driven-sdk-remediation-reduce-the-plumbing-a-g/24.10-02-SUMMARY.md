# Phase 24.10 Plan 02: The Declared Product Gate Runs on the Governed Path — Summary

A product class's own declared invariant now has a legitimate runtime home:
the Control Plane declares its identity, the deployment supplies its
predicate, it runs between admission and fitness, and its refusal is a
seventh `GateRefusal` sibling that reaches replay through machinery that
already existed.

## What cp-05 measured, and what this closes

`examples/cp-05-credit-exposure-rollup/assembler.py::reconciliation_guard` —
read under the phase boundary, never edited — is called from the example's own
spine and would be **stranded** by adopting `GovernedResolver`. Its docstring
states why it matters more than the three universal gates:

> *"Gross must be >= guarantee-adjusted, per group. Adjusted exposure exceeding
> gross is arithmetically impossible; if it happens, step 5.2 removed the same
> exposure twice. … The other three gates catch a broken pipeline. This one
> catches a PLAUSIBLE WRONG ANSWER — the failure mode spec §A says is invisible
> in the output."*

Dave: *"cp-05 cannot honestly adopt the canonical governed spine until its
reconciliation guard has a legitimate runtime home."*

The ruling executed is `D-IMPL-282` `R-11` option 1a (Dave, 2026-09-08):

> *"Use a Protocol-typed callable supplied to `build_governed_resolver`,
> analogous to `debt_scorer`. The gate identity/version remain declared in the
> Control Plane; implementation is deployment-supplied. Add a distinct
> product-gate refusal kind so runtime gate failure is distinguishable in
> replay/audit. Do not add an expression language and do not expand
> `GATE_DECLARED_OBLIGATIONS`."*

> *"the runtime gate is not a new universal policy vocabulary. It is a declared
> product invariant with a governed identity, whose implementation is supplied
> by the deployment. It executes after candidate construction and before
> fitness/fulfillment. Replay should be able to say which gate ran and, if it
> refused, which gate produced the refusal."*

## Claude's Discretion, exercised and recorded

The plan left four things to me. Each choice, and its reason:

| Question | Chosen | Why |
| --- | --- | --- |
| The Protocol's name and module | `ProductGateProtocol` in `ccf.products.resolver`, beside `AssemblyDebtScorerProtocol` | `D-08` names `debt_scorer` as the model; the two seams should be found in one place |
| Its signature | `__call__(self, *, candidate: ContextProductContract, evidence: ExecutionEvidence \| None = None) -> str \| None` | The invariant is a property of the ANSWER, so the answer is what is handed over — unlike debt, which is a property of the assembly and takes the `view` |
| Which of `(candidate, execution, view, evidence)` | `candidate` and `evidence` only | `execution` and `view` are the assembly's facts; a gate that could read them would be a second debt scorer wearing a gate's name |
| The refusal subclass and field set | `ProductInvariantRefusal(GateRefusal)` adding exactly one field, `gate_version` | The id already has a home — the inherited `gate`. One new field is the smallest thing that lets a record answer *which gate at which version* |

**The return type is the load-bearing choice.** A callable that returned its
own identity could mislabel which gate refused; returning a *detail string*
means the resolver stamps `gate` and `gate_version` from the Control Plane, so
`T-24.10-02-01` (spoofing the gate identity) is closed by the signature rather
than by a rule anybody has to follow.

### The record field the version pin was read from

`D-14`'s admitted half resolves the declaration at
**`record.content_generation_path.request.schema_name` and
`.schema_version`** — the question as asked, carried on the served
determination's own `DecisionReplayRecord`, where `schema_version` is the
product class's own semver lane (INV-CH7-49). The resolution walks the same
`ControlPlaneRegistry` the resolver read from (`keys_of_class` → `versions` →
`peek`) and selects on that pinned pair; `resolve_latest` is never called
except in the control, where it deliberately returns a *different* gate id.

`_applied_bindings` (`src/ccf/products/resolver.py:1739`) correctly mints no
separate binding row for the product class: it emits rows for constraint
artifacts, the request contract's own pin and a verified entitlement override,
and adding a fourth would mint a second pin for a thing the record already
pins. The gate identity is **declared** rather than per-determination, so
pinning the declaration pins the gate.

## Deviations from the plan

### 1. `[Rule 3 - Blocking]` the disclosure layer needed two entries the plan did not name

- **Found during:** Task 1, on `pytest tests/http_api`.
- **Issue:** `ValueError: no external statement is declared for the refusal
  kind 'product-invariant-refusal'`. `src/ccf/products/disclosure.py` holds
  `EXTERNAL_STATEMENTS` and `PERMITTED_AT_MINIMAL`, both closed by set equality
  against `REFUSAL_KINDS`, so a new kind cannot cross a door without both.
- **Fix:** an external sentence naming the FACT and not the invariant — *"an
  invariant the product class declares does not hold for this product"* —
  because a sentence that paraphrased the deployment's own predicate would put
  a product's logic on a consumer boundary. And `frozenset()` at `minimal`: the
  kind declares one field, the gate's declared lane, and it fails that table's
  own rule on both halves (a caller can do nothing with a version, and it
  states nothing the caller must satisfy). The gate **id** still crosses at
  every level as the promoted `reason`, so a consumer can name what refused.
- **Consequence, asserted rather than left implicit:**
  `test_the_guard_refuses_a_rollup_whose_adjusted_exceeds_its_gross` asserts the
  returned shell carries `gate_version` **present and withheld**, and test 3
  asserts the RECORD carries the real lane. `D-14` is discharged in the record,
  which is where an examiner reads it.
- **Commit:** `43688e63`.
