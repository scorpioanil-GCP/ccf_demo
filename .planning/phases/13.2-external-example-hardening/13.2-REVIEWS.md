# Cross-AI Plan Review — Phase 13.2

## Gemini Review

This review covers the implementation plans for **Phase 13.2: External-Example Hardening**. These plans address residual risks identified during the cross-AI review of the MCP external-consumer example, while executing a core SDK architectural shift ruled by Dave (2026-08-02).

## Summary
The five-plan sequence is a textbook example of high-integrity hardening. It moves from architectural promotion (Plan 01) to deployment composition (Plan 02), followed by a rigorous verification cycle involving live-traffic capture (Plan 03), structural validation (Plan 04), and end-to-end assertion hardening (Plan 05). The strategy is particularly strong in its handling of CI determinism, using request fingerprinting and schema smoke-tests to turn "soft" fixtures into "hard" invariants. The transition of context consumption tools into the SDK default-on surface (D-13) is handled surgically, respecting existing role-separation invariants.

## Strengths
*   **Logical Sequencing:** The "Promotion → Allowlist → Capture → Fingerprint" wave order (identified in RESEARCH Pitfall 1) is correctly maintained across plans. This prevents the immediate invalidation of new fixtures by surface changes.
*   **Structural Integrity:** The use of `anthropic` and `google-genai` Pydantic models for the schema smoke-test (D-01b) is a high-signal way to detect vendor-induced drift without hand-rolling schemas.
*   **Security Discipline:** Plan 03 explicitly mitigates key leakage (T-13.2-06) by ensuring the capture proxy only records bodies, never headers, and includes a human-review checkpoint (Task 3) for the D-10 reviewed event.
*   **Fidelity to Non-Functional Goals:** The "shrink" of `serve.py` in Plan 02 (D-15) directly addresses the "heft" concern for a hello-world example, while the byte-path probe (D-07) in Plan 05 closes a subtle dual-serialization risk.
*   **Zero-Import Enforcement:** Plan 05 correctly maintains the charter's zero-CCF-import requirement for client legs while hardening the assertions that verify it.

## Concerns
*   **API Key Availability (MEDIUM):** As noted in Research Assumption A3, the Gemini/ADK leg capture in Plan 03 depends on a key found in a sibling project's `.env`. If this key is stale or network access is restricted in the execution environment, the Gemini fixtures will remain hand-authored (falling back to 13.1 state).
    *   *Mitigation:* The plan already includes a fallback to keep existing fixtures if the capture fails, ensuring the phase isn't blocked.
*   **Fingerprint Sensitivity (LOW):** The fingerprinting in Plan 04 is strict (message count, tool names). While this is the goal, minor non-functional changes in vendor SDKs (e.g., how they order tool declarations) could cause CI failures.
    *   *Mitigation:* The fingerprint uses `sorted()` tool names, which covers the most likely cause of non-deterministic drift.

## Suggestions
*   **Capture Proxy Longevity:** While Plan 03 describes `capture_proxy.py` as an ephemeral tool, consider keeping it in the repo (as planned) but adding a "Testing/Hardening" section to the top-level `examples/README.md` explaining how to use it for new examples. This utility is high-value for future 10-band/50-band examples.
*   **D-11 Record Location:** In Plan 05, ensure the fresh-venv verification results are clearly appended to the phase-end `13.2-05-SUMMARY.md` as they provide the only "audit log" of the install-path verification.
*   **Schema Smoke-test Scope:** In Plan 04 Task 2, consider asserting that *no* unknown fields exist in the response fixtures (`extra=forbid` style validation), as this helps detect when vendors add new "chattiness" to their responses that might affect context window usage.

## Risk Assessment: LOW
The overall risk is low. Plan 01 (the most architecturally sensitive) is already completed successfully. The remaining plans (02-05) are largely focused on verification and harness hardening. The dependencies are well-understood, the "Don't Hand-Roll" philosophy is strictly applied to diffing and validation, and the rollback/fallback paths for live capture are clearly defined. The phase significantly increases the robustness of the SDK's primary adoption path.

## Codex Review

## Overall Assessment

The five-plan sequence is coherent and mostly achieves Phase 13.2: it respects the critical ordering of SDK promotion → allowlist → live fixture capture → replay fingerprinting → harness hardening. The main risks are not conceptual; they are execution contract risks: `build_experience_server` API compatibility, plan 01’s premature full-suite expectation before `serve.py` is updated, live-capture fragility, and a few places where “optional” tests should be mandatory because they enforce the phase’s core guarantees.

## Plan 13.2-01 — SDK Promotion + Allowlist

### Summary
Strong foundational plan, but it carries the highest API-design risk because it changes the SDK Experience builder surface. The promotion and allowlist belong here, but the plan needs sharper compatibility rules and should avoid requiring full-suite success while `serve.py` is intentionally deferred.

### Strengths
- Correctly puts D-13/D-05 before fixture regeneration.
- Preserves role separation through injected Protocol seams.
- Explicitly avoids fabric/artifact imports in `experience.py`.
- Records the SDK surface decision in `docs/DECISIONS.md`, which matches project discipline.

### Concerns
- **HIGH:** “Default-on” tools plus required provider/description parameters may create a breaking SDK API change. Existing downstream users of `build_experience_server` would now fail at construction.
- **HIGH:** Task 3 says full suite green before plan close, but `serve.py` is deferred to plan 02 and is one of the old-signature callers. That is internally inconsistent unless plan 01 also temporarily updates `serve.py`.
- **MEDIUM:** Allowlist semantics need exact definition: `None` vs empty tuple, unknown tool names, duplicate names, ordering, and whether unknown names fail fast.
- **MEDIUM:** Required deployment-supplied descriptions avoid No-Hardcoding, but the plan should define what happens if descriptions are missing.
- **LOW:** Test requirements focus on advertised tools, but should also assert excluded tool calls fail because the tool is not registered.

### Suggestions
- Define `tool_allowlist: Collection[str] | None = None`, where `None` means all default tools and an empty collection means no tools.
- Fail fast on unknown allowlist entries with a clear `ValueError`.
- Either update `serve.py` minimally in plan 01 or remove `make test`/full-suite acceptance until plan 02.
- Consider default provider stubs that register tools but raise `ExperienceProductNotServable`, if preserving construction compatibility matters.
- Add tests for unknown allowlist names and excluded-tool invocation behavior.

### Risk Assessment
**HIGH.** The architecture is right, but the SDK signature/default behavior needs exact compatibility handling.

## Plan 13.2-02 — Shrink `serve.py`

### Summary
Good follow-through on the promotion. It moves deployment-specific behavior back into composition and makes the example’s tool surface artifact-driven. The plan should tighten validation around the artifact allowlist and avoid relying on line-count reduction as an acceptance signal.

### Strengths
- Correctly removes deployment-side `@server.tool` registrations.
- Keeps descriptions and allowlist in `experience.yaml`, preserving No-Hardcoding.
- Resolves D-06 cleanly by exposing exactly context, lineage, and replay.
- Keeps zero client-side filtering as the enforcement mechanism.

### Concerns
- **MEDIUM:** The plan does not require validation that allowlist entries correspond to known configured tool names.
- **MEDIUM:** Old fixtures may still reflect the pre-allowlist request shape until plan 03. This likely passes before fingerprinting, but the plan should explicitly acknowledge that temporary state.
- **LOW:** “Line count materially reduced” is subjective and not a useful acceptance criterion.
- **LOW:** `grep -c "@server.tool"` catches decorators but not indirect registration; acceptable, but a tools/list assertion is stronger.

### Suggestions
- Add a serve-time validation step: allowlist must be non-empty, unique, and a subset of configured tool names.
- Replace line-count acceptance with behavior: `tools/list == artifact allowlist`.
- Add an explicit offline note: old fixtures are tolerated until plan 03 because fingerprinting is not active yet.
- Confirm the bare client still retrieves lineage/replay without importing CCF.

### Risk Assessment
**MEDIUM.** Mostly straightforward, but correctness depends on artifact validation and observed MCP tool listing.

## Plan 13.2-03 — Live Capture + Diff Utility

### Summary
This plan addresses the biggest review concern, but it is operationally fragile because it depends on network, API keys, vendor behavior, and capture-proxy correctness. The human checkpoint is appropriate. The plan should tighten capture proxy requirements for Google auth, path forwarding, and response modes.

### Strengths
- Correctly runs after the final allowlisted tool surface exists.
- Bodies-only recording is the right security posture.
- Adds a reusable diff utility without new dependencies.
- Human review gate matches the “reviewed fixture regeneration” requirement.

### Concerns
- **HIGH:** Live capture can fail due to missing keys, network restrictions, quota, model behavior, or vendor API drift. The fallback keeps old Gemini fixtures, which weakens D-01 if not explicitly marked as incomplete.
- **HIGH:** Capture proxy auth handling is under-specified, especially for Gemini. Google APIs may use `x-goog-api-key`, query params, or SDK-specific headers.
- **MEDIUM:** “Commit whatever conversation actually happened” may break client/run assumptions if the fixture count changes.
- **MEDIUM:** Model-name normalization can invalidate request fingerprints later unless replay-time client requests use the same normalized model names.
- **MEDIUM:** The diff workflow needs a clear “raw capture → normalized capture → committed fixture” distinction.
- **LOW:** Grepping for `api[_-]?key` may produce false positives if body fields contain harmless names.

### Suggestions
- Make the proxy forward all non-sensitive client headers needed by SDKs, inject/override auth safely, and never persist headers.
- Add explicit support for non-streaming only, or fail clearly if a streaming response is requested.
- Preserve raw captures under `/tmp` and commit only normalized fixtures; record both raw-vs-current and normalized-vs-current diff summaries.
- If Gemini capture fails, mark D-01a partially incomplete and require Dave approval before proceeding.
- Add a post-capture assertion that fixture counts match what client legs expect, or update the replay logic/client expectations.

### Risk Assessment
**HIGH.** The plan is necessary, but live vendor capture is the least deterministic part of the phase.

- **LOW:** Gemini tool declaration shape may vary; helper should tolerate exactly the pinned SDK shape and fail clearly otherwise.

### Suggestions
- Add a required unit test for happy fingerprint, mismatched fingerprint, missing request fixture, and malformed JSON.
- Implement `_fingerprint_for_path(path, body)` as a separately tested helper.

### Risk Assessment
**MEDIUM.** The direction is solid; the risk is incomplete negative-path testing.

## Plan 13.2-05 — Harness Assertions + Docs/Fresh Venv

### Summary
Good closing plan. It turns several review concerns into standing assertions and finishes with a realistic phase gate. The main risks are MCP response-shape brittleness, external docs verification, and Makefile/fresh-venv interpreter assumptions.

### Strengths

### Concerns

- **MEDIUM:** D-12 requires live web fetch; execution may be blocked by network/tooling. The plan needs a fallback if official docs cannot be fetched.
- **MEDIUM:** Fresh-venv `make example-ext-00` may accidentally use the repo `.venv` if the Makefile hardcodes it.
- **LOW:** Duration output should be stable enough for assertions that grep it, but not over-specified.
- **LOW:** Heading strings in code are fine, but future template reuse would benefit from one shared constant if other examples adopt it.

### Suggestions

- For D-12, specify: if live fetch fails, record the failure and use the prior verified research as fallback only with explicit residual risk.
- Run fresh-venv commands with `PATH=/tmp/.../bin:$PATH` or a Makefile variable override verified from `Makefile`.
- Add an assertion that unauthorized byte-path probes still fail, or confirm existing auth tests cover this.
- Keep the duration line informational: one regex check only.

### Risk Assessment
**MEDIUM.** Good final hardening, with moderate execution risk around tooling and environment assumptions.

# Cross-AI Plan Review: Phase 13.2 External Example Hardening

## Summary
The implementation plan for Phase 13.2 is exceptionally high-fidelity, demonstrating a deep understanding of both the SDK's architectural invariants (role separation) and the specific failure modes of LLM-integrated examples (fixture drift). The plan transforms a "hello-world" example into a production-grade verification suite by implementing request fingerprinting, schema guards, and an artifact-driven allowlist. The sequencing is logically sound, ensuring that server-side surface changes (allowlist/promotion) land before the live capture of fixtures that depend on that surface.

## Strengths
- **Invariant Protection:** The plan explicitly identifies and mitigates the risk of breaking `test_mcp_role_separation.py` by utilizing Protocol injection rather than direct fabric imports in `experience.py`.
- **Fixture Fidelity:** Moving from hand-authored to live-captured fixtures with a dedicated `diff_fixtures` utility solves the "silent drift" problem and creates a professional audit trail (D-10 reviewed event).
- **Logical Sequencing:** The "Wave" structure correctly prevents the "Capture $\rightarrow$ Change $\rightarrow$ Invalid Fixture" loop by ordering SDK promotion and the allowlist before the live capture.
- **Strictness of Verification:** The inclusion of a byte-path probe (D-07) to catch serialization divergence between MCP resources and tools is a high-maturity engineering detail.
- **Zero-Trust Deployment:** The use of a server-side allowlist (D-05) physically removes dangerous tools (like `invoke_agent`) from the advertised surface, rather than relying on client-side discipline.

## Concerns

- **Gemini Key Availability (LOW):** The research identifies that the Google API key is not in the current shell but in a different project's `.env`. While a fallback is provided, if the Gemini leg fails, the "hardening" is only partial.
- **Fingerprint Sensitivity (LOW):** In `13.2-04`, the fingerprinting for Gemini ignores the `model` field because it resides in the URL path. While correct, if the model is changed in the URL but the body remains the same, the replay server will serve the fixture for the wrong model. (Low risk for a v0 example).
- **Fresh-Venv Overhead (LOW):** D-11 is a manual one-off. Given the project's emphasis on CI-enforced invariants, there is a slight risk that "works on my machine" persists if this isn't eventually converted to a permanent CI job, though the plan acknowledges it as a one-off.

## Suggestions
- **Fingerprint Path Inclusion:** In `13.2-04`, explicitly include the URL path in the fingerprint for Gemini requests to ensure the model specified in the URI matches the fixture.
- **Schema Test Location:** The plan suggests `tests/examples/test_ext00_fixture_schemas.py`. Ensure this directory is created if it doesn't exist to avoid `pytest` collection errors.
- **Diff Utility Generalization:** While deferred, the `diff_fixtures.py` utility is clearly valuable. I suggest adding a comment in the code indicating how it should be generalized for the future 10-band/50-band examples to avoid rewrite.

## Risk Assessment: LOW
The risk is low. The plan is grounded in comprehensive research of the existing codebase and official MCP documentation. It adheres to all project invariants and incorporates a robust "trust but verify" approach to LLM fixture management. The dependency chain is clean, and the security model for API keys is strictly enforced.

## Consensus Summary

Four independent reviewers (Gemini, Codex GPT-5, Cursor, Ollama/gemma4) assessed the five-plan sequence. Verdicts: Gemini LOW, Ollama LOW, Cursor MEDIUM, Codex MEDIUM-HIGH. All four judge the architecture, wave ordering, and decision coverage sound; concerns concentrate on execution-contract specifics, not design.

### Agreed Strengths
- **Wave ordering is load-bearing and correct** (all 4): promotion → allowlist → live capture → fingerprint encodes RESEARCH Pitfall 1 in `depends_on`, preventing fixture invalidation.
- **Security posture** (all 4): bodies-only capture proxy (never headers), key-grep gate, human D-10 review checkpoint, server-side allowlist as registration omission rather than client-side filtering.
- **Schema smoke-tests use installed vendor SDK Pydantic models** (Gemini, Codex, Cursor) instead of hand-rolled schemas — detects vendor drift cheaply.
- **Role-separation invariant preserved** via Protocol injection in `experience.py` (Cursor, Ollama, Gemini).
- **Byte-path probe (D-07)** flagged as high-maturity catch for dual-serialization drift (Ollama, Gemini, Codex).

### Agreed Concerns
1. **Gemini live-capture fragility / fallback contradiction** (all 4; HIGH for Codex & Cursor). The API key lives in a sibling project's `.env`; if capture fails, the "keep old Gemini fixtures" fallback contradicts plan 04's fingerprint acceptance — old 4-tool request fixtures would fail fingerprinting and break `make example-ext-00`. Reviewers wanted Gemini capture made a hard gate or an approved request-fixture rewrite path.
2. **Allowlist fail-open semantics** (Codex, Cursor; MEDIUM). Unknown allowlist names silently register nothing; artifact `tools.*.name` can diverge from SDK constants. Reviewers wanted fail-fast `ValueError` on unknown entries and a serve-time assert that artifact names equal SDK constants.
3. **Fingerprint-mismatch test should be mandatory, not optional** (Codex, Cursor; HIGH/MEDIUM). D-03 is core phase behavior; the drift probe belongs in automated verify, plus fail-loud when a response fixture lacks its request sibling.
4. **Capture-proxy under-specification** (Codex, Cursor; MEDIUM): auth-header handling for Google (`x-goog-api-key`/query params), query-string forwarding, and record-only-200+JSON semantics were not pinned down.
5. **Fingerprint sensitivity around Gemini model-in-URL** (Gemini, Ollama, Codex; LOW-MEDIUM): body fingerprint ignores the model since it lives in the URL path; suggested including URL path in the Gemini fingerprint.

### Divergent Views
- **Overall risk**: Gemini and Ollama rate the phase LOW (verification-heavy, good fallbacks); Codex rates MEDIUM-HIGH, driven by the `build_experience_server` API-compatibility break (default-on tools with newly-required provider/description params) — a concern only Codex weighted heavily, with Cursor partially agreeing (prefer optional providers when tools aren't allowlisted).
- **Plan 01 full-suite gate**: Codex called the "full suite green before serve.py update" internally inconsistent; Cursor judged it fine since plan 01 doesn't shrink serve.py yet.
- **CINV-01 coverage**: only Cursor flagged that description parameterization covers the three promoted tools but leaves `list_agents`/`invoke_agent` on docstring prose.
- **D-10 label collision** (13.2 store-isolation vs 13.1 reviewed-regeneration): raised only by Cursor.

### Disposition note
Phase 13.2 executed and verified before this review ran. Several consensus concerns were in fact handled during execution (live capture succeeded for both vendors per 13.2 verification; fingerprint validation landed). Remaining actionable items — allowlist fail-fast semantics, mandatory fingerprint-mismatch unit test, capture-proxy 200+JSON/query-string spec, CINV-01 coverage of agent tools — are candidates for a follow-up hardening pass or Phase 14 documentation of intentional residuals.
