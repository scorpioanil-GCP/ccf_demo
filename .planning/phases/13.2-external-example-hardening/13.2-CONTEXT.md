**Gathered:** 2026-08-02

<domain>
## Phase Boundary

Close the residual risks the four-AI cross review (`.planning/phases/
13.1-external-consumer-examples/13.1-REVIEWS.md`, consensus section)
flagged on the shipped `examples/external/00-hello-context` — and resolve
the one SDK-surface question the review raised. This is hardening plus one
ruled promotion, not a redesign: the phase-13.1 architecture (four client
legs, transport-level replay, bearer auth, fabric-side D-16) stands.

Deliverables in scope:
1. Fixture fidelity: live-captured fixtures, schema smoke-test guard,
   request-fingerprint matching, fixture-diff utility.
2. Tool-surface control: server-side tool allowlist for the example.
3. Assertion hardening in `run.py`: byte-path probe, README heading-name
   check, CI duration annotation; fresh-venv install verification;
   `.mcp.json` snippet verified against current Claude Code docs.
4. **SDK promotion (Dave's ruling, 2026-08-02):** `get_context`,
   `get_lineage`, and `get_replay_record` are promoted from
   deployment-side `serve.py` composition into the SDK Experience surface,
   **enabled by default** — external context consumption is the primary
   adoption path, so the front door serves it out of the box.

Deep financial-services examples (10-band) and SituationalIntelligence
(50-band) remain out of scope.

<decisions>
## Implementation Decisions

### Fixture fidelity (consensus concern #1 — Codex HIGH)
- **D-01:** Do BOTH: (a) regenerate the Anthropic and Gemini/ADK fixtures
  once from real SDK traffic captured through the documented proxy path,
  committed as a D-10 (13.1) reviewed event; and (b) add a permanent
  schema smoke-test that validates fixture request/response shapes against
  the installed SDKs (`anthropic==0.120.2`, ADK/Gemini) so future
  hand-edits cannot drift structurally.
- **D-02:** The executor performs the one-time live capture during phase
  execution, sourcing `ANTHROPIC_API_KEY` and the Google/Gemini key from
  the local environment. Keys are never committed and never stored; only
  the recorded request/response JSON (key-free) lands in `fixtures/`.
  Clarified with Dave: adopters never need API keys — CI and the example
  suite stay fully offline; keys are only for anyone voluntarily running
  live mode, using their own LLM-vendor account.
- **D-03:** Strengthen `replay_server.py` matching beyond ordinal-per-path:
  verify a fingerprint of each incoming request (model, tool names,
  message count) against the recorded `*-request.json` before serving the
  ordinal response — fail loudly on drift instead of serving the wrong
  fixture. Ordinal order retained for readability.
- **D-04:** Build a small fixture-diff utility (compare a live recording
  against checked-in fixtures, highlight JSON diffs) so future D-10
  reviewed events are auditable; document in `fixtures/README.md`. Pays
  off for the 10-band and 50-band examples.

### Tool-surface control (consensus concern #2 — Cursor HIGH)
- **D-05:** Server-side tool allowlist: the example's server exposes only
  the tools this example needs, driven by configuration/env in the
  example's artifacts — the model physically cannot call what is not
  advertised. Deterministic in both CI and live mode; client legs remain
  untouched (13.1 D-06 zero-CCF-imports preserved). No client-side
  filtering.
- **D-06:** How lineage/replay retrieval (13.1 D-15) coexists with the
  allowlist is Claude's discretion — constraint: the bare-leg D-15
  assertion keeps working, and LLM legs need only `get_context`.

### Assertion hardening (consensus concerns #3–#6)
- **D-07:** Add a byte-path probe to `run.py`: templated Experience
  resource bytes must equal `get_context` tool bytes (closes the dual
  serve-path serialization risk).
- **D-08:** Strengthen the README assertion from "exactly seven `##`
  headings" to the seven Phase-13 template heading names in order.
- **D-09:** Log `example-ext-00` wall-clock duration in `run.py` output —
  soft annotation, no gate.
- **D-10:** `.store/` isolation was explicitly NOT selected — leave as-is
  (serve uses a temp fabric DB; noted, not in scope).
- **D-11:** Clean-runner install check: a one-off fresh-venv verification
  during execution (`pip install -e ".[dev]"` → `import anthropic` →
  `make example-ext-00` passes), result recorded in the plan SUMMARY. No
  permanent CI change.
- **D-12:** Verify the docs-only `.mcp.json` snippet (`"type": "http"`,
  `${CCF_TOKEN}` expansion) against current official Claude Code MCP docs
  (web fetch) in this phase; fix `README.md` if wrong.

### SDK promotion (Dave's ruling — new D-IMPL entry required)
- **D-13:** Promote `get_context`, `get_lineage`, and `get_replay_record`
  from deployment-side `serve.py` registration into the SDK Experience
  surface (`runtime/ccf_runtime/mcp/experience.py`), **enabled by
  default**. Rationale (Dave, 2026-08-02): external context consumption is
  the primary adoption path; the front door should serve it out of the box.
- **D-14:** Record this as a new `D-IMPL-NN` entry in `docs/DECISIONS.md`
  with Dave's ruling and date (per CLAUDE.md §15 — SDK-surface changes are
  decision-log matters). Existing tests and examples are updated as needed;
  mypy --strict and full test suite stay green; docstrings cite §8.3/§7.1
  of CLAUDE.md and mark the surface per project convention.
- **D-15:** After promotion, the example's `serve.py` shrinks to
  configuration/composition (enabling, wiring the serve-record store,
  allowlist) — addressing the "651-line hello-world" heft concern.

### Claude's Discretion
- D-15 (13.1) retrieval mechanics under the allowlist (per D-06 above).
- Exact fingerprint fields and failure diagnostics in `replay_server.py`.
- Shape of the schema smoke-test (pytest vs run.py assertion) and where
  the fixture-diff utility lives (`fixtures/` vs a shared location).
- How the default-on tools interact with existing Experience server
  consumers/tests — backward-compatibility mechanics are Claude's to
  design, defaults-on per D-13 is locked.

</decisions>
