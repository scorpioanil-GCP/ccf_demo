## Summary

Everything this phase needs is already in the tree and was verified directly. The example under change is `examples/external/00-hello-context/` (serve.py 651, run.py 538, replay_server.py 141, three client legs 71–97 lines, 8 fixture files + fixtures/README.md). The promotion target `runtime/ccf_runtime/mcp/experience.py` (377 lines) currently registers one templated resource plus `list_agents`/`invoke_agent`, with all behavior injected via three Protocol seams — the promotion must follow the same injected-Protocol pattern because invariant tests (`tests/invariants/test_mcp_role_separation.py`, `tests/crossproc/test_experience_edge.py`) grep the module's source and imports: no graph package imports, no foreign URI schemes, no fabric handles. Only two other callers of `build_experience_server` exist (`tests/crossproc/servers/mcp_experience_child.py` and the example's `serve.py`), so the backward-compat surface for the signature change is small and fully enumerable.

Two findings materially shape plan ordering. First, **the D-05 allowlist changes what `tools/list` advertises, which changes the tool declarations the SDKs embed in every model request** — the current committed `*-request.json` fixtures advertise four tools (`list_agents`, `get_context`, `get_lineage`, `get_replay_record`). Therefore the correct execution order is: promotion (D-13) → allowlist (D-05) → live capture (D-01/D-02) → fingerprint matching (D-03) — capturing fixtures before the allowlist lands would immediately invalidate them. Second, **the D-12 `.mcp.json` verification is already answered**: current official Claude Code docs confirm `"type": "http"` is correct (with `streamable-http` accepted as an alias) and `${VAR}` environment-variable expansion is supported in exactly the `url` and `headers` fields of HTTP server entries — the README snippet (`"type": "http"`, `Authorization: Bearer ${CCF_TOKEN}` in headers) is correct as shipped; the phase task reduces to citing the verification.

No new packages are needed: `anthropic==0.120.2`, `google-adk 2.5.0`, `google-genai 2.14.0`, `mcp 1.28.1` are all installed in `.venv` [VERIFIED: local venv pip list]. Both LLM SDKs ship Pydantic models suitable for the D-01 schema smoke-test (`anthropic.types.Message` and `google.genai.types.GenerateContentResponse` both import and validate — verified by running the venv Python).

**Primary recommendation:** structure the phase as three waves — (1) SDK promotion + allowlist + serve.py shrink + decision-log entry; (2) live capture + fixture regeneration + fingerprint matching + schema smoke-test + diff utility; (3) run.py assertion hardening (byte-path probe, heading names, duration), fresh-venv one-off, README/docs closure.

### Pattern 1: Injected-Protocol tool seams (the promotion pattern)
**What:** `experience.py` registers tools whose behavior is a deployment-supplied Protocol callable — exactly how `product_resolver` / `agent_directory` / `agent_invoker` work today (experience.py lines 286–377).
**When to use:** D-13. The module MUST NOT gain fabric handles: `tests/invariants/test_mcp_role_separation.py::test_the_experience_module_imports_no_graph_package` fails on any graph import, and `test_experience_edge.py` greps the module source for forbidden names. `get_lineage` can be served from the resolver's `ServableProduct.product.lineage` (no new seam strictly required), but `get_replay_record` needs a new injected read seam (e.g., a `ReplayRecordReaderProtocol` returning canonical-JSON bytes of the most-recent record) — the SDK cannot touch the ArtifactStore from this module (role separation: artifact scheme literals are grep-forbidden in experience.py source).
**Key constraint (Claude's discretion area):** how "default-on" interacts with the injected seams. Recommended resolution: the three tools are registered unconditionally by `build_experience_server` (default-ON per Dave), backed by required-or-defaulted provider parameters; existing callers (`mcp_experience_child.py`, example `serve.py`) are the only two call sites to update [VERIFIED: repo-wide grep — exactly two non-test-assertion callers].

### Pattern 2: Allowlist as server-builder configuration (D-05)
**What:** `build_experience_server` gains an exposure/allowlist parameter (tuple of tool names, or a small config contract); tools not in the allowlist are simply never registered — "the model physically cannot call what is not advertised." The example's allowlist values live in `artifacts/experience.yaml` (`[MECHANISM]` key added; prose/values `[ADAPT]`), read by serve.py — No-Hardcoding preserved.
**D-06 recommended resolution:** allowlist for the example = `{get_context, get_lineage, get_replay_record}`; exclude `list_agents`/`invoke_agent` (the example exposes no agents anyway — `agent_exposure.agents: []`). The bare leg's D-15 assertion (lineage + replay retrieval) keeps working because those tools stay advertised; the LLM legs' fixtures will show all three allowlisted tools in the request `tools` array — that is fine, the fixtures force a `get_context`-only script, and the `invoke_agent` live-mode hazard (Cursor HIGH) is eliminated because it is not advertised.
**FastMCP note:** registration-time omission is strictly simpler and more honest than post-hoc tool removal; do not reach for `_tool_manager` internals.

### Pattern 3: Fingerprint-checked ordinal replay (D-03)
**What:** `replay_server.py._load_fixtures` currently skips `*-request.json` (line 68). Change: load them, and before serving ordinal N, compare a fingerprint of the incoming request body against fixture N's recorded request. Recommended fingerprint fields (Claude's discretion, grounded in the actual fixture shapes verified above):
- Anthropic (`/v1/messages`): `model`, sorted `[t["name"] for t in tools]`, `len(messages)`
- Gemini (`:generateContent`): sorted function-declaration names under `tools[0]["functionDeclarations"]`, `len(contents)` (no model field in body — model is in the URL path; optionally fingerprint the path segment)
**Failure mode:** HTTP 500 with a JSON body naming path, ordinal, expected-vs-actual fingerprint — mirroring the existing "fixtures exhausted" loud-fail style.

### Pattern 4: Schema smoke-test against installed SDK types (D-01b)
**What:** a pytest module (recommended over run.py assertion — it runs in `make test` independent of the example harness, and pytest diffs are better diagnostics) that, for each fixture pair:
- `anthropic.types.Message.model_validate(json.loads(anthropic-NN.json))` [VERIFIED: import + class exists in installed 0.120.2]
- `google.genai.types.GenerateContentResponse.model_validate(...)` for `gemini-NN.json` [VERIFIED: name exists in installed google-genai 2.14.0]
- Request sides: validate structural shape (keys/types) — Anthropic request params have TypedDict types (`anthropic.types.MessageCreateParams` region) rather than validating Pydantic models; a structural assertion (required keys present, tools array shape) is the honest check there [ASSUMED: exact TypedDict validation ergonomics — executor should prefer key/shape assertions if model_validate is unavailable for request types].
**Location:** `tests/examples/` if such a home exists, else alongside the example under the path `make test` collects — planner should check where existing example-adjacent tests live (13.1 put assertions in run.py only; a new pytest home is a small decision).

### Pattern 5: Byte-path probe (D-07)
**What:** in run.py, after the legs, open one authenticated MCP session: `read_resource` on the templated/concrete URI (`experience_product_uri(...)`) and `call_tool("get_context", ...)`; assert byte equality of the two bodies. Ground truth for why they can diverge: the resource path returns `canonical_bytes(servable.product)` computed in experience.py (line 341), while `get_context` returns `canonical_bytes(served.product)` from `serve()`'s returned value in serve.py (line 528) — two serializations of what should be the same product. Reuse run.py's existing session helper used for PASS 5 (lineage/replay retrieval).

### Anti-Patterns to Avoid
- **Fabric handles in experience.py** — role-separation and edge tests grep source/imports; the promotion is Protocol seams only.
- **Client-side tool filtering** — explicitly ruled out by D-05; `client_bare.py` currently filters to satisfiable tools, which becomes unnecessary but must not become the mechanism.
- **Hand-editing fixtures during regeneration** — D-01 exists because 13.1's fixtures were hand-authored; the capture must be mechanical, with the diff utility making the review real.
- **Inline tool prose in experience.py** — tool descriptions are deployment values; keep prose artifact-carried (CINV-01/§6.4). Note tension: default-on tools need *some* description at registration. Recommended: descriptions passed as parameters to `build_experience_server` (deployment-supplied, like `server_name`), never authored in the module.

## Common Pitfalls

### Pitfall 1: Capturing fixtures before the allowlist lands
**What goes wrong:** regenerated fixtures embed the old 4-tool (or 5-tool) advertisement; the allowlist then changes `tools/list`, the SDKs send different `tools` arrays, and the new D-03 fingerprint check rejects every request.
**How to avoid:** wave ordering — D-13 promotion and D-05 allowlist land and pass offline CI *before* the live capture. The capture is done against the final server surface.
**Warning signs:** fingerprint failures naming tool-name mismatches immediately after regeneration.

### Pitfall 2: Breaking the two existing `build_experience_server` callers
**What goes wrong:** signature change (new provider params, allowlist param) breaks `tests/crossproc/servers/mcp_experience_child.py` (line 400) and the crossproc edge tests behind it.
**How to avoid:** update the child server in the same task as the signature change; run `pytest tests/crossproc tests/invariants` before the full suite. Backward-compat mechanics are Claude's discretion, but with exactly two callers, explicit updates beat defaulting gymnastics.

### Pitfall 3: Source-grep invariant tests on experience.py
**What goes wrong:** the promotion adds an import or scheme literal that `test_experience_edge.py` / `test_mcp_role_separation.py` grep-forbid (graph package, egress/artifact URI schemes, fabric handles).
**How to avoid:** read both test modules before writing the promotion; keep everything behind Protocols; `get_replay_record` bytes come from an injected reader, never from `ccf.artifacts` imports in this module.

### Pitfall 4: Gemini request bodies carry the model in the URL, not the body
**What goes wrong:** a fingerprint spec of "model, tool names, message count" applied naively to Gemini finds no `model` field in the body [VERIFIED: gemini-00-request.json has only `contents` + `tools`].
**How to avoid:** per-path fingerprint field sets; for Gemini use function-declaration names + contents length (+ optionally the path's model segment).

### Pitfall 5: Live-mode conversation drift during capture
**What goes wrong:** the live model calls tools in a different order/count than the two-turn recorded script (the 13.1 bare-leg `invoke_agent` crash precedent), producing more than two request/response pairs per leg.
**How to avoid:** the allowlist (3 tools, no agents) plus the fixed prompt constrain this, but the capture proxy should record *whatever happens* and the executor commits the actual conversation (renaming ordinals accordingly) — the fixtures README already documents model-name normalization (`claude-fixture`, `gemini-fixture`); keep that normalization step and reflect it in the diff-utility review.

### Pitfall 6: README heading-name check vs template evolution (D-08)
The seven current headings [VERIFIED: grep]: `What this demonstrates`, `Run it`, `The story`, `Artifact-by-artifact`, `Whitepaper / CLAUDE.md sections exercised`, `What to change first`, `What would fail`. run.py PASS 4 currently does `grep -c '^## '` == 7; replace with an ordered exact-name list (source the list from one place so future bands reuse it).
