# Phase 13.2: Code Review Report

**Reviewed:** 2026-08-02
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Reviewed the Phase 13.2 external-example-hardening surface: the promoted
Experience-server tools and `tool_allowlist` in
`runtime/ccf_runtime/mcp/experience.py`, the hello-context deployment
composition (`serve.py`, `replay_server.py`, `run.py`), the fixture tooling
(`capture_proxy.py`, `diff_fixtures.py`), and the cross-process / schema
tests. Invariant checks pass: `experience.py` imports neither
`ccf.artifacts` nor `ccf.graph`, holds no sibling-role URI scheme literal,
carries `__ccf_mode__ = "algorithmic"` with no LLM-client import, and its
promoted-tool descriptions are deployment parameters. The fixtures JSON
secret scan found no API keys, bearer tokens, or credential-shaped values —
`artifacts/tokens.yaml` carries clearly-labeled synthetic demo tokens only.
No Critical findings. Five Warnings concern a CINV-01 inconsistency
(module-authored docstrings become wire-advertised tool prose for the agent
tools), a latent type lie in `serve.py`'s agent directory, an
artifact-vs-constant tool-name seam that can silently empty the allowlist,
error-response fixture pollution in the capture proxy, and a dropped query
string on the forwarded upstream URL.

## Warnings

### WR-01: Agent-tool prose is module-authored via docstrings, contradicting the stated CINV-01 posture

**File:** `runtime/ccf_runtime/mcp/experience.py:479-513` (also `464-471`)
**Issue:** The module docstring (lines 31-37, 48-50) and D-IMPL-74 rationale
commit to "tool prose is never authored here" — which is why
`get_context` / `get_lineage` / `get_replay_record` require
deployment-supplied `*_description` parameters. But `list_agents` (line
480-481) and `invoke_agent` (line 494-506) are registered with **no**
`description=` argument, so FastMCP falls back to the function docstring
("List one tenant's exposed agents with their rendered tool surfaces.",
"Invoke one agent's bound skill through the injected factory path....") as
the wire-advertised tool description. The templated resource
`context_product` (line 465) does the same. That is module-authored prose
on the MCP surface — exactly what the three promoted tools were
parameterized to avoid. `tests/crossproc/test_experience_edge.py` asserts
the *skill-surface* derivation but never asserts the top-level tool
descriptions, so this is unguarded.
**Failure scenario:** A deployment that must localize or govern all
advertised prose (the CINV-01 claim) cannot: the agent tools' descriptions
are fixed English baked into `/runtime`.
**Fix:** Add `list_agents_description` / `invoke_agent_description` (and a
resource description) parameters to `build_experience_server`, mirroring
the three promoted tools, and pass `description=` at registration; or
explicitly document why the agent-tool prose is exempt and pin it with a
test.

### WR-02: `serve.py` agent directory lies about its type and crashes if the artifact ever declares an agent

**File:** `examples/external/00-hello-context/serve.py:550-555`
**Issue:**
```python
def agent_directory(*, tenant: str) -> tuple[()]:
    ...
    return tuple(experience["agent_exposure"]["agents"])
```
The annotation claims an always-empty tuple, but the body returns whatever
the artifact declares. `AgentDirectoryProtocol` requires
`tuple[ExposedAgent, ...]`; if a user follows the artifact's `[ADAPT]`
guidance and adds an agent entry, this returns raw YAML dicts, and
`agent_tool_listing(agent)` (experience.py:346) would fail with
`AttributeError: 'dict' object has no attribute 'skills'` — but only if the
allowlist were also widened, making the failure appear far from its cause.
Under `mypy --strict` the `tuple[()]` annotation vs. the actual
`tuple[Any, ...]` return is also inconsistent.
**Fix:** Either hard-assert emptiness
(`assert not experience["agent_exposure"]["agents"]; return ()`) or parse
entries into `ExposedAgent` and annotate `tuple[ExposedAgent, ...]`.

### WR-03: Artifact-carried tool `name` fields are decorative — renaming them silently breaks the allowlist and the harness

**File:** `examples/external/00-hello-context/artifacts/experience.yaml` (tools/`tool_allowlist`); consumers `serve.py:594-615`, `run.py:557-596`
**Issue:** `build_experience_server` registers tools under the fixed
constants `get_context`/`get_lineage`/`get_replay_record`
(experience.py:127-136); it takes no name parameters. Yet the artifact
carries `tools.<x>.name` fields, `run.py` calls tools by
`experience["tools"][...]["name"]`, and the artifact header marks
"allowlisted tool names" as `[ADAPT]`-safe. If a user renames a tool in the
artifact: (a) the allowlist entry no longer matches any
`EXPERIENCE_TOOLS` member, so the tool is **silently never registered**
(no error — `frozenset` intersection just comes up empty), and (b)
`run.py` calls a nonexistent tool. Fail-open configuration: a typo in
`tool_allowlist` disables a tool with no diagnostic.
**Fix:** In `build_experience_server`, reject allowlist entries not in
`EXPERIENCE_TOOLS` (`unknown = allowed - EXPERIENCE_TOOLS; if unknown:
raise ValueError(...)`), and either remove the artifact `name` fields or
have `serve.py` assert they equal the SDK constants.

### WR-04: Capture proxy records vendor *error* responses as fixtures, consuming ordinals

**File:** `examples/external/00-hello-context/fixtures/capture_proxy.py:92-112`
**Issue:** The request/response pair is written to disk before
`upstream.status_code` is examined. A 429/401/500 vendor error body is
recorded as `<prefix>-NN.json`, permanently occupying ordinal NN; the
retried request then records as NN+1, and the committed fixture set now
contains an error body that `replay_server` will happily serve verbatim to
a client leg (which will fail confusingly, far from the cause). Also
`upstream.json()` (line 101) raises unhandled if the vendor returns
non-JSON (HTML error page, SSE stream), producing a bare 500 with no
diagnostic — inconsistent with the module's fail-loudly posture.
**Fix:** Only write fixture files when `upstream.status_code == 200` and
the body parses as JSON; on error, return the upstream status/body without
recording and log a warning.

### WR-05: Capture proxy drops the request query string when forwarding upstream

**File:** `examples/external/00-hello-context/fixtures/capture_proxy.py:93-95`
**Issue:** `await client.post(f"{base}{path}", ...)` forwards
`request.url.path` only. Any query parameters the SDK appends (google-genai
commonly sends `?alt=...`/`$alt`; either SDK may add query params in future
versions) are silently discarded, changing upstream semantics relative to
what the client sent — the recorded fixture would then not correspond to a
faithful live exchange.
**Fix:** Forward `request.url.path` plus `request.url.query` when present:
`url = f"{base}{path}" + (f"?{request.url.query}" if request.url.query else "")`.

## Info

### IN-01: `_spawn` leaks the stderr file handle

**File:** `examples/external/00-hello-context/run.py:214-219`
**Issue:** `stderr=stderr_path.open("wb")` is never closed; the descriptor
lives until process exit. Harmless in a short-lived harness, but a leak.
**Fix:** Open in a `with`-managed variable and close after `Popen` returns
(the child holds its own dup), or use `contextlib.ExitStack`.

### IN-02: `READY` announcement parsing can raise `IndexError` instead of the crafted `AssertionError`

**File:** `examples/external/00-hello-context/run.py:221-227`
**Issue:** A child printing exactly `"READY "` (or `READY` + garbage)
passes the `startswith("READY ")` guard but `int(announcement.split()[1])`
raises `IndexError`/`ValueError` without the helpful stderr-path message.
**Fix:** Validate with `re.fullmatch(r"READY (\d+)", announcement)`.

### IN-03: `--legs` with an empty selection defeats PASS 5's fallback

**File:** `examples/external/00-hello-context/run.py:484-486, 550-567`
**Issue:** `--legs ""` yields an empty tuple that passes the unknown-legs
check; the D-15 fallback then calls `get_replay_record` before any serve
has occurred, and the tool errors ("no product has been served yet"),
failing with a misleading "refused" assertion rather than a scope error.
**Fix:** `assert legs, "at least one leg is required"`.

### IN-04: replay_server docstring says "ordinal-per-path" but cursors are per-prefix

**File:** `examples/external/00-hello-context/replay_server.py:16-18, 125, 132`
**Issue:** Cursors are keyed by fixture prefix, so two distinct Gemini
model paths (both ending `:generateContent`) share one ordinal sequence.
Adequate for the fixed conversation, but the documented contract
("ordinal-per-path") is not what is implemented.
**Fix:** Reword the docstring to "ordinal-per-route-prefix" (or key
cursors by full path).

### IN-05: `fingerprint` can raise `TypeError` on a tool entry missing `name`

**File:** `examples/external/00-hello-context/replay_server.py:107-118`
**Issue:** `sorted(t.get("name") for t in tools if isinstance(t, dict))`
mixes `None` and `str` if a tool dict lacks `name`, raising an unhandled
`TypeError` — a raw 500 traceback rather than the module's JSON
diagnostic shape (the T-13.2-09 posture applied to bodies but not here).
**Fix:** `sorted(t["name"] for t in tools if isinstance(t, dict) and isinstance(t.get("name"), str))`.

### IN-06: Synthetic bearer tokens live in a committed artifact (acceptable, note only)

**File:** `examples/external/00-hello-context/artifacts/tokens.yaml:24,29`
**Issue:** `fmb-external-context-token-2026` / `-2025` are committed. The
file's own header labels them SYNTHETIC and the demo requires them; the
fixtures JSON scan found no real key material (`sk-ant`, `AIza`,
authorization headers) anywhere — capture_proxy's bodies-only recording
(T-13.2-06) held. No action required; recorded so the secret scan is
auditable.
