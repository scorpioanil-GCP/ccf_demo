## Blocking

### B-1 — `resource` key presence tells an unauthorized subject from a nonexistent one, at `minimal` and at `reasoned`

**`src/ccf/products/disclosure.py:611-622`** (the whole-member step) and **`src/ccf/products/disclosure.py:388-392`** (`INDISTINGUISHABLE_BELOW_FULL`).

Quoted, from `disclosure.py:614-616`:

```
    # crosses at `minimal`. `replay_reference`, `request` and `resource` are
    # deliberately untouched: the first is the address of the record this
    # determination produced, and the other two are what the caller itself
```

That reasoning is about a member's *content*. The channel is its *presence*, which the same module names at `disclosure.py:49-52` as the harder one to notice:

```
is kept. Removing a key would make the shell's shape a channel — a consumer
counting keys would learn which internal cause it hit — and a shape channel is
harder to notice than a prose one.
```

`RefusalEnvelope.resource` (`src/ccf/products/refusal.py:535-537`) is hash-transparent at `None`, so the canonical rendering **omits the key** when it is absent. The two causes of `subject-unavailable` are built in two places and exactly one of them sets it:

* unauthorized — `runtime/ccf_runtime/authz/delivery_boundary.py:334-339` always passes `resource=ResourceRequestIdentity(...)`;
* nonexistent — reaches the wire through `src/ccf/products/door.py:636` (`envelope_for(resolved, request=stated)`) or through `GovernedResolver._record_refusal` at `src/ccf/products/resolver.py:1313`, and **neither call site accepts or passes a `resource=`**. There is no SDK path that attaches one, so this is structural, not a deployment mistake.

Measured on this tree:

```
$ .venv/bin/python  # two SubjectUnavailableRefusal shells, built as the SDK builds them
minimal  unauth-only keys: ['resource']   nonexistent-only: []
reasoned unauth-only keys: ['resource']   nonexistent-only: []
```

**Failure scenario.** Principal P asks the HTTP door for `/product/t/c/1.0.0?subject=ACME-CORP`. Body arrives 404 either way. P counts the keys inside `"refusal"`: `resource` present ⇒ *the subject exists and I may not have it*; `resource` absent ⇒ *no such subject*. The same read works over the MCP tool and the MCP standing resource, because all three doors serialize the envelope with `canonical_bytes` (`runtime/ccf_runtime/http_api/routes/product.py:164`, `runtime/ccf_runtime/mcp/egress.py:1005`, `runtime/ccf_runtime/mcp/experience.py:992`).

This is the exact clause `D-IMPL-253` amendment 2 (4) names — *"same … body schema/field presence"* — and the exact closure `D-IMPL-258` (2) applied to `policy_bindings` in this phase, left open for the member beside it.

**Fix:** add `"resource"` to `INDISTINGUISHABLE_BELOW_FULL["subject-unavailable"]`. `_withheld_whole_member` already resolves it: the field declares `None` as its sentinel, so the normalization is the one the ruling asks for and the key disappears on both sides together. (`request` needs the same audit: it is required and non-sentinel, so both causes always carry it — that half is sound.)

### B-2 — a `constraint-refusal` discloses the deployment's Control Plane artifact key, its version and its `policy_id` at the safe default

**`src/ccf/products/disclosure.py:341`**:

```
    "constraint-refusal": frozenset({"bound"}),
```

`bound` is a `ParameterBound` (`src/ccf/products/provenance.py:265-271`), which embeds `source: ProvenanceSource` — `kind` / `identity` / `version` — and `policy_id`. Because `RefusalEnvelope.fields` holds each declared field as one canonically-rendered blob, permitting `bound` permits the whole nested object.

Measured on this tree, at `level="minimal"`:

```json
"fields": {
 "bound": "{\"authority\":\"policy\",\"operator\":\"maximum\",\"policy_id\":\"ACME-INTERNAL-TRAVERSAL-POLICY-7\",\"source\":{\"identity\":\"policy-constraint:acme-bank:max-depth\",\"kind\":\"artifact\",\"version\":\"sha256:deadbeefcafe\"},\"value\":\"6\"}",
 "requested": "\"undisclosed\""
}
```

This contradicts the table's own governing rule, stated once at `disclosure.py:68-71`:

```
sentence and it holds for every entry: **a field crosses at ``minimal`` only
when it states what the caller must satisfy or may do next, and reveals nothing
about fabric state, another tenant, another principal, or the existence of a
subject.**
```

and it contradicts its two nearest siblings, which withhold the same class of information deliberately:

* `disclosure.py:312` — `"tolerance-exceeded": frozenset({"authority", "tolerance"})`. `ToleranceExceededRefusal` also declares a `source: ProvenanceSource`, and it is **not** permitted. The bound's value and the authority token cross; the artifact pin does not.
* `disclosure.py:344` — `"policy-resolution-conflict": frozenset()`, with the comment two lines above: *"Which of the deployment's own policy artifacts disagree is internal governance state, and a caller can do nothing with it."*

**Failure scenario.** Any caller entitled to any product class asks for `max_depth=9` against a class whose deployment registered a `maximum` of 6. The 400 body hands back the Control Plane registry key, the exact content-hash version, and the internal policy identifier of a governance artifact that caller has no entitlement to read — at `minimal`, which is the level a deployment that never configured disclosure gets. It is a governance-topology enumeration primitive: vary the parameter, harvest the key set.

**Fix:** narrow to what the caller must satisfy, the way `tolerance-exceeded` already does — permit `bound.operator` and `bound.value` (via a promoted field or a narrowed rendering) and withhold `bound.source` and `bound.policy_id` below `reasoned`. If splitting the member is unacceptable, `frozenset()` is the safe entry and the bound survives in the replay record, which is where `policy-resolution-conflict` already puts it.

### B-3 — `PolicyConstraint.reason` is read by nothing; its docstring says it reaches the refusal shell

**`src/ccf/controlplane/artifacts.py:563-564`** (the claim) and **`:583`** (the field):

```
        reason: The declared justification or citation, carried into a refusal
            shell subject to disclosure policy (``D-IMPL-254``).
```
```
    reason: str
```

The field is **required** — no default — so every deployment authoring a `policy_constraints:` section must write a citation for it. Measured:

```
$ grep -rn "constraint\.reason\|\.constraint\.reason" src/ runtime/ tests/ examples/
$ echo $?
1
```

Zero readers. `_source_of` (`constraints.py:333-338`) builds a `ProvenanceSource` from `key`/`version`; `_bound_of` (`:340`) builds a `ParameterBound` from `operator`/`value`/`authority`/`source`/`policy_id`. `_refuse_against` (`constraints.py:607-655`) writes its own three `detail` strings from the fold and never consults the artifact. Nothing carries `reason` into `ConstraintRefusal`, into `PolicyResolutionConflict`, into `EffectiveRequest`, or into the replay record. No disclosure level makes it cross, because it never enters the shell at any level.

**Failure scenario.** A bank authors `reason: "12 CFR 30 Appendix B — traversal depth limit"` on every policy constraint, on the strength of this docstring, and expects an examiner or a caller to see the citation on a refusal. Neither does. The citation survives only inside the artifact, reachable only by resolving the pin — which B-2 shows is the one part of the bound that *should not* be crossing.

**Fix:** either carry it (add `reason` to `ConstraintRefusal` and give it a `PERMITTED_AT_MINIMAL` entry, or fold it into the resolution recorded on dimension 2), or correct the docstring to say the citation is resolved from the pinned artifact and does not travel. A required field with a documented behavior it does not have is worse than an optional one with none.

### B-4 — an unentitled policy-override attempt vanishes from replay whenever the same request is also refused

**`src/ccf/products/constraints.py:999`** — the only place override records are carried:

```
        overrides=verified_overrides,
```

It sits inside the `EffectiveRequest` constructor at the **success** return of `resolve_effective_request`. Every refusal return of that function discards `verified_overrides`: `constraints.py:898-907` (`required-absent`), `:920-935` via `_refuse_against` (`bound-exceeded`, `not-in-allowed-set`), `:967-980` (technical bound), the `PolicyResolutionConflict` returns at `:536` and `:566`, and the `refuse_request` verdict at `:994`. None of `ConstraintRefusal`, `PolicyResolutionConflict` or `ProductRequestViolation` declares an `overrides` member.

The resolver then records that branch with no resolution at all — **`src/ccf/products/resolver.py:1312-1317`**:

```
            return self._record_refusal(
                envelope=envelope_for(resolved, request=identity),
                execution=None,
                request=request,
                perspective=perspective,
            )
```

No `resolution=`, so `ReplayRefusalRecorder.record` passes `resolution=None` and `build_replay_record` writes `request_resolution=NO_REQUEST_RESOLUTION` (`src/ccf/replay/record.py:1441-1445`). Dimension 2 says *no resolution happened*.

Two shipped claims are false as a result:

* **`src/ccf/products/request.py:287-289`** — *"Both facts, entitled and honored, land in the replay record whichever way they came out."*
* **`src/ccf/products/provenance.py:337-339`** — *"An unentitled attempt is recorded with `entitled=False` and `honored=False` rather than omitted."*

**Failure scenario.** Principal P, absent from `overridable_policies`, sends `policy_overrides=("ACME-P7",)` alongside `max_depth=9`. `_verified_overrides` (`constraints.py:1376-1435`) mints `OverrideRecord(entitled=False, honored=False)` — correctly. The fold then refuses `max_depth=9` against the ceiling, `ConstraintRefusal` is returned, and the override record is dropped before it reaches any writer. P can probe the deployment's policy identifiers, one request at a time, and leave no trace of a single attempt — which is precisely the signal `D-IMPL-253` Q7 (*"otherwise anyone who knows a policy ID could bypass it"*) exists to make visible. The attempts that *succeed* are recorded; the ones that fail are not, which inverts the audit value.

**Fix:** carry the records past the refusal. The narrowest change is to let `resolve_effective_request` return `(refusal, verified_overrides)` — or attach the tuple to a wrapper — and have `GovernedResolver` pass a resolution-bearing value at `resolver.py:1313`. A partial `EffectiveRequest` is not required; dimension 2 needs the override tuple, not the parameters.

### B-5 — a delivery-boundary denial for one tenant is recorded under another

**`src/ccf/products/resolver.py:743-746`** (the claim):

```
        tenant_id: The tenant every determination this recorder writes was made
            under. A refusal carries no vessel to read it off, so it is stated
            once here rather than at each call — a recorder is bound to a
            deployment exactly as its resolver is.
```

**`src/ccf/products/resolver.py:858`** (the use), inside `ReplayRefusalRecorder.record`:

```
            tenant_id=self.tenant_id,
```

The recorder's `tenant_id` is fixed at construction. The HTTP product door is **not** tenant-bound: `ApiDependencies` "holds no bind address, no tenant" (`runtime/ccf_runtime/http_api/dependencies.py:12`), no authorizer guards the product router (`app.py:371` wires `authorizer=` into the HITL router only), and the tenant arrives as a path segment — `runtime/ccf_runtime/http_api/routes/product.py:327` `"/{tenant}/{product_class}/{version}"` — which is handed straight to the governed step at `:594-596`. `GovernedResolver` refuses a foreign tenant (`resolver.py:1225-1231`), but that check runs **after** `govern_entitlement` has already decided and recorded.

Measured on this tree — recorder bound to `alpha`, request addressed to `beta`:

```
shell.resource.tenant_id = beta
record.tenant_id         = alpha
record.dim1.tenant_id    = alpha
```

`ContextFabricSnapshot.unread`'s own parameter doc (`src/ccf/replay/record.py:433`) says `tenant_id` is *"The tenant the determination was made under."* It is not. One record disagrees with itself about which tenant was decided against, and a replay filtered by tenant will return `beta`'s denials under `alpha` and miss them under `beta`.

**Failure scenario.** A multi-tenant deployment — the posture `D-IMPL-05` makes first-class and the `{tenant}` path segment invites — serves tenants `alpha` and `beta` through one `create_app`. Every denial addressed to `beta` lands in the audit trail stamped `alpha`. An examiner asked *"show me every governed determination made under `beta` on 2026-09-05"* gets an incomplete answer, and the count they do get is inflated by another tenant's denials.

A second consequence rides along: `record` resolves the disclosure level with `tenant=self.tenant_id` (`resolver.py:838-840`), so `beta`'s denial is disclosed under `alpha`'s policy. I am **not** reporting that half as a defect — `runtime/ccf_runtime/authz/product_entitlement.py:487-490` rules it deliberate (*"a denial is decided under the tenant the caller addressed, while the level is read under the tenant whose door is answering"*). It is noted because a reader triaging the record-attribution half will hit it.

**Fix:** either take the determination's tenant per call — `record(..., tenant_id=...)`, defaulting to the recorder's — or refuse at the door: have `build_router`/`create_app` compare the path tenant against the recorder's bound tenant and answer before `govern_entitlement` runs, on the `recorded_boundary` construction-refusal posture. The second is the smaller change and keeps the recorder's docstring true.

## Advisory

### A-1 — `door.py`'s "already been disclosed" claim is false on its own `envelope_for` branch

**`src/ccf/products/door.py:85-89`**:

```
**This module is the Delivery layer.** It is the shape a door puts on a wire
and nothing more: it decides nothing, discloses nothing and records nothing.
What it carries has already been determined, already been resolved against its
authorities, and already been disclosed by
:func:`~ccf.products.disclosure.disclose`.
```

The last clause is false for the branch at `door.py:636`, `return envelope_for(resolved, request=stated)`. That envelope has never been through `disclose`: it carries `disclosure=None` and the fabric's internal prose verbatim. Measured:

```
disclosure:        None
detail:            INTERNAL: policy ACME-P7 at sha256:cafe bounds max_depth to 6 for tenant acme
replay_reference:  no-replay-reference
```

No door checks `envelope.disclosure` before emitting — `grep -rn "disclosure" src/ccf/products/door.py runtime/ccf_runtime/http_api/routes/product.py runtime/ccf_runtime/mcp/{egress,experience}.py` returns only prose. `_refusal_response` (`product.py:159-166`) serializes whatever it is handed. So a deployment resolver that returns a bare refusal value — a shape `door_refusal` documents, supports, and which the SDK's own `DeterministicAssembler` now produces (`src/ccf/agents/assembler.py:484-503`) — puts internal truth on the wire at every level, with no policy read.

**Why advisory and not blocking.** `door.py:636` is the line the carried finding already names; I am not re-reporting the criterion-36 half. What is not carried is (a) the disclosure consequence, which is a leak rather than a missing reference, and (b) the module docstring at `:85-89`, which is a distinct shipped artifact asserting the thing that branch does not do. `tests/invariants/test_determination_authority_disclosure_delivery.py` passes 36/36 because it is a docstring-presence and roster check, not a behavioral one — so nothing in CI would notice. Triage may reasonably merge this into the carried entry; it is recorded separately so the leak is not lost when the reference half is fixed.

**Fix:** the honest minimum is to correct the docstring. The structural fix is for `door_refusal` to refuse an envelope whose `disclosure is None`, in the same voice as the `ValueError` two lines above it — a door handed an undisclosed shell has been handed something no Disclosure layer produced.

Unreachable.

3. **A `float` bypassing a declared `ArgumentDomain`, because `_as_decimal` returns `None` for one and the domain step then `continue`s (`request.py:1226-1228`).** Rejected by execution: `refuse_request` answers `('type-mismatch', 'depth')` for `0.5` and `-3.0` against a `number`-typed argument, so no float reaches the domain step un-refused.
4. **`_pinned_query_body`'s new key order (`fluree.py:792`) silently discarding a body's own `from` rather than refusing it.** Rejected: correct pinning is the property the fix bought, all callers are SDK-internal, and refusing would be a behavior change outside the fix's scope.

Rejected as a finding: in-process construction is a supported surface for a library, and B-4 covers the audit consequence that matters.
6. **`_capabilities_of` (`resolver.py:938-977`) deriving the empty tuple on every shipped boot path, so the new `TraversalDepthCapability` on the Fluree and Neo4j stores is never picked up.** Rejected: the docstring measures and states exactly this (*"for every shipped boot path this derives the empty tuple — the honest answer"*), and names the explicit-`capabilities=` escape. Documented, not false.
7. **cp-00/01/02/03 assemblers still raising `AssemblyRefused` for tenant and role mismatch while the SDK's own `DeterministicAssembler` now returns `AssemblyRefusal` for both.** Rejected as out of subject: `examples/` is not in `git diff … -- src runtime`. Flagged here only because `src/ccf/agents/errors.py:170-176` calls the two "governed determinations" and the shipped examples disagree — worth a look in whatever phase next touches the examples.
