# Phase 24.6 Plan 02: the resolution algorithm and two constraint-layer kinds Summary

One pure function that turns a question plus every authority that bounds it into a
provenance-carrying record — defaults, caller overlay, policy constraints folded by
**comparability**, technical capability, then the existing conformity comparison over the
*effective* values — with Dave's four worked cases proven rather than narrated, each behind a
watched control.

## What was built

**Task 1 — `src/ccf/products/constraints.py` and two kinds** (commit `2e2534a0`).

The module docstring states the five-step sequence and the purity sentence before any class,
on the order plan 01 established. Below it: `CAPABILITY_TRAVERSAL_DEPTH` (a mechanism name and
never a value), `PinnedConstraint`, `TechnicalCapability`, `ConstraintRefusal`,
`PolicyResolutionConflict`, `applicable(...)` and `resolve_effective_request(...)`.

Three properties are structural rather than documented:

- **`preferred` cannot refuse.** It does not reach a refusing branch because the fold table
  `_FOLDS` routes it to `guidance` and nothing else. There is no `if operator == "preferred"`
  anywhere; the routing is a table, which is also what gives the Q5 sabotage a one-line needle.
- **A hard constraint is never dropped because another outranks it.** Priority orders which
  surviving bound is *reported* on the parameter; every applicable hard bound is still held
  against the value, at the line carrying the marker `# D-04: every applied constraint holds`.
- **Applicability is re-checked inside the pure function**, so its purity is not also a trust
  assumption about its caller: a constraint for another tenant, another class or another
  century passed in directly is ignored (T-24.6-06).

Nothing is clamped. A value outside a bound is a `ConstraintRefusal` carrying the bound with
its own authority and source — which is what lets a technical limit be refused **by name**,
with `authority == "technical"` and a `capability` source that has no version lane. The single
exception is Dave's worked case 3, and it is the module's **only** parameter-name-keyed branch:
a `maximum` on `DEBT_TOLERANCE_PARAMETER` replaces the value instead of refusing, because the
comparison that can still refuse (observed Debt against the tolerance) happens after assembly.
`grep '== "' src/ccf/products/constraints.py` finds two hits and both are docstring prose.

`REFUSAL_KINDS` is at **22**; both kinds also joined `_PRE_ASSEMBLY_REFUSALS`, because both are
reached while the effective request is still being built — strictly before an operator plan
exists — so a lineage offered with either would claim evidence that could not exist yet.

## Deviations from Plan

**1. [Rule 3 — blocking] The refusal-vocabulary walk widened to a third name family, and three
pre-existing classes were placed in the two allowlists.**
Found during Task 1, RED by construction. `discover_refusal_types` collects classes whose names
end in `Refusal` or `Violation`; `PolicyResolutionConflict` ends in neither, so
`test_the_refusal_vocabulary_is_closed_by_set_equality` compared a mapping that named it
against a tree that did not, and `test_control_6_*` went RED beside it. Two ways out. Renaming
the class was refused: the plan's interfaces block fixes the name and plans 03, 04, 12 and 13
use it. Exempting it from the gate was refused for a better reason — *"nothing enters the
vocabulary by name"* is the property that gate exists to hold, and a vocabulary with one
member exempted is a weaker gate in exchange for a smaller diff. So `NAME_FAMILIES` became
`("Refusal", "Violation", "Conflict")`, which then found three pre-existing classes and forced
them to be placed: `DefaultConflict` (a `CCFContract`, agent composition) into
`NON_PRODUCT_REFUSALS`, and `WebhookEndpointConflict` and `FragmentFamilyConflict` (both
`ValueError`) into `NON_VALUE_VIOLATIONS`. **No source class changed**; both constants' prose
was re-voiced so the name each set is closed over matches the name it claims to be closed
over. A future `…Conflict` shell now cannot ship untranslated either. Commit `2e2534a0`.

**2. `src/ccf/products/__init__.py` was NOT edited, against the plan's "Export from
`src/ccf/products/__init__.py`".**
Measured before deciding. That file declares no `__all__` at all and its docstring states the
rule in its own words: *"The package re-exports nothing, deliberately: a second import path for
the same symbol is a second surface the drift manifest has to track."* Every sibling —
`gates`, `refusal`, `request`, `payload`, `contract`, and `provenance` from plan 01 of this
same phase — is reachable only from its own module. Exporting the constraint names there would
have made them the only ones. This is plan 01's deviation 2 applied to the sibling package, on
the same measurement.

**3. [Rule 2] `_require_aware` was hoisted, so the zone-less guard is total.**
The plan puts the naive-`asked_at` `TypeError` in `applicable(...)`. That guard is only reached
when there is at least one constraint to test: a request with **no** applicable constraints
never calls `applicable` at all, so a resolution could have been recorded with a zone-less
`EffectiveRequest.asked_at` — an instant nobody can resolve an effectivity window against, at
replay. One private `_require_aware` is now called from both entry points, so there is one
reading of what an instant is rather than two. `test_a_naive_asked_at_is_refused` asserts both.
Commit `8ad00fdc`.

**4. The return union includes `ProductRequestViolation`.**
The plan's interfaces block spells the signature as `-> EffectiveRequest | ConstraintRefusal |
PolicyResolutionConflict`, and its step 5 says *"a verdict is returned as the
`ProductRequestViolation` it is."* Both cannot be true, so the annotation carries the fourth
member. The plan's `key_links` pattern still matches: the union is on one line and its first
three members are spelled exactly as written.

**5. `PolicyResolutionConflict.reason` declares `ccf_hash_transparent: False`.**
The plan's interfaces block gives the field a default and says nothing about its hash posture.
CINV-06 (`D-IMPL-243` amendment 1) requires every defaulted `CCFContract` field new since
`13bd250` to declare one, so the alternative was making the single-member `Literal` required at
every construction site. `False` is the correct posture — the reason is content that renders
into the hash, not a sentinel that is omitted at its default — and a `False` mark is not part
of `tests/contracts/test_hash_transparency.py`'s roster, which tracks `True` marks only.

**6. The surface fragment was written at Task 1 rather than Task 2.**
The plan places `docs/surface-changes/24.6-02-*.md` in Task 2's files. Written that way, the
tree would have been RED on the drift and completeness gates at the Task 1 commit, since Task 1
is where the seven public names arrive. Same file, same content; plan 01's deviation 5, same
reason.

**7. The fold routing is a table (`_FOLDS`), not an operator-name branch.**
The plan describes the fold as prose over the five operators. A table was chosen because it
makes two things structural rather than documented: `preferred` reaches no refusing branch at
all, and `test_the_fold_table_covers_the_whole_constraint_vocabulary` asserts
`set(_FOLDS) == CONSTRAINT_OPERATORS`, so a sixth operator added to the Control Plane
vocabulary is a red build here rather than a constraint this module silently ignores. It is
also what gives the C-04 sabotage a one-line needle.

**8. The test fixture declares a third parameter, `tier`.**
The plan names `debt_tolerance` (number) and `depth` (integer). `allowed_set` takes a non-empty
tuple of **names**, so the intersection tests and the non-comparable-pair test need a
string-typed parameter. `tier` is the test module's own fixture vocabulary and reaches nothing
in `src/`.

**9. The scratch modules are registered in `sys.modules` before execution.**
`tests/products/test_empty_operator_halves.py::_scratch_gates` does not need this because
`gates.py` declares no dataclass. `constraints.py` does (`_Candidate`), and under
`from __future__ import annotations` `dataclasses` resolves string annotations through
`sys.modules[cls.__module__]` — without the entry the copy fails to import, which would have
made all three controls fail for a reason unrelated to their sabotage. The entry is popped in
a `finally`, and the names are not under `ccf.`, so nothing that walks the SDK's own packages
sees them.

## Findings for Dave

**F-1. The plan's output block still pins the stale digest.** It says criterion 35 *"still
reads `c3224bb4…`"*. `CRITERIA-LOCK.md` Amendment 2 (`D-IMPL-256`) added criterion 36 and
re-pinned to `014dcd64…`. **The digest on this tree reproduces `014dcd64…` exactly**, with 36
criteria, 38 lines, wrap detector 0 against a control of 1, and both historical digests
reproducing at their pinned commits. Nothing is wrong with the tree; the plan text is stale and
plans 03-16 carry the same block. This repeats plan 01's F-1 and is stated again only because
the stale sentence is still in front of every executor.

**F-2. Two allowlist constants now hold names outside the family their names claim.**
`NON_PRODUCT_REFUSALS` holds `DefaultConflict` and `NON_VALUE_VIOLATIONS` holds two
`…Conflict` names. Both docstrings were re-voiced so the prose is true, but the *constant
names* still say "REFUSALS" and "VIOLATIONS". They are public names in the surface manifest, so
renaming them is a surface change I did not make inside this plan's fence. Flagging in case you
want them renamed in a later plan of this phase rather than carried.

**F-3. A policy `maximum` above the caller's value does not move the tolerance.** The ruling
says a `maximum` on `debt_tolerance` "REPLACES the value with authority `policy` instead of
refusing." I read "instead of refusing" as: the replacement happens exactly where the refusal
would have — i.e. only when the caller's value **exceeds** the maximum. So a caller asking for
`.10` under a policy maximum of `.20` keeps `.10` with authority `caller`; the alternative
reading would have policy *loosening* a caller's own self-imposed tolerance, which reads wrong.
Stated because it is a reading, not a quotation.

**F-4. A bound over a parameter with no effective value records nothing.** If the caller omits
a parameter and the class declares no default for it, an applicable `maximum` on that parameter
neither creates a value nor refuses — `required` is the operator that speaks about presence,
and it does refuse (`required-absent`). This is my reading of the vocabulary's division of
labor and it is asserted by
`test_a_required_parameter_absent_after_defaults_is_refused`; it is not something the ruling
states either way.

**F-5. Nothing calls the algorithm yet, so its blast radius today is zero.**
`effective_debt_ceiling` still returns `min(declared, requested)` and is still what the serving
path uses. Plan 03 is where the two meet. Worth knowing when reading the "1603 passed" figure:
it does not yet exercise the new resolution through any door.
