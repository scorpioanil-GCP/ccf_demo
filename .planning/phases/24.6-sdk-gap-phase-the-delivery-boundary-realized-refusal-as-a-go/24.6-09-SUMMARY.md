# Phase 24.6 Plan 09: the HTTP door maps every kind and leaks nothing Summary

Dave, D-18 (`D-IMPL-253` Q18, verbatim): **"I agree with class-based mapping
and a uniform body. I would not automatically classify all
entitlement/fulfillment refusals as 409; authorization semantics may warrant
403 internally, while suppression-safe policy may deliberately map externally
to a less revealing class. The response body and disclosure policy must be
authoritative, not HTTP status. The key invariant is that no known governed
refusal becomes 500."**

And the sequence principle (`D-IMPL-256`): **"Replay belongs to the governed
determination, not to HTTP or MCP."**

Three things landed. The door now **maps** every kind in the vocabulary from
one table keyed by class. It **decides** nothing — the entitlement
determination is `govern_entitlement`'s, already recorded and already
disclosed by the time the route sees it. And a door that could not record one
is **not built**.

## What the door answered before, and what it answers now

Measured on the shipped table rather than counted from the plan:

```
REFUSAL_KINDS                                        → 23
STATUS_BY_KIND rows                                  → 23
set equality against REFUSAL_KINDS.values()          → True
  400 the request class                              →  3
  404 the unavailable class                          →  1
  409 the fulfillment-withheld class                 → 19
500 among the values                                 → False
```

Before this plan **two** of the twenty-three kinds had a status. The other
twenty-one reached `served_answer`, which raised `TypeError`: no response at
all, an opaque 500. The route's own docstring said so, and said the remainder
*"wait for their ruling"*. The ruling arrived.

`500` is now reserved for exactly one thing: a `kind` **absent** from
`REFUSAL_KINDS` — a value this SDK did not mint claiming to be a refusal. That
is an invariant violation and it still escapes loudly, with its own control
test (`test_a_kind_the_vocabulary_does_not_hold_still_escapes`, built through
`model_construct` because the field is validated).

**The table is keyed by refusal CLASS**, not by token, and `STATUS_BY_KIND` is
projected through `REFUSAL_KINDS`. So no kind string is spelled anywhere in
`refusal_status.py`: a renamed token moves both sides at once, and a deleted
class is an `ImportError` rather than an orphaned row. The closure is asserted
by set equality with a two-way planted-drift control.

The `403` in the `{"error_code", "message"}` shape is retired from this route.
It was three of the six D-27 channels at once — a different status, a
different body schema and a different message from the one a nonexistent
subject received — and it told an unauthorized principal that the subject
exists. The typed codes (`ERROR_PRINCIPAL_NOT_ENTITLED`,
`ERROR_PRODUCT_CLASS_UNENTITLED`, `ERROR_PRODUCT_ROLE_UNGRANTED`) are
unchanged and still the contract; they are now **internal truth**, asserted in
the replay record the denial minted rather than on the body, which is Q27's
*"Don't destroy audit truth merely to achieve external suppression silence"*
applied at a door.

**A door that entitles and cannot record is not built.** `recorded_boundary`
runs at `create_app` *and* at `build_router`, and the message names whichever
builder was actually called. There is no warn-and-serve posture, no
denial-branch 503 and no `ERROR_PRODUCT_DOOR_UNRECORDED`: a door that failed
closed only on denial would make auditability contingent on outcome, and would
reopen the unauthorized/nonexistent difference as a *misconfiguration*.

## The D-27 control: eight channels, three levels, measured

`observational_equivalence_violations(a, b, governed)` names one comparison per
leak Dave listed, plus the vocabulary members the same paragraph names, plus
one channel nobody has ruled on. It emits **one violation per key**, so a
divergence is attributable to the member that caused it rather than to "the
key sets differ".

Measured, per level:

```
minimal   ruled → []
reasoned  ruled → []
full      ruled → ['detail', 'fields.cause', 'fields.error_code']
unruled (every level) → ['policy_bindings', 'schema.refusal:policy_bindings']
```

The `full` expectation is **derived** from
`INDISTINGUISHABLE_BELOW_FULL["subject-unavailable"]`, not spelled: a fourth
member added to that table moves this test without an edit. Those three
members differing at `full` is disclosure **by policy**, which is what `full`
means.

**Both sides mint through the same seam**, and that is load-bearing. The
unauthorized case runs the real entitlement path; the nonexistent case is a
fixture resolver that builds `SubjectUnavailableRefusal(cause="nonexistent")`
and records it through *the same `ReplayRefusalRecorder` instance the app was
built with* (reached through a holder filled after the app is constructed). A
fixture that hand-built a shell would put the sentinel on both sides and the
replay-reference channel could never fire — the `24.6-07` F-4 shape, caught
there and avoided here.

Six watched controls, each shown **reporting** a planted divergence before the
emptiness above is trusted: status; evidence presence; field key set;
sentinel-against-reference; a reference that resolves to nothing; and the
single-answer refusal. Plus `test_byte_identity_is_not_required`, which
asserts the two answers carry different request identities, different resource
identities and different bytes, and that the comparison is silent about all
three — the am.2 (4) rider as a property of the instrument.

## Findings for Dave

**F-1. `policy_bindings` tells a consumer which of the two subjects it hit, at
every disclosure level — and it does so twice over. This is `24.6-08` F-2
arriving where F-2 said it would.**

`24.6-08` flagged that `disclose` does not touch `policy_bindings` at any
level, so a refused consumer can read *which Control Plane artifacts governed
the refusal, at which versions* — and noted that the two D-27 subjects *"will
meet at one door in plans 09/10, and that is where the control test lives"*.
They met. Measured at this door:

| | unauthorized | nonexistent |
|---|---|---|
| `policy_bindings` **value** | the tenant's entitlement policy, at its version (D-34) | nothing — the assembler consulted no policy |
| `policy_bindings` **presence in the body** | present | **absent** — the canonical rendering omits an empty tuple |

The second row is the more serious one. Field *presence* is the channel
amendment 2 (4) names by name, and it is readable without reading a single
value: a consumer counting keys can tell *you may not* from *there is no such
thing* at `minimal`.

**What I did and did not do.** I did not fix it: what may cross a consumer
boundary is a disclosure-policy ruling, and it is yours. I did not hide it
either — the fixture is not rigged, and
`test_the_unruled_policy_binding_channel_is_measured_and_named` pins the exact
state at all three levels so that **any** change turns red: a ruling applied, a
fixture rigged later, or the member quietly disappearing. Every other channel
is clean at `minimal` and `reasoned`, so C-22 is discharged against the six
channels you named.

**Three ways to close it, and I picked none:**

1. **Add `policy_bindings` to `INDISTINGUISHABLE_BELOW_FULL["subject-unavailable"]`.**
   One table entry, no code. It closes both rows at once, because the
   disclosure step replaces a withheld value and keeps its key — so the
   presence half closes for free. Cost: a refused consumer inside the tenant
   loses a genuinely useful diagnostic at `minimal` and `reasoned`.
2. **Withhold it for every kind below `full`.** Wider, and probably right
   across an A2A boundary, but it changes what nineteen other kinds disclose on
   a path nobody asked to make quieter (the shape of F-3 in `24.6-08`).
3. **Leave it, and rule that a Control Plane key and version may cross.** Then
   the honest follow-on is that the *nonexistent* path must pin something too,
   or the presence channel stays open — which pushes work onto every assembler
   rather than onto one table.

My reading is that (1) is the smallest change that closes the channel this
phase actually opened. It is a ruling, not a defect, and nothing is red.

**F-2. The `403`→`404` change is a breaking wire change for a client of this
door, and it is worth your eye even though it is exactly what D-27 asks for.**
A client branching on `response.status_code == 403` or on
`response.json()["detail"]["error_code"]` for `GET /product/...` now reads
`404` and `response.json()["kind"]`. The `403` for *tenant* authorization on
the HITL routes is untouched, and so is the `401`. It is recorded in the
surface fragment with its migration note; flagging it here because it is the
one thing in this row an adopter would notice on the wire.

**F-3. The plan's output block still pins the stale digest.** It says criterion
35 *"still reads `c3224bb4…`"*. The pin is `c0fdc4f4…` (CRITERIA-LOCK
Amendment 3, `D-IMPL-257`), and **the tree reproduces it exactly** with the
instrument the lock file itself records — 38 lines, 36 criteria, wrap detector
0 against a control of 1, digest control moving the sha. Eighth plan in a row
to report this; plans 10–16 carry the same block.
