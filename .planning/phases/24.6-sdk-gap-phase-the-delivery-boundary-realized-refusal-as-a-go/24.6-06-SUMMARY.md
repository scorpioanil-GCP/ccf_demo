# Phase 24.6 Plan 06: hw1's negative test re-derived to served computed-empty parity Summary

The one named example re-derivation D-12 calls for. hw1's negative conformance
test asserted that an empty fabric is **refused by name** on both transports.
Under `D-IMPL-253` Q12 an operator that evaluates an empty graph has computed,
so both transports now **serve** a computed-empty product with the same bytes,
and the test proves parity of the served *answer* instead of parity of the
refusal.

The module keeps its name (criterion C-16 names it), keeps its subject (the
UNSEEDED copy), and keeps its sabotage — inverted. `D-IMPL-235` (4): a test the
fix flips is rewritten under the fix, never deleted.

The comparison's five named classes: fewer than two legs; a leg that did not
exit 0; a leg that refused (any kind); a leg with no content address; two legs
whose stdout differs. Byte-identity is the standard, the same one
`test_both_documented_transports_return_the_same_answer` holds the seeded run
to — an empty answer is an answer, and agreeing on it is the same claim as
agreeing on a full one.

Three claims, and the third is the one the plan added:

   documented commands over the unseeded copy, no violations, and the agreed

   `plan_id` matching the vessel's, and a Debt equal to what the deployment's own
   declared factors give.

   could be declared are read from `ccf_config.yaml` and found empty, and the

### The Debt expectation is derived, and that was measured rather than argued

A test asserting `debt.debt == 0` against a fabric whose Debt is 0 proves
nothing about where the 0 came from. The assertion reads `completeness` and
`semantic_consistency` from the copy's own `binding.yaml` and computes
`1 − F·C·S`. To show that is genuinely derived, a private copy's declared
completeness was moved to `0.5` and the same question asked:

```
declared C=0.5 S=1
derived expectation = 0.5
served D_c          = 0.5
derived matches served : True
a literal Decimal(0)   : False
```

So a constant expectation fails on a copy where the derived one passes. The
mutation was on a temporary copy; `git status` over `examples/` was clean before
and after.

## Deviations from Plan

**1. The plan's `served_parity_violations` ordering was made non-short-circuiting.**
The plan lists the five classes "in order" and separately requires the sabotage
to report *"both the exit and the refusal by name"*. Those two are in tension
under the sibling module's early-return style: a leg that exits 1 AND refuses
would be reported only as an exit. Collecting every class is what makes the
sabotage's own assertion possible, and it is the honest report besides — the
plan's sabotage requirement is the ruling here.

**2. The in-process read is driven through `InProcessAdapter` + `decode_outcome`,
not through `ProductClient`.** The plan says *"boot the copy through `ccf.client`
exactly as `consume.py` does … then `result.product.computed_empty` (or the
served contract off the adapter's result — read `src/ccf/client/result.py` for
the accessor)"*. Measured: `Result` has **no** vessel accessor — its public
members are `refused`, `refusal`, `product_id`, `parameters`,
`temporal_boundary`, `payload`, `debt`, `content_address`, `replay_ref`,
`lineage`, `expires_at`. Reaching `_served.vessel` would be a private-attribute
read; adding a public accessor is a client-surface change this row is fenced
from. So the plan's own parenthetical alternative was taken, using the idiom
`tests/client/test_inprocess_adapter.py` already established for the same reason
in `24.6-05`.

**3. The question the in-process read asks is READ, not typed.** The plan says
`ProductClient.for_product("hw1.companies-over-revenue")` with the parameters
implied. Instead the threshold and the `--as-of` boundary are parsed off the
documented in-process command, the parameter *name* is read off the deployment's
request contract (`arguments.required`, asserted to be exactly one), and the
product id off `product_class.schema_name`. Nothing about hw1's vocabulary is
spelled in the test, and the in-process read is provably the same question the
two subprocess legs asked.

**4. [Rule 2] The parity test asserts the agreed answer is the EMPTY one.**
The plan's five violation classes do not include "the answer is empty" — that
is `EMPTY_ANSWER`'s job and the plan names the constant without saying where it
is used. Asserting it only inside the comparison would have made it one more
parity rule; asserting it on the agreed stdout in the test makes it a claim
about the *subject*. Sabotage S4 shows why it is not optional: with the seeded
copy substituted, the comparison reports zero violations.

**5. The plan's Task 2 commit subject was not used verbatim.** The plan gives one
subject line covering both tasks (*"hw1's negative test re-derived …; README
teaching paragraph present tense"*), but the two tasks are two commits by the
per-task commit protocol. Each commit's subject names its own change, both carry
`(24.6-06)` and `(24.6-L-06)`, and together they say what the plan's single line
says.

**6. `FRESHNESS_OVER_NOTHING` and `_UNIT` are named constants in the test.**
Not in the plan's interfaces. `Decimal(1)` appearing twice inside an arithmetic
expression would read as two magic numbers; naming them lets the comment carry
the reason (the multiplicative identity over an empty observation set, and the
leading `1` of `D_c = 1 − F·C·S`) rather than leaving a reader to infer it. Both
are algebraic facts, not figures about hw1's data — the same standing the
reference debt scorer's own `[0, 1]` endpoints have.
