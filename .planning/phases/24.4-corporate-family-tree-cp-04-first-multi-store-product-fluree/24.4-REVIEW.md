# Phase 24.4: Code Review Report

**Reviewed:** 2026-09-01
**Depth:** standard
**Files Reviewed:** 37
**Status:** issues_found

## Summary

Single-agent §3.1 review of the cp-04 corporate-family-tree example, its
artifacts, its ten test modules, the fixture dump tool, and the touched
Makefile section. The close panel's known findings (served-roster denominator,
the four unfailable seam checks, the unguarded anchor block, CFT-G15's sparse
content check, the basename-only test-reference resolver, the D-IMPL-234
carve, measure_debt's structural C=1/F=1, the container-pollution failures)
were treated as handled and not re-derived; findings below are adjacent to or
distinct from them.

The serving spine, the two-store deployment, the projection, and the test
machinery are unusually well-defended. The defects that remain cluster in two
places the panel did not look: **the refusal channel** (guards written as
`SystemExit` and a coercing depth resolver sit on a served network path that
can only translate `Exception`s into governed refusals), and **the request
contract's own text** (two declared-operative parameters — `debt_tolerance`
and `intent` — that no code enforces, one of them promising a `409` that
cannot fire).

## Critical Issues

### CR-01: Caller-reachable `SystemExit` refusals escape the MCP door as an unhandled `BaseException`

**File:** `examples/cp-04-corporate-family-tree/deployment.py::refuse_open_jurisdiction_world` (also `refuse_unminted_membership`, `perspective`, `_setting`), reached per-request via `examples/cp-04-corporate-family-tree/server/compose.py::build_resolver` → `deployment.read` → `deployment.source_read`
**Issue:** `source_read` runs the closed-world jurisdiction guard on **every
request**, and the guard's subject is anchor-dependent: the declared set
`{NL, US-DE}` is the demonstration family's observed set, so any other anchor
in the estate (Zimmer Biomet → `{US-DE, CH}`, most GB/LU/IN anchors, and every
family none of whose members holds a `legal_entity` row) raises `SystemExit`.
The README documents this as a property on the CLI path — where `SystemExit`
prints and exits 1 — and that disposition is fine **for `run.py`**. But the
same code path is behind the MCP product tool: `compose.build_resolver`'s
`resolve` runs inside a FastMCP tool handler, and the SDK's own egress
docstring (`runtime/ccf_runtime/mcp/egress.py`) records that FastMCP wraps a
raised tool **`Exception`** as a `ToolError` with `isError=True`.
`SystemExit` is a `BaseException`, not an `Exception`: it is not converted to
a governed refusal and propagates into the anyio task group — tearing down the
session/stdio server rather than answering the caller. A caller-supplied `lei`
naming any non-demonstration family is therefore a remote input that crashes
the door instead of producing a refusal that names itself. The same holds for
`refuse_unminted_membership`'s empty-walk branch and, at first request, for
`_setting`'s unset-variable branch. Nothing in
`tests/examples/test_cp_04_two_callers.py` drives a non-demonstration anchor
through the door, so the suite cannot see this.
**Fix:** Serving-path guards must refuse in the fabric's vocabulary, not the
interpreter's. Minimal change: in `source_read`/`read`, raise
`ccf.agents.errors.AssemblyRefused` (already the door's propagated,
FastMCP-wrappable refusal type for identity/contract/existence) — or return a
typed verdict as data, matching `AnchorUnresolvable`'s shape — from
`refuse_open_jurisdiction_world`, `refuse_unminted_membership`, and any other
guard reachable after boot. Reserve `SystemExit` for boot-time/CLI
artifact-authoring checks that no remote request can trigger. E.g.:

```python
# deployment.py — serving-path guard
if undeclared:
    raise AssemblyRefused(
        f"family members serve jurisdiction(s) {undeclared} that"
        " artifacts/source-vocabulary.yaml does not declare ..."
    )
```

Then add a two_callers case driving one non-demonstration anchor through the
tool and asserting `isError=True` with the refusal text — the case that turns
red today.

### CR-02: `debt_tolerance` is declared operative ("refuses with 409") and is enforced nowhere; the scenario field is write-once, read-nowhere, and pinned to the artifact's value

**File:** `examples/cp-04-corporate-family-tree/ccf_config.yaml:237` (`debt_tolerance: ... the ceiling above which assembly refuses with 409 and the debt block`); `examples/cp-04-corporate-family-tree/deployment.py:2904`; `examples/cp-04-corporate-family-tree/produce.py::measure_debt`
**Issue:** Three linked defects on one parameter:
1. The request contract's `arguments.debt_tolerance.description` — the text a
   caller discovers the surface from — promises a `409` refusal. **No code
   anywhere in the example compares `D_c` (or any `DebtAssessment` field) to
   `debt_tolerance`.** `grep` over the tree finds the token only in prose and
   in the one assignment below. A caller supplying `debt_tolerance: "0.01"`
   is served a product with `D_c ≈ 0.0909` — above their declared ceiling —
   with no error. This is exactly Standard §2.4's *"a parameter that appears
   to work and does not will be relied on in a dispute"*, and unlike `as_of`
   it is **not** declared inert and **not** refused. (`question.yaml` marks
   the value `[TBC — product owner]` and README/summary say the debt signal
   is "advisory at every rung"; neither corrects the contract document, which
   is the one callers read.)
2. `deployment.read` sets
   `debt_tolerance=str(demonstration_parameters()["debt_tolerance"])` — the
   **demonstration artifact's** value, not `asked.parameters` — so even a
   future enforcement branch keyed on the scenario field would enforce `0.25`
   against every caller regardless of what they asked.
3. `FamilyScenario.debt_tolerance` has zero readers (the spine's `Scenario`
   Protocol does not even declare it) — the same write-once-read-nowhere
   shape as cp-03's `fail_closed`, which there required a ruling; no ruling
   covers this parameter here.
**Fix:** One of three, explicitly: (a) implement the refusal — compare the
assessed `D_c` against the **caller's** `debt_tolerance` in
`produce.assemble_and_serve` after `measure_debt` and return a typed `409`
verdict as data; (b) move `debt_tolerance` into
`request_contract.unsupported_arguments` with a declared reason, deleting the
409 promise from its description; or (c) obtain a `D-IMPL` ruling that the
parameter is advisory-at-this-tier and rewrite the contract description to say
so. In all cases fix `read()` to carry `asked.parameters[PARAM_DEBT_TOLERANCE]`
rather than the artifact's copy, or delete the dead field.

## Warnings

### WR-01: `resolve_max_depth` crashes on non-numeric input and silently coerces bool/float — an ungoverned path for a caller-supplied value

**File:** `examples/cp-04-corporate-family-tree/deployment.py::resolve_max_depth`
**Issue:** `int(cast(Any, parameters[PARAM_MAX_DEPTH]))` raises an uncaught
`ValueError` for `max_depth="six"` — reachable from the MCP tool, whose JSON
arguments are caller-typed and reach `assembler.assemble` before
`refuse_request` ever runs (the CLI's `type=int` shields only `run.py`). The
result is a `ToolError` with interpreter prose instead of the D-60
returned-as-data `type-mismatch` violation. The same line accepts
`max_depth=True` as depth 1 (`bool` is `int`; `produce.assemble_and_serve`'s
`isinstance(max_depth, int)` door also passes it) and truncates
`max_depth=2.5` to 2 — a coercion adjacent to the clamp this rung's own
docstrings forbid, saved only by `refuse_request` later flagging the original
parameter's type.
**Fix:** Refuse non-`int` (and `bool`) by type before converting:

```python
requested_raw = parameters[PARAM_MAX_DEPTH]
if isinstance(requested_raw, bool) or not isinstance(requested_raw, int):
    return DepthNotAnInteger(parameter=PARAM_MAX_DEPTH, supplied=requested_raw)
requested = requested_raw
```

(or route the value through `refuse_request` first — see WR-02).

### WR-02: Contract validation runs after the full two-store source read, contradicting the declaration in two documents

**File:** `examples/cp-04-corporate-family-tree/produce.py::assemble_and_serve` (order: `read(...)` → `refuse_request` → unsupported-parameter loop); `examples/cp-04-corporate-family-tree/ccf_config.yaml` (`request_contract` header)
**Issue:** `ccf_config.yaml` states *"Checked at the door, before either store
is opened, so a question this class does not answer costs nothing"*, and
produce.py's inline comment above `refuse_request` repeats *"Checked before
the graph is touched ... costs nothing."* In the shipped order, `read()`
performs the complete assembly-side read — anchor resolution, the bounded
Fluree walk, three node-fact enumerations, the batched PostgreSQL join, the
minting and both closed-world guards — **before** `refuse_request` and before
the `as_of` inert-parameter check. A question carrying an undeclared
parameter, a type mismatch, or the declared-and-always-refused `as_of` pays
for a full two-estate read and is then refused. "The graph" in the comment can
be read as the fabric's L3 (ingest is indeed later), but "before either store
is opened" and "costs nothing" are false as written.
**Fix:** The request contract is available off `booted.artifacts` without the
source read — validate the request and check `unsupported` **before** calling
`read(...)` (build the contract from
`booted.artifacts[KEY_REQUEST_CONTRACT]`), or amend both documents to state
the true order. Prefer the reorder: it also shrinks the surface CR-01/WR-01
expose, since malformed questions then never reach the estate.

### WR-03: `intent` — "selects the policy envelope; an unknown intent is a 400" — is unimplemented, and the caller's copy is silently discarded

**File:** `examples/cp-04-corporate-family-tree/ccf_config.yaml` (`arguments.intent`); `examples/cp-04-corporate-family-tree/deployment.py::request`
**Issue:** The contract declares `intent` required with the description
"selects the policy envelope; an unknown intent is a 400". Nothing selects
anything on it — the policy bundle key is fixed — and no value check exists:
`refuse_request` verifies only `type: string`, so `intent: "anything"` serves.
Worse, `deployment.request` sets
`intent=declaration["parameters"][PARAM_INTENT]` from `question.yaml`
unconditionally, so `ProductRequest.intent` is always
`concentration-review` even when the caller's `parameters["intent"]` says
otherwise — two copies of one fact that can disagree with no refusal, on a
product whose own `demonstration_request` docstring names exactly that
duplication as the defect it avoids for `lei`.
**Fix:** Either validate the caller's `intent` against a declared closed set
and refuse unknowns as the description promises, or rewrite the description to
what is true ("names the caller's purpose; travels into the content address;
not interpreted at this tier") — and in `request()`, derive
`ProductRequest.intent` from `parameters` (refusing a mismatch), not from the
artifact.

### WR-04: The door forwards the entitled perspective, but `deployment.read` rebuilds it with the config's `principal_id` — the verified caller identity never reaches the replay record

**File:** `examples/cp-04-corporate-family-tree/server/compose.py::build_resolver` (perspective "FORWARDED, never re-derived"); `examples/cp-04-corporate-family-tree/deployment.py::read` / `::perspective`
**Issue:** `serve.py::resolve_perspective` builds
`Perspective(principal_id=grant.client_id, role=composed.role)` — "the subject
is the **verified** `client_id`" — and `compose` forwards it to
`assembler.assemble`. But the assembler consumes only `perspective.role`
(passed into `produce` and on to `deployment.read`), and `read()`
reconstructs the scenario perspective from the registered artifact via
`perspective(role)`, whose `principal_id` is `ccf_config.yaml`'s
`PRIN-COV-001`. The projection and `build_replay_record` therefore run under
the config's principal, not the door's verified caller. The two coincide today
because the minted token's `client_id` is the same string, which is exactly
why `test_the_resolver_assembles_under_the_perspective_it_was_handed` (which
checks the role axis only) cannot see it. This is DI-15.5-03's re-derivation
returning on the principal axis: a token grant carrying a different
`client_id` would be entitled as one principal and replay-recorded as another.
**Fix:** Thread the full forwarded `Perspective` through `produce` to `read`
(or have `read` accept a `principal_id` override beside `role`) so the
scenario's perspective artifact is `model_copy(update={"role": ...,
"principal_id": forwarded.principal_id})`; assert the principal in the replay
record from the door test the way the role is asserted today.

### WR-05: `run.py::_report` crashes on the payload's own declared `NOT_EVALUABLE` depth sentinel

**File:** `examples/cp-04-corporate-family-tree/run.py::_report` (`deepest = max((int(node["depth"]) for node in nodes), default=0)`)
**Issue:** `projection.py::_node` serves
`"depth": generation_by_node.get(uri, NOT_EVALUABLE)` — the string sentinel is
a declared member of the payload's vocabulary ("never `0` and never
`null`-as-a-lookup", spec §C.4 trap 5). The reporter does `int(node["depth"])`
over every node: the first payload that actually exercises the sentinel (any
future estate where the L4 undirected walk admits a node outside the directed
reach at the ceiling — the exact D-36 gap the sentinel exists for) makes the
report die in `ValueError` after printing the JSON. The defensive value and
its only consumer disagree about the contract.
**Fix:** Skip or bucket non-int depths:

```python
depths = [node["depth"] for node in nodes if isinstance(node["depth"], int)]
deepest = max(depths, default=0)
```

and print the count of `NOT_EVALUABLE` members if any — the gap made visible,
per the projection's own docstring.

### WR-06: SQL identifiers interpolated into the attribute-leg statement without identifier quoting

**File:** `examples/cp-04-corporate-family-tree/deployment.py::resolve_attributes`
**Issue:** `f'SELECT {projection} FROM "{resolved.schema}".{table} WHERE
{key_column} = ANY(%s)'` — `schema` comes from an environment variable and is
double-quoted but not escape-doubled (a `"` in the value breaks out of the
identifier); `table`, `key_column`, and each of `served_columns` come from
`artifacts/source-vocabulary.yaml` and are interpolated bare. All sources are
deployment-controlled, so this is not remotely injectable, but the example is
the adoption template (§9): adopters will repoint these artifacts at their own
estates, and a column name like `legal-name` or a quoted schema silently
breaks or escapes the statement. The key **values** are correctly bound via
`ANY(%s)`.
**Fix:** Compose identifiers with `psycopg.sql`:

```python
from psycopg import sql
query = sql.SQL("SELECT {cols} FROM {sch}.{tbl} WHERE {key} = ANY(%s)").format(
    cols=sql.SQL(", ").join(map(sql.Identifier, (key_column, *columns))),
    sch=sql.Identifier(resolved.schema), tbl=sql.Identifier(table),
    key=sql.Identifier(key_column),
)
```

(The `{schema}`-substitution in `tests/examples/cp_04_seed.py` and the dump
tool share the pattern; test-side it is acceptable, but the seed's
`CREATE SCHEMA IF NOT EXISTS {schema}` would also benefit.)

### IN-02: `assemble_and_serve` reuses the local `served` for two unrelated types

**File:** `examples/cp-04-corporate-family-tree/produce.py::assemble_and_serve`
**Issue:** `execution, served = _project(...)` binds the served **roster**
(`tuple[str, ...]`); forty lines later `served, store = _serve(...)` rebinds
it to a `ServedProduct`. Correct today only because `measure_debt` consumes
the roster in between; a future edit that moves either line inherits a
type-confused name.
**Fix:** Name them `served_roster` and `served_product`.

### IN-03: `transport.ask` falls back to a wall clock

**File:** `examples/cp-04-corporate-family-tree/transport.py::ask` (`asked_at = request.temporal_boundary or datetime.now(UTC)`)
**Issue:** The assembler's docstring makes "nothing here reads a clock" a
claim of the assembly path; a `WireRequest` without a `temporal_boundary`
silently assembles at `now()`, producing a content address no replay can
re-ask. `run.py` always supplies `as_of`, so the branch is latent.
**Fix:** Refuse a boundary-less wire request by name, or document the fallback
as the deliberate non-replay mode.

### IN-04: The door's scratch root grows without bound over its lifetime

**File:** `examples/cp-04-corporate-family-tree/server/compose.py::build_resolver`; `server/serve.py::serve`
**Issue:** Every ask mints a fresh per-run SQLite file and an
`artifacts-store` under the one `root` the door holds; nothing removes them
until process exit. Correct for isolation, but a long-lived stdio door
accumulates one full fabric per question. (Robustness note, not a performance
finding.)
**Fix:** Per-ask subdirectory removed in a `finally`, or a documented
statement that the door's lifetime is expected to be short.

### IN-05: `detect_cycles` excludes self-loops and recurses without a bound

**File:** `examples/cp-04-corporate-family-tree/deployment.py::detect_cycles`
**Issue:** `len(stack) >= 2` means an `owns` edge from a company to itself —
a real GLEIF pathology — would never surface as an `ownership_cycle` finding,
and the exclusion is nowhere documented as deliberate (the D-35 self-loop
discussion concerns ingest minting, not source data). Separately, `walk` is
recursive; elementary-path depth is small on this estate but unbounded in
general — `RecursionError` on a pathological family would be an ungoverned
failure.
**Fix:** Document the self-loop disposition (or report length-1 circuits),
and note the recursion bound beside the walk.

### IN-06: `refuse_stale_vocabulary_pointer` failure message misstates the condition

**File:** `examples/cp-04-corporate-family-tree/deployment.py::refuse_stale_vocabulary_pointer`
**Issue:** The message reads "its VALUES carry none of {len(missing)} of
them" — fired whenever **any** IRI is missing, including when five of six are
present. A refusal that must name itself should not miscount itself.
**Fix:** "is missing {len(missing)} of the six:".

### IN-07: `--asked-at` accepts a naive datetime despite the help text requiring timezone-aware

**File:** `examples/cp-04-corporate-family-tree/run.py::_parser` / `::_asked_instant`
**Issue:** Help says "ISO-8601 and timezone-aware"; `datetime.fromisoformat`
accepts a naive value and nothing checks `tzinfo`. Today the naive instant
flows through consistently (every downstream comparison derives from it), but
the printed transcript and content address then carry an instant whose UTC
meaning is host-dependent.
**Fix:** Refuse `parsed.tzinfo is None` by name.

### IN-08: `question.yaml` carries a second `unsupported_parameters` list no code reads

**File:** `examples/cp-04-corporate-family-tree/artifacts/question.yaml` (`unsupported_parameters: [as_of]`)
**Issue:** The operative declaration is
`ccf_config.yaml::request_contract.unsupported_arguments`; the question
artifact's copy is decorative and can drift — the exact two-copies shape the
tree elsewhere refuses (see WR-03, and `demonstration_request`'s own rule for
`lei`).
**Fix:** Delete the block, or add a check that holds the two documents equal.
