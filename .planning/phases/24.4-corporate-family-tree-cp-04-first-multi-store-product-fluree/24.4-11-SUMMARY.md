**One-liner.** `CFT-G06` through `CFT-G09`, `CFT-G15` and `CFT-G16` execute

the identical outcome, and only moving a class through the shipped projection

**Serially, in this tree, by this agent.** No subagent, no worktree, one

### `CFT-G06` — silently honor the inert parameter

Mutation: the declared-but-inert branch in `assemble_and_serve` neutralized, so
the parameter is noted and then ignored.

Observed, **both limbs**:

> `CFT-G06: 'as_of' was ANSWERED rather than refused — a tree came back over 22 members.`
> `CFT-G06: the assembly SERVED ['Assembled'] while 'as_of' was on the wire.`

The second limb is the one a reason-string check cannot make. It exists because
cp-03's close panel found precisely that shape in its own `OFS-G06`: a product
can note the parameter, emit the declared reason, and complete the assembly
anyway.

### `CFT-G07` — drop the closing edge

Mutation: `closing_edge` emitted as `None` for every finding.

Observed:

> `CFT-G07: the cycle reached the consumer with NO closing edge.`

The members survived, every count stayed right, and the arrow that makes it a
circuit was gone. The members are compared as an **ordered sequence** and not as
a set, because the same circuit entered from a different node names a
**different** closing edge — `test_the_cycle_check_refuses_a_rotated_roster`
feeds the shipped check exactly that and watches it refuse.

### `CFT-G08` — flag cycle membership on the nodes

**RUN IN TWO VARIANTS, and the reason is recorded rather than glossed.** The
declared sabotage moves the cycle *off* `findings[]` *and* onto the nodes. The
gate's positive limb — the finding must exist — returns first, so the **content
limb was never reached**.

**Variant A**, the sabotage as declared:

> `CFT-G08: no finding of type 'ownership_cycle' is in findings[].`

**Variant B**, the node flag alone with the finding kept:

> `CFT-G08: the served node field 'in_cycle' takes the value True on EXACTLY the cycle members ['CycCalderIndustrialNv', 'CycMeridianHoldingsSa', 'CycThornburyCapitalLtd'] and on no other member.`

**The content limb reads a PARTITION and never a name.** A check scanning the
node keys for the token "cycle" is green against a flag called `flagged`, which
`test_the_orthogonality_check_refuses_a_flag_named_anything` demonstrates
against the shipped check. Measured against the shipped product **before** the
sabotage was written: no field of a served node partitions the 22 members into
the cycle's three — `lei` and `attributes` are null on twenty, `depth` takes
three different values across the three, `type_chain` and `conditioning` are
identical across all 22, and `uri`, `entity_id` and `label` are distinct per
member. So the check is not merely reactive; it was shown to have nothing to
report on a correct product before it was shown to report on a wrong one.

### `CFT-G09` — drop members whose PostgreSQL join fails

Mutation: the served member set filtered to those whose join resolved.

Observed, **all three limbs**:

> `CFT-G09: 2 members were served where expected.yaml::census.anchor_subtree declares 22. Served ['SuperMicroComputerBV', 'SuperMicroComputerInc']`
> `CFT-G09: [the twenty, by name] resolve to no PostgreSQL row and were DROPPED from the tree.`
> `CFT-G09: the unresolved roster reached the consumer as [] where expected.yaml declares [the twenty].`

The sabotage returns a smaller, tidier, **wrong** family with no error at all,
and only the roster catches it: a count alone passes on twenty entirely
different nodes.

### `CFT-G15` — serve the tree without type information

Mutation: `type_chain` served as an empty list on every node **and** on the
anchor.

Observed, **all four limbs**: all 22 members "were served with an EMPTY class
chain"; the anchor's chain "reached the consumer as `[]` where expected.yaml
declares `['Agent', 'Corporation', 'FormalOrganization', 'LegalEntity',
'LegalPerson', 'Organization', 'Party']`"; and `CycCalderIndustrialNv` "carries
0 classes where expected.yaml::census.cycle_member_typing declares 7".

### `CFT-G16` — substitute a hand-written role map

Mutation: a module-level role map keyed by **entity name** substituted for
`FamilyTreeProjection._detailed_for` at both call sites.

**RED ONLY ON THE MUTATION LIMB, AND THAT IS THE FINDING WORTH CARRYING OUT OF
THIS PLAN.** Under the sabotage the served outcome was **identical**: 22
detailed for `credit-officer`, 0 for `kyc-analyst`, the class axis still named
`Corporation`, and every node's `carries_class_axis` still agreeing with its own
served chain. **Both outcome limbs PASSED.** What failed was the limb that
strips the class axis from one member's chain, through the shipped projection,
and requires that member to move in both views in opposite directions:

> `CFT-G16: with the class axis stripped from 'CycCalderIndustrialNv', role 'credit-officer' detailed [all 22] where the class chain implies [the other 21]. The conditioning did not FOLLOW the chain.`
> `CFT-G16: … role 'kyc-analyst' detailed [] where the class chain implies exactly ['CycCalderIndustrialNv'].`

**A gate written as criterion 40 words it — *"perspective conditions on FIBO
class"*, asserted by observing that two roles see different views — would have
passed its own sabotage.** That is wave 8's `CFT-G05` finding recurring on a
different gate, and the mutation limb was written *before* the sabotage was run,
from exactly that reasoning.

A **second** check went red beside it:
`test_no_role_to_entity_mapping_exists_anywhere_in_the_example` named **24**
collection literals in the sabotaged file naming a declared role or a served
entity — the 22 entity URIs inside the map plus its two role keys. That limb is
**structural** and deliberately not a token scan: the word "class" appears in
both a class-conditioned projection and a role map keyed by class name, and
`credit-officer`, `kyc-analyst` and several entity names appear legitimately in
this example's **prose** already, so the scan is over the parsed source and looks
only inside `dict`, `list`, `tuple` and `set` literals.

## Deviations from Plan

### 1. [Rule 1 — Bug] Two expectations resolved from the file their own sabotage was about to mutate

**Found during:** Task 3, planning the six sabotages against the committed gate
module.

**Issue:** `CFT-G06` read its expected status from
`examples/cp-04-corporate-family-tree/produce.py::ParameterNotSupported`, and
`produce.py` is the file that gate's sabotage edits. The cycle finding type was
read from `examples/cp-04-corporate-family-tree/deployment.py`, which is safe,
but the same reasoning applied to `projection.py` for `CFT-G07` and `CFT-G08`.
An expectation and a behavior resolving from one file move together under a
mutation of that file — which is exactly the shape that lets a gate pass its own
sabotage.

**Fix:** the status is now **authored** in the module from locked criterion 30
and Standard §9, with a precondition asserting the shipped verdict type still
carries the same number so a drift is reported rather than absorbed; the cycle
type now comes from `artifacts/expected.yaml::census.cycle_1.type`. The one
remaining overlap — `CFT-G09`'s unresolved finding type token — is recorded in
the gate's own `observed_red` record with the reason it does not let the gate
pass.

**Files modified:** `tests/examples/test_cp_04_payload.py`. **Commit:**
`8ecd22f`.

### 2. [Rule 2 — missing critical functionality] `CFT-G15`'s second cycle is not assertable from a served payload

**Found during:** Task 2, writing the content limb.

**Issue:** the plan's acceptance criterion asks that `CFT-G15` assert the
chain's content *"for the anchor and for one member of each cycle"*. **Against
this estate the second half cannot be done from a served payload**, and the
reason is already declared rather than discovered here:
`artifacts/expected.yaml::census.cycle_2` records `external_in_edges: 0`, so no
walk from any LEI-bearing anchor reaches cycle 2, and
`census.cycle_member_typing` records that no cycle member carries an LEI — so
cycle 2 cannot be reached as a subtree and cannot be asked for as an anchor
either. Asserting its five-class chain would have meant asserting something the
gate's own subject (*each served node*) does not cover.

**Fix:** the observation was **asserted in the direction the estate can carry**
rather than dropped. `test_no_cycle_two_member_reaches_a_served_payload` asserts
that no cycle-2 member is in the served set, that `expected.yaml` still declares
zero external in-edges, and that the two declared chain lengths still differ —
so if the estate ever changes, the scope note fails rather than going quietly
stale. The 7-versus-5 fact itself is asserted against the store by
`tests/examples/test_cp_04_cycles.py::test_the_two_circuits_class_chains_differ_and_no_member_carries_an_lei`,
which is where it belongs.

**Locked criterion 39 is discharged in full** — it says *"each served node
carries its FIBO class chain"*, and that is what the gate asserts. Nothing about
a ruled criterion was reinterpreted.

**Files modified:** `tests/examples/test_cp_04_payload.py`. **Commit:**
`8c530a7`.

### 3. [Rule 2 — missing critical functionality] `CFT-G08` needed a second sabotage variant

**Found during:** Task 3.

**Issue:** the declared sabotage — *"flag cycle membership on the nodes instead
of in `findings[]`"* — trips the gate's positive limb, which returns before the
content limb runs. Recording that as the observation would have left the
partition check, which is the gate's whole content, never watched failing.

**Fix:** a second variant with the finding kept and the node flag alone, run
separately and recorded separately. Both variants and both observed messages are
in the `observed_red` record. This is the wave-8 shape applied to a different
gate: there, `CFT-G01`'s sabotage had to be **strengthened** because the obvious
one was inert; here `CFT-G08`'s had to be **split** because the obvious one
short-circuits.

**Files modified:** `examples/cp-04-corporate-family-tree/artifacts/gates.yaml`.
**Commit:** `ff075da`.

### 4. [Rule 3 — blocking] the sibling roster constant had to be extended

**Found during:** Task 3, after writing the six records.

**Issue:** `test_cp_04_gates_declaration.py::OBSERVED_RED_IDS` held the roster at
five and `test_exactly_the_sabotaged_gates_are_recorded_observed_red` asserts it
in **both** directions, so writing six records without extending it makes that
check red by construction.

**Fix:** extended to eleven, and watched failing with `CFT-G16`'s record renamed.
It was not weakened: both directions are still rosters, and the docstring already
recorded that plans 11 and 12 would move the boundary.

**Files modified:** `tests/examples/test_cp_04_gates_declaration.py`. **Commit:**
`ff075da`.

### 5. [Rule 1 — Bug] a control misread the field it was controlling, and the shipped check caught it

**Found during:** Task 2, the first run of the module.

**Issue:** `test_the_conditioning_check_refuses_a_field_that_disagrees_with_the_chain`
built its "compliant" pair with `carries_class_axis` set **per role**. That field
is a property of the **node**, not of the role: both views of a member that
carries the class must report that it carries it, and only `detailed` differs.
The shipped check refused the supposedly-compliant pair, which is the control
being controlled by the thing it controls.

**Fix:** the compliant pair now reports the field identically under both roles
and only the violating pair disagrees; the misreading is recorded in the
control's own docstring so a later reader meets it as a correction rather than
as a convention.

**Files modified:** `tests/examples/test_cp_04_payload.py`. **Commit:**
`8c530a7`.
