## The two findings worth naming beyond their fix

**Finding 2 is not a tidiness point.** `served_jurisdictions` names the
fill-from-anchor sabotage as living in `deployment.py`; `_attributes` names the
SAME sabotage as living in `projection.py`. Applied at the second site, the
shipped roster did not move, because it was reading the first site's map — so
`CFT-G09` stayed GREEN while twenty members carried a jurisdiction no source
asserted about them, and the only thing that noticed was a pinned content
address. **Two places computing one fact is the defect one level up, and this is
the second time this phase has met it** — the first was `S`'s denominator.

**Finding 9's fix exposed a bigger one, and it came from BUILDING the control
rather than from reading the code.** `refuse_stale_vocabulary_pointer` looks for
the IRIs that `family_predicate_iris()` returns, and that function reads
`SOURCE_VOCABULARY` — the very document the fourth condition requires to be among
the named ones. So for that document the second condition compares a file against
itself and **cannot fail**: a scratch `source-vocabulary.yaml` declaring
`iri: TBC` for all six passes. Asserted as a property by
`test_the_vocabulary_pointer_cannot_fail_over_its_own_source_document`, recorded
as deferred item 15, and NOT closed — closing it needs either a second,
independent statement of the six IRIs (a second place for one fact) or a decision
about where they live.

## Deviations from Plan

1. **Finding 2's roster reads `_attributes`, not the emitted node blocks.** The
   obvious reading of the finding is *"read what the payload served"*, and the
   node blocks gate `attributes` on the role's conditioning — so a role
   detailing nothing would see every member as unresolved, which would make a
   role's VIEW change a finding about the ESTATE, and would move the
   `kyc-analyst` content address Dave pinned on 2026-09-01. `_attributes` is the
   resolution both node blocks and the roster now read, and it is
   role-independent. **Verified payload-neutral by `CFT-G16`'s two pinned seals
   passing unchanged.**

2. **Finding 11's scope claim is asserted rather than declared.** The instruction
   this project works under is that expected values come from an artifact. The
   VALUES do — `census.anchor.type_chain`. The SCOPE — that every subtree member
   carries that identical chain — is asserted as an observation, because
   `expected.yaml` records the homogeneity in a COMMENT and writing the seven
   names a second time would be the second place to change one fact that
   document refuses by name. **Flagged rather than presented as ruled:** if Dave
   wants a declared `class_profile` key, the append is mechanical and this note
   is where the alternative is recorded.

3. **Finding 4's fix touches `docs/schemas/`, outside `examples/` and `tests/`.**
   Explicitly permitted by this plan's instruction, conditional on no declared
   value moving — which is asserted as an empty roster of failing ids rather than
   reported.

4. **`resolve_max_depth`'s residual: DOCUMENT AS CLI-ONLY.** Dave ruled it an
   advisory with two closures; one had to be taken and named. Taken: document,
   do not refuse — because a type refusal inside `resolve_max_depth` would put a
   second, differently-worded rejection of a bad depth beside the one `CFT-G03`
   already holds, on a path no shipped caller reaches. **No code changed and no
   wording written into anyone's name.** Recorded in `24.4-CLOSE-REVIEWS.md` §7
   as this plan's disposition, his to overturn.

5. **Findings 5, 8, 10, 13's residuals are ADVISORY, not fixed.** Each is a
   wording or strengthening question in another author's reasoning, and §3.1's
   triage puts advisory findings in the review appendix rather than in the fix
   set. They are in `24.4-CLOSE-REVIEWS.md` §5 and §9.
