## `D-IMPL-229`, implemented

### The policy axis is observed family membership

`ccf_config.yaml` now classifies both entity classes on `family_id`.
`deployment.py::mint_family_membership` mints the anchor's LEI onto every node
the walk admitted, so the value is **observed** and there is nothing to be
absent.

**Measured, not assumed.** `PolicyFilter._admits` was instrumented in the SDK's
own module for one full run:

| | |
| --- | --- |
| calls to `_admits` | **22** |
| distinct `(entity_class, attribute)` pairs | `(family_anchor, family_id)`, `(family_member, family_id)` |
| distinct values presented | exactly one — the anchor's LEI |
| **calls where the value was `None`** | **0** |

### `{NL, US-DE}` moved and did not disappear

It is now `source-vocabulary.yaml::entitlement.served_jurisdictions`, served on
the payload and asserted there. It appears **nowhere** as
`permitted_classifications` — that key is declared `[]`.

`refuse_open_jurisdiction_world` holds it closed in **both** directions against
what the payload SERVES. Nulls are excluded from the comparison, because a null
token inside a closed set is what `D-IMPL-229` refuses by name.

### A row-less member carries `null`, never the anchor's Delaware

`served_jurisdictions` reads the stored `legal_jurisdiction` or returns `None`.
There is no fallback and no `or` in the function.

**The fill-from-anchor sabotage, observed:**

| | compliant | sabotaged |
| --- | ---: | ---: |

| closed-world check | passes | **still passes** |

**The set does not move; only the roster does.** That is the whole reason
`D-IMPL-229` requires the roster: a check reading the jurisdiction set measures
vocabulary, and only the roster measures content.

### The finding carries its roster

`unresolved_jurisdiction`, four keys in the shape `expected.yaml` declares,
`members` = the twenty by URI, orthogonal to the tree exactly as the cycle
findings are. Never a count and never `len(findings) > 0` (`D-13`).

### No new gate id was minted

The roster's home is **`CFT-G09`**, which already governs *"a node carrying no
LEI stays in the tree AND in the roster. A failed join is a null resolution or a
finding"* — the finding IS the mechanism that gate names. The roster of twenty
and the `CFT-G16` discriminating class are appended to `expected.yaml` for plan
`24.4-11` to read. Sixteen gates, `CFT-G01`..`CFT-G16`. The withdrawn
seventeenth id appears nowhere in the example.

## Ontology role 1 was NOT built, and why

No type-constrained walk, no per-hop admitted-class filter, no stopped-at node,
and no `CFT-G17` value anywhere. The measured reason, twice over:

1. **`D-32` — the estate cannot exhibit the stop.** Over all 748 family nodes no
   LEI-bearing anchor reaches a node outside the 7-class `LegalPerson`
   `Corporation` profile within depth 3.
2. **`D-33` — the SDK cannot express it.** Traversal types the walk on EDGES
   only; `seed_entity_classes` selects walk STARTING POINTS and is never
   re-applied per hop.

**Measured again in this plan, and it sharpens both:** all 22 SMCI-subtree nodes
carry the **IDENTICAL 7-class chain**. No FIBO class discriminates between
members of this family at all.

That measurement is why `perspective_discriminating_class` is what it is. The
two roles differ by a difference between **VIEWS**, not between members: both
read `Corporation` off the same chain, the credit officer details the members
that carry it (**22**) and the KYC analyst details the ones that do not (**0**).
One mutation to one node's chain moves that node in both views, in opposite
directions — which is what a role map keyed by entity name cannot do.

## Deviations from plan

### 1. [Rule 2 — missing critical mechanism] The perspective roster could not live in `ccf_config.yaml`

**Found during:** Task 2. §D.2.1 role 3's claim is about TWO roles, and
`ccf_config.yaml::default_perspective` holds one.

**Why not there:** `src/ccf/controlplane/artifacts.py::DeploymentConfig` rules
that *"unknown top-level keys are an error"* and reserves exactly eight section
names. A `perspectives:` block would be refused at parse.

**Fix:** a `perspective_conditioning:` block in `source-vocabulary.yaml`, beside
the `entitlement:` block that already lives there for the same reason. It
declares one class axis by IRI and each role's side of it, and names no entity.
`deployment.perspective(role)` selects among the declared roles and refuses an
undeclared one.

**Commit:** `ccfca1f`

### 2. [Rule 1 — the plan's own check cannot distinguish the compliant case] The assembler grep gate is import-scoped

The plan's `<automated>` block runs
`! grep -nE '\b(mcp|fastmcp|ccf_runtime|ccf\.client|egress|server)\b' assembler.py`,
and the same task requires the module docstring to STATE the standalone claim.
Those two are mutually exclusive as written: stating *"it imports nothing from
`ccf_runtime`"* puts the token in the file.

**Measured on the shipped, compliant file:** **5** whole-file grep hits, **all 5
inside the module docstring**, **0** in any import.

**Fix:** an AST-based, import-scoped check with a control on the control —
sabotaged by inserting each of the six forbidden roots as an import in turn, and
it fired on **all six**. The plan's expression is retained in the record as the
weaker form it is.

Two further notes on that expression: `grep` here is `ugrep 7.8.4`, which the
phase has already recorded as rejecting `\b` inside an alternation; and the
compliant file's own exit code was `0`, i.e. the gate as written reports a
violation against a conforming file.

### 3. [Rule 1 — bug] Four `sdk_mechanism` citations in the recipe named symbols that do not exist

`artifacts/assembly-recipe.yaml` cited `assembler.py::_normalize_edges`,
`::_resolve_attributes`, `::_detect_cycles` and `::_surface_duplicate_pair`. All
four live in `deployment.py` under their real names. The citation lint could not
see them while `assembler.py` did not exist; creating it turned `make lint` red.

Re-resolved to `deployment.py::normalize_edges`, `::resolve_attributes`,
`::detect_cycles` and `::surface_duplicate_pairs`. This is `D-IMPL-227`'s class:
*"a pointer to the wrong file and a pointer to the wrong ruling are the same
defect: a reader stops looking."*

**Commit:** `674e27d`

### 4. [Rule 1 — bug] `debt_tolerance` could not satisfy its own request contract

`question.yaml` quotes it `"0.25"` — deliberately, because the canonical encoder
refuses a float — and `ccf_config.yaml`'s request contract declares
`type: number`. The request was refused `type-mismatch` on every run.

Fixed at rung 03's own seam: `deployment.demonstration_request` converts to
`Decimal` when composing the question, which is the one representation that
satisfies both. The same function composes `lei` from `question.yaml`'s
`subject:` rather than the artifact carrying the anchor twice.

### 5. [Rule 1 — bug] `FamilyScenario.depth_by_node` carried a claim that is false when measured

It read: *"a second computation of the same number, deliberately: if the two ever
disagree, the walk is not doing what the operator parameters say it is."*
They disagree at depth 2. Corrected in place with the measurement, and recorded
as `D-36` — see **Deferred issues**.

### 6. [Rule 1 — bug] `deployment.py::classify_family` and its vocabulary

Struck and replaced per `D-IMPL-229`, together with `ccf_config.yaml`'s
`permitted_classifications`, `source-vocabulary.yaml`'s
`classification_sources`, and the spec's §B.2 residency row. This is the
plan-brief's authorized amendment of plan `24.4-06`'s file, not a re-planning of
it. Every public name the already-shipped test modules use — `normalize_edges`
with `directions=`, `detect_cycles`, `enumerate_family_triples`,
`FamilyEdges.from_pairs`, `family_predicate_directions` — is unchanged and all
**69** cp-04 tests pass.

### 7. [Rule 1 — the control was wrong, not the code] My own `refuse_unbound_family_scope` could not fail

Written alone and sabotaged with a config naming a different family, it was
observed **GREEN**. `policy_parameters` uses `model_copy(update=...)`, which
overwrites the declaration — so a check on the BOUND set structurally cannot see
a config that names a family. Split into `refuse_declared_family_scope` (which
refuses a non-empty declaration) and `refuse_unbound_family_scope` (which refuses
an empty or wrong binding). Both then fired.

The same discipline caught a second wrong control in the session: a lineage
sabotage patched `deployment.config`, a function the product class does not flow
through, and reported GREEN until it was re-driven from the config FILE.

## Deferred issues

Both are recorded in full in `deferred-items.md` §5 and §6.

**`D-36` — the Traversal category expresses an undirected NEIGHBORHOOD.**
`TraversalNeighborhood.apply` symmetrizes its adjacency, so the L4 walk serves
**20 / 22 / 22** at depths 1 / 2 / 3 where the directed family tree gives
**20 / 21 / 22**. The one divergent node is `CycThornburyCapitalLtd`, reachable
in two undirected hops through cycle 1's closing edge. **No declared figure
moves** — criterion 11's census figure re-derives exactly at 20 / 21 / 22 over
the 722 normalized edges, and everything the phase demonstrates is taken at the
declared default of 3, where the two agree at 22. Criterion 49 forbids touching
`src/`, so this rung works within the gap and records it, exactly as `D-35` did.
This is the phase's **fifth** mechanism gap surfaced without a line of `src/`
changing.

**§E.2's `S` routing for absent attribute rows cannot be implemented at the
declared numbers.** Folding attribute coverage into `S` gives
`D_c ~= 0.909` against a declared `debt_tolerance` of `0.25`, so the product
would refuse 409 and never serve the tree that criteria 12 and 33 exist to
protect — while the same table says SERVE. The reconciling per-component weights
are `[TBC — this build]` in §E.2's own words. **No weight was invented.** Every
factor is measured against the whitepaper's own definitions and the shortfall is
served as data — the roster finding and `attributes: null` — rather than folded
into a scalar nobody chose. Measured: `D_c = 0.0909`, signal `ok`. **This needs
a ruling.**
