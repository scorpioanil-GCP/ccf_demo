# Phase 24.4 Plan 10: Five Gates, Five Sabotages, Five Reds — Summary

**One-liner.** `CFT-G01` through `CFT-G05` execute against the shipped product
and every one of them has now been watched failing under its own name — and the
plan's own headline finding is that `CFT-G05`, written the obvious way, would
have passed its own sabotage, because two depths seal to two addresses even when
the walk has stopped reading depth at all.

## The five sabotages, as run

**Serially, in this tree, by this agent.** No subagent, no worktree, one
sabotage in the tree at any moment, `git status --short` confirmed clean between
each and at the end. All five were run at commit **`6213b86`** on
**2026-09-01**.

**Every sabotage mutated the product's Python; none mutated a declaration.** The
constraint is mechanical: if the expected roster and the product's behavior both
resolved from one document, mutating that document would move both sides
together and the gate would pass its own sabotage.

### `CFT-G01` — admit an untyped node

Mutation: the drop guard `if chains.get(uri)` removed so an untyped node is
admitted rather than dropped, **and** the first walked node's type read forced
empty.

**The second half is necessary and is recorded rather than glossed.** Measured
against the committed fixture: all 748 documents carry `@type`, and every object
of every family predicate has a document (657 distinct objects, 0 without one).
So removing the guard **alone changes no output**, and would have been a
sabotage this gate could not have failed — the fourteen-idle-gates shape at the
sabotage rather than at the gate. Stating it is the honest version; a one-line
diff with a green run under it would not have been.

Observed:

> `CFT-G01: node 'http://example.org/fibo/CycCalderIndustrialNv' was served UNTYPED — an empty type_chain.`

### `CFT-G02` — admit a seventh predicate

Mutation: every normalized parent-to-child edge admitted carrying a seventh
predicate beside the ones the source asserted.

**The name is drawn from the declared excluded roster; the fixture cannot
supply it.** `gates.yaml` says the sabotage "draws on real data rather than an
invented predicate" — true of the live `fibo-v2` ledger, which carries seven
other relationship predicates, and **false of the committed fixture**, which
carries exactly the six family predicates plus `ex:lei`, `rdfs:label` and
`rdf:type`. So `hasSubsidiary` is real in the estate and injected by name here.
Recorded rather than implied.

Observed:

> `CFT-G02: the served edge set carries ['hasSubsidiary'], which are not among the six declared family predicates [...]`

### `CFT-G03` — replace the refusal with a silent clamp

Mutation: the `DepthOutOfBounds` return replaced by
`min(max(requested, minimum), maximum)`.

Observed, **both limbs**:

> `CFT-G03: max_depth=7 was ANSWERED rather than refused — a tree came back, walked at max_depth_applied=6 over 22 members`
> `CFT-G03: and the answer was CLAMPED to the declared ceiling 6.`

This is the fourteen-idle-gates class stated concretely: the request said 7, the
walk did 6, the payload was well formed and the content address greened.

### `CFT-G04` — default at serve time

Mutation: `declared_depth_default()` replaced by the literal `3`.

**RED only on the control limb, and that is the point.** The plain limb — *a
missing `max_depth` walks at 3* — **passed under the sabotage**, exactly as a
number-only check would have reported. What failed was the control.

Observed:

> `CFT-G04: with the declared default moved to 1, a missing max_depth still walked at 3. The default did not FOLLOW the declaration`
> `CFT-G04: moving the declared default served the IDENTICAL member roster (22 members).`

The control writes a scratch copy of `ccf_config.yaml` as a **text rewrite of
one line**, never a parse-and-dump: `deployment.py::refuse_stale_vocabulary_pointer`
reads that document's *comments* for the sentence naming where the six predicate
IRIs live, and a YAML round trip would lose it and refuse the whole assembly for
a reason having nothing to do with the gate. The fixture asserts the rewrite
changed exactly one line and that the reloaded declaration reports the new
value — a scratch config that silently failed to take effect would make the
control vacuous, which is how the first draft of this measurement went wrong
(see deviation 1).

### `CFT-G05` — make `max_depth` not change the content address

Mutation: `traversal_parameters` made to return the declared operator parameters
unchanged, so the caller's depth never reaches the walk.

Observed, **on the roster limb only**:

> `CFT-G05: 'max_depth=1 (the declared floor)' and 'max_depth absent (the declared default)' served the IDENTICAL member roster (22 members), so max_depth reached the payload's label but not the walk.`

**THE TWO CONTENT ADDRESSES STILL DIFFERED.** Measured before the gate was
written (by monkeypatch) and again under the real file edit: depth 1 sealed to
`7116f517…` and depth 3 to `205ae065…` while both served the same 22 members,
because `max_depth_applied` is echoed into the payload and the payload is what
is sealed. **A gate asserting only "two depths are two content addresses" —
which is the criterion's own wording — passes its own sabotage.** The roster
limb was written before the sabotage was run, from exactly that reasoning, and
it is the only thing that made this gate able to fail.

## No gate passed its first sabotage

All five went red on the first attempt, each naming its own id, and no gate was
rewritten and re-sabotaged. **That is not the same as saying the risk was
absent.** Two of the five were rewritten *before* they were ever run, because
the design pass measured that the obvious version could not discriminate:

1. **`CFT-G05` written on addresses alone** — measured to pass its own sabotage
   (above). The roster limb exists because of that measurement.
2. **`CFT-G04` written as "the walked depth is 3"** — passes against a
   serve-time literal `3`. The scratch-declaration control exists because of
   that.

A third near-miss belongs in the same list: **`CFT-G01`'s sabotage**, not the
gate. The obvious sabotage — remove the drop guard — is inert against a fixture
that types every node, so the sabotage was strengthened rather than the gate.

## Deviations from Plan

### 1. [Rule 1 — Bug] `git checkout --` on the artifact destroyed the five records I had just written

**Found during:** Task 2, after the five sabotages were complete.

**Issue:** While running a control on the amended declaration test, I made
`gates.yaml` look like it had *lost* a record, watched the check go red — and
then reverted with `git checkout -- examples/…/gates.yaml`. That command reverts
to the **index**, and the five `observed_red` records were unstaged, so it
discarded them along with the control's mutation. Confirmed immediately:
`grep -c "observed_red: null"` returned **16**.

**Fix:** The records were re-authored from the same script and re-verified
(`five recorded`, eleven still `null`, sixteen ids, no `CFT-G17`). Nothing was
lost beyond the re-run. The diff against `HEAD` was then checked to be
**addition-only apart from the five `observed_red: null` lines**, so the
re-authoring is demonstrably not a rewrite of anything wave 3 authored.

**Carried forward:** a per-file revert is only safe for a file whose desired
state *is* the index. Once a file carries unstaged work worth keeping, the
sabotage must be reverted by an inverse edit, not by `git checkout --`.

**Files modified:** none beyond the re-authored `gates.yaml`. **Commit:**
`f17d7ab`.

### 2. [Rule 2 — missing critical functionality] the wave-3 boundary assertion had to be amended, and it says so itself

**Found during:** Task 2, running the sibling declaration module.

**Issue:** `test_cp_04_gates_declaration.py::test_no_gate_is_yet_recorded_as_observed_red`
held all sixteen `observed_red` values to `null`. This plan makes that false by
construction. Its own docstring anticipates it: *"This assertion is expected to
be EDITED by those plans, not deleted — it is the wave-3 boundary written down,
so a later reader can tell an unsabotaged roster from a roster whose records
were lost."*

**Fix:** edited, not deleted, and not weakened. It is now
`test_exactly_the_sabotaged_gates_are_recorded_observed_red`, asserting **both
directions as rosters** (`D-13`) against a new code-level constant
`OBSERVED_RED_IDS` — recorded but not owed, and owed but not recorded, are two
different defects and each is refused by name. A second test was added
requiring every record's `result`, `date` and `commit` to be non-empty, because
`result: ""` validates against the closed schema and says nothing.

**Watched failing:** with `CFT-G05`'s record renamed so it looked lost, three
checks went red together — the closed-schema validation (the key is required),
the two-sided roster, and the empty-record check. **Files modified:**
`tests/examples/test_cp_04_gates_declaration.py`. **Commit:** `f17d7ab`.

### 3. [Rule 2] citations qualified to full paths so the checker can read them

**Found during:** the end-of-plan ratchet measurement.

**Issue:** the first draft cited `deployment.py::traversal_parameters` and
siblings by bare filename. Eleven files in this tree are named `deployment.py`,
so the citation lint counts those as **ambiguous — unchecked**, and the count
rose 47 → 53. Unanchored stayed 0-delta, so the tracked ratchet never moved, but
an unchecked citation is a citation nobody is holding to the tree.

**Fix:** every citation qualified to
`examples/cp-04-corporate-family-tree/deployment.py::…`, which is the house
style already used in `gates.yaml` for `src/` and `runtime/`. Ambiguous returned
to **47** and `checked and passing` rose to **1756**. **Commits:** `6213b86`,
`f17d7ab`.

## What was NOT done, deliberately

- **`CFT-G17` was not minted, and criterion 41 was not rescued.** No test in the
  new module names it, no test asserts a type-constrained stop, and the token
  appears nowhere in `gates.yaml`. The module's docstring records the two
  measured reasons (`D-32`, `D-33`) and that a positive-property restatement was
  refused by name as a tautology over a class-homogeneous population.
- **No `as_of` pin and no depth clamp** anywhere in the shipped module. The clamp
  exists only as a sabotage, applied and reverted.
- **No count-only assertion.** Every comparison over members or predicates is a
  roster. Where a length appears in a failure *message* it is describing a
  roster the assertion already compared.
- **The other eleven `observed_red` values were left `null`** — plans `24.4-11`
  and `24.4-12` own them.
- **`STATE.md`, `ROADMAP.md` and `DECISIONS.md` were not touched.**
- **Criterion 37's wording question was not touched.** It is still open for Dave,
  as `.continue-here.md` records.
