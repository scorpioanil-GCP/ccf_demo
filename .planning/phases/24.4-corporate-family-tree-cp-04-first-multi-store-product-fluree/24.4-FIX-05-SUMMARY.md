## The CR-01 boot-vs-serve partition — justified by tracing, not by name

`deployment.py` had ~30 `raise SystemExit` sites. They are not all the same, and the partition was determined by TRACING which raises a legitimate remote request's DATA can trigger against a correctly-authored deployment — Dave's rule: *"Reserve SystemExit for boot-time/CLI artifact-authoring checks that no remote request can trigger."*

**Converted (serve-path refusals whose condition depends on THIS request's runtime data):**

| Function | Branches | Why serve-path |
|---|---|---|
| `refuse_open_jurisdiction_world` | `not served`, `not observed`, `undeclared`, `idle` | subject is the SERVED family (the caller's anchor's observed jurisdictions); a legitimate ask for a non-demonstration anchor trips it |
| `refuse_unminted_membership` | `not nodes`, `missing` | subject is the served family's walk/membership |
| `perspective` | the `chosen`/caller-role branch (not the config-default branch) | subject is the caller's `role` |

**Left as `SystemExit` (artifact-authoring / config / mechanism assertions no request DATA triggers):** the env `"is not set"` sites (`_setting`, `connection` — objective-explicit boot guards); the vocabulary/config-consistency checks (`refuse_stale_vocabulary_pointer`, `family_predicate_iris`, `family_predicate_directions`, `normalize_edges`'s direction guard, `membership_source`, `membership_value_kind`, `conditioned_roles`, `_rule_for`, `anchor_entity_class`, `member_entity_class`, `build_envelopes`'s payload-key guard); `refuse_open_jurisdiction_world`'s `not declared` branch (empty static artifact); `perspective`'s default-role branch; and both **family-scope** guards.

**On the objective's "family-scope" naming — a determination, recorded for Dave, not a guess.** The objective lists "family-scope" among the serve-path refusals, but its operative discriminator is *"fires as a function of the CALLER'S ANCHOR rather than of deployment configuration."* Traced:
- `refuse_declared_family_scope` fires on `ccf_config.yaml` declaring a family — a deployment-authoring error no request DATA triggers. **Config, not caller.**
- `refuse_unbound_family_scope` references `family_id(asked.subject)` as `expected`, but its raise only fires if `policy_parameters`' substitution fails — a binding-mechanism bug no legitimate request triggers. **Mechanism, not caller.**

Neither matches the operative discriminator, and converting a guard that fires only on a mis-authored/mechanism-broken deployment is exactly the "converting a boot guard" the objective warns is as much a defect as leaving a serve refusal as `SystemExit`. So both stay `SystemExit`. Because the converted jurisdiction guard raises earlier in `source_read` for a refusing anchor, and family-scope passes on every legitimately-served anchor, no legitimate request reaches a family-scope `SystemExit` — leaving them does not carry the CR-01 defect forward. If Dave intended family-scope converted, this is the one-line reversal to make.
