## Both addresses were re-derived, twice, and copied from no prompt

Neither hash was taken from the brief, the README, `D-IMPL-233` or any summary.
Each was produced by two independent runs that had to agree before anything was
written:

| Derivation | `credit-officer` | `kyc-analyst` |
|---|---|---|
| `run.py --role <role>` against the **live estate** (Fluree `fibo-v2`, PostgreSQL `ccf_v2`) | `205ae0658ea626982b9d2923d81a226a00899b0c43ba74bbae4dfea8a140d498` | `838afbb037a8ca820a2854b1ac7eedd296262508ce00d747369bf48ee6077ea8` |
| the `views` fixture against the **committed fixture** in a local `fluree/server:4.1.4` + `postgres:16` | identical | identical |
| detailed members, counted off the served nodes | 22 detailed / 0 undetailed | 0 detailed / 22 undetailed |

The second derivation was the load-bearing one and it was run *before* the pin
was authored: a figure true only of the live estate would be a figure no CI leg
could ever read, and the pin would have been unassertable. The two agreeing is
what makes it a pin rather than a transcript of one machine.

## Task 1 — the pin, and the rule it had to amend

`expected.yaml`'s own header said, in terms:

> **AND THERE IS NO CONTENT ADDRESS IN HERE.** A `payload_hash` authored here
> would be a transcript of a run […] or the suite agreeing with itself.

Dave's instruction contradicts that sentence, and the sentence is not mine to
delete quietly. It is **preserved and marked AMENDED IN PART**, in the same
marked form this phase used for criterion 37 and criterion 41, with the reason
the amendment is narrow written beside it:

- **The rule refuses a transcript** — a hash standing in for content the census
  blocks already declare properly. These two are not that.
- **The served member roster is the same 22 under both roles**, by design and by
  `CFT-G16`'s own first limb. So **no roster in that document can tell the two
  roles apart, and none of them moves when the role stops being read.** The seal
  and the detailed count are the only declared figures that can.
- **A pin nobody writes in the artifact is a pin the test must author** — and a
  test that authors the figure it asserts is the suite agreeing with itself,
  which is the same failure the original rule was written against, arriving from
  the other side.

The declaration also records, as data-adjacent prose, why *"the two addresses
differ"* is **not** what is pinned: `perspective_role` is echoed into the sealed
payload, so two addresses appear even when the role is read for its name and
never for its meaning — the `CFT-G05` `max_depth_applied` defect restated. Each
address is pinned **exactly** instead.

## Task 2 — a fourth limb on `CFT-G16`, not a new gate

`CFT-G17` is withdrawn and was not minted. The roster is still **sixteen**.

`pinned_perspective_violations` reads everything it asserts out of
`artifacts/expected.yaml`, and nothing out of the test module:

| Limb | What it asserts | Source |
|---|---|---|
| declaration | the pinned roles are exactly the roles the deployment declares | `perspective_content_addresses` vs `deployment.declared_roles()` |
| declaration | the two pinned addresses **differ** | `perspective_content_addresses` |
| roster | both roles serve the declared family, as a **ROSTER** (`D-13`) | `unresolved_subtree_members` ∪ `census.anchor_subtree_store_split.the_two_resolving` |
| seal | each role's served content address equals the pinned one | `perspective_content_addresses` |
| count | each role's detailed count equals the pinned one | `perspective_detailed_members` |

Two of those limbs are about the **declaration** rather than the product,
because a check that reads its expectation from a file is only as strong as the
file. A pin naming one role, or naming both roles with one address, would be
satisfied by a product serving a single view under two names.

The 22-member roster is **derived**, never authored: `expected.yaml` declares
the family in two halves (the twenty with no `legal_entity` row, and the two
that resolve), and `declared_family_roster` takes the union and asserts it still
totals the `census.anchor_subtree.reachable_nodes` the same document declares —
20 ∪ 2 = 22, no overlap — so a declaration that lost a member fails there rather
than quietly shrinking what the gate compares against.

**Six controls ship with it.** Five hand the *shipped* check a divergent
subject — a moved seal, one address written twice, a pin missing a declared
role, a moved detailed count, a family missing a member — and two of those five
additionally assert that the *other* limb stayed quiet, so each control isolates
what it names. The sixth is a negative control proving the check can pass, so
the five are watching a check that can fail rather than one that refuses
everything.

## Task 3 — the sabotage, both halves observed

### Sabotage A — the projection ignores the requested role

`FamilyTreeProjection._detailed_for` returns the class test without reading the
role's declared side. Exactly Dave's *"role is cosmetic."*

- **(a) RED naming its own gate id.** `test_cft_g16_perspective_conditions_on_fibo_class`
  failed. The pinned seal fired — *"role `'kyc-analyst'` sealed to `2ea513a5…`
  where expected.yaml pins `838afbb0…`"* — and so did the pinned count —
  *"shown detail for 22 members where expected.yaml declares 0"* — beside the
  pre-existing identical-views and one-mutation limbs.
- **(b) The tree of 22 stayed green.** 36 of the module's 37 tests passed,
  including `test_cft_g09_a_node_with_no_lei_stays_in_the_tree_and_the_roster`,
  `test_cft_g15_each_served_node_carries_its_fibo_class_chain` and
  `test_the_duplicate_pair_is_surfaced_by_the_product`; 130 further cp-04 gate
  tests passed across six other modules. **No limb reported a moved family** —
  zero `symmetric difference` violations, against a control confirming that
  token is producible by this check.

### Sabotage B — the role's *suppression* becomes cosmetic

The attribute block is served regardless of whether the role details the
member. This one was run because sabotage A does not settle the question Dave's
instruction actually raises: A trips several limbs, so it cannot show whether
the pin is **load-bearing or merely redundant** with the roster.

Under B, `kyc-analyst` is shown detail for **nobody** — `"detailed_members": []`
— and is served **two non-null attribute blocks anyway**. Measured on the served
payload, not inferred.

- The served roster: the declared 22, unchanged.
- Both detailed rosters: exactly right. Both detailed counts: exactly 22 and 0.
- The class axis: named correctly. The one-mutation limb: still moves the target
  in both views, in opposite directions.
- **Every other limb of `CFT-G16` stayed green, and so did all 156 other cp-04
  gate tests.** The ONLY violation reported was the seal, `838afbb0…` →
  `745b2543…`.

**That is the pin proving it is load-bearing.** A suppression leak on the
non-detailing role is invisible to every roster, every count and every
named-fact assertion in this suite, and is caught by nothing but the pinned
seal.
