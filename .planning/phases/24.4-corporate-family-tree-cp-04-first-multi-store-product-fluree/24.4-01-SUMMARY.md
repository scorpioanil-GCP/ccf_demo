## Decisions Made

1. **The cycle roster order is a convention, and it had to be pinned.** Criterion 15
   asserts an EXACT ordered roster, but the same elementary circuit entered from a
   different node is the same set in a different order. Rotating each circuit to start
   at its lexicographically smallest member reproduces the locked criterion-15 and
   criterion-16 rosters exactly. **Plan `24.4-06`'s shipped detector must carry this
   convention**, or a correct detector will fail a correct criterion.
2. **The fixture stores each predicate in the estate's own orientation, not normalized.**
   Criterion 6's control reverses one predicate and asserts the root count moves; a
   pre-normalized fixture would make that control unable to fire.
3. **Non-resolving LEIs are absent, not null.** Criterion 12 asserts 20 of 22 subtree
   nodes resolve to no Postgres row; a null-filled placeholder row would falsify it
   while every count still looked right.
4. **The schema name is a parameter.** `postgres_dsn` is session-scoped and delegates
   isolation to a fresh schema; six cp-04 modules seed one fixture.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A false claim in `cp_04_seed.py`'s docstring, caught before commit**
- **Found during:** Task 2 (the seeding contract)
- **Issue:** The docstring asserted that transacting a fixed ledger name six times
  "duplicates every triple" and that "1,058 raw triples become 6,348". That was reasoned
  from Fluree being append-only, not measured. Measured against `fluree/server:4.1.4`:
  the second transaction of an identical body returns `200`, advances `t` from 1 to 2,
  and leaves the family-triple count at **1,058** — RDF set semantics make it a data
  no-op.
- **Fix:** Replaced the assumed claim with four measured ones: `create` on an existing
  ledger returns **409 `err:db/LedgerExists`**; a sibling's write into a shared ledger
  is permanent and moved the census **1,058 → 1,059**; a shared Postgres schema does not
  error but silently rebuilds a sibling's table (142 → 141 → 142). All four are recorded
  in `24.4-MEASUREMENT.md`'s reproduction section.
- **Files modified:** `tests/examples/cp_04_seed.py`
- **Verification:** each of the four run against live containers; outputs recorded
- **Committed in:** `2e8aee0`

**2. [Rule 1 - Bug] An unmeasured claim in the measurement document, caught inside the pass**
- **Found during:** Task 1 (appendix A)
- **Issue:** The criterion-19 appendix row first read *"`SuperMicroComputerInc` has no
  `isDirectlyConsolidatedBy` edge at all"* — written from the shape of the argument
  rather than from a query. Measured, SMCI has exactly **one**, to
  `SuperMicroComputerBV`. Had it stood, criterion 19's control would have been an EMPTY
  walk asserting no cycle — a control that cannot fail.
- **Fix:** Corrected the row to the measured walk (2 nodes, depth 1, 0 cycles) and
  recorded the correction and the full per-predicate child counts in the document.
- **Files modified:** `24.4-MEASUREMENT.md`
- **Verification:** per-predicate child counts from the anchor, all six measured
- **Committed in:** `dddd901`

**3. [Rule 2 - Missing Critical] `seed()` verifies readback rather than trusting a 200**
- **Found during:** Task 2
- **Issue:** Probed against `fluree/server:4.1.4`: a transaction body carrying an
  unrecognized top-level key is accepted with **HTTP 200** and a real commit receipt. A
  body whose `insert` key were misspelled would report success having written nothing,
  and every downstream census assertion would be a true statement about an empty graph.
- **Fix:** `seed()` reads both stores back and refuses to return until each holds what
  the fixture carries. The Fluree readback polls until two **consecutive** reads agree —
  stability, not correctness — and compares once afterwards, so it is not a retry loop
  that stops when the number matches the expectation.
- **Files modified:** `tests/examples/cp_04_seed.py`
- **Verification:** seeded twice; both raised nothing and both reproduced all 32 figures
- **Committed in:** `2e8aee0`

## Findings Raised, NOT Resolved

**1. Criterion 13's `PSC-0124` is not the unique deepest root.** Depth 6 is attained by
**seven** roots: `PSC-0018`, `PSC-0037`, `PSC-0053`, `PSC-0089`, `PSC-0124`, `PSC-0140`,
`PSC-0153`. `PSC-0124` is among them, so criterion 13 is **TRUE as written** and nothing
was adjusted. But a criterion-13 check phrased as *"the deepest root is `PSC-0124`"*
would assert a uniqueness the estate does not carry, and nothing distinguishes
`PSC-0124` — six of the seven span 7 nodes and `PSC-0037` spans 11, so it is not even the
largest. **Plan `24.4-04` should phrase the check as "depth 6, and `PSC-0124` attains
it".** Raised for Dave; not resolved here.

**2. The cycle-roster ordering convention is load-bearing and is not stated in the
criteria.** Criteria 15 and 16 assert exact ordered rosters that hold only under
rotation-to-smallest-member. Recorded in `24.4-MEASUREMENT.md` under criterion 14 so
plan `24.4-06` inherits it.
