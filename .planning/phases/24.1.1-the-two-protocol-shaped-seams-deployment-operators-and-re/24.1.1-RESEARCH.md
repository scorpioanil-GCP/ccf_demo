## Summary

Two things dominate this phase and neither is where the fence suggested it would be.

**First: the replay question has a definitive negative answer.** A refusal returned as data
**cannot** reach the Decision Replay record with `src/` edits confined to
`src/ccf/agents/assembler.py` and `src/ccf/deployment/operators.py`. This is not a close call
or a matter of effort. `src/ccf/replay/record.py::build_replay_record` requires an
`ExecutionResult` and a `ContextProductContract`; `src/ccf/replay/serve.py::serve` requires a
`ServableProduct` that is not constructible outside `run_gates`;
`src/ccf/agents/assembler.py::DeterministicAssembler` holds a
`src/ccf/projection/plan.py::ProjectionOutput`, which carries exactly two fields (`plan_id`,
`payload`) and is structurally not an `ExecutionResult`; and **no module in `src/` or
`runtime/` calls `.assemble(` at all**, so no code path exists that would carry an assembler's
return value anywhere near replay. §2 gives the traced path, the reading options, and the
one module I recommend enumerating.

**Second: the `D-60` design is dominated by an import cycle, not by the type shape.** A
module-level `from ccf.products.refusal import RefusalEnvelope` in
`src/ccf/agents/assembler.py` breaks **13 of 115** `ccf` modules with a hard circular-import
`ImportError` — measured, with the same sweep returning **0** on the alternative. A
module-level `from ccf.products.request import ProductRequestViolation` in the same file
breaks **0 of 115**. And placing a new refusal contract *in* `assembler.py` and wiring it into
`src/ccf/products/refusal.py::REFUSAL_KINDS` breaks **55 of 115**. The cycle picks the design
before any argument about vocabulary does. §4 has the four probes and their controls.

Third, smaller but load-bearing: `src/ccf/products/refusal.py::REFUSAL_KINDS` is **closed by
set equality** against an AST walk of `src/` for every class name ending in `Refusal` or
`Violation`. Any new refusal contract with such a name forces an edit to a **third** `src/`
module, and criterion 12's `PLUS` clause is scoped to *replay-path* modules — so a new
`AssemblyRefusal` type collides with criterion 12 by a route that has nothing to do with
replay. §4.2.

**Primary recommendation:** widen `assemble` to `AssemblyOutcome | ProductRequestViolation`
(zero new types, zero cycle risk, zero `src/` modules beyond the two named), add
`deployment_operators` as a defaulted keyword to `build_operator_registry`, and take criterion
9 to Dave **before Wave 1** with the three readings in §2.4 — because the strong reading needs
`src/ccf/replay/record.py` and the phase cannot decide that for itself.

## 2 · THE REPLAY QUESTION — criterion 9

### 2.1 The actual replay write path in `src/`, traced

There is exactly **one** replay-writing path in `src/`. Here it is, symbol by symbol:

```
src/ccf/products/resolver.py::GovernedResolver.__call__
  │
  ├─ refuse_request(...) → ProductRequestViolation | None
  │     └─ if violation is not None:
  │           return envelope_for(violation, request=identity)   ← RETURNS. NO RECORD WRITTEN.
  │
  ├─ build_operator_registry(...) → ProjectionEngine(...).execute(...) → ExecutionResult
  ├─ ContextProductContract(...)  ← the candidate
  ├─ run_gates(...) → ServableProduct | <a refusal>
  │     └─ if not isinstance(gated, ServableProduct):
  │           return envelope_for(gated, ..., pre_assembly_lineage=candidate.lineage)
  │                                                              ← RETURNS. NO RECORD WRITTEN.
  │
  ├─ src/ccf/replay/record.py::build_replay_record(execution=…, product=gated.product, …)
  └─ src/ccf/replay/serve.py::serve(product=gated, record=…, replay_writer=ReplayWriter(…), …)
        └─ ReplayWriter.write_replay_record → store.put → DeliveryCapability.deliver → ServedProduct
```

The examples reproduce the same shape by hand:
`examples/cp-00-institutional-holders/produce.py::assemble_and_serve` returns the
`ProductRequestViolation` **before** `build_replay_record` is reached, so cp-00's own governed
refusal writes no record either.

**Therefore, as of `a29bd0c`, no refusal of any kind lands in the Decision Replay record.**
Not a request refusal, not a gate refusal. This is the tree's current, deliberate posture — a
refusal returns as a `src/ccf/products/refusal.py::RefusalEnvelope`, and the record is what
authorizes a *delivery*. `src/ccf/replay/serve.py`'s module docstring is explicit that the
successful append *is* the delivery capability: "A caller with no capability has nothing to
deliver with." A refusal has nothing to deliver.

Measurement, with control:

```
$ grep -rn "refus" src/ccf/replay/*.py | wc -l        →  12   (all prose about refusing a read
                                                              or a pin; zero refusal types)
$ grep -c "refus" src/ccf/products/gates.py           →  35   (CONTROL — same instrument, a
                                                              file that genuinely holds refusals)
```

### 2.2 Why the assembler is structurally the furthest thing from replay

Four independent blockers, each verified:

1. **`build_replay_record` needs an `ExecutionResult`.**
   `src/ccf/projection/engine.py::ExecutionResult` carries `plan_id`, `operators_invoked`,
   `steps`, `provenance`, `projection`, `executed_queries`, `survivor_cap`,
   `source_attestation`, and the `state_watermark()` / `touched_entities()` /
   `touched_relationships()` methods `ContextFabricSnapshot.build` calls.
   `src/ccf/agents/assembler.py::DeterministicAssembler` holds
   `projection: ProjectionOutput`, and `src/ccf/projection/plan.py::ProjectionOutput` declares
   **two fields — `plan_id` and `payload`**. It cannot supply the argument.

2. **`build_replay_record` needs a `ContextProductContract`.** It reads `product.tenant_id`,
   `product.temporal_boundary`, `product.debt`, `product.debt_evidence`,
   `product.source_refresh_recency`, `product.obligation_in_force`, and
   `content_hash(product)`. A refusal has no product by definition — that is what makes it a
   refusal.

3. **`serve()` needs a `ServableProduct`**, which
   `src/ccf/products/gates.py::ServableProduct` makes unconstructible outside `run_gates`.
   `DeliveryCapability.deliver` is typed to it.

4. **Nothing in `src/` or `runtime/` ever holds an `AssemblyOutcome`.** Measured:


### 2.4 What each reading of criterion 9 costs — the D-IMPL entry's raw material

**Reading A — the refusal is persisted as its own `DecisionReplayRecord`.**

| Module | What must change | Why |

**Reading B — the refusal is a named sub-structure inside an existing dimension.**

*inside* an existing dimension".

| Module | What must change |
| --- | --- |
| `src/ccf/replay/record.py` | One keyword on `build_replay_record` (e.g. `assembly_refusal: str \| None = None`), one field on `ContentGenerationPath` or `PolicyBindingsSnapshot`, one `NO_ASSEMBLY_REFUSAL` sentinel |

**Reading C — no replay module changes; the refusal merely *carries* what replay pins.**
Costs zero extra modules but, on my reading, does not satisfy "lands in the Decision Replay

and because Dave may have meant something closer to it than to A.

### 2.5 The control criterion 9 asks for

> a control proving a refusal cannot be silently absent from replay

The sentinel-default pattern gives a *positive claim* but not a forcing function: a caller
holding a refusal and passing the sentinel produces a well-formed, false record. The tree
already has the right precedent for closing exactly that hole —
`src/ccf/agents/errors.py::FalseGrantClaimError`, raised when a caller passes the positive
`NO_GRANTS_SET_HASH` claim while the agent's bound skill-set is non-empty, because "the agent
itself knows zero grants cannot be true, so recording the claim would corrupt replay dimension
4 at write time". **The equivalent here is the strongest control available:** refuse at write
time when the caller passes the no-refusal sentinel alongside evidence that a refusal
occurred. Plus a sabotage leg — delete the threading line, watch the test go RED — in the
`every wave found the class in its own work` discipline.

### 2.6 Recommendation for the `D-IMPL-214` entry

Enumerate **`src/ccf/replay/record.py`** and nothing else, on Reading B, and take the choice
between A / B / C to Dave before Wave 1. Two reasons: Reading A is the fence moving in
substance even if a `D-IMPL` entry technically licenses it; and the phase cannot honestly
decide for itself which reading a locked criterion has, since the criterion is not the
phase's to interpret.

**A second module may also be forced, by a route that is not replay at all — see §4.2.** If
the planner picks a design that needs `src/ccf/products/refusal.py`, criterion 12's `PLUS`
clause does not cover it (that clause says *replay-path* modules), and that is a separate
ruling, not a wider `D-IMPL`.

## 3 · THE `D-59` SEAM SHAPE

### 3.1 What is closed today, and what is not

`src/ccf/deployment/operators.py::build_operator_registry` dispatches on artifact **type**
through an `isinstance` chain over the four canonical parameter-artifact classes and raises
`ValueError` on anything else. The registry underneath is open:
`src/ccf/operators/registry.py::OperatorRegistry.register(operator, *, version=None)` takes no
category argument and reads `operator.key`, `operator.category` and `type(operator.parameters)`
off the operator.

Two honest nuances the CONTEXT does not state, both of which the planner needs:

1. **A deployment that owns its spine can already register post-build.** The builder's own
   docstring says: "Nothing is sealed and nothing is frozen — the registry is already
   append-only with no `unregister`." `examples/cp-00-institutional-holders/produce.py`
   assigns `operators = build_operator_registry(...)` and hands it to `ProjectionEngine`
   several statements later; a `registry.register(...)` between the two would work today.
   cp-00 did not do that because its operator runs at the **source boundary, before L1
   ingest**, not inside the projection plan — which is also why its recipe witness is
   `payload_key_present` rather than `operator_in_lineage`.
2. **A deployment that uses the SDK's own resolver has no route at all.**
   `src/ccf/products/resolver.py::GovernedResolver.__call__` builds the registry inline and
   consumes it in the same expression chain; `build_governed_resolver` takes
   `operator_parameter_keys: tuple[str, ...]` and no operator channel. **This is the genuinely
   closed door.** Closing `D-59` at the builder alone leaves it closed —
   see §3.5.

### 3.2 The constraint that is already mechanised

Criterion 2 asks for a control proving a caller cannot order an operator into a position it
does not belong in. **Two already exist and the new seam inherits both for free:**

- `src/ccf/operators/registry.py::OperatorRegistry.register` raises `ValueError` when
  `operator.category not in CATEGORY_ORDER`, and records `entry.category` from the operator.
- `tests/deployment/test_operator_builder.py::test_the_builder_passes_no_category_to_register`
  is an **AST check over the whole of `src/ccf/deployment/operators.py`**: it walks every
  `ast.Call` whose `func.attr == "register"` and asserts none carries a `category=` keyword.
  It is written explicitly against the "future edit declares each operator's own category"
  failure. A new `registry.register(operator)` call satisfies it without an edit, and it will
  keep firing over the new one. **Criterion 2's control is largely already shipped**; what is
  owed is a *new* test that a deployment operator reporting a non-canonical category is
  refused.

`DuplicateOperatorKey` (criterion 3) is likewise free: the seam calls the same `register`, and
`tests/deployment/test_operator_builder.py::test_two_entries_producing_one_operator_key_are_refused`
is the shape to mirror with a deployment operator colliding with an SDK operator key.

### 3.3 Three options

#### Option A — an additional keyword taking already-constructed operators  ★ RECOMMENDED

```python
def build_operator_registry(
    *,
    parameters: Mapping[str, OperatorParametersArtifact],
    view: GraphView,
    pins: ResolvedPins,
    policy_bundle_key: str,
    similarity_index_version: str | None = None,
    deployment_operators: Sequence[Operator] = (),      # NEW — defaulted
) -> OperatorRegistry:
```

Registration body: `for operator in sorted(deployment_operators, key=lambda o: o.key): registry.register(operator)`.

| Property | Verdict |
| --- | --- |
| Existing signature callable unchanged (criterion 7) | **Yes** — defaulted keyword; all existing call sites compile |
| Caller-declared category re-introduced (`INV-CH7-26`) | **No** — `register(operator)` takes no category; the AST test keeps it that way |
| `DuplicateOperatorKey` stays fatal | **Yes** — same `register`, uncaught |
| New operator key / entity class literal in the module (`CINV-01`) | **No** — the caller supplies instances |
| New imports into `ccf.deployment` | `Sequence` and `ccf.operators.base.Operator`. The module already imports `ccf.operators.categories`, `.params`, `.registry`; the `cinv02-deployment-gates` ban is on `ccf.products.gates` only |
| Determinism | Sort by `operator.key` so registration order is a function of the operators, matching the module's existing "sorted so registration order is a function of the manifest keys" discipline |

**Why I recommend it.** It is the smallest thing that closes the finding, it introduces no new
concept (the SDK already hands `SimilaritySelect` an injected index the same way), it makes
the deployment's operator visible to the *same* registry the plan reads, and it leaves the
`isinstance` chain — which is about *artifact* dispatch — untouched, so criterion 7's "every
existing call site compiling and passing unmodified" is trivially provable.

**Its honest weakness:** the deployment operator's parameters do not travel as a Control Plane
artifact through this channel. The operator instance carries them, and it is the caller's job
to have built them from an artifact. `D-IMPL-38` says operator parameters are declared,
versioned Control Plane artifacts, and Option B is the shape that honours that. I still
recommend A, because B costs more surface than a fenced two-item phase should spend, and A
does not *prevent* B later — a deployment can construct its operator from a parsed artifact
before handing it in.

#### Option B — a mapping from artifact type to constructor

```python
    operator_factories: Mapping[
        type[OperatorParametersArtifact], Callable[[Any], Operator]
    ] = {},
```

Dispatch extends the `else:` branch: `if type(parameter) in operator_factories: registry.register(operator_factories[type(parameter)](parameter))`.

- Additive: yes, defaulted.
- Category: still read off the operator — safe.
- **Pro:** the deployment's parameters stay a declared, versioned Control Plane artifact with
  its own semver lane, exactly like the four canonical ones. This is the `D-IMPL-38`-correct
  design.
- **Con:** the value type must be `Callable[[Any], Operator]` or a `TypeVar`-parameterised
  protocol — mypy's contravariance on callable arguments will not accept
  `Callable[[OperatorParametersArtifact], Operator]` against a concrete subclass constructor.
  **This is one of the two places an `Any` escape is tempting** (criterion 11 — §6).
- **Con:** dispatch must be on the **exact** type, not `isinstance`, for the reason
  `src/ccf/products/refusal.py::envelope_for` gives in its own docstring: an `isinstance` chain
  "would translate an unknown subclass as its nearest known ancestor" — a well-formed answer
  to the wrong question.

#### Option C — a registration hook

```python
    register_deployment_operators: Callable[[OperatorRegistry], None] | None = None,
```

- Additive: yes.
- Category: safe (the hook can only call `register`, which takes none).
- **Reject.** It hands the caller the registry mid-construction to do anything with, makes the
  builder's return value's contents unpredictable from its arguments, and buys nothing over
  post-build registration, which already works (§3.1 nuance 1). A seam whose value over the
  status quo is zero is not a seam.

### 3.4 What cp-00 does today — the local workaround the seam replaces

`examples/cp-00-institutional-holders/deployment.py::source_read` constructs a bare
`OperatorRegistry()`, registers
`examples/cp-00-institutional-holders/deployment.py::DominantSecurityResolution` into it via
`registry.register(cast(Any, DominantSecurityResolution(parameters=...)))`, resolves it back
out with `registry.resolve(OPERATOR_DOMINANT_SECURITY)`, and applies it to a candidate view
built at the source boundary. Its own docstring states the finding verbatim: "there is no path
by which a deployment's own operator reaches the registry the projection plan resolves
against. The registry itself is open; the composition path in front of it is not."

**Criteria 10 and 16 forbid rewriting this.** Criterion 16 is explicit — "`cp-00` is NOT
rewritten to register a deployment operator" — and it should not be, because cp-00's operator
runs *before ingest*, at a layer the projection plan does not reach. Rewriting it would be
changing the example's architecture to fit a seam, which is exactly backwards. The `D-59`
pressure test belongs in a new `tests/` fixture.

### 3.5 A named limitation the planner must not paper over

Closing `D-59` at `build_operator_registry` leaves `GovernedResolver` /
`build_governed_resolver` unable to pass a deployment operator through. Criterion 1 does not
require it — "the SAME registry the operator plan reads" is satisfiable by a test that calls
the builder and hands the result to `ProjectionEngine` directly, which is what cp-00's spine
and every archive example do. But a reader will reasonably expect the SDK's own resolver to
have the channel too. **Record this as a known, deliberate limit rather than widening
criterion 12 to reach `src/ccf/products/resolver.py`.**

## 4 · THE `D-60` REFUSAL SHAPE

### 4.1 The import cycle decides this, and it was measured

`src/ccf/agents/assembler.py`'s own docstring already warns about a cycle that is "real rather
than hypothetical": `ccf.products.request` imports `ccf.skills.catalog`, which imports
`ccf.agents.definitions`, which initializes the `ccf.agents` package — and
`src/ccf/agents/__init__.py` imports `AssemblyOutcome` from `assembler.py`. I measured what
each candidate import actually does, by copying `src/` to a scratch tree, adding one import,
and importing **every one of the 115 `ccf` modules first, one at a time**, counting only
failures that do *not* also fail on the unmodified tree.

| Probe | Edit to `src/ccf/agents/assembler.py` | Modules broken (of 115) |
| --- | --- | --- |
| Baseline | none | **0** |
| PROBE2 | `from ccf.products.request import ProductRequestViolation` (module level) | **0** |
| PROBE | `from ccf.products.refusal import RefusalEnvelope` (module level) | **13** |
| PROBE4 | new `AssemblyRefusal(CCFContract)` here **+** `REFUSAL_KINDS` entry in `refusal.py` | **55** |
| PROBE5 | new `AssemblyRefusal(CCFContract)` in `src/ccf/products/request.py`, imported here, wired to `REFUSAL_KINDS` | **0** |

The 0/13/55 spread is the control for itself: the same sweep, the same instrument, three
different answers. PROBE's failure is explicit —
`ImportError: cannot import name 'RefusalEnvelope' from partially initialized module
'ccf.products.refusal' (most likely due to a circular import)` — and it is **order-dependent**:
importing `ccf.agents.assembler` first succeeds, importing `ccf.products.refusal` first fails.
That is precisely the non-determinism `D-IMPL-37` rejects and the assembler's docstring names.

**Why PROBE2 is safe when the docstring warns otherwise:** `src/ccf/products/request.py`
already defers its own cycle-closing import to the bottom of the module
(`from ccf.skills.catalog import SkillArgumentSchema  # noqa: E402`, the `D-IMPL-56` pattern),
so `ProductRequestViolation` is fully defined before the agents chain runs. The docstring's
caution was written about `ProductRequest` in *annotations* and remains correct as written;
the value import of `ProductRequestViolation` is a different, and measurably safe, fact.

### 4.2 The exhaustiveness gate — a third `src/` module by a non-replay route

`src/ccf/products/refusal.py::REFUSAL_KINDS` is **closed by set equality**.
`tests/products/test_refusal_envelope.py::discover_refusal_types` performs an `ast` walk over
every `*.py` under `src/`, collects every `ClassDef` whose name ends in `Refusal` or
`Violation`, resolves its family transitively (`gate` / `contract` / `exception` /
`unresolved`), and
`test_the_refusal_vocabulary_is_closed_by_set_equality` asserts four equalities against
`REFUSAL_KINDS`, `NON_PRODUCT_REFUSALS` and `NON_VALUE_VIOLATIONS`.

Consequences the planner must price in:

- Any new `CCFContract` named `…Refusal` or `…Violation`, anywhere in `src/`, **fails the
  build** unless it is added to `REFUSAL_KINDS` or to `NON_PRODUCT_REFUSALS`. Both live in
  `src/ccf/products/refusal.py` — a **third** `src/` module, and **not a replay-path module**,
  so criterion 12's `PLUS` clause does not cover it.
- Adding a `REFUSAL_KINDS` member also requires a per-kind test function in
  `tests/products/test_refusal_envelope.py`:
  `test_every_kind_has_its_own_test_function` enforces one, by AST, and
  `test_no_aggregate_assertion_stands_in_for_a_per_kind_one` blocks a loop standing in for it.
- Naming a new refusal type outside the `…Refusal`/`…Violation` vocabulary to slip past the
  walk would be gaming a guard. Do not.

### 4.3 The three candidate shapes

#### Shape 1 — `AssemblyOutcome | ProductRequestViolation`  ★ RECOMMENDED

```python
def assemble(self, *, request: ProductRequest, perspective: Perspective,
             tenant_id: str) -> AssemblyOutcome | ProductRequestViolation: ...
```

| Against | Verdict |
| --- | --- |
| Criterion 5 — "reuses the existing refusal posture rather than minting a second vocabulary **beside** `ProductRequestViolation`" | Strongest possible satisfaction: it *is* `ProductRequestViolation` |
| Criterion 12 — `src/` confined to two modules | **Yes.** No new type, no `refusal.py` edit, no `src/ccf/agents/__init__.py` export |
| Import cycle | **0 of 115** (PROBE2) |
| Public-surface manifest | **0 added / 0 removed / 0 reshaped** (§7) |
| The finding cp-00 actually recorded | Closed exactly: `produce.assemble_and_serve` already returns a `ProductRequestViolation` as data, and `HoldersAssembler` is forced to raise it |

**Its cost, stated plainly:** `DeterministicAssembler`'s two existing refusals — a tenant that
is not the agent's, a perspective that is not the declared axis-3 role — cannot honestly be
expressed as a `ProductRequestViolation`. That type's `reason` is a closed four-member
vocabulary (`undeclared-parameter`, `missing-required-parameter`, `type-mismatch`,
`class-mismatch`), all of which are about a *request's conformity to a declared contract*.
Re-using `class-mismatch` for a tenant mismatch would be "a confident verdict about the wrong
question", which is the failure `src/ccf/products/request.py::_refuse_address` exists to
prevent. So under Shape 1, `AssemblyRefused` **stays** for those two — and see §4.5.

#### Shape 2 — a new `AssemblyRefusal(CCFContract)` in `src/ccf/products/request.py`

Structurally clean (PROBE5: 0 of 115), semantically the most precise, and it lets
`DeterministicAssembler`'s tenant/perspective refusals become data. Costs **three** `src/`
modules (`assembler.py`, `request.py`, `refusal.py`), a new `REFUSAL_KINDS` member, a new
per-kind test in `tests/products/test_refusal_envelope.py`, an `__all__` addition, and a
`docs/surface-changes/` fragment. It also arguably *is* "a second vocabulary beside
`ProductRequestViolation`", which criterion 5 names as the thing not to mint.

#### Shape 3 — `AssemblyOutcome | RefusalEnvelope`

Attractive on paper: one canonical envelope, already carries `request: RequestIdentity` and
`pre_assembly_lineage`, no new type. **Reject on two independent grounds.**
(a) The import breaks **13 of 115** modules (PROBE), order-dependently.
(b) `RefusalEnvelope.kind` is only honestly minted by `envelope_for`, which is total over
`REFUSAL_KINDS` and raises `TypeError` on anything else — so an assembler wanting to report a
tenant mismatch as an envelope needs a `REFUSAL_KINDS` member anyway, and constructing an
envelope directly with a hand-written `kind` string is the flattening that module exists to
forbid.

### 4.4 What happens to `AssemblyRefused`

**Keep it.** `src/ccf/agents/errors.py::AssemblyRefused` covers a channel-1 identity
disagreement — the agent's own tenant, the agent's own declared perspective — and the errors
module already says why that is exceptional rather than governed: "the disagreement describes
a *different agent* rather than a recoverable argument, and choosing which side was meant is
the deployment author's call". That is the same line
`src/ccf/agents/errors.py::NotYetBound` draws ("a deployment-shape fact, like a missing Control
Plane key, not an expected governance outcome a caller inspects"). Removing it would delete a
distinction the tree makes deliberately, and would put a wiring defect and a bad question on
the same channel.

Under Shape 2 the ruling could go the other way. It is a real choice and it belongs in the
`D-IMPL` entry, not in a plan.

### 4.5 What `DeterministicAssembler` must do — criterion 6

Criterion 6 requires `DeterministicAssembler` to conform to the widened Protocol **and** to
have "its refusal path exercised by a test watched RED". Conformance is free (§6.1 —
covariance). The refusal path is not, and this is the sharpest tension in the phase:

- Under **Shape 1** with `AssemblyRefused` kept, `DeterministicAssembler` has **no data-refusal
  path at all**. Its two existing refusals still raise; the tests at
  `tests/agents/test_assembler.py::test_the_assembler_refuses_a_tenant_that_is_not_its_own` and
  `::test_the_assembler_refuses_a_perspective_it_was_not_declared_under` are unchanged, so
  nothing goes RED and criterion 6 is unmet on its plain reading.
- The clean fix that stays inside `assembler.py`: give `DeterministicAssembler` an optional
  `request_contract: ProductRequestContract | None = None` field and, when present, call
  `src/ccf/products/request.py::refuse_request` and **return** the violation as data. That is
  SDK mechanism (the SDK's own door function), it makes the reference assembler actually
  demonstrate the seam it now offers, it needs no module beyond `assembler.py`, and the import
  is PROBE2-safe. It also enlarges `DeterministicAssembler`'s constructor, which moves the
  public-surface manifest (§7) — a fragment, not a criterion-12 problem.
- Under **Shape 2**, criterion 6 is met directly by converting the tenant refusal to data.

**This is a ruling, not a plan decision.** Shape 1 + `refuse_request` on the reference
assembler is what I recommend; Shape 2 is what a strict reading of criterion 6 alone would
choose; and criterion 12 pulls the other way. Take all three to Dave together.

### 6.3 The answer

**Widening the return type does essentially nothing to strict-mode checking**, because there
are **zero** parameters, annotations or call sites typed against `ContextAssemblerProtocol` in

returning only `AssemblyOutcome` if the phase leaves its refusals raising.

**Corollary the planner should not miss:** `examples/cp-00-institutional-holders/assembler.py`
and `tests/agents/test_assembler.py::_RegimeBoundedAssembler` need **no signature edit at all**
to stay conforming. Their `-> AssemblyOutcome` annotations remain valid. Any plan that says
"every implementation must widen its annotation" is asserting something mypy does not require.

### 6.4 Where an `Any` escape would be tempting

Three places, named so a reviewer knows where to look:

1. **`D-59` Option B's factory-mapping value type.** `Callable[[OperatorParametersArtifact],
   Operator]` will not accept a concrete-subclass constructor under contravariance, and
   `Callable[[Any], Operator]` is the path of least resistance. **Option A avoids this
   entirely** — one more reason to prefer it.
2. **`D-59` Option A's `Sequence[Operator]`, at the caller.** cp-00 already writes

   The honest control is a `tests/` fixture whose operator annotates

3. **A Protocol-typed helper added in `src/`.** If any wave adds a
   `def consume(a: ContextAssemblerProtocol) -> ...` to `src/`, it becomes the first real
   union-narrowing site and `warn_unreachable` will also fire on a branch mypy proves dead.

**Call sites most likely to need a narrowing guard:** none in `src/` or `runtime/` today. In
the unchecked trees, `tests/examples/test_cp_00_output.py:545` is the one site whose receiver
is *statically* the Protocol (`assert isinstance(seam, ContextAssemblerProtocol)` narrows), so
it is the site to write as though mypy were watching.
