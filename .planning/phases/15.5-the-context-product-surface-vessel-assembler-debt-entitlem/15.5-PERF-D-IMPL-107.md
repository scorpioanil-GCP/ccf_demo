## 2. Method

1. **Located the asymmetry before touching anything.** The four individual
   operator benchmarks and `test_composed_ab` were all in band; only the
   four-category plan was out. That is a statement about *plan shape*, not about
   any operator: under `CATEGORY_ORDER` the four-operator plan segments into
   `[policy] → [similarity] → [temporal, traversal]`, so it is the **only**
   micro benchmark that (a) issues a second pushed query and (b) issues a query
   carrying a `traverse` family. `test_composed_ab` (policy + similarity) stops
   at one pushed segment, which is exactly why it stayed green.
2. **Dated the architecture against the baseline.** `perf/baselines/local.json`
   was recorded at commit `8aefb2a` (2026-08-03). `git merge-base --is-ancestor
   14c044a 8aefb2a` returns false: the segmented engine loop (`15.2-07`) and the
   native SQLite `GraphQuery` pushdown (`15.2-09`) **post-date the baseline**.
   `src/ccf/operators/planner.py` and `src/ccf/contracts/canonical.py` are
   byte-unchanged since it. So the regression is not in an operator; it is in
   what Phase 15.2 put between the plan and the substrate.
3. **Profiled a real execution** rather than the benchmark harness: booted the
   1k perf fabric through `perf.conftest.build_fabric`, wrapped
   `SqliteGraphReader._query` to count and time every statement, and ran
   `ProjectionEngine.execute` under `cProfile`.
4. **Captured the exact SQL and parameters** the failing execution issued and
   timed the statements standalone against the same database file, so a
   candidate rewrite could be compared **row-for-row** against the shipped one
   without the engine in the way.
5. **Re-measured after each change** at three levels: standalone SQL, direct
   `engine.execute`, and the benchmark itself.

## 3. Cause A — a quadratic walk in the pushed traverse query

### Evidence

Per `engine.execute` at the base commit, 7353 SQLite statements totalling
0.8478 s of a 1.2851 s execution. The distribution is the finding:

```
execute total 1.2851s
sqlite _query calls 7353  time 0.8478s
       2 calls   0.7980s rows=3349  WITH RECURSIVE survivors AS MATERIALIZED (...
    7349 calls   0.0317s rows=7349  SELECT entry_json FROM lineage WHERE ...
       2 calls   0.0181s rows=4000  WITH survivors AS MATERIALIZED (...
queries issued: 2
  allowed: None traverse: False valid: None policy: True
  allowed: 996  traverse: True  valid: True  policy: False
```

**Two statements out of 7353 accounted for 62% of the entire execution.** They
are the entity answer and the relationship answer of the second pushed segment —
the one carrying the traverse family — and each carries the whole `WITH` chain,
so the walk is computed twice.

`EXPLAIN QUERY PLAN` names the defect outright:

```
(9230, 3106, 0, 'SCAN c')     <- inside RECURSIVE STEP
(9232, 3106, 0, 'SCAN w')
```

The recursive term joined the crossable set on a **disjunction**:

```sql
FROM walk w
JOIN edges c
  ON (c.subject_uri = w.uri OR c.object_uri = w.uri)
```

SQLite cannot serve an `OR` across two columns from an index, so for every row
the walk has already reached it re-scans the whole materialized crossable set:
`|walk| × |edges|` row comparisons — 986 × 2363 on the 1k rung, paid twice. The
work is quadratic in the segment's own answer, which is why it is invisible on
every benchmark whose plan produces no traverse-bearing second segment.

### The fix (`4984a77`, `src/ccf/graph/backends/sqlite.py`)

A `hops` CTE states the same relation once per direction so the recursive term
can join by **equality**, which SQLite indexes:

```sql
hops(subject_uri, object_uri) AS MATERIALIZED (
    SELECT c.subject_uri, c.object_uri FROM edges c
  UNION
    SELECT c.object_uri, c.subject_uri FROM edges c
)
...
FROM walk w
JOIN hops c
  ON c.subject_uri = w.uri
```

### Why it is safe

- **It is `GQ-10` written so an index can be built on it.** `GQ-10`
  (`docs/GRAPH_QUERY_SEMANTICS.md:201`) already makes an edge crossable in
  either direction; the disjunction and the two-direction union express the same
  crossability relation.
- **`hops` derives from `edges` and adds no row.** Every predicate that governed
  the expansion surface — the as-of cut, the segment's validity and policy
  predicates, the permitted relationship types, and both-endpoints-surviving
  closure — still governs it, because they are applied in `edges`, upstream.
- **`UNION`, never `UNION ALL`.** A self-loop renders twice and collapses to the
  one row the disjunction matched. (`walk` itself is a `UNION` recursive CTE, so
  it would dedup regardless; the `UNION` here makes the set smaller as well.)
- **The reached-node expression is untouched.** It still reads as the general
  undirected step; under this join its `CASE` simply always takes the
  `object_uri` branch.
- **The `allowed_entities` closure inside the recursive term is unchanged** —
  the `D-IMPL-87` resurrection defect stays closed.
- **Rows verified identical, not assumed.** The shipped statement and the
  rewrite were executed against the same database with the same parameters and
  their result lists compared with `==`:

| statement | before | after | speed-up | rows | identical |
|---|---|---|---|---|---|
| entity answer | 0.4035 s | 0.0225 s | 17.9× | 986 | **yes** |
| relationship answer | 0.3974 s | 0.0250 s | 15.9× | 2363 | **yes** |

- `tests/conformance/test_substrate_differential.py` and
  `tests/graph/test_sql_pushdown.py` hold the translated answer byte-identical
  to the fallback's (`GQ-31`). Both green.

`engine.execute`: **1.2851 s → 0.5420 s.**

## 4. Cause B — the residual, and what it actually is

With the walk fixed, `test_composed_chain` measured **0.4684515 s**, still
**+26.98%**. That residual is *not* a defect. Instrumented per execution:

```
execute 0.5420s/iter
  content_hash (in IntermediateCache)  12.0 calls/iter  0.2992s/iter
  materialize_view                      2.0 calls/iter  0.1471s/iter
```

Before Phase 15.2 the engine took **one** `reader.as_of()` read and applied all
four operators in process. The segmented loop takes **two** substrate reads and
therefore materializes two graph views and canonically hashes two more of them.
That is `D-IMPL-87` working as ruled, and the arithmetic matches the residual
almost exactly (one extra `materialize_view` ≈ 0.074 s on top of the extra view
hashing). **The baseline was never re-measured after that decision landed.**

D-IMPL-107 forbids absorbing this by moving the baseline, and reversing
`D-IMPL-87` is an architectural change no one asked for. So the **per-view cost
of canonical rendering** came down instead.

### The fix (`65bd68d`, `src/ccf/contracts/canonical.py`)

Four changes, none of which alters a canonical byte:

1. **Set elements were normalized twice** — once to render the sort key, once to
   be returned (`(_dumps(_normalize(e)), _normalize(e)) for e in value`). Every
   claim in the fabric carries its lineage as a `frozenset`, so this doubled the
   cost of hashing a view. Normalize once; sort the normalized value.
2. **A set of fewer than two elements has exactly one ordering**, so no sort key
   is rendered for it. A claim observed once carries one lineage entry, which
   makes this the common case by a wide margin.
3. **`type(value).model_fields` is memoized per class.** It is a class-level
   property reached through a Pydantic deprecation shim, and hashing one 1k-rung
   view resolves it ~88,000 times. The names are fixed once a class is built.
4. **An exact-class shortcut for `str`/`int`/`bool`/`None`** ahead of the
   `isinstance` chain. Subclasses miss it deliberately and are still decided by
   the chain, so the rule about what is canonically encodable is unchanged —
   this is dispatch, not policy.

Effect on `engine.execute`, measured after each step:

| | s/iter |
|---|---|
| base commit | 1.2851 |
| + walk fix | 0.5420 |
| + (1) normalize set elements once | 0.4826 |
| + (3)(4) field-name memo, exact-scalar dispatch | 0.4475 |
| + (2) no sort key for a <2-element set | **0.4128** |

## 5. Byte-identity of `canonical_bytes` — proved, not assumed

`canonical_bytes` is what the Context Product **content address** and the A2A
**signature** are computed over (`runtime/ccf_runtime/mcp/egress.py:270`). A
one-byte change would move every content address in the tree, break
`ReplayEnvironment.rehydrate_product` (`src/ccf/replay/engine.py:449-455`, which
raises `ReplayDivergence` on address mismatch), and invalidate every recorded
replay record and peering signature. That is not authorized by D-IMPL-107, which
rules in a performance regression and nothing else.

**Method.** `src/ccf/contracts/canonical.py` as it stood at the base commit
`db4fdce` was extracted (`git show db4fdce:src/ccf/contracts/canonical.py`) and
loaded as a second module *alongside* the working-tree module in one process.
For a 56-case corpus, `old.canonical_bytes(obj)` and `new.canonical_bytes(obj)`
were compared as **actual bytes** with `==` — not "parses to the same object".
Cases that raise were compared on the raised exception type and message instead,
so a change in refusal behaviour would also have shown.

**Corpus.** Deliberately loaded with the shapes canonical serializers usually
differ on:

- `None`, `True`/`False`, positive/negative/big `int`, and `str`/`int`
  **subclasses** (which must miss the new exact-class shortcut and be decided by
  the `isinstance` chain);
- non-ASCII text (`Ünïcödé — 財務 — Ωμέγα`, non-breaking space), emoji, and a
  string carrying quotes, backslashes, newlines and tabs — i.e. the
  `ensure_ascii=False` surface;
- `Decimal` plain, zero, negative, `1E+5` and `1E-7` (positional-notation
  rendering);
- `datetime` UTC, with microseconds, with a **non-UTC offset**, and at years 3
  and 999 (the `strftime('%Y')` width surface), plus `date`;
- **empty** list, tuple, dict, set and frozenset;
- sets of size 1, 2 and 3, sets of ints, sets mixing `"1"`/`1`/`True`/`None`,
  sets of tuples, sets of models, a singleton set of models, lists of sets and
  dicts of sets — i.e. every path through the changed `Set` branch, both sides
  of the new `len < 2` shortcut;
- two dicts with the same items in **different insertion order**;
- nested models, tuples of models, and models holding empty collections;
- and **real fabric artifacts** from the 1k rung: the `as_of` `GraphView`
  (3,158,031 B), a full `ExecutionResult` (2,707,140 B), the composed view
  (2,625,320 B), an entity record, a relationship record, the provenance chain,
  the projection output, and all four operator parameter sets.

**Result: 56 cases, 0 mismatches.** Byte-for-byte identical, including the
3.1 MB view and the 2.7 MB execution result.

**Recorded addresses in the tree are unchanged.** No tracked artifact was
modified by this work (`git status` clean apart from the two source commits) and
nothing was "updated" to match. Independently confirmed by execution rather than
by inspection:

- `make ci-core` — **2613 passed, 85 skipped**, including `tests/replay`,
  `tests/crossproc` (peering signatures) and `tests/examples`;
- `make examples` — all ten green, including `examples/06-decision-replay`
  (which rehydrates a recorded product and would raise `ReplayDivergence` on any
  address move) and `examples/external/00-hello-context` assertion 8,
  *"fabric-side byte-equal reproduction (D-16)"*;
- `examples/08-e2e-demo` reproduced its pinned replay record
  (`bc596817514152fd…`) and skill-set digest (`6592ac147e297f35…`).

## 7. Two notes for whoever reads this next

**(a) The remaining 0.41 s is dominated by a cache that can never hit.**
`ProjectionEngine.execute` builds a fresh `IntermediateCache` and routes every
operator through it; `build_operator_plan` dedups keys and the segments
partition them, so **each operator key is invoked exactly once per `execute()`**
and the memo is never consulted a second time. Yet `IntermediateCache.run`
computes `content_hash(view)` — a full canonical rendering of the graph view —
on every invocation purely to build that key: ~0.20 s of the remaining 0.41 s,
about half the benchmark. It could be made lazy (defer the input-identity hash
until a prefix is seen twice) with identical hit behaviour and identical return
values. **I did not take it**: `D-IMPL-36` rules the cache's existence and shape,
the key's composition is documented as "everything `Operator.apply` can
observe", and restructuring a replay-critical memo to win time this phase does
not need is a decision for Dave, not for a perf fix. Recorded as the largest
remaining lever.

**(b) D-IMPL-107's second consequence is still open.** In `15.5-09`,
`make perf-micro` is the **first** term of an `&&` chain
(`15.5-09-PLAN.md:197`), so while it exited 1 it short-circuited
`tests/test_surface_drift.py`, `tests/perf_smoke` and `tests/perf_gate`
entirely. The gate is green now, so the short-circuit no longer bites — but the
ordering defect is still there and will bite again the next time that battery
goes red. `15.5-07` places it last and skips nothing. Correcting the asymmetry
is the planning owner's, not this work's.
