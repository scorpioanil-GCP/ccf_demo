# Phase 15.5 Plan 07: The Nine §6.3 Elements Borne, and the Payload Declared

All nine Context Product Contract elements are now borne by named fields on
shipped types, the enumeration `15.5-02` left with three deferrals has none,
a product class can declare its payload schema and D-IMPL-31's
constituent-validity floors, `contract.py`'s module docstring names only
fields that exist — and **no recorded content address moved**, because
D-IMPL-106 placed the one element that could have moved them where it could
not.

## What Was Built

### The three absent elements, on the class (task 2)

| Element | Type | Field | Default |
| --- | --- | --- | --- |
| Freshness SLA | `FreshnessSLA(max_age_seconds_by_signal: Mapping[str, int])` | `RegisteredProductClass.freshness_sla` | `UNMEASURED_FRESHNESS_SLA` |
| Discovery | `ProductDiscovery(domain, intents, capabilities)` | `.discovery` | `NOT_DISCOVERABLE` |
| Addressability | `ProductAddress(address_template)` | `.addressability` | `NOT_ADDRESSABLE` |
| (D-IMPL-31 floors) | `ConstituentValidityFloors(min_validity_seconds_by_signal)` | `.constituent_validity_floors` | `NO_VALIDITY_FLOORS` |
| (payload pin) | `str`, `str` | `.payload_schema_key` / `.payload_schema_version` | `NO_PAYLOAD_SCHEMA` |

All five mirror onto `ProductClassDeclaration` — **minus
`payload_schema_version`**, preserving the authored-key/derived-version
asymmetry `artifacts.py:502-510` states: an artifact that declared it would be
authoring a hash of something it does not contain.

**`freshness_sla` is per-signal, not scalar.** D-IMPL-106 ruled the placement
and said in terms that *no scalar is ruled in by silence*; §6.3 at
`docs/CCF_Whitepaper_1-2.md:1453` says the SLA "varies by signal and by
decision" and that "a product that mixed the two without surfacing the
asymmetry would produce an unreliable agent input" — which a single number
does.

**`addressability` is the path half only.** D-IMPL-98 ruled that the request
surface is a typed request contract per class and that addressability and that
contract are one commitment. The query half — subject and instant as typed
arguments — is plan `15.5-08`'s, and nothing here models a query parameter, so
its shape is not foreclosed.

### The declared payload schema (task 1)

`src/ccf/products/payload.py`:

- `ProductPayloadSchema` — an **alias** of `SkillArgumentSchema`, asserted
  (`ProductPayloadSchema is SkillArgumentSchema`), never a copy. D-IMPL-103
  branch (i) measured the sibling at five duplicated symbols and declined it.
- `refuse_payload(*, payload, declared) -> PayloadSchemaViolation | None` —
  one pure comparison, fixed refusal order (undeclared → missing-required →
  type-mismatch) over sorted names so the verdict cannot move with a payload's
  insertion order.
- `PayloadSchemaViolation` — carries both sides (`declared_type`,
  `presented_type`, `declared_keys`, `presented_keys`) in the
  `AttestationRefusal` voice, with dotted paths (`ownership.smuggled`,
  `beneficial_owners[].party_uri`).

Two readings made deliberately and documented where they are made: `bool` is
not an `integer` (it subclasses `int` in Python and does not in JSON Schema),
and `float` is not a `number` **in this tree** — `ccf.contracts.canonical`
refuses `float` outright, so admitting one would declare conformant a payload
that cannot reach a content address.

### The D-IMPL-103 widening (task 1)

`SkillArgumentProperty` gains `properties`, `items` and `required`, all
defaulted to "not declared". The nested types are `SkillArgumentMember` (no
nesting fields at all) and `SkillArgumentElement` (members, no `items`), so
**depth 3 and a list of lists are not expressible** rather than refused.

The widening is asserted as a widening on the *rendered* surface every harness
adapter consumes, not only on the model: a depth-1 declaration renders exactly
the two keys it rendered before.

## The Three Rulings, and Where Each Bound the Work

**D-IMPL-106 — `freshness_sla` class-level.** Honoured. Asserted directly:
`"freshness_sla" in RegisteredProductClass.model_fields` **and**
`"freshness_sla" not in ContextProductContract.model_fields`. This is why no
content address moved.

**D-IMPL-102 — no fourth gate.** Honoured, and made structural rather than
promised: `PayloadSchemaViolation` deliberately does not derive from

this plan — verified: it appears in no commit's diff.

bounds. `SkillArgumentSchema` was extended, not replaced; three call sites of
`to_input_schema()` and all nine `argument_schema` files, including all three
harness adapters, are unchanged because the render is unchanged for existing
declarations.

**1. [Ruling — D-IMPL-103] `ProductPayloadSchema` is an alias, not a new class**
- **Found during:** Task 1
- **Issue:** The plan's `must_haves` list `src/ccf/products/payload.py` as

- **Fix:** `ProductPayloadSchema = SkillArgumentSchema`, an explicit alias with

- **Files:** `src/ccf/products/payload.py`, `tests/products/test_payload_schema.py`
- **Commit:** cad963a

**2. [Ruling — D-IMPL-102] No fourth gate; `PayloadSchemaViolation` is not a `GateRefusal`**
- **Found during:** Task 1
- **Issue:** The plan's task-1 action describes the refusal in the
  `AttestationRefusal` voice, which could be read as deriving from
  `GateRefusal`.
- **Fix:** It derives from `CCFContract` directly, and the reason is recorded
  on the class: a violation that inherited the gate refusal type could be
  returned from the gate path by a later caller who assumed the type meant it
  belonged there. `run_gates` stays byte-untouched.
- **Files:** `src/ccf/products/payload.py`, `src/ccf/products/__init__.py`
- **Commit:** cad963a

**3. [Ruling — D-IMPL-106/98] Element placement and scope**
- **Found during:** Task 2
- **Issue:** The plan was written before the rulings and left the placement of
  `freshness_sla` and the declaration-only status of discovery/addressability
  open.
- **Fix:** Class-level throughout (D-IMPL-106 option (b)); discovery and
  addressability land as real fields, not declaration-only (D-IMPL-98). The
  request contract is left entirely to `15.5-08`.
- **Files:** `src/ccf/products/contract.py`, `src/ccf/controlplane/artifacts.py`
- **Commit:** 8a462b2

**4. [Rule 1 — bug] The recursive schema shape renamed `SkillCatalogEntry` in the published OpenAPI document**
- **Found during:** Task 3 verification (the full sweep)
- **Issue:** The first implementation of the widening made
  `SkillArgumentProperty` self-referential with a depth validator. Pydantic's
  definition-remapping does not collapse `-Input` / `-Output` variants through
  that recursion, so FastAPI emitted `SkillCatalogEntry-Input` and
  `SkillCatalogEntry-Output` instead of `SkillCatalogEntry` —
  `tests/http_api/test_openapi.py::test_every_contract_bearing_route_lands_a_schema`
  went red, and the committed `openapi.json` external integrators read would
  have had two renamed models.
- **Fix:** Restructured to `SkillArgumentMember` + `SkillArgumentElement`, so
  the one-level ceiling is **structural** — the nested types have no nesting
  fields to fill in — rather than a validator. No recursion, no split,
  `SkillCatalogEntry` keeps its name. This is also a strictly stronger reading
  of the ruling: a ceiling expressed as a missing field is not a rule a later
  author can relax. The alternative — regenerating `openapi.json` with the
  split and relaxing the guard to accept a suffixed name — was rejected as
  weakening a deliberate gate to accommodate an accidental consequence.
- **Files:** `src/ccf/skills/catalog.py`, `src/ccf/products/payload.py`,
  `tests/skills/test_argument_schema_nesting.py`
- **Commit:** a77ab1c

## The 15.5-02 Residual, Ruled

Plan `15.5-02` recorded an open question in its own module docstring:
`contract.py`'s field-to-element table routed Policy Binding through
`lineage.policy_bundle_versions`, a nested field a top-level `model_fields`
union cannot reach, while the enumeration keyed it to
`accepted_policy_binding_modes`; it declined to say whether the nested route
still existed.

**Ruled here: both routes exist and they carry different things.**
`lineage.policy_bundle_versions` carries the bundle versions actually *bound
into* the state a given product was assembled from — a per-product fact, and
the one that reaches the replay record. `accepted_policy_binding_modes`
carries what the **class** accepts, which is what governance means and what
`run_gates` compares against. The element is keyed to the second because the
union reaches it and because keying two elements to `lineage` would collapse
them, which the injectivity guard rejects. `contract.py`'s rewritten table now
says the same thing, so the two no longer disagree. Recorded in both module
docstrings.
