<domain>
## Phase Boundary

**What commissioned it.** Dave read `examples/s1-01-hello-context-product` and
asked the question the SDK has to survive:

> *"Your example ran a chill down my spine because today I would put an MCP server
> in front of the fluree database and run a query and return the results. What is
> the benefit of using CCF? This is what I fear you have created in the SDK. The
> true power of CCF is not predicting a set of static permutations. It's about
> providing 6 dimensions to the context I am consuming as the calling agent."*

**In scope.** The Context Product delivery surface: the vessel and its declared
payload schema; the three missing contract elements; Context Debt delivered to the
consumer; the assembler as a Protocol implemented by a declared agent; entitlement
at the delivery boundary; runtime request parameters replacing artifact literals;
and aggregate-product composition.

**Out of scope.** Mode 2 packaging (stays above `serve()` per `D-IMPL-94`, lands in
Phase 17), Mode 3 coordination, `src/ccf/unstructured/`, tier-3 external sources.
The documentation rewrite itself — Phase 16 is parked at 6/21 and resumes against
the surface this phase corrects.

**Why it precedes Phase 16.** Documenting the surface first would document the
defect. Every example after `s1-01` copies its shape.
</domain>

<decisions>
## Implementation Decisions

### The vessel — LOCKED (`D-IMPL-97`)

> *"The true ContextProduct is nothing more than a vessel that has been assembled
> to represent a unique capability for the calling agent to consume. Kind of like
> MCP — a standard ContextProduct doesn't really need to subclass, it just needs to
> have certain operations and payloads which we have already determined via the
> whitepaper."*

- **One standardised vessel, no class hierarchy.** No per-product subclass, in
  `src/` or in user code. Class identity stays data — `schema_name` resolved
  through the Control Plane registry.
- **The payload is disciplined by a declared JSON Schema** registered with the
  product class, in the shape MCP tools declare `inputSchema`. Reuse the machinery
  already proven on eight artifact classes; do not invent a second one.
- **This is a wording correction to whitepaper §7.6, not a reversal** (Dave,
  explicitly: *"Vessel wording is not reversal"*). The intent — typed payload,
  cross-cutting invariants once on the base — is preserved.
- **Bound the MCP analogy.** MCP carries no governance semantics. The vessel is
  MCP-shaped in typing discipline *with a governance envelope MCP has no
  equivalent for*. Do not let a plan drift into "it's just MCP".

### The assembler — LOCKED (`D-IMPL-97`)

> *"The assembler, which I agree should be a Protocol, is what makes the
> ContextProduct a KYC_ContextProduct."* … *"Agent becomes the implementation
> protocol."*

- **Protocol for the producer, vessel for the produced.**
- **The Protocol's implementation is a declared agent** from the `context_assembly`
  archetype — a Control Plane artifact from the Agent Factory, never SDK code and
  never a subclass.
- The assembler knows where its data lives and how to get it; talks to the six
  backends directly so the 15.2/15.3/15.4 adapter work is not lost; creates or uses
  tools; **may enlist other agents** to produce content, or stay deterministic; may
  keep its own KG in whichever of the six stores is simplest.
- The calling agent invokes the **product**, not an MCP server in front of a
  database. The orchestration mess is handled inside.
- **Products may be front-ended by MCP servers**, like databases are.
- **Products may aggregate other products.**

### Context Debt — LOCKED

> *"It combines multiple signals into a comprehensive product that includes
> ContextDebt by design. It can work for any number of parameters that the product
> allows."*

- **Debt is constitutive, not an annotation.** The product *is* the composite; debt
  is computed across it by design.
- **Debt must reach the consuming agent.** Today `DebtAssessment` is computed and
  discarded — on neither the product nor the replay record.
- Dave's worked shape: *"the last time ACME key investor data was updated — or if
  an event had transpired with one of the key shareholders that should be
  considered by the consuming agent."* Two signals: **recency** and **salience**.

### Systems of record — LOCKED (`D-IMPL-95`)

L1 reads the enterprise stores and **never** writes them. CCF's Context Graph is
CCF-owned, on the same substrate, written only through L2. No plan may target a
source store as a graph target.

### Scope discipline — LOCKED (`D-IMPL-96`)

*"No fabric changed"* is revoked; it was an anti-leakage rule used as a no-change
rule. **The fabric may and must change here.** What still binds is the four
CI-enforced anti-leakage lints. `D-13`'s carve-out, `D-14`'s two-limb bound and
plan 16-19's `gate_16.py` allowlist are withdrawn with the old wording.

### Entitlement — LOCKED that a fabric change is required

Dave: *"I need to make a fabric change to accommodate this."* Framing: entitlement
is not a new axis — it is **`P` applied at delivery**, where today it applies only
during assembly.

### Anti-recurrence — LOCKED by criterion 2

Three of the eight §6.3 elements went missing while every gate stayed green,
because the suite tests what the fabric *does*, never what the delivered product
*carries*. The contract must become an **executable assertion**, not prose.

### Claude's Discretion

- Whether `freshness_sla`, `discovery` and `addressability` land on
  `RegisteredProductClass` (where `contract.py` already claims they live) or

- Test strategy, beyond criterion 2's requirement that the eight elements be
  enumerated executably.
</decisions>

<open_questions>
## Must be surfaced for Dave's ruling during planning

Enumerated with evidence in `docs/CONTEXT_PRODUCT_REVISION.md` §9–§10. **Do not
guess these — surface them.**

1. **The request contract — this one gates the others.** Is the request surface a
   typed contract per product class? Dave's shape: *"maybe it's just the company
   name and 'top investors above 25%' or something like that."* It is what makes a
   product **callable** rather than configurable, and it collapses the
   fixed-subject and fixed-instant defects into one design instead of two patches.
2. **Debt's shape on the wire** — scalar, per-factor, per-subject, or per-claim;
   and whether recency and salience are one field or two.
3. **Where debt lands** — product, replay record, or both, and what replay
   determinism demands of each.
4. **What "a material event transpired" means mechanically**, without encoding
   domain values in the core. The hardest line in the design.
5. **Payload validation** — a fourth validation gate, or a bind at class
   registration.
6. **Debt composition weighting** for aggregate products.
7. **The unruled coupling.** If entitlement bounds what an assembler may consult on
   a caller's behalf, then completeness — and therefore debt — differs per
   principal, so **debt cannot be computed once per product**. This changes the
   shape of the debt work substantially and is not yet ruled.
</open_questions>

<specifics>
## Specific Ideas

- **The reference use case, in Dave's words:** an `InvestmentBankingAssistantAgent`
  whose job is to answer, about **any company at any time**: *"Who ultimately owns
  Acme Corporation, and does any natural person's stake cross the KYC reporting
  threshold?"*
- **The three literals to eliminate** from `examples/s1-01-hello-context-product`:
  `subject_entity_ref`, `temporal_boundary`, `now`.
- **Defend the as-of mechanism while fixing its use.** The engine reads no clock by
  design — the caller passes `now` at serve time and the original boundary at
  replay time, same code path. The caller supplying the instant is correct; the
  instant being a YAML literal is the defect. Do not "fix" this by putting a clock
  in the engine.
- **Delete `DeploymentBinding`.** A Protocol the example invented, calls *"the
  adoption checklist"*, and CCF does not ship. All eight examples call
  `load_and_boot` identically; seven differ only in a filename.
- **Perspective must be derived at the door, not in the engine.** `execute()` keeps
  taking a `Perspective`; the door decides which one a caller may assert. This
  keeps replay determinism untouched — replay must feed the *recorded* perspective
  and must not re-authenticate a principal who may no longer exist.
- **Measured baselines** (2026-08-10, not regression-gated): boot 74.3 ms once per
  process; projection execute 8.68 ms per question; the replay append that gates
  delivery 0.29 ms; full example 347 ms. A second question in a live service costs
  ~10 ms.
</specifics>
