# Phase 15.5 Plan 15: The Seam, Widened Once

The perspective a product door authorizes is now the perspective the assembler
is conditioned under — **provable at the value, not assumed from the
parameter.** `DI-15.5-03` is closed, plan `15.5-08`'s undeliverable must-have is
delivered, and the seam was edited once rather than twice.

## What Was Actually Wrong, Since Most Of It Was Right

All three doors already resolved an entitled `Perspective` and refused a caller
not entitled to the class or to the role. What they did not do was *forward*
it. In `runtime/ccf_runtime/mcp/egress.py` the defect was literal:

```python
entitled_perspective(...)          # a bare expression statement
servable = resolver(tenant=..., product_class=..., version=...)
```

The decision was computed, the refusal honoured, and the answer thrown away.
So each door guaranteed the **refusal** leg while leaving entirely unproven
that the product it *did* serve was shaped under the perspective it had
authorized. Those are two different security properties, and the served bytes
were identical either way — which is why no shipped test caught it.

The same three-string seam is why `15.5-08` could declare *"the request surface
is validated where it crosses the door"* and name no door file. One cause, two
gaps, one widening.

## The Four Tasks

### 1 — Both Protocols widened, and the widening refuses rather than defaults

```python
def __call__(
    self, *, tenant: str, product_class: str, version: str,
    perspective: Perspective, request: ProductRequest | None,
) -> ServableProduct: ...
```

**`perspective` is required and non-nullable.** This is the substance of the
plan, not a style choice: a resolver silently constructing its own perspective
is indistinguishable from one honouring the door's, and a parameter defaulting
to `None` recreates exactly that ambiguity one layer down.

**`request` is required with no default but typed `ProductRequest | None`**, and
the asymmetry is argued rather than assumed. A surface can honestly have *no
way to ask*: `ccf-product://{tenant}/{product_class}/{version}` is three path
segments with no query among them. Manufacturing a request there would mean the
SDK choosing a subject, an intent and a freshness figure — CINV-01 values it
must never hold — and reading a clock for `asked_at`, which is the
literal-instead-of-argument defect `D-IMPL-98` exists to remove, reintroduced
one layer up. `None` is the positive assertion, in the voice
`requested_role: str | None` already carries on `PerspectiveResolverProtocol`
two modules away.

### 2 — All three doors pass what they resolved

Eleven resolver definitions across `runtime/`, `examples/` and `tests/` carry
the widened signature. The measured blast radius held: 2 Protocols, 3
invocation sites, 1 dependency field, and the supplying files.

**The HTTP door got the request surface** because it is the one door that can
have one. Whitepaper §6.3 writes the address as
`/context-products/credit-risk/counterparty/{counterparty-id}?intent=…&freshness=…`
— path for *what*, query for *what is being asked of it* — so `subject`,
`intent`, `freshness` and `asked_at` are now query parameters, supplied together
or refused (400, `product-request-incomplete`). A defaulted axis is a question
nobody asked, answered anyway.

**`schema_name` and `schema_version` come from the path the door already
resolved, never from the caller.** A request addressed to another class is
therefore *unrepresentable* on this surface rather than merely refused — the
strongest available form of "validated where it crosses the door", and the
reason the route needs no address cross-check.

**The reference deployments honour the perspective rather than accepting it.**
`examples/04-cross-process/producer_child.py` and
`examples/external/00-hello-context/serve.py` both refuse to serve when the
perspective the door authorized is not the one their product was assembled
under. A resolver that ignored the argument would put the gap back one layer
down, where nothing on the wire would show it.

**`refuse_bound_payload` is wired at the bind.** Plan `15.5-09` shipped it
unwired with its own precondition written down: *"once a request has resolved
to a `RegisteredProductClass` and the payload for that bind exists."* That
place is the deployment's resolver — the assemble-and-gate path — so
`producer_child.py` now carries `registered` and `control_plane` on its
assembled slice and makes the one call after the payload exists and before it
leaves.

### 3 — The pin `15.5-08` could not reach

Three mechanical edits, exactly as `15.5-08-SUMMARY.md` specified:
`register_product_class` calls `refuse_request_contract_pin`,
`RegisteredProductClass` carries `request_contract_key` /
`request_contract_version`, and both default to the sentinel so all 29+ existing
registrations keep saying what they always said.

One thing was not mechanical. `NO_REQUEST_CONTRACT` lived in
`ccf.products.request`, which imports `ProductClassRegistrationError` from
`ccf.products.contract` — so a `RegisteredProductClass` field defaulting to it
would close an import cycle at load time. It moved to `contract.py` beside the
field it defaults, which is exactly where `NO_PAYLOAD_SCHEMA` already lives and
how `ccf.products.bind` already reads it, and is re-exported from `request.py`
unchanged. A test asserts the two names are the **same object**, because two
equal strings is the state that assertion exists to rule out.

**No content address moves, asserted rather than claimed.**
`RegisteredProductClass` is a `CCFContract`, so two new fields change *its*
canonical bytes — harmless only if it is inside no content address. A test walks
`ContextProductContract`'s field graph for a `RegisteredProductClass` and pins
its ten-field set literally, so a later change hanging the registered class off
the product fails here rather than silently invalidating every recorded address.
`make schemas` produces no diff.

### 4 — Asserted structurally, at the value

Three assertions in ascending strength, in
`tests/invariants/test_mcp_role_separation.py`. **Only the third would have
failed against the shipped defect**, which is the whole reason it exists:

| | Level | What it catches |
| --- | --- | --- |
| 1 | shape | a later `perspective=None` default — the single edit that would restore DI-15.5-03 |
| 2 | AST | the shipped defect's exact form: `entitled_perspective(...)` as a bare expression statement |
| 3 | behaviour | a door forwarding a **freshly-constructed** perspective, which passes 1 and 2 and is identical in every byte a consumer sees |

Assertion 3 stands the authenticated egress server up in process, reads one
product as a verified and entitled caller, and compares what the resolver
received against what that deployment's perspective seam returned for that
grant. Its companion asserts the other half — that a refused caller reaches the
seam **zero** times, because forwarding is only a security property if refusal
comes first.

**The role-separation invariant is updated but not weakened.**
`PRODUCT_RESOLVER_PROTOCOLS` keeps both members and every existing assertion is
untouched: the two seams are still two modules importing neither each other nor
a sibling, `_calls_a_product_resolver` still discovers exactly the three doors,
and the principal-free-package and replay-resolves-nobody scans are unchanged.

## The Behaviour Change That Wants Dave's Ruling

**`GET /product/...` no longer serves in the ungoverned posture.** With no
entitlement seams bound, or with them bound and no verified grant present, the
route refuses with 503 and `product-door-ungoverned`.

This follows directly from the plan's own must-have — *"a door that cannot pass
a perspective refuses rather than silently constructing one"* — and there was no
third option: the seam requires a `Perspective`, the ungoverned door has none,
and manufacturing one is the exact defect being closed.

**It supersedes `T-07-24`'s preservation of that posture,** which three shipped
tests asserted. The trade, stated plainly:

- **Given up:** the acknowledged insecure posture (D-IMPL-73) loses one route.
  `create_app` still accepts no seams and still builds, and every other noun
  answers exactly as before. `ccf product get` — which builds its app with
  `acknowledge_insecure_default=True` — now reports the refusal; `--local` never
  served a product anyway, since its resolver refuses every address.
- **Gained:** no product this fabric serves over HTTP was ever shaped under a
  perspective nobody named.
- **Restoring service is two constructor arguments**, documented in the
  surface-change fragment with the code.

Rather than editing the three tests to pass, each was rewritten to assert the
new posture with the supersession stated in its own docstring, and the
canonical-bytes and 404 claims moved to the *governed* app where they still
assert something. `docs/surface-changes/15.5-15-resolver-seam.md` opens with
this change, before any surface entry.

## Deviations from Plan

**1. [Rule 2 — correctness] The ungoverned HTTP door refuses rather than serving**
- **Found during:** Task 2, at the third door.
- **Issue:** `_enforce_entitlement` was inert with seams unbound or no grant, so
  the route reached the resolver with no perspective at all. The widened seam
  makes that unexpressible, and the plan forbids a default.
- **Fix:** a typed 503 with `ERROR_PRODUCT_DOOR_UNGOVERNED`, distinguishing the
  two configurations in prose and naming the seam to bind. Three tests rewritten
  to assert the new posture; two moved to the governed app.
- **Files:** `runtime/ccf_runtime/http_api/routes/product.py`,
  `runtime/ccf_runtime/http_api/errors.py`, `tests/http_api/test_routes.py`,
  `tests/http_api/test_product_entitlement.py`, `tests/cli/test_cli.py`
- **Commits:** `c244400`, `685cbf0`

**2. [Scope — the plan's own truth, delivered] The HTTP door gained the four §6.3 query axes**
- **Found during:** Task 1, designing the `request` half.
- **Issue:** widening the seam to *carry* a request satisfies nothing if no door
  can ever *supply* one. The MCP URIs structurally cannot.
- **Fix:** four optional query parameters on the HTTP route, all-or-nothing,
  assembled at the door with the address taken from the path.
- **Files:** `runtime/ccf_runtime/http_api/routes/product.py`, `openapi.json`
- **Commit:** `c244400`

**3. [Rule 3 — blocking] `NO_REQUEST_CONTRACT` had to move modules**
- **Found during:** Task 3.
- **Issue:** `request.py` imports `contract.py`, so a `RegisteredProductClass`
  field defaulting to a `request.py` constant is an import cycle.
- **Fix:** defined in `contract.py` beside the field, re-exported from
  `request.py`. Identity asserted by test.
- **Files:** `src/ccf/products/contract.py`, `src/ccf/products/request.py`
- **Commit:** `e4dbc10`

**4. [Rule 1 — reporting defect] The two Protocol entries read `behavior`, not `reshaped`**
- **Found during:** Task 4.
- **Issue:** `tools/dump_surface.py` records a `Protocol`'s `__init__`
  (`"(*args, **kwargs)"`) and never its `__call__`, so no call-Protocol
  signature change can produce a manifest diff line, and `reshaped` fails
  `tests/test_surface_completeness.py`.
- **Fix:** classified `behavior` — the exempt class that exists for exactly
  this — with the reason stated in the fragment, and the underlying gate
  blindness logged as **DI-15.5-06** rather than swallowed. Plan `15.5-11` hit
  the same wall for `ReplayEnvironment`; two plans reaching for the exempt class
  to describe a signature change is the signal.
- **Files:** `docs/surface-changes/15.5-15-resolver-seam.md`,
  `.planning/.../deferred-items.md`
- **Commit:** `60605ca`

No authentication gate arose. No package was installed.

## Known Stubs

None. Two things read as absences and are neither:

- **`request=None` at the two MCP doors** is the positive assertion *this
  surface carries no way to ask*, asserted by test alongside the value check.
  Filling it in would require the SDK to hold deployment values and read a
  clock.
- **`parameters={}` on the request the HTTP door assembles** is the positive
  assertion *this question needs nothing beyond its four axes*. The
  class-declared remainder is a typed surface whose D-IMPL-103 nesting a flat
  string-valued query cannot carry without the door guessing at coercions; the
  limitation is documented at the assembly site rather than left to be
  discovered.
