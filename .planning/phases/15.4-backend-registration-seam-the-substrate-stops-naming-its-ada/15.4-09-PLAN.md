<objective>
Add `ccf backends`, the command that replaces what the schema enum used to do.

Dropping the six-name `Literal` removed an `enum` from
`docs/schemas/ccf.deployment-manifest.json`, and with it an adopter's editor
autocompletion for the `backend` field. That cost is accepted rather than worked
around: injecting registered names back into the generated schema is the
"generated list" D-12 already rejected, wearing a different hat.

What ships instead answers a better question. The enum could only ever say what
someone hard-coded. A command that reads the registry says what is *installed
here*, third-party adapters included — which is the question an adopter writing
a manifest actually has, and the one that becomes interesting the moment
adapters can arrive from outside this repository.

It is a noun-verb command over an HTTP route, not a local generation path,
because that is the CLI's whole posture: every action travels the same routes
any client uses, and the first exception to that is the one that makes the
second easy. `ccf schema export` made exactly this argument and paid exactly
this price — one route module.

Purpose: close D-15's second half.
Output: one route, one CLI noun, a regenerated OpenAPI document, and tests on
both surfaces.
</objective>

    **What the response deliberately does not carry, and why it is in the
    docstring.** The registry knows each adapter's distribution name and
    version. The route returns neither. An adopter writing a manifest needs to
    know which names the deployment will accept; a caller who learns which
    packages are installed at which versions has learned the deployment's
    dependency inventory, which is a reconnaissance surface and not something
    this endpoint owes anyone. Names are the answer to the question; the rest is
    disclosure. If a later phase needs versions, that is a decision with its own
    entry, not a field someone adds because the registry happened to have it.

    **What happens when `declared_names()` refuses.** Plan 15.4-02's
    fail-closed ruling makes `declared_names()` raise for any installed
    distribution's bad metadata — a duplicate, reserved or malformed name,
    whoever declared it. This route calls it directly, so the one command an
    operator reaches for to answer "which adapters does this deployment have"
    raises in exactly the case they need it, and an uncaught exception arrives
    as an opaque 500 that throws away the one thing that refusal was written to
    carry: the name of the offending distribution, which is what tells a
    packaging conflict apart from a missing adapter. Catch
    `DuplicateBackendName`, `ReservedBackendName` and the malformed-name
    `ValueError` at the route boundary and return `503` in the API's existing
    typed-error shape, with a stable code (`backend_registry_conflict`) and the
    registry's own message. `503` because the deployment is misconfigured
    rather than the request malformed; not `200` with an empty list, because an
    empty list is a different fact and fail-closed exists precisely so nothing
    answers past the ambiguity.

    That refusal body carries one distribution name, which narrows the
    disclosure rule above, and the narrowing is deliberate: without the name
    the refusal is unactionable. It is reachable only when the deployment's own
    installed adapters already conflict, and it is still not a version and
    still not an inventory. Test it — monkeypatch `declared_names` to raise
    `DuplicateBackendName` naming two distributions, call the route, and assert
    `503`, the error code, and both distribution names in the body.

    **The route enumerates no vocabulary.** The names come from the registry,
    which derives them from the backends package and from installed entry
    points — the same CINV-01 argument `schema.py` makes about
    `SDK_ARTIFACT_CLASSES`, and the reason a hand-written list here would
    reintroduce exactly what plan 15.4-06 removed.

    Note in the docstring that the answer is *deployment-local*: it describes
    the process serving the request. Under `ccf --local` that is the CLI's own
    process; over HTTP it is the server's. Both are honest answers to "what is
    installed here", and an adopter should know which one they asked.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP caller → deployment inventory | A read route that describes what the server has installed |
| CLI → HTTP API | The CLI holds no privileged path; whatever it can do, a client can do |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15.4-11 | Information disclosure | `GET /backends` response | mitigate | On the success path, names only: distribution names, versions and module paths are deliberately omitted, with the reason in the route docstring, and a test asserts the body has exactly one key. Widening the success path later is a decision with its own entry, not a convenience. The refusal path is the one stated narrowing — a `503` carrying the registry's own message, which names the offending distribution — because without the name a fail-closed refusal is unactionable, and it is reachable only when the deployment's installed adapters already conflict. |
| T-15.4-30 | Elevation of privilege | a new route with a bespoke auth posture | mitigate | The router is included under the same authentication and tenant-authorization dependencies as every other read route, asserted by a test that an unauthenticated request is refused exactly as for `GET /schema`. |
| T-15.4-31 | Tampering | a privileged local path in the CLI | mitigate | The command returns a `RequestSpec` and nothing else. D-IMPL-79's argument holds: the first exception to "every command travels the routes any client uses" is the one that makes the second easy. |
| T-15.4-02 | Tampering | adapter code executed to answer a listing | mitigate | The route calls `declared_names()`, which reads names and imports nothing. Listing adapters must never load them. |
| T-15.4-42 | Repudiation | a public name added in one commit and claimed in the next | mitigate | Each task writes its half of the fragment in the same commit that adds the name, and each runs `tests/test_surface_drift.py`.
