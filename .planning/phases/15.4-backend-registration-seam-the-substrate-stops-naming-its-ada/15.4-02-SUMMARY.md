refusals, and one connection-validation wrapper that cannot echo the value it

## What Was Built

### Task 1 — the record, the Protocol, the pin, and the two discovery sources (`840b2fb`)

`src/ccf/graph/registry.py`, 748 lines, ten public names at this commit.

**Discovery is two sources with one record type.** Built-in adapters are found
by reading module names out of the adapter package's directory — a disk read,
so no packaging metadata is involved and neither of the two measured failure
modes can reach it: a stale editable install cannot hide an adapter, and the
repo-root `*.egg-info` that shadows the installed `dist-info` whenever `.` is
on `sys.path` cannot either. Third-party adapters come through the
`ccf.graph_backends` entry-point group, which is what lets an adapter ship as a
separate installable distribution with no line changing in this repository.

Neither source imports anything. `.name`, `.value`, `.dist.name` and
`.dist.version` are metadata reads; `.load()` is called in `resolve` alone.

**Three refusals, computed in discovery so no caller can reach a name the
fabric would not honour:**

| Refusal | Fires when | Message carries |
| --- | --- | --- |
| `ReservedBackendName` | an entry point declares a name the SDK's own adapter package holds | the declaring distribution, and `pip uninstall <it>` |
| `DuplicateBackendName` | two *different* distributions declare one name | both distributions and both versions |
| `ValueError` | a declared name fails `^[a-z][a-z0-9_]*$` | the offending value |

**The fail-closed ruling.** `resolve` calls `declared_names` first, so any of
the three refuses *every* boot — including a boot of a built-in that has
nothing to do with the conflict. That is a real choice: D-05 requires only that
unselected code is not imported. It is ruled fail-closed in the module
docstring, with the narrower degrading alternative recorded as considered and
rejected, and the operability requirement that follows is a message
requirement: each refusal says *packaging conflict* and says the requested
adapter was never reached, so an operator can tell a conflicting install from a
missing one.

**The window between waves, handled rather than crashed into.** Plan 15.4-03
creates the six write modules; plan 15.4-04 adds their `REGISTRATION` records.
In between, built-in discovery finds six adapters `resolve` cannot load, and
the honest behaviour is a `ValueError` naming the module and the adapter and
saying which half is missing — never an `AttributeError` escaping a `getattr`.

**`AdapterPin` and `ResolvedSecret`.** The pin holds `name`, `version` and
`secret_refs` — reference *names* only, no field that can hold a credential.
`ResolvedSecret` carries `field`, `ref_name` and `value: SecretStr` as one
object, because the pin needs names while a store constructor needs values and
two parallel mappings can drift. Verified at execution: neither `repr()` nor
`model_dump_json()` reproduces a recognisable token, and `canonical_bytes`
raises `CanonicalizationError` on it — so a `ResolvedSecret` cannot be
content-hashed into an artifact even by accident.

**The confinement.** `importlib.import_module` appears exactly once, in one
private function, and nowhere else under `src/` or `runtime/`. The module
docstring states the residual in `src/ccf/boot.py`'s voice rather than claiming
it away: an AST import lint cannot see a dynamically-constructed module name,
so the claim strength is *no unforced path exists*, never *no path exists*.

### Task 2 — discovery imports nothing, and both collisions refuse (`12a6ef8`)

`tests/graph/test_backend_registry.py`, 17 tests at this commit.

The V6 test writes a throwaway adapter whose module-level body records its own
import — both to `sys.modules` and to a marker file — declares it through a
fake entry point, and asserts the module is **absent** after `declared_names()`
and **present** after `resolve()`. That is the difference between a property and
a description of the code that is believed to have it.

The V10 test carries the companion assertion that makes it about the hazard
rather than about the code: the duplicate is refused in *discovery*, so neither
candidate module reaches `sys.modules` and neither marker file exists. A test
that asserted only the exception would pass against a registry that refused
after importing one of them, which is the failure that matters — by then a
package nobody chose has already run its module-level code.

Fakes are real `importlib.metadata.EntryPoint` objects with a distribution
attached through the stdlib's own `_for` path, so `.dist.name` and
`.dist.version` read exactly as they do in production.

Two AST tests scan `src/` **and** `runtime/` — the same pair
`RULE_TREE_SCOPE["backend-imports"]` covers, because T-15.4-03 is dispositioned
*accept* on the strength of the confinement and a scan narrower than the rule it
compensates for would leave the accepted residual larger than the register says.
The concrete gap a graph-only scan leaves open is a dynamic
`import_module("ccf.graph.backends.<name>")` in `src/ccf/deployment/manifest.py`,
which holds the adapter name and is exactly where someone would reach for one.

Both detectors were sanity-checked against synthetic ASTs for both spellings
(`importlib.import_module(x)` and `from importlib import import_module`) and
for the non-call cases they must not count.

### Task 3 — one config-validation wrapper (`348f9ae`)

`validate_connection(registration, connection) -> CCFContract` and
`InvalidBackendConfig`, plus seven more tests (24 total).

Every line of the refusal is built from `error["loc"]` and `error["msg"]`.
`error["input"]` and `str(exc)` are never read, and the two forbidden keys are
named in a comment at the construction site so nobody simplifies it back. The
message names the **adapter** (Pydantic names only the model class, and the
refusal this replaces named the adapter), names the **field** as a dotted path,
sorts its lines so two runs over one bad mapping produce one message, and
reports every problem in one exception.

The leak test supplies a recognisable token under a misspelled key and requires
it absent from `str(exc)`, from `repr(exc)`, and from the exception's chain.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] Built-in discovery reads the adapter directory rather than importing the adapter package**

- **Found during:** Task 1
- **Issue:** the plan's action text says `pkgutil.iter_modules(<the backends
  package>.__path__)`, and reaching `__path__` requires
  `import ccf.graph.backends`. `cinv02-backend-import` (written in 15.4-01,
  registered in 15.4-07) denies the adapter package to **every** module outside
  it and has no carve-out for the registry — deliberately, since its docstring
  names `ccf.graph.registry` as *the seam a core module uses instead*. The
  static import would have been a finding at 15.4-07, and 15.4-06's
  pre-registration dry run would have caught it one wave earlier.
- **Fix:** the directory is derived from `Path(__file__).parent / "backends"`
  and passed to `pkgutil.iter_modules` as a path list. No import, so no finding
  — and the key link the plan asks for (`iter_modules`) is unchanged.
- **Why this is strictly better, not a workaround:** it is the same reasoning
  `tools/lints/substrate_names.py` already applies to the same directory ("a
  path rather than a dotted name because this is a disk read, not an import"),
  and it means the registry needs no exemption from the rule it exists to make
  satisfiable. The plan's own argument for the design — that built-in discovery
  should not depend on packaging metadata — is served by a filesystem read more
  directly than by an import.
- **Files:** `src/ccf/graph/registry.py`
- **Verification:** `backend_imports.check(registry.py, "ccf.graph.registry")`
  returns no findings; `make lint` exit 0.
- **Committed in:** `840b2fb`

**2. [Rule 2 — Missing critical] `tests/invariants/test_single_writer_boot.py` asserted a stale permitted-importer set**

- **Found during:** Task 1
- **Issue:** `test_only_l2_and_the_composition_root_name_the_writer_module`
  asserted `offenders == ["ccf/boot.py"]` — a hand-written second definition of
  `cinv02-graph-writer`'s permitted set. Plan 15.4-01 widened that set to admit
  `ccf.graph.registry` for the neutral base; the test did not know, so the first
  module to exercise the carve-out failed a test that CI was already passing.
- **Fix:** the permitted set is now read from the rule —
  `NEUTRAL_WRITER_OK_MODULES` and `is_write_module` imported from
  `tools.lints.harness_imports` — so the rule and its test cannot disagree.
  Containment is asserted as the property, with a separate non-vacuity
  assertion that the composition root is still in the offender list (a regex
  that matched nothing would otherwise pass silently).
- **Why it matters beyond this plan:** the fix is **forward-compatible with
  15.4-03**. When that plan lands six `backends/<name>_write.py` modules, each
  legitimately naming the base it subclasses, `is_write_module` already admits
  them — so 15.4-03 finds this test green and does not need to edit it. Had I
  patched the literal to `["ccf/boot.py", "ccf/graph/registry.py"]`, 15.4-03
  would have had to edit the same line, on a file neither plan declares in
  `files_modified`.
- **Files:** `tests/invariants/test_single_writer_boot.py`
- **Verification:** `pytest tests/invariants -q` → 78 passed, under both
  `PYTHONPATH=src:runtime` (what `make test` uses) and `PYTHONPATH=.:src:runtime`.
- **Committed in:** `840b2fb`

**4. [Rule 2 — Missing critical] The sanitized refusal is raised outside the handler, not with `raise ... from None`**

- **Found during:** Task 3 (caught by the leak test, which asserted more than
  the plan's acceptance criterion did)
- **Issue:** the plan's contract is that a supplied value can never travel with
  a connection refusal. `raise InvalidBackendConfig(message) from None` sets
  `__cause__ = None` and `__suppress_context__ = True`, so a *printed*
  traceback omits the chain — but `__context__` still points at the
  `ValidationError`, and its text carries the supplied value. Measured:
  `caught.value.__context__` rendered
  `input_value='...-not-log-me-9f3a'`. Anything that walks exception chains
  explicitly — a structured logger, an error reporter — would surface it.
- **Fix:** the message is built inside the handler and the exception is raised
  after the handler has exited, so no implicit context is attached at all. The
  placement carries a comment saying why `from None` is not enough, and the
  docstring carries the same as a bullet in the message contract.
- **Files:** `src/ccf/graph/registry.py`
- **Verification:** the leak test asserts the token is absent from `str`, from
  `repr`, and that both `__cause__` and `__context__` are `None`.
- **Committed in:** `348f9ae`

**5. [Rule 3 — Blocking] Two refusal messages tripped `cinv01a-prompt-shape`**

- **Found during:** Task 1
- **Issue:** the `ReservedBackendName` and `DuplicateBackendName` messages score
  two prompt-shape signals (three or more sentences, over 200 characters) and
  carried none of the developer-diagnostic markers that exempt a long
  refusal — so `make lint` reported two CINV-01a findings.
- **Fix:** each message now ends with the concrete remedy in backticks
  (`` `pip uninstall <distribution>` ``), which is both the repo's existing
  precedent for a long refusal (`ccf.deployment.manifest`'s path-containment
  message, `_DRIFT_MESSAGE`) and genuinely the thing an operator needs. Shortening
  the messages was the alternative and was rejected: the packaging-conflict
  legibility requirement is what makes the fail-closed ruling operable.
- **Files:** `src/ccf/graph/registry.py`
- **Verification:** `make lint` exit 0.
- **Committed in:** `840b2fb`

**6. [Design note, not a fix] The write-seam import is `TYPE_CHECKING`-guarded**

- **Found during:** Task 1
- **Rationale:** the 15.4-01 carve-out permits `ccf.graph.registry` to import
  `ccf.graph._writer`, and the lint sees the statement whether or not it is
  under `if TYPE_CHECKING`. But at this wave `ccf.graph._writer` imports every
  adapter read module and `psycopg`, so a runtime import would make
  `import ccf.graph.registry` pull in the whole adapter set — importing adapters
  at start-up by another door, which is exactly what the module docstring
  records D-06 as rejected for. The guard keeps the registry importable at zero
  cost and keeps that rejection honest. `make_writer` is still typed with
  `BootToken` and `BaseGraphWriter` from `ccf.graph._writer`, as the acceptance
  criterion requires, and `mypy --strict` is clean.
- **Files:** `src/ccf/graph/registry.py`
