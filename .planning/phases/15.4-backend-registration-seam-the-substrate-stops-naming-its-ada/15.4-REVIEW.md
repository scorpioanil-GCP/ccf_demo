# Phase 15.4: Code Review Report

**Reviewed:** 2026-08-09
**Depth:** standard
**Files Reviewed:** 32 (plus `tools/lints/harness_imports.py`, read as the rule this phase re-founded)
**Status:** issues_found

## Summary

The phase does most of what it claims. The credential path is the strongest part of the
work: `validate_connection` builds every line from `detail["loc"]` and `detail["msg"]`
and raises **outside** the `except` block, so `__context__` and `__cause__` are both
`None` (verified by executed test); `canonical_bytes` refuses `SecretStr` through the
unsupported-type fallthrough (verified — `SecretStr` is not a `str` subclass, so it
reaches the terminal `raise`); all six connection contracts derive from `CCFContract`
and inherit `extra="forbid"`, swept per-adapter by `tests/deployment/test_adapter_config.py`;
and no store's `graph_identity` reproduces a credential. The `AdapterPin` has no field a
value can reach, and the end-to-end absence test in `tests/replay/test_adapter_pin.py`
carries a real non-vacuity partner (`probe.SEEN == [PROBE_SECRET_VALUE]`).

The tests are, with the exceptions noted below, unusually non-vacuous. `test_backend_registry.py`
proves "discovery imports nothing" with a module that records its own import rather than
by asserting `.load()` is not called; `test_writer_seam.py` pairs its confinement scan with
an explicit non-vacuity count; `test_harness_trace.py`'s golden literal is never retouched.
`test_param_registry_parity.py` closes the "suite passes by not running" hole in both
directions. 61 tests across the six phase suites pass; both new lint rules run clean.

What the phase did **not** get right clusters in three places, and all three are provable
rather than stylistic.

**One, the composition root.** `boot()` guards `mint_boot_token` but leaves
`registration.make_writer` — now arbitrary third-party code — outside every guard. An
exception there leaks the store's connection and leaves the graph identity permanently in
`_LIVE_WRITERS`, so a corrected retry is refused as a second writer. This is exactly the
failure boot.py's own comment says must not happen, and it is reproduced below.

**Two, the static gate.** Both import rules read only what `imported_module_names` reports,
which discards the alias names of an `ImportFrom`. `from ccf.graph import _writer` and
`from ccf.graph.backends import sqlite_write` therefore produce **zero findings**, and both
spellings work at runtime — verified by executing them. A helper that fixes this
(`submodule_import_names`) already exists in `harness_imports.py` and is wired only to the
deployment-gates rule. Combined with `BackendRegistration.make_writer` being a public field
on a public record returned by a public `resolve`, layer 3 of the D-IMPL-41 stack is weaker
than five separate docstrings assert it is.

**Three, fail-closed discovery.** The duplicate-name refusal keys on the distribution
*name* only. Two declarations from the same distribution name at different versions
pointing at different modules — the ordinary failed-uninstall state — are silently
accepted, and `matches[0]` picks whichever the metadata iterator yields first. Two
declarations with no distribution metadata collapse to the same sentinel and are likewise
accepted. Both reproduced below. That is the "adapter set depends on discovery order"
hazard the module docstring says it exists to close.

The lint rules that carry the phase's central claim (`cinv04-substrate-name`) have no test
of any kind, fail *open* when their derived vocabulary is empty, and over-match generic
English words whose only crime is sharing a stem with an adapter module.

## Critical Issues

### CR-01: `boot()` leaks the store and permanently locks the graph when `make_writer` raises

**File:** `src/ccf/boot.py:268-277`

**Issue:** `mint_boot_token` adds `store.graph_identity` to `_LIVE_WRITERS` and only
`BaseGraphWriter.close()` ever removes it. `registration.make_writer(store, token)` sits
between the mint guard and the worker-construction guard, protected by neither:

```python
    try:
        token = mint_boot_token(graph_identity=store.graph_identity)
    except BaseException:
        store.close()
        raise

    writer = registration.make_writer(store, token)   # <-- unguarded

    def shutdown() -> None:
        writer.close()
        store.close()

    try:
        spec = registry.resolve(...)
```

If `make_writer` raises, the store is never closed and the graph identity stays in
`_LIVE_WRITERS` for the life of the process. Reproduced with a third-party adapter whose
`make_writer` raises:

```
boot raised: third-party adapter blew up building its writer
store.close() called? -> False
graph identity still marked live? -> True
RETRY PERMANENTLY REFUSED: a GraphWriter already exists for graph 'memory://b731...'
```

Consequences, in order of severity:

* **A corrected retry is refused as a second writer.** boot.py:295-296 states this
  explicitly as the thing that must not happen ("A half-booted fabric must not leave the
  graph marked as written-to; otherwise a corrected retry would be refused as a second
  writer") and guards the *later* region for exactly that reason. For `sqlite` the same
  `database_path` is unbootable for the rest of the process; for `postgres`/`mongo`/`neo4j`
  the same `(host, database, schema/partition)` likewise.
* **A connection pool leaks** — a psycopg connection, a pymongo client, a neo4j driver,
  or an httpx client — with no object returned that the caller could close.
* This is precisely the seam the phase widened. Before D-IMPL-93 the writer was constructed
  by in-core code the composition root fully controlled; `make_writer` is now a callable
  supplied by an arbitrary installed distribution. `fluree.py:735-745` already argues this
  exact discipline ("construct, guard, close on ANY failure, re-raise unchanged") and cites
  `ccf.boot.boot`'s shape around `mint_boot_token` as the precedent — the precedent just
  stops one line too early.

Also reachable without third-party code: every in-tree `_make_writer` raises `TypeError`
on an `isinstance` mismatch, and any subclass `__init__` that raises *after*
`super().__init__()` consumes the token produces the same stuck state.

**Fix:** Extend the guard to cover writer construction, and release the mint on failure.

```python
    try:
        token = mint_boot_token(graph_identity=store.graph_identity)
    except BaseException:
        store.close()
        raise

    try:
        writer = registration.make_writer(store, token)
    except BaseException:
        # The token may or may not have been consumed; either way this graph
        # has no live writer, so it must not stay marked as having one.
        release_boot_token(token)   # new helper in ccf.graph._writer
        store.close()
        raise
```

with, in `src/ccf/graph/_writer.py`:

```python
def release_boot_token(token: BootToken) -> None:
    """Release a graph a token was minted for but no writer ever took.

    Only reachable from the composition root (CINV-02). A mint that produced no
    writer must not leave the graph unbootable — see ccf.boot.boot.
    """
    _LIVE_WRITERS.discard(token.graph_identity)
```

Add a test that boots against an adapter whose `make_writer` raises and then asserts a
subsequent boot on the same graph identity succeeds, and that the store was closed.

### CR-02: Both import lints are blind to `from <package> import <submodule>`, defeating the single-writer static gate

**File:** `tools/lints/__init__.py:58-70`; `tools/lints/harness_imports.py:229-251`; `tools/lints/backend_imports.py:108-124`

**Issue:** `imported_module_names` returns `[node.module]` for an `ImportFrom` and discards
`node.names`. `matches_module("ccf.graph", ("ccf.graph._writer",))` is `False`, so
`from ccf.graph import _writer` matches nothing in either rule. Verified:

```
graph-writer findings: []
backend-import findings: [... only the 'ccf.graph.backends' line ...]
```

for the source `from ccf.graph import _writer\nfrom ccf.graph.backends import sqlite_write\n`
attributed to `ccf.products.evil`. Both spellings bind the submodule at runtime — also
verified:

```
reached neutral base: ccf.graph._writer
mint_boot_token available: True
token minted outside ccf.boot: forged://x
reached write module: ccf.graph.backends.sqlite_write <class '...SqliteGraphWriter'>
```

Two distinct holes follow:

1. **Any module under `src/` or `runtime/` can mint a boot token and name a concrete
   writer class with zero lint findings.** `harness_imports.py:47-54` records the first
   half as "a pre-existing blind spot", but the phase re-founded this rule around a
   *class* of guarded modules and simultaneously widened the writer-constructor surface
   (`BackendRegistration.make_writer` is a public field on a public frozen dataclass
   returned by public `resolve`, importable from anywhere). "Even with a writer
   implementation on disk, no other module can name it" (harness_imports.py:21-23) is not
   true as written.
2. **A reader module can import its sibling write module with zero findings** —
   `backend_imports` exempts everything under `ccf.graph.backends`, and the graph-writer
   rule sees only `ccf.graph.backends`. Verified: `check_source` returns `[]` from both
   rules for `from ccf.graph.backends import sqlite_write` attributed to
   `ccf.graph.backends.mongo`. `src/ccf/graph/backends/__init__.py:14-18` states this
   arrangement is structurally prevented — "if a reader imported its writer, every importer
   of the reader would transitively reach write code and the rule would flag the reader
   itself." It would not.

The same blind spot is mirrored (deliberately) in
`tests/invariants/test_single_writer_boot.py:145-148`, whose regex only matches
`from ccf.graph._writer import` / `import ccf.graph._writer`, so the test cannot catch it
either.

**Fix:** `harness_imports.submodule_import_names` already computes exactly the missing
names and is used only by `cinv02-deployment-gates`. Feed it to the other two rules.

```python
# tools/lints/harness_imports.py, inside check_source's walk
reached = set(imported_module_names(node)) | set(submodule_import_names(node))
for name in reached:
    ...
    if is_write_module(name):
        ...
```

```python
# tools/lints/backend_imports.py — import the helper (or lift it into tools/lints/__init__)
for name in set(imported_module_names(node)) | set(submodule_import_names(node)):
    if not matches_module(name, (BACKENDS_PACKAGE,)):
        continue
    ...
```

For hole 2, exempting `ccf.graph.backends` from `cinv02-backend-import` must not exempt it
from `cinv02-graph-writer`: a write module may name the neutral base and a write module may
name *its own* reader, but no module under the adapter package should name a *different*
adapter's write module. Once `submodule_import_names` is wired in, the existing
`WRITER_OK_MODULES` check already produces that result. Add negative unit tests for both
spellings (see WR-05) and widen the regex in
`tests/invariants/test_single_writer_boot.py:145` to match.

### CR-03: The duplicate-adapter refusal fails open on same-distribution-name and metadata-less declarations

**File:** `src/ccf/graph/registry.py:473-498`, `src/ccf/graph/registry.py:582-583`

**Issue:** The duplicate check compares `_distribution_of(previous) == _distribution_of(entry_point)`
— the distribution **name** alone — and `continue`s on a match, justified by the comment
"both declarations name the same code, so there is nothing for the fabric to choose
between." That premise is false in two reachable states, and in both `resolve` then does
the thing the module docstring says it exists to prevent: `matches[0]` silently takes the
first match.

Reproduced:

```
case1 declared_names: ['dup']                    # ccf-x-adapter 1.0.0 -> mod_a
                                                 # ccf-x-adapter 2.0.0 -> mod_b
case1 resolve -> ModuleNotFoundError No module named 'mod_a'   # mod_a won, silently
case2 declared_names: ['dup2']                   # two entry points, no dist metadata
                                                 # <- no refusal
```

* **Case 1** is the ordinary failed-uninstall / double-`dist-info` state: two metadata
  directories for one distribution name at different versions, pointing at different
  module targets. The fabric picks one by metadata iteration order, and the `AdapterPin`
  it writes into Decision Replay dimension 2 records that arbitrary winner's version as
  fact. `_version_of` is available at the comparison site and is simply not consulted.
* **Case 2**: `_distribution_of` returns the `UNKNOWN_DISTRIBUTION` sentinel whenever
  `entry_point.dist is None`, so two unrelated metadata-less declarations of one name
  compare equal and are treated as one distribution declaring one name twice. This is a
  fail-open on precisely the "bad metadata" class the module's fail-closed ruling is
  written about.

`registry.py:580-583` reasons that `matches` "holds exactly one element" because
"Duplicates are already refused above." It does not, in either case. It is also an
unchecked `[0]` on a second, independent metadata scan — if the entry-point set changes
between `_declared()` and the `.select()` call, that is an `IndexError` rather than a
refusal.

**Fix:** Compare identity, not just the distribution name, and never index blind.

```python
        previous = third_party.get(entry_point.name)
        if previous is None:
            third_party[entry_point.name] = entry_point
            continue
        same_declaration = (
            _distribution_of(previous) == _distribution_of(entry_point)
            and _version_of(previous) == _version_of(entry_point)
            and previous.value == entry_point.value
            and _distribution_of(entry_point) != UNKNOWN_DISTRIBUTION
        )
        if same_declaration:
            # One distribution declaring one name twice at one target: a
            # malformed table, not an ambiguity.
            continue
        ... raise DuplicateBackendName(...)
```

and in `resolve`, use the entry point discovery already returned rather than re-scanning:

```python
    else:
        entry_point = third_party[name]   # _declared() already resolved it
```

Add tests for both reproduced cases; they are two lines each against the existing
`_entry_point` helper in `tests/graph/test_backend_registry.py`.

### WR-02: Third-party entry-point load failures escape untyped, while the built-in path is carefully refused

**File:** `src/ccf/graph/registry.py:582-590`

**Issue:** `_load_builtin` uses `getattr(module, REGISTRATION_ATTRIBUTE, None)` so a
built-in without a record is refused with a message naming the module and the adapter, and
`tests/graph/test_backend_registry.py:391` explicitly asserts `not isinstance(caught.value,
AttributeError)`. The third-party branch calls `entry_point.load()` bare. Verified:

```
third-party missing attribute -> AttributeError : module 'ccf.graph.protocols' has no attribute 'MISSING_ATTR'
```

and a bad module target yields a raw `ModuleNotFoundError` (seen in the CR-03 repro).
Arbitrary module-level code in the named adapter can raise anything at all. None of these
appear in `resolve`'s or `boot`'s documented `Raises:`. The careful treatment is on the
half written by the SDK; the half written by a stranger gets none.

**Fix:** Wrap the load and refuse in the same shape the built-in path uses.

```python
        try:
            registration = entry_point.load()
        except Exception as failure:
            detail = f"{type(failure).__name__}: {failure}"
        else:
            detail = None
        if detail is not None:
            raise ValueError(
                f"adapter {name!r} is declared by {origin} but its declaration"
                f" could not be loaded ({detail}). The declaration names"
                f" {entry_point.value!r}; the distribution that ships it is"
                " installed but broken, which is a different problem from an"
                " adapter that is not installed."
            )
```

(raised outside the handler, per `validate_connection`'s own precedent, so no third-party
exception text rides along on `__context__`). Document the refusal on `boot`.

### WR-03: `cinv04-substrate-name` fails **open** when its derived vocabulary is empty

**File:** `tools/lints/substrate_names.py:159-183, 200-210, 278-280`

**Issue:** `substrate_vocabulary` returns the empty set when
`base / "src/ccf/graph/backends"` is not a directory, and `check_source` then returns `[]`
for every file. `repo_base_for` falls back to `pathlib.Path.cwd()` when no ancestor holds

```
vocabulary at a base with no adapter package: []
findings there: []
```

### WR-04: `cinv04-substrate-name` over-matches generic words whose only crime is sharing a stem with an adapter module

**File:** `tools/lints/substrate_names.py:41-47, 149`

**Issue:** The vocabulary is `{fluree, memory, mongo, neo4j, postgres, sqlite}` (verified),
and `_WORD_PATTERN` treats `_` and `-` as boundary characters. `memory` is ordinary
English. Verified against an unrelated core module:

```
'ccf.artifacts.store' names the graph substrate memory in a code position.   # CACHE_MODE = "in-memory"
'ccf.artifacts.store' names the graph substrate memory in a code position.   # def build(memory_budget: int)
```

Neither line is about a graph substrate. The rule passes today only because no such literal
currently exists outside the two exempt packages, and D-13 forbids an allowlist — so the
only escape is adding a whole package to `SUBSTRATE_NAME_EXEMPT_PACKAGES`, which disables
the rule for that package entirely.

The deeper problem is that the rule's blast radius is set by **adapter module naming**, and
nothing bounds it. A future `backends/file.py` or `backends/graph.py` would make every core
parameter, attribute, and string containing `file` or `graph` a CINV-04 violation across
`src/`, with no edit here and no warning.

**Fix:** Constrain the derived vocabulary rather than the boundary. Either (a) require an
adapter stem to be registered — read `REGISTRATION.name` off the write modules' AST rather
than the file stem, so a helper module contributes nothing — or (b) add a documented
minimum-distinctiveness rule and a stated escape for a stem that collides with common
vocabulary. Whichever is chosen, add a test that pins a synthetic adapter package
containing a generic stem and asserts the intended behaviour, so the trade is measured
rather than latent.

### WR-06: `mongo_write` retains the unscoped `seq` computation that `fluree_write` fixed as a review finding

**File:** `src/ccf/graph/backends/mongo_write.py:318-321, 469-473`

**Issue:**

```python
            "seq": self._arrival_index(
                ENTITY_CLAIMS, {**scope, "entity_uri": entity_uri}
            )
            + len(self._entity_claims),
```

The committed term is scoped to the node; the buffered term is `len(self._entity_claims)`,
which counts claims buffered for **every** entity in the transaction. `fluree_write.py:604-619`
documents this exact defect as "review finding WR-07", explains the consequence in full
("`A1, B1, A2` in one transaction gives `A` seq 0 and 2, and the next transaction's `A3`
reads `count(A) == 2` and computes 2 — a duplicate ... `_restitch_chain` yields a different
supersession chain per read"), and fixes it with a scoped `sum`. The Mongo module — the
template Fluree's docstring says it copied from — was not updated. The relationship
counterpart at line 469-473 has the same shape.

Dormant today for the same reason Fluree states: `BaseGraphWriter` opens one transaction
per claim. That is a property of the caller, not of the batched adapter, and the write seam
contract explicitly anticipates batched adapters (D-IMPL-88). Leaving one of two batched
adapters holding the defect while the other carries a paragraph explaining why it must not
is how the divergence outlives the memory of the fix.

**Fix:** Apply Fluree's scoped form to both Mongo sites, with a cross-reference so the two
stay legible as one decision:

```python
            "seq": self._arrival_index(
                ENTITY_CLAIMS, {**scope, "entity_uri": entity_uri}
            )
            + sum(
                1
                for buffered in self._entity_claims
                if buffered["entity_uri"] == entity_uri
            ),
```

### WR-07: `BackendStore` does not require `close()` to be idempotent, but `FabricHandle.close()` is unguarded and public

**File:** `src/ccf/graph/registry.py:223-242`; `src/ccf/boot.py:105-123, 275-278`

**Issue:** `FabricHandle.close()` calls `self._shutdown()` with no `_closed` guard, and
`FabricHandle` is also a context manager — so `with booted.handle:` around a body that also
calls `close()` invokes `store.close()` twice. `BaseGraphWriter.close()` is guarded;
`BackendStore.close()`'s Protocol declaration says nothing.

All six in-tree stores delegate to a driver whose `close()` happens to tolerate a second
call, so nothing is broken today. But `BackendStore` is now a **published** Protocol that
third parties implement, and the out-of-tree fixture's own author added a `_closed` guard
(`tests/fixtures/ccf-demo-adapter/src/ccf_demo_adapter/store.py:259-264`) because without
it `_detach` would double-decrement the handle count and delete a graph another handle is
still using. That is an adapter author discovering an unwritten requirement by reasoning
about a bug — exactly the situation a Protocol docstring exists to prevent.

**Fix:** State the requirement on the Protocol and stop relying on it:

```python
    def close(self) -> None:
        """Release this store's hold on its substrate. **Must be idempotent** —
        :meth:`ccf.boot.FabricHandle.close` is public and the handle is also a
        context manager, so a second call is an ordinary caller shape, not a
        defect."""
```

and guard `FabricHandle.close()`:

```python
    def close(self) -> None:
        if self._closed:
            return
        self._closed = True
        self._shutdown()
```

### WR-08: Built-in discovery assumes an on-disk `.py` directory, and its failure mode gives wrong advice

**File:** `src/ccf/graph/registry.py:358-385, 553-560`

**Issue:** `_backends_directory()` is `Path(__file__).resolve().parent / "backends"` and
`_builtin_names` drives `pkgutil.iter_modules` over that path. The module argues at length
that a disk read is more robust than packaging metadata, which is true for the failure
modes it names — but it makes built-in discovery depend on the package existing as a real
directory of importable module files. Under any packaging that does not lay files out that
way (zipapp, a frozen/PyInstaller bundle, a sourceless distribution), `_builtin_names`
returns `{}` and **every SDK adapter silently ceases to exist**.

The refusal an operator then reads is actively misleading:

> `no installed adapter registers the backend name 'sqlite'. Registered adapters: none. An
> adapter becomes available by installing a distribution that declares it under the
> 'ccf.graph_backends' entry-point group.`

That instruction is correct for a third-party adapter and wrong for a built-in — following
it cannot fix the problem, and nothing in the message distinguishes "the SDK's own adapter
package could not be read" from "you did not install anything."

**Fix:** Distinguish the states. When `_backends_directory()` does not resolve to a
readable directory, say so rather than reporting an empty built-in set:

```python
def _builtin_names() -> dict[str, str]:
    directory = _backends_directory()
    if not directory.is_dir():
        raise RuntimeError(
            f"the SDK's own adapter package is not readable at {directory}."
            " Built-in discovery reads that directory rather than packaging"
            " metadata, so this is an installation problem with the SDK"
            " itself, not a missing third-party adapter."
        )
    ...
```

### WR-09: `ResolvedSecret.field` is never read, and can silently disagree with the mapping key that is

**File:** `src/ccf/graph/registry.py:322-356`; `src/ccf/boot.py:256-266`

**Issue:** `ResolvedSecret`'s docstring justifies the type's whole existence on
reconciliation: *"two parallel mappings can disagree ... One object carries both, so a pin
cannot record a reference the value did not come from and no caller has to keep two
mappings in step."* But `boot()` keys everything off the **mapping key**:

```python
    _refuse_undeclared_secrets(registration.name, registration.secret_fields, resolved_secrets)
    store = registration.open_store(
        config,
        {field: secret.value for field, secret in resolved_secrets.items()},
    )
```

`secret.field` is never consulted. Confirmed: `grep -rn "\.field\b" src/ccf/boot.py
src/ccf/graph/registry.py src/ccf/deployment/manifest.py` shows the only reads are of
`ManifestEntry`/`SecretReference.field` in the manifest path; `ResolvedSecret.field` is
written at `manifest.py:410` and read nowhere in `src/`.

So a direct `boot()` caller can pass
`{"api_token": ResolvedSecret(field="bearer_token", ref_name="X", value=...)}` and the
mismatch is accepted in silence. The manifest path happens to keep them in step because
`_resolve_secret_references` writes both from one source — but that is the caller being
careful, not the contract holding, and `boot()` is public and documented for direct use.

**Fix:** Either enforce the reconciliation the docstring promises, or delete the field.
Enforcing is a two-line addition in `_refuse_undeclared_secrets`:

```python
    disagreeing = sorted(
        key for key, secret in supplied.items() if secret.field != key
    )
    if disagreeing:
        raise ValueError(
            f"backend {adapter_name!r}: a resolved credential is keyed by a"
            f" field its own record does not name: {', '.join(disagreeing)}."
            " The key and the record's `field` are one fact; a caller that"
            " can desynchronize them is the two-parallel-mappings problem"
            " ResolvedSecret exists to remove."
        )
```

### IN-01: `load_and_boot` runs discovery three times and validates the connection twice
