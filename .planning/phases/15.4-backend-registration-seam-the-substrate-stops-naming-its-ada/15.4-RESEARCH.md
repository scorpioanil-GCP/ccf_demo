# Phase 15.4: Backend Registration Seam — The Substrate Stops Naming Its Adapters - Research

**Researched:** 2026-08-09
**Domain:** Python plugin registration (stdlib entry points), module restructuring under an import lint, typed configuration boundaries, credential handling
**Confidence:** HIGH (nearly every claim was measured against this tree or executed in this venv; the three LOW items are named in the Assumptions Log)

---

## Summary

This phase turns one dependency arrow around. Today `src/ccf/boot.py` and
`src/ccf/graph/_writer.py` import the six graph adapters; after this phase each
adapter declares itself and the core looks it up. Everything else follows from
that: the eleven per-database keyword arguments collapse into one mapping, the
six-name `Literal` becomes a registry check, and the per-adapter cost of adding
a substrate goes to zero.

The work is smaller than it looks and the seams are cleaner than expected. I
measured the exact split point in `_writer.py`: **lines 176–973 contain no
reference to any backend at all** — not one name, not one constant. The neutral
base (`BaseGraphWriter`, the transaction protocols, the shared SQL adapter) is
already backend-free, so D-03's "the neutral machinery stays central" is a
lift-and-shift of the six sections below line 973, not a disentangling job. The
whole seam is 14 import statements in exactly 2 files (`boot.py`,
`_writer.py`) — that is the entire scope of structural property (1).

Three things need care. **Secrets**: I verified that Pydantic 2.13.4 prints the
offending input value verbatim in validation errors, including for a misspelled
field — so a resolved credential must never be inside a model that gets
validated. I also verified that `ccf.contracts.canonical` **refuses**
`SecretStr` outright, which turns "a credential can never be content-hashed"
from a discipline into a mechanism. **Property (2)** is the harder lint because
a substrate name is a string, not an import; I measured a formulation with zero
false positives on the post-migration tree and state its blind spots.
**Two premises in CONTEXT.md are factually wrong** and are corrected below
before anything is planned on top of them.

**Primary recommendation:** Split `_writer.py` at line 973 (verified clean),
give each adapter a registration record loaded through a `ccf.graph_backends`
entry-point group, resolve the named adapter only at boot, keep resolved
credentials out of every Pydantic model, and add the two lint rules as one
extension to `harness_imports.py` plus one sibling module.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Where per-backend write code lives**

- **D-01: Two modules per backend.** `backends/<name>.py` holds reads;
  `backends/<name>_write.py` holds writes. Every backend follows the split,
  including `memory`.

  *Why this and not the alternatives.* All six backends' writer classes live
  today in one 3,200-line file, `src/ccf/graph/_writer.py`, and
  `tools/lints/harness_imports.py:92` enforces single-writer by saying that
  exactly one module — `ccf.graph._writer` — may only be imported from L2.
  That module imports all six backends (`_writer.py:96,133,142,152,156,157`),
  which is precisely what property (1) forbids. The write code therefore has to
  move, and the question was what happens to the lint when it does.

  With a dedicated write module per backend, the lint rule keeps its exact
  present shape: it guards write modules, and only L2 may import them. One
  rule, six files instead of one. Nothing about how single-writer is enforced
  has to be redesigned or re-argued.

- **D-02: Rejected — reads and writes in one file per backend.** The read module
  is imported by many callers, so the lint could no longer say "only L2 imports
  this file." The rule would have to shift from guarding a module to guarding a
  class, which is both weaker and harder to check statically. Single-writer is
  architectural (CLAUDE.md §10); trading a checkable rule for an
  approximately-checkable one is not an acceptable price for fewer files.

- **D-03: Substrate-neutral write machinery stays central.** `_writer.py`
  survives as the neutral base (`BaseGraphWriter`, the transaction seam, the SQL
  adapter shared by both SQL backends) minus every per-backend subclass. The
  lint guards it exactly as today, plus the six new write modules.

**How a backend announces itself**

- **D-04: The manifest names the adapter in force; entry points make it
  findable.** Both, not either.

  The deployment manifest names the adapter — explicit, auditable, versioned,
  and pinnable in replay, which is how CCF records everything else that affects
  an answer. Python entry points let someone ship an adapter as a separate
  installable package that CCF finds without a line changing in this repo. That
  combination is what makes per-adapter cost genuinely zero rather than merely
  small.

  Note for planning: `pyproject.toml` declares **no** entry points today. This
  is CCF's first plugin surface, so the entry-point group name, its
  documentation, and its versioning are new ground rather than an extension of
  an existing pattern.

- **D-05: Third-party code is imported only when the manifest names it.**
  Discovery reads declared adapter names without executing anything. Only the
  adapter the manifest names is imported, at boot.

  Two consequences, both wanted. Nothing an installed package ships runs unless
  a deployment asked for it by name — the fail-closed posture CCF already takes
  elsewhere, now applied to a supply-chain surface that did not previously
  exist. And the optional `neo4j` and `pymongo` drivers stay unloaded when
  booting SQLite, preserving today's lazy-import behavior
  (`boot.py:191,211`) without a special case.

- **D-06: Rejected — importing every declared adapter at startup.** It would
  surface a broken adapter earlier, but at the cost of running arbitrary
  installed packages' module-level code at every boot. Not a trade CCF should
  make, and it would also undo the optional-extra deferral.

**Connection settings and secrets**

- **D-07: Each adapter declares a typed config model; the registry validates it
  before boot.** A Pydantic model per adapter naming exactly what that adapter
  requires. A missing or misspelled setting fails at the boundary with a message
  naming both the adapter and the field.

  This follows CLAUDE.md §11 ("Typed contracts at every boundary. Validation is
  at the boundary, never deferred") and preserves something the current code
  does deliberately: `_preflight_backend` (`manifest.py:255-266`) refuses a
  manifest whose declared backend lacks its connection argument, and refuses a
  credential supplied for a backend that was not selected. That behavior must
  survive the migration — it moves into the adapter's declared model rather than
  the hand-maintained dictionary it lives in now.

- **D-08: The manifest holds references to secrets, not secrets.** A manifest
  names an environment variable; boot resolves it. One mapping, so the shape
  stays uniform, and the manifest still contains no credential.

  This is a net improvement over today rather than a lateral move. Right now
  `fluree_bearer_token` and the database passwords travel as separate boot
  arguments precisely so they are never persisted — safe, but invisible: nothing
  in the versioned record says which credential a deployment used. A named
  reference is auditable, and replay can pin *which reference was in force*
  without ever recording what it resolved to.

  Planning must confirm the resolved value never reaches a log, a replay record,
  an error message, or a manifest. `backends/fluree.py:678-679` documents the
  current no-persistence guarantee and is the reference point for what must not
  regress. Note that Phase 15.3 code review found a real defect in exactly this
  area (WR-02/WR-03: a credentialed Fluree URL connected anonymously because
  `httpx` derives no header from `base_url` userinfo) — credential plumbing in
  this codebase has bitten once already.

**Consequences that follow from the above (not separately discussed)**

- **D-09: Replay pins the adapter.** Once an adapter can be a third-party
  package, which adapter and which version answered is something that affects
  the answer, so CCF pins it. Adapter name, adapter version, and the *names* of
  any secret references in force — never a resolved secret value. Planning
  decides which replay dimension carries it; the existing backend pin in
  dimension 2 (per 15.2-08) is the natural home.

- **D-10: The public API break is pre-authorized; the migration note is owed.**
  `boot()` and `load_and_boot()` lose their per-database keyword arguments
  (`manifest.py:288-294`). **D-15B** grants free rein on the public API pre-1.0
  (`pyproject.toml` version is `0.1.0`) on the explicit condition that adopters
  get a migration, and `docs/SURFACE-CHANGES.md` is where that migration is
  written. This phase owes an entry there.

  Known call sites that must migrate: `tests/graph/test_fluree_backend.py:1706-1707`
  asserts `fluree_bearer_token` is present in both signatures — that assertion is
  now false by design and must be rewritten, not deleted, so the guarantee it
  was protecting (a token reaches the backend) still has a test.
  `tests/conftest.py:343,351` supplies `neo4j_partition` / `mongo_partition`.

- **D-11: Proof is an out-of-tree adapter, not an in-tree seventh backend.**
  The evidence that per-adapter cost is zero should exercise the path an actual
  third party would take: a minimal adapter living outside `src/ccf` entirely,
  registered through entry points, that passes the existing conformance suite.
  An in-tree seventh backend would only prove the in-repo path, which is the
  weaker claim.

  Alongside it, the unchanged bar: four database test legs green, and
  `tests/conformance/query_corpus.py` byte-untouched. Per D-IMPL-93's own
  standard, "the corpus grew" is recordable and "the SDK bent" fails.

- **D-12: The six-name `Literal` becomes a plain string checked against the
  registry at boot.** (`artifacts.py:975`.) A *generated* list was considered
  and rejected: generated or not, it is still six database names sitting in a
  core file, which is the thing property (2) forbids.

  Verified during discussion, so planning need not re-check it: there is no
  exported JSON Schema file in the repo, and `DeploymentManifest` is
  content-addressed by its file bytes rather than by its model schema. Dropping
  the `Literal` therefore does not disturb existing manifests or their replay
  pins. The only cost is one-directional — a typo is caught at boot rather than
  at parse — and it is paid back by an error message that can name what *is*
  registered, which the `Literal` never could.

## Architecture Patterns

### System architecture — how a fabric boots after this phase

```
 deployment manifest (YAML, content-hashable Control Plane artifact)
   backend: "sqlite"                 ← plain string, no Literal
   connection: {database_path: "./fabric.sqlite3"}
   secrets:    {bearer_token: "CCF_FLUREE_TOKEN"}   ← names, never values
              │
              ▼
 ┌────────────────────────────────────────────────────────────────┐
 │ ccf.deployment.manifest.load_and_boot   (the wiring layer)     │
 │   1. parse manifest                                            │
 │   2. registry.names()   ── reads declared entry-point NAMES,   │
 │                            imports NOTHING            (D-05)   │
 │   3. refuse if manifest.backend ∉ names, naming what IS there  │
 │   4. registry.resolve(name)  ── imports EXACTLY this adapter   │
 │   5. validate manifest.connection against adapter.config_model │
 │   6. resolve secret refs from os.environ  ← the ONE env read   │
 └────────────────────────────────────────────────────────────────┘
              │  adapter record + validated config + resolved secrets
              ▼
 ┌────────────────────────────────────────────────────────────────┐
 │ ccf.boot.boot   (composition root — takes VALUES, not env)     │
 │   store            = record.open_store(config, secrets)        │
 │   token            = mint_boot_token(store.graph_identity)     │
 │   writer           = record.make_writer(store, token)          │
 │       └── record.make_writer lives in backends/<name>_write.py │
 │           and is the only thing that imports it                │
 └────────────────────────────────────────────────────────────────┘
              │
              ▼
   FabricHandle(reader, worker, registry, shutdown, adapter=…)
              │                                     └─→ replay dim 2 pin
              ▼
   AssemblyWorker (L2) holds the ONLY write handle
```

Three properties survive unchanged from today, and the diagram makes each
visible:

- The write handle is constructed in exactly one place and reaches exactly one
  consumer. `FabricHandle` still has no writer attribute (`boot.py:69-98`).
- Selection is explicit. Nothing infers a substrate from the shape of a
  connection string — the refusal `boot.py:138-149` documents.
- Only the named adapter is imported. Neo4j and MongoDB drivers stay unloaded
  when booting SQLite, exactly as `boot.py:191,211` achieves today, but now by
  construction rather than by two hand-written lazy branches.

### Entry-point discovery (RQ1, D-04/D-05)

Everything below was executed in this venv against a throwaway plugin package
built for the purpose, then uninstalled. [VERIFIED: executed]

**The API on Python 3.12.3:**

```python

```

Proof that discovery executes nothing, from an unbuffered run against a plugin
whose module prints on import:

```
STEP 1: before entry_points()
STEP 2: after discovery — names: ['demo', 'demo.dotted']
STEP 2b: ccf_demo in sys.modules? []
STEP 3: about to load
!!! SIDE EFFECT: ccf_demo_adapter.backend was imported
STEP 4: loaded {'name': 'demo'}
```

So D-05 is satisfied directly by the stdlib: `.name` and `.value` are read from
`entry_points.txt` metadata; `.load()` is the only thing that imports.

**Declaring the group** (`pyproject.toml`, setuptools >=77):

```toml
[project.entry-points."ccf.graph_backends"]
sqlite   = "ccf.graph.backends.sqlite_write:REGISTRATION"
postgres = "ccf.graph.backends.postgres_write:REGISTRATION"
# ... and so on
```

**Group naming.** The spec requires `^\w+(\.\w+)*$` and recommends a group name
starting with a PyPI name the consumer project owns, followed by a dot
[CITED: packaging.python.org/specifications/entry-points/]. The distribution
here is named `ccf`, so `ccf.graph_backends` follows the convention. One caveat
worth one sentence in the design: this repo is private and `ccf` has never been
published, so the namespace is conventional rather than owned.

**Sharing one path between in-tree and out-of-tree adapters.** Two shapes, and
the choice has a real security consequence:

| Shape | In-tree adapters | Out-of-tree adapters | Cost |
|---|---|---|---|
| (a) Uniform — all six register through `ccf`'s own entry points | entry points | entry points | One path, one code path to test. **But** a third-party distribution can declare `sqlite` and, depending on discovery order, shadow the built-in (measured below). Also makes boot depend on install metadata being fresh. |
| (b) Split source, one record type — built-ins from `ccf.graph.backends`, third parties from entry points | in-package discovery | entry points | Built-ins can never be shadowed and boot works with stale metadata. Two discovery sources, one record type and one resolution path. |

**Measured collision behaviour**, with two distributions installed, one of which
declares `demo` and `sqlite`:

```
all: [('demo', 'ccf-demo-adapter', '0.1.0', …),
      ('demo.dotted', 'ccf-demo-adapter', '0.1.0', …),
      ('demo', 'ccf-evil-adapter', '9.9.9', …),
      ('sqlite', 'ccf-evil-adapter', '9.9.9', …)]
eps["demo"] returns: ccf-demo-adapter        # silently first-wins
```
[VERIFIED: executed]

Names are **not** deduplicated across distributions, and `EntryPoints.__getitem__`
returns the first match without complaint. The spec is explicit that "if
different distributions provide the same name, the consumer decides how to
handle such conflicts" [CITED: packaging.python.org]. **CCF must decide
fail-closed**: a duplicate name is a broken deployment and must raise, naming
both distributions. This is the same posture `_open_backend` takes on an
ambiguous substrate selection (`boot.py:170-176`).

Given the shadowing result, **shape (b) is the recommendation** — but this sits
under "Claude's discretion" (registry internal structure), so the planner should
choose deliberately and record why.

**Known failure modes, all measured:**

1. **Stale editable-install metadata.** Editing `[project.entry-points]` in
   `pyproject.toml` without reinstalling leaves the new entry invisible:

   ```
   after editing pyproject WITHOUT reinstall: ['demo', 'demo', 'demo.dotted', 'sqlite']
   ```
   The freshly added name is absent. `make install` (`pip install -e ".[dev]"`)
   fixes it; the Makefile header already documents the general editable-install
   staleness trap (08-RESEARCH Pitfall 7).

2. **Two metadata directories for `ccf` in this repo.** With `.` on `sys.path`
   (which `ENV_DOCS := PYTHONPATH=.:src:runtime` in the Makefile produces, and
   which any `python script.py` from the repo root produces), three
   distributions named `ccf` are discoverable:

   ```
   ccf distributions visible: ['ccf.egg-info',
                               '/home/parkave/ccf_code/ccf.egg-info',
                               '/home/parkave/ccf_code/.venv/…/ccf-0.1.0.dist-info']
   ```
   `entry_points()` chains over `_unique(distributions())`, deduplicating by
   normalized distribution name — first wins in `sys.path` order. So the
   repo-root build-time `ccf.egg-info` **shadows** the installed `dist-info`.
   Both are refreshed by `pip install -e .`, so they normally agree; a branch
   switch or partial build can desync them. This is a second, independent
   argument for shape (b) above: built-in adapters that do not travel through
   packaging metadata cannot be affected by it at all.
   [VERIFIED: executed; `entry_points` source inspected]

3. **Case and normalization.** Entry-point names are compared as written. Decide
   whether adapter names are case-sensitive and state it. Recommend: exact
   match, lowercase by convention, refuse anything else — the manifest is a
   versioned document and "which case won" is not a question an audit should
   answer by convention.

### Typed config models (RQ3, D-07)

Today's mapping, verbatim (`src/ccf/deployment/manifest.py:253-266`):

```python
supplied = {"database_path": …, "postgres_dsn": …, "neo4j_uri": …,
            "mongo_uri": …, "fluree_url": …}
required = {"sqlite": "database_path", "postgres": "postgres_dsn",
            "memory": None, "neo4j": "neo4j_uri", "mongo": "mongo_uri",
            "fluree": "fluree_url"}[manifest.backend]
```

Two refusals follow from it, and **both must survive**:

| # | Refusal | Where today | How it survives |
|---|---|---|---|
| (a) | Declared backend's connection argument is missing | `manifest.py:269-274` | A **required field** on the adapter's config model. Pydantic raises `missing`; wrap it so the message names the adapter. |
| (b) | An argument the declared backend does not take was supplied | `manifest.py:275-281` | `extra="forbid"` on the config model. Pydantic raises `extra_forbidden` naming the key. **This is the one easy to lose** — see the warning below. |

Two more refusals live in `boot.py` and must also survive:

| # | Refusal | Where today | How it survives |
|---|---|---|---|
| (c) | Not exactly one backend selected | `boot.py:170-176` | Structurally impossible: the manifest names exactly one adapter. |
| (d) | `fluree_bearer_token` supplied without `fluree_url` | `boot.py:177-181` | Becomes an adapter-internal concern — the Fluree config model declares both, and a secret reference for an adapter that was not selected cannot exist because there is one mapping validated against one model. |

**Why refusal (b) is the one that gets lost in a migration.** Today it is an
explicit loop over *all five* connection arguments checking that only the
required one is present. Under one mapping validated against one model, the
protection comes entirely from `extra="forbid"`. If the config models inherit
from `CCFContract`, they get `extra="forbid"` and `frozen=True` for free
(`src/ccf/contracts/base.py:48`). If someone writes a plain `BaseModel` instead,
Pydantic's default is `extra="ignore"` and refusal (b) silently disappears with
no test failing. **Recommend: config models derive from `CCFContract`, and a
test asserts that every registered adapter's config model forbids extras.**

**The memory adapter declares a model with no fields.** Then `{"memory": true}`
plus any connection key is refused by `extra_forbidden` automatically — the
`"memory": None` special case in the dict disappears without a special case
replacing it.

**Error messages must name the adapter.** Pydantic's `ValidationError` names the
*model class* and the field, not the adapter. Wrap it:

```
manifest declares backend 'postgres'; its connection settings are invalid:
  dsn — Field required
registered adapters: fluree, memory, mongo, neo4j, postgres, sqlite
```

`ccf.boot`. `boot()` today takes values and reads no environment; keeping it
that way preserves testability, keeps the composition root deterministic, and
keeps the single new environment dependency in the wiring layer where the

```python
#: Guarded write modules: the neutral base, plus every per-backend write module.
WRITER_MODULE = "ccf.graph._writer"
WRITE_MODULE_SUFFIX = "_write"          # ccf.graph.backends.<name>_write

def is_write_module(name: str) -> bool:
    return name == WRITER_MODULE or (
        matches_module(name, ("ccf.graph.backends",))
        and name.rpartition(".")[2].endswith(WRITE_MODULE_SUFFIX)
    )
```

- Guarded set: `_writer` plus every `backends/*_write.py`.
- Permitted importers of a *per-backend write module*: `ccf.assembly`,
  `ccf.boot` — unchanged, exactly as today.
- Permitted importers of the *neutral base*: those two **plus any guarded write
  module** (each subclasses `BaseGraphWriter` and implements `_GraphTxn`).

No substrate name appears anywhere in the lint. Adding a seventh adapter's write
module extends the guarded set automatically — this is the "name the class, not
the instance" discipline that D-GATE-15.3 records the project learning three
times in one phase.

**One honest residual, and it is new.** If the registry resolves a write module
with `importlib.import_module(...)` rather than a static `import` statement, the
AST walker sees nothing — a dynamic import is invisible to an import lint. That
does not weaken the rule (nothing else statically names a write module), but it
does mean the *actual* import path is unguarded. Mitigation: confine dynamic
resolution to one function in one module and add a test asserting that function
is the only `import_module` call site under `src/ccf/graph`. State the residual
in the module docstring in the same voice `boot.py:22-26` uses for the
determined-insider claim.

## Don't Hand-Roll

| Problem | Do not build | Use instead | Why |
|---|---|---|---|
| Finding installed adapters | A scan of `site-packages`, a config file listing plugin modules, or a naming convention over importable modules | `importlib.metadata.entry_points(group=…)` | The PyPA-specified mechanism. Handles wheels, editable installs, eggs, and zipped distributions; reads names without importing, which is exactly D-05. |
| Masking a credential in `repr` | A custom `__repr__`, a wrapper class, a "don't print this" comment | `pydantic.SecretStr` | Verified to mask in `repr`, `str`, `model_dump`, `model_dump_json` **and** to be refused by `canonical_bytes`. Four surfaces and one refusal for one type annotation. |
| Refusing a setting an adapter does not take | A loop comparing supplied keys against a per-adapter allowed set | `extra="forbid"` (already on `CCFContract`) | It is the same check, already written, already tested, and it names the offending key. |
| Refusing a missing required setting | An explicit `if value is None: raise` per field | Pydantic required fields | Same reason; also produces one error per problem instead of stopping at the first. |
| Walking Python source for the lints | A regex over file text, or a new parser | `ast` + the four helpers in `tools/lints/__init__.py` (`format_finding`, `read_tree`, `imported_module_names`, `matches_module`) | Four checkers already share them; the finding format and the exit-code contract come for free. | Deciding a duplicate adapter name | First-wins, last-wins, or a version comparison | An explicit refusal naming both distributions | Measured: the stdlib silently returns the first. The spec hands the decision to the consumer. Silent precedence is how a third-party package shadows a built-in adapter. |
| A "does this manifest name a real backend" check | A generated list of valid names in a core file | A registry membership test at boot | D-12's own argument: generated or not, it is still six database names in a core file. |

standard library or in this repository. The phase is a rearrangement, not a
construction. The one genuinely new thing is a *policy* — what to do about

## Common Pitfalls

### Pitfall 1: `extra="forbid"` silently absent from a config model

**What goes wrong:** refusal (b) — "a credential supplied for a backend that was
not selected" — disappears with no test failing.
**Why it happens:** Pydantic's default is `extra="ignore"`. A model written as
`class SqliteConfig(BaseModel)` instead of `(CCFContract)` loses the guard, and
the loss is invisible: valid manifests still work.
**How to avoid:** derive every config model from `CCFContract`
(`src/ccf/contracts/base.py:48` sets `extra="forbid", frozen=True`), and add a
test that iterates registered adapters asserting
`model_config["extra"] == "forbid"`.
**Warning sign:** a manifest with a typo'd connection key boots successfully.

### Pitfall 2: a resolved secret inside a validated model

**What goes wrong:** a misspelled key puts the credential into a
`ValidationError` message, which reaches logs and tracebacks.
**Why it happens:** Pydantic reports `input_value=` verbatim — verified for both
`string_type` and `extra_forbidden` errors.
**How to avoid:** validate references, then resolve. Never construct a model
from a mapping that already contains resolved values.
**Warning sign:** any test that constructs a config model from a dict containing
a real-looking token.

### Pitfall 3: the empty-string secret

**What goes wrong:** `os.environ.get("CCF_FLUREE_TOKEN")` returns `""` or
`None`, the adapter treats it as "no credential", and the fabric connects
anonymously — precisely WR-02, arriving through a new door.
**Why it happens:** a manifest that *names* a reference has asserted a
credential is required. Silence is not consent.
**How to avoid:** a named reference that does not resolve to a non-empty value
is a refusal, not a fallback. Test it.
**Warning sign:** a test asserting "unset variable → anonymous connection works".

### Pitfall 4: stale entry-point metadata

**What goes wrong:** an adapter is declared but not discovered, or a removed
adapter is still discovered.
**Why it happens:** entry points live in build-time metadata, not in
`pyproject.toml`. Verified: editing the file without reinstalling leaves the new
name invisible. Verified separately: this repo carries **both** a root
`ccf.egg-info` and an installed `dist-info`, and the root one shadows the
installed one whenever `.` is on `sys.path`.
**How to avoid:** `make install` after any entry-point change; state the
requirement in the adapter-authoring docs; prefer in-package registration for
the six built-ins so a stale metadata directory cannot make the SDK unbootable.
**Warning sign:** a green local run and a red CI run, or the reverse.

### Pitfall 5: a third-party distribution shadowing a built-in name

**What goes wrong:** an installed package declares `sqlite` and, depending on
discovery order, answers for it.
**Why it happens:** measured — cross-distribution names are not deduplicated and
`eps["name"]` returns the first silently.
**How to avoid:** refuse duplicates, naming both distributions. Consider making
built-ins unreachable through entry points at all.
**Warning sign:** `registry.names()` returning a name twice and nothing
complaining.

### Pitfall 6: the read module importing its own write module

**What goes wrong:** `backends/sqlite.py` imports `backends/sqlite_write.py`
inside a factory function, and every importer of the read module transitively
reaches write code — the CINV-02 rule then flags the read module.
**Why it happens:** it is the obvious way to put a writer factory on a
registration record that also carries the store factory.
**How to avoid:** put `REGISTRATION` in the **write** module. It may import the
read module freely (the read module is unguarded); the reverse is forbidden. The
entry point then names the write module, which only `ccf.boot` and the registry
ever load.
**Warning sign:** a new `cinv02-graph-writer` finding on a `backends/<name>.py`.

### Pitfall 7: the conformance suite quietly not running the new adapter

**What goes wrong:** the out-of-tree adapter is installed but no conformance
param names it, so D-11's proof proves nothing.
**Why it happens:** the param lists are hand-written in two files
(`test_graphstore.py:47-55`, `test_substrate_differential.py:118-123`).
**How to avoid:** add the param explicitly in both, and assert in a test that
the param list and the registry agree — a mismatch is the failure mode that
looks green.
**Warning sign:** `-m "not postgres and not neo4j and not mongo and not fluree"`
test counts not rising after the adapter lands.

### Pitfall 8: regenerated files forgotten

**What goes wrong:** `make lint`/`make test` go red on a file nobody edited.
**Why it happens:** three committed artifacts are generated and drift-asserted
in the always-on `test` job: `docs/schemas/` (`make schemas`,
`tests/cli/test_schema_export.py`), `docs/surface/v0.2-surface.json`
(`tools/dump_surface.py`, `tests/test_surface_drift.py`), and
`http_api/openapi.json`. D-12 changes the first; D-10 changes the second.
**How to avoid:** the plan that drops the `Literal` re-runs `make schemas` in
the same change; the plans that reshape `boot()`/`load_and_boot()` write
`docs/surface-changes/` fragments (the drift gate accepts documented drift —
`tests/test_surface_drift.py:1-25`).
**Warning sign:** a red `test` job with no test-file change in the diff.

## Code Examples

### Reading adapter names without importing anything (D-05)

```python
# Source: verified by execution against importlib.metadata on Python 3.12.3
import importlib.metadata as md

BACKEND_GROUP = "ccf.graph_backends"

def declared_names() -> dict[str, str]:
    """Adapter name -> its object reference. Imports nothing."""
    return {ep.name: ep.value for ep in md.entry_points(group=BACKEND_GROUP)}

def resolve(name: str) -> object:
    """Import exactly the one adapter the deployment named."""
    matches = list(md.entry_points(group=BACKEND_GROUP).select(name=name))
    if len(matches) > 1:
        dists = ", ".join(sorted(f"{m.dist.name} {m.dist.version}" for m in matches))
        raise ValueError(
            f"adapter name {name!r} is declared by more than one installed "
            f"distribution ({dists}); the fabric does not choose between them"
        )
    return matches[0].load()          # the ONLY import
```

Note `.select(name=…)` rather than `eps[name]`: the mapping form returns the
first match silently, which is the shadowing hazard measured above.

### A config model that cannot leak (D-07/D-08)

```python
# Source: CCFContract at src/ccf/contracts/base.py:48; SecretStr behaviour
# verified against pydantic 2.13.4 in this venv.
from ccf.contracts.base import CCFContract   # extra="forbid", frozen=True

class FlureeConnection(CCFContract):
    """What the Fluree adapter needs. References only — never values."""
    url: str
    partition: str | None = None
    bearer_token_ref: str | None = None      # an ENV VAR NAME, not a token
```

Validation happens on this. Resolution happens after, and the resolved value
goes straight into the store constructor as an argument — the shape
`fluree_bearer_token` already has today (`boot.py:237`,
`backends/fluree.py:706`). If a resolved value must live on a typed object at
all, annotate it `SecretStr`: `canonical_bytes` then **refuses** it, which turns
the no-persistence guarantee into a mechanism.

### Refusing an unresolved secret reference (the WR-02 lesson)

```python
import os

def resolve_secret(adapter: str, field: str, env_name: str) -> str:
    value = os.environ.get(env_name)
    if not value:                       # unset OR empty — both are refusals
        raise ValueError(
            f"backend {adapter!r} field {field!r} names environment variable "
            f"{env_name!r}, which is unset or empty. A named reference asserts "
            f"a credential is required; the fabric does not fall back to an "
            f"anonymous connection. The variable's value is never logged."
        )
    return value
```

The message names the variable and never its value — the posture
`backends/fluree.py:604-620` already takes ("neither value appears in this
message").

## Security Domain

### Applicable ASVS categories

| ASVS category | Applies | Standard control |
|---|---|---|
| V2 Authentication | yes (indirectly) | Adapter credentials reach the substrate through the driver's own auth channel — `auth` pair for Neo4j (`backends/neo4j.py:151-165`), `Authorization` header for Fluree (`backends/fluree.py:580-621`), libpq DSN for Postgres. This phase must not change any of them. |
| V3 Session Management | no | The SDK holds no user sessions. |
| V4 Access Control | no (for this seam) | Tenant authorization lives in the HITL/HTTP doors, untouched here. |
| V5 Input Validation | **yes** | The manifest is adopter-authored input. Adapter name, connection mapping and secret-reference names are all validated at the boundary — Pydantic `extra=forbid` models per adapter (D-07) plus a registry membership check (D-12). |
| V6 Cryptography | no | No new cryptography. `content_hash` is unchanged. |
| V7 Error Handling & Logging | **yes** | The dominant risk. Verified: Pydantic echoes `input_value` in validation errors. Every refusal message must name the adapter and the field and never the value. |
| V10 Malicious Code | **yes** | Entry-point discovery is a new supply-chain surface. D-05 (import only what the manifest names) and duplicate-name refusal are the controls. |
| V14 Configuration | **yes** | Secret references in a content-hashed artifact; the manifest still carries no credential. |

### Threat patterns for this seam

| Pattern | STRIDE | Mitigation |
|---|---|---|
| A third-party distribution declares a built-in adapter name and answers for it | Spoofing | Refuse duplicate names, naming both distributions. Consider keeping built-ins off the entry-point path entirely. Measured: the stdlib silently returns the first. |
| An installed package's module-level code runs at every boot | Tampering / Elevation | D-05 — discovery reads names only; only the named adapter is loaded. Verified achievable with the stdlib. |
| A credential lands in a content-hashed manifest | Information disclosure | The manifest holds reference *names*. Reinforced by `canonical_bytes` refusing `SecretStr`. |
| A credential lands in an error message | Information disclosure | Resolve after validation, never before. Existing store constructors already state and honour this (`fluree.py:604-620`). |
| A credential lands in a replay record | Information disclosure | D-09 pins reference names only. V15 asserts it. |
| A mis-set environment variable produces an anonymous connection | Spoofing | Refuse unresolved and empty references. This is WR-02 arriving through a new door; V14 is its regression test. |
| A dynamic import evades the import lint | Tampering | Confine `import_module` to one function; test that it is the only call site under `src/ccf/graph`. Stated as an honest residual, not claimed away. |
| A leaked connection pool on repeated boot failure | Denial of service | WR-05, open debt, exposure raised by D-08. Five-line fix. |

## Open Questions

1. **Q1 — Does the exported schema keep a hint of the valid backend names?**
   - What we know: `docs/schemas/ccf.deployment-manifest.json` currently carries
     a six-value enum; dropping the `Literal` removes it, and adopters lose
     editor autocompletion for that field.
   - What is unclear: whether that adoption cost was weighed, since D-12 was
     decided under the belief that no exported schema existed (Correction 1).
   - Recommendation: accept the loss, and add a `ccf backends` CLI subcommand
     listing registered adapters (fits D-IMPL-22, No-Hardcoding-clean, and it
     answers a question the enum never could — *what is installed here*).
     Alternative to reject explicitly: injecting the registered names into the
     generated schema, which is the "generated list" D-12 already rejected,
     wearing a different hat.

2. **Q2 — Where do adapter name and version reach the replay record from?**
   - What we know: `FabricHandle` exposes reader, worker, registry and a
     shutdown closure and nothing else (`boot.py:78-89`); `build_replay_record`
     reads from an `execution` object (`record.py:482-517`).
   - What is unclear: whether the adapter fact travels on the handle, on the
     execution object, or as a Control Plane binding.
   - Recommendation: an `adapter` attribute on `FabricHandle` — smallest route,
     one public-surface addition, one fragment. Note it makes `FabricHandle`
     carry a fact rather than only capabilities, which is a small departure from
     its current "no state you can misuse" character.

3. **Q3 — Allowlist or no allowlist for the two new rules? (needs Dave)**
   - What we know: D-IMPL-93 and CONTEXT.md both say `allowlist.yaml` governs
     exceptions. But `apply_allowlist` runs only for `no-hardcoding`
     (`__main__.py:152`), it requires a fingerprint in the finding text
     (`no_hardcoding.py:255-266`), and **two written statements in the repo say
     import rules take no allowlist** (`allowlist.yaml` header;
     `harness_imports.py:41-43`).
   - What is unclear: whether the CONTEXT wording was a general instruction
     about *where exceptions are declared* or a specific requirement to wire the
     new rules into the YAML.
   - Recommendation: no allowlist; carve-outs are named constants in the checker
     module, reviewed with the code — stricter than asked for, and consistent
     with every existing import rule. **Surface this to Dave rather than
     deciding it quietly** (CLAUDE.md §15: SDK-extension ambiguity → ask).

4. **Q4 — Does WR-01 get fixed in this phase?**
   - What we know: the duplicated `POLICY_KEY_SEPARATOR` at `_writer.py:2452`
     sits inside lines this phase relocates wholesale, and the 15.3 review found
     its stated justification false and identified it as what made CR-01
     possible.
   - What is unclear: whether fixing recorded debt inside relocated lines counts
     as scope creep or as the responsible handling of a line you are moving
     anyway.
   - Recommendation: fix it — deleting one duplicated constant and calling the
     shared function is smaller than the paragraph explaining why it was moved
     unchanged. If not, record the deferral explicitly in the gate package.

5. **Q5 — Does WR-05 get fixed in this phase?**
   - What we know: `FlureeGraphStore.__init__` leaks an `httpx.Client` on any
     construction failure (`fluree.py:584-608`); D-08 makes construction
     failures more likely by adding a resolution step that can fail.
   - What is unclear: whether "the phase raises the exposure of open debt" is
     itself a reason to close it.
   - Recommendation: fix — five lines, and the phase is the reason it matters
     more. Otherwise record the raised exposure in the gate package so it is a
     decision rather than an oversight.

6. **Q6 — Are adapter names case-sensitive, and is there a reserved namespace?**
   - What we know: entry-point names are compared as written. `ccf.` is already
     a reserved prefix for artifact class ids (D-IMPL-84) precisely because a
     manifest can be authored to squat an SDK name.
   - What is unclear: whether the same reservation should apply to adapter
     names, so a third party cannot register `sqlite`.
   - Recommendation: exact lowercase match; refuse anything else. Consider
     reserving the six built-in names against third-party registration — the
     D-IMPL-84 precedent argues for it directly.
