## Verified findings

### F0 — HIGH — `tools/lints/harness_imports.py:200` — **the harness-neutrality lint does not see `from google import adk`**

**Found by Cursor. Reproduced empirically by the orchestrator, and it is the
most serious result this panel produced** — more so than F1, because it lands on
a mission-level invariant rather than a seam.

```
$ check_source("from google import adk\n",       ..., "ccf.boot")  ->  []
$ check_source("from google.adk import agents\n", ..., "ccf.boot")  ->  ["... cinv02-harness harness import 'google.adk' is forbidden in core ..."]
```

The first form produces **no finding at all**. `HARNESS_DENY` holds dotted
entries (`google.adk`, `langgraph`, `claude_agent_sdk`), and the deny loop at
line 200 still calls `imported_module_names`, which reports only `google` for
that spelling. `matches_module("google", {"google.adk", ...})` is false.

**Why this is the serious one.** CLAUDE.md §1 makes harness neutrality one of
**four mission-level success conditions**, and §7.3 states: *"Zero harness
imports in core. CI enforces this via an import lint... A harness import in
`/src` is a defect of the same class as an LLM client in an algorithmic
module."* `from google import adk` is idiomatic ADK usage. The lint that makes
that invariant "an invariant, not an aspiration" does not see it.

**Cursor's framing, which is the insight and is quoted rather than paraphrased:**
CR-01 and CR-02 are *"seam completeness"* bugs — a fix covering one failure shape
(raise / one import form) leaves the isomorphic neighbour green. This is CR-02's
fix stopping 27 lines short **inside the very file it was applied to**: line 227
uses the corrected `reached_module_names`; line 200 was left on the old helper.

**Not independently reproduced, same code shape, recorded as unverified:** Cursor
also names `tools/lints/orchestration_imports.py:61` and
`tools/lints/algorithmic.py:77` as carrying the identical pattern. Both do call
`imported_module_names` (confirmed by reading). An orchestration probe returned
`[]` for *both* spellings including the one that should fire, so the module path
chosen was outside that rule's scope and the probe established nothing either
way. Treat those two as *likely by inspection, unproven by execution* — and
prove them before or while fixing.

**Why the existing tests stay green:** they exercise `from google.adk import
agents` and `from ccf_runtime.adapters import ...` — forms the old helper
already saw. The suite cannot fail on the spelling that is open.

**The fix is nearly free:** `reached_module_names` already exists in the same
module and is already imported there.

**Verified:** empirically, output above; plus
`grep -n "imported_module_names\|reached_module_names" tools/lints/*.py`
showing line 200 on the old helper and line 227 on the new one.

### F1 — HIGH — `src/ccf/graph/registry.py:787` — a third-party import failure's message is echoed verbatim

**Found independently by three of four reviewers** (Codex, Gemini, Ollama). That
convergence is the single strongest signal this panel produced.

`_load_third_party()` catches `Exception`, builds
`detail = f"{type(failure).__name__}: {failure}"`, and interpolates `detail`
into the public `ValueError` raised at line 790. Raising outside the `except`
block correctly removes `__context__` — but it does not sanitize the message
that was already copied out.

**Failure scenario.** An installed third-party adapter's module-level code
raises during import with a credential in its message — e.g. a client
constructed at import time against `postgres://user:secret123@host/db`, or
`RuntimeError(f"bad token {os.environ['GRAPH_TOKEN']}")`. `resolve("that_adapter")`
then raises a CCF `ValueError` containing that value, and the value reaches
operator logs, the CLI's stderr, and `GET /backends`'s 503 body.

**Why it matters more here than it would elsewhere.** This sits exactly on the
seam this phase created. Before 15.4, no arbitrary installed distribution's
exception text could reach a CCF refusal; the adapter set was closed. The phase
opened that seam deliberately, and this is the one path across it that was not
given the sanitizing discipline the rest of the module was built with.

**The contrast is inside the same file.** `validate_connection` (line ~899)
documents that `detail["input"]` is *never* read and neither is `str(error)`,
building its message from `loc` and `msg` alone. That discipline was applied to
CCF's own validation errors and not to third-party exception text.

**Verified:** read at `src/ccf/graph/registry.py:787,790`.

**Suggested shape of a fix (not applied):** keep the exception *type* and the
adapter/distribution identity, drop `str(failure)`. The remedy a reader needs is
"which distribution, and reinstall it" — the third party's own message adds
little and carries unbounded content.

### F2 — HIGH — `tools/lints/substrate_names.py` — the recurrence rule knows only *built-in* substrate names

**Found by Codex.**

`substrate_vocabulary(base)` derives its vocabulary from `*.py` stems in the
SDK's own adapter package and nothing else. So `cinv04-substrate-name` enforces
*"no **built-in** substrate name in core"*, not *"no substrate name in core"* —
which is how the phase goal, the ROADMAP and `D-IMPL-93` all state it.

**Failure scenario.** Install a third-party adapter named `demo`. Add
`if backend == "demo": ...` or `DEMO_TIMEOUT = 30  # demo needs longer` to
`src/ccf/boot.py`. `cinv04-substrate-name` does not fire, because `demo` is not
in its derived set. `cinv02-backend-import` does not fire either — nothing was
imported. Both structural guarantees pass on a change that is exactly the
per-adapter substrate coupling `D-IMPL-93` exists to forbid.

**Codex's framing is the sharp part and is quoted rather than paraphrased:**
this makes the third-party "zero substrate cost" claim *"partly true by
construction of the measurement."* The demo adapter cost zero lines partly
because the rule that would catch a non-zero cost cannot see its name.

**The tension this sits in, which the fix has to resolve rather than ignore.**
A vocabulary that consulted installed entry points would make the lint
**environment-dependent** — green on a machine without the adapter installed,
red on one with it. A structural invariant whose verdict depends on the local
virtualenv is a different kind of weak. This is a design question, not a patch.

**Verified:** read `substrate_vocabulary`'s derivation path; its own docstring
states the source is the adapter package under `base`.

### F3 — MEDIUM — `tools/lints/__init__.py:74` and `:98` — relative imports are invisible to both lint helpers

**Found by Codex.** This is **CR-02's defect class one level deeper** — the
blocker the single reviewer found was that `from ccf.graph import _writer` was
invisible; this is that `from .graph import _writer` still is.

Both `imported_module_names()` and `submodule_import_names()` return `[]` for
any `ImportFrom` carrying `node.level` (a relative import). `backend_imports`
and the widened `cinv02-graph-writer` both build on those helpers, so
`from .graph.backends import sqlite_write` inside `src/ccf/boot.py` reaches the
adapter and emits no finding.

**Exploitability is low; the guarantee is still narrower than stated.** `src/ccf`
uses absolute imports by convention throughout, so no current module trips this.
But "by convention" is what the lint exists to replace — CR-02 was serious for
exactly that reason, and the same argument applies unchanged here.

**Verified:** `node.level` early-returns at `tools/lints/__init__.py:74` and
`:98`. Both helpers, both blind.

### F4 — MEDIUM — `src/ccf/boot.py:344-345` and `:348-350` — sequential cleanup skips the second step if the first raises

**Found independently by Gemini and Ollama.** Adjacent to the fixed CR-01.

```python
except BaseException:
    release_boot_token(token)
    store.close()
    raise
```

If `release_boot_token(token)` raises, `store.close()` never runs and the store
connection leaks. `shutdown()` at 348-350 has the same shape: a `writer.close()`
that raises skips `store.close()`.

**What makes this worth recording rather than dismissing.** The comment directly
above the block shows the author reasoned about ordering explicitly — *"release
the mint first, so a store whose `close` also raises cannot leave the graph
permanently unbootable"*. The failure mode of `store.close()` raising was
considered; the failure mode of `release_boot_token()` raising was not. The fix
is `try/finally`, and the ordering rationale already recorded stays correct.

**Verified:** read at `src/ccf/boot.py:341-350`.

### F5 — LOW — `runtime/ccf_runtime/http_api/routes/backends.py:129-137` — a documented registry refusal returns 500, not the typed 503

**Found by Codex.**

The route catches `(DuplicateBackendName, ReservedBackendName, ValueError)`.
`_builtin_names()` raises `RuntimeError` when the SDK's own adapter package is
unreadable — a refusal the registry documents at `registry.py:425-430` and
`:647`. `RuntimeError` is not a `ValueError` subclass, so that path escapes the
handler and surfaces as an unshaped 500 instead of the actionable typed 503 the
route promises.

**Failure scenario.** A zipped, frozen or damaged install where
`src/ccf/graph/backends` is not a readable directory. The operator gets a bare
500 rather than the reinstall message the registry wrote for exactly that case.

**Verified:** compared the route's catch tuple against `_builtin_names()`'s
documented raise.

### F6 — HIGH — `src/ccf/boot.py:331-350` — CR-01 guards `make_writer` *raising*, not *returning a writer that never releases*

**Found by Cursor. Verified.** The second half of a fixed blocker.

CR-01 made a raising `make_writer` release the mint. A `make_writer` that
*returns* is still trusted unconditionally — `boot()` performs no
`isinstance(writer, BaseGraphWriter)` check. Three facts compose into the same
outcome CR-01 closed:

1. **The public `GraphWriter` Protocol does not declare `close()`.** Verified:
   `src/ccf/graph/protocols.py:565` declares `upsert_entity` and
   `upsert_relationship` and nothing else — *zero* occurrences of `def close` in
   the protocol body. A third-party author writing against the documented public
   protocol has no reason to implement one.
2. **`_LIVE_WRITERS` is cleared in exactly two places** — `release_boot_token`
   (`_writer.py:228`) and `BaseGraphWriter.close` (`_writer.py:580`). A writer
   that is not a `BaseGraphWriter` subclass clears it from neither.
3. **`FabricHandle.close` sets `_closed = True` at line 124, *before* calling
   `_shutdown()` at line 125.** A shutdown that raises cannot be retried; the
   second `close()` returns immediately.

**Failure scenario.** A third-party `make_writer` returns a duck-typed object
satisfying the public `GraphWriter` protocol — `upsert_entity`,
`upsert_relationship`, no `close`. Boot succeeds and the mint has already added
`graph_identity` to `_LIVE_WRITERS`. `handle.close()` sets `_closed = True`, then
`writer.close()` raises `AttributeError`. The mint is never released, the store
may leak, and a second `close()` is a no-op. **The graph is unbootable for the
process lifetime — CR-01's exact outcome, reached through the success path CR-01
did not cover.**

**What makes this more than theoretical.** The gap is between the *public*
protocol the SDK documents for adapter authors and the *private* base the
runtime actually requires. `DI-15.4-05` records that same split from the other
direction — six private names an adapter must reach for. This is that gap
producing a live defect rather than an inconvenience.

**Verified:** protocol body read; both `discard` sites enumerated; `_closed`
ordering read at `boot.py:122-125`. The existing CR-01 regression test
(`tests/graph/test_boot_seam.py`) covers a *raising* constructor only.

## Rejected on verification

### Gemini HIGH — "missing mandatory secrets are not refused" — REJECTED as stated

Gemini reported that neither `boot()` nor the manifest preflight verifies that
every field in `registration.secret_fields` is actually supplied, and framed a
Fluree deployment omitting `bearer_token` as a silent anonymous connection —
"the exact `WR-02` failure class the phase claimed to eliminate".

**The mechanism it describes is real: `_refuse_undeclared_secrets` computes
`set(supplied) - set(declared)` and so refuses only *extra* secrets, never
missing ones.** The finding is rejected on what `secret_fields` *means*, not on
what the code does.

`BackendRegistration.secret_fields` is documented as *"Config keys whose value
is a credential — supplied at boot rather than declared in a versioned
document."* That is a **classification** — which keys hold secrets, so they
travel in the separate mapping and never reach a content hash or a validation
echo — **not a requirement that each be present.** An unauthenticated Fluree
server is a legitimate deployment, and this repository's own always-on Fluree
leg (37 tests) runs against one.

**What survives, downgraded, and it is not nothing.** There is no way for an
adapter to declare a credential *mandatory*. A manifest that names a secret
reference whose environment variable is unset is refused; a manifest that omits
the reference entirely is not. An adapter that requires authentication cannot
say so. That is a gap in the **adapter declaration surface**, which is
`DI-15.4-05`'s subject — filed there rather than as a defect here.

## Consensus

**Agreed concerns (2+ reviewers):**

- **F1, the third-party exception echo — 3 of 4.** Codex, Gemini and Ollama each
  reached it independently, from different directions. Treat as the panel's
  primary result.
- **F4, sequential cleanup — 2 of 4.** Gemini and Ollama.

**Divergent:**

- **Overall risk.** Codex says HIGH, citing F1 plus the two lint gaps as making
  the structural guarantee "weaker than claimed". Gemini says the inversion is
  "structurally sound and effectively enforced". Both are defensible: the
  *achieved* structure is sound, and the *enforcement* has two holes that only
  matter for third-party adapters — which is precisely the case the phase exists
  to serve.

**Agreed strengths (verified, recorded because a review that only accuses is
not a review):**

- `validate_connection`'s sanitization — raising outside the `except` block so
  `__context__` and `__cause__` are both `None`, and building the message from
  `loc` and `msg` only. Named as excellent by Gemini and sound by Codex.
- The CR-01 fix. Codex confirmed token release precedes `store.close()`, so a
  failing close cannot leave the graph permanently marked live.
- The CR-03 fix. Codex confirmed distribution name alone is no longer sufficient
  — version and target must agree, and unknown metadata refuses.
- The CR-02 fix for *absolute* imports. Both forms now caught via
  `reached_module_names()`.
- `substrate_vocabulary`'s WR-03 fix — refusing on an empty vocabulary instead
  of passing every file — and the `GENERIC_WORD_STEMS` escape, which Gemini
  called "a thoughtful and necessary control for a derived vocabulary".
- Manifest preflight ordering: undeclared secret fields are refused **before**
  any environment variable is read.

## Triage (CLAUDE.md §3.1)

The phase is already gated, so this triage is a **recommendation to Dave, not a
gate condition**. `D-GATE-15.4` was approved on the evidence available at the
time, and nothing here contradicts the phase's headline claim — the out-of-tree
adapter did arrive at zero substrate cost. F2 bounds how much that measurement
*proves*; it does not falsify it.

**Nothing here reopens `D-GATE-15.4`, and nothing here falsifies the phase's
headline claim** — the out-of-tree adapter did arrive at zero substrate cost.
What the panel establishes is narrower and worth stating precisely: **the
enforcement is weaker than the achievement.** The structure the phase built is
sound; two of the three lints that are supposed to hold it in place have blind
spots, and one of those blind spots predates this phase and belongs to harness
neutrality rather than to backends.

That last point deserves emphasis: **F0 is not a Phase 15.4 defect.** The
harness deny loop was blind to `from google import adk` before this phase began.
Phase 15.4 fixed the same defect one file over, under CR-02, and stopped 27
lines short. The panel found it because it was told to look at what is adjacent
to a fixed blocker — which is the argument for running a panel after a
single-reviewer pass, stated as concretely as it can be.

**Suggested shape:** one gap-closure plan covering F0 + F3 + F6 (the lint-and-seam
completeness set, all one defect class), a second small one for F1 + F4 + F5, and
F2 carried to a design cycle with `DI-15.4-05`.
