## F0 — HIGH — the harness-neutrality lint did not see `from google import adk`

### What was wrong

`HARNESS_DENY` holds dotted entries. The deny loop at `harness_imports.py:200`
called `imported_module_names`, which reports only `google` for that spelling,
so `matches_module("google", {"google.adk", ...})` was false and the statement
produced **no finding at all**. Line 227 of the same file already used the
CR-02-corrected `reached_module_names` — the fix stopped 27 lines short inside
the file it was applied to.

This predates Phase 15.4. It is a mission-level invariant (CLAUDE.md §1
condition 3; §7.3 calls a harness import in `/src` a defect of the same class
as an LLM client in an algorithmic module), and `from google import adk` is
idiomatic ADK usage.

### Why the suite stayed green

The deny entries split into two families, and only one was ever exposed:

| deny entry | shape | blind? |
| --- | --- | --- |
| `google.adk` | dotted | **yes** — reachable as `from google import adk` |
| `langgraph`, `claude_agent_sdk`, `anthropic` | single-segment | no — they have no parent to be named by |

Every spelling a test author naturally reaches for works for the
single-segment entries. The asymmetry was invisible from the test file.

### The two other checkers: proven blind by execution, both fixed

The panel recorded `orchestration_imports.py:61` and `algorithmic.py:77` as
*likely by inspection, unproven by execution* — its own probe returned `[]` for
both spellings including the one that should have fired, because the module
path it used was outside that rule's scope, so `check_source` returned early.
Re-probed with module paths **inside** each rule's scope:

```
[BLIND] cinv02-harness  'from google import adk'            -> []
        (control)       'from google.adk import agents'     -> finding

[BLIND] d06-split       'from ccf_runtime import adapters'  -> []      (driver -> adapters)
        (control)       'from ccf_runtime.adapters import x'-> finding
[BLIND] d06-split       'from ccf_runtime import orchestration' -> []  (adapter -> orchestration)
        (control)       'from ccf_runtime.orchestration import x' -> finding

[BLIND] cinv03          'from ccf import llm'               -> []
        (control)       'from ccf.llm import LLMClient'     -> finding
[BLIND] cinv03          'from google import generativeai'   -> []
        (control)       'import google.generativeai'        -> finding

[ok   ] cinv02-harness  'from claude_agent_sdk import query'-> finding  (single-segment)
[ok   ] cinv03          'from anthropic import Anthropic'   -> finding  (single-segment)
```

**Verdict: both were blind, in every direction, and both are fixed.** The
`cinv03` case is the sharper one — `from ccf import llm` is the SDK's *own* LLM
seam entering the algorithmic path unremarked, which is the Algorithmic ⇄
Semantic Alternation (CLAUDE.md §11) not being enforced against a spelling a
CCF developer is more likely to write than the one that was covered.

`cinv02-backend-import` was already on the corrected helper (CR-02) and was
clear; it is included in the F3 change only.

### The fix

All four import rules read `reached_module_names`, one finding per statement
per rule (`sorted(...)[0]`, so the message names the deny entry itself rather
than an expanded suffix). Expansion cannot over-reach: an expanded name matches
only when it equals or descends from a deny entry, so `from google import
protobuf` → `google.protobuf` matches nothing.

The `harness_imports.py` docstring paragraph that *argued* for the old helper
("the expanded form would be a claim about a package this rule has no business
making") is replaced with why that argument was wrong in the one direction that
mattered.

## F3 — MEDIUM — relative imports were invisible to both name helpers

`imported_module_names` and `submodule_import_names` both early-returned `[]`
for any `ImportFrom` carrying `node.level`, so `from .graph.backends import
sqlite_write` inside `src/ccf/boot.py` reached an adapter with no finding.

Resolution now uses the importing module's package, derived by a new
`package_for(path, module_name)`. The path is what settles the one case the
module name cannot: the runner maps `src/ccf/graph/__init__.py` to `ccf.graph`,
and `from . import _writer` there must resolve against `ccf.graph`, not `ccf`.

`package=` is an **optional** keyword defaulting to `""`. A caller that does not
pass it gets exactly the old behaviour — as blind as before, never silently
wrong in a new way. Unresolvable cases (unknown package; dots climbing past the
root) return nothing rather than a guess.

**Blast radius: zero current findings.** `src/` and `runtime/` contain no
relative imports today (verified by grep); the ones in `examples/` and `tests/`
are outside all four rules' `RULE_TREE_SCOPE`. That is exactly the review's
point — "by convention" is what the lint exists to replace.

## F6 — HIGH — CR-01 guarded `make_writer` raising, not returning a writer that never releases

### The three facts, and how they compose

1. `ccf.graph.protocols.GraphWriter` declared `upsert_entity` and
   `upsert_relationship` and nothing else — no `close()`.
2. `_LIVE_WRITERS` is cleared only by `release_boot_token` and
   `BaseGraphWriter.close`. An object that is neither cannot release the graph.
3. `FabricHandle.close` set `_closed = True` *before* `self._shutdown()`, so a
   failing shutdown could never be retried.

A third-party `make_writer` returning a duck-typed object satisfying the
*documented public* protocol boots fine; `handle.close()` marks the handle
closed, `writer.close()` raises `AttributeError`, the mint is never released,
and the graph is unbootable for the process lifetime — CR-01's exact outcome
through the success path CR-01 did not cover.

### The decision: (b) AND (a), and why neither alone

The review offered (a) `boot()` type-checks the returned writer, or (b) the
public `GraphWriter` Protocol gains `close()`, and called (b) the better fix.
**Both shipped, because they close different halves and neither is sufficient:**

- **(b) is the declaration.** `GraphWriter` now declares `close()` with its
  lifecycle obligation stated: idempotent, and releasing the graph is the
  load-bearing half. Without it, an adapter author reading `protocols.py` has
  no way to *learn* the requirement — which is precisely the `DI-15.4-05` split
  between the public surface and what the runtime requires, producing a live
  defect rather than an inconvenience. But a Protocol is structural
  documentation. A third-party callable can ignore it and still return, and
  nothing at boot would notice.
- **(a) is the enforcement.** `adopt_writer(writer, *, adapter)` in
  `ccf.graph._writer` refuses a returned object that is not a
  `BaseGraphWriter`, with a `TypeError` naming the adapter and the type it
  returned. Without it, (b) changes what a careful author reads and nothing
  else. But (a) alone would leave the documented surface still saying less than
  the runtime requires — the defect would be unreachable while its cause stayed
  in the file.

**`isinstance`, not `hasattr(writer, "close")`.** The latter admits an object
with a `close` that does not release the graph — the same defect with one more
step in it. The requirement is not "has a close method", it is "is the thing
whose close releases the mint", and that is a class identity. This adds **no
new contract**: `BackendRegistration.make_writer` is already typed
`-> BaseGraphWriter`, and `public/how-to/write-a-graph-backend-adapter.md` row 4
already says "subclasses the SDK's neutral `BaseGraphWriter`". The declared type
was a statement rather than a gate only because a third-party distribution is
not inside this repository's `mypy --strict` run.

**Where it lives.** `ccf.graph._writer` — the module that owns `_LIVE_WRITERS`,
`BaseGraphWriter` and the mint/release pair. Not `ccf.boot`, both because the
invariant is that module's own and to keep the `boot.py` footprint minimal for
the parallel F4 merge.

### The close-ordering half

`FabricHandle.close` now runs `_shutdown()` first and sets `_closed = True`
after. Idempotency on success is unchanged and the WR-07 argument in that
docstring survives verbatim — a successful close still runs the shutdown exactly
once. A *failed* close now leaves the handle in the state it is actually in, so
a retry re-runs the closure. Safe because both steps the closure drives are
required to be idempotent: `GraphWriter.close` (now declared as such) and
`BackendStore.close` (which the registry already requires of a third-party
store).

### Documentation and DI-15.4-05

- `public/how-to/write-a-graph-backend-adapter.md` gains a paragraph under the
  contract table: #4 is checked, not merely asked for, and what happens if it
  is not met.
- `DI-15.4-05` is **narrowed, not closed**, with a dated note. The six private
  names it tabulates are untouched and still unavoidable. What changed is the
  class of the remaining gap: it is now entirely "private names an adapter must
  reach for", with no remaining known case of "a public name that says less than
  the runtime requires". The design question it poses is unchanged and open.

### Test design — why the F0 suite cannot repeat the defect

The brief was that F0's test must cover *every denied form for every deny
entry*, because testing one spelling is the defect. `test_import_spellings.py`
therefore derives its parametrization from the deny constants themselves:

- `denied_spellings(entry)` generates six forms for any entry, plus four more
  for a dotted one (the parent-named family that was open).
- `permitted_lookalikes(entry)` generates the near-misses that must stay clean.
- The cases are built from `HARNESS_DENY`, `VENDOR_LLM_DENY`, `LLM_MODULES`,
  `ADAPTER_TREE`, `ORCHESTRATION_TREE` and `BACKENDS_PACKAGE` at collection
  time, so **a new harness or vendor SDK arrives already covered in every
  form**, and a maintainer cannot add an entry and test only the spelling they
  happened to think of.
- `test_deny_sets_are_populated` guards the derivation itself — an emptied deny
  set would make every derived case vacuously pass, which is the `WR-03`
  `substrate_vocabulary` lesson applied to a test file.
- `test_a_module_in_neither_tree_is_untouched` pins the orchestration rule's
  early return — the exact behaviour that made the panel's own probe
  inconclusive — so the next reader finds it stated rather than rediscovers it.

This is the same reasoning that made `is_write_module` a predicate rather than
an enumeration, applied to the tests instead of to the rule.
