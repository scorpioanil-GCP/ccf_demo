## F1 — HIGH — third-party import failure echoed verbatim

**File:** `src/ccf/graph/registry.py`, `_load_third_party`.

`detail = f"{type(failure).__name__}: {failure}"` copied an installed
distribution's arbitrary exception text out of the handler, then interpolated
it into the public `ValueError`. Raising outside the `except` block correctly
cleared `__context__` and `__cause__` — it removed the *object* and kept the
*string*.

**Fix.** Keep the exception *type* only. `origin` already carries the declaring
distribution, its version, and the entry point's own `module:attribute` target,
which is the diagnosis for the two commonest cases (missing module, missing
attribute) without reading the stranger's prose at all.

**No debug-level log of the dropped text.** Considered and rejected in the
docstring: a log line is the same disclosure through a quieter door, and a
deployment shipping structured logs to an aggregator would have moved the
credential from one collection surface to another. `validate_connection` logs
nothing for the same reason. The residual is stated rather than claimed away —
an exception *class name* is still third-party text, but it is an identifier
rather than a rendered message, which is the whole of why it is the piece kept.

**Message tightened after CINV-01 fired** (`65abfc6`). The first version
explained the redaction policy inside the message itself: four sentences, 518
characters, which is two `cinv01a-prompt-shape` signals. Resolved by shortening
the message and naming the remedy as a backticked command — this module's own
house style, and what puts the literal in the lint's developer-diagnostic
category — not by an allowlist entry (CLAUDE.md §6.4).

**Test:** `tests/graph/test_backend_registry.py::test_a_third_party_load_failure_does_not_echo_its_own_message`.
A probe adapter whose module-level body raises
`RuntimeError("connection refused for postgres://svc:hunter2f1secret@db.internal:5432/graph while registering")`.
This is a third failure shape, distinct from the two already parametrized: a
missing module and a missing attribute raise with text *the interpreter* wrote,
so echoing them leaked nothing. This one raises with text a *stranger* wrote,
in the one place a stranger's code runs during resolution.

The test asserts in both directions, because a redaction test that only asserts
absence passes on an empty refusal:

- absent: the DSN, the password substring, and the third party's own phrasing,
  from both `str()` and `repr()`;
- present: the distribution, the adapter name, the exception type, and the
  "not installed" disambiguation;
- `__context__` and `__cause__` both `None`, so there is no chain to walk.

## F4 — MEDIUM — sequential cleanup skips the second step

**File:** `src/ccf/boot.py`. **Both sites fixed with `try`/`finally`.**

### Exact line changes in `boot.py` — for merge resolution

`src/ccf/boot.py` is contended with the agent closing F0/F3/F6. Two hunks, both
strictly inside the failed-`make_writer` handler and `shutdown()`. Neither
touches `FabricHandle.close` (lines 106–125), the `make_writer` call itself
(line 332), or anything F6 would move.

**Hunk 1 — `@@ -344,2 +344,13 @@`.** Replaces exactly two lines at old 344–345:

```python
-        release_boot_token(token)
-        store.close()
+        # (9 lines of comment, appended below the existing rationale block)
+        try:
+            release_boot_token(token)
+        finally:
+            store.close()
```

The pre-existing comment at old lines 334–343 is **unchanged**; the new comment
is appended after a `#` spacer. The `raise` at old line 346 is unchanged.

**Hunk 2 — `@@ -349,2 +360,12 @@`.** Replaces exactly two lines, the body of
`shutdown()` at old 349–350:

```python
-        writer.close()
-        store.close()
+        """(6-line docstring)"""
+        try:
+            writer.close()
+        finally:
+            store.close()
```

The `def shutdown() -> None:` line itself (old 348) is unchanged.

Net: `+22 -4` in `boot.py`, confined to old lines 344–350.

### Why this matters and what was preserved

The comment above the handler shows its author reasoning about ordering
explicitly — release the mint first, so a store whose `close` also raises
cannot leave the graph permanently unbootable. That rationale is correct and
survives unaltered; it reasoned about the *second* step raising. What it did
not consider is the *first* step raising, which skipped the second entirely and
leaked the store's connection — the exact leak the handler exists to prevent,
arriving through the handler itself. The new comment says exactly that.

`shutdown()` has the same shape and is the *ordinary* path: it is what
`FabricHandle.close` calls and what every `with handle:` block reaches on exit.
Since D-IMPL-93 the writer it closes first can be third-party, and
`FabricHandle.close` sets `_closed` before delegating — so one raise meant one
permanently leaked connection with no retry available.

**Tests:** `tests/graph/test_boot_cleanup.py`, a **new file** rather than an
addition to `test_boot_seam.py`, deliberately: `test_boot_seam.py` is where an
F6 regression test would most naturally land, and a new file has no merge
surface with the parallel agent.

- `test_a_release_that_raises_still_closes_the_store` — `release_boot_token` is
  replaced with one that raises, over an adapter whose `make_writer` raises.
  Asserts the store was closed anyway, and that the adapter's own failure is
  still readable on the raised exception's `__context__` rather than discarded.
- `test_a_writer_close_that_raises_still_closes_the_store` — a third-party
  writer whose `close()` raises *before* `BaseGraphWriter.close` runs (the
  harsher ordering: the mint is still held when the exception leaves). Asserts
  the store's connection is released anyway.

Both assert the store's own close *count*, not the shape of the source: "these
two lines are inside a `finally`" is a description of the code, "the connection
was released" is the property.

## F5 — LOW — a documented registry refusal returned 500

**File:** `runtime/ccf_runtime/http_api/routes/backends.py`.

`declared_names` documents four refusals. Three are `ValueError` subclasses;
the fourth — the SDK's own adapter package not being a readable directory
(`registry.py:424-438`, `:647`) — is a `RuntimeError`. The catch tuple had been
assembled from the three that shared a base class, so a zipped, frozen or
damaged install escaped as an unshaped 500.

**Catch-site reasoning preserved.** The existing comment explains why the three
are named individually rather than collapsed into the `ValueError` arm; it is
kept verbatim and extended with why the fourth is not one of them. The module
docstring's "When the registry refuses" paragraph is updated, and a new
paragraph records the finding.

It is the case where an unshaped 500 costs most: the remedy is
`pip install --force-reinstall` of *the SDK*, which is the one an operator
staring at a backend endpoint is least likely to guess.

**Test:** `tests/http_api/test_routes.py::test_backends_refuses_503_when_the_sdks_own_adapter_package_is_unreadable`.
Drives the **real** `declared_names` with only `_backends_directory` redirected
to a nonexistent path, rather than injecting a `RuntimeError` into the route —
an injected exception would assert the catch tuple's contents while proving
nothing about the path, which is the shape of mistake that let this through in
the first place. Asserts 503, the pinned literal error code, and that
`force-reinstall` and `not readable` survive into the body.

**Mutation:** removing `RuntimeError` from the tuple, the `RuntimeError`
escapes the ASGI app entirely rather than becoming a shaped response —
`E RuntimeError: the SDK's own adapter package is not readable at
/nonexistent/ccf-adapter-package-f5 ...` raised out of `registry.py:430`.

**No `openapi.json` drift.** `make openapi` regenerated; `git status` reports
the file unchanged. The status code, error code and body shape are all
unchanged — only the set of situations that reach them widened. The route
declares no `responses=` for 503, so nothing about the widening is describable
in the schema.

**The `ccf backends` CLI command reaches this route over HTTP**
(`runtime/ccf_runtime/cli/commands/backends.py:51` issues `GET /backends`), so
it inherits the fix with no CLI change. `src/ccf/deployment/manifest.py:292` is
the other `declared_names` caller; it is a preflight with no HTTP status to
shape, and a `RuntimeError` carrying an actionable message is the correct
behaviour there. Left alone deliberately.
