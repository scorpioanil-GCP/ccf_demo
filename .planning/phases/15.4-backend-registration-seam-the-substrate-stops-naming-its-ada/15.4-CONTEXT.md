# Phase 15.4: Backend Registration Seam — The Substrate Stops Naming Its Adapters - Context

**Gathered:** 2026-08-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Turn the dependency between the CCF core and its graph adapters around. Today
the core imports the adapters; after this phase the adapters register with the
core and the core never names one.

Concretely, all six existing backends (sqlite, postgres, memory, neo4j, mongo,
fluree) migrate behind a registry. Each backend declares its own name, factory,
required connection settings, and preflight rule. The core looks up instead of
branching. The eleven per-database keyword arguments on `_open_backend` collapse
into one configuration mapping. The six-name `Literal` in
`controlplane/artifacts.py` is replaced by a registry check.

Success is two structural properties, both lint-enforced:

1. No import of `ccf.graph.backends.*` from outside `backends/`.
2. No substrate name in core outside the registry.

**Dave's standing instruction for this phase, recorded verbatim in intent:**
build the *complete* seam, not a partial one that leaves CCF unable to
demonstrate what it can do. Half-measures were explicitly ruled out during
discussion — see D-02 and D-06 below for the two that were considered and
rejected on those grounds.

**Not in this phase:** anything that weakens operator purity, as-of correctness
(`INV-CH7-14`), single-writer (`INV-CH7-10`), or cross-substrate replay
determinism. Nor the cross-adapter FIBO demonstration — that is deferred work
with its own phase (see `<deferred>`).

</domain>

<decisions>
## Implementation Decisions

### Where per-backend write code lives

- **D-01: Two modules per backend.** `backends/<name>.py` holds reads;
  `backends/<name>_write.py` holds writes. Every backend follows the split,
  including `memory`.

  *Why this and not the alternatives.* All six backends' writer classes live
  today in one 3,200-line file, `src/ccf/graph/_writer.py`, and
  `tools/lints/harness_imports.py:92` enforces single-writer by saying that
  exactly one module — `ccf.graph._writer` — may only be imported from L2.
  That module imports all six backends (`_writer.py:96,133,142,152,156,157`),
  which is precisely what property (1) forbids. The write code therefore has to
  move, and the question was what happens to the lint when it does.

  With a dedicated write module per backend, the lint rule keeps its exact
  present shape: it guards write modules, and only L2 may import them. One
  rule, six files instead of one. Nothing about how single-writer is enforced
  has to be redesigned or re-argued.

- **D-02: Rejected — reads and writes in one file per backend.** The read module
  is imported by many callers, so the lint could no longer say "only L2 imports
  this file." The rule would have to shift from guarding a module to guarding a
  class, which is both weaker and harder to check statically. Single-writer is
  architectural (CLAUDE.md §10); trading a checkable rule for an
  approximately-checkable one is not an acceptable price for fewer files.

- **D-03: Substrate-neutral write machinery stays central.** `_writer.py`
  survives as the neutral base (`BaseGraphWriter`, the transaction seam, the SQL
  adapter shared by both SQL backends) minus every per-backend subclass. The
  lint guards it exactly as today, plus the six new write modules.

### How a backend announces itself

- **D-04: The manifest names the adapter in force; entry points make it
  findable.** Both, not either.

  The deployment manifest names the adapter — explicit, auditable, versioned,
  and pinnable in replay, which is how CCF records everything else that affects
  an answer. Python entry points let someone ship an adapter as a separate
  installable package that CCF finds without a line changing in this repo. That
  combination is what makes per-adapter cost genuinely zero rather than merely
  small.

  Note for planning: `pyproject.toml` declares **no** entry points today. This
  is CCF's first plugin surface, so the entry-point group name, its
  documentation, and its versioning are new ground rather than an extension of
  an existing pattern.

- **D-05: Third-party code is imported only when the manifest names it.**
  Discovery reads declared adapter names without executing anything. Only the
  adapter the manifest names is imported, at boot.

  Two consequences, both wanted. Nothing an installed package ships runs unless
  a deployment asked for it by name — the fail-closed posture CCF already takes
  elsewhere, now applied to a supply-chain surface that did not previously
  exist. And the optional `neo4j` and `pymongo` drivers stay unloaded when
  booting SQLite, preserving today's lazy-import behavior
  (`boot.py:191,211`) without a special case.

- **D-06: Rejected — importing every declared adapter at startup.** It would
  surface a broken adapter earlier, but at the cost of running arbitrary
  installed packages' module-level code at every boot. Not a trade CCF should
  make, and it would also undo the optional-extra deferral.

### Connection settings and secrets

- **D-07: Each adapter declares a typed config model; the registry validates it
  before boot.** A Pydantic model per adapter naming exactly what that adapter
  requires. A missing or misspelled setting fails at the boundary with a message
  naming both the adapter and the field.

  This follows CLAUDE.md §11 ("Typed contracts at every boundary. Validation is
  at the boundary, never deferred") and preserves something the current code
  does deliberately: `_preflight_backend` (`manifest.py:255-266`) refuses a
  manifest whose declared backend lacks its connection argument, and refuses a
  credential supplied for a backend that was not selected. That behavior must
  survive the migration — it moves into the adapter's declared model rather than
  the hand-maintained dictionary it lives in now.

- **D-08: The manifest holds references to secrets, not secrets.** A manifest
  names an environment variable; boot resolves it. One mapping, so the shape
  stays uniform, and the manifest still contains no credential.

  This is a net improvement over today rather than a lateral move. Right now
  `fluree_bearer_token` and the database passwords travel as separate boot
  arguments precisely so they are never persisted — safe, but invisible: nothing
  in the versioned record says which credential a deployment used. A named
  reference is auditable, and replay can pin *which reference was in force*
  without ever recording what it resolved to.

  Planning must confirm the resolved value never reaches a log, a replay record,
  an error message, or a manifest. `backends/fluree.py:678-679` documents the
  current no-persistence guarantee and is the reference point for what must not
  regress. Note that Phase 15.3 code review found a real defect in exactly this
  area (WR-02/WR-03: a credentialed Fluree URL connected anonymously because
  `httpx` derives no header from `base_url` userinfo) — credential plumbing in
  this codebase has bitten once already.

### Consequences that follow from the above (not separately discussed)

- **D-09: Replay pins the adapter.** Once an adapter can be a third-party
  package, which adapter and which version answered is something that affects
  the answer, so CCF pins it. Adapter name, adapter version, and the *names* of
  any secret references in force — never a resolved secret value. Planning
  decides which replay dimension carries it; the existing backend pin in
  dimension 2 (per 15.2-08) is the natural home.

- **D-10: The public API break is pre-authorized; the migration note is owed.**
  `boot()` and `load_and_boot()` lose their per-database keyword arguments
  (`manifest.py:288-294`). **D-15B** grants free rein on the public API pre-1.0
  (`pyproject.toml` version is `0.1.0`) on the explicit condition that adopters
  get a migration, and `docs/SURFACE-CHANGES.md` is where that migration is
  written. This phase owes an entry there.

  Known call sites that must migrate: `tests/graph/test_fluree_backend.py:1706-1707`
  asserts `fluree_bearer_token` is present in both signatures — that assertion is
  now false by design and must be rewritten, not deleted, so the guarantee it
  was protecting (a token reaches the backend) still has a test.
  `tests/conftest.py:343,351` supplies `neo4j_partition` / `mongo_partition`.

- **D-11: Proof is an out-of-tree adapter, not an in-tree seventh backend.**
  The evidence that per-adapter cost is zero should exercise the path an actual
  third party would take: a minimal adapter living outside `src/ccf` entirely,
  registered through entry points, that passes the existing conformance suite.
  An in-tree seventh backend would only prove the in-repo path, which is the
  weaker claim.

  Alongside it, the unchanged bar: four database test legs green, and
  `tests/conformance/query_corpus.py` byte-untouched. Per D-IMPL-93's own
  standard, "the corpus grew" is recordable and "the SDK bent" fails.

- **D-12: The six-name `Literal` becomes a plain string checked against the
  registry at boot.** (`artifacts.py:975`.) A *generated* list was considered
  and rejected: generated or not, it is still six database names sitting in a
  core file, which is the thing property (2) forbids.

  Verified during discussion, so planning need not re-check it: there is no
  exported JSON Schema file in the repo, and `DeploymentManifest` is
  content-addressed by its file bytes rather than by its model schema. Dropping
  the `Literal` therefore does not disturb existing manifests or their replay
  pins. The only cost is one-directional — a typo is caught at boot rather than
  at parse — and it is paid back by an error message that can name what *is*
  registered, which the `Literal` never could.

### Claude's Discretion

- The entry-point group name and the registry's internal structure.
- How `_writer.py`'s neutral base is split from the per-backend subclasses,
  provided D-01 and D-03 hold.
- Which lint module the two structural checks live in — extending
  `tools/lints/harness_imports.py` or adding a sibling. The requirement from
  D-IMPL-93 is only that it is the same machinery, and that
  `tools/lints/allowlist.yaml` governs any exception.
- Plan sequencing and wave structure.

<code_context>
## Existing Code Insights

### Reusable assets

- **`tools/lints/harness_imports.py`** is the machinery D-IMPL-93 names. It
  already walks `src/` resolving import statements and reporting violations with
  file and line, and already implements exactly the rule shape both new checks
  need: "module X may only be imported from Y." The two structural properties
  are new rules in a proven walker, not new machinery.
- **`tools/lints/allowlist.yaml`** is the established place for a declared
  exception, so any unavoidable carve-out has a home that is reviewed rather
  than invisible.
- **`_preflight_backend`** (`manifest.py:216-266`) already encodes, as data,
  precisely what D-07 turns into per-adapter declarations: which connection
  argument each backend requires, and that `memory` requires none. The mapping
  at lines 261-266 is the registry's content in dictionary form — the migration
  is largely relocating knowledge that is already declarative.
- **The four-substrate CI legs** (postgres 25, neo4j 20, mongo 22, fluree 37
  tests) plus the differential suite are the migration's regression net. They
  were built in 15.2/15.3 to prove adapters agree; here they prove six adapters
  still agree after moving.

### Established patterns this phase must respect

- **Explicit selection, never inference.** `_open_backend`'s docstring states
  the rule: a fabric that guessed its own substrate could silently boot against
  a development SQLite file in production and still pass every test. The
  registry must keep selection explicit — a name in the manifest — and never
  fall back to a default because a setting was absent.
- **Fail-closed refusals as returned values.** Gate refusals are returned;
  exceptions are reserved for broken deployments (Phase 04 decision). An
  unregistered adapter name is a broken deployment, so it raises — but the
  message must name what *is* registered.
- **Optional extras stay optional.** `neo4j` and `pymongo` are extras; boot must
  stay importable and every other backend bootable without them
  (`boot.py:151`). D-05 preserves this by construction.
- **Fluree's import shape is deliberately different.** `httpx` is a core pin, so
  Fluree imports at module top with no lazy deferral, as SUBQ-14 evidence. The
  registry must not flatten this distinction into "all adapters load the same
  way" — the difference is a recorded claim.

### Integration points

- `boot()` → registry lookup replaces `_open_backend`'s branch cascade.
- `load_and_boot()` → per-database arguments become one mapping (D-10 break).
- `DeploymentManifest.backend` → plain string plus registry validation (D-12).
- `_preflight_backend` → per-adapter declared config models (D-07).
- L2's writer acquisition → registry-supplied factory; the write handle still
  reaches only L2 (D-01, D-03).

<specifics>
## Specific Ideas

- **Complete, not partial.** Dave's explicit instruction. Two half-measures were
  raised and rejected on this basis: exempting `_writer.py` from the
  no-backend-import rule (which would leave per-adapter churn exactly where
  D-IMPL-93's recurrence test forbids it), and keeping the per-database keyword
  arguments as deprecated pass-throughs alongside a new mapping (which would
  leave adapter names in the public surface). Neither should reappear during
  planning as a de-risking measure.

- **Communication standard for this phase.** Dave asked for tightly written,
  plain sentences and materially less jargon in anything surfaced to him.
  Applies to plans, summaries, and the gate package, not only to conversation.

## Deferred Ideas

### Cross-adapter FIBO demonstration — Dave's existing asset, for a later phase

Dave has stood up four live databases on **192.168.4.76**, each loaded with the
same FIBO ownership data, plus a working driver that asks one logical question
four ways and prints a presence matrix showing the answers agree.

**What exists** (`/home/parkave/fluree/examples/fibo/`):

| File | What it does |
|---|---|
| `compare_backends.py` | The driver. One ownership query, four backends, normalized to `(owner, company)` pairs, presence matrix output. |
| `load_neo4j.py`, `load_postgres.py`, `load_mongo.py`, `fluree_to_mongo.py` | Loaders for each store. |
| `fibo-instances.json`, `fibo-export.json`, `*.ttl` | Source data. |

**Connection details** (all overridable by environment variable):

| Store | Endpoint | Shape |
|---|---|---|
| Fluree | `http://192.168.4.76:8090`, ledger `fibo:main` | SPARQL over `/v1/fluree/query` |
| MongoDB | `mongodb://192.168.4.76:27017`, db `fibo` | `entities` + `relationships` collections |
| Neo4j | `bolt://192.168.4.76:7687` | `:KGEntity` nodes, `HAS_OWNERSHIP_INTEREST_IN` edges |
| PostgreSQL | `192.168.4.76:5432`, db `parkavedb`, user `parkave` | `entities` + `relationships` tables |

Passwords come from `NEO4J_PASSWORD` / `PGPASSWORD` and are empty by default.
Dave covered four of the six backends deliberately — the ones he judged most
challenging.

**The distinction that decides which phase can use this.** Each store holds a
**hand-built layout**, not CCF's. CCF's tier-1 adapters own their storage
layout; CCF writes it. So there are two genuinely different demonstrations
available here, and they are not interchangeable:

1. **Load FIBO through CCF's own ingest into all four stores**, then ask one
   Context Product question and show four substrates return identical bytes.
   This is the stronger claim, and it is the one that shows what CCF adds:
   Dave's driver proves four *hand-written* queries agree; CCF would prove one
   query, translated four ways by the adapters, agrees — with lineage,
   attestation, and replay intact. Requires CCF ingest of the FIBO data and a
   CCF-layout load into each store.
2. **Treat the existing native layouts as external sources** — the tier-3 case
   Phase 15.2 designed for and explicitly deferred ("must not require a refactor
   to add", Dave, 2026-08-07). This exercises a different seam entirely.

Both are worth doing; they belong to different phases. Neither is Phase 15.4.
Dave's instruction: *"document this for your testing and example code in an
upcoming phase so that we can leverage what has been done to fully appreciate
the power of CCF across disparate adapters."*

Note for whoever plans it: this is also the natural home for the out-of-tree
proof adapter from D-11 to graduate from a minimal conformance shim into a real
demonstration.
