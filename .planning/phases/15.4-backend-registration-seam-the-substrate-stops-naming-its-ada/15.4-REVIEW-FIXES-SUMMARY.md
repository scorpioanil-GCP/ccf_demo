## Accomplishments

- **CR-01** — `boot()` no longer leaves a graph permanently unbootable when a third-party writer constructor raises. The store is closed and the graph is released, so a corrected retry boots instead of being refused as a second writer.
- **CR-02** — both CINV-02 import rules now see `from ccf.graph import _writer` and `from ccf.graph.backends import sqlite_write`. Before this, any module under `src/` or `runtime/` could reach `mint_boot_token` and name a concrete writer class with zero findings, and one adapter's reader could name another adapter's write module with zero findings.
- **CR-03** — duplicate-adapter discovery fails closed on the two states it used to accept: one distribution name at two versions pointing at different modules, and two declarations with no distribution metadata. Both previously let the fabric pick an adapter by metadata iteration order and write that arbitrary winner's version into Decision Replay as fact.
- Seven warnings closed, each with a test: an unauthenticated endpoint no longer discloses distribution versions; the substrate-name checker refuses rather than silently passing everything when it cannot read its vocabulary, and stops firing on `"in-memory"`; Mongo's buffered `seq` is scoped like Fluree's; `ResolvedSecret.field` is actually reconciled; a broken third-party declaration is a typed refusal; `FabricHandle.close` is idempotent and `BackendStore` says so is required; the `make_writer` scan counts references rather than only calls.

## The three blockers

### CR-01 — a failed boot left the graph unbootable

`mint_boot_token` adds a graph identity to `_LIVE_WRITERS` and only
`BaseGraphWriter.close()` ever removes it. `registration.make_writer(store, token)`
sat between the mint guard above it and the worker guard below it, protected by
neither — and since D-IMPL-93 that call is a callable an arbitrary installed
distribution supplied. If it raised, the store's connection leaked with no object
returned that a caller could close, and the graph stayed marked as having a writer
that did not exist. `boot.py`'s own comment names that outcome as the thing that
must not happen; the guard it wrote for it started one line too late.

`release_boot_token` was added to the neutral write base — beside the mint it
undoes, inside the one module that owns `_LIVE_WRITERS`, and with no widening of
who may mint. `boot()` wraps the constructor in the same guard shape the mint
above it already had, releasing the mint before closing the store so a store whose
own `close` raises cannot make things worse.

**Regression test:** `tests/graph/test_boot_seam.py::test_a_failing_writer_constructor_closes_the_store_and_frees_the_graph`
boots a probe adapter whose writer constructor raises over a store with a fixed
graph identity, then asserts the store was closed and that a corrected retry over
the same graph boots.

**Mutation check:** with the guard body removed the test fails on
`assert probe.OPENED[0].closes == 1` → `assert 0 == 1`. Restored and re-verified.

### CR-02 — both import rules were blind to one spelling

`imported_module_names` returns `[node.module]` for an `ImportFrom` and discards
the alias names, so `from ccf.graph import _writer` reported `ccf.graph` and
matched nothing. Two holes followed, and each made a written claim false:

- `harness_imports.py`'s "even with a writer implementation on disk, no other
  module can name it" — any module could, through that spelling.
- `backends/__init__.py`'s claim that a reader importing its sibling writer is
  structurally prevented, because "every importer of the reader would transitively
  reach write code and the rule would flag the reader itself" — `backend_imports`
  exempts everything inside the adapter package and the writer rule saw only
  `ccf.graph.backends`, so nothing flagged anything.

`submodule_import_names` was lifted from `harness_imports` into `tools/lints`
beside the helper it supplements, `reached_module_names` was added for the union,
and both rules now read it. Each reports at most one finding per import statement
rather than one per spelling, on the precedent `cinv02-deployment-gates` already
set. The `backend_imports` finding now names the most specific module the
statement reaches. The mirrored regex in
`tests/invariants/test_single_writer_boot.py` — which had the same blind spot and
so could not have caught this either — was widened to three spellings.

**Regression tests:** five negative controls across
`tools/lints/tests/test_harness_imports.py` and `test_backend_imports.py`, plus
two positive controls proving a write module may still name its own reader and the
base through the package spelling.

**Mutation check:** with `reached_module_names` reduced to
`imported_module_names`, five tests fail. Restored and re-verified.

### CR-03 — the duplicate refusal failed open

The check compared `_distribution_of(previous) == _distribution_of(entry_point)`
— the distribution **name** — and `continue`d on a match, on the premise that
"both declarations name the same code". Two reachable states are not that:

- **Two metadata directories for one distribution name at different versions,
  pointing at different modules.** The ordinary failed-uninstall state. `matches[0]`
  took whichever the iterator yielded first, and the `AdapterPin` written into
  Decision Replay dimension 2 recorded that arbitrary winner's version as fact.
  `_version_of` was available at the comparison site and simply not consulted.
- **Two declarations with no distribution metadata.** Both return the
  `UNKNOWN_DISTRIBUTION` sentinel, so "same distribution" compared two sentinels
  rather than two facts — a fail-open on precisely the bad-metadata class the
  fail-closed ruling is written about.

`_is_one_declaration_twice` now passes over a duplicate only when it is provably
one declaration — one distribution, one version, one target — and never when the
declaring distribution could not be identified. `_duplicate_refusal` takes the
shape that fits the failure: two distributions is "uninstall one", one
distribution declaring itself twice is "this environment's metadata is
inconsistent", which no uninstall of a rival package can fix. The unchecked
`matches[0]` on a second metadata scan in `resolve` is gone; the declaration
`_declared()` already resolved is used instead, which also removes one of the
scans IN-01 counts.

**Regression tests:** `tests/graph/test_backend_registry.py` gains
`test_one_distribution_name_at_two_versions_is_refused_not_chosen_between`,
`test_two_declarations_with_no_distribution_metadata_are_refused`, and
`test_one_distribution_declaring_one_name_twice_at_one_target_is_passed_over` —
the third so the fix stays a discrimination rather than a widening. The first also
asserts neither candidate was imported, because a refusal that arrives after
loading one of them has already run a stranger's module-level code.

**Mutation check:** with the name-only comparison restored, the first two fail
with `DID NOT RAISE DuplicateBackendName`. Restored and re-verified.

| **WR-04** | `GENERIC_WORD_STEMS` matches a listed stem as a whole token only, so `"in-memory"` and `memory_budget` in an unrelated module are silent while `BACKEND = "memory"` still fires. | **WR-06** | Both Mongo `seq` sites use the scoped `sum` `fluree_write` already uses, with cross-references so the two read as one decision. |
| **WR-07** | `FabricHandle.close` is guarded; `BackendStore.close` states the idempotency requirement a third-party adapter author previously had to discover by reasoning about a bug. |
| **WR-08** | An unreadable adapter package raises rather than reporting an empty built-in set, so the operator stops being told to install a distribution when the SDK's own package could not be read. |
| **WR-09** | `_refuse_undeclared_secrets` refuses a credential whose record names a field other than its mapping key. `ResolvedSecret`'s docstring now says the reconciliation is performed rather than merely possible. |
| **WR-10** | The scan counts references — attribute loads, the `getattr` string form, bare-name calls — rather than only calls, so `factory = record.make_writer; factory(...)` no longer walks past. Its remaining scope is stated in its own docstring. |
| **IN-02** | The parity suite's docstring now states the boundary: an installed third-party adapter turns it red, that is the rule working as ruled, and here is what to do. |

**WR-01's resolution, stated because it took a judgement.** The finding offers two
remedies: correct the docstring, or narrow the message. Narrowing was preferred and
is what was done — but it was done in the **registry**, not at the route. The route
forwards `str(conflict)` verbatim, so the property has to hold where the message is
built or it holds nowhere, and the same messages reach the CLI and an operator's
logs. The registry's own argument for it is not an HTTP argument: `declared_names()`
is the *listing* function, so anything that can ask what adapters a deployment has
reaches these refusals. One claim in the route docstring could not be narrowed and
was corrected instead — the body carries one distribution name for a reserved or
malformed name and up to two for a duplicate, and a duplicate refusal that named
only one of the two would be unactionable.

**WR-04's resolution, likewise.** The finding offers (a) deriving the vocabulary
from registered adapter names rather than file stems, or (b) a minimum-distinctiveness
rule with a stated escape. Option (a) was rejected on measurement: the collision is
`memory`, and the memory adapter *registers* the name `memory`, so reading
`REGISTRATION.name` off the AST changes nothing about the false positives. The two
false positives (`"in-memory"`, `memory_budget`) are also lexically indistinguishable
from the true positive the loose boundary exists to catch (`memory_dsn`), so no
boundary tightening separates them. Option (b) is what shipped, scoped to the
colliding word so the loose boundary survives everywhere else. D-13 is respected:
this is a named constant reviewed with the code, it narrows how one word matches
rather than exempting any module, and adding an entry is a code change.

**Mutation checks on the warning fixes.** WR-03: with both raises disabled, two
tests fail with `DID NOT RAISE`. WR-04: with the strict-pattern branch removed,
four tests fail. WR-07: with the `_closed` guard removed, the store records three
closes instead of one. All restored and re-verified.

### Rejected

**WR-05 — "Neither new lint checker has a test of any kind."** Checked and
**false**. `tools/lints/tests/test_backend_imports.py` has 11 test functions and
`tools/lints/tests/test_substrate_names.py` has 20, both created in plan 15.4-01
and merged. The finding's own `grep` looked in `tests/` and `examples/`; the lint
checkers' tests live in `tools/lints/tests/`, which is where every other checker's
tests live and which CI runs as its own step (`.github/workflows/ci.yml:35`). The
minimum set the finding asks for was already present, including the "rule fires on
`from ccf.graph import _writer`" case it predicted would be red — which is how
CR-02 could have been caught, except that the existing test asserted the *backend*
rule fires on it, and the backend rule did (via the package name), while the
writer rule silently did not.

**One observation that follows.** `make ci-core` does not reproduce CI's lint job
in full: CI runs `pytest tools/lints/tests -q` before `python -m tools.lints --all`,
and `ci-core`'s `test` target is `pytest -q` with `testpaths = ["tests"]`. So the
lint checkers' own tests are gated in CI but not by the local sweep — which is
plausibly why a reviewer looking at a local run concluded they did not exist. Both
were run explicitly here (141 passed). Changing `ci-core`'s composition is outside
this pass's scope; recorded so the next person does not repeat the inference.
