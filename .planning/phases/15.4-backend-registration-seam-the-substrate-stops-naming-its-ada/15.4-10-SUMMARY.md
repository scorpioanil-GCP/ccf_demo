## What Was Built

### Task 1 — the distribution, the dict store, and the reader (`8a9b6bc`)

`tests/fixtures/ccf-demo-adapter`, a distribution named `ccf-demo-adapter` at
0.1.0, `src` layout, one package, declaring:

```toml
[project.entry-points."ccf.graph_backends"]
demo = "ccf_demo_adapter.demo_write:REGISTRATION"
```

It lives under `tests/` rather than `examples/` so it stays out of
`make examples`, and the pyproject comment records that moving it later should
be a deliberate step rather than an accident of where it started.

**The store is two flat dicts, and the unlikeness is the design.** `nodes` is
keyed `(tenant_id, kind, node_key)` and `claims` is keyed
`(tenant_id, kind, node_key, claim_id)`, with each claim carrying its own
lineage inside it. The nearest in-tree adapter mirrors five relational tables
per tenant; copying it would have proven the copy works, not that the seam
works. Tenant scope and compound uniqueness are properties of the key here,
rather than of a nesting level.

**Rows are objects.** `_Claim` satisfies the `Row` Protocol through
`__getitem__`, mapping both axes' node-key column names onto the one name this
store keeps. Both reference adapters hand the shared core dicts; doing it once
with something that is not a dict is what makes `Row` demonstrably a Protocol.

**Graph identity is derived from an explicit `graph_name`**, the way the SQLite
adapter derives its identity from a database path — and, for the same reason,
named graphs are shared per process with handle refcounting. Two stores on one
name are two handles on one graph and share state; two names are two graphs; the
last close discards the graph. Without the sharing, an identity claiming
`same graph` over separate state would make the second boot's refusal an
artefact rather than the invariant working.

**The reader declines pushdown for every query.** There is no translation branch
and no `_translate_query` attribute at all. Rows are narrowed by tenant and the
as-of row filter, materialized through the shared core, handed to the shared
fallback for the predicate families and survivor set, and frozen through the
interface's ordering.

### Task 2 — the write module, the transaction, and the record (`d51f316`)

`DemoConnection` takes one required `graph_name` and inherits `extra="forbid"`
plus `frozen=True` from the contract base rather than re-declaring them.
`secret_fields` is empty; there is nothing here to authenticate to.

`_DemoTxn` implements the nine typed operations natively, written against the
seam's own contract rather than transcribed from an in-tree adapter. Both
contract rules hold: rowcounts resolve before commit (a re-arrival returns 0,
which is the writer's whole idempotency signal), and reads see the
transaction's own operations. All-or-nothing comes from a deep copy taken on
first touch and restored **in place**, because the store and its reader hold a
reference to the same state object.

One deliberate strictness: `insert_lineage` **raises** when the claim it is
given does not exist, rather than returning 0. Every caller writes lineage
against a claim it has just appended or just matched, so an absent one is a
defect in the write path — and returning 0 would report it as a duplicate entry
and lose the evidence silently.

The module docstring states **both halves** of the CINV-02 position, rather than
one implying the other: the lint's tree scope cannot reach a third-party
adapter, and the single-writer invariant does not need it to, because the
mechanism is the boot-token mint.

## The install posture, ruled

**Always-on, not opt-in.** The alternative — an opt-in
`make install-demo-adapter` with CI always installing it — was rejected for one
concrete reason: plan 15.4-11 adds a parity test asserting that the conformance
param lists and `declared_names()` agree **in both directions**. Under opt-in, a
developer who ran `make install` and then `make ci-core` gets a red parity test,
because `demo` is a param and is not installed. The proof would then be
conditional on a step nothing reminds anyone to take, which is the failure mode
that parity test exists to close.

The accepted cost is visible: every development checkout and every CI runner
reports a seventh name from `ccf backends list`. It is bounded because the
fixture is not a dependency of the `ccf` distribution, and that is now a **test**
rather than a sentence — `test_the_sdk_distribution_does_not_depend_on_the_fixture`
reads `pyproject.toml` and asserts the fixture appears in no dependency list,
with a non-vacuity check that the lists were really read.

Recorded in `tests/fixtures/ccf-demo-adapter/README.md` and in the `make install`
recipe comment. **Plan 15.4-12 should carry it into the gate package under
discretionary choices, with the alternative named** — that package does not exist
yet, so this summary is the handoff.

## Findings — reported, not fixed

The plan's standing instruction was that anything requiring an edit to
`src/ccf` is a finding about the seam rather than a fix to apply. Three surfaced.

### 1. Six names an out-of-tree adapter needs are not exported

Classified programmatically against each module's `__all__` rather than by eye:

| Name | Module | Status |
| --- | --- | --- |
| `materialize_view` | `ccf.graph.reader` | not in `__all__`, docstring says "Graph-tier internal API" |
| `_ordered_view` | `ccf.graph.reader` | private |
| `_entity_records` | `ccf.graph.reader` | private |
| `_relationship_records` | `ccf.graph.reader` | private |
| `_LineageRowsFor` | `ccf.graph.reader` | private |
| `_GraphTxn` | `ccf.graph._writer` | private, in a private module |

Everything else the adapter imports is public: `Row`, `ENTITY_KIND`,
`RELATIONSHIP_KIND`, `fallback.answer`, `BaseGraphWriter`, `BootToken`,
`BackendRegistration`, `BackendStore`, the five contracts from
`ccf.graph.protocols`, `canonical_timestamp`, `CCFContract`.

**None of them is avoidable.** `_ordered_view` cannot be replaced by
constructing a `GraphView` locally, because ordering "belongs to the interface,
never to an answerer" — an adapter that sorted for itself would fork the
convention the shared helper exists to hold. `_entity_records` and
`_relationship_records` have no public counterpart at all, so
`entity_history` and `relationship_history` are unimplementable from public
names. `BaseGraphReader` **is** public but is SQL-shaped: it wants five SQL
`ClassVar` statements and a `_query(sql, params)`, which a dict store cannot
supply.

So D-11's claim holds exactly as written — no line changed in `src/ccf` — while
the surface a third-party adapter must reach for is not the public surface. That
is a gap between the two, and it is worth a decision rather than a docstring.

### 2. The `ccf` distribution name is taken on PyPI by an unrelated project

Measured during execution: `pip index versions ccf` reports an unrelated
project at 7.0.12. This repository's `ccf` is 0.1.0, private and unpublished.

The consequence lands on exactly the population this plan exists to represent: a
third-party adapter's natural spelling is `dependencies = ["ccf"]`, and in any
environment without the local editable install that resolves to somebody else's
package rather than failing. This fixture therefore declares no dependencies at
all, with the reasoning in its pyproject comment and README, and relies on
install ordering plus a loud `ImportError`.

Nothing in this plan can fix it. It is a naming decision for the phase gate,
and it is upstream of anything an adapter author can do.

### 3. Derived parameter lists absorbed a genuinely third-party adapter — with no edit

The positive finding, and it is the one plan 15.4-04's summary predicted.
`tests/deployment/test_adapter_config.py` gained six `[demo]` parameters on
arrival, all passing, because its adapter list comes from `declared_names()` and
its driver list from `pyproject.toml`'s extras. That summary's claim — "a
seventh substrate and its extra are covered on arrival" — was tested here
against a substrate the SDK does not contain, which is a stronger case than the
one it was written for.
