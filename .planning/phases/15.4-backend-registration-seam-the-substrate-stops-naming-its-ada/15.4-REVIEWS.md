## Gemini Review

# Plan Review: Phase 15.4 — Backend Registration Seam

## Summary
The plan set for Phase 15.4 is exceptionally well-structured and technically rigorous. It successfully addresses the core objective of inverting the dependency between the CCF core and its graph adapters, moving from a hard-coded branch cascade to a dynamic registry. The strategy of using AST-based lint rules (Property 1 and 2) as both final gates and interim validation tools (by calling them directly in Wave 2–5 plans) is a highlight. The plans proactively correct two false premises from the initial context (the existence of a schema and the absence of a replay pin), showing high attention to the current state of the codebase. The "zero-cost" proof in Plans 10 and 11 is handled with mathematical precision through the use of an out-of-tree adapter and anchored git diff measurements.

## Strengths
- **Proactive Structural Validation:** Writing the lint rules in Wave 1 (Plan 01) but only registering them globally in Wave 6 (Plan 07) is a sound approach for a major refactor. Crucially, the plans bridge this "enforcement window" by calling the lint functions directly in the acceptance criteria of Wave 2–5 plans (e.g., Plan 05 Task 1 calling `substrate_names.check` directly).
- **Registry Security & Discovery:** Plan 02 correctly identifies and mitigates the "shadowing" risk where a third-party package could claim a built-in name (`sqlite`, etc.) by using `.select(name=...)` instead of a dictionary lookup and implementing explicit refusal of duplicate/reserved names.
- **Mechanical Precision in the Writer Split:** Plan 03's split of the 3,215-line `_writer.py` is based on measured AST spans (identifying line 973 as a clean split point), which significantly reduces the risk of accidental behavior changes during the relocation of 2,230 lines of code.
- **Secret Hygiene:** The plan set is paranoid about credential leaks in a healthy way. Using `SecretStr` for values and environment-variable *references* in the content-addressed manifest (Plan 06) ensures that credentials never reach the Control Plane audit trail or Pydantic validation error messages.
- **"Meta-Testing" for Conformance:** Plan 11 Task 1 adds a parity test (`test_param_registry_parity.py`) to ensure that the hand-written parameter lists in the conformance suites match the registry. This eliminates the risk of a "green" proof that passes simply because it wasn't executed.

## Concerns

### 1. Verification of the `ADAPTER_BASE` Anchor (LOW)
Plan 10 Task 1 and Plan 11 Task 2 rely on a manually recorded `ADAPTER_BASE` SHA to measure the zero-cost substrate addition.
*   **Risk:** In a non-interactive/CI environment, there is a risk that the SHA captured in the Plan 10 summary might be mis-recorded or drift if the environment state changes between Wave 6 and Wave 7.
*   **Mitigation:** Plan 11 Task 2 already includes a cross-check against a derived SHA (`git rev-list ... | head -1 | ^`). This is sufficient, but ensuring the SHA is captured *immediately* after the Wave 6 merge is vital.

### 2. Staleness of Build Metadata (LOW)
Plan 10 Task 3 correctly identifies that entry points live in build-time metadata (`.egg-info` or `dist-info`) and requires a `make install`.
*   **Risk:** If a developer or CI runner skips the install step after a branch switch that adds/removes an entry point, discovery will fail in a way that looks like a code bug.
*   **Mitigation:** The plan's instruction to prefer in-package registration for built-ins (Plan 02) and explicit install steps in CI/Makefile (Plan 10) adequately covers this.

### 3. Reachability of `make_writer` (LOW)
Plan 02 Task 2 notes that `BackendRegistration.make_writer` is now a public field, potentially widening the access to writer constructors beyond the `cinv02-graph-writer` lint's static checks.
*   **Risk:** A core module could theoretically obtain a writer factory via `registry.resolve(name).registration.make_writer` without triggering the import lint.
*   **Mitigation:** The plan handles this by adding an AST-based test in `tests/graph/test_backend_registry.py` that scans the entire tree for *calls* to `make_writer`, limiting them to `boot.py`. This is a sophisticated and appropriate compensating control.

## Suggestions
- **Plan 06 Task 1 (Schema):** When running `make schemas` after dropping the `Literal`, explicitly verify that the `docs/schemas/ccf.deployment-manifest.json` file is actually modified as expected (enum removed, pattern added) before committing. A "no-op" schema generation would indicate a Pydantic model configuration issue.
- **Plan 07 Task 2 (Gate Retirement):** When deleting `tools/gates/gate_15_3.py`, double-check for any `TODO` or `FIXME` comments in other files that point to this gate, as they will become dangling references.

## Risk Assessment: LOW
The risk is low because:
1.  **Exhaustive Regression Net:** The plans run the full "four-substrate" container legs (postgres, neo4j, mongo, fluree) multiple times, including after the massive code move in Plan 03.
2.  **Structural Enforcement:** The invariants are not just aspirations; they are enforced by code (registry refusals) and CI (AST lints).
3.  **Self-Correcting:** The research phase found errors in the commissioning premises and the plans explicitly incorporate those corrections (C-01, C-02).
4.  **Demonstrability:** The out-of-tree adapter proof (Plan 10/11) provides empirical evidence that the architectural goal (zero-cost addition) has been met.

## Codex Review

**Summary**

The plan set is strong and unusually explicit about invariants, verification, and migration risk. It likely achieves the main architecture goal: core code stops statically importing graph adapters, backend-specific config moves into adapters, and an out-of-tree adapter proves the seam. The main remaining risks are not in the broad direction but in a few contract mismatches and sequencing holes: the secret-reference pin cannot be produced from the proposed `boot()` signature, the registry/config-validation API is referenced before it is actually specified, and Wave 2 can temporarily expose built-in adapter names before they are resolvable.

**Strengths**

- The phase goal is kept structural: lints replace line-budget proxies, and the plans repeatedly check that names and imports are gone from core.
- Single-writer gets real attention: `_LIVE_WRITERS` stays central, write modules are guarded, and the `make_writer` widening is recorded instead of hidden.
- Plugin threat modeling is solid: discovery avoids imports, duplicate/shadowed names are refused, optional drivers remain lazy, and the out-of-tree proof uses entry points.
- The plan treats generated artifacts and public surface drift as first-class gates, which is important for a phase with public API breaks.
- V8 is correctly framed as a history measurement, not just a test result.

**Concerns**

- **HIGH — Secret-reference pinning is underspecified and currently inconsistent.**  
  In 15.4-05 Task 1, `boot()` takes `secrets: Mapping[str, SecretStr]`, and `FabricHandle.adapter` is supposed to carry secret reference names. But a `SecretStr` value mapping contains field names and resolved values, not the environment variable reference names from 15.4-06’s `backend_secrets`. Unless `boot()` also receives reference metadata, it can only pin `"bearer_token"`, not `"CCF_FLUREE_TOKEN"`. This weakens D-08/D-09 and V15.

- **HIGH — The registry config-validation wrapper is assumed but not actually defined.**  
  15.4-04 Task 3 says “the wrapper the registry provides produces a message naming both the adapter and the field,” and 15.4-05 Task 1 says boot should “let the registry’s wrapper produce the refusal.” But 15.4-02 only exports `declared_names()` and `resolve()`, and `BackendRegistration` has no `validate_config`/`validate_connection` API. This is a real implementation gap around V11/V12 and the no-secret-in-error-message requirement.

- **MEDIUM — Wave 2 can leave the public registry in a broken intermediate state.**  
  15.4-02 creates public `declared_names()`/`resolve()`. 15.4-03 then creates `backends/*_write.py`, so `_builtin_names()` can discover built-in names before 15.4-04 adds `REGISTRATION`. If 15.4-02 lands before 15.4-03, then after 15.4-03 `declared_names()` may list adapters that `resolve()` cannot load. Either force 15.4-03 before 15.4-02, merge 03+04 together, or add placeholder registrations in 03.

- **MEDIUM — The V8 zero-cost measurement is measured but not gated.**  
  15.4-11 Task 2 runs `git diff --stat <ADAPTER_BASE>..HEAD -- src/ccf`, but `git diff --stat` exits 0 even when output is non-empty. The acceptance criteria require empty output, but the automated verify will not fail. For the phase’s headline claim, this should be a hard gate using `git diff --quiet` after printing the stat.

- **MEDIUM — Generated-file verification commands appear commit-state dependent.**  
  15.4-06 Task 1 uses `make schemas && git diff --exit-code -- docs/schemas/`; 15.4-09 similarly uses `make openapi && git diff --exit-code -- openapi.json`. These only pass after the regenerated files are already committed or if no change occurred. If the execution workflow verifies before commit, these will fail on the exact plans that intentionally change generated artifacts. Clarify the workflow or change verify to compare regenerated output after staging/commit.

- **MEDIUM — Duplicate/invalid third-party metadata can brick unrelated built-in boots.**  
  15.4-02 makes `declared_names()` refuse duplicate, reserved, or invalid entry points globally, and `resolve()` calls `declared_names()` first. That means an invalid unselected plugin can prevent booting a built-in adapter. This may be acceptable fail-closed behavior, but it should be explicitly ruled. D-05 only requires not importing unselected code; it does not necessarily require all bad installed metadata to block every boot.

- **LOW — The substrate-name lint exemption for `ccf.similarity` is broad.**  
  15.4-01 Task 3 exempts the whole `ccf.similarity` package to avoid `sqlite_vec`. That is defensible, but it also means future graph-substrate names inside similarity code are invisible to `cinv04-substrate-name`. A narrower exemption around `sqlite_vec`-style identifiers would keep more of the rule’s force.

- **LOW — The OpenAPI generated artifact path is inconsistent across the phase materials.**  
  Research mentions `http_api/openapi.json`; 15.4-09 says root `openapi.json`. If the repo really uses the former, plan 09’s file scope and verify are wrong. This is easy to settle before execution.

**Suggestions**

- Add an explicit secret-reference carrier: either `boot(secret_refs: Mapping[str, str])`, a small `ResolvedSecret(field, ref_name, value)` contract, or have `load_and_boot()` construct the `AdapterPin` and pass it into `boot()`. Do not infer env var names from the `secrets` mapping.
- Add a registry API such as `validate_connection(registration, mapping) -> CCFContract` that sanitizes Pydantic errors and names adapter/field. Then update 15.4-02 interfaces and 15.4-04/05 tasks to use it.
- Tighten Wave 2 ordering: make 15.4-02 depend on 15.4-03, or make 15.4-03 include minimal `REGISTRATION` records so discovered built-ins are always resolvable.
- Replace V8/freeze verification with commands that fail on non-empty diffs, while still recording `--stat` output.
- Add direct `backend_imports.check(...)` spot checks in 15.4-05/06, not only substrate-name checks, so the enforcement window is guarded before 15.4-07 registers the rule.
- Decide and document whether bad unselected plugin metadata should fail all boots or only `ccf backends list` / resolving that name.

**Risk Assessment**

**MEDIUM.** The architecture is sound and the plans are much more complete than average, especially around lints, public-surface drift, and plugin security. The remaining risks are concentrated in a few contract seams that could let implementation drift while tests still appear green: secret-reference pinning, registry validation, and the intermediate registry state. Fixing those before execution should lower the phase risk substantially.

# Cross-AI Plan Review: Phase 15.4 Backend Registration Seam

## 1. Summary

The twelve plans are a strong, coherent inversion of the core→adapter dependency, with honest handling of C-01/C-02, a deliberate lint-registration window, and a real out-of-tree proof for D-11. They will achieve the phase goal if a few cross-plan gaps are closed before execution: the config-validation wrapper V11 depends on is never tasked; `_open_backend` has test callers research missed; and plan 05’s signature break is sequenced in a way that can leave `make typecheck` red between tasks. None of these are conceptual flaws — they are the class of miss an internal reviewer sharing the same research assumptions would also make.

## 2. Strengths

- **Goal fidelity.** Property (1) and (2) are enforced as structural lints; line budgets are superseded, not raised. Half-measures Dave rejected (exempt `_writer`, keep deprecated kwargs) do not reappear as de-risking.
- **Enforcement window is honest.** 15.4-01 builds checkers with negative controls; 15.4-07 registers them only when the tree can pass. Interim plans call `substrate_names.check()` directly rather than pretending `make lint` already enforces property (2).
- **Single-writer preserved by shape.** Widening `cinv02-graph-writer` to a predicate over `*_write` modules (15.4-01), keeping `_LIVE_WRITERS` in one module (15.4-03), and stating the `make_writer` reachability residual (15.4-02 / 15.4-12) is better than claiming the lint is unchanged when the public surface got wider.
- **Secrets posture is load-bearing.** Resolve-after-validate, no credential on config models, empty-ref refusal (V14 / WR-02 door), and `canonical_bytes` refusing `SecretStr` are correctly treated as mechanism, not discipline.
- **V8 measurement is careful.** `ADAPTER_BASE` recorded before 15.4-10, not derived from wave-6 sibling merge order, avoids a false falsification from 15.4-08’s `record.py` edit.
- **Wave 2 parallelism is sound.** 15.4-02 (registry) and 15.4-03 (writer split) do not fight over the same production seam; 15.4-04 correctly depends on both.
- **Surface-drift discipline.** Claiming public names in the same commit that adds them (03/04/09) matches how `tests/test_surface_drift.py` actually fails.

## 3. Concerns

### HIGH — Config-validation wrapper is assumed, never planned

**Where:** 15.4-04 Task 3 (V11); 15.4-05 Task 1; 15.4-06 Task 2 `read_first` citing “the config-validation wrapper's message contract”; research §Typed config models (“Wrap it”).

**What:** Research requires a wrapper so refusals name **adapter + field**, not only the Pydantic model class. 15.4-04 asserts “the wrapper the registry provides”; 15.4-05 says “letting the registry's wrapper produce the refusal.” **15.4-02 never adds any `validate_*` / wrap function to `registry.py`**, and 15.4-04 Task 1 does not either. 15.4-06 later builds refusal messages inline in manifest preflight — a third place, after V11 was supposed to already pass.

**Why it matters:** V11 is how refusal (a) survives the migration of `_preflight_backend`. Without a single tasked owner, executors will either leave V11 incomplete or invent three divergent wrappers (registry / boot / manifest), which is how credential-shaped `input_value=` leaks come back.

**Fix:** Add an explicit task (best: 15.4-02 Task 1 or a new 15.4-02 Task 3) for something like `validate_connection(adapter: str, data: Mapping) -> CCFContract` that (1) builds from `error["loc"]`/`error["msg"]` only, never `str(exc)` / `error["input"]`, and (2) is the only call site boot and preflight use. Point 15.4-04’s V11 test at that function by name.

### HIGH — `_open_backend` test callers omitted from the migration surface

**Where:** 15.4-05 Task 1–2; research Migration Surface (“`_open_backend` … exactly one caller”).

**What:** Production has one caller; tests do not:

```1703:1749:tests/graph/test_fluree_backend.py
from ccf.boot import _open_backend, boot
...
store, _make_writer = _open_backend(... fluree_bearer_token="tok-abc", ...)
...
with pytest.raises(ValueError, match="without fluree_url"):
    _open_backend(... fluree_bearer_token=..., fluree_url=None)
```

15.4-05 deletes `_open_backend` and rewrites the signature assertion, but Task 2’s action/grep center on `boot(` kwargs. The token-without-URL test encodes refusal (d), whose new home is “secrets key without required connection field” / “secret for undeclared field” — not spelled out.

**Why it matters:** After Task 1, these imports fail. An executor under time pressure may delete the refusal test instead of relocating the guarantee (the same failure mode the plan correctly forbids for the signature assertion).

**Fix:** Extend 15.4-05 Task 2 with an explicit `_open_backend` caller inventory (grep, not research’s “one caller” claim), and map each test to the new seam (`boot(..., secrets=...)` or registry `open_store`).

### MEDIUM — 15.4-05 Task 1 verification cannot stay green before Task 2

**Where:** 15.4-05 Task 1 `<verify>` runs `make typecheck` after reshaping `boot()`; Task 2 migrates 23 call sites.

**What:** Under `mypy --strict`, every remaining `boot(database_path=...)` is a type error the moment the signature changes. If GSD commits per task, Task 1 leaves the tree red until Task 2.

**Fix:** State that Tasks 1–2 are one commit, or move typecheck/ci verification to after Task 2 only. Same pattern risk in 15.4-06 Tasks 2→3 for `load_and_boot`.

### MEDIUM — Connection field renames are under-emphasized relative to their blast radius

**Where:** 15.4-04 interfaces (`postgres_dsn` → `dsn`, `neo4j_uri` → `uri`, …); 15.4-05/06 migrations.

**What:** Adopters and tests must learn a new vocabulary inside `connection={}`. The D-15B fragments mention before/after for SQLite and credentials; the rename of the Postgres/Neo4j/Mongo keys is easy to bury and will produce confusing `extra_forbidden` / `missing` errors.

**Fix:** Require the 15.4-05 and 15.4-06 Migration fields to include an explicit key-mapping table (old kwarg → new connection key).

### MEDIUM — Permanently installing the demo adapter via `make install`

**Where:** 15.4-10 Task 3.

**What:** After the phase, every developer/CI environment that runs `make install` gets `demo` in `declared_names()` and in `ccf backends list`. That is correct for the proof, but it permanently widens the “what is installed here” answer with a fixture package.

**Why it matters:** Adopters following the bootstrap README will see a seventh backend that is not a supported substrate. Parity tests then require `demo` forever.

**Fix:** Document this in the how-to and gate package; or make the fixture install opt-in (`make install-demo-adapter`) while CI always installs it. Either is fine — silence is not.

### MEDIUM — Enforcement window still allows silent property-(2) regressions in prose outside checked files

**Where:** 15.4-01 → 15.4-07 window; interim checks only on files each plan touches.

**What:** Plans correctly call the checker on `boot.py` / `manifest.py` / `artifacts.py` / `registry.py`. A substrate name reintroduced in an untouched core module (e.g. `binder.py` docstring enumeration, or a new helper) would not fail until 15.4-07.

**Fix:** Low-cost hardening: one wave-5 or wave-6 “dry run” of `substrate_names.check` over all of `src/ccf` (excluding backends) before registration, recorded in 15.4-06 or 15.4-07 Task 1 — not only on the files just edited.

### LOW — `GET /backends` fails closed on discovery refusals

**Where:** 15.4-09; 15.4-02 `declared_names()` raises on duplicate/reserved names.

**What:** A poisoned third-party entry point makes listing adapters error for every client. Fail-closed is right; the route plan should say whether that surfaces as 500 vs a typed error, so operators are not debugging “HTTP is down” for a packaging conflict.

### LOW — Research vs plan disagreement on checker placement (resolved well)

**Where:** Research recommended putting `cinv02-backend-import` inside `harness_imports.py`; 15.4-01 uses a sibling so `make lint` stays green until 15.4-07.

**What:** The plan’s reason is better than the research default. No action needed beyond keeping that rationale in the gate package so a later “simplify the lints” pass does not merge them and re-break the window.

### LOW — Dimension-2 adapter pin is optional at the builder

**Where:** 15.4-08.

**What:** Deliberate: example 06 pins; others keep `NO_ADAPTER`. Correct for sentinel coverage. Residual: production adopters can ship forever on `no-adapter` with no CI pressure. Acceptable for v0 if the gate package says so; do not silently “finish” the other examples later without a decision.

# Cross-AI Plan Review: Phase 15.4

## Summary

This is a rigorously engineered refactoring phase that inverts the dependency between CCF core and its graph adapters. The 12-plan, 9-wave structure is exceptionally well-sequenced, with explicit acknowledgment of enforcement gaps, measured (not asserted) claims, and comprehensive treatment of the plugin security surface. The plans correctly identify that this is mechanical relocation rather than redesign—the research shows lines 176-973 of `_writer.py` are already backend-neutral. However, the enforcement window (Wave 1-6 lints written but not registered) relies on plan-sequence discipline rather than automation, and the dynamic import blind spot is accepted rather than eliminated.

## Strengths

1. **Honest enforcement window documentation**: Plan 01 explicitly states the rules exist but aren't registered until Plan 07, and explains what guards the properties during that window (the plan sequence itself). This is better than claiming enforcement that doesn't exist.

2. **Measured claims**: Plan 11 Task 2 records `ADAPTER_BASE` as a SHA before Plan 10's first commit, then runs `git diff --stat` with verbatim output. This is a measurement, not an assertion—the phase's headline claim can be re-run by any reader.

3. **Surface change discipline**: Every plan writes its surface-change fragment in the same commit that causes the drift, with Plan 12's completeness gate cross-checking at FQN granularity in both directions with change-type agreement.

4. **Security-first plugin design**: Discovery reads metadata without importing (Plan 02), credentials never enter config models (Plan 04), built-in names are reserved against third-party claims (D-16), and duplicate names across distributions are refused naming both.

5. **Single-writer preservation**: Plan 01 widens the guarded set with a predicate (`is_write_module`), Plan 03 keeps `_LIVE_WRITER` and `_MINT_KEY` in exactly one module, and the test suite proves a second boot against one graph identity still raises.

6. **Migration accounted for**: 43 call sites identified by AST scan, 31 pass only `database_path` (one-line mechanical edit), `tests/conftest.py` already splats a dict, and D-15B migration notes are written per changed surface.

## Concerns

### HIGH

1. **Enforcement window relies on discipline**: Plans 01-06 operate without active lint enforcement. While Plan 01 documents this window explicitly ("between this plan and plan 15.4-07 the two new rules exist and are proven to *fire* by their negative controls, but they do not run over the tree"), a developer merging a plan out of sequence could introduce violations that slip through. The negative controls prove the rules *can* fire, not that they *will* catch violations during the window.

2. **Dynamic import is invisible to AST lint**: Plan 02's `resolve()` uses `importlib.import_module`, which an AST import lint cannot see. The compensating control (one call site confined to `registry.py`, with a test scanning `src/` and `runtime/`) is documented as an "honest residual" in Plan 01 and Plan 02. This is accepted rather than mitigated—a future developer could add a second call site without triggering the import lint.

3. **Writer factory reachability widened**: Plan 02's `BackendRegistration.make_writer` is a public field on a public record returned by public `resolve()`. A core module can now obtain a writer *constructor* without importing a guarded write module. Plan 02's test asserts all call sites are in `boot.py`, but this is runtime verification, not a static guarantee. Plan 12 acknowledges this as a residual, but it's a genuine narrowing of what CINV-02 bounds.

### MEDIUM

4. **Entry-point metadata staleness**: Plan 10 requires `make install` after entry-point changes. The research notes: "editing the file without reinstalling leaves the new name invisible." A developer running tests without reinstalling could see green locally while CI fails, or vice versa. This is documented in Pitfall 4 and Plan 10 Task 3, but remains operational friction that could cause confusion.

5. **Wave 6 merge order unspecified**: Plans 07, 08, and 09 are all Wave 6 and merge in unspecified order. Plan 11 explicitly warns against anchoring measurements on any Wave 6 plan's commit because Plan 08 changes `src/ccf/replay/record.py`. Plan 10 records `ADAPTER_BASE` before its first commit to avoid this, but if Wave 6 plans merge interleaved with Wave 7, the measurement range could pick up unrelated changes.

6. **Schema regeneration coordination**: Plan 06 Task 1 runs `make schemas` in the same change that drops the `Literal`. If this step is missed or the regenerated file isn't committed, CI fails on `tests/cli/test_schema_export.py`. The plan acknowledges this ("the plan that lands D-12 must re-run `make schemas` in the same change"), but it's a coordination dependency that could cause a red CI.

### LOW

7. **Memory backend write module**: Plan 03 splits `memory_write.py` like the other five backends, but the memory backend has no I/O, no driver dependencies, and no transaction semantics beyond in-process state. The split is mechanically consistent, but adds a file that may feel like over-engineering. The plan justifies this as "every backend follows the split, including `memory`" to keep the rule uniform.

8. **Surface fragment extension**: Plan 04 extends Plan 03's `15.4-03-write-modules.md` fragment rather than creating a new `15.4-04-` fragment. Plan 12 Task 1 must verify all twelve names from Plan 04 are claimed. This is documented ("it extends that fragment rather than opening a `15.4-04-` one because the fragment is keyed to the module set it describes"), but adds dependency complexity.

9. **Third-party adapter lint scope**: The CINV-02 lints are scoped to `src/` and `runtime/`, so they don't walk a third-party adapter. This is documented as "a scope statement, not a hole" in Plan 10 and Plan 12, with the invariant resting on `mint_boot_token` instead. It's honest, but worth noting that a third-party adapter could violate the import rule without the lint catching it.

10. **Fluree credential handling interaction**: Plan 04 Task 2 closes WR-05 (httpx.Client leak on construction failure), and Plan 06 handles credential references. The research notes WR-02/WR-03 were fixed in 15.3, but Plan 06's secret-resolution step could interact with the construction-failure path. Plan 04 Task 2 says "do not change the credential handling itself," but the interaction surface isn't explicitly tested.

## Suggestions

1. **Add a Wave 3 checkpoint lint run**: Between Plan 03 (write modules split) and Plan 06 (manifest changes), add an optional `make lint --backend-imports --substrate-names` that developers can run to check progress. This doesn't enforce, but gives visibility into whether the tree is moving toward the properties. Document it in Plan 01's summary as a development aid.

2. **Strengthen the dynamic import test**: Plan 02's test asserts exactly one `import_module` call site. Add a second assertion that the containing function is private (starts with `_`) and has no callers outside `registry.py`. This makes the confinement harder to accidentally violate.

3. **Add a `make_writer` reachability lint**: Since the writer factory is now reachable through a public record, consider adding a lint rule (or extending CINV-02) that flags any `make_writer` attribute access outside `boot.py`. This would make the Plan 02 test a static guarantee rather than runtime verification.

4. **Document the Wave 6 merge protocol**: Add a note to the Phase 15.4 summary that Wave 6 plans (07, 08, 09) should merge as a batch before Wave 7 begins, to avoid the measurement-range contamination Plan 11 warns about. This is process discipline, not code, but worth recording.

5. **Add a schema-regeneration test to Plan 06**: In addition to running `make schemas`, add a test that asserts the committed `docs/schemas/ccf.deployment-manifest.json` matches what `tools/dump_schemas.py` emits. This catches the case where someone runs the command but forgets to commit the result.

6. **Test the Fluree construction-failure + credential-refusal interaction**: Plan 04 Task 2 tests construction failure closes the client. Plan 06 tests credential references. Add one test that triggers a credential refusal *during* Fluree store construction and asserts the client is still closed. This covers the interaction surface.

## Risk Assessment

**Overall: MEDIUM**

The plans are exceptionally well-designed with honest acknowledgment of gaps, measured claims, and comprehensive security treatment. The phase goal is achievable. However:

- The **enforcement window** (Wave 1-6 without active lint) is the highest risk—it relies on plan-sequence discipline rather than automation. A developer merging out of order could introduce violations.
- The **dynamic import blind spot** is accepted rather than eliminated—a known limitation with compensating controls.
- The **writer factory reachability** is genuinely widened, with runtime verification rather than static guarantees.

These are all documented as residuals, which is better than hiding them. The risk is MEDIUM rather than HIGH because the plans explicitly name these gaps, provide compensating controls, and the verification matrix at Plan 12 will catch violations before the phase closes. The out-of-tree adapter proof (Plan 10-11) is rigorous and the measurement is verifiable by any reader.

**Recommendation**: Proceed with the plans as written, but implement suggestions 1 and 3 to strengthen the enforcement window visibility and the writer-factory reachability guarantee.

## Consensus Summary

Three findings were checked against the tree rather than taken on the reviewers' word. All
three hold, and all three contradict something the plans or the research currently assume.

### Verified defects

**1. The config-validation wrapper is assumed but never planned.** Raised independently by
Codex (HIGH) and Cursor (HIGH) — the only finding two reviewers reached on their own.

Plans 04, 05 and 06 all reference "the wrapper the registry provides" for refusals that name
both the adapter and the field. Plan 02 defines no such function: it exports `declared_names()`
and `resolve()`, and `BackendRegistration` carries no `validate_config` or `validate_connection`.
Confirmed by grep — plan 02 contains neither name, while plans 04, 05 and 06 each say "wrapper".

Why it matters: V11 is how the current `_preflight_backend` refusal survives the migration.
With no owner, an executor either leaves V11 incomplete or invents three divergent wrappers in
registry, boot and manifest. Cursor names the specific consequence — a hand-rolled refusal that
formats `str(exc)` or `error["input"]` puts the credential back in the message, which is exactly
the leak surface the research enumerated and D-08 exists to close.

Fix both reviewers converge on: add a task to plan 02 for a public
`validate_connection(adapter, mapping)` that builds messages from `error["loc"]` and
`error["msg"]` only, export it, and point plans 04, 05 and 06 at it by name.

**2. The V8 measurement cannot fail.** Codex (MEDIUM), verified: `git diff --stat` exits 0
whether or not its output is empty (`git diff --quiet` is the one that exits 1). Plan 11's
automated verify for the phase's headline claim — that a seventh substrate costs zero lines
under `src/ccf` — therefore passes regardless of what the diff contains. The acceptance
criterion requires empty output; the command does not enforce it. Fix: print `--stat` for the
record, then gate on `git diff --quiet`.

**3. `_open_backend` has test callers the research missed.** Cursor (HIGH), verified at
`tests/graph/test_fluree_backend.py:1703, 1717, 1746`. The research's "exactly one caller"
(`boot.py:343`) is true for production code and false for the suite. Plan 05 deletes
`_open_backend`, so those imports break, and one of them encodes a refusal — a bearer token
supplied without a URL — whose new home under the `secrets` mapping no plan names. The risk is
that an executor deletes the test rather than relocating the guarantee, which is the same
failure mode plan 05 already forbids for the signature assertion it rewrites.

### Agreed strengths

Named by two or more reviewers:

- **The claims are measured, not asserted.** V8 anchored on a recorded SHA, the writer split
  based on measured AST spans, the lint hit counts reproduced. All four reviewers said some
  version of this.
- **Plugin security is treated as a real surface.** Discovery without import, duplicate and
  reserved names refused, optional drivers still lazy, entry points used for the proof.
- **Single-writer is preserved by shape, and its one widening is recorded rather than hidden.**
  Three reviewers called the `make_writer` disclosure the right handling even while disagreeing
  about how much more it needs.
- **Surface-drift discipline** — claiming public names in the same commit that adds them.
- **Secret hygiene** — no credential on a config model, `canonical_bytes` refusing `SecretStr`,
  empty-reference refusal as the WR-02 regression door.
- **The rejected half-measures did not return** as de-risking steps.

### Agreed concerns

- **Writer-factory reachability.** All four saw it; they disagree on severity (below).
- **Entry-point metadata staleness.** Gemini (LOW) and Ollama (MEDIUM): a developer who edits
  entry points without re-running `make install` sees a discovery failure that looks like a
  code bug.
- **Schema regeneration coordination.** Gemini and Ollama: if `make schemas` runs but the
  regenerated file is not committed, CI fails on a plan that intended the change. Ollama
  suggests asserting the committed file matches what the generator emits.

### Single-reviewer concerns worth acting on

- **Secret-reference pinning is underspecified** (Codex, HIGH). `boot(secrets: Mapping[str,
  SecretStr])` carries field names and resolved values, not the environment-variable reference
  names from plan 06's `backend_secrets`. As written the pin can record `bearer_token` but not
  `CCF_FLUREE_TOKEN`, which weakens D-08, D-09 and V15. Needs an explicit carrier.
- **Wave 2 intermediate state** (Codex, MEDIUM). If plan 02 lands before plan 03, built-in
  discovery can list adapters that `resolve()` cannot load, because `REGISTRATION` does not
  arrive until plan 04.
- **Signature-break tasks leave the tree red between commits** (Cursor, MEDIUM). Under
  `mypy --strict`, plan 05 task 1 changes `boot()` and task 2 migrates 23 call sites; committing
  per task leaves typecheck red in between. Same shape in plan 06 tasks 2→3.
- **Connection key renames need a mapping table** (Cursor, MEDIUM). `postgres_dsn`→`dsn`,
  `neo4j_uri`→`uri`, `mongo_uri`→`uri`, `fluree_url`→`url`,
  `fluree_bearer_token`→`secrets["bearer_token"]`. Easy to bury in a migration note and it
  surfaces as confusing `extra_forbidden` errors.
- **The demo adapter installs permanently** (Cursor, MEDIUM). After `make install`, every
  developer and CI environment reports a seventh backend in `ccf backends list`. Correct for the
  proof; needs a decision on whether it is opt-in, and a line in the gate package either way.
- **Bad third-party metadata can block unrelated boots** (Codex, MEDIUM). `resolve()` calls
  `declared_names()` first, so an invalid unselected plugin prevents booting a built-in adapter.
  Defensible fail-closed behavior, but it should be ruled explicitly — D-05 requires not
  importing unselected code, not that bad metadata fails every boot.
- **A full-tree dry run before registration** (Cursor, MEDIUM). Interim checks run only on the
  files each plan touches, so a substrate name reintroduced in an untouched core module would
  not surface until plan 07. One dry run of `substrate_names.check` over all of `src/ccf` before
  flipping the rules on closes the window's one real hole.

### Divergent views

- **The enforcement window.** Gemini and Cursor call it a strength — rules written in wave 1
  with negative controls, registered in wave 6 when the tree can pass, with interim plans calling
  the checker directly instead of pretending `make lint` enforces anything. Ollama rates it the
  phase's **highest** risk, on the ground that it relies on plan-sequence discipline rather than
  automation. Both readings are defensible and they point at the same fix: Cursor's full-tree dry
  run is the cheap way to convert discipline into a check.
- **Writer-factory reachability.** Gemini calls the AST call-site test "a sophisticated and
  appropriate compensating control" and rates it LOW. Ollama rates it HIGH and wants a static
  lint rule instead of a runtime test. Cursor treats recording it as a strength. The disagreement
  is about whether a test that scans for call sites counts as a static guarantee.
- **Overall risk.** Gemini LOW; Codex, Cursor and Ollama MEDIUM. The gap traces to the wrapper
  finding, which Gemini did not surface.

### Recommended disposition

The three verified defects are plan edits, not redesign. None of the four reviewers proposed
restructuring the twelve-plan sequence, and Cursor states plainly that these are "not reasons to
restructure." The wrapper needs an owner before wave 3, the `_open_backend` test callers need to
be in plan 05's migration table before wave 4, and V8's gate is a one-line change to plan 11.

Nothing here reopens a decision Dave made. The scope line held under four independent reads —
every reviewer that mentioned FIBO, WR-04/06 or IN-02/03 said to keep them out.
