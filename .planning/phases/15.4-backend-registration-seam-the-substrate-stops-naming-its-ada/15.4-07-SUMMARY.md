## What Was Built

### Task 1 — both checkers registered, scoped, flagged (`e5ad3c6`)

`CHECKERS` gains `"backend-imports": backend_imports.check` and
`"substrate-names": substrate_names.check`. `substrate_names.check` carries an
optional third `base=` keyword the other checkers do not; the positional pair
the runner calls is unchanged, so registration needed no adaptation, and a
comment above `CHECKERS` says so rather than leaving the next reader to
rediscover it.

`RULE_TREE_SCOPE` gains two explicit entries. Both needed to be explicit for
the same reason, stated in the comment block above the map: **a rule absent
from that mapping runs over every linted tree**, so an omission is not a
narrower scope — it is a wider one, arrived at silently.

| Rule | Scope | Why this and not the default |
| --- | --- | --- |
| `backend-imports` | `("src", "runtime")` | The invariant is worded over core, and `runtime/` has zero violations today so including it costs nothing and closes the seam a deployment-wiring module would leave open. Scoped OFF `tests/` deliberately: the 45 backend imports there are per-backend unit suites importing the backend they are a unit suite *for* |
| `substrate-names` | `("src",)` | The property is worded over the *core*. An example that boots a particular store has to name it, a per-backend test has to name it, and the runtime's operational surfaces report the name a deployment supplied |

The comment for `backend-imports` also carries the blind spot forward:
`importlib.import_module` is invisible to an AST import lint, and the
compensating single-call-site test scans `src/` and `runtime/` — **the same
two trees this scope covers**, so the control is exactly as wide as the rule
(T-15.4-03, accepted and stated).

Two flags, `--backend-imports` and `--substrate-names`, following the shape of
the existing four.

**The failure message was confirmed, not widened.** It reads "Fix the code, or
— for CINV-01 only — add a reviewed entry to tools/lints/allowlist.yaml."
CINV-01 is `no-hardcoding` and nothing else, so the sentence was already
accurate about both new rules and stays accurate. The task asked for a check;
the check is the whole of the change here.

**D-13 is written down three times, and each time as a deviation.**
`allowlist.yaml`'s header now names `cinv02-backend-import`,
`cinv04-substrate-name` and `cinv04-substrate-prose` as taking no allowlist,
and gives three independent reasons: `apply_allowlist` runs for `cinv01*` and
nothing else so the path is structurally unreachable; the `fingerprint` field
is a hash of an offending *literal*, which an import rule cannot produce; and
the sentence the file already carried — an import restriction with exceptions
is not an invariant — applies with more force to a rule whose subject is that
core names no adapter. The runner's module docstring carries the same argument
where a reader of `apply_allowlist` will meet it, and both say plainly that
this is **stricter than D-IMPL-93's own wording**, which says `allowlist.yaml`
governs exceptions to these rules. Dave ruled no allowlist. Plan 15.4-12 owes
the gate package the same paragraph.

`tools/lints/__init__.py`'s package docstring now lists all seven checkers
rather than five, records that `substrate_names` adds the optional `base=`
keyword to both entrypoints, and closes by stating that only `no_hardcoding`
findings are ever offered to the allowlist.

**Seven new runner tests** (15 in the module, 122 in `tools/lints/tests`):

| Test | Claim |
| --- | --- |
| `test_the_registered_rule_set_is_exactly_these_seven` | both new rules are in `CHECKERS`, so `--all` runs them; spelled as a set so a future addition is deliberate |
| `test_both_new_rules_are_scoped_in_config_not_by_accident` | T-15.4-26 — both scopes asserted exactly |
| `test_each_new_rule_has_its_own_flag` | the two flags parse to the two rule ids |

| `test_substrate_names_covers_src_alone` | the same substrate-naming parameter in four trees; only the `src` path reported |
| `test_the_adapter_package_is_not_reported_by_either_rule` | inside `backends/` both rules are silent — the one place the exemptions exist for |
| `test_neither_new_rule_can_reach_the_allowlist` | D-13, structurally: neither checker's source mentions `no_hardcoding`, so there is no second route to `apply_allowlist` |

The two scope tests plant `src/ccf/graph/backends/zzquux.py` in the tmp tree, so
`substrate_names.repo_base_for` resolves the base to the tmp tree and derives a
one-word vocabulary from it. That keeps them hermetic — independent of the real
adapter set **and** of the process's working directory, which is what the
`repo_base_for` fallback would otherwise reach for.
