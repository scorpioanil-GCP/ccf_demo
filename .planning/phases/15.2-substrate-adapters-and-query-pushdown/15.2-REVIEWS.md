# Cross-AI Plan Review — Phase 15.2

## Gemini Review

# Phase 15.2 Plan Review: Substrate Adapters and Query Pushdown

## 1. Summary
The plan set for Phase 15.2 is an exceptionally thorough and architecturally rigorous design for transitioning the CCF SDK from a "load-everything" graph model to a "question-answering" substrate model. By prioritizing normative prose (`GQ-NN` clauses) and a reference fallback implementation as the source of truth, the plans ensure that semantic parity across SQL, Cypher, and NoSQL substrates is a requirement of the build rather than an accidental outcome. The strategy for managing the "pushed-traversal leak" (Pitfall 1) and the decision to implement a plan-static "first maximal pushable prefix" rule provide a sound security and determinism foundation while leaving clear extension points for future multi-segment pushdown.

## 2. Strengths
*   **Prose-First Governance:** Plan 01 enforces the "prose decides, code implements" hierarchy, ensuring that edge cases (depth-0, seeds, hop admissibility) are resolved before a single line of pushdown code is written.
*   **Structural Integrity:** The use of a template-method pattern in `BaseGraphReader` (Plan 04) ensures that record materialization, ordering, and serialization remain centralized. This makes "Ordering and serialization belong to the interface" a structural property rather than a convention.
*   **Security-Centric Traversal:** The explicit focus on "hop admissibility" (Path-level predicates) across all adapters prevents information disclosure leaks where walks could otherwise bypass Policy or Temporal filters by hopping through excluded nodes.
*   **Pragmatic Risk Management:** The staged approach for MongoDB (Plan 11) — landing `$match` pushdown first as a conformant floor and treating `$graphLookup` as a budgeted promotion — prevents a difficult substrate from becoming a phase-ending blocker.
*   **Tier-2 Reusability:** The `ProductSource` design (Plan 09) elegantly reuses the existing `PeeringAdmissionGate` and `AdmittedProduct` token-guard mechanism, achieving "admission-as-a-type-system-property" with zero refactor of the governance logic.
*   **Rigorous Replay Guardrails:** The verification of historical record comparison paths (A5) before extending the replay record (Plan 06) is a high-signal safety check for preserving the validity of existing audit trails.

## 3. Concerns
*   **Cypher Depth Literal (Plan 10):**
    *   **Severity:** **LOW**
    *   **Reason:** While well-mitigated via validation (isinstance int, >=0, bounded), inlining a literal into query text is a departure from the "no f-string SQL" rule. The plan correctly identifies this as a named, documented exception, but it remains a site requiring high-scrutiny during review.
*   **Mongo Doubled-Edge Layout (Plan 11):**
    *   **Severity:** **LOW**
    *   **Reason:** Correcting for `$graphLookup` directedness by storing edges twice (forward/reverse) increases write volume and storage size. However, given that this is confined to the Mongo backend and necessary for BFS correctness, it is a sound trade-off for v0.2.
*   **Segmentation Simplification (Plan 01/06):**
    *   **Severity:** **MEDIUM**
    *   **Reason:** The "first maximal pushable prefix" rule is less ambitious than the roadmap's "one query per pushable segment." While it is the **only sound path** given the current `GraphQuery` vocabulary (as Pitfall 2 demonstrates), it means that any Similarity operator in a plan will "kill" pushdown for any subsequent pushable operators. This is a legitimate v0.2 posture, but the documentation in Phase 16 must be very clear about this performance cliff.

## 4. Suggestions
*   **Telemetry Standardization:** In Plan 04, ensure the `translated_answers` and `fallback_answers` counters are standardized in the `GraphReader` Protocol so that external telemetry collectors can rely on their presence without type-checking.
*   **Corpus Diversity:** In Plan 05, ensure the `query_corpus.py` strategies specifically generate "orphaned" nodes (nodes with no edges) and "self-loops" (nodes with edges to themselves) to verify substrate-native traversal base cases.
*   **SQL Dialect Documentation:** In Plan 07, add a comment to the recursive CTE SQL blocks pointing to the specific `GQ-NN` clauses they satisfy, mirroring the docstring discipline of the fallback module.
*   **Memory Store Identity:** In Plan 05, the `graph_identity` for the memory store should include the `tenant_id` if the store is not globally unique, to ensure the single-writer boot check distinguishes between different tenants' in-memory graphs.

## 5. Risk Assessment
*   **Overall Risk: LOW**
*   **Justification:** The phase is exceptionally well-researched with high-confidence repo-seam findings. The dependency chain is "secure-by-construction" (prose → fallback → properties → differential). The most significant technical risks (Mongo semantics and Cypher parameterization) are either budgeted with fallback paths or addressed via empirical verification tasks (A1-A3) early in their respective plans. The preservation of the 15.1 binder and registration seams is explicitly verified by diff in the close-out plan, minimizing regression risk for recently hardened features.

## Codex Review

## Summary

The plan set is unusually thorough and mostly coherent: it respects the “semantics first” requirement, treats replay and conformance as first-class, and keeps the tier-2 and tier-3 extensibility constraints visible. The main risks are not missing intent, but execution complexity and a few semantic traps where the plans assert equivalence before proving the underlying representation can support it. I would approve the planning direction, but tighten several plans before execution, especially around fallback input shape, pushed-operator double application, replay record compatibility, and the scope of shipping five backends in one phase.

## Strengths

- The dependency order is mostly sound: prose → contracts → fallback/properties → memory/differential → engine segmentation → native adapters.
- The D-01 amendment is correctly surfaced as a blocking decision instead of being smuggled into implementation.
- Conformance design is strong: prose as authority, fallback as reference implementation, differential tests for adapters, and property tests against the fallback.
- The plans preserve key project constraints: no harness imports, single-writer confinement, no adapter-side canonical serialization, and no capability negotiation.
- The memory backend is a good adversarial floor and validates the “no query engine required” claim.
- ProductSource is designed as composition over existing admission rather than rebuilding governance.
- Security concerns are named well: tenant scoping, hop admissibility, injection risks, credential hygiene, admission bypass, and replay repudiation.

## Concerns

- **HIGH: Fallback input semantics are underspecified.** Plans describe fallback as operating over `EntityRecord` / `RelationshipRecord`, but also require it to enforce as-of observed/superseded predicates. If those records are already materialized as-of and do not retain enough claim-boundary data, the fallback cannot independently prove INV-CH7-14. Clarify whether fallback receives raw claim rows, materialized records plus temporal metadata, or only already-filtered records.

- **HIGH: Plan 06’s “double-application is identity” claim is risky.** Applying pushed operators again over a reduced view may not be identity for traversal, especially when seed classes are recomputed from the reduced view or when traversal closure differs after relationships are pruned. This needs a proof in semantics, not just a test.

- **HIGH: The all-or-nothing `_translate_query()` hook conflicts with partial pushdown language.** Plan 07 wants SQL to translate common full queries; Plan 11 explicitly ships Mongo `$match` with fallback traversal. Under an all-or-nothing hook, “partial `$match` then fallback traversal” is not represented cleanly unless the hook returns a partially reduced row universe and fallback finishes the whole query. That interface contract needs to be explicit before adapter work.

- **HIGH: Scope is very large for one phase.** Five backends, write-seam refactor, replay contract changes, ProductSource, attestation enforcement, conformance suites, CI containers, schemas, and perf all in one phase is high delivery risk. Mongo and Neo4j especially can consume disproportionate time.

- **MEDIUM: Requirement dependency mismatch.** Plan 15.2-02 references `SUBQ-11` but does not depend on 15.2-01, where SUBQ IDs are minted. That is acceptable operationally only if Wave 1 ordering is enforced outside `depends_on`; otherwise the requirement reference is unresolved.

- **MEDIUM: Plan 04 atomic Protocol widening may still miss structural conformers.** The plan names `BaseGraphReader` and `SnapshotReader`, but any test stubs or third-party-like internal Protocol implementations may break once `GraphReader` requires `query` and `attestation`.

- **MEDIUM: ProductSource tenant mismatch behavior is a design choice hidden in implementation.** Plan 09 chooses empty answer for non-matching tenant, while SnapshotReader raises. That may be correct, but it should be in `GRAPH_QUERY_SEMANTICS.md`, not just a module docstring.

- **MEDIUM: Replay record changes appear in multiple plans.** Plan 06 adds query sequence; Plan 08 adds source attestation. Both use sentinel defaults. The combined canonical compatibility should be tested together, not only independently.

- **MEDIUM: Attestation “accepted mode sets” are sensible, but “minima” wording remains misleading.** Since there is no ordering, plans and requirements should consistently say accepted modes, not minima.

- **MEDIUM: SQL/Cypher/Mongo pushdown may under-specify classification attribute safety.** Dynamic JSON path construction from artifact-authored attribute names needs identifier/path validation, not just parameterized values.

- **LOW: Surface-change fragments per plan plus single regeneration is good, but fragile.** The final plan should explicitly fail if any public drift lacks exactly one 15.2 fragment.

- **LOW: Perf impact is treated as evidence only.** That is consistent with project rules, but this phase may materially change performance baselines; the gate package should clearly separate correctness approval from re-baseline approval.

## Suggestions

- Define a single internal “query answer input” contract before Plan 04: raw claim rows, record rows, or materialized records. Make fallback, memory, ProductSource, and adapter hooks all target that same shape.

- Replace the Plan 06 double-application assumption with one of these clearer options:
  - record pushed operators as executed without reapplying them, with provenance minted from the planned operator and query pin; or
  - prove and document per-operator idempotence over pushed views before using double application.

- Reconcile partial pushdown before Plan 07/11. Either keep `_translate_query()` strictly whole-query or define a `TranslatedAnswer` shape that says which families were handled and what residual fallback must apply.

- Add an explicit dependency from 15.2-02 to 15.2-01, or remove requirement IDs from 15.2-02 frontmatter until after minting.

- Add a dedicated “combined replay compatibility” test after Plan 08: old record, query-sequence-only record, attestation-only record, and record with both new fields.

- Make ProductSource tenant mismatch behavior a `GQ-NN` clause.

- Require validation for dynamic JSON/Cypher identifiers: classification attribute names, relationship type names, labels/types if rendered into query text.

- Consider making Mongo `$graphLookup` promotion explicitly optional for phase success, with SUBQ-08 wording allowing “conformant Mongo adapter with traversal fallback” if parity is not reached.

- Add a phase-level “review before Dave gate” requirement before 15.2-12, given the Phase 15.1 lesson that code review must precede human approval.

## Concerns

### HIGH

- **`CATEGORY_ORDER` claim is wrong; amendment justification must be restated.**

```67:72:src/ccf/operators/base.py
CATEGORY_ORDER: tuple[OperatorCategory, ...] = (
    "policy",
    "similarity",
    "temporal",
    "traversal",
)
```

  Plans 01/06/CONTEXT claim the three pushable categories sit *ahead of* Similarity, so the prefix rule “loses no pushdown any shipped plan could legally have.” That is false. For any plan that includes Similarity, the prefix rule pushes **only Policy**; Temporal and Traversal run in-process. Multi-segment D-01 would have *attempted* a second push after Similarity — and RESEARCH Pitfall 2 correctly says that is unsound without an allowed-node set. The amendment is still the right sound choice, but Task 0 must argue **“loses no *sound* pushdown”**, not “CATEGORY_ORDER already put pushables first.” Otherwise Dave ratifies a false premise.

- **`BaseGraphReader` SQL template vs non-SQL adapters (plans 04/05/10/11).** Today the module is explicitly “five SQL statements + `_query()`.” Plan 04’s `query()` still starts from `SELECT_*_AS_OF` ClassVars, then optionally `_translate_query`. Memory/Neo4j/Mongo cannot honestly live in that shape. Plan 05 waves at “use shared helpers if ClassVars fight,” but there is no single plan that **refactors the shared materialization API** (row → record → order → freeze) into a substrate-agnostic template. Without that Wave-3 design spike, adapters will fork lineage/supersession (Pitfall 5) or invent parallel bases — differential suite then compares accidents.

- **Plan 08 changes `execute()`’s return contract.** Today:

```224:232:src/ccf/projection/engine.py
    def execute(
        ...
    ) -> ExecutionResult:
```

  Gate refusals live in `run_gates` → `ServableProduct | GateRefusal`. Returning `AttestationRefusal` from `execute` forces every example/caller/union type to change, or the refusal must be raised (violating the refusal-value convention). Plans say “signature stays byte-stable” for the binder (06) but 08 quietly widens the return type. **Resolve before Wave 5:** either `ExecutionResult | AttestationRefusal` with an explicit migration task across call sites, or a pre-execute helper the deployment layer calls (closer to binder placement), or fold attestation into the existing gate path.

Plan 04 Task 3 then says assert “lineage-at-boundary and supersession-as-of” under 23/24 — those are reader/`as_of` properties, not those INV numbers. ## Ollama Review (gemma4:cloud)

# Cross-AI Plan Review: Phase 15.2 Substrate Adapters and Query Pushdown

## Summary
This is a high-fidelity, architecturally rigorous plan to transition the CCF SDK from a "materialize-everything" read model to a "query-pushdown" model. The plan is exceptionally well-structured, utilizing a "Reference Implementation (Fallback) $\to$ Differential Suite $\to$ Native Translation" pipeline that effectively eliminates the risk of semantic drift across five different substrates. It meticulously respects existing project invariants (single-writer, operator purity, replay determinism) and employs a conservative "first-maximal-pushable-prefix" rule to avoid complex state-leakage hazards. The dependency ordering is logical, and the commitment to "zero churn" on existing `as_of()` call sites ensures stability for the upcoming Phase 16.

## Strengths
*   **The Oracle Pattern (D-05):** Defining normative prose first, then a reference fallback, then auditing that fallback with property tests, and finally using it as a byte-identity oracle for native adapters is the gold standard for this type of SDK work.
*   **Information Disclosure Controls:** The explicit focus on "hop admissibility" (Pitfall 1) prevents the common "reachability leak" where a pushed traversal could reveal the existence of a policy-excluded node by allowing a path to jump over it.
*   **Structural Safety:** By generalizing the write seam (`_GraphTxn` in 15.2-02), the plan enables non-SQL backends without violating the `CINV-02` confinement rule (everything stays in `_writer.py`).
*   **Replay Integrity:** The use of `content_hash(GraphQuery)` as the per-round-trip pin, combined with the sentinel-defaulted field in `ContentGenerationPath`, preserves historical record compatibility while enabling granular audit trails.
*   **Tier-2 Integration:** The `ProductSource` implementation treats admission as a type-system property (`AdmittedProduct`), ensuring governance is not rebuilt but reused.

## Concerns

*   **Neo4j Driver Compatibility (LOW):** Assumption A1 (Driver 6.x $\to$ Server 5.x) is a potential friction point. While the plan includes a verification task, a version mismatch in CI could delay the wave.
*   **Mongo Traversal Complexity (MEDIUM):** The "doubled-edge" physical layout is a necessary but significant departure from the SQL model. If the `$graphLookup` promotion fails to reach byte-identity, the fallback path is the only safety net. The risk is correctly budgeted, but the implementation of the "doubled" writer is a point of failure.
*   **Memory Backend "Triviality" (LOW):** The memory backend is a "thin shell over fallback." While this is the intent, the plan must ensure it doesn't become a "cheat" that masks bugs in the fallback's own logic (though the property suite in 15.2-04 mitigates this).
*   **A5 Replay Comparison (MEDIUM):** If the verification in 15.2-06 Task 3 finds that historical records are re-derived rather than compared by address, the sentinel-default strategy could potentially break.

## Suggestions
*   **Tighter Bound on Depth Literals:** In 15.2-10 (Neo4j), the "validated integer" should be checked against a hard-coded `MAX_DEPTH_CEILING` (e.g., 100) to prevent potential Denial-of-Service via extremely deep Cypher paths.
*   **Explicit "No-Op" Telemetry Test:** In 15.2-06, add a test case where a plan is 100% in-process; verify that `translated_answers` is exactly 0 and `fallback_answers` is 1 (for the degenerate query), ensuring the telemetry doesn't double-count or miss-count.
*   **Mongo Payload Validation:** For the `ProductSource` mount (15.2-09), suggest adding a "payload ceiling" check (e.g., 10MB) before `model_validate`, as loading a massive product into memory to treat it as a graph source could trigger OOMs.

## Risk Assessment: LOW
The overall risk is **LOW**. 

The plan is "defensive by design." By implementing the fallback and the differential suite before the native translations, the developers have created a safety net where any "optimization" (pushdown) that changes the result is caught immediately as a defect. The "First Maximal Pushable Prefix" rule is a prudent trade-off—sacrificing a small amount of theoretical pushdown potential to ensure total soundness and avoid a massive expansion of the `GraphQuery` vocabulary. The dependency on Dave's ruling for the D-01 amendment (Task 0) ensures alignment on the project's core constraints before implementation begins.

- **The oracle pattern is the gold standard for this work** (all four): normative prose → reference fallback → property suite auditing the fallback → differential byte-identity for adapters. Semantic parity across substrates is a build requirement, not an accident.
- **Dependency spine is correct** (Codex, Cursor, Ollama): prose → contracts → fallback/seam → memory floor + corpus → segmentation → SQL → Neo4j → Mongo → gate.
- **D-01 amendment is Dave-gated, not smuggled** (all four): the blocking Task 0 checkpoint with STOP-and-replan on the vocabulary-extension option is the right discipline.
- **Hop admissibility prevents the reachability leak** (all four): path-level predicates on every hop stop pushed traversals from revealing policy/temporally excluded nodes (INV-CH7-40).
- **Mongo risk is correctly budgeted** (all four): `$match` floor first, `$graphLookup` as staged promotion with a sanctioned degrade path under D-04.
- **ProductSource reuses governance instead of rebuilding it** (all four): `AdmittedProduct` token-guard makes admission a type-system property with zero changes to `admission.py`.
- **15.1 do-not-disturb checks are explicit** (Gemini, Cursor): binder/registration/admission seams verified by diff in plan 12, matching the failure mode this repo learned in Phase 15.1.

### Agreed Concerns

1. **[HIGH — verified] CATEGORY_ORDER mis-claim invalidates the D-IMPL-87 rationale as written** (Cursor; consistent with Gemini's "Similarity kills subsequent pushdown" MEDIUM). Plans 01/06 and CONTEXT claim the three pushable categories sit ahead of Similarity, so the prefix rule "loses nothing." Actual order: `policy → similarity → temporal → traversal`. For any plan containing Similarity, the prefix rule pushes **only Policy**; Temporal and Traversal run in-process. The amendment remains the only *sound* choice (RESEARCH Pitfall 2), but Task 0 / D-IMPL-87 must argue "loses no **sound** pushdown," with worked examples for both the no-Similarity and Similarity-present cases — otherwise Dave ratifies a false premise. The Phase 16 docs must also name the performance cliff.
2. **[HIGH] Plan 06's double-application identity claim is under-proved** (Codex, Cursor). Re-applying pushed operators over an already-reduced view may not be identity for traversal (seed recomputation, pruned closure), and Gate 2 lineage strict equality (`operators_invoked`, provenance/parameter hashes) must be pinned in the end-to-end regression — not just product `canonical_bytes`. Either prove per-operator idempotence over pushed views in the semantics prose, or record pushed operators as executed-without-reapplying with provenance minted from the planned operator + query pin.
3. **[HIGH] Non-SQL materialization template / fallback input shape underspecified** (Codex, Cursor). `BaseGraphReader` is SQL-ClassVar-shaped; plan 05 says "use shared helpers if the ClassVars fight" but no task extracts a substrate-agnostic materialization API (rows → records → order → freeze). Without it, memory/Neo4j/Mongo/ProductSource risk forking lineage/supersession semantics and the differential suite compares accidents. Also clarify what the fallback receives (raw claim rows vs materialized records + temporal metadata) so it can independently enforce INV-CH7-14.
4. **[HIGH] Partial-pushdown contract is ambiguous** (Codex; latent in Cursor's 04 concern). The all-or-nothing `_translate_query()` hook conflicts with Mongo's "$match-only + fallback traversal" stage 1. Define before adapter work: either strictly whole-query, or a `TranslatedAnswer` shape naming which predicate families were handled and what residual the fallback must apply.
5. **[HIGH] Plan 08 widens `ProjectionEngine.execute()`'s return contract** (Cursor; Codex flags combined replay compatibility in the same area). Returning `AttestationRefusal` from `execute()` — which today returns `ExecutionResult` — either breaks the refusal-value convention (if raised) or silently changes every call site. Decide placement in planning: pre-execute check, gate-path integration, or explicit union widening with a call-site migration task.
6. **[MEDIUM-HIGH] Scope** (Codex HIGH, Cursor MEDIUM-HIGH, Ollama implicit). Five backends + write-seam refactor + replay changes + attestation + ProductSource + two suites + three CI container legs is a long critical path; Neo4j is less budget-protected than Mongo. Mitigation already in-plan: D-04 degrade posture, staged Mongo, wave ordering.
7. **[MEDIUM] ProductSource tenant-mismatch behavior must be a GQ-NN prose clause** (Codex, Cursor): empty-view vs raise is a normative decision for 01 §7, not a module docstring; tenant-boundary tests must distinguish "empty because excluded" from "empty because hidden cross-tenant leak."
8. **[MEDIUM] Combined replay-record compatibility** (Codex, Cursor): both sentinel-defaulted fields (`graph_query_sequence`, `source_attestation`) must be tested together (old record / one field / both), and the A5 stored-content-address verification in 06-T3 must not be skipped.
9. **[MEDIUM] Property-suite invariant IDs may be mis-mapped** (Cursor; Codex adjacent on "minima" wording): align INV-CH7-23/-24/-26 references with SPEC_INVENTORY before writing tests, and rename attestation "minima" to "accepted modes" consistently.
10. **[LOW] Plan 02 references SUBQ-11 without depends_on 15.2-01** (Codex, Cursor): acceptable only because Wave 1 ordering enforces it operationally; add the edge or note it.
