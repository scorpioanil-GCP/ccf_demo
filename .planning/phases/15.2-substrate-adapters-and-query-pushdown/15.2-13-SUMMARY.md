# Phase 15.2 Plan 13: MongoDB Backend — Staged Aggregation Pushdown Summary

The fifth and last adapter of Phase 15.2 ships **promoted, not degraded**: MongoDB answers the whole `GraphQuery` in the aggregation dialect — `$match` filter documents for every record predicate and one `$graphLookup` over a doubled-edge collection for the traverse family — byte-identical to the reference implementation across the full differential corpus, `allowed_entities` shapes included.

## Stage outcome — the gate-package answer

**Promoted.** The plan budgeted stage 1 (`$match` + fallback traversal) as an acceptable success state and named the degrade as a legitimate shipped posture. It was not needed. Both stages landed, each committed on its own evidence:

| Stage | Commit | Posture | Evidence |

| 2 — `$graphLookup` traversal promotion | `761fba1` | **Shipped** | Same corpus green with the walk in the engine, plus the four trap shapes asserted by name |

Nothing is behind a default-off flag; there is no degraded tail. Promote-vs-degrade remains a 15.2-14 ratification entry, and the entry now reads *promoted with proof*.

## A3 verification record (Task 3 step 1, run BEFORE any promotion code)

Assumption A3 (`15.2-RESEARCH.md:953`) — *`$graphLookup.restrictSearchWithMatch` accepts the plain-match predicates the hop-admissibility filter needs, no `$expr` required*.

Probed against the live container (**server 7.0.39, pymongo 4.17.0**), each shape run as a real aggregation:

| Predicate shape inside `restrictSearchWithMatch` | Result |
|---|---|
| scope equality (`partition`, `tenant_id`) | ACCEPTED |
| `relationship_type: {$in: […]}` | ACCEPTED |
| `observed_at: {$lte: <canonical text>}` | ACCEPTED |
| `$or: [{superseded_at: null}, {superseded_at: {$gt: …}}]` | ACCEPTED |
| entity membership `to: {$in: […]}` (the `allowed_entities` uniform rule) | ACCEPTED |
| all five combined in one filter | ACCEPTED |
| the shipped shape (`relationship_key` `$in` + `to` `$in`) | ACCEPTED |

**A3 HOLDS.** No predicate the hop filter needs is rejected; no `$expr` was required anywhere. The promotion proceeded on measurement, not on the assumption.

The same probe measured the three documented `$graphLookup` mismatches rather than trusting the manual:

- `maxDepth: 0` reached exactly the one-hop neighbours, `depthField` values `[0]` → **CCF hop *h* ↔ `depthField` *h−1*; `depth_limit=N` → `maxDepth: N-1`** confirmed;
- the starting document was **absent** from the `as` array at every depth → **explicit seed re-inclusion required**, confirmed;
- an out-then-in path (`a→b`, `d→b`; reaching `d` from `a`) **was** reachable over the doubled-edge collection at `maxDepth: 1` → **the doubling is what makes one directed stage express the undirected walk**, confirmed.

`depth_limit=0` remains inexpressible by the stage (`maxDepth: 0` is already one lookup), so the adapter skips the stage entirely and answers the walk starting points.

## What was built
