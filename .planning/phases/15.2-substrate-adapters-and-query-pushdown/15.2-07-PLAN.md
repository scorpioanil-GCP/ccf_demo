<objective>
Make operators declare pushability (D-03) and make the engine own the
multi-segment split (D-01 as amended by the D-IMPL-87 resolution): read_intent()
on the Operator surface, a pure segmentation function producing ALL alternating
pushed/in-process segments, and the engine's execute loop reworked to issue one
reader.query() per pushable segment — with every post-in-process segment
carrying the survivor set as seeds + allowed_entities under the uniform rule,
and the D-10 size-cap mechanism deciding push-vs-in-process for those segments.

This plan supersedes the void set's first-maximal-pushable-prefix treatment
entirely. Execution shape for pushed segments: the engine re-applies each pushed
segment's operators through cache.run over that segment's answer — sound because
the answer is a fixed point of its own operators (the GQ segment-answer
fixed-point clause, stated under the uniform rule in plan 15.2-01), and required
because provenance must be execution-derived (the repo's "engine records what
ran, never what was declared" pattern; minting provenance from plan-side
prediction was considered and rejected). The price is that Gate 2 must be
PINNED, not presumed: the end-to-end regression asserts lineage strict equality
for BOTH plan shapes, not only product canonical_bytes.

Cap mechanism (D-10): the engine accepts an optional survivor-cap value at
construction (keyword-only, default None = no cap — the SDK ships mechanism,
never a threshold constant; the Control Plane wiring and the replay dimension-2
pin land in plan 15.2-08). When a post-in-process segment's survivor count
exceeds the cap, the engine runs that segment's operators in-process over the
surviving view instead of pushing — always sound, no extra substrate read, and
visible in the executed query sequence. The same execution surface implements
D-10's final locked sentence — "pushed-vs-scanned telemetry (D-04) additionally
reports set sizes" — as an engine-level survivor-set size report, outside the
replay record exactly as the plan 15.2-05 reader counters are.

Hard constraints: execute()'s signature and plan.required_operators() stay
byte-stable (the 15.1 binder sits on those seams); the stage order (operators →
acquisition → Π) survives; the engine records what ran.

Output: read_intent across the four shipped operators, multi-segment
segmentation, the cap mechanism, the set-size telemetry, and the equivalence +
matrix + Gate-2 + cap regression tests. The replay-record pin fields land in
plan 15.2-08; this plan keeps the executed query values on the execution path
so 15.2-08 can thread them without touching the loop.
</objective>
