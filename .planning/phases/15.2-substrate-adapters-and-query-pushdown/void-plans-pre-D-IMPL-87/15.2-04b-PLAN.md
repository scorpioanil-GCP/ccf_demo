<objective>
The read-side twin of plan 15.2-02: extract the substrate-agnostic
materialization template — rows → records → canonical order → freeze, including
lineage-at-boundary and supersession-as-of rendering — out of BaseGraphReader's
SQL-ClassVar shape, so the four non-SQL readers this phase ships (memory in
15.2-05, ProductSource in 15.2-09, Neo4j in 15.2-10, Mongo in 15.2-11) inherit
the two rules reader.py exists to centralize instead of forking them.

This plan exists because cross-AI review (Consensus concern 3; RESEARCH
Pitfall 5) found the gap: today BaseGraphReader is "five SQL statements +
_query()", and _lineage() issues SQL itself — a non-SQL adapter could not
honestly reuse the shared layer without either faking SQL or re-implementing
lineage/supersession, in which case the differential suite would compare
accidents. After this plan, plan 15.2-04 builds query() on a materialization
core any row source can feed.

Behavior is byte-identical before and after; this is a confinement refactor in
the plan-02 mold: zero public-surface movement, zero test edits, one new
contract test.
</objective>
