## For the Gate Package (per the plan's output spec)

- **Re-application design choice.** Pushed segments' operators are re-applied through `cache.run` over the segment's answer, entitled by the GQ-19 segment-answer fixed-point clause (`GQ-19` at docs/GRAPH_QUERY_SEMANTICS.md:356) — re-application reproduces the substrate's answer bit-for-bit, so every provenance fact stays execution-derived. The rejected alternative — recording provenance without re-applying (minting from plan-side prediction) — would have made the provenance chain a declaration rather than a record, violating the repo's "engine records what ran" rule; the price paid is that Gate 2 is PINNED, not presumed: the end-to-end regression asserts lineage strict equality (`run_gates → ServableProduct`) for both plan shapes, not just product bytes.
- **Engine-level placement of the D-10 set-size telemetry.** The survivor set exists only at the engine (it is the entity URIs of the post-in-process view), and a capped segment issues no query at all — so a reader-level report could never see it. `last_survivor_set_sizes` is per-execution (reset at `execute()` start; deliberate contrast with the reader's monotonic `translated_answers`/`fallback_answers` counters), outside the replay record (D-04 — performance is never a replay input; the 15.2-08 no-telemetry pin covers it), and report-only (no threshold logic in the property; the cap decision lives only at the segment decision point).
- **Executed-queries threading shape for 15.2-08.** `ExecutionResult.executed_queries: tuple[GraphQuery, ...] = ()` (sentinel-defaulted), appended at each `reader.query()` call site in execution order (GQ-20). 15.2-08 threads `content_hash` of each entry into the Decision Replay record (D-11) and lands the canonical bytes in the ArtifactStore without touching the loop — execution facts already travel to `build_replay_record` via `ExecutionResult`, and this field rides the same path. No record field was added in this plan.

## Decisions Made

- **Seeds are not authored by the engine on post-in-process segments.** The plan's frontmatter phrase "survivors as seeds + allowed_entities" is implemented in the GQ-17 normative form: `allowed_entities = survivors`, `seeds = None` — walk starting points are computed *within* the set by the answerer (`seed_entity_classes` select within `allowed_entities`). Promoting every survivor to an explicit walk start would make every survivor a seed (seeds are included, GQ-10), widening the pushed answer beyond the in-process semantics — breaking both the GQ-19 fixed point and the byte-equivalence this plan must prove. GQ-15's own sentence is the authority: "seeds say where walks start, not which nodes they may cross." `compile_segment_query` still accepts a `seeds` parameter, so the seam remains capable of explicit seeds if a future design needs them. The threading test asserts `second.seeds is None` and that the answered walk-start data lies within the survivor set.
- **The per-operator equivalence property feeds `apply()` the answer-form view.** The raw degenerate everything-answer retains dangling edges (the GQ-05/GQ-21 pre-seam byte-compat carve-out); over such a view an in-process traversal could hop through an as-of-excluded phantom endpoint, which GQ-13 normatively excludes from any pushed answer. Since every mid-plan operator input in the segmented engine is an answer (pushed answers are constrained → endpoint-closed; in-process outputs close via `_substitute`), the property uses the endpoint-closed everything-answer, produced through the production fallback under a vacuous `allowed_entities` covering the drawable pool. Documented in the test docstring.
- **SUBQ-06 left Pending deliberately.** This plan's frontmatter lists SUBQ-06, but that requirement's sentence includes the D-11 replay-record hash-tuple pin and ArtifactStore query-bytes — plan 15.2-08's deliverables (15.2-08 also claims SUBQ-06). Marking it complete here would assert an untrue checkbox; 15.2-08 flips it. SUBQ-05 is fully delivered and marked Complete.
