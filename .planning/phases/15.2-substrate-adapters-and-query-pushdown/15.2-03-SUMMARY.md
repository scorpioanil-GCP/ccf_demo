## The Extraction Shape (read this, plans 06/10/12/13)

The entry point, module-level in `src/ccf/graph/reader.py`:

```python
def materialize_view(
    *,
    entity_rows: Sequence[Row],
    relationship_rows: Sequence[Row],
    tenant_id: str,
    as_of: datetime,
    lineage_rows_for: Callable[[str, str, str], Sequence[Row]],
) -> GraphView: ...
```

- **Row contract:** the existing `Row` Protocol (`__getitem__(str)`) — a plain `dict` qualifies. Entity rows carry the sqlite column names: `entity_uri`, `claim_id`, `claim_json`, `policy_bundle_version`, `superseded_by`, `superseded_at`; relationship rows carry `relationship_key` in place of `entity_uri`. `superseded_at` is canonical RFC3339 text or `None`; `claim_json` is the claim's JSON dump (its `lineage` field is overwritten from the supplier).
- **Row filter is the caller's job:** `entity_rows`/`relationship_rows` must already be the claims current at `as_of` under the source's own row filter (`observed_at <= boundary AND (superseded_at IS NULL OR superseded_at > boundary)`) — the one "as of" place a substrate expresses natively. The other two places (lineage set, supersession edge) are rendered inside the core and cannot be forked.
- **Lineage-supplier contract:** positional `(kind, node_key, claim_id) -> Sequence[Row]` where each returned row carries `entry_json` (a `LineageEntry` JSON dump). The supplier returns **every** accumulated entry for the claim — no boundary filtering; the core applies the boundary. Tenant scope is the supplier's own concern (the SQL client closes over its tenant; a dict source indexes however it likes). `kind` is `ENTITY_KIND` / `RELATIONSHIP_KIND` from the same module.
- **Ordering:** applied inside the core (entities by `entity_uri`, relationships by `relationship_key`, stable sort) — never trusted from the source. An unordered source materializes the same canonical bytes as a sorted one.
- **Visibility:** `materialize_view` is deliberately NOT in `__all__` and absent from the surface manifest — graph-tier internal API for callers inside `ccf.graph`. If plan 15.2-05 promotes the seam, the docs fragment belongs to that plan.

History reads (`entity_history` / `relationship_history`) delegate to the same module-level record builders with `boundary=None` — the whole accumulated lineage set and the full supersession chain are the answer there, per the docstrings.
