## What the seam carries — round trips

| Option | Description | Selected |
|--------|-------------|----------|
| Segmented, engine decides | Engine splits the plan at non-pushable boundaries; one query per pushable segment; replay pins every round trip's bytes | ✓ |
| Exactly one, pushable prefix only | Push the longest prefix; everything after runs client-side; with similarity present the prefix is policy alone | |
| Whole plan, adapter splits | Adapter absorbs what it recognizes, returns the residual; split under adapter control diverges provenance per substrate | |
| One visit, narrow the read only | Seam only scopes the initial read; operators unchanged; fixes scaling but pushes no work down | |

**User's choice:** Segmented, engine decides (recommended).
**Notes:** Question was reformulated at the user's request after they asked "What is in the OperatorPlan?" — inspection showed `OperatorPlan` is a one-field frozen dataclass (ordered operator instances) with intent living in `operator.parameters`, three of four categories statically pushable, and Similarity the exception (injected `SimilarityIndexProtocol`). The round-trip question (similarity sits *between* pushable operators) replaced the original seam-shape question.

## What the seam carries — segment request

| Option | Description | Selected |
|--------|-------------|----------|
| A typed query contract | Frozen `GraphQuery` value; adapters translate; `content_hash(q)` is replay's pin; adapters never see an Operator | ✓ |
| The plan segment itself | Adapter switches on `operator.key` and reads parameters; couples adapters to the registry key space; user-registered operators break pushdown | |
| Scoped read primitives | Narrow typed methods composed by the engine; the question is not a value so replay synthesizes a parallel record | |

**User's choice:** A typed query contract (recommended).
**Notes:** Accepted cost recorded: the query vocabulary is a fixed commitment — what it cannot express cannot be pushed, by anyone.

## Operator shape

| Option | Description | Selected |
|--------|-------------|----------|
| The operator declares it | Optional `read_intent() → QueryFragment \| None` from parameters alone; None = not pushable; custom operators pushable without SDK change | ✓ |
| An engine-side compiler | `compile_segment()` switches on category; operators unchanged byte-for-byte; custom operators never pushable | |
| A Control Plane artifact | Declared pushdown map (key → fragment template); wrong mapping = silently wrong rows, not a type error | |

**User's choice:** The operator declares it (recommended).
**Notes:** Named hazard captured for conformance: `read_intent()`/`apply()` divergence must be excluded by proving `apply(full) == apply(pushed(intent))`.

## Pushdown fallback

| Option | Description | Selected |
|--------|-------------|----------|
| Adapter always answers | No "I can't" in the Protocol; SDK ships one shared fallback helper; split depends only on the plan; trace identical everywhere; pushed-vs-scanned is telemetry | ✓ |
| Adapter declares capabilities | Engine re-splits per substrate; best perf shape; round-trip count and intermediate provenance become substrate-dependent | |
| Adapter refuses, engine retries | Typed PushdownUnsupported + recompile; wasted round trip; lazy per-query discovery; same trace divergence | |

**User's choice:** Adapter always answers (recommended).
**Notes:** This ruling fixed what "replay portability" means: rows AND trace match across substrates (total portability).

---

## Conformance suite

| Option | Description | Selected |
|--------|-------------|----------|
| Differential vs the fallback | The fallback helper is the executable spec; byte-identical assertion over a generated corpus; the helper defines truth | |
| Property assertions only | Named-invariant suite per adapter (existing test_graphstore.py pattern); no oracle; coverage bounded by imagination | |
| Written semantics + both suites | Normative prose defines semantics; fallback is its reference impl (citation-linted); differential + property suites, properties run on the fallback too | ✓ |

**User's choice:** Written semantics + both suites (Option 3).
**Notes:** User asked three clarifying questions before deciding: (1) what Option 3 really is — answered with the three-artifact triangle (prose decides, fallback executes, adapters agree, properties audit the oracle) and the circular-oracle weakness of Option 1; (2) a client-perspective walkthrough — the "Priya writes a DynamoDB adapter" scenario contrasting `depth_limit=0` discovery, dispute resolution, and upgrade behavior under each regime; (3) performance implications — none at runtime, marginal in CI, but Option 1 would freeze the fallback (it is both oracle and production degrade path) while Option 3 keeps it optimizable. Sequencing consequence recorded: prose is written first. Model note: user switched session model to Fable 5 mid-discussion (design-phase model mandate).

## Survivor-Constraint Mechanism

| Option | Description | Selected |
|--------|-------------|----------|
| In-query frozen field | `allowed_entities: frozenset \| None` on GraphQuery; query stays a value; content_hash pin unchanged; adapters translate natively | ✓ |

## Constraint Rule (same area)

| Option | Description | Selected |
