## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01 — Segmented pushdown; the engine owns the split.** The engine splits
  the operator plan at non-pushable boundaries and issues one substrate query
  per pushable segment. Round-trip count is plan-dependent; a later segment's
  seeds are data-dependent (survivors of an in-process segment). Replay pins
  **every** round trip's query bytes, not one. The conformance suite must pin
  the split itself, not only the results.
- **D-02 — The segment request is a frozen, typed `GraphQuery` contract**
  (tenant_id, as_of, policy_bundle_versions, entity_classes, seeds,
  traverse: `TraversalSpec`, require_valid_at_boundary — exact fields are the
  planner's to finalize against the semantics prose). `GraphReader.query(q)
  → GraphView`. The question is a *value*: `content_hash(q)` is replay's
  per-round-trip pin, and canonical ordering/serialization live in the
  interface, never in adapters (locked roadmap constraint 3). Adapters never
  see an `Operator`. Accepted cost: the query vocabulary is a fixed
  commitment — what it cannot express cannot be pushed, by anyone.
- **D-03 — Operators declare their own pushability.** The `Operator` Protocol
  gains one optional method: `read_intent() → QueryFragment | None`, computed
  from `self.parameters` alone — no view, no data, no clock, so purity is
  untouched. `None` means not pushable; the engine materializes for that
  segment instead. `apply()` keeps its exact current signature
  (`src/ccf/operators/base.py:142`); existing operators change only by
  *gaining* `read_intent()`. `SimilaritySelect.read_intent()` returns `None`
  (it consults an injected `SimilarityIndexProtocol` the substrate does not
  hold). A user-registered custom operator becomes pushable without an SDK
  change. **Named hazard the planner must design against:** `read_intent()`
  and `apply()` diverging returns silently different rows — conformance must
  prove `apply(full_view) == pushed(intent)` per shipped operator.
- **D-04 — Adapters always answer; there is no "I can't" in the Protocol.**
  A conformant adapter answers any well-formed `GraphQuery`, degrading
  internally to scan-and-filter. The SDK ships one reusable fallback helper
  (`ccf.graph.fallback`) so no adapter reimplements BFS. Consequence: the
  engine's split depends **only on the plan, never the substrate**, so
  round-trip count and provenance chain are identical everywhere — replay
  portability is total (rows *and* trace). What was actually pushed vs.
  scanned is telemetry, deliberately outside the replay record: performance
  is never a replay input. No capability negotiation, no typed
  pushdown-refusal path.
- **D-05 — Prose decides, fallback executes, adapters agree, properties audit
  the fallback.** Three artifacts: (1) normative semantics prose defining what
  a `GraphQuery` means — including deliberately-decided edge semantics
  (`depth_limit=0`, traversal through policy-excluded state, seed inclusion,
  empty answers) — written **first**; (2) `ccf.graph.fallback` as the
  reference implementation of that prose, docstrings citing clauses
  (enforceable via the existing `tools/lints/citations.py` citation-guard
  pattern); (3) two conformance suites: differential (every adapter
  byte-identical to the fallback over a generated query corpus) *plus*
  property assertions pinning named invariants (INV-CH7-14/-23/-24/-26) —
  with the property suite running **on the fallback itself**.
- **D-06 — All five adapters ship this phase** and run under both suites:
  `postgres.py` / `sqlite.py` (migrated; both already hold as-of SQL;
  traversal via recursive CTE), `memory.py` (**new** in-memory KV floor, zero
  dependencies, thin shell over `ccf.graph.fallback`, always-on in `make ci`),
  `neo4j.py` (**new**, Cypher variable-length MATCH, behind a `neo4j` extra,
  container-gated CI leg), `mongo.py` (**new**, `$match` + `$graphLookup`,
  behind an extra, container-gated CI leg; the Homecams triangulation point).
  **Named risk:** `$graphLookup` depth semantics do not match BFS exactly —
  Mongo is the hardest differential target; budget for it deliberately.
- **D-07 — `as_of()` is reframed, not deprecated: it is the
  everything-question.** `as_of(tenant, at) ≡ query(GraphQuery(tenant_id,
  as_of=at))` — the degenerate query with no predicates. `BaseGraphReader`
  derives `as_of()` from `query()`, so adapter authors implement **one**
  method. Zero churn across all 15 call sites; `src/ccf/replay/snapshots.py:108`
  keeps its legitimate everything-read; the 13 example call sites stay valid
  for Phase 16.
- **D-08 — Tier-2: same seam, admitted at mount.** A `ProductSource`
  implements the same `GraphReader.query()` Protocol. Its constructor accepts
  **only** an `AdmittedProduct` — the type `PeeringAdmissionGate.admit()`
  alone can produce (`AdmissionBypassError` already enforces
  unconstructability) — so "admission is a seam every non-graph source passes
  through" becomes a **type-system property**; tier 3 later means another
  gate producing the same admitted wrapper, zero refactor. `ProductSource`
  needs no query engine: the shared fallback answers over the product's
  records. The view is ephemeral; nothing enters L3 — single-writer is not
  implicated. Products whose payload carries no graph-shaped state refuse at
  **mount** with a typed refusal. The same differential suite runs on
  `ProductSource`.
- **D-09 — A typed `SourceAttestation` contract with per-dimension modes**,
  one closed Literal per provenance dimension:
  `policy_binding: assembly-stamped | admission-verified | none`;
  `lineage: graph-supplied | product-carried | none`;
  `peer: PeerRef | None`. The three tiers are three well-known **values** of
  one schema — tier 3 (`none`/`none`/`None`) is expressible today.
  `GraphReader` gains an `attestation` property; product classes declare
  per-dimension minima; the engine refuses a source below minimum with a
  typed refusal **naming the failing dimension**. Canonically serializable,
  so the attestation in force pins into replay. Temporal correctness is *not*
  an attestation dimension — as-of is a conformance obligation every source
  owes.

## Summary

This phase replaces the fabric's single materialized read
(`src/ccf/projection/engine.py:262`, the only `as_of()` call in the execution
path) with a segmented query loop against a new `GraphReader.query(GraphQuery)
→ GraphView` seam, and ships five adapters that answer it plus a tier-2
`ProductSource` that mounts an `AdmittedProduct` behind the same Protocol. The
good news from the code audit: the repo is unusually well-positioned. Both SQL
backends already implement the exact as-of predicate the seam needs
(`SELECT_ENTITIES_AS_OF` — `observed_at <= ? AND (superseded_at IS NULL OR
superseded_at > ?)`); the `relationships` table carries `subject_uri` /
`object_uri` / `relationship_type` as real columns, so recursive-CTE traversal
needs no JSON parsing; `content_hash` already provides the per-round-trip
replay pin with zero new mechanism; `BaseGraphWriter` is already
substrate-neutral over `_Store`/`_Txn` Protocols, so the three new backends add
transaction classes rather than writer modules; and the tier-2 governance
(`PeeringAdmissionGate`, `AdmittedProduct`, `AdmissionBypassError`) is complete
and needs zero change.

The hard parts are semantic, not mechanical, and the planner should budget for
them explicitly. (1) **The pushed-traversal leak hazard**: the in-process path
runs traversal over a view that Policy/Similarity/Temporal already pruned; a
pushed traversal walks the substrate's *full* graph unless the query carries
the upstream predicates as *path* constraints — a walk that hops through a
policy-excluded node leaks reachability, violating the substitution semantics
(INV-CH7-40) at the substrate tier. Every hop, not just every result, must
satisfy the segment's predicates. (2) **Mongo's `$graphLookup` mismatch**:
verified against official docs — it is *directed* (connectFromField →
connectToField) while CCF BFS is undirected; its `maxDepth: 0` means one
lookup (one hop), so `depth_limit=N` maps to `maxDepth=N-1` and
`depth_limit=0` cannot be expressed by the stage at all; and the starting
document is excluded while CCF includes seeds. (3) **Cypher quantifier
bounds** are (almost certainly — see Assumptions Log) not parameterizable, so
the Neo4j adapter must inline a validated integer depth into query text, a
deliberate, documented exception to the no-string-built-queries discipline.
(4) **The replay-record extension** must follow the `workflow_step_sequence`
sentinel precedent to avoid breaking canonical hashes of existing records.

**Primary recommendation:** Build in strict dependency order — semantics prose
first (D-05 requires it), then `GraphQuery` + `ccf.graph.fallback` + the
property suite over the fallback, then `memory.py` (the trivially-conformant
floor that also *is* the `ProductSource` engine), then the engine's
segmentation loop against the fallback-backed reader, then migrate
SQLite/Postgres, then Neo4j, then Mongo last with a deliberate risk budget
(ship `$match` pushdown + fallback traversal first if `$graphLookup`
differential parity resists; D-04 makes that legitimate and invisible to
replay).

## Project Constraints (from CLAUDE.md)

Directives that bind this phase's plans (all verified against `CLAUDE.md` rev 4):

- **Whitepaper fidelity wins conflicts** (§1). Cite whitepaper §7.3/§7.4/§7.10
  in public docstrings; SDK extensions (ProductSource, attestation) cite
  CLAUDE.md/DECISIONS.md and are labeled SDK-defined (§11).
- **Mechanism, not values** (§11, CINV-01): no domain values, thresholds, or
  defaults in `/src`. `GraphQuery` fields must be required-at-construction;
  parameter contracts declare fields, never defaults (D-IMPL-38 pattern).
- **Single-writer** (§10, INV-CH7-10, CINV-02): every new backend's write
  statements live in `ccf.graph._writer` only; no adapter acquires a write
  handle; `ProductSource` holds no writer and nothing it answers enters L3.
- **Harness neutrality** (§7.3): zero harness imports in `/src` — none of the
  new modules touch harnesses; CI lint enforces.
- **Algorithmic ⇄ Semantic Alternation** (CINV-03): every new graph/operator
  module carries `__ccf_mode__ = "algorithmic"`; no LLM client imports.
- **No-Hardcoding Rule** (§6.4): conformance corpora and example artifacts
  carry domain values in artifacts/fixtures, never in `/src`.
- **Refusals are returned values; exceptions mean broken deployments** (Phase
  04 decision, STATE.md): attestation refusals and mount refusals are typed
  returned values; a substrate that cannot be reached is an exception.
- **Surface discipline** (ERGO-01/ERGO-12): Protocol/type changes require
  `make surface` regeneration; artifact-class schema changes (e.g., attestation
  minima on product-class declarations, `DeploymentManifest.backend` Literal
  extension) require `make schemas` regeneration and pass the `$schema`
  freshness gate.
- **Do not disturb Phase 15.1 seams**: the binder
  (`ccf.deployment.binder::refuse_operator_set_divergence`, signature
  `(*, declared, plan) -> None`) sits between plan construction and
  `ProjectionEngine.execute` in adopter code; the registration seams
  (`ManifestEntry.registration` typed|versioned dispatch,
  `refuse_registration_the_sdk_fixes` preflight, `ccf.` namespace prefix
  reservation). Segmentation is internal to `execute()`; keeping
  `execute()`'s signature and `plan.required_operators()` stable keeps the
  binder untouched. Any new SDK artifact class must respect the registration
  dispatch and namespace reservation.
- **Decision-log discipline** (§12, §15): whitepaper-silent commitments the
  planner cannot resolve inside the locked decisions become `D-IMPL-NN`
  entries for Dave, not defaults.

### Pattern 1: Template-method `query()` in `BaseGraphReader` (constraint 3 made structural)

**What:** `BaseGraphReader.query()` is the one concrete implementation of
ordering, record materialization, and freezing; adapters implement a narrower
substrate hook (today's shape: five `ClassVar` statements + `_query()`; the
new shape: answer "which claim rows survive this `GraphQuery`"). `as_of()`
becomes `return self.query(GraphQuery(tenant_id=..., as_of=at))` — one method
for adapter authors (D-07).

**Why this repo already argues for it:** `reader.py`'s module docstring is
explicit that the bitemporal read has three places "as of" must hold — row
filter, lineage set, supersession edge — "and only the first of them is
expressible in SQL." If adapters materialized their own records, the
differential suite would assert that five independent implementations of the
lineage-at-boundary rule happen to agree. Keep `_lineage(boundary=...)`,
`_supersession_as_of`, and the sort in shared code; let adapters answer rows.

**Consequence for non-SQL adapters:** Neo4j/Mongo adapters return
row-equivalents (the `Row` Protocol is just `__getitem__(str)` — a dict
satisfies it), or the planner generalizes the hook. Either way the shared
layer is the only place canonical bytes are produced.

### Pattern 2: Segment compilation (D-01 + D-03)

**What:** Walk the ordered plan; group maximal runs of operators whose
`read_intent()` is non-`None`; union the run's `QueryFragment`s into one
`GraphQuery`; issue it; run the non-pushable operator(s) in-process over the
returned view; survivors seed the next segment's `GraphQuery.seeds`.

**Load-bearing detail — the split is static:** D-04 fixes that the split
depends only on the plan. `read_intent()` is computed from `self.parameters`
alone, so the segment structure is knowable before execution — which is what
lets the conformance suite "pin the split itself" (D-01): assert the segment
boundaries and per-segment fragment union as a pure function of the plan.

**Provenance:** the recorded query sequence comes from execution (the
established "engine records what ran" rule — `operators_invoked` is built in
the loop, never copied from the plan). Record `content_hash(q)` per issued
query, in order.

### Pattern 3: Fallback as the one BFS (D-04)

**What:** `ccf.graph.fallback` = pure functions over
`(entities, relationships, GraphQuery) → surviving records`, implementing the
prose clause by clause, docstrings citing clauses. `memory.py` is a dict-backed
store + this fallback. `ProductSource` is the same fallback over the product's
payload records. SQL/Neo4j/Mongo adapters call it when they choose not to
translate a query shape.

**Key property:** because the fallback is a *production* degrade path (not a
test helper), the property suite runs on it (D-05 artifact 3) and the
differential suite compares every adapter against it — the oracle is audited
by something it does not define (the prose + the invariant properties).

### Pattern 4: Attestation as data (D-09)

**What:** `SourceAttestation` is a frozen contract of closed Literals; each
reader exposes it as a property; product classes declare per-dimension minima;
the engine compares before the first read and returns a typed refusal naming
the failing dimension (refusal-value convention, not an exception). Tier-1
readers all share one well-known value (`assembly-stamped` / `graph-supplied`
/ `None`); `ProductSource` carries (`admission-verified` / `product-carried` /
`PeerRef`); tier 3 is expressible today as (`none`/`none`/`None`).

### Pattern 5: `SnapshotReader` gains `query()` (replay correctness)

`SnapshotReader` (`src/ccf/replay/snapshots.py:61`) structurally conforms to
`GraphReader` and pins `(tenant_id, temporal_boundary)`. Once the engine reads
via `query()`, a replayed execution issues `query()` calls — so
`SnapshotReader` must implement `query()` with the same scope check
(`q.tenant_id` and `q.as_of` must match the snapshot; anything else is a
`SnapshotScopeViolation`) and delegate to the live reader. Replay verification
then compares the re-executed query-hash sequence against the recorded pins.
The `snapshots.py:108` everything-read stays valid under D-07 unchanged.

### Anti-Patterns to Avoid

- **Adapter-side ordering or serialization** — a mis-sorting adapter must be
  *unable* to change product bytes; sort in the interface even when the
  substrate already sorted (locked constraint 3).
- **Capability negotiation / pushdown-refusal types** — explicitly ruled out
  by D-04. No `can_push()`, no `PushdownUnsupported`.
- **A tier-2-shaped admission special case** — `ProductSource` must accept
  `AdmittedProduct` (the wrapper), not `ContextProductContract` + flags;
  tier 3 arrives as another gate producing the same wrapper (constraint 2).
- **Extending `LineageEntry` or graph state for tier-2 provenance** —
  D-IMPL-58 reading (d) already settled that lineage continuity is a property
  of the federation boundary (`AdmissionRecord` artifact), not of graph state.
- **A second hashing or timestamp convention** — `content_hash` and
  `canonical_timestamp` are the only ones; substrate-native timestamp columns
  are the documented cross-backend drift trap (04-RESEARCH Pitfall 3, cited in
  both backends). New backends store canonical text, even in Neo4j/Mongo where
  native temporal types are available.
- **Clock reads anywhere below the caller** — `GraphQuery.as_of` arrives as
  data, exactly as `temporal_boundary` does today.

## Substrate Query-Capability Triangulation

How each D-06 substrate expresses the three pushable predicate families
(as-of, policy/class filters, bounded typed traversal). Timestamps are
canonical RFC3339 UTC text in every substrate (fixed-width → lexicographic
order is chronological), so string comparison expresses temporal predicates
everywhere — this repo decision is what makes the whole matrix workable.

### SQL (SQLite + Postgres) — migration, not rewrite

- **As-of:** already shipped — `SELECT_ENTITIES_AS_OF` /
  `SELECT_RELATIONSHIPS_AS_OF` carry `observed_at <= ? AND (superseded_at IS
  NULL OR superseded_at > ?)` in both dialects [VERIFIED: sqlite.py:229,
  postgres.py:269].
- **Policy/class:** `policy_bundle_version` is a column (direct predicate);
  classification attributes and `valid_from`/`valid_to` live inside
  `claim_json` → `json_extract(claim_json, '$.attributes.<attr>')` in SQLite
  (verified working on local 3.45.1); Postgres via `claim_json::jsonb ->> ...`
  or `json_extract_path_text` [VERIFIED locally for SQLite; Postgres jsonb
  operators are decades-stable — HIGH].
- **Traversal:** `WITH RECURSIVE` in both (SQLite since 3.8.3; verified
  working locally; Postgres since 8.4). The `relationships` table carries
  `subject_uri`/`object_uri`/`relationship_type` as columns — the recursive
  term joins on columns, no JSON parsing. **Undirected**: the recursive term
  must UNION both directions. **Depth**: carry a `depth` column in the CTE,
  bound with `WHERE depth < ?` — the bound is a parameter, no literal
  inlining needed in SQL. **Hop admissibility**: the recursive term must join
  through `relationship_claims` (as-of predicate) and against admissible
  entities (see Pitfall 1).

### In-memory KV floor (`memory.py`)

Needs nothing from a query engine: dict-of-records per tenant, the fallback
answers. What it *does* need: a `_Txn` class in `ccf.graph._writer` (the
`_Store`/`_Txn` Protocols at `_writer.py:198/205` are already
substrate-neutral) and boot wiring so the conformance suite can write through
L2 like every other backend. Zero dependencies, always-on in `make ci`,
and it doubles as the teaching example and the `ProductSource` engine.

### Neo4j (Cypher)

- **As-of:** claims as nodes/relationship-properties carrying `observed_at` /
  `superseded_at` as canonical text; `WHERE c.observed_at <= $boundary AND
  (c.superseded_at IS NULL OR c.superseded_at > $boundary)` — string
  comparison is chronological. Physical layout is backend-internal
  (D-IMPL-34), so the adapter designs its model for this predicate.
- **Traversal:** undirected variable-length pattern
  `MATCH p = (seed)-[:TYPE*0..N]-(x)` or quantified path patterns. **The
  bounds almost certainly cannot be parameters** (`*0..$depth` is rejected;
  see Assumptions Log A2) — the adapter inlines a validated non-negative
  integer into the query text. This is a *named, documented* exception to the
  no-string-built-queries rule (see Security Domain); everything else stays
  parameterized. Replay is unaffected: the pinned value is
  `content_hash(GraphQuery)`, not the rendered Cypher (D-02).
- **Hop admissibility:** path predicates —
  `all(n IN nodes(p) WHERE <policy/temporal predicates>)` — so no path hops
  through an excluded node (Pitfall 1).
- **Multiple relationship types:** `[:A|B|C*0..N]` unions types in the
  pattern; the type set is dynamic, so the adapter builds the type list from
  validated identifiers or filters with `all(r IN relationships(p) WHERE
  type(r) IN $types)` (parameterizable, slower). [ASSUMED: performance
  tradeoff; correctness of both forms is standard Cypher.]
- **CI leg:** `neo4j:5-community` (or 2025.x) service container, gated by a
  `neo4j` pytest mark, following the `postgres` service pattern in
  `.github/workflows/ci.yml:55–57,113`.

### MongoDB (`$match` + `$graphLookup`) — the hardest differential target, by design

Verified against the official manual
[CITED: mongodb.com/docs/manual/reference/operator/aggregation/graphLookup/]:

- **`maxDepth: 0` = non-recursive** — one lookup only. `depthField` starts at
  **0 for the first match**. The **starting document is not included** in the
  `as` array. Therefore: CCF hop *h* (1-based) ↔ `depthField` *h−1*;
  `depth_limit=N` → `maxDepth: N-1`; **`depth_limit=0` (seeds only) cannot be
  expressed by the stage at all** — the adapter must skip `$graphLookup` and
  return seeds. Seeds must be re-added to results explicitly (CCF includes
  seeds; `$graphLookup` excludes the start).
- **Directed:** follows `connectFromField → connectToField` only. CCF BFS is
  **undirected**. Two directed `$graphLookup`s do *not* compose — an
  alternating-direction path (out, then in) is reachable by neither. The
  clean resolution: the Mongo backend owns its physical layout (D-IMPL-34),
  so store each admissible edge as **two traversal documents** (forward +
  reverse) and run one `$graphLookup` over the doubled collection.
- **Hop admissibility:** `restrictSearchWithMatch` applies a filter to
  documents *during* traversal — the hook for policy/temporal predicates on
  every hop [ASSUMED: exact operator restrictions inside
  `restrictSearchWithMatch` (e.g., no `$expr`) not verified this session —
  verify at implementation].
- **Operational bounds:** 100 MB stage memory; spills to temp files unless
  `allowDiskUse: false` (then errors). Sharded `from` allowed on MongoDB
  5.1+; not usable in transactions targeting sharded collections. Single-node
  CI containers are unaffected.
- **De-risking path (recommended):** D-04 makes "push `$match`
  (as-of + policy + class predicates), scan traversal via the fallback" a
  fully conformant first landing — byte-identical results, identical replay
  trace, only telemetry differs. Promote traversal to `$graphLookup` once the
  differential corpus passes. This turns D-06's named risk into a bounded,
  incremental task instead of a phase tail.
- **CI leg:** `mongo:7` (or 8) service container behind a `mongo` mark.

### Gremlin/Neptune (out of scope — design accommodation only)

The seam accommodates it by construction: a future `gremlin.py` implements
`query()`, inherits ordering/materialization from the interface, and proves
itself against the D-05 suites without SDK change. Nothing this phase builds
may assume SQL-shaped or Cypher-shaped substrates — the fallback floor is the
existence proof that no query engine at all is required.

## Common Pitfalls

### Pitfall 1: Pushed traversal leaking through excluded state (the big one)
**What goes wrong:** In-process, `TraversalNeighborhood` walks the view that
Policy/Temporal (and possibly Similarity) already pruned — an edge to an
excluded node "is not a hop this walk can take" (categories.py:304). A pushed
traversal walks the *substrate's full graph*: a path seed→X→target where X is
policy-excluded returns `target`, leaking X's existence by reachability and
violating the substitution semantics (INV-CH7-40) at the substrate tier.
**Why it happens:** Predicates applied to the *result set* instead of to
*every node and edge on the path*.
**How to avoid:** The semantics prose must state hop admissibility explicitly
(the CONTEXT already names "traversal through policy-excluded state" as a
deliberately-decided edge semantic). Mechanically: recursive-CTE recursive
terms carry the policy/temporal predicates; Cypher uses
`all(n IN nodes(p) WHERE ...)`; Mongo uses `restrictSearchWithMatch`; the
fallback prunes before walking (as `categories.py` does today).
**Warning signs:** differential failures only on corpus entries with
multi-hop paths through mixed-admissibility neighborhoods — make the corpus
generator produce exactly those.

### Pitfall 2: The post-materialization segment (survivors as constraints, not just seeds)
**What goes wrong:** After an in-process Similarity segment, entities have
been *removed* from the view. If a later pushed segment's traversal may not
pass through removed entities, `seeds` alone under-specifies the query — seeds
say where walks start, not which nodes they may cross. A pushed segment-2
traversal over the substrate can re-reach entities Similarity removed.
**Why it happens:** The `GraphQuery` vocabulary (D-02) has `seeds` but the
survivor *set* is the real constraint.
**How to avoid:** This is squarely inside Claude's discretion
("segment-boundary mechanics") but it is load-bearing: either the vocabulary
carries an allowed-node set (potentially large — the phase exists because
shipping whole graphs does not scale), or the split rule makes segments after
an in-process segment non-pushable for traversal, or the prose defines
segment-2 semantics as "walk the substrate, then intersect" (which changes
results and would fail the D-03 equivalence property). The planner must pick
one and encode it in the prose *before* the fallback is written. Note the
common case is unaffected: a plan with no Similarity is one fully-pushable
segment (Policy → Temporal → Traversal), which is also the D-07 degenerate
path when nothing is pushable.
**Warning signs:** `apply(full_view) == pushed(intent)` holding per-operator
but failing per-*plan* on plans containing Similarity.

### Pitfall 3: `$graphLookup` off-by-one, direction, and seed exclusion
**What goes wrong:** Three independent mismatches compound: `maxDepth` is
0-based relative to the first lookup (CCF `depth_limit=N` → `maxDepth=N-1`);
`depth_limit=0` is inexpressible (skip the stage); the starting document is
excluded (CCF includes seeds); and the stage is directed while CCF BFS is
undirected — two directed lookups cannot express alternating-direction paths.
**How to avoid:** Doubled-edge physical layout (forward + reverse traversal
documents — the backend owns its layout per D-IMPL-34), explicit seed
re-inclusion, `maxDepth` offset, and stage-skip at depth 0 — each a named
clause in the semantics prose mapping table. Ship `$match`-only pushdown
first (D-04 makes it conformant), promote traversal after parity.
[CITED: mongodb.com/docs/manual/reference/operator/aggregation/graphLookup/]
**Warning signs:** differential failures clustered at depth 0/1 and on
mixed-direction paths.

### Pitfall 4: Breaking canonical hashes when extending the replay record
**What goes wrong:** `canonical.py` normalizes models field-by-field over
`type(value).model_fields` — adding *any* field to `ContextFabricSnapshot` or
`ContentGenerationPath` changes the canonical bytes (and content addresses) of
every newly-rendered record, and re-derivations of *old* records stop
matching their stored addresses.
**Why it happens:** `extra=forbid` + frozen + canonical hashing makes contract
shape part of identity — deliberately.
**How to avoid:** Follow the one precedent that already navigated this:
`ContentGenerationPath.workflow_step_sequence: str = NO_WORKFLOW_TRACE`
(record.py:334) — a sentinel-defaulted field added when workflow traces
landed, with the sentinel as a *positive* assertion ("this decision issued no
segmented queries"). The query sequence is a dimension-5 fact (how the product
came to be — it is the executed read path), and D-01's "pins query bytes"
lands naturally as an ordered tuple of per-round-trip hashes or a
pre-serialized canonical block, exactly as the workflow seam did. The planner
must verify how replay *compares* old records before finalizing (whether any
path re-derives content addresses of historical records), and state the
compatibility claim in the plan.
**Warning signs:** replay tests green on new records, red on any fixture
recorded before the phase.

### Pitfall 5: Forking the record-materialization rules per adapter
**What goes wrong:** An adapter that builds its own `EntityRecord`s
re-implements lineage-at-boundary and supersession-as-of — the two rules
`reader.py` explicitly centralizes because a divergence "would report a
Postgres bug rather than a divergence."
**How to avoid:** The `query()` template method (Architecture Pattern 1).
Adapters answer rows/row-equivalents; the interface materializes, orders,
freezes. This is also what makes constraint 3 ("ordering and serialization
belong to the interface") structural.
**Warning signs:** an adapter importing `EntityRecord` construction paths, or
lineage queries appearing in adapter modules.

### Pitfall 6: Conformance suites that bypass single-writer
**What goes wrong:** The differential suite needs identical data in five
substrates; the tempting shortcut is a test-only bulk loader writing directly
to each substrate — demonstrating exactly the bypass the D-IMPL-41 stack
prevents, and skipping the write-path code (idempotent upsert, lineage union,
supersession) whose outputs the reads depend on.
**How to avoid:** The existing suite's discipline (test_graphstore.py
docstring: "Nothing constructs a writer. Every write goes through the L2
admission path on a fabric booted by the real composition root"). This forces
the prerequisite the plans must include: new backends need `_Txn` classes and
boot wiring *before* their conformance legs can run (see Open Question 4).
**Warning signs:** any conformance module importing from `ccf.graph._writer`.

### Pitfall 7: Cypher quantifier parameterization and injected depth
**What goes wrong:** `*0..$depth` is rejected by Cypher (Assumptions Log A2);
the workaround — inlining depth into query text — collides with the repo's
"no f-string SQL" discipline, and a sloppy implementation opens injection.
**How to avoid:** One named exception: depth (and possibly the relationship
type list) is validated (`isinstance(int)`, `>= 0`, bounded) and formatted
into the template at a single site with a docstring citing this decision;
tenant ids, boundaries, seeds, and every other value remain driver
parameters. Verify the limitation empirically at implementation (one driver
round trip) before committing to the workaround.
**Warning signs:** more than one string-formatting site in `neo4j.py`.

### Pitfall 8: Prose-clause citations that rot
**What goes wrong:** D-05 wants fallback docstrings citing prose clauses,
enforced by `tools/lints/citations.py` — but a `GRAPH_QUERY_SEMANTICS.md:NNN`
line-number citation rots on every prose edit (cite01 checks line existence,
not content), silently un-binding the oracle from its authority.
**How to avoid:** Give clauses stable backticked IDs (e.g., `` `GQ-07` ``) in
the prose and cite in cite02's *anchored* form (backticked anchor immediately
before `file:line`), so the lint verifies the cited lines still hold the
anchor token; an edit that moves a clause without updating citations goes red.
The citation-guard's own docstring documents exactly this binding model.
**Warning signs:** the `--report` unanchored-citation count rising as the
fallback lands.

### Pitfall 9: Similarity accidentally becoming pushable
**What goes wrong:** A well-meaning implementation gives `SimilaritySelect` a
`read_intent()` that pushes its *class pass-through* filter. But the operator
consults an injected index at apply time — any pushed fragment either
duplicates or contradicts the index's verdict.
**How to avoid:** `SimilaritySelect.read_intent()` returns `None`, full stop
(locked by D-03 and re-affirmed in Deferred Ideas). The conformance suite
should assert the shipped operators' pushability matrix explicitly (three
pushable, one not) so a drive-by "optimization" fails a named test.

### Bounded undirected traversal via recursive CTE (SQLite/Postgres; verified pattern locally on SQLite 3.45.1)
```sql
-- Sketch: hop admissibility enforced in the recursive term (Pitfall 1).
-- Depth is a parameter here — no literal inlining needed in SQL.
WITH RECURSIVE walk(uri, depth) AS (
    SELECT e.entity_uri, 0
    FROM entities e
    WHERE e.tenant_id = :tenant AND e.entity_class IN (:seed_classes...)
      -- + the segment's policy/temporal predicates on the seed's current claim
  UNION
    SELECT CASE WHEN r.subject_uri = w.uri THEN r.object_uri
                ELSE r.subject_uri END,          -- undirected: both endpoints
           w.depth + 1
    FROM walk w
    JOIN relationships r
      ON r.tenant_id = :tenant
     AND (r.subject_uri = w.uri OR r.object_uri = w.uri)
     AND r.relationship_type IN (:types...)
    JOIN relationship_claims rc                   -- as-of on the edge claim
      ON rc.tenant_id = r.tenant_id
     AND rc.relationship_key = r.relationship_key
     AND rc.observed_at <= :boundary
     AND (rc.superseded_at IS NULL OR rc.superseded_at > :boundary)
    WHERE w.depth < :depth_limit
    -- + hop-admissibility predicates on the reached entity's current claim
)
SELECT DISTINCT uri FROM walk
```
