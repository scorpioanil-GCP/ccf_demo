The non-traverse predicate families are answered **in the engine**, byte-identical

## The headline: the trap is real, and it was demonstrated

This is the plan's most important result, because it is the one that could not be
obtained by reading the code.

| Layer | Under normal operation | With `_translate_query` monkeypatched to `None` |
|---|---|---|
| **2** — differential byte-identity (7 tests, full corpus) | **7 passed** | **7 passed — STILL GREEN** |
| **3** — pushdown telemetry | **passed** | **FAILED: `assert 0 == 4`** |

A `_translate_query` that never runs passes the **entire** differential corpus.
D-04/`GQ-34` make the degraded posture byte-identical *by design*, so layer 2
cannot distinguish a working translation from an absent one — which is exactly
the defect the 15.2 §3.1 review caught on Neo4j, where the leg's whole evidence
was the corpus.

The falsification harness lived only in the scratchpad (a `pytest_sessionstart`
plugin); nothing was edited in the tree and `git status` was confirmed clean
after the run.

**Consequence worth carrying forward:** any future substrate adapter that claims
pushdown on a green differential suite alone is claiming something its evidence
cannot support. The telemetry assertion is not a supplement — it is the only
layer that discriminates.

## Which F-A6 branch the policy family took — quoted

**The FAILED branch**, as plan 15.3-01 measured:

> "F-A6 FAILED as expected, and fails SILENTLY. The resolution is the write-time
> ccf_policy_key materialization (D-07 rung 1) … but NOT in the form the plan
> named: `any(k IN $keys WHERE k IN c.prop)` is rejected 400 because an IN
> right-hand side must be an inline list or a parameter, never a property
> expression. The working form is `c.ccf_policy_key IN $keys` + RETURN DISTINCT,
> which the multi-value fan-out makes semantically identical."

So `_ENTITY_POLICY` is:

```cypher
  AND c.ccf_policy_bundle_version IN $policy_versions
  AND c.ccf_policy_key IN $policy_keys
```

with `$policy_keys` computed in Python and the survivors statement carrying
`RETURN DISTINCT`. `grep -c '\[$attribute_by_class' src/ccf/graph/backends/fluree.py`
returns **0**.

Two properties of this resolution are worth stating because they are *better*
than the predicate it replaced, not merely equivalent:

1. **No artifact-authored string enters query text at all.** The keys are
   literal values in a parameter list. Neo4j's form puts the attribute *name*
   into map-parameter content resolved as a property accessor; this one does not
   name an attribute anywhere in the statement.
2. **It is unaffected by `attribute_predicate`'s charset gate.** A refused
   attribute name still contributes its policy key, because a key is a value.
   So wave 2's Rule-2 addition costs no pushdown on the family that matters —
   as its own docstring predicted, now confirmed by the corpus.

## Deviations from Plan

### 1. [Rule 2 — Missing validation] A third decline: the policy key's separator-injection guard

- **Found during:** Task 1, writing the key construction
- **Issue:** The materialized key is `f"{class}\x00{attr}\x00{value}"`. Wave 1
  argued the NUL separator is safe because it "is code-authored and impossible in
  a CCF class or attribute name" — but that argument covers the *class* side
  only. Attribute **names** and permitted **classification values** are both
  artifact-authored, and a NUL in either makes the encoding non-injective: a
  query with `attr="a\x00b"`, `permitted={"c"}` produces the same key as a stored
  claim with `name="a"`, `value="b\x00c"`. The pushed answer would admit a claim
  the fallback excludes — a T-15.2-03 divergence, and precisely what the
  differential bar exists to catch.
- **Fix:** `policy_key()` returns `None` when any component carries the
  separator, and `_translate_query` declines the whole query. A read-side guard
  is **sufficient and complete**: a key built from NUL-free components carries
  exactly two separators and splits one way only, so it can never equal a stored
  key whose components smuggled one in (which would carry three or more).
- **Why a decline rather than an error:** nothing is refused. The fallback
  answers the whole query byte-identically and the event is visible in
  `fallback_answers` — the D-04 posture, not a new failure mode.
- **Files:** `src/ccf/graph/backends/fluree.py`
- **Commit:** `be32f9c`

### 2. [Rule 3 — Structural] The separator lives on both sides of the CINV-02 boundary, bound by a test

- **Issue:** The write half (`_POLICY_KEY_SEPARATOR` in `ccf.graph._writer`) and
  the read half must agree exactly, but the import can only run one way:
  `_writer.py` imports `backends/fluree.py`, and the reverse would both cycle and
  violate CINV-02's confinement.
- **Options considered:** (a) move the constant into `backends/fluree.py` and
  have `_writer.py` import it — structurally strongest, but it **deletes lines
  from `_writer.py`**, disturbing wave 2's measured `864 added / 0 deleted`
  SUBQ-13 headline and touching a file outside this plan's declared
  `files_modified` in a phase with an explicit change-surface gate; (b) duplicate
  the constant and bind the two with an executable assertion.
- **Chosen: (b).** `_writer.py` is untouched (`git diff --numstat` prints
  nothing for it). `test_the_write_path_materializes_exactly_the_key_the_read_path_pushes`
  runs a real claim through `_fluree_claim_projection` and compares the result
  against `policy_key()`, so a drifted separator fails CI instead of producing a
  policy family that silently matches nothing — the same silent-failure class
  F-A6 caught.
- **Commit:** `be32f9c`

### 4. [Criterion vs. action text] The dynamic-access mention, fixed by rewording

`grep -c '\[$attribute_by_class'` initially returned **1** — inside the `#:`
docstring the plan's own action step 2 *mandates* ("the `#:` docstring must state
…"; "Under no circumstances port `c[$attribute_by_class[ec]]` unprobed").

Unlike deviation 3 this one **could** be fixed properly, so it was: the comment
now says "dynamic property access — `c[$key]` with the attribute name supplied as
map-parameter content (`backends/neo4j.py:335-340`)", which is the phrasing wave 1
and the module docstring already use. No meaning lost, citation preserved, and the

### 5. [Scope] `_EDGE_TYPES` is defined but not assembled in stage 1

Plan-directed (action step 1 names all nine fragments and asks for `_EDGE_TYPES`'s
`#:` note verbatim in argument), but stage 1 declines every traverse query, so the
only field that supplies `$types` never reaches an assembled statement. It is
consumed by plan 15.3-04. Recorded under Known Stubs rather than left implicit.

### 6. [Honest limit] The byte-budget guard's second check happens after one round trip

The survivors statement is measured **before** any request — that is where
`allowed_entities`, the caller-influenced term, lands. The edges statement carries
`$survivors`, which is server-derived, so its check necessarily follows the first
round trip. A decline there still returns `None` and the fallback answers the
whole query correctly; the cost is one wasted request, which is performance, not
correctness. Stated because the plan's phrasing ("deliberately *before* any round
trip") is true of the depth ceiling and only partly true of the byte budget.

### 7. [Rule 3 — Blocking] The worktree has no `.venv`

`make`'s `$(PYTHON)` is `.venv/bin/python`, absent in a GSD worktree. Every gate
ran as `PYTHONPATH=src:runtime /home/parkave/ccf_code/.venv/bin/python -m …` —
the main checkout's interpreter with the **worktree's** `src` on the path, which
is the DI-15.2-04 discipline (`$(ENV)` is what makes the tree under test the tree
that changed). `make leg-fluree` itself is correct for CI and a normal checkout.
