# Phase 15.3 Review Fixes: CR-01 Summary

Closed the one **Critical** finding from `15.3-REVIEW.md` — a materialized
policy key that was not injective over `entity_class`, letting the pushed policy
family return a claim the audited fallback excludes (T-15.2-03 over-disclosure).
Read-side guard extended from two components to three; the false premise that
produced the defect corrected in both docstrings that carried it; regression
pinned by a server-free test verified failing against the pre-fix code.

## Status: COMPLETE — CR-01 closed, scope held

---

## What was wrong

`policy_key()` in `src/ccf/graph/backends/fluree.py` builds the read side of the
`GQ-08` classification cut that probe F-A6 forced into a materialized
membership test. It refused to encode the `NUL` separator in `attribute` and in
`value` — **two of its three components**:

```python
if any(POLICY_KEY_SEPARATOR in part for part in (attribute, value)):
    return None
return POLICY_KEY_SEPARATOR.join((entity_class, attribute, value))
```

The docstring justified the omission — *"The class name is safe by
construction"* — and then derived the entire injectivity argument from it: *"A
key built here carries exactly two separators, so it can only equal a stored key
that also carries exactly two."*

The premise is false. `EntityClaim.entity_class` is a bare `str`
(`src/ccf/contracts/claims.py:115`) with no charset validation, exactly like an
attribute-map key; a class name is user-declared ontology vocabulary and is
artifact-authored on the same footing as the two components that *were* gated.
So the read side could build a three-separator key, and the argument resting on
"exactly two" collapsed with its premise.

### Reproduction — before the fix

Pure function of the claim and the query. No server:

```
claim   : entity_class="A", attributes={"B\x00C": "D"}
stored  : ['A\x00B\x00C\x00D']        # _fluree_claim_projection, gates NOTHING
query   : classification_attribute_by_class={"A\x00B": "C"}, permitted={"D"}
pushed  : 'A\x00B\x00C\x00D'          # policy_key("A\x00B", "C", "D")
COLLIDES: True
fallback: attribute_by_class.get("A") -> None -> claim EXCLUDED
translate: reached post_query -> PUSHED
```

`_ENTITY_POLICY` pushes `c.ccf_policy_key IN $policy_keys`, so the translated
statement returns that claim. `_admissible_entity`
(`src/ccf/graph/fallback.py:116-119`) excludes it, because the claim's own class
`"A"` has no declared classification attribute. **The pushed path
over-discloses a record the policy family excludes** — threats T-15.2-01 /
T-15.2-03, and precisely the divergence the differential byte-identity bar
exists to catch.

### Reproduction — after the fix

```
claim   : entity_class="A", attributes={"B\x00C": "D"}
stored  : ['A\x00B\x00C\x00D']
query   : classification_attribute_by_class={"A\x00B": "C"}, permitted={"D"}
pushed  : None
COLLIDES: False
translate: DECLINED
```

The key is refused, `_translate_query` declines the whole query, and the
fallback answers it — D-04, the same posture as the other four declines.
Nothing is refused to the caller; only the path changes.

## The fix

```python
if any(
    POLICY_KEY_SEPARATOR in part
    for part in (entity_class, attribute, value)
):
    return None
return POLICY_KEY_SEPARATOR.join((entity_class, attribute, value))
```

**Why the read side alone is sufficient** — verified, not assumed, and now
recorded in the docstring:

- every key `policy_key` builds carries **exactly two** separators, because all
  three components were checked;
- a stored key built from components carrying *k* extra separators has `2 + k`,
  and a two-separator string can never equal a three-or-more-separator string —
  so no read key can ever collide with a stored key built from
  separator-bearing components;
- a stored key carrying exactly two therefore had separator-free components, and
  such a string splits into `(class, attribute, value)` exactly one way.

Therefore a read key matches a stored key **iff the two triples are equal**.
Matching is exact — which is what the docstring claimed all along. The claim was
sound; its premise was not.

### Why `_writer.py` was left alone — and it was a judgement call

The review's suggested fix (and its WR-01) also collapses the duplicated
`_POLICY_KEY_SEPARATOR` in `ccf.graph._writer` and routes
`_fluree_claim_projection` through the shared `policy_key()`. **Not done here.
Chosen: the smaller change.** The reasoning, recorded either way as instructed:

1. **It is unnecessary for correctness.** With the read side gated, an
   unencodable stored key is *unreachable* — it carries three or more separators
   and no read key can have more than two. Leaving it materialized is the
   **fail-closed** direction: the claim simply never matches a pushed key and is
   answered by the fallback. There is no input for which the ungated write side
   now produces a wrong answer.
2. **The binding test genuinely holds the two constants equal.**
   `test_the_write_path_materializes_exactly_the_key_the_read_path_pushes`
   projects a real claim through `_fluree_claim_projection` and compares it
   against `policy_key()`. It compares on separator-free inputs — which is
   exactly the set of inputs on which the two constructions must agree, because
   it is exactly the set that can ever match. A drifted separator still fails
   CI. (WR-01 is right that the test does not cover the guarded branch; after
   this fix the two sides *are* meant to differ there, deliberately and
   benignly.)
3. **It preserves a measured claim.** Plan 15.3-03 deliberately did not touch
   `_writer.py` to protect wave 2's `864 added / 0 deleted` SUBQ-13 figure,
   paying the duplication down with the binding test instead. Re-opening that
   file to make a redundant change would disturb a recorded measurement for no
   correctness gain.

The counter-argument is real and belongs to WR-01, not here: one implementation
is structurally better than two, and the duplication is *what made CR-01
possible* — the guard lived on one copy only. That is a Warning about the shape
of the code, triaged separately; it is not a correctness gap after this fix.

### Docstrings corrected

Two places carried the false premise and both were fixed — the premise, not just
its consequence:

- `policy_key`'s docstring: now states that **all three** components are
  artifact-authored (with the contract citations), records the CR-01
  reproduction and date, and re-derives the injectivity argument from the
  established premise rather than the assumed one.
- the `POLICY_KEY_SEPARATOR` module note, which said the separator meant *"no
  artifact-authored string can forge a key boundary from the class side"* — the
  same claim in the same words, one level up. Now says the separator alone
  forges nothing and the guard is `policy_key`, and names the correction.

## Why nothing in the phase caught it

Four mechanisms had the opportunity:

| Mechanism | Why it was blind |
|---|---|
| `make gate-15.3` | Measures the change **surface**, not behaviour. `fluree.py` is Tier A, unbounded; the defect lived entirely inside the permitted surface, so exit 0 was the *correct* answer to the question the gate asks |
| Differential byte-identity bar | The generated corpus contains no control characters in class names, so the colliding shape is never drawn. A property bar is bounded by its generator |
| The unit test | Asserted refusal for two of three components — **the same gap as the code, repeated in the test.** A test written from the code's own premise can only confirm it |
| The 15.3-03 deviation record | Reasoned correctly about the attribute and value sides and inherited wave 1's "the class side is safe" claim without re-deriving it |

**The lesson, and it rhymes with the gate package's §9.** §9 found that any
enumeration written by hand against a rule stated as a category will
under-enumerate. CR-01 is that shape one level down: **a guard written by hand
over a tuple of components will under-cover the tuple, and a test written from
the guard's own premise will confirm the gap rather than expose it.** The three
components are a category — "every artifact-authored component of the key" — and
both the guard and its test enumerated two of them.

## What was wrong, and what fixed it

### WR-10 — the gate could not police its own rule surface

`tools/gates/*` is Tier C, free, on the reason "a gate that could not add
itself could not exist". The consequence: `ALLOWLIST`, `BUDGETS`,
`FROZEN_PATHS`, `SINGLE_OWNER_DENY` and `WRITER_EXPECTED_ADDITIONS` all sat
**inside the measured surface with no check at all**. A wave that widened the
allowlist or raised a budget to make its own diff pass was mechanically
indistinguishable from the gate's own authorship. `main()` forbids exactly that
in prose — *"Fix the DIFF — never the allowlist, the budgets, or the rules"* —
and nothing enforced it. The pressure was demonstrated, not hypothetical: the
allowlist was widened three times during this phase, correctly each time, with
nothing to distinguish a correct widening from an expedient one.

**Fix.** `rule_surface()` normalizes the rule DATA into canonical, sorted,
order-independent lines; `rule_surface_digest()` hashes them;
`check_rule_surface` (`gate153-rule-surface`) requires the digest to appear in
`docs/DECISIONS.md`. The choice of file is the load-bearing part: the third
correction already bounds that path **append-only**, so recording a rule change
cannot be done by editing the record of the last one.

| | |
|---|---|
| Digest | `sha256:0320e23fd7978653f3ce01831221677af6b65895c6ed88f895c83659a754f513` |
| Normalized rule lines | 44 |
| Pinned in | `docs/DECISIONS.md` — D-IMPL-92 fourth correction |

**Stated in the docstring, and repeated here because it is the claim people
will over-read: the pin makes a rule change *audited*, not *impossible*.** A
rule change plus an appended, dated entry carrying the new digest passes — by
design. D-IMPL-92's method is that the proxy may be corrected *upward, toward
the rule*; a pin that forbade correction would have forbidden the three
corrections that already had to happen. What it removes is the **silent**
change. It covers rule data, not the check bodies, and `--base` overrides
remain unrestricted (recorded as a residual rather than implied away).

### WR-09 — the `_writer.py` AST check did not reach module level

`top_level_defs()` collected only `ClassDef` / `FunctionDef` /
`AsyncFunctionDef`, so every module-level statement in that file — `__all__`,
module constants, the per-backend query-string constants — was invisible.
`src/ccf/graph/_writer.py` is **Tier A with no line budget** (absent from
`BUDGETS`), so rewriting an existing module-level constant there passed every
check the gate ran, while the gate's headline claim was "no mechanism anywhere
in the SDK changed".

**Fix.** HEAD's module body must be an ordered **supersequence** of the base's:
existing statements may be added to, never modified or removed; new ones are
free, because Tier A is where a new substrate's constants have to live under
CINV-02. A failed match does not consume the walk cursor, so one modified
constant is one finding rather than a cascade.

**The `__all__` companion — the measurement was verified before acting on it.**

| | |
|---|---|
| Module-level statements at base `96f54c5` | **33** |
| At HEAD | **51** |
| Unmatched under a strict ordered supersequence | **exactly 1** |
| Which one | `__all__`, which gained `FlureeGraphWriter` — a *modified* `Assign`, not an addition |

The reported figures held. The permission granted is bounded to that one shape:
a flat literal collection of string constants, bound to the same name, gaining
**exactly one** member, and that member must be a **new top-level definition in
this same module whose name begins with a backend name this phase added to the
`backend` `Literal`** — derived from the mechanism, resolving to
`{FlureeGraphWriter}` here. More than one companion is a finding. It is
**recorded** in the gate package like the two conformance companions, not
merely permitted. It is **not** a blanket exemption for module-level
assignments.

### WR-07 — `P_SEQ` summed two terms scoped to different keys

```python
P_SEQ: self._count(_FLUREE_ENTITY_CLAIM_COUNT, {**scope, "key": entity_uri})
       + len(self._entity_claims)          # NOT scoped to entity_uri
```

`P_SEQ` is *"the graph rendering of SQLite's `rowid`"* — the tiebreaker
ordering two claims of one entity that share an `observed_at`, under
`SELECT_ENTITY_HISTORY`'s `ORDER BY c.ccf_observed_at, c.ccf_seq`. The
committed term is scoped to the key; the buffer term counted **every** claim
buffered in the transaction, across all keys. A sum of two differently-scoped
counts is not a sequence.

Buffer `A1, B1, A2` in one transaction and `A` gets seq 0 and **2** while `B`
gets **1**. The next transaction reads `count(A) == 2` and computes **2** —
duplicating `A2`. Two claims of one entity sharing an `observed_at` and a `seq`
then order non-deterministically, and `_restitch_chain` yields a different
supersession chain per read. Silently, which is the whole point of the
tiebreaker.

Dormant **only** because `BaseGraphWriter.upsert_entity` opens one transaction
per claim, so `len(buffer)` is always 0. That is a property of today's caller,
not of the adapter — and `_FlureeTxn` is the batched adapter whose entire
premise is buffering. The `+ len(...)` term exists solely to support buffering
more than one, and it was wrong for exactly that case.

**Fix.** Both sites count only claims buffered under the same key, which is
what `select_entity_chain` and `select_relationship_chain` already do two
methods away — the scoping was present in the reads and absent in the write.

### IN-01 — the gate's `git()` returned partial output on failure

`if proc.returncode != 0 and not proc.stdout: raise` meant a git command that
failed *after* writing some stdout returned that partial output, and `measure`
and `diff_lines` treated it as complete. A truncated `--numstat` under-reports
changed paths, under-reports added lines against a budget, and hides an
unlisted path from the allowlist — **every one in the direction that makes the
gate pass.** Same class as WR-09 and WR-10: a check whose failure mode is a
quiet green.

**Fix.** Any nonzero exit raises, with the exit code in the message. The escape
had no caller that needed it: `git_ok` covers the `--exit-code` forms and
`blob` covers a path absent at a ref, and both read `returncode` themselves.
