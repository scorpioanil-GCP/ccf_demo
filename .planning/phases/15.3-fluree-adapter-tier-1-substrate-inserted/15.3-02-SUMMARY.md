## What the write path had to do that `_MongoTxn` does not

`_MongoTxn` was a complete template for eight of the nine operations. The two
places it is not are both consequences of one fact: **RDF set semantics has no
update primitive.** Asserting a second value for a property *adds* it beside
the first rather than replacing it.

1. **Supersession** (`update_*_supersession`). Mongo's `$set` has no JSON-LD
   analog, so the transaction must know the **old** value in order to emit a
   ground `delete` for it. The rowcount half of `_MongoTxn` carries verbatim;
   the mutation half is new code. Claims buffered in this same transaction are
   handled differently again — they have not been sent, so the pending insert
   triple is *mutated in place*, and clearing a value **removes the key**
   rather than writing null (an absent property already reads back as null,
   and an explicit null would create a value where the read path's `IS NULL`
   expects none).

2. **The observed window** (`upsert_*_node`). Same reasoning: widening
   `first_observed_at` / `last_observed_at` by bare re-assertion would leave
   the node carrying *two* values, and RDF's fan-out would surface both. The
   widening is therefore a delete/insert pair against the committed value,
   skipped entirely when the value does not move — which matters because
   `_restitch_chain` re-states every link of a chain on every write, making
   identical-value calls the common case rather than the exception.

## Deviations from Plan

### 1. [Rule 2 — Missing validation] Artifact-authored attribute names could reach an IRI position

- **Found during:** Task 2, writing `_fluree_claim_projection`
- **Issue:** The plan said to "project them under `ATTRIBUTE_PROPERTY_PREFIX`",
  keeping only the `isinstance(value, str)` gate. But `EntityClaim.attributes`
  is typed `Mapping[str, str]` and documented as *"an opaque,
  deployment-defined attribute map — the SDK never enumerates its keys"*, so
  an attribute **name** is arbitrary artifact-authored text. A projected
  attribute is addressed by its **predicate**, and the strict compact-IRI
  guard applies to predicate positions — so a name containing `:` reads as a
  compact IRI with an undefined prefix and Fluree rejects **the entire
  buffered transaction** at parse time. That is not a lost projection; it is
  refused admission of a perfectly legal CCF claim, and it contradicts the
  module's own stated rule that no artifact-authored string occupies an IRI
  position.
- **Fix:** Added `attribute_predicate(name) -> str | None` to
  `ccf.graph.backends.fluree`, the exact structural mirror of mongo's
  `attribute_field_path` (same `^[A-Za-z0-9_-]+$` charset, excluding `:` and
  `.` by construction rather than by blocklist), and gated the projection on
  it. Placed in the backend module rather than `_writer.py` because that is
  where the mongo precedent lives and because plan 15.3-03's read side will
  need the same gate.
- **Why nothing is lost:** the attribute still travels verbatim inside
  `claim_json`, and — unlike the Mongo case — refusing a name costs **no
  pushdown on the predicate family that matters**, because the policy family
  reads `ccf_policy_key`, which is a *literal value* and safe for every
  attribute name including the refused ones.
- **Files:** `src/ccf/graph/backends/fluree.py`
- **Commit:** `1e236b5`
