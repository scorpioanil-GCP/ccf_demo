## Write posture + write language

### Q1 — Write-transaction posture (D-IMPL-88 precondition (b))

| Option | Description | Selected |
|--------|-------------|----------|
| Buffered batch, one commit | `_FlureeTxn` accumulates the nine typed ops, commits as a single POST; rowcounts resolve by read-before-buffer, sound under `INV-CH7-10`. Same shape as `_MongoTxn`. | ✓ |
| Bolt explicit transactions | Real held transaction via the neo4j driver over Bolt. Works in CI, but explicit transactions require a single-node server — Raft/peer deployments reject `BEGIN`. Couples Fluree to the `neo4j` extra. | |
| Per-op autocommit | Each operation its own POST. Simplest; abandons write atomicity. | |

**User's choice:** Buffered batch, one commit.
**Notes:** This is the ratification D-IMPL-88 assigned to discuss-phase, and it was the last precondition standing — Phase 15.3 is now unblocked for planning.

### Q2 — Write surface (first pass, then reopened)

The first pass recommended **multi-clause Cypher** on a symmetry argument (one language across read and write; `_Neo4jTxn`'s operations lift nearly verbatim). The user challenged the framing before answering — see the interjection below — and the question was reformulated with JSON-LD promoted.

| Option | Description | Selected |
|--------|-------------|----------|
| JSON-LD transaction | Fluree's own primary write path — insert/delete/where, one POST, native atomicity. Hard condition: adapter-owned minimal `@context` with zero type coercion, ledger created with no default context; F-A5 verifies `xsd:string`. | ✓ |
| Multi-clause Cypher | `MERGE ... ON CREATE`; one language across read and write. Privileges the Neo4j shape over Fluree's native model; leans on Cypher-writes-onto-RDF, the thinner surface on that engine. | |
| SPARQL UPDATE | `INSERT ... WHERE FILTER NOT EXISTS`; RDF-native. Weakness: 4.1.3 shipped breaking SPARQL changes inside a minor. | |
| Probe all three, decide on evidence | One task running F-A4/F-A5 in each surface against a live container, JSON-LD as default if more than one passes. | |

**User's choice:** JSON-LD transaction.
**Notes:** Reads stay Cypher — not a preference but a constraint, since SPARQL 1.1 cannot express bounded-depth repetition at all.

### User interjection — "why are we not thinking of a neutral interface"

The user objected to tying the Fluree adapter to Cypher and proposed a neutral `GraphOp[]` IR with per-adapter translation, arguing the core SDK should never see Cypher, SPARQL, SQL, or Mongo queries.

Resolution, recorded because it shaped the rest of the discussion:

- **The neutral IR already exists and is the shipped 15.2 seam.** `_GraphTxn` (`_writer.py:320`) is nine typed operations with "no SQL" stated in the docstring; `GraphQuery` is the read-side equivalent, canonically serializable and pinned into the ArtifactStore for replay. The proposed design was already the architecture.
- **The question as originally posed was mis-framed.** Write-surface choice is an adapter-internal detail *below* the neutral seam, and presenting it as an architectural decision was misleading. Corrected.
- **Where CCF's IR deliberately differs from the proposal:** the sketch included `deleteEntity` / `deleteRelationship` / `setProperty`. Those cannot exist in CCF's IR — the graph is append-only with logical supersession, and `update_*_supersession` is documented as the only mutation ever applied to an existing claim (INV-CH7-04). A generic property-graph IR would be more portable and would break the invariants the fabric exists to hold.
- **Factual correction to the comparison table offered:** the shipped Mongo adapter does not use multi-document transactions; `_writer.py:1999` is `bulk_write(ordered=True)` per collection, buffered and applied at commit.
- **Where the objection was correct and changed the outcome:** Fluree's primary write path genuinely is JSON-LD, and the Cypher recommendation had let symmetry-with-Neo4j do work it shouldn't have. That recommendation was withdrawn.

### Q3 — Ledger / partition / tenant mapping

| Option | Description | Selected |
|--------|-------------|----------|
| One CCF-owned ledger; `partition` + `tenant_id` as predicates | Matches Neo4j and Mongo: compound-key properties in one physical container. `graph_identity` = host/port/ledger#partition, credential-free. Keeps `Fluree-Min-T` single-valued. | ✓ |
| Ledger per partition | "Fresh graph per boot" physically true; Fluree ledgers are cheap. Costs per-ledger Min-T state, dynamic CI ledger creation, divergence from the other four backends. | |
| Ledger per tenant | Strongest isolation, plausibly attractive to a bank. Costs the most; research does not recommend it for v1. | |

**User's choice:** One CCF-owned ledger with predicates.
**Notes:** Discovered during scouting that both Neo4j and Mongo realize a *two-level* scoping (`partition` for one fabric's graph, `tenant_id` for multi-tenancy) as properties rather than physical containers. That reframed the question from "ledger per tenant?" to "what, if anything, maps onto a physical ledger" — and the answer became consistency with the existing four.

## Pushdown staging

### Q1 — Does stage 2 ship?

| Option | Description | Selected |
|--------|-------------|----------|
| Both stages ship, staged within the phase | Stage 1 (non-traverse + fallback traversal) is a conformant floor; stage 2 promotes at byte-identity over the full corpus. Mirrors what Mongo did. | ✓ |
| Stage 1 only; traversal via fallback | Smallest, most certain phase. But Fluree becomes the only tier-1 backend not pushing traversal, and the telemetry says so on every traverse query. | |
| Go straight to full Cypher pushdown | Cypher's semantics match CCF BFS far more closely than `$graphLookup`. Cost: no working floor if F-A2/F-A3 fail. | |

**User's choice:** Both stages, staged.
**Notes:** Verified during discussion that Mongo did land stage 2 (`backends/mongo.py:835`) and needed four `$graphLookup` semantic corrections. Research argues Cypher avoids all four — no directedness doubling, no maxDepth off-by-one, no seed exclusion — but the promotion gate stays byte-identity, not expectation.

### Q2 — Suite scope

| Option | Description | Selected |
|--------|-------------|----------|
| Both — differential and six-semantics | One `pytest.param` in each of `test_substrate_differential.py:120-122` and `test_graphstore.py:48-53`. Matches what DI-15.2-02 established at the 15.2 close. | ✓ |
| Differential only | The harder, more diagnostic gate; smaller diff. Recreates the asymmetry DI-15.2-02 closed. | |

**User's choice:** Both suites.

### Q3 — Probe timing (first pass rejected; user asked for pros/cons in a table)

The first pass was declined with a request for a pros/cons comparison. A three-table analysis was produced — per-probe cost/consequence, then options for each question — before re-asking. The per-probe table surfaced the asymmetry that decided it: F-A4 and F-A5 gate everything and fail *silently*; F-A2 and F-A3 gate only stage 2 and fail *loudly*.

| Option | Description | Selected |
|--------|-------------|----------|
| Split — F-A1/F-A4/F-A5 up front, F-A2/F-A3 at stage 2 | Severe-and-silent probes run before any code depends on them; loud-and-local traversal probes run where they bind. Two probe moments. | ✓ |
| Task 1 — all five up front | One container spin-up, one evidence record. F-A2/F-A3 probed speculatively if stage 2 later descopes. | |
| Inline — each at the point it's needed | Fewest tasks, no speculative work. A falsified F-A4/F-A5 surfaces with code already written against it. | |

**User's choice:** Split timing.
**Notes:** Precedent cited: 15.2-08's mandatory pre-committed probe falsified its assumption and produced D-IMPL-89 — a real replay defect found because the probe ran before the code.

### Q4 — Falsification response

| Option | Description | Selected |
|--------|-------------|----------|
| Pre-committed ladder, rung 3 named concretely | Workaround → stage-1 + deferred item → STOP only if the finding would change what `as_of` **means**, not how it is expressed. | ✓ |
| Pre-committed ladder, rung 3 left as judgment | Same rungs, "semantics question" left to executor classification. | |
| Workaround or bust | Stage 2 unconditional. No defined exit if both the documented form and its workaround fail. | |
| STOP on any probe failure | Every falsification goes to Dave. Routes questions the 15.2-12 plan already answered through a ruling that doesn't need one. | |

**User's choice:** Ladder with rung 3 named concretely.
**Notes:** The concrete wording exists specifically to remove executor classification judgment — the risk flagged when the ladder was first proposed.

## CI leg posture + image pinning

### Q1 — Where the leg runs

| Option | Description | Selected |
|--------|-------------|----------|
| Fourth always-on service in `ci.yml` | Health-gated service block, `CCF_TEST_FLUREE_URL`, own `pytest -m fluree` step, skipped-leg-is-a-failure rule applying. No install-step change — httpx is core. | ✓ |
| Opt-in leg in `live-legs.yml` | Keeps the always-on job at three containers. Makes Fluree the one backend whose conformance is not continuously proven. | |

**User's choice:** Fourth always-on service.
**Notes:** Fluree is operationally the lightest of the four legs — ~63–70 MB, seconds to start, purpose-built `GET /health`, auth off by default.

### Q2 — Pin governance

| Option | Description | Selected |
|--------|-------------|----------|
| Exact pin + scheduled drift detector | Pin `4.1.4` exactly; a scheduled `live-legs.yml` job runs the same differential against the floating `4.1` tag so upstream breaks surface on their own schedule. | ✓ |

| Exact pin, re-verify at planning only | Lightest. After the phase closes, nothing notices the pin going stale. | |

**User's choice:** Exact pin + scheduled drift detector.
**Notes:** Justified by five patch releases April–July 2026 and a breaking SPARQL change shipped *inside* a minor (4.1.3).

## No-refactor evidence

### Q1 — How the claim is proven

| Option | Description | Selected |
|--------|-------------|----------|
| Mechanical allowlist check, committed as gate evidence | A gate script enumerates the permitted change surface and fails on anything outside it. Lives with the phase, not in `tools/lints`, because it asserts a fact about one diff rather than a standing invariant. | ✓ |
| Narrower mechanical check: suite files only | Cheapest; literally the sentence claimed. Says nothing about whether `/src` outside the adapter was touched. | |
| Narrative evidence in the gate package | Zero machinery; matches how 15.2's gate package handled evidence. Makes the headline claim a thing asserted in a document. | |

**User's choice:** Mechanical allowlist check.

### Q2 — What counts as violating the claim

| Option | Description | Selected |
|--------|-------------|----------|
| No SDK-core change; suite additions permitted with recorded justification | Hard line on `src/ccf`; corpus additions allowed but must be recorded with why, distinguishing "the SDK bent" from "the corpus grew". | ✓ |
| Strict: two param lines, nothing else | Strongest claim. Forces an honest fixture addition to read as a failure, which pressures toward not adding it. | |
| SDK core only — tests unconstrained | Simplest to satisfy; gives up the most quotable half of the evidence. | |

**User's choice:** No SDK-core change with justified suite additions.
**Notes:** Surfaced during the question that `docs/GRAPH_QUERY_SEMANTICS.md` (1.0.1) sits behind a citation gate carrying line numbers into `/src` and `/tests` cites — the 15.2 record notes a naive insert produced 124 findings in one edit. "The prose does not change" is therefore a practical constraint, not only an aesthetic one.

## Deferred Ideas

- Tier-3 raw external sources — reading the institution's *existing* Fluree KG. A tier-1 adapter does not deliver it; a different phase if the engagement wants it.
- Fluree as an L1 MCP-ingress source — available today, configuration only, proceeds ahead of and independently of this adapter.
- Exposing Fluree's native capabilities (time travel, branching, SHACL, vector/BM25) through the seam — a `GraphQuery` vocabulary conversation, not an adapter decision.
- A `fluree` leg in the Phase 11 perf battery — raised, not pursued.
- Adapter documentation and a worked deployment manifest — Phase 16 owns the docs rewrite against the post-15 surface.
- Bolt as an alternative wire — considered and rejected for v0 (single-node-only explicit transactions; unwanted `neo4j` extra coupling). Recorded so a future reader knows it was weighed, not overlooked.
