## User Constraints (from CONTEXT.md)

### Locked Decisions

**Write path**

- **D-01 — Buffered batch, one commit.** `_FlureeTxn` accumulates the nine typed
  operations and commits as a **single POST**; nothing reaches the server until
  commit. Per-operation rowcounts resolve by *read-before-buffer* — sound precisely
  because `INV-CH7-10` single-writer guarantees no concurrent writer can invalidate
  the pre-commit read. Bolt explicit transactions rejected. Per-op autocommit
  rejected. **This ratifies D-IMPL-88 precondition (b).**
- **D-02 — JSON-LD writes, Cypher reads.** Writes: Fluree's own primary write path —
  JSON-LD `insert`/`delete`/`where`, one POST, atomicity native. Reads: openCypher
  (SPARQL 1.1 cannot express bounded-depth repetition at all).
  **Hard condition:** the adapter owns a **fixed minimal `@context` with zero
  datatype coercion** and creates the ledger with **no default context**. Probe
  **F-A5** verifies strings land as `xsd:string` before any code depends on it.
  *Superseded during discussion:* Cypher-for-writes was **withdrawn**.
- **D-03 — One CCF-owned ledger; `partition` + `tenant_id` as predicates.**
  `(partition, tenant_id, entity_uri)` compound identity carried as properties
  inside one physical container. `graph_identity` = host/port/ledger#partition,
  **credential-free** (T-15.2-05, T-04-24 precedent). Ledger-per-partition and
  ledger-per-tenant both rejected for v1.

**Pushdown**

- **D-04 — Both stages ship, staged within the phase.** Stage 1: non-traverse
  pushdown (property filters + `allowed_entities` as a Cypher `$param` list) with
  **fallback traversal**. Stage 2: bounded **undirected** Cypher variable-length
  traversal, hop admissibility via `all(n IN nodes(p) WHERE ... AND n.entity_uri IN
  $allowed)`. **Promoted only at byte-identity over the full corpus including
  resurrection shapes.** Research expects this to go better than Mongo's — *do not
  assume it; the promotion gate is byte-identity, not expectation.*
- **D-05 — `fluree` joins BOTH suites.** One `pytest.param` line in
  `test_substrate_differential.py` **and** one in `test_graphstore.py`.
- **D-06 — Split probe timing.** Up front, in the phase's first task: `F-A1`,
  `F-A4`, `F-A5` (gate everything, **fail silently**). At stage-2 promotion:
  `F-A2`, `F-A3` (bind only at stage 2, **fail loudly**).
- **D-07 — Pre-committed falsification ladder.** (1) documented workaround;
  (2) workaround also fails → **ship stage 1** + a `DI-15.3-NN` deferred item;
  (3) **STOP and raise a `D-IMPL` only if the finding would change what `as_of`
  MEANS on this substrate — not merely how it is expressed.**

`src/ccf/deployment/manifest.py:215-263` (`_preflight_backend`) maps

both files cannot be booted and cannot be declared in a manifest.** There is no
registration seam; the enumeration *is* the mechanism. CONTEXT.md's own
`<code_context>` "Integration Points" section says as much — "Boot exclusivity wiring
— single-writer enforcement at boot, same shape as the other four backends" — which
contradicts D-10's list, in the same document.

Note also that the mongo `boot.py` diff carries **13 deleted lines**: they are
docstring sentences rewritten to enumerate one more backend, plus the `backend:
Literal[...]` line in `manifest.py`. So a naive "additive-only, zero deletions" gate
would also fail. The change *kind* is "one more member of an existing enumeration",
not "a modification of a mechanism".

**Why this is blocking rather than advisory.** The gate script is a phase
deliverable (D-10) whose whole value is that it *fails*. Shipping it against an
enumeration that cannot be satisfied means either (a) the phase cannot close, or
(b) an executor quietly widens the list — which is exactly the "narrated, not
checked" failure D-10 exists to prevent. Either outcome destroys the claim.

**Proposed repair (Dave's ruling, or a planner clarification if Dave delegates it).**
Keep D-10's intent — a mechanically-checked, falsifiable diff surface — and make the
enumeration true, by splitting it into two tiers with different admissibility rules:

- **Tier A — adapter surface (unbounded content, must be new or additive):**
  `src/ccf/graph/backends/fluree.py` (new file);
  `src/ccf/graph/_writer.py` (`_FlureeTxn` + `FlureeGraphWriter` only — assert no
  existing class body changed).
- **Tier B — registration sites (bounded, enumeration-extension only):**
  `src/ccf/boot.py`, `src/ccf/deployment/manifest.py`,
  `src/ccf/controlplane/artifacts.py`, `pyproject.toml`,
  `docs/schemas/ccf.deployment-manifest.json` (generated),
  `tests/conftest.py`, plus one `pytest.param` line in each conformance suite.
  Gate rule: **no existing backend name is removed, and each file's net added lines
  are under a stated budget** (the mongo precedent gives the budget: boot ≤ 70,
  manifest ≤ 25, artifacts ≤ 10, conftest ≤ 45). A change beyond the budget in a
  Tier-B file is the refactor the claim denies, and the script says so.
- **Tier C — free (evidence, not SDK):** the new
  `tests/graph/test_fluree_backend.py`, `.github/workflows/*`, `Makefile`,
  `docs/SURFACE-CHANGES.md` + its per-plan fragment, and the gate package itself.

The claim then reads, truthfully and still falsifiably: *"adding a real substrate
touches one new module, one writer class, and a bounded one-line extension of four
existing enumerations — no mechanism anywhere in the SDK changed."* That is a
**stronger** statement than the one D-10 currently makes, because it is one that can
survive contact with the tree.

**What is NOT reopened:** D-10's requirement that the surface be script-checked and
committed with the gate package; D-11's hard line on *mechanism* change; the
`GRAPH_QUERY_SEMANTICS.md` freeze. All three stand unmodified.

## Summary

Three things changed relative to the feasibility research, and the planner needs all
three before drawing tasks.

**1. The version pin is still correct, and the licence is unchanged — but the Cypher
surface is six weeks old.** `v4.1.4` (2026-07-23) is still the newest release as of
2026-08-08; `fluree/server:4.1.4` is still the newest image tag, and `latest`/`4`/`4.1`
all resolve to it. BSL 1.1 with the same Additional Use Grant holds at the `v4.1.4`
tag, now with an *additional* "For clarity" paragraph that explicitly permits
internal-component use. **But** the openCypher 9 front-end shipped in **v4.1.1
(2026-06-30)**, `v4.1.3` shipped a "Cypher field-report round" of fixes, and `v4.1.4`
shipped "Enrich Cypher transaction commit result for write parity." The feasibility
research treated Cypher as a settled surface; it is a *six-week-old* surface under
active field repair. That changes the risk weighting on stage 2 materially, and it
is the strongest argument for D-09's exact pin and drift detector.

**2. The Neo4j walk does not translate.** The Neo4j hop predicate reads *relationship
properties* (`r.partition`, `r.relationship_key`, `r.relationship_type` —
`backends/neo4j.py:440-446`). In Fluree, a Cypher relationship over plain RDF triples
**has no properties**; only a *reified/annotated* edge does, and a property-reading
relationship variable silently sees only reifier-bundled edges. Compounding this:
the only bounded variable-length pattern Fluree supports is a **single fixed
relationship type** (bounded type-alternation and undirected-untyped are both
documented as deferred), so `type(r)` cannot carry the CCF type either. **Stage 2
therefore requires a physical-model change inside the adapter** — this document
recommends edge-as-node interposition (§R5), which is the direct analogue of Mongo's
doubled-edge collection, and which lands hop admissibility entirely on `nodes(p)`,
exactly as D-04's own wording already anticipates. Failure mode without the change is
**an empty reached set, silently** — no error.

**3. The JSON-LD write body cannot express a multi-operation batch conditionally —
and does not need to.** A JSON-LD update body carries one `where`/`delete`/`insert`
triple. Because read-before-buffer plus single-writer already gives the adapter the
committed state, the batch should be emitted as **one ground `delete` + `insert` body
with no `where` clause at all**. That is the D-02-faithful shape, it makes `flakes_added`
a meaningful aggregate cross-check, and it is what probe F-A4 must actually assert.

**Primary recommendation:** plan three tasks in one wave — (1) probes F-A1/F-A4/F-A5
+ store envelope + `_FlureeTxn` + registration wiring; (2) stage-1 read translation +
both suite params + CI leg; (3) stage-2 walk on the interposed model behind F-A2/F-A3,
with D-07 rung 2 (`ship stage 1`) pre-costed as the likely outcome if the six-week-old
path-enumeration engine misbehaves. Resolve BF-1 with Dave before the gate script is
written.

## R2 — Concrete HTTP wire shapes

Base path is discovered at `GET /.well-known/fluree.json`; the standalone server
default is **`/v1/fluree`**. `[CITED: api/endpoints.md]` The adapter should read the
well-known document once at construction rather than hard-coding `/v1/fluree` — one
`GET`, and it makes the store correct behind a differently-mounted server. **`GET
/health` is at the server root, NOT under the API base path.**

### Ledger bootstrap — `POST {base}/create`

```http
POST /v1/fluree/create
Content-Type: application/json

{"ledger": "ccf:main"}
```

Response `201 Created`: `{"ledger":"ccf:main","t":0,"commit_id":"bafy…"}`
Status codes: `201` created · `400` bad body · `401` (only when admin auth enabled) ·
**`409 Conflict` — ledger already exists** · `500`.

**Two facts that answer D-02's hard condition directly:**

1. **`POST /create` has no context parameter.** The only body field is `ledger`. There
   is no way to attach a default context at creation, so *a freshly created ledger has
   no default context* — `GET /context/{ledger}` returns `"@context": null` ("If no
   default context has been set, `@context` is `null`"). **D-02's "create the ledger
   with no default context" is satisfied by simply never calling `PUT /context`.**
   `[CITED: api/endpoints.md § POST /create, § GET/PUT /context]`
2. **`409` is the idempotent-bootstrap signal.** Under D-03 (one CCF-owned ledger)
   every boot calls `POST /create` and must treat `409` as success. The adapter's
   constructor is the natural site — the Neo4j precedent runs `_SCHEMA` DDL there
   (`backends/neo4j.py:231-233`).

### Write — `POST {base}/update/{ledger}` (JSON-LD)

```http
POST /v1/fluree/update/ccf:main
Content-Type: application/json
Accept: application/json
```

Body forms accepted: a plain `{"@context":…, "@graph":[…]}` insert, **or** a
`where`/`delete`/`insert` update document. Response (the commit receipt):

```json
{
  "t": 5,
  "timestamp": "2024-01-22T10:30:00.000Z",
  "commit_id": "bafybeig…commitT5",
  "flakes_added": 3,
  "flakes_retracted": 1,
  "previous_commit_id": "bafybeig…commitT4"
}
```

`[CITED: api/endpoints.md § POST /update; transactions/commit-receipts.md]`

Status codes: `200` · `400` invalid syntax · `403` · `404` ledger not found ·
**`409` optimistic-concurrency conflict that survived the server's bounded
reconcile-and-retry — documented as retryable, distinct from `400`** ·
`413 Payload Too Large` · `500`.

**Concurrency, verbatim:** *"Writes to a single ledger are serialized by a per-ledger
write lock… the server reconciles the cached state to the current head and re-tries
(bounded, up to 16 attempts). A `409 Conflict` is returned only if the retry budget is
exhausted."* Under INV-CH7-10 single-writer, a CCF deployment produces no contention;
a `409` here means something outside CCF wrote the ledger, which is a broken
deployment (exception), never a refusal.

#### The batch shape the buffered commit should use — and why

A JSON-LD update body carries **one** `where`, **one** `delete`, **one** `insert`.
Multiple *independent* conditional operations are not expressible in a single body:
their `where` clauses would join, not union. The documented semantics are explicit
about the trap — *"WHERE returns zero rows — nothing is inserted, even for
all-literal INSERT templates"* `[CITED: transactions/conditional-updates.md]` — so a
body that mixes a guarded update with unrelated ground inserts silently drops the
inserts whenever the guard misses.

**Recommendation: emit a purely ground body with no `where` clause.** Read-before-buffer
plus single-writer means the adapter already knows the committed state at commit time,
so every conditional is resolvable in Python. The batch becomes:

```json
{
  "@context": { /* the fixed minimal adapter context — §R3 */ },
  "delete": [ /* ground triples: the supersession values being replaced */ ],
  "insert": [ /* ground triples: claims, nodes, lineage, new supersession values */ ]
}
```

Documented support: *"No WHERE clause at all — the INSERT fires once (the plain insert
path)."* A ground `delete` with no `where` is the JSON-LD analogue of SPARQL's
`DELETE DATA`; it is **not** explicitly documented and is therefore **F-A4's central
assertion** (§R4).

This shape is also the one that keeps D-02 honest: no mapping through a query
language, one POST, atomicity native, and every conditional resolved by the same
Python-side machinery `_MongoTxn` already uses (`_writer.py:1974-1993`).

**RDF set semantics is free idempotency.** Re-asserting an existing triple is a no-op
that adds zero flakes. Because a CCF `claim_id` is a content hash of the claim's
content key (`_writer.py:210-239`), a claim re-arrival produces byte-identical triples
— so `insert_entity_claim`'s "0 for a re-arrival" contract is naturally honoured by
the substrate as well as by the pre-buffer read. Belt and braces; the read is still
the authority, because the *rowcount* must be resolvable before commit.

**Size limit — new, and load-bearing.** *Transaction requests: default limit 10 MB,
configurable `--max-transaction-size`.* `413 Payload Too Large` on breach.
`[CITED: api/headers.md § Request Size Limits]` The buffered batch is one body; a very
large L2 admission batch could approach it. The plan should state a batch-byte budget
and a documented behaviour on breach (split into two commits — which sacrifices
all-or-nothing — or fail loudly). **Recommend: fail loudly with a typed error naming
the limit.** Splitting silently would break write atomicity, which D-01 exists to
preserve.

### Read — `POST {base}/query/{ledger}` (Cypher)

```http
POST /v1/fluree/query/ccf:main
Content-Type: application/cypher
Accept: application/json
Fluree-Min-T: 42
```

Body: raw Cypher **or** the JSON envelope `{"cypher": "...", "params": {...}}` (the
Neo4j-HTTP shape). *"Cypher targets a ledger directly and must use the path form; it
has no `FROM`/dataset clause."* Responses default to **cypher-json**, described as *"a
Neo4j-compatible tabular envelope with native scalars"*; `Accept: application/ld+json`
switches to RDF JSON-LD. `[CITED: api/endpoints.md § POST /query/{ledger};
query/cypher.md § Running Cypher]`

**The exact cypher-json envelope is not documented.** `query/output-formats.md`
documents JSON-LD / SPARQL-JSON / typed-JSON / AgentJson and does not describe
cypher-json's row structure. **The adapter's row-extraction code must be written
against observed bytes, not against a guess — this is an F-A1 sub-assertion (§R4).**
Whatever the envelope, the extracted rows must arrive at
`ccf.graph.reader.materialize_view` (`reader.py:239`) as plain dicts satisfying
`reader.Row`, exactly as `Neo4jGraphReader._query` produces them
(`backends/neo4j.py:570-583`).

Status codes: `200` · `400` invalid syntax · `404` ledger not found ·
`406` format not available for this query form · `413` query exceeds size limit ·
`503` query timeout or resource limit.

**Query size limit — new, and directly relevant to `allowed_entities`.**
*Query requests: default limit **1 MB**, configurable `--max-query-size`.*
`[CITED: api/headers.md]` The feasibility research recorded this as
`[ASSUMED: no hard cap documented]`; it is documented, and it is small.
`allowed_entities` travels as a `$param` list in the body. The Control Plane survivor
cap (`GQ-18`) bounds the set, but the two limits are unrelated numbers.

**Recommendation:** mirror the `MAX_DEPTH_CEILING` decline pattern
(`backends/neo4j.py:292-306`, ratified as mechanism at D-GATE-15.2 checkpoint Q2) —
the adapter computes the rendered body size and, above a stated byte budget,
**declines the translation and lets the fallback answer (D-04, `GQ-29`)**. Same
argument, verbatim: it bounds the generated request, not the vocabulary; it changes
which path answers, never the answer. This is a new named mechanism constant, and the
Q2 ruling is its precedent.

**Response header `X-Fluree-T`** carries the transaction time of the data returned —
useful in probes to prove read-after-write actually took effect.

### Read-after-write — `Fluree-Min-T` is real and is the right mechanism

> *"`Fluree-Min-T: 42` — Before executing the request, the server refreshes the
> referenced ledger(s) until each has reached at least the requested transaction time.
> If the target `t` is not visible before `query_min_t_timeout_ms`, the server returns
> a read-after-write timeout error. JSON-LD query bodies may also specify the same
> requirement as `opts.min-t`, `opts.min_t`, or `opts.minT`; body opts take precedence
> over the header."*
> `[CITED: api/headers.md § Fluree-Min-T; also api/endpoints.md § POST /query]`

Supporting evidence that the mechanism is implemented, not aspirational:
`v4.0.7` shipped `feat(server): query freshness for disconnected query servers (TTL
refresh + read-after-write min-t)`, and `v4.1.1` shipped `fix: db() reflects
owned-state commits (read-your-writes)`.
`[VERIFIED: GitHub release bodies, 2026-08-08]`

**Concrete threading:** every `POST /update` response carries `t`; the store keeps
`self._min_t = max(self._min_t, response["t"])` and every subsequent read sends
`Fluree-Min-T: {self._min_t}`. Because the adapter sends Cypher (`Content-Type:
application/cypher`) rather than a JSON-LD body, **the header form is the only one
available** — `opts.min-t` lives in a JSON-LD query body. Note the documented
constraint: *"The header must resolve to at least one target ledger. On a
ledger-scoped endpoint the endpoint's ledger is used"* — the adapter always uses the
ledger-scoped route, so this is satisfied.

**Failure mode to handle:** a read-after-write **timeout error** is a distinct outcome
from a slow read. The plan should state what the adapter does with it. Under CCF's
rules this is a broken deployment, not a refusal → raise, do not degrade.

## R3 — The `@context` / datatype-coercion hazard (F-A5's target)

### How coercion happens, and how to avoid it

**The default is already correct.** *"**xsd:string** is the default for plain string
literals when no type is specified."* `[CITED: concepts/datatypes.md]` A JSON string
value in a JSON-LD write body lands as `xsd:string` unless something says otherwise.

**The two ways something could say otherwise:**

1. **A term definition in the request's own `@context`** that declares
   `"@type": "xsd:dateTime"` for a property, or a `@value` object carrying an explicit
   `"@type"`. Both are under the adapter's total control: the adapter authors the
   `@context` and never emits `@value` objects for temporal fields.
2. **The ledger's stored default context.** Two independent facts make this a non-risk
   provided the adapter never sets one:
   - `PUT /context` takes *"A JSON object mapping prefixes to IRIs"* — a **prefix map**.
     Term-level datatype coercion is not the documented shape of a Fluree default
     context. `[CITED: api/endpoints.md § PUT /context]`
   - Default-context injection is **off by default on the HTTP API** and is a
     *query-side* feature only: *"The HTTP API defaults this behavior off; pass
     `?default-context=true` on a query request to opt in."* `[CITED:
     concepts/iri-and-context.md § Server and CLI behavior]` The adapter never passes
     that parameter, and writes are not documented as receiving default-context
     injection at all.

### The minimal zero-coercion `@context`, concretely

The adapter needs no prefix mappings and no term definitions. The safest context is
**an empty object** — or none at all — combined with **colonless identifiers**:

```jsonc
{
  "@context": {},          // no @vocab, no @base, no term definitions, no coercion
  "insert": [
    {
      "@id": "ccf_e_9f2a…",           // adapter-minted, colonless, opaque
      "@type": "CcfEntityClaim",       // a bare label, namespace code 0
      "ccf_partition":  "ccf",
      "ccf_tenant_id":  "tenant-a",
      "ccf_entity_uri": "counterparty://acme",   // artifact data as a STRING LITERAL
      "ccf_claim_id":   "…",
      "ccf_claim_json": "{…}",
      "ccf_observed_at": "2026-03-01T00:00:00.000000Z"   // plain JSON string → xsd:string
    }
  ]
}
```

Three properties of this shape, each load-bearing:

- **No `@vocab`.** *"By default they are just names — no IRI prefix is invented for
  them. Internally they live under namespace code 0 (the empty prefix), so a label
  written as `Person` reads back as `Person` on every surface: `labels(n)`, Bolt, and
  even JSON-LD/SPARQL queries against the same ledger."* `[CITED: query/cypher.md §
  Names, and opting into IRIs]` This is exactly what makes JSON-LD writes and Cypher
  reads address the same data with no mapping layer. It is also a **hard condition**:
  *"Adding `@vocab` to a ledger whose data was written bare (or vice versa) changes
  what Cypher statements match."* If anything ever sets a default context with
  `@vocab` on this ledger, every read silently returns nothing.
- **No `@type` coercion anywhere** → every string is `xsd:string`.
- **Artifact-authored data never occupies an IRI position.** See below.

### The strict compact-IRI guard — a hazard the feasibility research did not name

JSON-LD parsing is **strict by default** about compact IRIs:

> *"If you write a value that looks like a compact IRI — `prefix:suffix` — but the
> prefix is not defined in `@context`, Fluree rejects the request at parse time."*
> Accepted without a prefix: hierarchical absolute IRIs whose suffix starts with `//`;
> a small allowlist of schemes (`urn:`, `did:`, `mailto:`, `tel:`, `data:`, `ipfs:`,
> `ipns:`, `geo:`, `blob:`, `magnet:`, `fluree:`); variables and blank nodes.
> The guard applies to *"`@id`, `@type`, predicates / property names, datatype IRIs in
> `@type` of `@value` objects, graph names, selection predicates, VALUES `@id` cells"*
> and **not** to *"Literal string values (only IRI positions)"*.
> `[CITED: concepts/iri-and-context.md § Strict Compact-IRI Guard]`

**CCF `entity_uri` values are artifact-authored.** Some legal CCF entity URIs would be
*accepted* (`counterparty://acme` — suffix starts with `//`), some would be *rejected*
at parse time (`counterparty:acme` — looks compact, prefix undefined), and a
`@context` that happened to define the prefix would make one *silently expand* into a
different identifier. All three outcomes are wrong.

**This is Fluree's analogue of `attribute_field_path` (`backends/mongo.py:160-192`,
threat T-15.2-01): the one place artifact-authored data could become query/document
structure.** Mongo closed it with a charset gate; Neo4j closed it by binding
artifact-authored names as parameters and never as pattern text
(`backends/neo4j.py:284-290`). The Fluree closure is stronger and simpler:

> **Rule: no artifact-authored string ever occupies an IRI position.**
> Every `@id` is adapter-minted and colonless (recommend
> `ccf_<kind>_<hex>` from `content_hash(partition, tenant_id, key…)`). Every property
> name is a code-authored constant. Every `@type` label is a code-authored constant.
> `entity_uri`, `relationship_type`, `entity_class` and every claim attribute travel as
> **`xsd:string` literal values**, where the guard explicitly does not apply and where
> Cypher reads them as ordinary properties compared against `$param`s.

This rule is also what makes `opts.strictCompactIri: false` unnecessary — the adapter
must **not** set it (it exists for legacy migrations and would re-open the hazard).

### How probe F-A5 asserts, rather than infers

The datatype must be **read back**, not assumed. Two independent assertions, both
cheap:

1. **Direct datatype read via SPARQL `DATATYPE()`.** `v4.0.7` shipped
   `fix: DATATYPE() returns the datatype IRI, not a compact string`
   `[VERIFIED: GitHub release body v4.0.7]`, so the answer is an unambiguous IRI:

   ```http
   POST /v1/fluree/query/ccf:main
   Content-Type: application/sparql-query
   Accept: application/sparql-results+json
   ```
   ```sparql
   SELECT ?v (DATATYPE(?v) AS ?dt)
   WHERE { ?s <ccf_observed_at> ?v }
   ```
   **PASS:** `?dt` is `http://www.w3.org/2001/XMLSchema#string` for **every** temporal
   property the adapter writes (`ccf_observed_at`, `ccf_superseded_at`,
   `ccf_valid_from_cmp`, `ccf_valid_to_cmp`, `ccf_first_observed_at`,
   `ccf_last_observed_at`).
   **FAIL:** anything else, most dangerously `#dateTime`.
   *(Using SPARQL here is a diagnostic probe, not the read path — D-02's "Cypher reads"
   governs `query()`, not a test assertion. If the planner prefers to keep even probes
   Cypher-only, the fallback assertion is (2) alone, which is weaker.)*

2. **Behavioural assertion that comparison is lexicographic, not temporal.** Write two
   timestamps whose canonical text differs but which denote the same instant is
   impossible under CCF's canonical serializer (it always emits `Z` with microsecond
   precision) — so instead assert the *fixed-width* property: write
   `2026-03-01T00:00:00.000000Z` and `2026-03-01T00:00:00.000001Z` and assert
   `WHERE c.ccf_observed_at > $boundary` discriminates them at microsecond
   granularity. A substrate that coerced to `xsd:dateTime` at millisecond precision
   would collapse them. This is the direct byte-drift assertion
   (04-RESEARCH.md Pitfall 3; `backends/neo4j.py:57-63`).

3. **Ledger-context assertion (D-02's other half).** `GET /context/{ledger}` must
   return `{"@context": null}`. Assert it after bootstrap, in the same probe. Cheap,
   and it catches a future change that starts setting a default context.

**Why this fails silently without the probe (D-06's rationale, made concrete).**
Fluree's comparison rules say: *"Ordering (`<`, `<=`, `>`, `>=`) raises an error —
ordering between incompatible types is undefined"* but also *"temporal types can be
compared with string representations that parse to the same temporal type."*
`[CITED: concepts/datatypes.md § Type Coercion and Compatibility]` So a coerced
`xsd:dateTime` column compared against a string `$boundary` does **not** error — it
compares *temporally*, at whatever precision the engine normalizes to. The as-of cut
would still "work", and would diverge from the fallback only on sub-precision
boundaries — scattered, non-obvious differential failures, exactly as D-02 predicts.

## R5 — Stage-2 traversal translation: what carries over, what breaks

This section is the phase's dominant risk. **Read it before drawing the stage-2 task.**

### What carries over from `Neo4jGraphReader` verbatim

`backends/neo4j.py:585-756` (`_translate_query`) is a three-statement shape:
**survivors → edges → walk**, with the reached set filtering both row sets in Python.
The overall shape, the short-circuits, and the segment predicates transfer:

| Neo4j element | Fluree | Note |
|---|---|---|
| The three-statement structure and the Python-side reached-set filter (`:737-748`) | **carries verbatim** | Fluree has no read transaction to hold three statements in; three sequential `POST`s under one `Fluree-Min-T` is the equivalent, and is sound because CCF has one writer and the reads are within one `query()` |
| Empty-`allowed_entities` short-circuit (`:628-633`, `GQ-04`) | **carries verbatim** | pure function of the query value, no round trip |
| Over-ceiling `depth_limit` decline (`:634-641`, `GQ-29`) | **carries verbatim**, plus a new body-size decline (§R2) | same D-04 argument, same ratified-mechanism precedent |
| `_SURVIVORS_MATCH` as-of cut — `c.observed_at <= $boundary AND (c.superseded_at IS NULL OR c.superseded_at > $boundary)` (`:308-312`) | **carries verbatim** | string comparison + `IS NULL` both documented-supported; correctness depends entirely on F-A5 |
| `_ENTITY_VALIDITY` / `_EDGE_VALIDITY` over the write-time `*_cmp` re-renderings (`:320-323`, `:366-369`) | **carries verbatim** | keep `_neo4j_claim_projection`'s discipline (`_writer.py:1512-1562`) — canonical re-render at write time |
| `_ENTITY_ALLOWED` / `_EDGE_ALLOWED` / `_EDGE_CLOSURE` membership predicates (`:347`, `:379-399`) | **carries verbatim** | `x IN $param` list membership; probe once (F-A2 companion) |
| `_EDGE_TYPES` as `rc.relationship_type IN $types` on the **claim node** (`:389`) | **carries verbatim** | this is a *claim node* property, not a relationship property — unaffected by the break below |
| Walk-start selection within survivors, seeds intersected with survivors (`:702-713`, `GQ-11`) | **carries verbatim** | pure Python |
| `depth_limit == 0` skips the walk (`:715-718`) | **carries verbatim** | and matches Mongo's third correction |

### What breaks — three findings, in descending severity

#### Break 1 (CRITICAL) — relationship properties do not exist on plain edges

`_WALK_EDGES_ALL` (`backends/neo4j.py:440-446`) is:

```cypher
AND all(r IN relationships(p) WHERE r.partition = $partition
        AND r.tenant_id = $tenant
        AND r.relationship_key IN $crossable
        AND r.relationship_type IN $types)
```

Fluree's relationship-lowering table `[CITED: query/cypher.md § Relationship lowering
— three shapes, three behaviors]`:

| Pattern | Sees plain RDF? |
|---|---|
| `(a)-[:T]->(b)` | Yes |
| `(a)-[r:T]->(b)`, `r` **value-only** (`type(r)`, `startNode`, `endNode`, `collect`) | Yes |
| `(a)-[r:T]->(b)`, `r` **property-read** (`r.prop`, `properties(r)`, `keys(r)`) | **No — only reifier-bundled edges** |

and, of relationship values obtained from `relationships(p)`:
*"`properties(r)` / `r.prop` its edge properties (**present only for a
reified/annotated edge — a plain path edge has none**)."*

**Consequence:** if CCF edges are written as plain RDF triples, every `r.<prop>` in
the hop predicate evaluates to null, `all(...)` is false for every path, and the walk
returns **an empty reached set**. The query is syntactically valid, returns `200`, and
answers wrongly. This is *not* covered by the "clear error, never a silently wrong
result" promise, which is about *parse-time rejection of unsupported forms*.

Fluree's docs state the consequence in exactly these terms for the general case:
*"If your data was loaded via JSON-LD without `@annotation`… `MATCH (a)-[r:T]->(b)
RETURN r.since` returns zero rows even though the base triples exist."*

#### Break 2 (CRITICAL, compounding) — the only bounded var-length pattern is a single fixed type

Documented as deferred:
- **Bounded type-alternation** `-[:A|B*1..3]->` — *"use the unbounded form"* (F-A3's premise).
- **Undirected untyped** `-[*]-` — *"A direction is required; undirected untyped
  (`-[*]-`) is deferred."*

CCF traversal is **undirected** and **bounded** (`GQ-10`,
docs/GRAPH_QUERY_SEMANTICS.md:201). Intersecting the constraints leaves exactly one
admissible pattern shape: **a single, fixed, code-authored relationship type,
undirected, with literal bounds** — i.e. Neo4j's `-[:CCF_EDGE*1..N]-`.

But then `type(r)` is always the constant `CCF_EDGE` and carries no CCF information.
So the *type cut* (`GQ-10` typed crossability) also has nowhere to live on a plain
edge. Break 1 and Break 2 together mean: **on plain RDF edges, neither the
crossability cut nor the type cut is expressible.** F-A3's named workaround
(`all(r IN relationships(p) WHERE type(r) IN $types)`) would require CCF relationship
types to *be* the RDF predicates, which Break 2 forbids for a bounded pattern.

#### Break 3 (HIGH) — the policy family's classification cut needs dynamic property access, which is not documented

`_ENTITY_POLICY` (`backends/neo4j.py:335-340`) reads:

```cypher
AND any(ec IN keys($attribute_by_class)
        WHERE c.entity_class = ec
          AND c[$attribute_by_class[ec]] IN $classifications)
```

`c[$key]` is **dynamic property access with a parameterized key** — the mechanism that
lets an artifact-authored attribute name stay data. Fluree's documented accessor
surface is *"Property accessors `n.prop` in expression position… Bare-variable target
only in v1"*; `n[expr]` appears nowhere in the reference, the cookbook, or the
Neo4j-differences list. Map indexing by a key expression is likewise undocumented
(only *list* indexing `list[i]` is). **Presumed absent; must be probed.**

This one bites **stage 1**, not stage 2 — the policy family is a non-traverse
predicate family.

### The recommended resolution: edge-as-node interposition

All three breaks have one shared cause — *the information the predicates need is not
readable where the engine puts it* — and therefore one shared fix: **move the
information onto node properties, where Fluree Cypher reads it reliably**, and reduce
every hop predicate to **membership in a set the adapter already computed**.

This is not novel; it is Mongo's move. `backends/mongo.py:33-42` reshapes the physical
model (the doubled-edge `TRAVERSAL_EDGES` collection) so that one `$graphLookup`
expresses the undirected walk, and `_walk` states hop admissibility as
`relationship_key ∈ crossable` — *"membership in that already-computed set rather than
re-deriving the predicates on traversal documents… a re-derivation is a second place
for the semantics to live, and the two would eventually disagree"*
(`backends/mongo.py:862-876`). The physical model is adapter-internal by D-IMPL-34.

**The model.** Every CCF relationship becomes an intermediate **edge node** joined to
its two endpoints by a single code-authored predicate:

```
(:CcfEntity {ccf_admit_key})  -[:CCF_LINK]->  (:CcfEdge {ccf_admit_key})  -[:CCF_LINK]->  (:CcfEntity {ccf_admit_key})
```

- One predicate `CCF_LINK`, so the pattern is `-[:CCF_LINK*1..M]-`: single fixed type,
  undirected, bounded — the one admissible shape (Break 2 satisfied).
- Undirectedness needs **no doubling** (Mongo needed it because `$graphLookup` is
  directed; the Cypher pattern is not). Strictly cheaper than the Mongo write path.
- A CCF hop of depth *d* is `M = 2d` Cypher hops. The graph is bipartite
  (entity–edge–entity), so **only even-length paths end at an entity** and the parity
  handles itself once the terminal is labelled `(x:CcfEntity)`.
- **Every hop predicate becomes one node predicate over one parameter list:**

  ```cypher
  MATCH p = (seed:CcfEntity)-[:CCF_LINK*1..M]-(x:CcfEntity)
  WHERE seed.ccf_admit_key IN $starts
    AND all(n IN nodes(p) WHERE n.ccf_admit_key IN $admissible)
  RETURN DISTINCT x.ccf_entity_uri AS entity_uri
  ```

  with `$admissible` computed in Python as
  `{"e:"+uri for uri in survivors ∩ allowed} ∪ {"r:"+key for key in crossable}` —
  the two namespaces prefix-disambiguated so an `entity_uri` can never collide with a
  `relationship_key`. Crossability (type, temporal, policy, validity,
  `allowed_entities` on both endpoints, endpoint closure) is already fully decided by
  the *edges* statement that computes `$crossable`; the walk re-states nothing.

  This is `all(n IN nodes(p) WHERE …)` — precisely the form D-04's own text names, and
  precisely the form Fluree documents as working with property access on the loop
  variable (*"a node element scans the property at eval time"*).

**Semantics check — trail enumeration vs reachability.** The undirected bounded
var-length runs the **path-enumeration** search with Cypher relationship-uniqueness
(trail semantics), one row per path. CCF asks a *reachability* question. These agree
on the answer set: any walk of length ≤ M can be reduced to a trail of length ≤ M
between the same endpoints, so the set of nodes reachable by a trail within M hops
equals the set reachable by any walk within M hops. `RETURN DISTINCT` collapses the
multiplicity. **The set is the same; only the row count differs.** `[ASSUMED — a
graph-theoretic argument, not a Fluree claim; the differential corpus is what proves
it, and the resurrection/self-loop/mixed-direction shapes are exactly the cases where
it would show.]`

**Named operational risk.** *"It is guarded by visited/path caps that **error** rather
than silently truncate — narrow dense patterns with hop bounds, a bound end, or a
type."* An erroring cap is a hard failure, not a degrade. The corpus is small, so CI
is safe; a production graph is not. **The plan must state the adapter's response to a
cap error.** Recommendation: catch it and **decline the translation** (`return None`)
so the D-04 fallback answers — which is byte-identical by construction and visible in
`fallback_answers` telemetry. Note this decline happens *after* a round trip, unlike
the neo4j precedent's pure-value declines; that is a deliberate, documentable
difference, not a contract violation (`GQ-32` constrains what a *non-`None`* return
must contain, not when `None` may be produced).

### The alternative, and why it is second choice

**Edge annotations.** Write CCF edges as annotated edges — Fluree's RDF-1.2 reifier
bundles, the primitive Cypher relationship-properties sit on. Then `r.relationship_key`
reads, and `_WALK_EDGES_ALL` transfers almost verbatim.

Against it: (a) it is the *youngest* surface in play (RDF 1.2 edge annotations landed
v4.1.0, 2026-06-23; the Cypher front-end v4.1.1); (b) the docs list *"property filters
on a var-length relationship"* among the deferred forms, and a property-reading
relationship inside a path-enumeration walk sits uncomfortably close to that line;
(c) it makes the JSON-LD write body materially more complex, against a write path
already rated the harder half; (d) a property-reading `r` **stops seeing plain
edges**, so any modelling slip produces the same silent empty answer.

Interposition uses only mechanisms that are old, plain, and heavily exercised
(subjects, node properties, one predicate, membership tests).

### Mongo's four `$graphLookup` corrections, adjudicated one by one

CONTEXT.md asks for a verdict on each, and forbids assuming immunity. The four, named
from the code (`backends/mongo.py:33-42`, `:789-808`, `:841-852`):

| # | Mongo correction | Where it lives | Cypher verdict |
|---|---|---|---|
| 1 | **Directedness doubling** — `$graphLookup` follows `connectFromField → connectToField` in one direction; CCF traversal is undirected, and two directed lookups do not compose | the doubled `TRAVERSAL_EDGES` collection, maintained by the write path (`_writer.py:2159-2178`) | **STRUCTURALLY IMMUNE.** Cypher has a first-class undirected pattern (`-[:T]-`, "forward ∪ reverse Union"; undirected var-length runs path-enumeration). No doubling needed — the interposed model is written once. |
| 2 | **Seed exclusion** — `$graphLookup` excludes the starting document from its `as` array, while CCF includes the walk starting points | the caller, `reached = set(starts)` before the stage (`mongo.py:789-795`) | **NOT IMMUNE — but identical to Neo4j, not to Mongo.** Neo4j's translation also seeds `reached = set(starts)` (`neo4j.py:714`) because `*1..N` starts at one hop. The correction transfers verbatim from the Neo4j template. Cost: zero. |
| 3 | **`depth_limit = 0` has no `maxDepth` expression** — `maxDepth: 0` is already one lookup, so a zero bound must skip the stage entirely | the caller (`mongo.py:796-799`) | **NOT IMMUNE — same as Neo4j.** `-[:T*1..0]-` is not a bound; depth 0 must skip the `MATCH` and answer with the starts (`neo4j.py:715-718`). Transfers verbatim. |
| 4 | **`maxDepth` off-by-one** — `depthField` starts at 0, so CCF depth *N* is `maxDepth: N-1` | `_walk` (`mongo.py:901`) | **STRUCTURALLY IMMUNE in kind, REPLACED by a new one.** Cypher's `*1..N` is 1-based, so no `N-1`. **But interposition introduces its own arithmetic: CCF depth *d* is `*1..2d` Cypher hops.** That is an off-by-factor-of-two, and it is exactly the class of error #4 was. It must be asserted directly at depth 1, 2 and 3 against the fallback, not reasoned about. |

**Net:** two of Mongo's four transfer verbatim (they are really *Neo4j's* corrections
too), one is genuinely absent, one is replaced by a new one of the same family. Add to
these the **three Fluree-specific breaks above**, which have no Mongo analogue. The
honest count is therefore **five corrections, not zero** — the CONTEXT's instruction
not to assume immunity was well placed, and the "Cypher avoids Mongo's costs"
expectation should not be carried into the estimate.

## R8 — DI-15.2-03 non-reintroduction

### Status correction

CONTEXT.md's `<canonical_refs>` describes DI-15.2-03 as *"a live conformance question
about timestamp rendering."* **It is closed.** `.planning/phases/15.2-substrate-adapters-and-query-pushdown/deferred-items.md`
records: *"CLOSED 2026-08-08 — Dave ruled option (a)"* (`D-IMPL-90 (resolution,
2026-08-08)` in `docs/DECISIONS.md`). The fix landed in
`ccf.graph._writer::_claim_payload` (`_writer.py:242-278`): the persisted `claim_json`
now renders through `canonical_bytes`, so **one instant has one rendering everywhere
in the fabric**. Verified as a 12-arm A/B (3 backends × 2 authoring forms × 2
renderers): claim-identity digest `f7f27f52063700d5…` in all twelve; the answer-bytes
digest moves only for the defect.

The corpus now **exercises** the corner rather than documenting it:
`query_corpus.py::offset_authored_validity_cases` (`:649`) draws from
`AUTHORING_OFFSETS` (`:114`), registered in `corpus_cases()` (`:726-736`), with
`test_offset_authored_validity_answers_identically_on_each_reader` as the named
per-param regression. Each container leg grew by exactly +1 param when it landed.

**So the question for Phase 15.3 is not "is it open" but "can the Fluree write path
re-open it".** It can, in two distinct ways.

### Re-introduction vector 1 — a second rendering, on the wire

`_claim_payload` guarantees the `claim_json` **string** is canonical. But the Fluree
adapter also writes **projected comparison properties** —
`ccf_valid_from_cmp`/`ccf_valid_to_cmp`/`ccf_observed_at`/`ccf_superseded_at` — the
things the pushed `GQ-09`/`GQ-07` predicates actually compare. `_neo4j_claim_projection`
(`_writer.py:1512-1562`) and `_mongo_claim_projection` (`:1847-1901`) both re-render
through `parse_timestamp(...)` → `canonical_timestamp(...)`. **`_FlureeTxn` must do
the same, from the same helpers, and must not shortcut by copying the payload's raw
JSON value.**

**What the plan must assert:** a unit test in `tests/graph/test_fluree_backend.py`
that admits an **offset-authored** claim through booted L2 and asserts, directly
against the store, that `ccf_valid_from_cmp` reads back as canonical `…Z` text with
microsecond width. This is the Fluree twin of what `_utc_fixed_width` handled on the
SQL side — except that Fluree has no `_utc_fixed_width`: **the normalization happens
in Python at write time, and there is no second chance at read time.** That asymmetry
is worth a docstring.

### Re-introduction vector 2 — JSON-LD datatype coercion turning canonical text into a temporal value

This is where DI-15.2-03 and F-A5 meet, and it is the more dangerous vector because it
defeats the fix *after* the fix ran correctly. If `ccf_valid_from_cmp` lands as
`xsd:dateTime`, then `ccf_valid_from_cmp <= $boundary` compares **temporally**, not
lexicographically — and Fluree explicitly permits that comparison
(*"temporal types can be compared with string representations that parse to the same
temporal type"*). Two claims one microsecond apart could then compare equal at
whatever precision the engine normalizes to, and the pushed answer would diverge from
the fallback's `datetime`-value comparison on exactly the boundary cases the corpus
generates.

**What the plan must assert:** F-A5's `DATATYPE()` check must cover
`ccf_valid_from_cmp` and `ccf_valid_to_cmp`, not only `ccf_observed_at`. And the
differential leg must run the `offset_authored_validity_cases` shapes — which it does
automatically, because they are already in `corpus_cases()` and the fluree param joins
the same suite. **No corpus change is needed for DI-15.2-03 coverage.** Record that in
the gate package: it is direct evidence for the no-refactor claim (a corner discovered
on SQL, fixed at the contract tier, and inherited free by a substrate that did not
exist when it was fixed).

### The third, subtler vector — worth one sentence in the plan

Fluree's `/update` accepts `opts.eventTime` for backdated commits, requiring RFC 3339
values *"monotonically non-decreasing along the ledger's commit chain, and not in the
future."* `[CITED: api/endpoints.md § POST /update]` **The adapter must never set it.**
It would tie CCF's `observed_at` (data, arbitrary, non-monotone) to Fluree's commit
clock — which is precisely the transaction-time-for-observation-time substitution
D-IMPL-88 forbids, and which would fail on the first late-arriving observation. State
the prohibition in `_FlureeTxn`'s docstring so a future reader who discovers the
feature finds the refusal already argued.

## Common Pitfalls (Fluree-specific, beyond the six carried from feasibility research)

The feasibility research named six. These are the ones this session added; each has a
named mitigation and a place in the plan.

### Pitfall 7 — a property-reading relationship variable silently sees no plain edges
**What goes wrong:** the hop predicate returns an empty reached set; the query is
valid, returns `200`, and is wrong.
**Root cause:** Fluree relationships are edge annotations; `r.prop` requires a reifier
bundle (§R5 Break 1).
**Avoid:** edge-as-node interposition — no relationship property is ever read.
**Warning sign:** a traversal query that returns exactly the seeds and nothing else, at
every depth.

### Pitfall 8 — artifact-authored strings in IRI positions
**What goes wrong:** a CCF `entity_uri` like `counterparty:acme` is rejected at parse
time by the strict compact-IRI guard; a `@context` that defines the prefix would
instead expand it silently into a different identifier.
**Avoid:** the §R3 rule — adapter-minted colonless `@id`s, code-authored property
names, all artifact data as `xsd:string` literals. Never set
`opts.strictCompactIri: false`.
**Warning sign:** `400` with "Unresolved compact IRI" on a write that worked for other
fixtures.

### Pitfall 9 — a default `@context` or `@vocab` set on the ledger silently changes what every Cypher statement matches
**What goes wrong:** *"Adding `@vocab` to a ledger whose data was written bare (or vice
versa) changes what Cypher statements match."* Reads return nothing; writes still
succeed.
**Avoid:** never call `PUT /context`; assert `GET /context` returns `null` in F-A1;
never pass `?default-context=true`.
**Warning sign:** every read returns empty after an unrelated operational change.

### Pitfall 10 — the 1 MB query-body limit meets a large `allowed_entities` set
**What goes wrong:** `413 Payload Too Large` on a legitimate query.
**Avoid:** a byte-budget decline → fallback (D-04), mirroring `MAX_DEPTH_CEILING`.
**Warning sign:** failures correlated with survivor-set size, not with query shape.

### Pitfall 11 — the path-enumeration visited/path caps **error** rather than truncate
**What goes wrong:** a dense graph turns a valid traversal into a hard failure.
**Avoid:** catch and decline to the fallback; state the residual.
**Warning sign:** an error message naming a cap; `fallback_answers` climbing under load.

### Pitfall 12 — `opts.eventTime` looks like the answer to CCF's bitemporality and is not
**What goes wrong:** an author discovers backdated commits and ties `observed_at` to
the commit clock. It requires monotonically non-decreasing values; L2's write stream
guarantees none.
**Avoid:** state the prohibition in `_FlureeTxn`'s docstring (§R8).
**Warning sign:** a `400` on the first late-arriving observation — or worse, none,
because the fixtures happened to be ordered.

### Pitfall 13 — the depth doubling of the interposed model
**What goes wrong:** CCF depth *d* is `*1..2d` Cypher hops; an off-by-factor-of-two is
silent and looks like an ordinary differential failure at depth ≥ 2.
**Avoid:** assert depths 0, 1, 2 and 3 directly against the fallback before promotion.
This is Mongo's `maxDepth` off-by-one wearing different clothes.

## Open Questions

1. **BF-1 — the D-10/D-11 permitted-surface enumeration.**
   - *Known:* adding any substrate requires additive changes in `src/ccf/boot.py` and
     `src/ccf/deployment/manifest.py`; measured from the mongo landing.
   - *Unclear:* whether Dave rules this a D-10 clarification (planner fixes the
     enumeration) or a `D-IMPL` (the claim's wording is itself the decision).
   - *Recommendation:* present the Tier-A/B/C repair; the gate script cannot be written
     until it is settled. **Blocks task 3, not tasks 1–2.**

2. **Does F-A4(a) hold — is a ground `delete` accepted without a `where`?**
   - *Known:* ground `insert` without `where` is documented ("the plain insert path");
     SPARQL has `DELETE DATA`; JSON-LD's ground-delete form is not documented.
   - *Unclear:* the JSON-LD case.
   - *Recommendation:* probe first. If it fails, the SPARQL-UPDATE multi-op route works
     (v4.1.3 shipped multi-op UPDATE) but departs from D-02's letter → checkpoint for
     Dave, not an executor decision.

3. **Edge-as-node interposition vs edge annotations.**
   - *Known:* both are adapter-internal physical-model choices (D-IMPL-34); §R5 argues
     for interposition on maturity and on hop-predicate simplicity.
   - *Unclear:* whether annotations would in fact work under path enumeration (the docs
     defer "property filters on a var-length relationship").
   - *Recommendation:* implement interposition; make F-A3(e) record the annotation
     route's viability so a future reader knows it was measured, not assumed.

4. **Should the drift detector track `4` rather than `4.1`?**
   - *Known:* D-09 says `4.1`; `4.1` catches patch drift only and is a no-op until
     4.1.5.
   - *Unclear:* whether Dave intended minor-drift coverage.
   - *Recommendation:* implement `4.1` exactly as ruled; record the limitation in the
     job's comment so the gap is visible rather than assumed away. **Not a
     re-litigation — a documented scope note.**

5. **What does the adapter do on a `Fluree-Min-T` timeout?**
   - *Known:* the server returns a read-after-write timeout error.
   - *Unclear:* nothing about CCF forbids either choice.
   - *Recommendation:* raise (broken deployment), never degrade — degrading would
     answer from a stale `t`, which is a silent correctness failure. Consistent with
     the I.1 refusal-vs-exception line.
