# Phase 15.3: Code Review Report

**Reviewed:** 2026-08-09T03:11:53Z
**Depth:** standard

## Summary

Reviewed the Fluree v4 adapter surface added in phase 15.3: the HTTP/JSON-LD
store and openCypher read translation (`fluree.py`), the buffered-batch writer
(`_FlureeTxn` / `FlureeGraphWriter` in `_writer.py`), the four registration
sites, the phase gate, the test surface, and the CI changes. The diff was read
against base `96f54c5`, not as freshly-written files.

The areas flagged for close attention held up under most probing. Tenant and
partition confinement in the walk is genuinely closed on both the seed and the
path predicate, the `e:` / `r:` admit-key namespaces cannot collide (a
`relationship_key` is a `content_hash`, and the two prefixes differ in the
first character), `_FlureeTxn`'s buffered mutations are safe because
`BaseGraphWriter` opens exactly one transaction per claim so no node or
predicate is ever `_replace`d twice in one body, and the `schedule:` trigger on
`live-legs.yml` is correctly guarded — both secret-consuming / credit-spending
jobs carry `if: github.event_name == 'workflow_dispatch'`.

One defect is real and reproducible: **the materialized policy key is not
injective, because only two of its three components are gated for the
separator, and the write path gates none of them.** I reproduced a claim that
the pushed policy family admits and the audited fallback excludes. That is the
exact over-disclosure divergence the guard was written to prevent, and the
function's own docstring asserts an invariant ("a key built here carries
exactly two separators") that the code does not establish.

The remaining findings are bounded: a dead write-time projection with no
reader, an unreachable credential path, a leaked HTTP client on the
construction error path, a latent sequence-number collision guarded only by the
current one-claim-per-transaction shape, two documentation statements that are
false as shipped, and two structural gaps in the gate's own coverage.

## Critical Issues

### CR-01: The materialized policy key is not injective — the pushed policy family admits a claim the fallback excludes

**File:** `src/ccf/graph/backends/fluree.py:452-454`, `src/ccf/graph/_writer.py:2549-2551`

**Issue:**

`policy_key()` refuses to encode a `NUL` in `attribute` or `value`, but does
**not** check `entity_class`:

```python
if any(POLICY_KEY_SEPARATOR in part for part in (attribute, value)):
    return None
return POLICY_KEY_SEPARATOR.join((entity_class, attribute, value))
```

The docstring justifies the omission with "The class name is safe by
construction" and derives the whole injectivity argument from it — "A key built
here carries exactly two separators, so it can only equal a stored key that
also carries exactly two." Neither statement holds.
`EntityClaim.entity_class` is a bare `str` (`src/ccf/contracts/claims.py:115`)
with no charset validation, exactly like `attributes` keys, and
`classification_attribute_by_class` keys are artifact-authored. So the read side
can build a key with three separators.

The write side is worse: `_fluree_claim_projection` does not call `policy_key()`
at all. It joins with its own duplicated constant and gates nothing:

```python
policy_keys.append(
    _POLICY_KEY_SEPARATOR.join((entity_class, name, value))
)
```

Reproduced against the shipped code (no server needed):

```
claim   : entity_class="A", attributes={"B\x00C": "D"}
stored  : ['A\x00B\x00C\x00D']            # _fluree_claim_projection
query   : classification_attribute_by_class={"A\x00B": "C"},
          permitted_classifications={"D"}
pushed  : 'A\x00B\x00C\x00D'              # policy_key("A\x00B", "C", "D")
COLLIDES: True
fallback: attribute_by_class.get("A") -> None  ->  _admissible_entity == False
```

`_ENTITY_POLICY` pushes `c.ccf_policy_key IN $policy_keys`, so the translated
statement returns this claim. `ccf/graph/fallback.py:116-119` excludes it,
because the claim's own class `"A"` has no declared classification attribute.
The pushed path therefore **over-discloses a record the policy family excludes**
— threats T-15.2-01 / T-15.2-03, and precisely the divergence the differential
bar exists to catch. The differential suite cannot catch it because the corpus
does not generate control characters in class names.

`tests/graph/test_fluree_backend.py:2111-2112` asserts the refusal for the
`attribute` and `value` components only; there is no assertion for
`entity_class` and none for the write side.

**Fix:** gate all three components, and make the write side use the one
implementation rather than a second copy:

```python
# src/ccf/graph/backends/fluree.py
def policy_key(entity_class: str, attribute: str, value: str) -> str | None:
    if any(
        POLICY_KEY_SEPARATOR in part
        for part in (entity_class, attribute, value)
    ):
        return None
    return POLICY_KEY_SEPARATOR.join((entity_class, attribute, value))
```

```python
# src/ccf/graph/_writer.py — replace the local join, drop _POLICY_KEY_SEPARATOR
from ccf.graph.backends.fluree import policy_key
...
        for name, value in payload.get("attributes", {}).items():
            if not isinstance(value, str):
                continue
            key = policy_key(entity_class, name, value)
            if key is not None:
                policy_keys.append(key)
```

Refusing on the write side is safe and is the fail-closed direction: an
unencodable key is simply not materialized, the claim never matches a pushed
key, and the read side's decline (or the fallback) answers. Add the missing
assertions: `policy_key("A\x00B", "C", "D") is None`, and a write-side case
proving a separator-bearing attribute name materializes no key.

## Warnings

### WR-01: `_fluree_claim_projection` duplicates `POLICY_KEY_SEPARATOR` on a justification that is false

**File:** `src/ccf/graph/_writer.py:2452`, `src/ccf/graph/backends/fluree.py:262-274`

**Issue:** `fluree.py`'s docstring explains the duplicated constant with "The
write half of the pair lives in `ccf.graph._writer` (that module imports this
one; the reverse would break the CINV-02 confinement and cycle)". That argument
rules out `fluree.py` importing `_writer.py` — but the copy is in `_writer.py`,
and `_writer.py` already imports thirty names from `fluree.py` at
`_writer.py:109-145`, including `P_POLICY_KEY` and `attribute_predicate`.
Importing `POLICY_KEY_SEPARATOR` (or `policy_key` itself) is the direction that
already works. The second copy exists for no reason, and it is what made CR-01
possible: the guard lives on one copy only.

The drift test
(`test_the_write_path_materializes_exactly_the_key_the_read_path_pushes`,
`tests/graph/test_fluree_backend.py:2163`) compares the two constructions on a
clean key only, so it passes while the two disagree on every guarded input.

**Fix:** delete `_POLICY_KEY_SEPARATOR` from `_writer.py` and call the shared
`policy_key()` (see CR-01's fix). Extend the drift test with a
separator-bearing component so the assertion covers the branch that differs.

### WR-02: URL userinfo is silently discarded and never becomes a credential; the URL path is silently discarded too

**File:** `src/ccf/graph/backends/fluree.py:484-496`, `565-591`

**Issue:** `_server_root()` strips userinfo before the `httpx.Client` is built,
and nothing converts it into an `Authorization` header. httpx 0.28.1 does not
derive auth from URL userinfo either (verified: `build_request` on a client with
`base_url="http://u:p@host:8090"` emits no `Authorization` header). So a
deployment that supplies `fluree_url="http://user:pass@host:8090"` connects
**anonymously**, while the class docstring (`:82-88`, `:536-540`) and
`docs/SURFACE-CHANGES.md` both present URL userinfo as a supported credential
path. This diverges from the Neo4j precedent it cites: `neo4j.py:221-227` does
`clean_uri, auth = _split_credentials(uri)` and passes `auth` to the driver.

`_server_root` also drops the URL **path** (`_replace(..., path="")`), so
`http://host/fluree` silently becomes `http://host`. That contradicts
`:170-174`, which claims the well-known discovery is "what makes the store
correct behind a differently-mounted server" — the discovery document is itself
read from the stripped root, so a path-mounted server is unreachable.
`tests/graph/test_fluree_backend.py:1542` passes `/ignored` and asserts it is
dropped without recording that this is a lost capability.

**Fix:** either extract userinfo into an `Authorization: Basic ...` header the
way Neo4j extracts it into `auth`, or reject a URL carrying userinfo/path at
construction with a message naming `bearer_token` as the credential path:

```python
parts = urlsplit(url)
if parts.username or parts.password:
    raise ValueError(
        "fluree_url must not carry userinfo; supply bearer_token instead"
    )
if parts.path not in ("", "/"):
    raise ValueError(
        f"fluree_url must be an origin, not a mount path; got {parts.path!r}"
    )
```

Silently dropping a credential the caller supplied is the failure mode to
avoid.

### WR-03: `bearer_token` is unreachable through every supported boot path

**File:** `src/ccf/boot.py:222-231`, `src/ccf/deployment/manifest.py:289-296`, `541-544`

**Issue:** `FlureeGraphStore.__init__` accepts `bearer_token`, and both
`artifacts.py:943-950` and `manifest.py:394-399` document it as the deployment's
credential. But `_open_backend` constructs the store with `url` and `partition`
only, `boot()` exposes no `bearer_token` parameter, and `load_and_boot()`
neither accepts nor threads one. Combined with WR-02 there is **no supported way
to authenticate a Fluree backend** — an adopter must bypass `boot()` entirely
and mint a `BootToken` by hand, which is exactly the unforced path the
single-writer design exists to prevent.

**Fix:** add `fluree_bearer_token: str | None = None` to `boot()` and
`load_and_boot()`, threaded to the store constructor alongside `fluree_url`, on
the same never-persisted footing as `postgres_dsn`. Note this adds lines to
`boot.py` (budget 70, currently 56) and `manifest.py` (budget 25, currently 22)
— `manifest.py` is close enough to its budget that the D-IMPL-92 proxy may need
the correction discipline applied.

### WR-04: The `ccf_attr_*` attribute projection is write-only dead data

**File:** `src/ccf/graph/backends/fluree.py:307`, `381-421`; `src/ccf/graph/_writer.py:2552-2553`

**Issue:** `attribute_predicate()` and the `ATTRIBUTE_PROPERTY_PREFIX`
projection have exactly one caller — the write site at `_writer.py:2552` — and
**no reader**. Grepping `src/`, `tests/` and `tools/` finds no Cypher fragment
in `fluree.py` that references `ccf_attr_*`; every predicate family is answered
by `ccf_policy_key`, `ccf_entity_class`, `ccf_valid_*_cmp`, `ccf_admit_key` or
`ccf_relationship_type`. The Neo4j analogue exists because `neo4j.py:673` reads
it; the Fluree one does not.

Consequences: every entity claim carries a duplicate copy of its whole
string-valued attribute map into the transaction body — the body measured
against the hard `MAX_TXN_BODY_BYTES` limit at `fluree.py:717` — and the module
maintains its single documented "artifact-authored attribute name becomes an
IRI" surface (`:382`), with the compact-IRI hazard that entails, for no
consumer. The module docstring at `:37-39` describes these as "write-time
projections of the predicate-relevant fields"; on this backend they are not
predicate-relevant.

**Fix:** delete the projection from `_fluree_claim_projection` and delete
`attribute_predicate` / `ATTRIBUTE_PROPERTY_PREFIX` from `fluree.py`. That
removes the artifact-authored-string-to-IRI surface entirely, which makes the
module docstring's "no artifact-authored string ever occupies an IRI position"
rule true without exception. If the projection is being kept as headroom for a
future pushdown, say so at the definition and add a test that asserts it is
readable — an unread projection with no stated purpose will be deleted or
broken by the next maintainer.

### WR-05: The `httpx.Client` is leaked when `FlureeGraphStore.__init__` raises

**File:** `src/ccf/graph/backends/fluree.py:584-608`

**Issue:** the client is constructed at `:584`, then four requests run
unguarded: `/health` (`:591`), `/.well-known/fluree.json` (`:594-595`),
`.json()` on the discovery body (`:596`), and `POST /create` (`:603-608`). Any
of them raising leaves `self._client` referenced by nothing and never
`close()`d, holding its connection pool (and any keep-alive socket already
established by a non-2xx response) until GC. `boot()` propagates the exception,
so nothing downstream can clean up either. A supervisor retrying `boot()` against
a server returning 500 leaks one pool per attempt.

`:596` is also unguarded against a non-JSON body: a proxy returning an HTML 200
raises `json.JSONDecodeError`, which is not an `httpx.HTTPError` and so is not
covered by the documented `Raises:` contract at `:558-562`.

**Fix:**

```python
self._client = httpx.Client(...)
try:
    self._client.get(HEALTH_PATH).raise_for_status()
    discovered = self._client.get(WELL_KNOWN_PATH)
    discovered.raise_for_status()
    base = str(discovered.json().get("api_base_url") or "")
    self._base = base or DEFAULT_API_BASE
    created = self._client.post(...)
    if created.status_code != HTTPStatus.CONFLICT:
        created.raise_for_status()
except BaseException:
    self._client.close()
    raise
```

### WR-06: Every accumulated parameter is sent with every statement, and the byte budget counts the ones the statement never references

**File:** `src/ccf/graph/backends/fluree.py:1270-1362`

**Issue:** `params` is one dict mutated in place across up to three statements
and never has keys removed. By the time the walk is sent it carries `boundary`,
`policy_versions`, `policy_keys`, `allowed`, `types`, `survivors`, `starts` and
`admissible`, while `_WALK_MATCH_PREFIX` / `_WALK_NODES_ALL` reference only
`partition`, `tenant`, `starts` and `admissible`. Likewise `params["survivors"]`
is populated at `:1302` unconditionally, but `_EDGE_CLOSURE` is only appended
when `constrained` (`:1292-1293`) — so an unconstrained everything-question
sends the full survivor list as dead weight.

`_within_body_budget` (`:1396-1418`) is correct about what it measures ("the
exact bytes `post_query` would send"), which is precisely the problem: the
budget is consumed by parameters the statement cannot use. On a large
`allowed_entities` set the walk body carries `allowed` + `survivors` +
`admissible` where only `admissible` and `starts` are read, so pushdown can be
declined at roughly a third of the real request size. Every decline is
answered correctly by the fallback, so this is not a wrong answer — but the
guard rejects requests the server would have accepted.

It also makes the adapter depend on Fluree tolerating unreferenced request
parameters, which is not asserted anywhere and would break every translated
query if a future release validated them.

**Fix:** build a per-statement parameter dict instead of accumulating:

```python
def _bind(**extra: object) -> dict[str, object]:
    return {"partition": ..., "tenant": q.tenant_id, **extra}

survivor_params = _bind(boundary=boundary, **policy_bindings, **allowed_binding)
edge_params = _bind(boundary=boundary, ..., survivors=survivor_uris)
walk_params  = _bind(starts=sorted(starts), admissible=sorted(admissible))
```

and pass each to its own `_within_body_budget` / `post_query` pair.

### WR-07: `P_SEQ` is computed from the whole buffer, not the node's buffer — a latent chain-ordering collision

**File:** `src/ccf/graph/_writer.py:2837-2839`, `3026-3029`

**Issue:**

```python
P_SEQ: self._count(_FLUREE_ENTITY_CLAIM_COUNT, {**scope, "key": entity_uri})
       + len(self._entity_claims),
```

`self._count(...)` is scoped to `entity_uri`; `len(self._entity_claims)` is
**not** — it counts every entity claim buffered in the transaction, across all
entity URIs. Today the term is always `0`, because `BaseGraphWriter.upsert_entity`
(`_writer.py:684-735`) opens one transaction per claim and calls
`insert_entity_claim` exactly once. The `+ len(...)` term exists only to support
buffering more than one, and it is wrong for that case.

If a future batching path buffers `A1, B1, A2` in one transaction, `A` receives
seq `0` and `2`; the next transaction's `A3` reads `count(A) == 2` and computes
seq `2` — a duplicate. `SELECT_ENTITY_HISTORY` orders `ORDER BY
c.ccf_observed_at, c.ccf_seq` (`:1108`), so two claims of one entity sharing an
`observed_at` and a `seq` order non-deterministically, and `_restitch_chain`
would produce a different supersession chain per read. That defeats the very
tiebreaker `P_SEQ` exists to be ("the graph rendering of SQLite's `rowid`",
`fluree.py:230-231`), and it fails silently.

**Fix:** count only this node's buffered claims:

```python
P_SEQ: self._count(_FLUREE_ENTITY_CLAIM_COUNT, {**scope, "key": entity_uri})
       + sum(
           1
           for d in self._entity_claims
           if d[P_ENTITY_URI] == entity_uri
       ),
```

and the mirror in `insert_relationship_claim` on `P_RELATIONSHIP_KEY`.

### WR-08: `docs/SURFACE-CHANGES.md` states the shipped reader has no query translation

**File:** `docs/SURFACE-CHANGES.md:2101-2103`, `docs/surface-changes/15.3-02-fluree-backend.md:76-78`

**Issue:** the `FlureeGraphReader` entry, assembled from plan 15.3-02's
fragment, says:

> `_translate_query` is deliberately **not** implemented in this plan: the
> reader answers everything through the fallback, which is fully conformant
> under D-04

That was true at plan 15.3-02 and is false of the shipped code: plans 15.3-03
and 15.3-04 landed a translation answering every predicate family including the
bounded walk (`fluree.py:1164-1394`). `docs/SURFACE-CHANGES.md` is the
adopter-facing migration note, so a reader deciding whether to expect pushdown
gets the wrong answer from the one document written to tell them. The neighbouring
`MAX_DEPTH_CEILING` entry (`:2124-2126`) carries the same stale hedge — "the one
value a translated statement **would** inline" — where it now does.

**Fix:** update both the assembled entry and the `15.3-02` fragment to describe
the shipped reader (all predicate families pushed; four named declines — empty
`allowed_entities`, over-ceiling depth, non-injective policy family, over-budget
body — plus the post-round-trip path-cap decline), or add a superseding entry
recorded by `15.3-04`.

### WR-09: The gate's `_writer.py` AST check does not cover module-level statements

**File:** `tools/gates/gate_15_3.py:690-697`, `1095-1178`

**Issue:** `top_level_defs()` collects only `ClassDef` / `FunctionDef` /
`AsyncFunctionDef` from `module.body`. Every other module-level statement in
`src/ccf/graph/_writer.py` — assignments, `__all__`, imports, module constants
such as `ENTITY_KIND` / `RELATIONSHIP_KIND`, and any module-level SQL or
predicate constant — is invisible to the check. The gate's headline claim
(`:12-13`, `:1822-1825`) is "no mechanism anywhere in the SDK changed"; the
check's own docstring is narrower ("no existing class or function body"), and
the gap between them is real: `_writer.py` is Tier A with **no line budget**
(`ALLOWLIST:288-294`, and it is absent from `BUDGETS`), so a rewrite of an
existing module-level constant in that file passes every check the gate runs.

**Fix:** extend `top_level_defs` into a full module-body comparison keyed by
statement, e.g. compare `[ast.dump(n) for n in module.body if not isinstance(n,
(ast.ClassDef, ast.FunctionDef, ast.AsyncFunctionDef))]` between base and HEAD
and require the HEAD list to be a supersequence of the base list, so existing
module-level statements may be added to but not modified or removed.

### WR-10: The gate cannot police its own allowlist or budgets

**File:** `tools/gates/gate_15_3.py:378-382`, `280-418`, `480-492`

**Issue:** `tools/gates/*` is Tier C, "free", with the reason "this gate itself.
A gate that could not add itself could not exist". The consequence is that
`ALLOWLIST`, `BUDGETS`, `SINGLE_OWNER_DENY`, `FROZEN_PATHS` and
`WRITER_EXPECTED_ADDITIONS` are all editable within the measured surface with no
check at all. A wave that widened the allowlist or raised a budget to make its
own diff pass is mechanically indistinguishable from the gate's own authorship —
which is exactly the outcome `main()`'s failure message forbids in prose ("Fix
the DIFF — never the allowlist, the budgets, or the rules") and nothing enforces.
The third D-IMPL-92 correction shows the pressure is real: the allowlist was
widened three times during the phase, correctly each time, but nothing in the
gate distinguishes a correct widening from an expedient one.

`--base` is a second, smaller version of the same gap: `build_parser()` accepts
an arbitrary base ref with no restriction, and `check_base_resolution` only
requires ancestry plus the presence of `ADAPTER_MODULE` — a base one commit
before HEAD that happens to touch `fluree.py` passes both.

**Fix:** bind the gate's own rule surface to the append-only decision log. Add a
check that hashes the normalized rule surface (`ALLOWLIST` patterns + tiers,
`BUDGETS` limits, `FROZEN_PATHS`, `SINGLE_OWNER_DENY` keys) and asserts the
digest appears verbatim in `docs/DECISIONS.md`, which is already enforced
append-only. Widening then requires a dated correction entry, mechanically, and
the recursion the module docstring documents at `:115-145` becomes a check
rather than a narrative.

## Info

### IN-01: `git()` returns partial output when the command fails

**File:** `tools/gates/gate_15_3.py:581-592`

**Issue:** `if proc.returncode != 0 and not proc.stdout: raise` — a git command
that fails *after* writing some stdout returns that partial output silently, and
every downstream measurement (`measure`, `diff_lines`) treats it as complete. A
truncated `--numstat` would under-report changed paths, which is the direction
that makes the gate pass.

**Fix:** raise on any nonzero return code; the `and not proc.stdout` escape has
no caller that needs it (`blob()` and `git_ok()` already handle the
expected-failure cases).

### IN-02: `_graph_identity` omits the scheme and defaults the port to 8090

**File:** `src/ccf/graph/backends/fluree.py:467-481`

**Issue:** the identity is `fluree://{host}:{port}/{ledger}#{partition}` with
`port = parts.port or 8090`. `http://host` and `http://host:8090` produce the
same identity though they are different endpoints (conservative — over-refuses),
and `http://host` and `https://host` also collide. In the other direction,
`http://localhost:8090` and `http://127.0.0.1:8090` are the same server with
different identities, so both could hold a live writer. The last is a
pre-existing property shared with the Postgres and Neo4j identities
(`postgres.py:161-173`, `neo4j.py:168-181`) rather than something this phase
introduced, which is why it is Info rather than a finding against 15.3.

**Fix:** if tightened, include the scheme and use the scheme's default port
rather than a Fluree-specific literal — and do it across all three networked
backends at once, not just this one.

### IN-03: `test_no_relationship_property_is_read` greps a narrower shape than the rule it enforces

**File:** `tests/graph/test_fluree_backend.py:1960-1966`

**Issue:** the assertion is `re.findall(r"relationships\(\w+\)", source) == []`.
That catches the `relationships(p)` projection form probe F-A3(e) measured, but
not the more natural regression: a relationship variable bound in a pattern
(`-[r:CCF_LINK]-`) and read as `r.ccf_partition` in a `WHERE`. The named
failure mode — "an empty reached set with a 200" — arrives through either
shape.

**Fix:** add a second assertion that no pattern in the module binds a
relationship variable at all, e.g. `re.findall(r"-\[\s*[A-Za-z_]\w*\s*:",
source) == []` (the module's only relationship pattern is the anonymous
`-[:CCF_LINK*1..N]-`).
