# Phase 15.3 Plan 05: The Permitted-Change-Surface Gate — Summary

`make gate-15.3` exits **0 with zero findings**, and it has been watched to fail
**eight times on eight distinct violations** — four of them *after* the
authorised widenings, because an authorised widening is still a widening and is
exactly the move that can silently kill a gate's power.

The substantive result of this plan is not that the gate passes. It is that
**the gate found three real gaps between D-IMPL-92's normative rule and its
mechanical proxy**, and that finding them changed the ruling three times rather
than changing the diff once. The third gap arrived **recursively**: recording
the correction for the first two itself created it. That recursion is the
durable lesson for substrate #7, more than any of the three paths.

## What the gate found, and the ruling that followed

The first run against the real diff exited 1 on two changes. Neither was a
claim violation. Both were changes the **normative rule already permits or that
adding a substrate forces**, and in both cases the defect was that **layer 2
enumerated one instance of a class layer 1 states in general terms**. The
executor declined to widen the allowlist — the plan text, threat T-15.3-16 and
D-10's whole purpose all forbid it — and surfaced them as `D-IMPL` questions.

**Dave's verdict: extend the mechanical proxy to match the normative rule.
Never loosen the rule.** Recorded as an appended, dated correction to
`docs/DECISIONS.md` (`5204a97`), following the D-IMPL-86/-87 discipline so the
reasoning at each point in time survives. It is a **standing** ruling; substrate
#7 inherits both extensions and, more importantly, the reason they exist.

**Q1 — backend-specific unit tests are free as a CLASS.** Adding a required
`fluree_url` keyword to `_preflight_backend` forced three identical
`fluree_url=None,` lines into `tests/graph/test_mongo_backend.py`, which calls
it at three sites. Layer 1 already frees this verbatim ("backend-specific unit
tests … were never inside D-11's `src/ccf`-scoped hard line and are free");
Tier C had named only the new substrate's module. The allowlist now names
`tests/graph/test_*_backend.py`. **A bare special case for the mongo module was
refused** — it would repeat the very under-enumeration being fixed, and
substrate #7 would hit it again against a different neighbour.

**Q2 — one forced enumeration extension per conformance suite.**
`tests/conformance/test_graphstore.py` guards its fixture on a set literal of
backend names; without the new name in that set the added `pytest.param` raises
`NotImplementedError`, so the param addition is **not self-contained**. That
file has no `#:` block, so the first correction's comment-block permission
cannot reach it. The new permission is deliberately tight and is enforced
mechanically, not by intention — `is_forced_enumeration_extension` requires:

- the added and deleted lines are **identical once every string literal is
  removed** (no operator, identifier, bracket or call shape changed);
- the added line's literals are the deleted line's **plus exactly one**; and
- that one is the **new backend's name, derived from the `backend` `Literal`**
  rather than hard-coded.

**Both companions are RECORDED, not merely permitted.**
`check_recorded_in_package` requires every permitted non-param line to appear in
the gate package, armed by the package's existence exactly like the corpus rule.
It earned its keep on its first live run: it reported `8/9 line(s) present` and
named the missing one — the first draft of the package had paraphrased the
set-membership guard with its members reordered. An inaccurate record of a
permitted change is the same defect as no record (`ebb0aca`).

**Q3 — the decision log, and the recursion.** Recording the second correction in
`docs/DECISIONS.md` — which CLAUDE.md §11 makes **mandatory** for any `D-IMPL`
ruling — put that path into the measured surface, where Tier C had named
`docs/SURFACE-CHANGES.md` and `docs/surface-changes/*` and omitted the decision
log. The gate went red again, on the record of the fix for the previous failure.
**Ruling: `docs/DECISIONS.md` joins Tier C, bounded APPEND-ONLY** — added lines
pass, any deletion is a `gate153-append-only` finding. Grounds, in order of
weight: the test layer 1 actually applies is *"was never inside D-11's
`src/ccf`-scoped hard line"* and this path is not under `src/ccf` at all, so it
is free on the same footing as the `Makefile` and the CI workflows; §11 makes
logging mandatory, so a gate that fails because the project's own
decision-logging rule was followed is measuring the wrong thing; and D-IMPL-92
is standing, so every future substrate hits it identically.

**Why append-only and not a bare allow.** The D-IMPL-86/-87/-92 discipline is
that a correction is *appended and dated, never edited into the entry it
corrects*. Bounding the entry to zero deletions turns that documented discipline
into a **mechanical** one, so the allowlist entry stays a check that would still
fire on rewritten decision history rather than becoming a hole. A documented
discipline nothing enforces is the same class of object as an unfalsifiable
architectural claim — which is what this whole gate exists to convert.
**`docs/**` was considered and rejected**: it would free
`docs/GRAPH_QUERY_SEMANTICS.md`, which the same ruling freezes — real coverage
traded for a tidier allowlist.

**The rule itself is unchanged in all three cases.** Layer 1 gains nothing and
loses nothing. The four layer-2 checks, the budgets and their baselines, the
`_writer.py` AST assertion, the corpus rule, the freeze lines and the standing
scope are all untouched. Only the approximation moved, and only toward the rule
— which is the whole constraint: **a proxy may be corrected upward to match the
rule it approximates, never downward to match a diff it happens to be
measuring.**

**The shape, for substrate #7.** Three instances of one defect, the third
arriving recursively from the act of recording the second. The generalisation is
not the three paths: **any enumeration written by hand against a rule stated as
a category will under-enumerate, and the enumeration inside a gate is no more
exempt than the enumeration inside `boot.py` that BF-1 found.** The gate's own
allowlist is a registration enumeration. Each time, the fix was to name the
class.

## The eight negative tests — run, not assumed

Every one a **throwaway commit** (`git add -A && git commit --no-verify`),
because the gate measures `git diff BASE...HEAD`, which is commit-to-commit and
does not see the working tree. An uncommitted edit makes the gate exit 0, and
recording that as "watched to fail" would be false evidence for the one
requirement whose whole content is that the claim is demonstrated rather than
narrated. Each was reverted immediately with `git reset --soft HEAD~1` plus
`git restore --staged --worktree <the one file>` — the surgical equivalent of
the plan's `git reset --hard HEAD~1`, touching nothing else in the tree.

**On testing the widened Tier-C class directly, stated plainly rather than
faked.** The coordinator asked for a negative test that touches a path newly
inside the widened class "in a way that should still fail if such a shape
exists". **No such shape exists, by design.** Tier C is the *free* tier: layer 1
declares backend-specific unit tests outside the hard line entirely, so there is
no budget, no shape rule and no line count that a change to
`tests/graph/test_*_backend.py` could violate. A test asserting otherwise would
be theatre. What *can* be tested — and was, as negative test 5 — is that the
widening did not leak: the glob is `test_*_backend.py`, not `tests/graph/*`, and
paths outside it still fail.

The Q2 widening is the one that **is** shape-bounded, and it is where the real
proof lies: negative tests 6 and 7 attack it from both sides (an arbitrary edit
in the same file; a line that looks like an enumeration extension and is not),
and it holds on both.

Negative test 8 also surfaced **a second, independent defence nobody designed

nothing about each other: this gate's append-only bound, and the standing
citation lint the gate cites rather than re-implements. Found by running the
test, not by reasoning about it.

## Task 3 — the drift detector and the gate package

### `live-legs.yml` — the D-09 fluree upstream-drift detector

A `schedule:` trigger (`cron: "0 7 * * 1"`, weekly, a cadence and not a value)
alongside the unchanged `workflow_dispatch:`, plus a `fluree-drift` job carrying
a `services:` block this workflow did not have. It runs the same differential
leg `ci.yml` runs, against the **floating `4.1`** tag while `ci.yml` keeps the
exact `4.1.4` pin. `grep -c 'continue-on-error'` → **0**;
`grep -c 'fluree/server:4.1.4'` → **0** (the exact pin belongs to `ci.yml`, the
floating tag to the drift job; swapping them would defeat both).

**THE TRIGGER-SURFACE CHANGE, called out rather than slipped in.** This workflow
was `workflow_dispatch:` only and consumed Actions minutes only when a human
asked. It now consumes them on a cadence. I treated this as an executor call
rather than a question for Dave, on two grounds: D-09 already commissioned the
drift detector, and the cost is accepted on the record as threat **T-15.3-19**
("weekly, one leg, seconds of runtime against a ~70 MB Rust binary … the
trigger-surface change is called out explicitly in the SUMMARY so the cost is a
decision rather than a side effect"). If that reading is wrong, the cron line is
a one-line revert.

**A consequence handled rather than discovered later (Rule 2).** GitHub runs
**every** job in a workflow on **every** trigger unless the job says otherwise.
Adding `schedule:` would therefore have dragged the two opt-in example-03
live-model legs onto the cadence: a weekly 15-minute CPU-only Ollama run nobody
asked for, and an Anthropic run spending real API credit that would go red every
Monday on a repository without the secret — a permanently red workflow for a
reason unrelated to anything anyone changed. Both now carry
`if: github.event_name == 'workflow_dispatch'`, which is what keeps D-11's
opt-in posture true after the trigger surface widened. `fluree-drift`
deliberately carries no guard, so a human can also dispatch it and ask "has
upstream moved?" without waiting for Monday.

**The two honest limitations are in the job's own comment**, as facts rather
than as reconsiderations of D-09: `4.1` resolves to `4.1.4` today, so the job is
a **no-op until 4.1.5 ships** and a first green run proves the job works rather
than that no drift exists; and `4.1` tracks the **patch** stream only — a
`4.2.0` would pass unnoticed, and the `4` tag would have caught it.

## Q3, and how it closed

`make gate-15.3` reported, after the second correction was committed, **exactly
one finding**:

```
docs/DECISIONS.md:0 gate153-path-allowlist changed (+2/-0) but is not in the
D-IMPL-92 permitted-change surface.
```

The change is the appended D-IMPL-92 second correction itself — the record of
the ruling that resolved Q1 and Q2. **It is a third instance of the same
defect.** Layer 1 frees "Documentation" as a category; Tier C enumerated two
documentation paths (`docs/SURFACE-CHANGES.md`, `docs/surface-changes/*`) and
omitted the decision log. Recording the ruling there is not optional: CLAUDE.md
§11 requires it, the coordinator's own instruction directed it, and because
D-IMPL-92 is standing, **any** future substrate that surfaces a `D-IMPL` will
touch this path.

I did **not** add it to the allowlist. The ruling's own reasoning points at the
answer — name the class (documentation), not the instance — but that is a
ruling, not an executor's edit, and making it silently would be precisely the
move Q1 and Q2 exist to have caught. **Dave ruled** — Tier C gains
`docs/DECISIONS.md`, bounded append-only — and the gate now exits 0. The
recursion is recorded as the third correction's durable lesson.
