### The cypher-json response envelope — VERBATIM

This is the single most valuable artifact of the plan. The envelope is
documented nowhere (`query/output-formats.md` describes JSON-LD, SPARQL-JSON,
typed-JSON and AgentJson, and says nothing about cypher-json's row structure).

Request:

```http
POST /v1/fluree/query/ccf:probe-<uuid>
Content-Type: application/cypher
Fluree-Min-T: 1

{"cypher":"MATCH (n:CcfEntityClaim) WHERE n.ccf_tenant_id = $t RETURN n.ccf_entity_uri AS entity_uri","params":{"t":"tenant-a"}}
```

Response body, byte for byte:

```
{"results":[{"columns":["entity_uri"],"data":[{"row":["counterparty://acme"],"meta":[null]}]}]}
```

Response `content-type`: `application/vnd.fluree.cypher+json; charset=utf-8`

It is the Neo4j-HTTP tabular envelope. The extraction plan 15.3-02 should lift
verbatim (it is already in the module as `_rows`):

```python
result = response.json()["results"][0]
columns = result["columns"]
return [dict(zip(columns, entry["row"], strict=True)) for entry in result["data"]]
```

`dict(zip(columns, row))` is what makes rows satisfy `ccf.graph.reader.Row` for
`materialize_view`, exactly as `Neo4jGraphReader._query`'s `dict(record)` does.

### `X-Fluree-T` — **ABSENT**

The documented response header carrying the transaction time of the returned
data **is not sent on the Cypher route** by this build. Recorded, and harmless:
`Fluree-Min-T` on the *request* is what makes read-after-write correct, and it
was honoured on every probe that sent it. Nothing in the adapter should depend
on reading `X-Fluree-T` back.

### A11 — multi-key `ORDER BY` (string key, then integer key): **PASS**

The shape every one of plan 15.3-02's five acquisition statements needs
(`ORDER BY observed_at, seq`), and one that appears nowhere in §R1's
confirm/refute table.

```
{"results":[{"columns":["claim_id","observed_at","seq"],"data":[{"row":["c0","2026-03-01T00:00:00.000000Z",0],"meta":[null,null,null]},{"row":["c1","2026-03-01T00:00:00.000000Z",1],"meta":[null,null,null]}]}]}
```

Two claims sharing one `ccf_observed_at` arrive in `ccf_seq` order. **The
acquisition statements may order on both keys.** No Python-side stable sort is
needed, and the D-07 rung-1 repair budgeted for an A11 failure is not spent.

### A12 — inline map pattern in `MATCH`: **PASS**

`MATCH (c:Label {prop: $p})` parses **and** returns the same count as the
`WHERE`-clause form of the same query (both `2`). **The acquisition statements

## F-A6 — dynamic property access: **FAIL, and it fails SILENTLY**

This is the finding that most justifies D-06's probe-first split.

| Query | Result |
|---|---|
| Control: `WHERE c.ccf_tenant_id IN $values` | `{"n": 1}` |
| Probe: `WHERE c[$key] IN $values` | **`{"n": 0}` — HTTP 200** |
| Probe: `RETURN c[$key] AS v` | **`{"v": null}` — HTTP 200** |

`c[$key]` **parses, returns 200, and evaluates to null.** It is not covered by
Fluree's "clear error, never a silently wrong result" promise, which is about
parse-time rejection of unsupported *forms*.

Had `_ENTITY_POLICY` (`backends/neo4j.py:335-340`) been ported verbatim with
only the `ccf_` prefix changed, **the stage-1 policy family would have silently
excluded every claim** — a wrong answer with a 200 status, on the predicate
family that gates the majority of real queries. The probe's verdict is
therefore taken by comparison against a static-access control, and the test
enforces that method so a future reader cannot regress it to a status check.

### The resolution — proven end to end, but NOT in the form the plan named

**Assumption A7, as the plan words it, is REFUTED.** The named form
`any(k IN $keys WHERE k IN c.ccf_policy_key)` is rejected at parse time:

```
400 {"error":"Cypher lowering error: unsupported in v1: `IN` right-hand side must be an inline list `[a, b, ...]` in v1","status":400,"@type":"err:parse/CypherLower"}
```

An `IN` right-hand side must be an inline list **or a `$param`** (the control
proves parameters work); it may **not** be a property expression.

**But the mechanism survives, because a multi-valued property fans out into one
row per value rather than yielding a list.** Observed directly:

```
{"results":[{"columns":["claim_id","pk"],"data":[{"row":["pk1","Counterparty region emea"],"meta":[null,null]},{"row":["pk1","Counterparty risk_tier tier-1"],"meta":[null,null]},{"row":["pk2","Counterparty risk_tier tier-9"],"meta":[null,null]}]}]}
```

So plain membership expresses the intended "any materialized key is
admissible", and `RETURN DISTINCT` collapses the multiplicity:

```cypher
MATCH (c:CcfPolicyProbe) WHERE c.ccf_tenant_id = $t
  AND c.ccf_policy_key IN $keys
RETURN DISTINCT c.ccf_claim_id AS claim_id
```

Proven in the same test, five ways:

| Case | `$keys` | Selected |
|---|---|---|
| Selects the carrier, and only it | `Counterparty␀risk_tier␀tier-1` | `{pk1}` |
| Two admissible keys span both claims | tier-1 + tier-9 | `{pk1, pk2}` |
| Absent key is inadmissible (`GQ-08` third cut) | tier-absent | `{}` |
| The **second** value of a multi-valued claim selects it (fan-out) | `Counterparty␀region␀emea` | `{pk1}` |
| NUL separator discriminates a near-miss | tier-1**x** | `{}` |

Key shape is `f"{entity_class}\x00{attr_name}\x00{attr_value}"`. The NUL
separator is code-authored and impossible in a CCF class or attribute name, so
no artifact-authored string can forge a key boundary — and **no
artifact-authored string enters query text**, which is what keeps threat
T-15.3-03 closed on this path.

**Ladder position: rung 1** (the materialization), not rung 2 (declining the
translation whenever the policy family is present). Plan 15.3-03 inherits a
design that was measured, and plan 15.3-02's `_fluree_claim_projection` must
emit `ccf_policy_key` alongside the existing projected fields.

## F-A4 (b)-(e) — the ground buffered batch

### (b) One POST is one atomic commit: **PASS**

A body touching three distinct subjects advanced `t` by exactly one (`t: 1`);
the next commit was `t: 2`. D-01 is implementable as drawn — no escalation.

`previous_commit_id` is **absent** from the receipt (see (d)), so the
chain-linkage half of the documented assertion could not be checked from the
receipt. The `t` arithmetic carries the atomicity claim on its own.

### (c) Re-asserting an identical triple is a data no-op: **PASS, by a different observable**

`flakes_added == 0` is unobservable (the field does not exist). What *is*
observable is stronger in one respect: the content-addressed **`tx-id` of the
re-asserted body is byte identical** to the original —

```
first : fluree:tx:sha256:52d1ac5d1ff556616d4cbf7d2d9fddb5a8559065bf1930ce258f9afadf3ef08c
replay: fluree:tx:sha256:52d1ac5d1ff556616d4cbf7d2d9fddb5a8559065bf1930ce258f9afadf3ef08c
```

— and the data did not duplicate (count stayed 4; distinct ids `b0,b1,b2,bx`).
Note that **`t` DOES advance on the no-op** (`t: 3`): it counts commits, not
flakes. RDF set semantics gives the free idempotency the research predicted.

### (d) `flakes_added` counts triples: **FALSIFIED — the field does not exist**

A single claim of **known triple count k = 5** (one `@type` + four data
properties) produced this receipt, in full:

```json
{
  "ledger_id": "ccf:probe-c163426e8e3a4e3c8174ac8b6b6aef0f",
  "t": 4,
  "tx-id": "fluree:tx:sha256:b48841a1748b4eec8574b05584008eb90c1c3b61d345c9f51941dca5ddfb6534",
  "commit": {"hash": "bagaybqabciqornxkxfef5cbitey5mqyel5zop4mn7nm7m4qtjhl4e6b3f4uavvi"}
}
```

**Measured arithmetic: k = 5, `flakes_added` = ABSENT.** Also absent:
`flakes_retracted`, `previous_commit_id`, `timestamp`, `commit_id`. Adding
`opts.meta: true` adds `time`, `fuel` and `policy` — and still no flake counts.
The §R2 receipt shape (`{"t":5,"timestamp":…,"commit_id":…,"flakes_added":3,
"flakes_retracted":1,"previous_commit_id":…}`) is **not what 4.1.4 returns**.

**Why this needs no ruling.** The `_GraphTxn` contract requires
**per-operation** rowcounts (`_writer.py:333-338`) while one POST yields at
most **one aggregate** receipt, so a receipt field could only ever have
*cross-checked* the sum — never implemented the contract. Plan 15.3-02's
`_FlureeTxn.commit` therefore ships **without** the cross-check, and the
contract is satisfied exactly as `_MongoTxn` satisfies it: committed-state read
before buffering, plus the transaction's own buffer, sound under INV-CH7-10.
The plan text that anticipated writing the cross-check "against what was
measured" should be read as: what was measured is that there is nothing to
cross-check against.

### (e) Read-before-buffer is correct: **PASS**

A committed claim is visible to a plain existence read (`{"n": 1}`), and an
absent one returns `{"n": 0}`. That is precisely what lets a second
`insert_entity_claim` for the same identity resolve to `0` **before** commit
with no post-commit round trip.

## The Task 3 Ruling Gate — F-A4(a)

**The probe PASSED, its positive control closed the argument, and Dave ruled
`approved` on 2026-08-08.**

Request body, verbatim — note there is **no guard key at all**, only
`@context`, `delete` and `insert`:

```json
{
  "@context": {},
  "delete": [
    {"@id": "ccf_c_sup1", "ccf_superseded_at": "2026-03-09T00:00:00.000000Z"}
  ],
  "insert": [
    {"@id": "ccf_c_sup1", "ccf_superseded_at": "2026-03-10T00:00:00.000000Z"},
    {"@id": "ccf_c_new2", "@type": "CcfEntityClaim", "ccf_tenant_id": "tenant-sup", "ccf_claim_id": "new2"}
  ]
}
```

Response status: **200**. Receipt:

```json
{"ledger_id":"ccf:probe-985aec81b4c34d24a2a24b33e6ed1ede","t":2,"tx-id":"fluree:tx:sha256:89ec0a8ac1f1f71c52b37fd8b49e28c093d54ff5f8bff659df015c9276819c10","commit":{"hash":"bagaybqabciqe5alm4mw6elzeypf3jkvzbggqyday3t2lklxjwq3izhg34jnvmqi"}}
```

Follow-up read, verbatim:

```
{"results":[{"columns":["claim_id","superseded_at"],"data":[{"row":["new2",null],"meta":[null,null]},{"row":["sup1","2026-03-10T00:00:00.000000Z"],"meta":[null,null]}]}]}
```

**The follow-up read is the real assertion, not the 200.** An ignored `delete`
would have left `sup1` carrying *both* supersession values. It returned
**one**, carrying the **new** value, and the insert landed in the same commit.

### The positive control — closing the inferential gap

The paragraph above only follows **if** an un-retracted value would in fact
have produced two rows. F-A6 established multi-value fan-out for a property
inserted as an explicit **array**; it did **not** establish it for a property
written by two **separate inserts** on an existing subject. Those are the same
RDF semantic, but D-06's whole discipline is to measure rather than infer,
precisely because this class fails silently: **had Fluree done last-write-wins
on scalars, F-A4(a) would have returned one row whether or not the delete
applied** — passing while proving nothing.

The control runs the identical batch with the `delete` key removed against a
fresh ledger. Result — **two rows for `sup1`**, verbatim:

```
{"results":[{"columns":["claim_id","superseded_at"],"data":[
  {"row":["new2",null],"meta":[null,null]},
  {"row":["sup1","2026-03-09T00:00:00.000000Z"],"meta":[null,null]},
  {"row":["sup1","2026-03-10T00:00:00.000000Z"],"meta":[null,null]}]}]}
```

The discriminator therefore **has power**, and F-A4(a)'s single row is genuine
positive evidence of retraction rather than an artifact of scalar overwrite.

This is now a **permanent regression assertion**
(`test_fa4a_control_an_unretracted_value_survives_alongside_the_new_one`).
Without it, F-A4(a) would silently lose its discriminating power the day the
substrate changes that semantic — the exact silent-failure shape this plan
exists to catch. Both bodies are built by one
`_supersession_batch(retract=...)` constructor so the only difference between
them is the retraction; built separately they could drift and the control would
stop controlling for the right thing.

*Gap identified and first measured by the wave orchestrator before the ruling.*

### The ruling

**Dave ruled `approved` (2026-08-08).** D-02's letter holds unchanged:
`_FlureeTxn.commit` emits one ground `delete` + `insert` body with **no guard
clause**, and the **SPARQL UPDATE multi-operation departure is NOT taken**.
Plan 15.3-02 proceeds as drawn, and `_FlureeTxn`'s docstring must cite this
ruling.
