## Fixed Issues

### WR-01: A non-ASCII first path segment crashed the capture proxy instead of refusing it

**Files modified:** `examples/external/00-hello-context/fixtures/capture_proxy.py`, `tests/examples/test_ext00_hardening.py`
**Commit:** `c9b8e05`

**Confirmed before changing anything:**
`secrets.compare_digest("é", "abc")` raises
`TypeError: comparing strings with non-ASCII characters is not supported`.
Since Uvicorn and the Starlette `TestClient` percent-decode `scope["path"]`,
`POST /%C3%A9/v1/messages` presented `"é"` to `strip_secret` and produced an
unhandled 500 — an anonymous, unauthenticated caller could trigger a traceback
at will from the one function whose entire job is to refuse unauthenticated
requests cleanly.

**Applied fix:** both operands are compared as UTF-8 bytes
(`presented.encode("utf-8")` vs `secret.encode("utf-8")`). `compare_digest`
accepts `bytes` on both sides, so the comparison stays constant-time; I did
**not** add a length short-circuit, which would have leaked the secret's length
and traded one defect for a smaller one.

The docstring is corrected in the same commit. It claimed "Returns ``None`` on
any mismatch, which the handler turns into a ``403``" — which was false for
exactly this input. It now says "on **every** mismatch — including a segment
this function cannot even compare as text" and carries a paragraph naming the
`TypeError`, the percent-decoding that reaches it, and the reason the
short-circuit is omitted. Docstring-vs-code drift has been a recurring defect
across this phase's three iterations, so the prose is corrected wherever the
code under it changes.

**Regression (RED-then-GREEN confirmed).** The unauthenticated-shape loop in
`test_a_request_without_the_capture_secret_is_refused` gains two non-ASCII
shapes — the percent-encoded `/%C3%A9...` the review reproduced, and a raw
non-ASCII segment padded to the secret's own length so the refusal cannot be an
accident of shape. `_proxy_client` grew a `raise_server_exceptions` keyword and
this test drives it `False`, which is what makes a 500 observable as a status
code rather than re-raised into the test; the assertion message names the status
actually received. Verified failing against the pre-fix module and passing after.

### WR-02: The new default output directory was a predictable, pre-creatable path in shared temp

**Files modified:** `examples/external/00-hello-context/fixtures/capture_proxy.py`, `tests/examples/test_ext00_hardening.py`
**Commit:** `eecbaad`

**Applied fix:** `default_out_dir` now returns
`Path(tempfile.mkdtemp(prefix=f"ccf-ext00-capture-{stamp}-"))`. `mkdtemp`
creates the directory atomically at mode `0o700` with a random suffix, which
closes both halves of the finding at once:

1. The IN-02 name (`<tempdir>/ccf-ext00-capture-<stamp>`, second granularity)
   was fully derivable by any other local process, and the caller opened it with
   `mkdir(parents=True, exist_ok=True)` — so a hostile same-host process could
   pre-create it as a directory it owns or as a symlink elsewhere, and silently
   receive the captured vendor request and response bodies that the operator
   subsequently promotes into the git tree. That is the same hostile-same-host
   threat model the IN-01 capture secret was added to defend against, so leaving
   this half open was inconsistent with the phase's own posture.
2. Two runs starting in the same second resolved to one directory and
   `exist_ok=True` reused it, so the second run's `anthropic-00.json` overwrote
   the first's.

The timestamp is retained only as a human-readable prefix so an operator can
tell two capture runs apart at a glance, and the docstring now says explicitly
that it is *decoration, not the uniqueness mechanism* — so a future reader does
not mistake it for the guarantee.

**Every "fresh" claim was reconciled with what the code does**, which was the
reviewer's specific complaint (three places asserted freshness the code did not
provide): the module docstring's "default: a fresh timestamped scratch
directory" is now "a private scratch directory created by `tempfile.mkdtemp` —
mode `0o700`, unguessable name"; `default_out_dir`'s summary line changed from
"A fresh timestamped scratch directory" to "Create and return a private scratch
directory"; and README step 3 is rewritten (see WR-03).

**On the surviving `mkdir(parents=True, exist_ok=True)` in `build_app`.** I kept
it rather than removing or hardening it, and documented why in the docstring: it
is now a no-op for the default (already created by `mkdtemp`), so its permissive
`exist_ok` applies only to a directory the operator named explicitly as
`argv[1]`, where reusing or pre-creating the path is their own deliberate choice
rather than something a third party can predict. I deliberately did *not* add a
symlink refusal to that path — the review offered it as an either/or, and
refusing a symlink an operator chose themselves would break a legitimate use for
no security gain now that the predictable default is gone. Flagging in case you
read the trade-off the other way; it is a two-line addition.

**Regression (RED-then-GREEN confirmed).** The old test compared the default
against a year-2000 timestamp, which is why it could not see either problem.
It now asserts the directory exists, is not a symlink, is empty, is `0o700` on
POSIX, and — the assertion that actually pins the finding — that **two calls at
the same fixed timestamp are distinct directories**, since a fixed timestamp is
precisely what the old implementation made collide. Verified failing against a
reverted `default_out_dir` and passing after. The test cleans up every directory
it creates in a `finally`.

### IN-01: Capture proxy was an unauthenticated confused deputy for the operator's API key

**Files modified:** `examples/external/00-hello-context/fixtures/capture_proxy.py`, `examples/external/00-hello-context/fixtures/README.md`, `tests/examples/test_ext00_hardening.py`
**Commit:** `f1bfa03`
**Applied fix:** `main()` mints a one-time `secrets.token_urlsafe(24)` per
process and `build_app` now **requires** it as a keyword argument — there is
no construction path that yields an open proxy. Every request must present
the secret as its first path segment; a new `strip_secret()` consumes it
under `secrets.compare_digest` and the handler refuses `403` on any
mismatch **before** the route is matched, before the API key is read from
the environment, before anything is forwarded, and before an ordinal is
claimed. So the fix also preserves D-09 ordinal conservation.

**Deviation from the reviewers' suggested mechanism, and why.** Three
cross-AI reviewers proposed a shared-secret **header** printed alongside
`READY`. That does not work for this tool's actual usage: the documented
capture flow points the *vendor SDKs* at the proxy through their own
`ANTHROPIC_BASE_URL` / `GOOGLE_GEMINI_BASE_URL` variables, and neither SDK
exposes a seam for injecting an arbitrary extra header. A header-based
secret would have closed the exposure by making live capture impossible.
Putting the secret in the base URL's path prefix achieves the identical
security property — an unauthenticated local caller cannot guess it — with
zero SDK cooperation, because the SDKs append their own route to whatever
base URL they are given. `main()` prints the exact base URL to export.

New test `test_a_request_without_the_capture_secret_is_refused` drives three
unauthenticated shapes (no segment, wrong segment, bare `/`), asserts `403`
for each, asserts **nothing was forwarded upstream**, and asserts the next
authenticated capture still lands at ordinal `00`.

### IN-04: `run.py`'s D-16 reproduction silently depended on ordering inside `_mcp_probe`

**Files modified:** `examples/external/00-hello-context/serve.py`, `examples/external/00-hello-context/run.py`, `tests/examples/test_ext00_hardening.py`
**Commit:** `b67d0b6`
**Applied fix:** `serve.py` now owns
`get_context_request_label(*, tenant, entity)` and writes the
`ServeRequestRecord.request` descriptor through it. `run.py` passes that
label into `_assert_byte_equal_reproduction` and selects the record whose
`.request` equals it, instead of resolving `versions[-1]`.

This is the cross-AI suggestion ("pass the specific serve into the D-16
assertion") realized through the descriptor the deployment already writes,
rather than by plumbing a `replay_uri` back over the wire. Reason: both
serve paths append a record under the same verified `client_id`, and the
`get_replay_record` tool reads `latest[client_id]`, which is itself
overwritten by every serve — so fetching the URI over the wire would have
reproduced the same positional coupling one layer out. Selecting by the
serve's own descriptor is order-independent by construction: `_mcp_probe`
can reorder `read_resource` and `call_tool` freely and PASS 8 still
compares the record for the serve that produced the bytes. A serve with no
matching record is now a named `AssertionError` rather than a silent
comparison against the wrong record.

One shared function is deliberate: the writer (`serve.py`) and the reader
(`run.py`) cannot drift, which was the second half of the hazard.

New test `test_run_py_selects_the_d16_serve_record_by_label_not_position`
pins the label's exact form and asserts `run.py` no longer resolves
`content_address=versions[-1]`.
