<decisions>
## Implementation Decisions

### Allowlist fail-fast seam
- **D-01:** `build_experience_server` raises `ValueError` when `tool_allowlist`
  contains a name not in `EXPERIENCE_TOOLS`. Enforcement lives in the SDK builder —
  mechanism, not example glue.
- **D-02:** `serve.py` raises `ValueError` at composition time (before server start)
  when an artifact `tools.*.name` in `experience.yaml` does not equal the corresponding
  SDK tool constant, naming the offending artifact key and expected constant. No
  warn-and-continue.
- **D-03:** Fold in the provider-optionality residual: provider and description
  parameters of `build_experience_server` become optional (`None` defaults). New rule:
  a tool that IS allowlisted but lacks its provider or description raises `ValueError`
  at registration time (allowlisted ⇒ provider+description present).
- **D-04:** Backward compatible — parameters keep their names, become Optional
  keyword params with `None` defaults; existing callers passing everything are
  untouched.
- **D-05:** Test pinning: builder `ValueError` behaviors (unknown allowlist entry;
  allowlisted-without-provider) get unit tests next to existing experience.py tests;
  the artifact-name-mismatch raise gets a case in `tests/examples/`.

### Fingerprint guard strictness
- **D-06:** `replay_server.py` scans fixture pairs at startup and refuses to start
  (clear error listing unpaired fixtures) when any response fixture lacks its
  `*-request.json` sibling. Symmetric: a request fixture with no response sibling
  also fails startup.
- **D-07:** The mandatory fingerprint-mismatch test (mutated request body → loud 500
  with expected/actual) lives in `tests/examples/` alongside
  `test_ext00_fixture_schemas.py`, so `make test` collects it permanently.
- **D-08:** Include the URL path in the Gemini request fingerprint so model-in-URL
  drift is caught. The coarse fingerprint field set (same model/tools/count with
  different content passing) is documented as an intentional residual — not fixed.

### Capture-proxy semantics
- **D-09:** Non-200 or non-JSON upstream responses: pass through to the client
  unchanged, record nothing. Error bodies never consume fixture ordinals.
- **D-10:** Forward `path + query` verbatim upstream (faithful `?alt=` capture).
  When persisting request fixtures, redact key-bearing query params (`key`,
  `api_key`); headers are never persisted (existing rule, restated as spec).
- **D-11:** No fresh live capture this phase. The tightened proxy is proven by unit
  tests with a fake upstream (404 / non-JSON / query-string cases). Existing 13.2
  fixtures remain valid; no API keys or human D-10(13.1) checkpoint needed.

### CINV-01 agent tools and resource
- **D-12:** Parameterize `list_agents`/`invoke_agent` descriptions, mirroring the
  three promoted tools — no CINV-01 exemption carve-out.
- **D-13:** Fallback when agent-tool description params are `None`: SDK-level
  neutral default constants (module constants describing mechanism, not docstrings).
  Deliberate asymmetry vs the three consumption tools (which are required-when-
  allowlisted per D-03): agent tools default, consumption tools must be supplied.
- **D-14:** The MCP context-product resource description gets the same treatment:
  optional param + SDK default constant; example may override from `experience.yaml`.

### Claude's Discretion
- Exact error-message wording, redaction placeholder format, proxy test harness
  shape, wave structure, and whether `experience.yaml` gains agent-tool/resource
  description entries in the example (defaults make it optional).

</decisions>
