changes ALSO produces empty output. `test -z` returns 0 for both. A diff gate
written against an unresolvable ref therefore passes **vacuously** and is
indistinguishable from a genuine diff-empty result. Reproduced live in §4,
sabotage 3.

## 2. THE TWO-PART PRECONDITION — every later plan runs this verbatim

Neither half alone is sufficient. Run both before reading any diff:

    PB=phase-24.1-base
    git rev-parse --verify "$PB^{commit}" >/dev/null    # (a) the REF resolves
    test "$(git ls-files -- <member> | wc -l)" -gt 0    # (b) the MEMBER names tracked files

Half (a) is the new half, added by this plan. Half (b) is the `VAC-01` half
(Phase 21.1 criterion 1): a per-member diff, never a whole-tuple one that a
single mistyped key satisfies.

**Read `rev-parse`'s status DIRECTLY. Never through a pipe.** Measured both
ways against the same bad ref:

| Form | rc |
|---|---|
| `git rev-parse --verify 'phase-24.1-basx^{commit}' >/dev/null` | **128** — refuses |
| `git rev-parse --verify 'phase-24.1-basx^{commit}' \| head -1` | **0** — reports *head's* status, and passes |

## 4. THE SABOTAGES — four results, each watched

### Sabotage 1 — a real change is seen

Appended a line to a tracked file, re-read the member diff, reverted with
`git checkout -- <file>` (a single named path; no blanket reset, no `git clean`).

| Member | subject | diff during sabotage | after revert |
|---|---|---|---|
| `src` | `src/.gitkeep` | **NON-EMPTY** — `1 file changed, 2 insertions(+)` | empty |
| `src` | `src/ccf/products/gates.py` | **NON-EMPTY** — `1 file changed, 2 insertions(+)` | empty |
| `runtime` | `runtime/.gitkeep` | **NON-EMPTY** — `1 file changed, 2 insertions(+)` | empty |

`git status --porcelain | wc -l` = 0 after each revert. The `src` sabotage was
run twice — once on the placeholder file and once on a real shipped module —
because a `.gitkeep` is not representative of what criterion 16 actually guards.

### Sabotage 2 — a mistyped member is caught

The exact failure a whole-tuple diff hides:

| Mistyped member | `git ls-files` count |
|---|---|
| `src2` | **0** |
| `runtim` | **0** |
| `archive/example` (singular) | **0** |

A member naming nothing makes its diff trivially empty. Half (b) of the
precondition is what refuses it.

### Sabotage 3 — AN UNRESOLVABLE REF IS CAUGHT, and its empty output passes `test -z`

**This pair, side by side, is the point of the whole task.**

| Reading | rc | output | `test -z` |
|---|---|---|---|
| `git rev-parse --verify 'phase-24.1-basx^{commit}'` (unpiped) | **128** | — | — |
| `git diff --stat phase-24.1-basx -- src` (BAD ref) | **128** | **EMPTY**, length 0 | **PASSES** — vacuous green |
| `git diff --stat phase-24.1-base -- src` (GOOD ref) | 0 | **EMPTY**, length 0 | **PASSES** — genuine green |

The two green readings are **byte-identical**. Nothing in the output
distinguishes "no changes" from "I could not look." Only the `rev-parse`
guard separates them:

| Ref | guard |
|---|---|
| `phase-24.1-basx` | **REFUSES**, rc=128 |
| `phase-24.1-base` | PASSES |

The ref check is not ceremony. It is the only thing standing between
criterion 16 and a false green.

### Sabotage 4 — criterion 17's D and R forms can each fire

Deleted one tracked file under `archive/examples`, then renamed one, restoring
each by name.

| Probe | `--diff-filter=D` | `--diff-filter=R` | `git ls-files` count |
|---|---|---|---|
| clean | empty | empty | 265 |
| after `rm archive/examples/00-quickstart/README.md` | **FIRES** — names the file | empty | **265** |
| after `git mv README.md README-renamed-probe.md` | empty | **FIRES** — `R100 …README.md → …README-renamed-probe.md` | **265** |
| after restore | empty | empty | 265 |

**Two findings worth carrying, and neither is in the criterion's text.**

1. **The count of 265 did NOT move under either sabotage.** A working-tree
   deletion leaves `git ls-files` at 265 because the index is unchanged; a
   `git mv` leaves it at 265 because it is a rename. **The 265 figure alone
   is not a deletion detector.** The `--diff-filter=D` form is.
2. **A rename leaves `--diff-filter=D` EMPTY.** The D form alone is not a
   rename detector. The R form is.

Criterion 17 names the count, the D form and the R form. Each of the three
misses something the other two catch. This is measurement, not redundancy.

`git status --porcelain | wc -l` = 0 and `git ls-files -- archive/examples | wc -l`
= 265 after every restore.

## 5. Criteria integrity — nineteen, proven by a detector and not by a count

The ROADMAP's own preamble says why a count is not enough: *"the criterion
COUNT is not a wrap guard — a continuation line does not start with a digit,
so a real continuation-line detector is required beside the count."*

**Instrument:** a throwaway Python detector, run from the session scratchpad
and **not committed** — no new tracked file. It extracts the criteria block
from `.planning/ROADMAP.md`'s `### Phase 24.1:` section between the paragraph
ending *"…required beside the count."* and **`**Requirements:**`**, then
classifies every non-blank physical line as a CRITERION OPENER (matching
`^\s{2}[0-9]+\. `) or a CONTINUATION (anything else).

### The live reading

| Measure | Value |
|---|---|
| Opener count | **19** |
| Opener numbers | `1 … 19`, contiguous |
| Missing vs 1..19 | none |
| Repeated | none |
| **Continuation count** | **0** |
| **sha256 of the extracted block** | **`15d3ef6699bce8b860b4bfef413d36d1674d6cbe178a25955680544657c9300f`** |

Every criterion in this phase is a **single physical line**, criterion 3's
long MARKED amendment included. The sha256 was **re-derived this session**,
not copied forward from the plan; it agrees with the planning-time value.

**This sha256 is what every later plan re-checks against.** No plan in this
phase may author, edit, renumber or re-wrap a criterion line.

### The wrong bound, recorded rather than quietly corrected

Planning first bounded the block on `**Plans:**`. The order in the section is
criteria → `**Requirements:**` → `**Plans:**` → `**Depends on:**`, so that
bound swept the whole Requirements paragraph in. Re-run this session to
confirm the error is real and not a story:

| Bound | openers | continuations | sha256 |
|---|---|---|---|
| `**Requirements:**` (CORRECT) | 19 | **0** | `15d3ef66…c9300f` |
| `**Plans:**` (WRONG) | **19** | **3** — the three Requirements-paragraph lines | `a965b8cb…daa20` |

**The opener count was 19 under BOTH bounds.** The count did not detect the
bad bound; the continuation count and the sha did. At Wave 10 the wrong bound
would have tripped a false STOP the moment anyone edited the Requirements line.

### The two positive controls, both required and both watched

| Control | Expected | Observed |
|---|---|---|
| **A — criterion 7 re-wrapped** across an extra line break mid-sentence | openers STAY 19, continuations RISE by one | openers **19**, continuations **0 → 1**, the fragment named: `'ain-specific lives in definition artifacts, asserted by the No-Hardcoding lint (`CLAUDE.md'`, sha changes to `496861c2…0240e` |
| **B — criterion 12 deleted** | openers DROP to 18, gap check NAMES 12 | openers **18**, `missing vs 1..19 = [12]`, contiguity **False**, sha changes to `bf1aee1b…3ef35` |

Control A proves the detector distinguishes the two populations rather than
counting lines: a re-wrap does **not** change the opener count, so a count
alone would have reported "19, fine" on a silently re-wrapped criterion.
Control B proves a deletion is named by number, not merely counted.
