### A.5 Data traps the assembly must handle

1. **`report_period` is a spread, not one quarter.** 46 distinct periods spanning `31-DEC-2014` → `31-MAR-2026`, because one filing window carries amended filings restating historical periods. Distribution: `31-MAR-2026` **20,487**, `31-DEC-2025` **552**, `30-SEP-2025` **214**, then a long tail. **A query that does not pin `report_period` will silently mix a decade of positions into one answer.** The caller parameter surface must either fix the period or expose it.
2. **One issuer LEI fans out across many CUSIPs.** Amphenol carries **7** `(cusip, band)` groups: `032095101` strong 1,647 / weak 201, plus five other CUSIPs with 1–7 rows each including `81369Y506`, `8033009TT`, `002159795` — securities that are almost certainly *not* Amphenol, admitted by a fuzzy issuer-name match. Distribution across all 49 LEIs: 5 LEIs have 1 CUSIP, and one LEI has **52**. **Aggregating a holder's position across all CUSIPs for an LEI without a band filter will over-count.**
3. **`issuer_match_band = 'weak'` is 22.5% of rows** and is a *deliberate* imperfection — `known-issues.md` §8.15 and CLAUDE.md rule 5 in `ccf_dataprep` state that some joins are imperfect on purpose. A `weak` band is not a defect to filter away silently; it is a debt/completeness signal.
4. **There is no row timestamp.** `institutional_holder` has no `last_updated`, `observed_at` or `loaded_at` column. `s1-00`'s whole λ_c story turns on mapping a source column into `SignalEnvelope.observed_time`. The only candidate here is `to_date(report_period, 'DD-MON-YYYY')` — a **quarter-end date**, which is genuinely the instant the source's fact began to hold, so it is the bitemporally correct `valid_from`. It is also up to 90 days coarse. That is a real property of 13F, not a data defect, and the spec's §E half-life table should say so.

Estate-wide survey across the **99** `ccf_v2` tables carrying a `provenance` column:

| Value | Rows |
|---|---|
| `public` | 168,778 |
| `synthetic — engineered` | 30,365 |
| `synthetic — internal` | 13,840 |
| `derived` | 20 |
| `synthetic — engineered (person) / public (listing)` | 19 |

**Both tables `cp-00` reads are 100% `public`:** `institutional_holder` (22,476 / 22,476) and `legal_entity` (156 / 156). `ccf_v2.engineered_entity` (125 rows) is keyed on `entity_id` and carries **no `lei` column at all** — so no engineered entity can collide with an issuer LEI by construction.

**This changes criterion 9's honest wording.** Criterion 9 says *"real LEIs, invented behaviour"*. For this product that is only half right: the LEIs are real, the managers are real, the positions are real SEC filings. What a reader must be told instead is (a) the data is **one quarterly archive**, not a live feed; (b) **22.5% of issuer matches are `weak`** by design; and (c) the *estate around this table* contains synthetic and engineered data even though this product's two tables do not. Presenting it as "invented behaviour" would be inaccurate in the other direction.

### D.2 The assembler seam — and the finding that it is unused

`src/ccf/agents/assembler.py::ContextAssemblerProtocol` — four members: `assembler_id`, `assembler_version`, and keyword-only `assemble(*, request, perspective, tenant_id) -> AssemblyOutcome`.

`src/ccf/agents/assembler.py::DeterministicAssembler` — a frozen dataclass taking `agent: Agent`, `projection: ProjectionOutput`, `acquisitions: tuple[AcquiredContent, ...]`. It **does not run Π** — it holds Π's already-computed output. It returns `src/ccf/agents/assembler.py::AssemblyOutcome`, **not** a `ContextProductContract`. It raises `AssemblyRefused` on tenant mismatch or perspective-role mismatch.

**Measured: `DeterministicAssembler`, `ContextAssemblerProtocol` and `AssemblyOutcome` appear outside `src/ccf/agents/assembler.py` in exactly two places — `src/ccf/agents/__init__.py` (re-export) and `tests/agents/test_assembler.py` (20 hits). Zero hits in `examples/`, `archive/examples/`, `runtime/`.** Positive control: the same grep returned 20 lines from the test module, so the probe fires.

Consequences the planner must weigh:

- Using `DeterministicAssembler` requires an `Agent`, and `tools/lints/no_hardcoding.py`'s `cinv01c-factory-bypass` rule refuses `Agent(...)` construction outside an explicit `FACTORY_MODULE_ALLOWLIST`. So the agent must come from `AgentFactory` reading a definition artifact.
- `tests/examples/test_section_one_is_agent_free.py::DENIED_PACKAGES` bans `ccf.agents` for `s1-*` trees. `cp-*` is outside that glob today — but if the planner widens *that* glob too (it is a sibling of `SECTION_ONE_GLOB` and criterion 15 only names the spine-separation one), `DeterministicAssembler` becomes unreachable.
- **The shipped Mode 1 path (§B.2) reaches `ContextProductContract` without touching `ccf.agents` at all.**

### D.3 The gate call

`src/ccf/products/gates.py::run_gates(candidate, *, engine_resolved, now, registry, product_class, source_attestation=None) -> ServableProduct | GateRefusal`.

### D.5 What registering a new operator ACTUALLY requires today (the `D-10` question)

**A new NAME under an existing category is purely additive — zero SDK change.** Write a class conforming to `src/ccf/operators/base.py::Operator` (four members), return one of the four canonical strings from `category`, and call `OperatorRegistry.register(instance)`. Proven possible: `tests/operators/test_planner.py` defines an operator class with a caller-supplied `category`, and `tests/projection/test_acquisition.py` and `tests/conformance/test_substrate_properties.py` each define their own. Positive control: `grep "def category"` returns **2** hits in `src/` (the Protocol and the planner's composite), so the four-in-tests figure is not an artefact of a broad pattern.

**But there is a wiring caveat the planner must not miss.** `src/ccf/deployment/operators.py::build_operator_registry` — the function the `ccf_config.yaml` boot path uses — recognises **exactly four artifact types** by `isinstance` (`TraversalNeighborhoodParametersArtifact`, `TemporalAsOfParametersArtifact`, `PolicyFilterParametersArtifact`, `SimilaritySelectParametersArtifact`) and **`raise ValueError`s on anything else**: *"which names no canonical operator category; the builder does not guess which operator a deployment meant"*. So a deployment with a custom operator cannot register it through the config-driven builder. It must construct its own `OperatorRegistry()` and register directly — which is supported, open, and outside the `load_config_and_boot` convenience. **This is a real ergonomic gap and it is distinct from an algebra gap.**

**A new CATEGORY is not additive.** It requires editing `src/ccf/operators/base.py::OperatorCategory` (the `Literal`) **and** `src/ccf/operators/base.py::CATEGORY_ORDER` (which encodes INV-CH7-26's Policy-before-Similarity ordering), and it propagates through `OperatorProvenance.category`, `OperatorRegistry.register`'s refusal, `OperatorRegistry.by_category`, `src/ccf/operators/planner.py` ordering, and `src/ccf/deployment/config.py`. **Measured reach of `OperatorCategory` / `CATEGORY_ORDER`: 26 references across 5 files — `src/ccf/deployment/config.py`, `src/ccf/operators/registry.py`, `src/ccf/operators/planner.py`, `src/ccf/operators/categories.py`, `src/ccf/operators/base.py`. Zero in `runtime/`.** Positive control: the same grep for a name that cannot exist (`OperatorCategoryZZZ`) returned **0**.

That is a small blast radius in *files*, and a large one in *meaning*: `CATEGORY_ORDER` is the whitepaper §7.4 dependency order and INV-CH7-26 is stated as an invariant the fabric may never permit violating. A fifth category reopens that ordering argument. **The planner should record any category-level need as a distinct class of gap from a name-level one, exactly as `D-10` requires.**

### E.3 `Enrich` — the four-part assessment required by `D-06`/`D-08`/`D-09`

1. **The capability, stated use-case-agnostically.** *Given a set of already-resolved entity references and a declared set of attribute names, fetch those attributes from a source in a bounded number of round trips (one query per source per step, never one per entity) and attach them to the entities in the working view, recording per-attribute provenance.* The load-bearing property is the **batching contract**, not the fetching — the Standard retires the name "Batch Enrich" precisely because *"batch is mandatory, not a variant"*.
2. **Could it be a Protocol?** **Yes, and this is the natural shape.** The precedent is exact: `src/ccf/projection/acquisition.py::ContentAcquirer` is already a Protocol for *"acquire this named thing at decision time, return it with a content hash so replay can re-feed rather than re-fetch"*. An `AttributeEnricher` Protocol would be its sibling — something like `fetch(*, references: tuple[str, ...], attributes: tuple[str, ...]) -> Mapping[str, Mapping[str, str]]`, with a companion frozen `EnrichedAttributes` contract carrying a `content_hash` for replay determinism (INV-CH7-31). Other precedents for the shape: `src/ccf/operators/base.py::Operator`, `src/ccf/agents/assembler.py::ContextAssemblerProtocol`, `src/ccf/similarity/protocol.py`, `src/ccf/halflife.debt::DebtFactorScorerProtocol`.
3. **Could it be a use-case-agnostic concrete operator?** **Partly, and this is where it gets awkward.** As an `Operator` it would take declared parameters `(source_key, attribute_names, batch_size)` and return an `OperatorOutput` whose `view` carries the enriched entities. Its category would be `traversal` — which is arguably where it belongs (the Standard's own §10.1 lists Enrich under the `relational` capability class alongside Resolve, and the SDK's `traversal` category is the one that expands over the graph). So **it needs no new category**, which puts it firmly on the additive side of `D-10`. What it *does* need is a way to reach a source outside the graph from inside `Operator.apply`, whose docstring says *"Must be pure: no writes, no I/O against the graph, no clock reads."* Fetching from a foreign source at L4 is exactly the acquisition seam `ContentAcquirer` exists for — which argues for the Protocol form (2) over the operator form (3).
4. **Is it BESPOKE?** **No.** It is statable entirely without reference to any domain: references in, attribute names in, attributes out, batched, provenance-recorded. It passes `D-08` on the Protocol limb comfortably and on the use-case-agnostic limb as well.

**But `cp-00` does not need it.** The example reads ONE table. Every attribute of a holder position (`manager_name`, `value_usd`, `shares`) arrives in the same row as the position itself. There is nothing to enrich. **Under `D-06`/`D-07` this capability is therefore recorded and NOT built by 24.1.** It is a candidate for a later minor phase whose example genuinely spans a second source — `CP-SPEC-001` at 24.2 spans five systems of record and will exercise it for real.

### E.4 `Evaluate` — the four-part assessment

1. **The capability, stated use-case-agnostically.** *Deterministic computation over already-assembled state that produces values which are not graph state — measures, scores, variances, rankings — with the computation pinned by version and its inputs pinned by content address, so replay reproduces the values byte-identically.* The Standard's four modes are `aggregate · score · reconcile · rank`; its capability class is `in-memory`; and it says explicitly *"Evaluate in all modes"*.
2. **Could it be a Protocol?** **Yes — and one already exists at one remove.** `src/ccf/projection/plan.py::ProjectionPlan` is a Protocol whose `invoke` does exactly this: deterministic computation over `view` plus `operator_outputs`, returning a `ProjectionOutput.payload`. If the SDK wanted `Evaluate` *named*, the honest shape is not a new Protocol but a **documented statement that Π is where it lives**, plus (optionally) a thin `MeasureProtocol` the deployment composes *inside* its plan. Precedent for a scoped scorer Protocol: `src/ccf/halflife/debt.py::DebtFactorScorerProtocol` with `scorer_id`/`scorer_version` for replay pinning — that pair is exactly the pinning `Evaluate` would need.
3. **Could it be a use-case-agnostic concrete operator?** **No, and the reason is structural rather than a matter of taste.** `src/ccf/operators/base.py::Operator.apply` returns `OperatorOutput`, which is `view: GraphView` + `provenance`. **An operator cannot emit a number.** Making `Evaluate` an operator means either widening `OperatorOutput` to carry non-graph values — which touches the algebra, every operator, the planner's `IntermediateCache` keying and `ComposedOperator` — or writing computed measures back into the view as synthetic entities, which is a modelling hack. Either would reopen the algebra, and `D-10` says that is a different class of decision.
4. **Is it BESPOKE?** **No** in the general — "aggregate these numbers, rank these candidates" is domain-free. **But the specific evaluation a given product needs always is**: `cp-00`'s evaluation is *"keep holders whose `value_usd` exceeds the caller's number, sorted descending"*. That cannot be stated without naming this product's values. Under `D-09` **that belongs in the example's Π and its definition artifacts, not in `/src`** — which is precisely where `examples/s1-00-companies-over-revenue/deployment.py::OverThresholdProjection.invoke` puts the identical computation today.

**Recommended finding for the phase to record:** `Evaluate` is **not a gap**. The SDK's answer is Π, the answer is already exercised by a shipped example, and the deliverable is one line in the Standard→SDK mapping table saying so. Proposing an `Evaluate` operator would fail `D-08`'s second limb *and* reopen the algebra for a capability the SDK already provides.

### E.5 What `cp-00` itself actually needs — the pressure-test answer

Composing §A, §B.4 and §D: the recipe is **Resolve (L2, at ingest) → Policy (L4, optional) → Traversal mode temporal (L4, `temporal.as-of-boundary`) → contract assembly (which the Standard §10.2 says is "not an operator")**, with the threshold applied at Π. `s1-00` proves the identical shape runs on **one** operator.

**Best current estimate: `cp-00` needs ZERO new SDK operators.** That is a real result under `D-05`, and it is the outcome `D-05` predicts. The planner should scope the phase to *prove* that, not to hedge against it.
