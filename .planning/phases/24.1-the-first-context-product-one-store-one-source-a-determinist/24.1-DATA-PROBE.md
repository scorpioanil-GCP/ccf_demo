## 3. RULING — the pinned `report_period` is **`31-MAR-2026`**

Distribution, top eight of 46:

| `report_period` | rows |
|---|---|
| **`31-MAR-2026`** | **20,487** |
| `31-DEC-2025` | 552 |
| `30-SEP-2025` | 214 |
| `31-MAR-2025` | 146 |
| `30-JUN-2024` | 112 |
| `30-SEP-2024` | 111 |
| `31-MAR-2024` | 103 |
| `31-DEC-2024` | 100 |

**Why.** One filing window carries amended filings restating historical
periods, so the 46 periods span `31-DEC-2014` → `31-MAR-2026`. **A query that
does not pin `report_period` silently mixes a decade of positions into one
answer.** `31-MAR-2026` carries 20,487 of 22,476 rows — 91% — so pinning it
costs almost nothing and buys a single coherent quarter.

`report_period` parses cleanly, with the **must-match** control (not the
`is null` form, whose zero would agree with a broken instrument):

| Reading | Value |
|---|---|
| **FIGURE** rows in `31-MAR-2026` | **20,487** |
| **CONTROL** `to_date(report_period,'DD-MON-YYYY') > date '2000-01-01'` | **20,487** — equals the figure, so the instrument FIRES |
| `is not null` form | 20,487 |
| distinct parsed date | `2026-03-31` — exactly one |

This is the `from_entity_freshness` anchor `24-CONTEXT.md` `D-22` rules
legitimate. It is a quarter-end date and it is up to 90 days coarse. That is a
property of 13F, **not a data defect** — the framing that called it one is
WITHDRAWN by `24.1-RESEARCH.md`'s own correction banner.

### 6.2 THE PREMISE THAT DOES NOT HOLD — `strong` does NOT remove the off-security rows

`24.1-RESEARCH.md` §A.5 item 2 describes the off-security CUSIPs as
*"securities that are almost certainly not Amphenol, **admitted by a fuzzy
issuer-name match**."* The first half is right; **the causal half is wrong for
this anchor, and a later plan would inherit the wrong remedy from it.**

**Measured: every one of the five off-security CUSIPs is band `strong` with
`issuer_match_score = 1.0000`.** The `weak` band, for this anchor, sits
**entirely on the dominant CUSIP `032095101`** — the correct security.

So:

- **The band filter and the CUSIP fan-out are two different problems.**
  Filtering to `strong` removes 115 rows from the *right* security and leaves
  all five *wrong*-security rows in place. It is the opposite of the remedy.
- The remedy for the fan-out is **pinning the security**, not the band.

This is exactly the class `24-CONTEXT.md` `D-32` warns about: a premise read
from a document rather than re-measured. Reported here, not silently patched
into the research file.

### 6.3 A reconciliation, so nobody reads a contradiction

`24.1-RESEARCH.md` reports `032095101` as **strong 1,647 / weak 201**; this
session measures **strong 1,633 / weak 115**. Both are correct:

| Bound | strong | weak |
|---|---|---|
| ALL periods | **1,647** | **201** |
| pinned `31-MAR-2026` | **1,633** | **115** |

The research figure was unpinned. Control: the same all-period query with an
impossible `lei` → **0**. Not a discrepancy — a different bound, which is
itself the argument for §3's pin.

### 6.4 RULING — band: **NO FILTER. Both bands are served, and the band travels with the row.**

**Why.** `issuer_match_band = 'weak'` is 22.5% of the estate
(`strong` 17,410 / `weak` 5,066) and is a **deliberate** imperfection
(`ccf_dataprep/docs/known-issues.md` §8.15). It is a **completeness signal, not
a defect to filter away silently**. Filtering it costs, at threshold 0:

| Reading | managers | rows | `sum(value_usd)` |
|---|---|---|---|
| unfiltered | 1,753 | 1,763 | 113,467,355,837 |
| `strong` only | 1,638 | 1,648 | 110,694,377,404 |
| **COST of the filter** | **–115 (6.6%)** | **–115** | **–2,772,978,433 (2.4%)** |

Dropping 115 real holders to remove **zero** wrong-security rows is a bad
trade. The band is therefore carried into the product as a per-row signal, and
the spec's §C and §D must **say so**, together with the 22.5% figure.

### 6.5 RULING — CUSIP: **pin the security; do NOT aggregate across CUSIPs**

The over-count, measured:

| Reading | Value |
|---|---|
| distinct managers, all CUSIPs | 1,753 |
| raw rows, all CUSIPs | 1,763 |
| **rows minus managers** | **10** — the over-count aggregation would create |
| **CONTROL** same on the pinned CUSIP only | **0** |
| managers appearing on more than one CUSIP | **9** (control: 0 on the pinned CUSIP alone — the primary key `(lei, manager_cik, cusip, report_period)` holds) |

And the set-difference, with a **corrected** control:

| Reading | Value |
|---|---|
| managers ONLY off the dominant CUSIP | **5** |
| **CONTROL** managers ONLY on the dominant CUSIP | **1,742** |
| managers on both | 6 |

> **A control I had to throw away, recorded rather than hidden.** My first
> control for this figure was *"the same query with `cusip <> 'ZZZZZZZZZ'`"* —
> which returned **5**, the same number as the figure. That is not a passing
> control; it is a **tautological** one (any manager not on the dominant CUSIP
> is by definition on some other CUSIP), and by this project's own rule a
> control that agrees with the figure is not a control. Replaced with the
> reciprocal set difference above, which returns **1,742** — a different
> number, so the instrument is shown to work in both directions.

**Note for later plans:** pinning a literal CUSIP into an artifact works but
teaches little. The better shape — *resolve the anchor's security as the
dominant `(lei, period)` CUSIP* — is an **L2 resolution step**, which is
precisely the `Resolve` name criterion 11's operator-mapping hypothesis needs
to place at a layer. **That is a Wave-2+ design choice, flagged here, not made
here.**

## 7. RULING — the CCF graph is a **per-run SQLite file**, and `parkavedb` is a READ-ONLY SOURCE

`24.1-RESEARCH.md` UNKNOWN-2 and UNKNOWN-3 are open and no locked decision
covers them. `examples/s1-00-companies-over-revenue` mints a **per-run schema
inside the same Postgres it reads**, and the `parkave` role has `CREATE` on the
database and `INSERT` on `ccf_v2.institutional_holder` — so copying `s1-00`
literally would write into Dave's data estate on every run.

**RULED for this phase: the CCF graph lives in a per-run SQLite file under the
run root. `parkavedb` is a read-only source and nothing this phase runs writes
to it.** This is the mitigation for `T-24.1-02`.

Confirmed mechanically, in the venv with `PYTHONPATH=src:runtime`:

| Reading | Value |
|---|---|
| `ccf.graph.registry::declared_names()` | `['demo', 'fluree', 'memory', 'mongo', 'neo4j', 'postgres', 'sqlite']` — **7** |
| **FIGURE** `'sqlite'` in that set | **True** |
| **CONTROL** `'no_such_backend'` in that set | **False**, against a set of size 7 — the membership test is not answering True for everything |

`ccf.graph.backends.sqlite_write::SqliteConnection` — **the whole connection
surface a deployment must compose**:

| Field | Type | Required |
|---|---|---|
| `database_path` | `pathlib.Path` | **yes** |

One field, and nothing else: it derives from
`ccf.contracts.base::CCFContract`, which supplies `extra="forbid"`, so a
settings key the adapter does not declare is **refused** rather than ignored,
and a manifest omitting the path is refused with no fallback. Contrast the
Postgres path, whose `backends.yaml` composition in `s1-00` needs a
`from_env` DSN plus a `per_run: identifier` schema minter.

**The pedagogy this ruling buys for free.** The graph and the system of record
become **visibly two different substrates** — SQLite graph, Postgres source —
which is the honest shape of a Context Product and which `s1-00`, reading and
writing the same Postgres, cannot show.

1. **The connection role is not read-only** (`UNKNOWN-3`).
   `has_table_privilege(current_user, 'ccf_v2.institutional_holder', 'INSERT')`
   is **True**. §7's ruling means nothing this phase runs uses it, and §1 shows
   the session is opened `transaction_read_only = on` — but **whether a
   genuinely read-only role should exist for the example is Dave's call**, not
   a thing this phase can decide.
2. **How the credential reaches the example** (`UNKNOWN-4`). There is no
   provisioner for `cp-00`, so the DSN must come from the operator's
   environment. Hard constraint either way: **no connection value, host or
   credential enters the tree.**
