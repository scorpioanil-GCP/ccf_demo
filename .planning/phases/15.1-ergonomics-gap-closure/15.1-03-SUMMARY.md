# Phase 15.1 Plan 03: The `ccf.` Namespace Reservation Summary

The `ccf.` prefix is now the SDK's, reserved at the one function that resolves a manifest's
class string; the six author-versioned classes resolve to their real contracts instead of an
open envelope; and declaring the wrong registration path for a class whose contract fixes the
answer is refused in preflight, before any document is read.

## What Was Built

**The versioned-registerable mapping and the reservation (Task 1, `e5bc519`).**
`SDK_VERSIONED_ARTIFACT_CLASSES` holds exactly the six SDK-owned classes whose contracts
declare a string `artifact_version` — `ccf.agent-definition`, `ccf.prompt-artifact`,
`ccf.task-definition`, `ccf.workflow-definition`, `ccf.skill-catalog-entry`,
`ccf.skill-grant`. It is a **second** mapping, not an addition to `SDK_ARTIFACT_CLASSES`,
and the `#:` comment states the split in one sentence: the first means
*typed-registerable*, this one means *versioned-registerable*, and the two are disjoint by
construction because a contract either declares an `artifact_version` or it does not.

`refuse_registration_the_sdk_fixes(class_id, registration)` copies
`refuse_role_the_sdk_fixes` line for line in shape — a `ValueError` that refuses and never
corrects, both messages under 200 characters and both naming D-IMPL-85. A class in neither
mapping is not checked at all; the adopter's declaration stands, which is the default.

`resolve_artifact_class` consults `SDK_ARTIFACT_CLASSES`, then
`SDK_VERSIONED_ARTIFACT_CLASSES`, then refuses envelope resolution for any `ccf.`-prefixed
id in neither. The docstring paragraph that said refusing an unknown id "would be the SDK
claiming ownership of a namespace that is not its own" is rewritten: the SDK claims exactly
one prefix and nothing else, and the rejected four-id alternative is recorded with its
arithmetic — the squat was verified reachable for `ccf.hitl-policy`, `ccf.skill-grant` and a
wholly invented `ccf.made-up-class`, so a four-id list closes about a third of the hole.

The import-cycle check the plan required was run for all four source modules before
committing: `ccf.deployment.classes` importing `ccf.workflow.definitions`,
`ccf.agents.definitions`, `ccf.skills.catalog` and `ccf.skills.grants` creates no cycle, and
none of those packages imports `ccf.deployment` in either direction (`grep` returned empty).

**The preflight wiring and two stale documents (Task 2, `ce2f907`).**
`refuse_registration_the_sdk_fixes` is called in `load_and_boot`'s existing preflight loop on
the line after `refuse_role_the_sdk_fixes` — line 312, with `_preflight_backend` at 313, so
it runs before any document is read and before anything is registered. The `Raises:` section
names D-IMPL-84 and D-IMPL-85 and says what each refuses.

`examples/05-workflow-hitl/artifacts/manifest.yaml` documented the `ccf.hitl-policy` /
`ccf.scope-mapping` envelope hazard as something an adopter had to know to avoid. It now
teaches the mechanism instead: the `ccf.` prefix is reserved (D-IMPL-84), a manifest entry
naming a `ccf.`-prefixed class the SDK does not ship is refused at load, and **what the
reservation buys** — a class id in a manifest now means what it says, so
`registry.artifact_class_of(key)` is evidence rather than an unverified claim. The four
author-versioned documents are now recorded as outside the manifest **by this example's own
choice** (the four `register_versioned` calls are the lesson) rather than by necessity, which
is the honest statement after this plan.

The HTTP `/schema` route's served set is **unchanged**. Its docstring now states the contract
precisely — it serves the classes a manifest may name for **typed** registration, which is no
longer the same thing as "every SDK-owned class a manifest may name" — and the residual is
recorded in a new phase `deferred-items.md` naming all six author-versioned class ids, in
Phase 15's own found-during / what / why-not-fixed-here / where-it-belongs format.

**Six tests, all watched (Task 3, `9bd7e2d`, `86442c4`).** Five in `test_manifest.py` (seven
collected members, the reservation case being parametrized over three ids) and the
both-directions matrix in `test_class_lookup.py`, plus four companion assertions: the
computed author-versioned membership check in both directions, disjointness with
SDK-before-envelope ordering for the new mapping, the reservation asserted at
`resolve_artifact_class` itself, and the one-prefix-wide check that an implementation
refusing *every* unrecognized id would fail.

### Corrections to the Plan's Own Statements

**The `ccf.skill-grant` row is refused by D-IMPL-85, not D-IMPL-84.** The plan's test 3
parametrizes `ccf.hitl-policy`, `ccf.skill-grant` and `ccf.made-up-class` and says "assert
each is refused". All three *are* refused, but not by the same mechanism, and the difference
is a consequence of this plan's own Task 1 rather than a research error: `ccf.skill-grant` is
author-versioned, so it is now **in** `SDK_VERSIONED_ARTIFACT_CLASSES`, and a manifest entry
declaring `registration: typed` for it is refused by `refuse_registration_the_sdk_fixes`
(D-IMPL-85) one stop before `resolve_artifact_class`'s reservation (D-IMPL-84) is reached.
The parametrized case therefore carries `(class_id, decision_id)` and asserts the right
decision id per row, with a comment saying why the two mechanisms differ — writing all three
as D-IMPL-84 would have been a test asserting a mechanism that does not run.

**`resolve_artifact_class` is classified `Public surface: true`, not `false`.** The plan
specifies `Public surface: false` on the reasoning that the name and signature are unchanged.
`docs/surface-changes/README.md` defines the `behavior` + `Public surface: true` pair for
exactly this case — "an exported Python name whose observable behavior changed" — with
`load_artifact` (D-02) as the worked precedent, and unchanged-signature is the *defining
condition* of that class rather than a reason to mark it non-public.
`resolve_artifact_class` is in two `__all__`s and now raises where it used to return. Both
classifications pass the gate (the name is absent from the diff either way, so assertion 3
exempts `behavior` and assertion 4 never sees it); `true` is the one the convention names.

**Example 04's manifest filenames.** Not encountered in this plan — no file under
`examples/04-cross-process/` was touched — but the phase-level correction stands:
the files are `consumer-manifest.yaml` and `producer-manifest.yaml`.
