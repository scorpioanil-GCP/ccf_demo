## Critical Issues

### CR-01: `_binding_before` is still strictly-below and line-granular, so nine of the eleven certified spellings are admitted when the suite is on the statement's own line — CR-01's own inversion, one layer down

**File:** `tests/products/test_gate_two_call_shape.py:781-815` (`_binding_before`,
whose `:786-791` states the opposite of what it does), `:811`
(`if binding.lineno < line:`), `:65-74` and `:165-214` (the module docstring's
claim and its limits list, which does not name this), `:2086-2168`
(`test_a_plan_local_rebound_by_any_binding_form_is_seen`, whose name is the
claim); `15.1-16-SUMMARY.md:173-189` (the REJECT ledger) and `:488` (threat row
"mitigated"); `15.1-14-SUMMARY.md:436-437` (rows re-dispositioned to "closed in
15.1-16").

**Issue.** `_binding_records` now records a binding for every form. But
`_binding_before` puts a non-comprehension binding in force only for
`binding.lineno < line`. A compound statement's binding is recorded at the
**statement's** line, and a suite written on that same line is therefore read at
a line the binding is *not* in force at — so the **previous** binding answers, and
the checks report on an object the name no longer holds. That is not a
narrowing; it is the same inversion `_binding_records`'s own docstring
(`:635-649`) is written about.

Measured, driving the shipped `_binder_collapses` over probe bodies whose first
three lines are the compliant shape (`plan = FixturePlan(plan_id=pid,
required=requirements.required_operator_keys)`, `refuse_operator_set_divergence(
declared=declared, plan=plan)`):

```
spelling                one-line suite      multi-line (control, module's own test)
for target              **ADMIT**           REJECT
async for target        **ADMIT**           REJECT
with as                 **ADMIT**           REJECT
async with as           **ADMIT**           REJECT
except as               **ADMIT**           REJECT
match capture           **ADMIT**           REJECT
semicolon assign        **ADMIT**           REJECT
semicolon tuple         **ADMIT**           REJECT
semicolon import        **ADMIT**           REJECT
```

**Consequence (a) — the CR-03 shape runs silently, with the module having
recorded the evidence and then discarded it.** Concrete triggering input, driven
through the shipped helpers:

```python
def serve(pid, r, declared, requirements, alts):
    plan = FixturePlan(plan_id=pid, required=requirements.required_operator_keys)
    refuse_operator_set_divergence(declared=declared, plan=plan)
    plan = FixturePlan(plan_id=pid, required=declared.required_operator_keys); out = ProjectionEngine(reader=r).execute(plan=plan)
    return out
```

```
bindings for plan  : (_Binding(2, None), _Binding(4, None))
plan sources       : {('plan@4',): ('declared','required_operator_keys'),
                      ('plan@2',): ('requirements','required_operator_keys')}
binder calls       : [(3, ('declared',), ('plan@2',))]
executions         : [(4, ('plan@2',))]
unreadable calls   : []
binder problems    : 0
gate problems      : 0
names_binder       : True
```

The line-4 construction is CR-03 variant 1 (built from the binder's own
`declared=`) **and** variant 2 (handed to no binder) at once. `_plan_sources`
*recorded* it as `plan@4 → declared.required_operator_keys`. The execution then
resolves to `plan@2` because the line-4 binding is not "before" line 4, so
`call.handed == execution.plan` matches, property (2) reports "the plan bound is
the plan run", property (1) never sees the second construction, property (3) is
satisfied, the per-call readable assertion is green, coverage is green. **Every
assertion in the module passes.**

The same holds with the loop spelling, which needs no semicolon and is ordinary
Python:

```python
    for plan in alts: out = ProjectionEngine(reader=r).execute(plan=plan)
```
```
executions : [(4, ('plan@2',))]   problems: 0   -> SILENT
```
The engine runs every plan in `alts`; the binder saw none of them.
`with cm as plan: out = …`, `except ValueError as plan: out = …` and
`case [plan]: out = …` measure identically.

**Consequence (b) — tripwire (1) red on correct code, again.** WR-F2(a)'s
charter, in the one-line spelling:

```python
def serve(execution, candidate, declared, batches):
    ops = frozenset(declared.required_operator_keys)
    product = ProductLineage(operators_invoked=ops)
    for ops in batches: out = run_gates(candidate, engine_resolved=ops)
    return out
```
```
gate problems: 1 — "…both read `declared.required_operator_keys`"  -> RED
```
`ops` inside the loop body is an element of `batches` and has nothing to do with
line 2. The `with cm as ops:` one-liner measures identically.

**Why this is Critical rather than a residual.** Three things, each measured:

1. The module's *stated* behaviour is the opposite. `_binding_before:789-790`
   says the line-granularity cost is that such statements "resolve
   conservatively — none of them is 'before' the others — **which under-resolves
   rather than mis-resolves**". It does not under-resolve. It resolves to the
   **previous** binding, affirmatively, which is precisely mis-resolution, and
   precisely the failure mode `_binding_records:635-649` says the round exists to
   remove. The sentence's mitigating clause ("no file in the scanned trees is
   written that way") is true today and is not a mechanism.
2. The limits lists do not name it. `:165-214` ("What tripwire (2) still cannot
   see — Named rather than implied away") enumerates five residuals; a compound
   statement's suite on its own line is not among them. Neither is it in
   `:76-122`.
3. The record now says it is closed. `15.1-14-SUMMARY.md:436-437` were
   re-dispositioned this round from `mitigated` to "partially mitigated at the
   time of writing; **closed in 15.1-16**", listing `for` / `with … as` /
   `except … as` / `match` capture by name; `15.1-16-SUMMARY.md:488` records the
   threat as `mitigated`; the test is named
   `test_a_plan_local_rebound_by_any_binding_form_is_seen`. A reader auditing
   this at the gate is told the escape is gone.

Note what is *not* claimed here: the behaviour of these spellings is **unchanged
from the predecessor** (I ran the same bodies against `6cf00d3` — all silent
there too). What changed is that the round certifies them closed. The defect is
the same one this phase has been failing on for three rounds: a check narrower
than its own docstring.

**Fix — measured before proposing, and measured tree-wide.** Make a compound
statement's binding in force from its own line **inclusive**, which is what
Python does (the suite executes after the target is bound). Concretely: have
`_binding_records` mark bindings produced by `ast.For`, `ast.AsyncFor`,
`ast.With`, `ast.AsyncWith`, `ast.ExceptHandler`, `ast.MatchAs`, `ast.MatchStar`
and `ast.MatchMapping` as inclusive-from-their-own-line (an unbounded `until`
reuses the existing `<=` branch and needs no new field; every such binding is
already `path=None`, so `_resolve_at`'s termination argument is unaffected).

Applied as a monkeypatch and measured:

```
for / async for / with / async with / except / match, ONE-LINE suite : REJECT (was ADMIT)
the same, multi-line (the module's own probes)                        : REJECT (unchanged)
a read AFTER a for-loop rebinding                                     : REJECT (unchanged)
a for that rebinds a different name, then a legal rebind+bind         : ADMIT  (unchanged)
"comprehension does not leak" probe                                   : ADMIT  (unchanged)

tree, patched: projecting bodies 11, tripwire (2) problems 0,
               unreadable binder calls 0, tripwire (1) problems 0
all 19 test functions in the module, driven under the patch           : 0 failures
```

**One cost I measured and am stating rather than omitting**, as this round did
for `ast.withitem`: under the patch a read of the *old* value **inside the
compound statement's own header** (`with make(plan) as plan:`,
`for plan in transform(plan):`) resolves to the new binding instead of the old.
Today's strict `<` gets that case right. I did not find a body where that
mis-resolution changes a verdict — in the `with make(plan) as plan:` probe the
patched answer is REJECT and REJECT is the correct answer anyway, because the
`with`-bound plan is unbound — but I did not enumerate the case exhaustively and
I am not claiming I did. The semicolon spellings are **not** closed by this
patch; they need `(lineno, col_offset)` ordering, which I did not measure.
Whatever is chosen, `_binding_before:789-790`'s "under-resolves rather than
mis-resolves" must be corrected to what it does, and the surviving spellings
added to the limits list.

## Warnings

### WR-01: `_Binding.until` is a **line range**, not the comprehension's lexical scope, so a correct body that reads the shadowed name on a line the comprehension spans is now red — a regression against `6cf00d3`

**File:** `tests/products/test_gate_two_call_shape.py:729-733`
(`until = getattr(node, "end_lineno", None) or line`), `:793-799`
(`_binding_before`, which claims the range is "precisely the scope Python gives
it"), `:611-628` (`_Binding.until`'s docstring), `:2148-2168` (the "comprehension
does not leak" quiet-probe, which only covers the whole-line spelling);
`15.1-16-SUMMARY.md:490` (threat row "A comprehension target leaking past its
comprehension (red on correct code) | mitigated").

**Issue.** Python scopes a comprehension target **lexically**, to the
comprehension expression. `until` approximates that with the comprehension's
first and last **line numbers**, and `_binding_before:813` puts the binding in
force for every read on those lines. When any other expression shares one of
those lines, its read of the same name is attributed to the comprehension's
target.

Concrete triggering input, correct Python, driven through the shipped helpers:

```python
def serve(pid, r, declared, requirements, alts):
    plan = FixturePlan(plan_id=pid, required=requirements.required_operator_keys)
    refuse_operator_set_divergence(declared=declared, plan=plan)
    return ([str(plan) for plan in alts], ProjectionEngine(reader=r).execute(plan=plan))
```
```
bindings for plan : (_Binding(2, None), _Binding(4, None, until=4))
executions        : [(4, ('plan@4',))]
binder problems   : 1
  "probe.py:4: `ProjectionEngine.execute` runs `plan@4`, which no
   `refuse_operator_set_divergence` call in this body was handed beforehand."
```

The `plan` in the `execute` is the **outer** one — the comprehension target does
not leak — so the body is correct and the binder did see the object the engine
runs. **The predecessor at `6cf00d3` returns 0 problems on this body.** This is a
regression introduced by this round.

It is not confined to one-liners. Any outer read landing on a line the
comprehension spans triggers it:

```python
    return combine([x
        for plan in alts], ProjectionEngine(reader=r).execute(plan=plan))
```
```
executions: [(5, ('plan@4',))]   binder problems: 1   (predecessor: 0)
```
A generator expression measures identically. The tripwire-(1) direction is the
mirror image: a comprehension binding `ops` on the gate call's own line makes a
genuine collapse resolve to the comprehension's opaque token and go quiet
(measured: `gate problems: 0` on a body whose two sides are the same value).

`_binding_before:798-799` states the range is "precisely the scope Python gives
it". It is not; it is exact only when the comprehension owns whole lines. The
threat row records the leak as mitigated without that qualification.

**Fix.** State the approximation, or make the containment lexical. The honest
minimum is one sentence in `_binding_before` and one row in the limits list: the
scope is the comprehension's **line span**, which over-covers when another
expression shares its first or last line, and the cost in that case is a false
positive (property (2)) and a false negative (tripwire (1)). The structural fix
is to bind on lexical containment — mark the nodes inside each comprehension and
consult that, rather than a line range — which means threading the reading node
(or `col_offset`) into `_resolve_at`; **I did not measure that change** and am
not claiming it is free.

### WR-02: a walrus around an inline plan construction routes past property (2)'s hoist branch — the shape the round's own ledger lists as REJECTED

**File:** `tests/products/test_gate_two_call_shape.py:1528-1546` (the inline
branch), `:457-509` (`_path`, which returns `None` for a `NamedExpr` wrapping a
call), `:175-178` (the limits list's "A plan expression with no identifier
path"); `15.1-16-SUMMARY.md:184` ("a plan constructed inline as `execute`'s
`plan=` argument | **REJECTED**").

**Issue.** Property (2)'s hoist branch fires on
`_is_plan_construction(execution.plan_node)`. Wrapping the construction in a
walrus makes `plan_node` an `ast.NamedExpr`, which is not an `ast.Call`, so the
branch does not fire; `_binding_path` then yields `None` for the same node and
the execution takes the `execution.plan is None: continue` exit. Measured:

```python
def serve(pid, r, declared, requirements):
    plan = FixturePlan(plan_id=pid, required=requirements.required_operator_keys)
    refuse_operator_set_divergence(declared=declared, plan=plan)
    return ProjectionEngine(reader=r).execute(plan=(plan := FixturePlan(plan_id=pid, required=declared.required_operator_keys)))
```
```
plan sources    : {('plan@4',): ('declared','required_operator_keys'), ('plan@2',): (...)}
executions      : [(4, None)]
binder problems : 0    -> SILENT
```
without the walrus the identical body is **REJECTED** with the hoist message.
The module recorded the source (`plan@4 → declared.required_operator_keys`) and
then said nothing, so this is not the "no identifier path" limit the docstring
claims: the path exists and the module holds it.

This is pre-existing (the predecessor is silent too), but the round's ledger
re-asserts the shape as rejected without the qualification.

**Fix.** In `_handed_plan_source`, `_executions` and `_binder_calls`, unwrap
`ast.NamedExpr` before asking `_is_plan_construction` — or resolve a `NamedExpr`
plan argument to `_opaque(target.id, node.lineno)`, which is the token
`_plan_sources` already keyed it under and would make the execution resolve to
`plan@4` and be reported unbound. **I did not apply or measure either**; I am
reporting the defect, not certifying the remedy.

### WR-03: the binding model is textual, so a rebinding that executes *before* it textually — a loop-carried one — is invisible, and the limits list does not name it

**File:** `tests/products/test_gate_two_call_shape.py:818-855` (`_resolve_at`,
whose docstring argues termination from the walk "strictly ascending the body"),
`:165-214` (the limits list).

**Issue.** `_binding_before` answers "which binding is textually last above this
line", which is the right answer only for straight-line code. A loop makes lines
execute out of textual order. Measured:

```python
def serve(pid, r, declared, requirements, alts):
    plan = FixturePlan(plan_id=pid, required=requirements.required_operator_keys)
    refuse_operator_set_divergence(declared=declared, plan=plan)
    for item in alts:
        out = ProjectionEngine(reader=r).execute(plan=plan)
        plan = FixturePlan(plan_id=pid, required=declared.required_operator_keys)
    return out
```
```
binder problems: 0   -> SILENT
```
On the second and every later iteration the engine runs the line-6 plan, which is
built from the binder's own `declared=` and which no binder was handed. The
`while` spelling measures identically. This is a pre-existing property of the
line-aware model 15.1-14 introduced; it is not in either limits list, which
between them name reachability, unreadable plan expressions, unreadable
`required=`, `**kwargs`, body boundaries, unrecognised plan classes, attribute
and subscript targets, `global`/`nonlocal`, `del` and augmented assignment.

**Fix.** This is genuinely out of a line-ordered AST walk's reach — closing it
needs control-flow, not lexical, ordering. The correct action is to **name it**,
beside reachability, in `:165-214`: a rebinding inside a loop body that is
textually below a read in the same loop body is in force on every iteration after
the first, and this module reads it as never in force. One sentence, in the same
register as the reachability paragraph.

### IN-01: `_scopes` does not enumerate class bodies or lambdas, contra its own docstring, so a plan constructed there is invisible to both halves of tripwire (2)

**File:** `tests/products/test_gate_two_call_shape.py:423-429`

`:403-420` (`_scope_nodes`, which stops descending at `ClassDef` and `Lambda`),

`_scopes` collects the module and functions only, while `_scope_nodes` refuses to
descend into either — so a plan construction in a class body belongs to no
scanned scope at all. Measured:


Not "scanned and unresolvable" — **not scanned**. No coverage assertion, no
argument check, and the `MINIMUM_PROJECTING_BODIES` floor cannot see it because
the body never enters the count. Pre-existing and, in an example driver, unlikely
to the point of being theoretical, which is why this is Info rather than a
Warning; but the docstring at `:424` says the enumeration is complete and it is
not. One clause there, or a `ClassDef` arm in `_scopes`, closes the claim.
