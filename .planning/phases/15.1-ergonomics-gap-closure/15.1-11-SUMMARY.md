# Phase 15.1 Plan 11: Manifest Path Containment (CR-01) Summary

`load_and_boot`'s docstring has promised since Phase 15 that every manifest entry's `path`
resolves relative to the manifest's own directory; nothing enforced it, so `path: /etc/passwd`
read `/etc/passwd`. The promise is now enforced by two checks — a syntactic refusal at the
typed contract and a resolved-root containment check at the read — and the symlink escape a
purely lexical fix would have left open is closed.

## What Was Built

**The contract half (`artifacts.py`).** `ManifestEntry` gains a second `path` validator,
`_path_stays_beside_the_manifest`, sitting beside the existing glob refusal rather than
inside it — one validator per rule, so each refusal message says one thing. It refuses an
absolute path, a rooted or drive-qualified path, and any `..` segment. The predicate,
`_leaves_its_own_directory`, asks **both** `PurePosixPath` and `PureWindowsPath` and refuses
if either reads the value as leaving: the two flavours disagree about what *absolute* means
(`/etc/passwd` is absolute to one and merely rooted to the other; `C:\secrets` is the
reverse; `..\..\x.yaml` is one filename to POSIX and two parent segments to Windows), and a
content-hashed governance document must not be admissible on one machine and refused on
another.

**The read half (`manifest.py`).** `_document_inside_the_deployment(root, entry)` resolves
each entry against the manifest's own directory — both sides `resolve()`d, which normalizes
*and* follows symlinks — and raises `ValueError` for anything landing outside. It runs in
the **existing preflight loop**, on the line after `refuse_registration_the_sdk_fixes`, so an
entry that escapes is refused before **any** document is opened; the resolved paths are
carried forward in a `dict[str, Path]` keyed by `entry.key` (unique by the manifest's own
`_keys_are_unique` validator), and phase one reads from that mapping rather than re-joining
the path. Removing the old `root = manifest_file.parent` line from phase one and hoisting it
above preflight is the only structural change to the function; the two-phase parse-then-
register shape, the signature, the return type and the pin set are untouched.

**Documentation that matches the code.** `load_and_boot`'s `manifest_path` `Args:` entry now
says the containment clause is *enforced* and by which two mechanisms; its numbered
"what this call does, in order" list names the new preflight step; its `Raises:` names the
new `ValueError`. The module docstring's "Why the manifest enumerates" section gains the one
step further: a path that *leaves* the directory is strictly worse than a glob, because the
dropped-in file does not even have to be dropped in.

**The surface fragment.** `docs/surface-changes/15.1-11-manifest-path-containment.md`, four
entries — `ccf.controlplane.artifacts.ManifestEntry`, `ccf.deployment.ManifestEntry`,
`ccf.deployment.manifest.load_and_boot`, `ccf.deployment.load_and_boot` — all
`Public surface: true` / `Change type: behavior`, because `tools/dump_surface.py --report`
shows an empty diff (no name added, no signature reshaped) while a manifest that booted
before is refused after. Both the defining module and the package re-export get a section,
since the phase-close cross-check matches at fully-qualified-name granularity.

## Where the Check Lives, and Why It Is in Two Places

This was the plan's substantive design question, and the answer is *both* — argued, and then
measured rather than left as an argument.

**A `field_validator` alone is insufficient and it is not close.** The validator sees only
the string. `linked.yaml` is a plain relative name on every reading of it; what leaves the
deployment is the link, and no string inspection can see a symlink. Measured: with the
contract check committed and the read-site check reverted, the symlink test failed
`DID NOT RAISE ValueError` and a standalone probe confirmed the boot **succeeded** and
handed the outside document back on `BootedFabric.artifacts`.

**A read-site check alone is also insufficient**, for a different reason. Containment at the
read protects exactly one caller. `ManifestEntry` and `DeploymentManifest` are public,
exported from two module paths each, and an adopter can construct or parse one without ever
calling `load_and_boot` — validating it, passing it around, storing it. *Is this a
well-formed declaration?* is decidable from the string, and CLAUDE.md §11 puts validation at
the boundary, never deferred. Measured: with the read-site check committed and the contract
check reverted, all four lexical tests failed, because they assert an `ArtifactLoadError` at
parse with a declaration-specific message, and the read-site check produces a different
error at a different time.

**So the two are not one check written twice; they answer different questions.** The contract
answers *is this a well-formed declaration*, from the string, before any I/O, for every
consumer. The read answers *does this actually open a file inside the deployment*, against a
root only the caller knows. Deleting either leaves a real hole, and the test suite fails
differently for each deletion — which is the property that keeps a future "simplification"
from collapsing them.

**Symlinks: closed, and the decision is pinned by a positive control.** `resolve()` follows
links, so a syntactically-contained name pointing outside is refused. The alternative —
refusing every symlink — is a different and wrong rule, so
`test_a_symlink_inside_the_deployment_is_admitted` asserts that a link whose target is inside
the deployment still boots. Without that test, an implementation that banned links outright
would pass everything else.

**Refuse, never sanitize.** Nothing is rewritten, re-anchored, or normalized into range. The
posture is `refuse_registration_the_sdk_fixes`'s and `refuse_operator_set_divergence`'s: a
governance mechanism that silently repairs leaves the manifest saying one thing and the
deployment doing another, and the manifest is the document the audit plane reads back. An
adopter who genuinely needs a document from elsewhere copies it in, where it is versioned
with the rest of the artifact set.

**The refusal must not become the disclosure path it closes.** The read-site message names
the manifest key, the declared path and the *resolved* path — a refusal an operator cannot
locate is one they will route around — and never the file's contents. Every refusal test
asserts `OUTSIDE_MARKER not in message`.


The failure reason for all five is `Failed: DID NOT RAISE` — the refusal is **absent**, not
firing differently. The two passes are the positive controls (subdirectory path, symlink
resolving inside), which are expected to pass on both sides.

`DID NOT RAISE` says the refusal is missing; it does not say what the code did instead. A
standalone probe against the same reverted source recorded that:

```
absolute    BOOT SUCCEEDED -> artifacts[half-life].entries = ['outside-the-deployment-marker']
parent      BOOT SUCCEEDED -> artifacts[half-life].entries = ['outside-the-deployment-marker']
normalized  BOOT SUCCEEDED -> artifacts[half-life].entries = ['outside-the-deployment-marker']
symlink     BOOT SUCCEEDED -> artifacts[half-life].entries = ['outside-the-deployment-marker']
```

All four escape shapes booted a full fabric and handed a file from outside the deployment
back to the caller — the reviewer's finding, reproduced four ways.

**One test was corrected by this measurement.** The first probe run showed
`normalized` failing with `FileNotFoundError`, because `open` walks the literal path and
`deployment/nested/` did not exist. That would have made the test pass pre-fix for a reason
having nothing to do with containment. The test now creates the intermediate directory, with
a comment saying why, and the probe then showed the leak. A test whose pre-fix failure mode
is incidental is not evidence, and this one was one line away from being exactly that.
