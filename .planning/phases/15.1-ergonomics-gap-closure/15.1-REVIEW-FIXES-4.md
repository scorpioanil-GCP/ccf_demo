## Warnings

### WR-01: `_Binding.until` covers the comprehension's **outermost iterable**, which Python evaluates in the enclosing scope — so the fix's own docstring claim, "containment in it is exactly Python's scope rule," is false in both directions

**File:** `tests/products/test_gate_two_call_shape.py:962-967`
(`_binding_records`'s comprehension branch, `until = _after(node)`), `:820-830`
(`_Binding.until`, whose `:823-824` states the claim), `:1042-1052`
(`_binding_before`, "in force for reads **lexically inside** the comprehension …
and for no other read"), `:85-88` (module docstring), `:164-170` (the limits
bullet, which names the *evaluation-order* divergence and not this one);
`15.1-17-SUMMARY.md:204-205` ("which is the scope Python gives it") and `:401`
(threat row `mitigated`).

**Issue.** Python's comprehension scope **excludes the outermost iterable** — it
is evaluated in the enclosing scope and passed in as an argument. Proved by
running Python, not asserted:

```python
def demo():
    plan = "OUTER"
    seen = []
    def transform(x):
        seen.append(x); return ["A", "B"]
    result = [0 for plan in transform(plan)]
    return seen, plan
# -> (['OUTER'], 'OUTER', [0, 0])   the iterable read the ENCLOSING plan
```

`until` is `_after(node)` over the whole comprehension node, and `_at(node)` is
its `[`. The outermost iterable sits inside that span, so `_binding_before`'s
`position <= read < until` branch attributes its reads to the comprehension's own
target. Measured on the resolver:

```
def f(plan, transform, g):
    plan = mk()
    b = [g(x) for plan in transform(plan)]

bindings['plan'] = (_Binding((3,15), None), _Binding((4,8), None, until=(4,42)))
read at (4, 36)  ->  ('plan@4:8',)      # the comprehension's target
Python           ->  line 3's plan      # the enclosing binding
```

**Consequence (a) — a genuine Gate-2 collapse goes silent.** Concrete triggering
input, driven through the shipped `_gate_collapses`:

```python
def serve(declared, candidate, batches):
    ops = frozenset(declared.required_operator_keys)
    product = ProductLineage(operators_invoked=ops)
    results = [x for ops in run_gates(candidate, engine_resolved=ops)]
    return results
```

```
6cf00d3 = REJECT      aedf81b = ADMIT      now = ADMIT
control (target renamed to `y`, nothing else changed): REJECT on all three
```

Both sides read line 2's `ops`. It is CR-2's shape exactly, and the module says
nothing. `6cf00d3` — before comprehension bindings existed — gets it right.

**Consequence (b) — red on correct code.** The mirror, through the shipped
`_binder_collapses`:

```python
def serve(pid, r, declared, requirements, wrap):
    plan = FixturePlan(plan_id=pid, required=requirements.required_operator_keys)
    refuse_operator_set_divergence(declared=declared, plan=plan)
    return [row for plan in wrap(ProjectionEngine(reader=r).execute(plan=plan))]
```

```
6cf00d3 = ADMIT       aedf81b = REJECT     now = REJECT
  "probe.py:5: `ProjectionEngine.execute` runs `plan@5:11`, which no
   `refuse_operator_set_divergence` call in this body was handed beforehand."
control (target renamed): ADMIT on all three
multi-line spelling (iterable on its own line): REJECT — not a one-liner artifact
```

The engine runs the **outer** plan, which the binder was handed. The body is
correct and is reported unbound.

**Why this is a Warning and not merely Info.** Three things, each measured:

1. The docstring states the opposite of what the code does, in the load-bearing
   sentence a future maintainer would rely on. `:823-824` — "containment in it is
   exactly Python's scope rule" — and `:1046-1048` — "in force for reads
   **lexically inside** the comprehension … and for no other read." Reads in the
   outermost iterable are *not* lexically inside the comprehension's scope, and
   the module puts the binding in force for them.
2. Neither limits list names it. `:164-170` names the comprehension only as a
   place where **source order is not evaluation order** ("whose outermost
   iterable is evaluated before the element expression written to its left") —
   an *ordering* statement. This is a *scoping* divergence, and the two are
   different: the ordering one costs nothing here, and the scoping one costs a
   verdict in both directions.
3. It is a regression against `6cf00d3` in both directions — the same shape, and
   the same predecessor comparison, as the R4-WR-01 the round just fixed. The new
   test `test_a_comprehension_binds_only_inside_its_own_lexical_span` covers the
   *element expression* (correctly, in comp scope) and expressions *beside* the
   comprehension; it does not cover the outermost iterable, which is the one
   sub-expression inside the node's span that is outside its scope.

**Fix.** Two options; I measured neither as a patch and am not certifying either.

* *Structural.* Narrow `until` — or rather start `position` — past the outermost
  generator's `iter`: in `_binding_records`'s comprehension branch, anchor the
  first generator's target at `_after(node.generators[0].iter)` and leave `until`
  at `_after(node)`. Targets of the second and later generators stay at
  `_at(node)`, since their iterables *are* in comp scope. This is the same
  "anchor past the value" move `_after` already makes everywhere else, and it
  would resolve both bodies above correctly. **Unmeasured** — in particular, I
  did not check the interaction with a walrus in the outermost iterable, which
  binds in the enclosing scope.
* *Minimum honest.* Withdraw "exactly Python's scope rule" from `:823-824` and
  "and for no other read" from `:1046-1048`, add the entry to both limits lists
  with the two measured bodies, add a threat row, and correct
  `15.1-17-SUMMARY.md:204-205` and `:401`. Whichever is chosen, the sentence
  cannot stay as written: a check that claims exactness it does not have is the
  one defect shape this phase has produced in all five rounds.

### IN-04: `_scopes`'s stated imprecision covers a lambda's defaults; the same misattribution applies to a `def`'s decorators and defaults, and it can create an obligation in the wrong body — not only "cannot hide them"

**File:** `tests/products/test_gate_two_call_shape.py:521-525`.

The docstring states one imprecision — "a `lambda`'s *default* argument
expressions are evaluated in the enclosing body … and are counted here as the
lambda's. That misattributes which body they belong to; **it cannot hide them**,
which is the direction that matters." `_scope_nodes` yields a `FunctionDef`'s
`decorator_list` and `args` as part of *that function's* body, so the same holds
for a `def`. Measured:

```python
def serve(pid, r, declared, requirements, register):
    plan = FixturePlan(plan_id=pid, required=requirements.required_operator_keys)
    refuse_operator_set_divergence(declared=declared, plan=plan)
    @register((plan := FixturePlan(plan_id=pid, required=declared.required_operator_keys)))
    def g(): pass
    return ProjectionEngine(reader=r).execute(plan=plan)
```

```
scope serve()   projecting=True   names_binder=True   binder problems: 0  (ADMIT)
scope g()       projecting=True   names_binder=False  -> coverage fires, on g()
```

Python rebinds `plan` in **`serve`**'s scope (decorators evaluate in the
enclosing body), and the engine runs the plan built from the binder's own
`declared=`. The violation is caught — loudly — but as "`g()` must name the
binder", pointing a contributor at the wrong body. And a plan construction in a
`lambda`'s default now makes the *lambda* a projecting body obliged to call the
binder, which is an obligation in a body that did not evaluate the expression:
the imprecision runs in the "false positive" direction too, which the docstring's
"it cannot hide them, which is the direction that matters" does not say.
**Pre-existing for `def`; new for `lambda` this round**, though measured at 0
occurrences in `examples/`. Two clauses in `:521-525`.
