# Phase 15.1 Plan 12: CR-02 and WR-03 — the check that did not look Summary

**Three examples registered an author-versioned class through the path that runs
no D-05 bump check; the test that existed to prevent exactly that asserted over
three keys while its docstring claimed four, and the missing fourth was the one
broken site. All three now take `register_versioned`, the test asserts the four
it names, and it was watched red against the unfixed tree first.**

## Status: COMPLETE — 2/2 tasks

## The defect, stated exactly

`ccf.prompt-artifact` is author-versioned: its contract declares
`artifact_version`, it is a member of `SDK_VERSIONED_ARTIFACT_CLASSES`, and since
plan 15.1-02 a manifest entry declaring `registration: typed` for it is refused
at preflight by `refuse_registration_the_sdk_fixes`. All three examples reached
the refused end state anyway, by calling `registry.register_typed(...)` directly
— which the SDK does not police, by design (the `ccf.` reservation guards the
*manifest* seam, F-7/R-4-adjacent, and is not this plan's to change).

The guard that should have caught it,
`test_the_author_versioned_definitions_kept_their_bump_check`, said in its
docstring *"those **four** keys appear in the audit log under
`register_versioned` and NOT under `register_typed`"* and built a set of
**three**. `prompt_artifact_key` was absent. The one site that had lost its bump
check was the one site the check did not look at — so it passed, and was cited
as ERGO-18 evidence.

## Task 1 — the test, watched red first

failing against the tree that had the defect. `prompt_artifact_key` was confirmed
present in scope (`artifacts/agent-registration.yaml` declares it) before being
asserted on.

## Task 2 — the three sites, and what "correct" was at each

**Every site moved. None had a genuine reason it could not.** The judgment was
made per site, and the three facts that decided it are the same in all three:

1. Each `prompt-artifact.yaml` declares `artifact_version: "1.0.0"` — so
   `register_versioned` has something to verify and will not raise `TypeError`.
2. Each key is registered exactly once per run, so the move introduces no
   refusal on the happy path.
3. Resolution is unaffected: both paths store under `(key, content_hash(...))`
   and append to the same `_versions` list, so the agent definition's axis-6
   versioned-URI ref resolves identically either way.

| `examples/05-workflow-hitl/run.py:411` | `register_typed` | `register_versioned` + refusal check | Already correct — it said the four author-versioned classes take `register_versioned`. The code was what was wrong |
| `examples/06-decision-replay/run.py:661` | `register_typed` | `register_versioned` + refusal check | Said "Five are AUTHOR-VERSIONED (`register_versioned` …)" while one of the five took the other path. True now; header corrected |
| `examples/08-e2e-demo/run.py:959` | `register_typed` | `register_versioned` + refusal check | Explained at length why the bump check matters, then bypassed it. Rewritten |

The old path admits changed content under a claimed version, returns a fresh
content hash, and audits it `resolved=True` — the governance loss, on the real

## A correction to the review: CR-02's reproduction does not hold

The review states the concrete failure as: *"edit
`examples/08-e2e-demo/artifacts/prompt-artifact.yaml`'s `template` without
touching its `artifact_version`, re-run. Under `register_versioned` this returns
`RefuseUnbumpedChange` and nothing is stored."*

**It does not.** Tried it: template edited, `artifact_version` untouched, example
08 re-run — `exit=0`. Each run constructs a fresh in-process
`ControlPlaneRegistry`, so `bumps.get(declared)` is `None` and there is no prior
registration for the D-05 comparison to fire against. The bump check bites in a
Control Plane that outlives a single run, or on a second registration of the same
key within one process (which is what the probe above does) — not on a re-run of
the example.

The finding is correct; its repro is not. Recording that matters here, because
accepting a reproduction that was never run is the same failure mode as accepting
a test that never looked.

## WR-03 — the two docstrings that claimed a power they did not have

Both said the assertion *"is what fires if the driver ever goes back to filling
lineage from `execution`"*. **Verified myself rather than taken on report:**
reverted `examples/00-quickstart/run.py:301` to
`operators_invoked=execution.operators_invoked` and ran both related tests —
`2 passed`. Driver restored with `git checkout HEAD -- <file>` (no `git stash`).

So the claim was false, and no *other* output-level assertion would have caught
it either: `refuse_operator_set_divergence` forces the declared set, the plan's
required set and the engine's invoked set equal before the engine runs, so by the
time there is a product there is only one value to compare against itself. The
reviewer's proposed replacement test has the same property, by their own
admission — so adding it would have repeated the defect rather than closed it.

**No assertion was changed or removed.** Both docstrings now state:

- what the check *is* — a propagation check on Gate 2's postcondition, which
  fails if the driver serves a product other than the one it gated or reports a
  transcription other than the one it gated against;
- what it does **not** catch — the lineage-source reversion, and why no
  output-level assertion could;
- where that reversion *is* guarded — a source-level tripwire over the driver's
  call shape (`tests/products/test_gate_two_call_shape.py`).
