Orientation

Why this one is built first

Every other product in the catalog resolves its anchor through this one, and inherits its contract machinery, its typing decisions and its identity authority hierarchy. A defect here is a defect everywhere.

It is also the product that does not pass its own entry test cleanly — the answer barely changes with who is asking, and it composes two sources with one join rather than assembling across many. It is admitted on a written basis: contract machinery, not assembly merit. That is worth knowing before you read anything else here, because it explains why the interesting parts are the expiry and the refusals rather than the assembly.

What the failure actually is

A CRM lookup returns the same seven fields. What it does not return is a TTL. So the consumer caches the row indefinitely and keeps reasoning about a company whose registration has since lapsed — nobody has revalidated that it still exists as described.

The failure is not a missing signal. It is a missing expiry. That is the whole lesson of Tier 1.

Two details in that payload are the point

Its legal address is Wilmington, Delaware and its headquarters address is Parsippany, New Jersey. Until this estate labelled them, it held one address triple with nothing recording which of the two it was — and an unlabelled address does not fail loudly. A missing address returns nothing and you notice; an unlabelled one returns Wilmington for a company run from Parsippany.

And the debt figure is not decoration. D_c 0.2929 is measured against what the operators actually left standing, delivered inside the answer's content address. A consumer that receives context with no debt signal cannot know what it is trusting.

The silence is the mechanism

The two no answers carry no count, no marker and no notice of what was withheld. That is not a filter being tidy — it is Policy substituting the permissible subgraph for the full graph before anything reads graph state, so there is nothing left to leak a count from. A “1 entity hidden” notice would itself be the disclosure.

Build one

The order to work in

Dependency order, and it is not arbitrary: everything below is derived from something above it. The specification comes first because it is what the rest is checked against — and it was written and approved before any of this code existed, which is what let the build discover where it was wrong.

  1. The specification

    Seven sections in order. It names the contract's nine elements, the data catalog with each element's store and table, the operator recipe, the debt model, the readiness gaps with an owner each, and the acceptance criteria — each phrased so it can fail.

    {{spec}}

  2. The Control Plane document

    The product class, the operator parameters, the request contract, the resolution rules, the half-lives, the debt bands, the policy regime and the default perspective. Everything domain-specific about this product lives here or in artifacts/, and nothing does in the code.

    {{config}}

  3. The backend binding

    How the graph's own storage is composed, and how the system of record is reached — through a variable's name. No host, no port, no credential enters the tree.

    {{backends}}

  4. The four declared artifacts

    The caller's question and its pinned instant; the TTL and its ceiling; the operator recipe with a runtime witness per step; and what the served product should contain.

    {{question}} {{ttl}} {{recipe}} {{expected}}

  5. The interpreter

    Reads every document above and answers what the fabric asks: how to connect, what the question is, what the source read returns, how debt is measured, and how the payload is shaped. It names five table constants and nothing else about the domain.

    {{deployment}}

  6. The spine, the seam and the client

    The spine is the specification's operator table read as code — nine numbered steps, in an order that is not a convenience. The seam conforms to the assembler protocol. The client asks the question.

    {{produce}} {{assembler}} {{run_py}}

  7. The tests, and the README

    Thirteen tests, one per acceptance criterion or product gate, asserted against a run. Every gate has been deliberately broken once and watched fail — a gate never observed red is not evidence that it runs.

    {{tests}} {{readme}}

The half you write

What is yours, and what the fabric already does

The four Python files above are not equal. Two of them are yours to write for every product; two are nearly the same in every deployment and exist to be read once.

The ratio is the honest measure of what adopting this costs: roughly 1,150 lines you write against 660 you read once — and against 870 lines of declared artifacts that carry everything specific. If your code would still run meaningfully with the artifacts deleted, something has been hardcoded that should not have been.

What to change first

Four edits, in the order you will want them

  • To point at your own estate — the variable name in backends.yaml, and the five table constants in deployment.py. Nothing else in the code knows a table name.
  • To serve a different attribute — add it to attribute_keys in the Control Plane document. It flows to the payload, to the completeness measure and to the debt figure in one edit, because all three read that same list.
  • To change who sees what — the entitlement grants in the estate. No code changes at all. That is the test of whether entitlement is really Control Plane state or just a filter someone wrote.
  • To change the expiry — the TTL artifact. Read the note inside it first.

What would fail

Ask for a private borrower and it refuses

run.py --anchor CLI-000101

ttl-bounds: expires_at 2026-02-24T00:00:00+00:00 is outside
            (2026-08-16T12:00:00+00:00, 2026-08-17T12:00:00+00:00]
This is neither a fabric bug nor a data defect

The expiry is that borrower's kyc_last_refresh — months old by design — plus the declared 24-hour TTL. So it lands in the past and the TTL gate refuses on the first call. All 30 no-LEI borrowers are affected, and 27 of the 30 are live under their own declared ceiling.

The contract declares one TTL; the identity hierarchy declares two freshness ceilings. The two do not compose. The specification records it, a test asserts the refusal, and that test is written to go red when the declaration is corrected — so it is the evidence the change gets made on, not a test that ratifies a bug.

Ask as of “now” and everything refuses

The vendor table's retrieved_at is a snapshot load date, so against today's clock all 186 entities are past their expiry. That is the fabric working correctly against a snapshot that is no longer fresh — a fact about the load, not about the assembly.

The snapshot this page reproduces against

Every figure above comes from commit 39e72bd with the question pinned to asked_at 2026-08-16T12:00:00+00:00, producing content address ab2e1a62bf0e5b26c86b3dc122bc77ca4c7e8162ef86510f4a0901224723e9e4 — so the same question returns the same answer, and if your numbers differ you have re-derived rather than replayed.

Three more refusals, each returned rather than thrown

  • An anchor matching neither authority is a 404, never an empty payload. No such company and a company with nothing in it are different answers.
  • A lapsed registration is excluded entirely unless you ask for it — and when you do, the status comes back as a first-class field. The two answers have different content addresses, which is what proves the parameter changed the payload rather than the query.
  • as_of is declared and always refused. It is in the contract so you can discover it, and it fails loudly so nobody relies on it in a dispute.

Honest limits

What this example is not

  • No projection. Everyone authorized gets the same shape. What differs by principal is which companies exist to be shaped, and that is settled by the Policy step, not by conditioning the view.
  • No relationships, no traversal, no second time axis. Identity only — no exposure, no risk grade, no ownership. Five of the eight standard operators are deliberately unused, and the recipe artifact says which and why.
  • One gate has nothing to act on. The gate that refuses an empty served set cannot currently fire, because every principal in the estate sees at least 21 companies. A primitive with no instance in the data reads as machinery without a purpose, so it is recorded as owed rather than quietly passing.
  • The semantic-consistency term is structurally 1. It is meant to catch a vendor record disagreeing with the internal one for the same company — but in this estate no company has both, so nothing could disagree. A clean score that no data could have moved is not evidence of agreement.
  • Two of three half-lives are illustrative. They are publication cadences, not measured decision-relevance curves, and they are labelled that way. A catalog whose half-lives are all illustrative is not calibrated, and saying so plainly is more useful than implying otherwise.
